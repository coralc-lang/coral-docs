Chapter22

Attributes and Compile-Time Metaprogramming

Talking to the Compiler in Its Own Language

You have seen `#[[packed]]` and `#[[inline]]` and nodded without being sure what they did. These bracketed notes are how a Coral programmer talks directly to the compiler, and unlike comments, the compiler reads them.

A comment is for the next human and is discarded early. An attribute is a machine-readable instruction about layout, code generation, safety checking, or scheduling. When you write

    #[[inline]]
    i32 add(i32 a, i32 b) {
        return a + b;
    }

you have handed the compiler a directive. It may decline, but it cannot pretend it did not read it, and it cannot silently accept a typo.

A misspelled `#[[inlne]]` is not ignored. The compiler reports the unknown name and suggests `#[[inline]]`. The difference between silent ignoring and a suggested fix is the difference between a false belief and a one-line repair. The compiler never silently drops an instruction.

A `//` comment is a note for the cleaning staff, swept away before anyone who matters reads it. An attribute is a note on the worker's desk: it is acted on or reported, never pretended away.

Attributes are bracketed lists written above the item they modify:

    #[[name]]
    #[[name(arg1, arg2, ...)]]
    #[[one, two]]
    #[[one]] #[[two]]

The double brackets let the lexer distinguish an attribute from an index expression `a[i]` without lookahead. A single bracket is an index; a double bracket is an annotation.

The chapter has two jobs. First, catalogue every attribute by what it does, with the situation that calls for it. Second, explain the idea underneath: a small fixed set of directives plus the comptime machinery of Chapter 7 gives macro-level metaprogramming without a separate macro language. Coral prefers a directive to a preprocessor.

22.1 The Bracket Forms

There are two attribute shapes.

`#[[name]]` applies to the next declaration, statement, field, or file. A name-only attribute carries no arguments because its meaning is the whole of it; `#[[packed]]` means packed.

`#[[name(arg1, arg2, ...)]]` takes a small list of literals: a string, number, name, or list of names. Which are legal depends on the attribute: `#[[deprecated("use connect_v2 instead")]]`, `#[[align(16)]]`, `#[[generate(Drop, Eq, Debug)]]`, and `#[[cfg(target_os = linux)]]`.

Several attributes can attach to one item. List them in one bracket group separated by commas:

    #[[packed, generate(Eq, Debug)]]

or chain separate groups:

    #[[packed]]
    #[[generate(Eq, Debug)]]

Both mean the same and are read left to right; choose whichever reads better. They may be mixed:

    #[[cfg(target_os = linux), inline]]
    void flushCache();

Attributes must be compatible. Opposite directives cannot share a declaration, and the compiler will not pick a winner. `#[[packed]]` and `#[[reorder]]` are the canonical pair. An incompatible pair is a diagnostic, not a coin flip.

File-level attributes such as `#[[no_drop_all]]` must appear before the first declaration. This is the one place an attribute is not attached to the item directly beneath it.

22.2 Layout: Telling the Compiler What the Bytes Look Like

Some attributes control the exact bytes a value occupies. By default the compiler may insert padding and arrange fields for fast access. That freedom is good until bytes must match a network packet, on-disk record, register map, or C struct.

`#[[packed]]` removes padding and pins declaration order, so size is the sum of fields and bytes lie as written. Use it whenever an external contract specifies the layout:

    #[[packed]]
    struct PacketHeader {
        u8  version;
        u8  flags;
        u16 length;
        u32 checksum;
    }

Without `#[[packed]]`, the compiler might insert two bytes after `flags` and two after `length`; the struct becomes twelve bytes instead of eight, and fields land at wrong offsets. Write it to a socket and the receiver reads nonsense after the first fields.

The common mistake is forgetting `#[[packed]]` on a file-format struct: early fields work because they land naturally, and the first field needing padding breaks. When bytes are fixed by someone else, pack and stop guessing.

Packing costs access speed because unaligned fields are more expensive on some architectures. Pack only structs whose bytes are a public contract; leave the rest to the compiler.

A layout is a public contract when code outside your program, which you cannot change, depends on fixed bytes: a C library header, a 1980s file format, or an RFC protocol. Private structs have no such promise, and the compiler's freedom is free performance.

A shipping box has a fixed order so the receiver can unpack by the label; that is `#[[packed]]`. A garage box can be rearranged; that is `#[[reorder]]`. You cannot promise both.

A TGA header is a fixed sequence of little fields, and one wrong offset corrupts every image:

    #[[packed]]
    struct TgaHeader {
        u8  idLength;
        u8  colorMapType;
        u8  imageType;
        u16 colorMapOrigin;
        u16 colorMapLength;
        u8  colorMapDepth;
        u16 xOrigin;
        u16 yOrigin;
        u16 width;
        u16 height;
    }

Read against the file-format specification, the declaration and the specification are the same thing. Without the attribute, a later two-byte field would land wrong and produce a corrupted image rather than a compiler error.

`#[[reorder]]` grants explicit permission to permute fields for density. It can group small fields and pack a private in-memory struct tighter. It is wrong across a boundary, where field order is unspecified afterward:

    #[[reorder]]
    struct Particle {
        f32  x;
        f32  y;
        f32  vx;
        f32  vy;
        u8   kind;
        bool alive;
    }

Nobody serializes a `Particle`; it lives and dies inside one loop, so shuffling `kind` and `alive` into padding costs nothing and may speed the loop. `packed` says the order is fixed and mine; `reorder` says it is yours and free. Asking for both is a conflicting-attribute error.

`#[[nonull]]` removes a null check. Ordinarily a pointer may be null, so dereferences are guarded and null comparisons are meaningful. The attribute promises a pointer field or variable is never null, letting the compiler drop guards and optimize. Put it on a guaranteed field:

    struct LinkedList {
        #[[nonull]] Node* head;   // past the first insert, head is never null
        usize len;
    }

and on a variable once you know it points somewhere:

    #[[nonull]]
    Device* dev = findDevice("gpu0");
    dev->reset();

A false `#[[nonull]]` promise is undefined behaviour. Use it only where you just checked the pointer or an invariant guarantees it. Leave it off where null is legitimate; an unbacked assertion is worse than none.

`#[[align(N)]]` forces a minimum alignment in bytes. Use it when hardware or an algorithm demands a boundary: SIMD vectors aligned to sixteen or thirty-two bytes, a DMA buffer on a page boundary, or an atomic that must not straddle a cache line:

    #[[align(16)]]
    struct Vec4f {
        f32 x;
        f32 y;
        f32 z;
        f32 w;
    }

    #[[align(64)]]
    f32 accumulator[16];   // one full cache line, aligned

Alignment can only be raised, never lowered, and must be a power of two. `#[[align(3)]]` is an error, not a silent rounding.

The layout family: `packed` and `reorder` answer who decides field order, `nonull` lets the compiler delete a null check, and `align(N)` pins a hardware boundary. All four should be rare enough that seeing one makes a reader ask why.

22.3 Code Generation and Optimisation Hints

Backend attributes do not change meaning, only how code is compiled. The surface is deliberately small because hard-to-reason hints get misused.

`#[[inline]]` hints that a function should be spliced into callers, removing call overhead and exposing the body to optimization. The compiler may decline if inlining would bloat the caller. Small, hot, non-recursive functions are candidates:

    #[[inline]]
    i32 square(i32 x) { return x * x; }

`#[[inline_always]]` overrides the cost model and insists. Use it rarely and with evidence:

    #[[inline_always]]
    u32 maskFor(u32 bit) { return 1u << bit; }

A large `inline_always` function copied into a thousand call sites bloats the binary and instruction cache. Accessors are the classic right use; hundred-line functions are the classic mistake. Reaching for it often usually means the cost model is right and you have not measured.

`#[[vectorise]]` asks the compiler to turn scalar loop operations into packed SIMD. It can apply to a function or one loop:

    #[[vectorise]]
    void addArrays(const f32 a[], const f32 b[], f32 out[]) {
        for (usize i = 0; i < a.len; i += 1) {
            out[i] = a[i] + b[i];
        }
    }

    void mix(f32 a[], f32 b[]) {
        // ... scalar setup ...
        #[[vectorise]]
        for (usize i = 0; i < a.len; i += 1) {
            a[i] = a[i] * b[i];
        }
        // ... other work ...
    }

Attaching it to one loop points the compiler at the vectorizable part and leaves scalar work alone. Vectorization requires independent iterations; if each reads the previous result, the compiler refuses rather than producing wrong results. It is a request, and its payoff depends on target vector instructions.

`#[[hot]]` and `#[[cold]]` control code layout. Processors fetch instructions in blocks, so likely-next instructions should be nearby. `#[[hot]]` marks frequently executed code for speed; `#[[cold]]` marks rare paths (error handlers, failed assertions) for size and distance. The classic pair is a fast path and its error path:

    #[[hot]]
    Result<Order, str> submit(Order o) {
        if (!validate(o)) {
            return reportBadOrder(o);   // the #[[cold]] function below
        }
        return process(o);
    }

    #[[cold]]
    Result<Order, str> reportBadOrder(Order o) {
        logBadOrder(o);
        return Error::Err { .error = "invalid order" };
    }

Marking the error path cold keeps it from crowding the hot path out of the instruction cache. That, not the error path's own speed, is the gain.

`#[[noalias]]` promises a pointer parameter aliases no other pointer the function receives. Without it, the compiler must assume writes through one may change what the other sees, forbidding many reorderings. The attribute can be a large win in numeric inner loops:

    #[[noalias]]
    void scale(f32 out[], const f32 in[], f32 k) {
        for (usize i = 0; i < out.len; i += 1) {
            out[i] = in[i] * k;
        }
    }

Like `nonull`, a false `noalias` is undefined behaviour. Assert it only when buffers genuinely do not overlap: one is freshly allocated, the API contract says so, or the types make overlap impossible. Otherwise leave it off.

`#[[noreturn]]` tells the compiler a function never returns normally: it exits, loops forever, or transfers control elsewhere. Code after the call is unreachable and need not be generated:

    #[[noreturn]]
    void fatal(str message) {
        eprintln("fatal: {}", message);
        exit(1);
    }

Without it, a function that always calls `exit` appears to return, so the compiler generates code for whatever follows. With it, the compiler can also reject a `#[[noreturn]]` function that might return.

`#[[no_mangle]]` keeps a function's symbol name instead of mangling it with type information. Use it wherever something outside Coral finds a function by name: a C callback, exported shared-object function, or entry symbol:

    #[[no_mangle]]
    pub extern("C") i32 coral_entry(i32 argc, cchar** argv) {
        return runMain(argc, argv);
    }

Without it, the linker looks for `coral_entry` and finds `coral_entry_i32_...`, and the link fails with an unexplainable symbol. The attribute says the name is not the compiler's to rewrite.

`#[[section("...")]]` places a function, variable, or data in a named output section, for when the loader decides placement: a startup constructor table, read-only data, or a boot function at a fixed address:

    #[[section(".init_array")]]
    void registerDrivers() { drivers.addAll(BUILTIN_DRIVERS); }

    #[[section(".rodata")]]
    const u8 MAGIC[8] = { 'C', 'O', 'R', 'A', 'L', 0, 0, 0 };

The section name is a string because the linker understands it, not Coral. A wrong name is a link-time problem, which is why the attribute takes an opaque string.

`#[[used]]` keeps a symbol the compiler believes unreferenced. A symbol in a runtime-scanned section, or one called by external code, is referenced by something the compiler cannot see:

    #[[used]]
    #[[section(".init_array")]]
    void earlyInit() { ... }

`used` and `section` often travel together. A driver registrar in `.init_array` is called by the loader, not by Coral, so without `#[[used]]` the compiler would delete it and the driver would never register.

`#[[weak]]` gives a symbol weak linkage, so a strong definition elsewhere can override it. A library can provide a replaceable default allocator, panic handler, or platform hook:

    #[[weak]]
    void platformLog(str message) {
        eprintln("{}", message);
    }

A strong `platformLog` wins; otherwise the weak default is used. This is "here is a reasonable default, override me if you know better," and it keeps a platform layer optional.

22.4 The Drop Attributes: Opting Out of RAII

Two attributes change behaviour rather than performance, and they require understanding `@drop`. Coral implements RAII through `@drop`: when a value of a type implementing it goes out of scope, the compiler inserts the destructor once on every exit path. Most code wants this.

Automatic cleanup costs tracking and unwind calls, and some code manages memory by hand. The standard library does exactly that, so two attributes turn automatic RAII off at two scopes.

`#[[no_drop_all]]` is file-level and unique in not modifying a declaration. It appears once before the first declaration and disables drop-trait RAII for the whole file:

    #[[no_drop_all]]

    pub struct Arr<T, N> { ... }

Every standard-library and compiler source file carries it; ordinary user files omit it and get automatic RAII. This lets library and application worlds coexist. The opt-out rides on each declaration, so a library file merged into a user build unit keeps its setting.

`#[[no_drop]]` is the scoped version and the one you will use. On a variable it excludes that variable from RAII; on a block it excludes every local inside, nested blocks included:

    #[[no_drop]]
    String keep = String::from("I manage my own lifetime");

    #[[no_drop]]
    {
        File f = File::open("tmp");
        // f is not closed automatically at the end of this block
    }

It is the escape hatch for one value whose lifetime you manage by hand without disabling RAII for the file. With `defer` it says the allocation's lifetime is not the variable's. Used carelessly it says "I will remember to free this," and humans forget. Opting out turns cleanup into a manual obligation; use it only where nothing else will do.

A worked example shows the narrow honest use:

    void processInChunks(File* f) {
        #[[no_drop]]
        u8* buffer = alloc<u8>(65536);       // manual lifetime

        defer {
            dealloc<u8>(buffer);
        }

        while (true) {
            usize n = readChunk(f, buffer, 65536);
            if (n == 0) break;
            handle(buffer, n);
        }
    }

The buffer opts out because its lifetime is managed by `defer`, not by RAII on the variable. The attribute turns off automatic behavior for exactly this value, and the `defer` is the manual promise. A buffer that lives exactly as long as its variable should have no attribute.

22.5 Const and Control-Flow Attributes

Three attributes govern behavior promises and control flow. Each replaces a convention with compiler enforcement.

`#[[const]]` marks a method or function as const: it may not mutate parameters or, for a method, `self`. It is equivalent to trailing `const`, and both spellings work:

    #[[const]]
    i32 peek() { return self.top; }

    // identical meaning
    i32 peek() const { return self.top; }

Pick one spelling and be consistent; the promise is enforced either way. Mutating `self` or a parameter in a const method is E1001, reported at the assignment, not at a caller's surprise.

`#[[condassign]]` permits an assignment `=` at the top level of the next `if`, `while`, `for`, or `switch` condition:

    #[[condassign]]
    while (line = nextLine(file)) {
        process(line);
    }

An assignment in a condition is normally reported because `=` where `==` was meant is an old C bug. The attribute says "I meant it," as in a read-and-test loop. A real typo still errors. The attribute applies to the next statement's condition, not the body.

`#[[fallthrough]]` marks intentional fallthrough in a switch. Coral cases do not fall through by default; to share a tail, list both patterns on one arm or opt in:

    switch (mode) {
        Mode::Initialize => {
            setup();
            #[[fallthrough]]
        }
        Mode::Run => {
            run();
        }
        else => {},
    }

The attribute on the last statement of an arm tells compiler and reader that continuation is intended. Without it the compiler warns. Putting `#[[fallthrough]]` on the last arm, with nothing to fall into, is E0610, usually a copy-paste leftover. When two cases share a body, `|` on one arm is usually clearer.

22.6 Extending and Sealing

Two attributes control whether a type may be grown later, connecting to the trait and extend machinery of Chapter 6. `#[[extend]]` permits extend blocks; `#[[no_extend]]` forbids them.

The ordinary case needs no attribute: a type is open by default. Explicit `#[[extend]]` is mostly redundant, for symmetry or to make openness clear:

    #[[extend]]
    struct Logger {
        i32 level;
    }

`#[[no_extend]]` is the interesting half. A sealed type cannot gain methods from later extend blocks:

    #[[no_extend]]
    struct Sealed {
        i32 hidden;
    }

This lets a library seal a type so its behavior is exactly the methods it ships. A sealed type promises a closed interface: no third party can add a method, change an operation's meaning, or bolt on an unintended conversion. Sealing suits invariants that must not be circumvented: opaque handles, fixed state machines, security tokens. Most types want to be open, so sealing should require a deliberate annotation.

22.7 Generate: Boilerplate That Writes Itself

`#[[generate(...)]]` takes derived capabilities and writes their trait implementations and boilerplate from the field list:

    #[[generate(Drop, Eq, Debug, Clone)]]
    struct Player {
        str name;
        i32 score;
    }

`Drop` frees fields. `Eq` compares field by field. `Debug` formats a named structure. `Clone` copies fields. `Ord` compares in declaration order. Adding a field is handled in one place, the declaration, and generated implementations stay in sync.

These implementations are repetitive and hide bugs: a hand-written `Eq` that forgets a field, or a `Debug` that prints the wrong field, wastes an afternoon. The generator cannot forget or confuse fields because it reads them.

Coral's answer to boilerplate without a macro system is a fixed, compiler-known set of derives. A general macro can write anything, including unreadable code; a fixed list writes only mechanical things. You cannot invent a derive, but every derive is familiar and predictable.

Not every derive suits every type, and the attribute will not stop a bad request. `Drop` on a type with no owned resources is a no-op. `Clone` on a file handle copies the handle, so both values think they own the same file. `Eq` on floats compares exact equality, which Chapter 2 warned against. Derive what the type genuinely has, not what is convenient to type.

`#[[generate]]` keeps behavior from drifting from fields: add a field and generated `Eq`, `Debug`, and `Clone` already know it. The common mistake is deriving `Clone` on a resource-owning type and creating two owners.

22.8 Tooling, Platform, and the Entry Point

The final family configures building, testing, and starting. Each connects source to something outside it.

`#[[deprecated("...")]]` marks an item deprecated and names a replacement at each use:

    #[[deprecated("use connect_v2(host, port) instead")]
    pub Socket connect(str host) {
        return connect_v2(host, 80);
    }

Calling it warns with E0805 at the call site, quoting the replacement. One line turns a silent breaking change into a guided migration.

`#[[threadlocal]]` gives a static per-thread storage, so each thread sees its own copy. Use it for state that must not be shared: an error code, scratch buffer, or random seed:

    #[[threadlocal]]
    static ErrorCode lastError = ErrorCode::Ok;

Each thread has its own `lastError`, so one thread's failure cannot corrupt another's. Without the attribute, the static is shared and writes race.

`#[[test]]` and `#[[bench]]` mark functions for the test and benchmark runners:

    #[[test]]
    void testAddition() {
        @assert(square(3) == 9);
    }

    #[[bench]]
    void benchHash() {
        // the runner times this function
    }

There is no registration list or test framework configuration; the attribute is the registration. A file of `#[[test]]` functions is a test suite.

`#[[cfg(...)]]` guards an item with a compile-time condition, so platform-specific code sits next to portable code and only the current target compiles:

    #[[cfg(target_os = linux)]]
    void openSerial(str path) { /* termios setup */ }

    #[[cfg(target_os = windows)]]
    void openSerial(str path) { /* COM port setup */ }

    #[[cfg(target_os = linux, feature = "tls")]]
    void startTls(Socket* s) { ... }

The condition is evaluated at build configuration. A false declaration is absent from the program, as if never written. This is the single-source-tree-many-platforms mechanism at item level, and it prevents the two `openSerial` definitions from colliding.

`#[[link("...")]]` names a library to link. Where `extern` says a function exists, `link` says where to find it:

    #[[link("m")]
    pub extern f64 sqrt(f64 x);

The string goes to the linker, so `#[[link("m")]]` links the math library like `-lm`. The instruction lives next to the declaration that needs it, so they cannot drift apart.

`#[[simd]]` marks a type or operation as SIMD-intended, telling the compiler it may use the widest vector instructions. It pairs with `#[[vectorise]]`: `simd` says what the data is for, `vectorise` says how to generate the loop:

    #[[simd]]
    struct Vec4f {
        f32 x; f32 y; f32 z; f32 w;
    }

    #[[simd]]
    Vec4f add(Vec4f a, Vec4f b) {
        return Vec4f {
            .x = a.x + b.x, .y = a.y + b.y,
            .z = a.z + b.z, .w = a.w + b.w,
        };
    }

`#[[entry]]` names the start function when `main` is not it. A bare-metal program, kernel, or freestanding binary has no OS to call `main`, and the entry takes the form the hardware uses:

    #[[entry]]
    #[[section(".text.boot")]
    void _start() {
        initialiseHardware();
        kmain();
        // never returns
    }

On a hosted target `main` remains the entry and `#[[entry]]` is unnecessary; on a freestanding target it tells the compiler where the image begins.

Platform and tooling attributes all connect source to an outside thing: a platform, build feature, library, test runner, or linker. They cluster at a file's top and tell you what world it expects.

22.9 Unknown, Duplicate, and Conflicting Attributes

Attributes are instructions; a misspelled, repeated, or contradictory one must never be quietly dropped. Three diagnostics enforce this.

An unknown attribute is E0806, with a nearest-name suggestion:

    #[[inlne]]
    // warning E0806: unknown attribute `inlne`; did you mean `#[[inline]]`?

A silently ignored typo is the worst outcome: the programmer believes an optimization happened. Reporting the unknown name and suggesting a close match turns a silent no-op into a one-line fix.

A duplicate attribute is E0807. `#[[packed]] #[[packed]]`, or two spellings of one policy, is usually a copy-paste artifact, and the compiler says so.

A conflicting pair is a separate error. `#[[packed]]` with `#[[reorder]]`, or `#[[align(4)]]` with `#[[align(8)]]`, cannot both be true, and the compiler refuses to choose. An annotation that cannot be honored is worse than none because it teaches a reader something false.

There is deliberately no `#[[pub]]`. Visibility is a keyword, `pub`, part of the declaration, and the only way to export an item (Chapter 14). A second spelling would give the language two ways to disagree with itself.

An attribute is a sentence to the compiler, which must either act on it or say it could not. That is why misspellings are reported rather than ignored.

22.10 A Worked Example: A Network Packet

A network packet needs several attributes at once: fixed wire layout, printable debugging, and comparable values for tests:

    #[[packed]]
    #[[generate(Debug, Eq)]]
    pub struct PacketHeader {
        u16 magic;
        u8  version;
        u8  flags;
        u32 sequence;
        u32 length;
    }

Three attributes, three jobs. `#[[packed]]` guarantees the wire layout, so bytes match the protocol and the struct is exactly twelve bytes. `#[[generate(Debug)]]` names each field in logs. `#[[generate(Eq)]]` gives field-by-field comparison for tests.

`packed` has consequences beyond convenience because the header's layout is a contract. Seeing it tells a reader why the struct looks as it does and that it must not be reordered. The attribute informs reader and compiler alike, which is the best argument for attributes over conventions. A private in-memory version might use `#[[reorder]]` instead, telling the reader nobody promised these bytes anything.

22.11 A Second Worked Example: A Bare-Metal Boot File

The opposite end is a firmware entry file, where almost every platform attribute appears at once. It runs before any OS, so it chooses its own entry, memory placement, and defaults:

    #[[no_drop_all]]

    #[[entry]]
    #[[section(".text.boot")]]
    #[[noreturn]]
    #[[no_mangle]]
    void _start() {
        clearBss();
        initUart();
        kmain();
        loop {}
    }

    #[[packed]]
    #[[align(16)]]
    struct BootInfo {
        u32 magic;
        u16 version;
        u64 loadAddr;
    }

    #[[weak]]
    void platformLog(str message) {
        uartWrite(message);
    }

`#[[no_drop_all]]` disables RAII for firmware with a fixed static pool and no allocator. `#[[entry]]` names `_start` as the image start. `#[[section(".text.boot")]]` places it where the bootloader jumps. `#[[noreturn]]` says `_start` never returns. `#[[no_mangle]]` keeps `_start` findable by the reset vector. `#[[packed]]` fixes the layout the bootloader writes, and `#[[align(16)]]` promises its alignment. `#[[weak]]` gives `platformLog` a default that a larger image can override.

Eight attributes in one small file, each doing a job the declaration alone cannot express. Expect this density in hardware-facing code: the more you depend on things outside, the more compiler assumptions you must correct explicitly.

22.12 The Metaprogramming Bargain

The catalogue is only half the chapter; the other half is the trade it rests on.

Most languages that want metaprogramming grow a macro system. C's preprocessor is powerful and hard to debug; hygienic macro systems have their own syntax, scoping, and errors, so learning the language means learning two. A general macro language can express anything, including code no reader can follow, and its errors concern expansion rather than your program.

Coral offers two things instead: the fixed attribute set above, a small closed list every reader can know, and comptime from Chapter 7, ordinary Coral evaluated during the build that can compute values, select type parameters, and reject unsupported instantiations with `@compileError`. Comptime is the language you already know, run early.

It buys legibility: `#[[packed]]` has a short, public list of possible meanings, and comptime code is Coral, not a macro dialect. It buys error quality: a comptime mistake gets a code and location, not a wall of expansion output.

It costs reach. You cannot write a new attribute, invent a derive, or generate boilerplate the compiler was not told about. If you want a macro, the answer is usually comptime, and if even that will not do, the compiler's contributors can add an attribute deliberately rather than every program growing a private dialect.

The bargain matches Coral's restraint: a closed vocabulary learnable in an afternoon plus ordinary code run early. You cannot always make the compiler do something new, but every Coral program speaks the same dialect and a reader can understand all of it.

The whole set, sorted by target. Everything here is real and honored, not a planned slot.

    #[[used]]                 function, data           keep the symbol even if unreferenced
    #[[weak]]                 function, data           weak linkage; allow a strong override
    #[[no_drop_all]]          file (before decls)      disable RAII for the whole file
    #[[no_drop]]              variable, block          exclude a local (or a block) from RAII
    #[[const]]                function, method         forbid mutation of params and self
    #[[condassign]]           next statement           permit `=` in the next condition
    #[[fallthrough]]          statement in a switch    mark an intended fallthrough
    #[[extend]]               type                     permit extend blocks (the default)
    #[[no_extend]]            type                     seal the type against extend blocks
    #[[generate(...)]]        type (usually struct)    derive Drop, Eq, Debug, Clone, Ord, ...
    #[[deprecated("msg")]]    any item                 warn at each use, naming the replacement
    #[[threadlocal]]          static variable          give the static per-thread storage
    #[[test]]                 function                 register with the test runner
    #[[bench]]                function                 register with the benchmark runner
    #[[cfg(...)]]             any item                 compile only when the condition holds
    #[[link("lib")]]          extern declaration       name a library to link against
    #[[entry]]                function                 name a program entry other than main

Forms that apply to every row:

    #[[a]]                 one attribute
    #[[a, b]]              several in one group
    #[[a]] #[[b]]          several as chained groups
    #[[a(arg)]]            one with arguments
    #[[a, b(arg)]]         a group mixing both

Chainable where compatible; `packed` and `reorder` are the canonical incompatible pair. Everything else composes, and contradictions are reported. The one deliberate absence is `#[[pub]]`, because `pub` is a keyword.

22.14 Exercises

1. Comprehension. Explain to someone who knows only comments why an attribute is not a comment. Give one thing the compiler can do with `#[[packed]]` that it cannot do with `// packed`.

2. Comprehension. `#[[packed]]` and `#[[reorder]]` are mutually exclusive. Describe a struct where each is right and the other is a bug, and what the compiler says if you write both.

3. Implementation. Write a `#[[packed]]` struct for a three-byte record (type, length, value). Assert its size is three, remove the attribute, and predict the new size on a four-byte-aligned target.

4. Layout. Declare an `#[[align(32)]]` SIMD buffer and a `#[[nonull]]` pointer field whose container invariant guarantees it points somewhere. Explain what goes wrong if the invariant breaks.

5. Codegen. Mark a tiny accessor `#[[inline_always]]` and a large error handler `#[[cold]]`. Explain each choice and one cost of choosing wrong.

6. Vectorisation. Write a loop `#[[vectorise]]` can vectorize and one it cannot. Explain the difference and what the compiler does when it declines.

7. Drop. Write a function that allocates with `#[[no_drop]]` and frees with `defer`, then rewrite it with RAII. Which would a reader prefer here?

8. Sealing. Declare a `#[[no_extend]]` opaque handle with a private field and one public accessor. Why seal it, and what does the caller lose?

9. Derives. Put `#[[generate(Eq, Debug, Clone)]]` on a four-field struct, add a fifth field, and confirm the derives still agree. Name one capability you deliberately did not derive and why.

10. Tooling. Mark a function `#[[deprecated]]`, call it, and write down the warning. Then mark two platform versions with `#[[cfg(target_os = ...)]]` and explain what each build sees.

11. Meta. Coral uses a fixed attribute set plus comptime rather than macros. Argue for and against, naming one thing a macro could do that this cannot and one bug class the fixed set prevents.

12. Design. You are writing a plugin loader. Using only these attributes, describe how to place each plugin registration in a section, keep it from being stripped, let a program override a default implementation, and set the entry point.
