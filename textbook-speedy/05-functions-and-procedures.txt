Chapter5: Functions & Procedures

5.1 Functions as the Building Blocks

A program is like a recipe book divided into named recipes, which call smaller named steps. A function is that division applied to code: a named, callable unit that takes inputs, does work, and returns a result.

Everything in a Coral program happens inside functions: the entry point, the standard library, and your own composition of functions. This chapter covers declaration, argument passing, return values, and composition.

A function's signature is explicit, its types visible, and no hidden machinery sits in a call. Between call and body there is nothing but a jump. A Coral function is a C function made safer by types and more expressive by generics, methods, and traits.

Functions come in many shapes: plain, generic, variadic, methods, static methods, and extern declarations. They share the same syntax and rules, and all follow type-first: the type comes first.

5.2 Declaration

A function declaration states the name, parameters and types, and return type. The return type comes first, then the name, parameter list, and body.

    u64 countLines(str text)
    {
        u64 lines = 1;
        for (u64 i = 0; i < text.len; i++)
            if (text.ptr[i] == '\n') lines++;
        return lines;
    }

Read this as "a u64 called countLines that takes a str." Everything before the name is the answer's type; everything in parentheses is what you hand it.

The return type leads, so the reader does not search the body to learn what the function produces. A call to countLines returns something storable in a u64.

`u64 lines = 1;` starts at one because "number of lines" is one more than the number of newline separators; the last line need not end with a newline. This is easier than special-casing trailing newlines.

The loop is the plain for from the control-flow chapter: `u64 i = 0;` initializes the counter, `i < text.len` is the run condition, and `i++` steps it. `text.ptr[i]` reads the i-th character. A str is a pointer and a length: `.ptr` is the characters and `.len` is how many. The loop compares each byte to a newline.

The declaration says everything: a string view in, a count out, before the body.

A function returning nothing uses void. It prints, modifies, or releases something, and the compiler rejects any attempt to use its result. void means no value, not an unknown kind.

    void printGreeting(str name)
    {
        println("Hello, {}!", name);
    }

println takes a format string and one argument per {} placeholder, so name fills the placeholder and a newline is appended. Parameters are the function's inputs and are local variables initialized from the arguments. A parameter is a fresh copy, not a reference to the caller's variable (5.6).

5.3 Generic Function Syntax

Generic functions work for many types. They introduce type parameters in angle brackets, available in the parameter list, return type, and body.

    pub T max<T>(T a, T b)
    {
        if (a > b) return a;
        return b;
    }

Without generics you would write maxU64, maxI64, maxF64, and so on, one copy per type, and a new type would need library edits. The generic version works for any type supporting `>`.

The generic form is type-first, with type parameters in angle brackets after the name. The return type may use them: here it is T. The promise is "max of T and T returns T." Type parameters are placeholders: calling with u64 substitutes u64 everywhere and produces a specialized function. This is specialization (5.29), the key to fast generics.

For C programmers: this is not `_Generic` dispatch among enumerated branches, and not C++ template text manipulation. It is a language feature with real syntax and checking against your actual type.

Generics are central to the library: filter, map, and reduce; Option and Result; smart pointers; and every container (Vec<T>, Deque<T>, Map<K,V>). They avoid both code duplication and runtime boxing.

5.4 Invocation

A call writes the function's name followed by a parenthesized argument list. Arguments are evaluated, matched to parameters in order, and the function runs.

    u64 n = countLines(doc);

A call is how you use a function: name it, supply the values, and the return value flows back. Return values are usually stored or used immediately.

The call must match the declaration: the right number of arguments and each of the declared type. A mismatch is a compile error, checked before the program runs.

A call is an expression, so it can be assigned, passed, composed, or returned. This makes small functions composable: `process(build())` threads a value without a temporary.

A pipeline on one line when each step is short:

    u64 averageBytes = mean(fetchAllocations());   // build, then summarize, in one line

The call reads inside out: fetchAllocations produces a vector, mean consumes it, and a u64 lands in the variable. No intermediate needs a name because the signatures are visible. When a line stops reading clearly, name the temporary.

A call pushes arguments, jumps, and returns, roughly three things. The compiler knows the cost and may inline small hot functions, but the language never hides the call. For a guarantee that it costs nothing, use inline.

5.5 Inline Functions

An inline function is expanded at each call site: the body is copied where the call is, with arguments substituted. The #[[inline]] attribute marks it.

    #[[inline]] void criticalEnter()
    {
        flag (arch) {
        x86_64 => {
            asm { cli }
        },
        else => {
            ...
        }
        }
    }

The bare-metal critical-section functions are the canonical example. criticalEnter disables interrupts and criticalExit re-enables them, and the body is a few machine instructions. A real call would add push, jump, and return around them.

The attribute states intent where expansion matters. The critical-section functions must be inline because they bracket an operation at the instruction level: between disable and enable there should be only the instructions the author wrote. A call would add call machinery inside the critical section.

Inlining is a trade. Without the attribute, the compiler decides from its cost model. The attribute is the explicit statement that a function must be inlined, reserved for cases where expansion is essential, like interrupt bracketing. Application code rarely needs it.

5.6 Parameter Passing

Coral passes parameters by value. Each parameter is a copy of the argument: the function gets its own variable, and modifying it does not modify the caller's.

    void increment(u64 x)
    {
        x += 1;   // modifies the copy, not the caller's variable
    }

    u64 counter = 40;
    increment(counter);          // counter is still 40
    println("{}", counter);      // prints 40

The function cannot see counter. It has a local x initialized to 40, increments it to 41, and discards it; counter is untouched. This is C's behavior, simple, predictable, and fast: a function cannot corrupt caller data through parameters because it only has copies.

Passing by value is like photocopying a page: the function can scribble on its copy and your original is untouched.

The copy cost is real for large values. A 100-byte struct parameter copies 100 bytes. There is no hidden "pass a pointer because this is big" optimization, so Coral has one model: value means copy.

The cost is visible when a struct grows. Passing a value and passing a pointer differ by kilobytes of copying versus one address:

    struct BigBuf { u8 data[2048]; }

    void touch(BigBuf b)         { b.data[0] = 1; }   // copies 2048 bytes on the call
    void touchPtr(BigBuf* b)     { b->data[0] = 1; }  // copies one address

The first version copies two kilobytes and modifies only its copy, a silent no-op to the caller. The second pays an address and changes the caller's buffer. The star is the memo that the caller's memory is involved. For large read-only structs, a pointer avoids the copy.

When a function must modify the caller's data or copying is expensive, the caller passes a pointer. The pointer parameter gives access to the caller's memory, and the star makes the aliasing visible in both signature and call.

Passing a value is like handing over a photocopy; passing a pointer is like giving the address of the original. The star warns: "I may change your data." Ask whether the function should change the caller's value: if yes, pass a pointer; if no, pass the value.

    void readLine(str* out, Buffer* buf)
    {
        str line = extractLine(buf);
        *out = line;
    }

This is by-reference behavior expressed through the type system, not a hidden mechanism. There is no pass-by-reference keyword because the pointer is the mechanism. The stars show what the function can touch: out is where an answer goes, buf is where it is read from.

A swap needs pointers because exchanging requires reaching the caller's variables:

    void swap(u64* a, u64* b)
    {
        u64 tmp = *a;
        *a = *b;
        *b = tmp;
    }

    Vec<u64> x = Vec<u64>::withCap(2);
    x.push(20);
    x.push(40);
    swap(&x.data[0], &x.data[1]);   // x is now [40, 20]

The call passes addresses, and the function modifies the vector's elements. Had swap taken values, it would have exchanged copies and left the caller's elements untouched, a failure invisible at the call site.

Coral avoids exotic parameter modes: no copy-restore with its hidden write-back, no call-by-name with re-evaluation. It passes values or pointers, both visible. Ask whether the function should change the value; that resolves most confusion.

5.7 Parameter Lists and Arguments

The parameter list is a fixed sequence of typed parameters, matched positionally. There are no default parameters and no named arguments: every call supplies every argument, and position carries the meaning.

This simplicity means one signature per function. You never check which arguments are optional or what a name means in the current call. The cost is no convenient subset; the gain is that every call states its arguments in full.

The library works comfortably under this rule. Vec<T>::withCap(usize capacity) has no optional variant; if you want pre-filled storage you build it yourself. A few extra arguments buy signatures that always say everything.

There are no spread or splat operators. Variadic calls are checked per call and written out. To pass a collection, pass it as a vector or array and iterate; unpacking is an explicit loop or slice.

5.8 Variadic Functions

A variadic function accepts any number of trailing arguments. Coral ends the parameter list with a value pack, `... args`, which collects them into a typed, indexable pack.

    pub void vaprint(... args)
    {
        for (var arg : args) _fprintOne(&out, arg);
    }

This is the standard library's vaprint from std/io/ios.crl. The pack keeps each argument's type. The body iterates it with the ranged for and hands each to _fprintOne. (println and print use format strings; vaprint takes values with no format string.)

The call sites show the flexibility:

    vaprint(a, b, c, d);
    vaprint("value", x);
    vaprint("done");

Each call has a different argument count, and the compiler instantiates the function per call. Each argument must be printable, and the function fails to compile otherwise. Generality is checked per call, at the call site, not at runtime.

C's printf-style variadic is an untyped blob reinterpreted by the callee, so a format mismatch is a runtime error. Coral's value pack carries each argument's type into the body and the compiler checks them.

Coral's variadics are not dynamic. The pack is a typed collection of distinct typed values, and there is no runtime way to splat a vector into a call; the pack is a compile-time concept.

5.9 Return Values

return evaluates its expression and returns it to the caller, exiting the function. The value's type must match the declared return type, checked at every return.

`return` hands back a value and stops the function. A function that declares a return type but misses a path is a compile error, not a runtime surprise.

A void function exits with a bare return or by reaching the end. A typed function must return a value on every path, checked by the compiler. There are no implicit returns: the value that comes out is the one a return named.

A function returns a single value. When work produces several related values, return a type that carries them. The library defines Pair for two named values:

    pub struct Pair<T, U>
    {
        T first;
        U second;
    }

A function producing a minimum and maximum, or a value and a flag, returns a Pair. Named fields carry meaning an unnamed tuple would not. Coral has no tuple types: unnamed aggregates carry values without saying what they mean. A struct names all of it.

A Pair-carrying function finding both the smallest and largest value in one pass:

    pub Pair<u64, u64> minMax(const Vec<u64>* v)
    {
        Pair<u64, u64> out;
        out.first = 0xffffffffffffffff;
        out.second = 0;
        for (u64 i = 0; i < v->count(); i++)
        {
            u64 val = v->at(i);
            if (val < out.first)  out.first = val;
            if (val > out.second) out.second = val;
        }
        return out;
    }

The function walks the vector once, tracking the smallest in out.first and the largest in out.second. The caller reads them by name, with no ambiguity.

The single-return rule composes with error types. A fallible function returns a Result; a function whose answer may be absent returns an Option. Both are single values carrying the outcome, making every return complete.

The library's rule: Result for "this is an error and here is what kind," Option for "this value may simply not exist."

5.10 The Noreturn Function

A small class of functions never returns. The #[[noreturn]] attribute declares it in the signature.

    #[[noreturn]] extern void exit(i32 code);

exit terminates the program and does not come back. The compiler can rely on the attribute: after a noreturn call, code is unreachable, so following code that cannot be reached is an error.

This is type-first philosophy: the signature says not only what is produced but that the call never returns. It is used for process termination, startup handoff, and abort paths.

A common use is early-error paths. If a program cannot start without its config, the loader has no sensible value to return:

    #[[noreturn]] void die(str why)
    {
        eprintln("fatal: {}", why);
        flag (platform) {
        wasm => {
            abort();
        },
        else => {
            exit(1);
        }
        }
    }

Callers write if (!loadConfig()) die("no config"), and the compiler knows normal flow ends there. This removes a class of bugs where a program continues after deciding to die and crashes confusingly later.

5.11 Scope

The scope of a name is where it is visible. Coral uses lexical scope: a name is visible from declaration to the end of its block, and inner blocks see outer names.

    void process(Buffer* b)
    {
        u64 total = 0;
        for (u64 i = 0; i < b->len; i++)
        {
            u64 value = b->ptr[i];
            total += value;
        }
        // total is visible here; i and value are not
    }

total is visible throughout the function body. i and value are declared in the loop and visible only there. Each name's scope is exactly its declaring block.

This is C's scoping, inherited directly. The consequence for function design is that scope is pure text: you can determine what a name refers to by where it appears, not by who called the function.

The alternative, dynamic scope, resolves names against the calling context, so a name's meaning changes with the caller. That makes a name unknowable without the call stack and lets a correct function break with a new caller. Lexical scope makes every name mean what the text says.

A function is a sealed unit: its parameters and locals are its own, and name resolution is fixed by the text. It can be moved, renamed, or called anywhere with unchanged behavior. That is what makes functions building blocks.

5.12 Local Variables

A function's locals are the variables it declares, and their lifetime is tied to its execution. Each comes into being at its declaration, is initialized there, and dies when the function exits.

    u64 scan(str text, u8 target)
    {
        u64 count = 0;
        for (u64 i = 0; i < text.len; i++)
        {
            u8 c = text.ptr[i];
            if (c == target) count++;
        }
        return count;
    }

count exists for the whole body, initialized to zero. c exists for one iteration, initialized to the current character. Initialization is part of the declaration; a local is never uninitialized, because a declaration without a value is an explicit placeholder to fill before use, and the compiler checks it.

A local's lifetime is its scope. Storage is reclaimed at scope exit, and a pointer to a local is meaningful only inside it. Returning a pointer to a local names storage that is gone, and the failure appears at first use. The library documents that returned pointers are valid only while the container lives. A local with @drop is released at scope end, once, on every exit path.

5.13 Higher-Order Functions

A higher-order function takes a function as an argument or returns one. Coral supports them through function pointers, and the library is full of them.

Passing a function is like passing data: the caller supplies behavior instead of the function knowing what to do with each element.

A function type is a declaration without the name: return type and parameter types. Collection operations take predicates and transformations as function-type parameters.

    pub Vec<T> filter<T>(const Vec<T>* v, bool(T) pred)

pred has type bool(T): a function taking a T and returning a bool. filter calls it on each element and keeps those that return true. The caller says what filtering means for the collection:

    Vec<u32> nums = Vec<u32>::new();
    nums.push(1); nums.push(2); nums.push(3); nums.push(4);

    bool isEven(u32 n) { return (n & 1) == 0; }

    Vec<u32> evens = iter::filter(&nums, isEven);          // [2, 4]
    Vec<str> words = Vec<str>::new();
    words.push("a");
    words.push("the");
    words.push("of");
    words.push("program");
    words.push("side");

    bool isShort(str w) { return w.len <= 2; }
    Vec<str> short = iter::filter(&words, isShort);    // [a, the, of]

Each caller passes a different predicate, and filter behaves accordingly. The iter module follows the same pattern: map, filter, reduce, forEach, any, all, find, and countIf all separate the walk from the operation's meaning.

    pub Vec<U> map<T, U>(const Vec<T>* v, U(T) fn)
    pub T reduce<T>(const Vec<T>* v, T init, T(T, T) fn)

map takes a transformation and returns a new collection; reduce takes a combining function and folds to one value. These are the functional operations other languages advertise, implemented with the same explicit loops as everything else.

The whole trio on one example: convert Celsius temperatures to Fahrenheit, then total them.

    Vec<f64> celsius = Vec<f64>::new();
    celsius.push(0.0); celsius.push(20.0); celsius.push(37.0); celsius.push(100.0);

    f64 toF(f64 c) { return c * 9.0 / 5.0 + 32.0; }
    f64 addF(f64 a, f64 b) { return a + b; }

    Vec<f64> fahr = iter::map(&celsius, toF);        // [32, 68, 98.6, 212]
    f64 total = iter::reduce(&fahr, 0.0, addF);      // 410.6
    f64 avg = total / fahr.count();                  // 102.65
    println("average: {}", avg);

Three operations, three calls, the same shape: pass a collection and a function, get a result. No looping appears in the calling code; the looping lives inside the operations, once, shared by callers.

Sorting uses the same gesture. sortBy takes a comparison rule for "which comes first":

    bool byAge(Record a, Record b) { return a.age < b.age; }
    people.sortBy(byAge);   // sorts people by the byAge rule

A passed function is not called at the line where it appears; it is handed over. sortBy has a parameter typed bool(Record, Record) and calls it on every comparison. byAge is an ordinary function, and passing it is naming it: that is all a function pointer means so far.

5.14 Closures and Their Absence

A closure is a function that carries captured state from its surrounding scope. Coral has no closures, a design decision that shapes how higher-order functions are used.

A Coral function pointer carries only the function's address: no captured environment, no hidden state. Functions cannot remember the caller's scope; they receive everything through parameters.

In a language with closures you could write a counter that remembers its own n:

    // (not Coral) -- closure-style counter
    makeCounter() {
        u64 n = 0;
        return () => ++n;      // captures n
    }

Coral cannot do that: a returned function pointer is just an address with nowhere to store "my n." The Coral way is to make the state a parameter:

    void bumpCounter(u64* n)
    {
        *n = *n + 1;
    }

    u64 n = 0;
    bumpCounter(&n);   // n is 1
    bumpCounter(&n);   // n is 2

The state a closure would capture becomes an argument, and the signature states it honestly. The reader sees what the function uses.

Closures require machinery: a hidden allocation for the environment, a way to keep it alive, and a calling convention that passes it. Coral's philosophy is that a function is what its signature says. The pattern is more verbose and more honest: you never wonder what a passed function remembers.

5.15 Recursion

A function that calls itself is recursive. Recursion expresses naturally nested problems: tree traversals, parsers, and divide-and-conquer algorithms.

The classic factorial:

    u64 fact(u64 n)
    {
        if (n <= 1) return 1;
        return n * fact(n - 1);
    }

For fact(4), each call waits on the next until fact(1) hits the base case and returns 1, then the multiplications unwind: 2, 6, 24. Two things make it work: a base case that stops the chain, and each call having its own locals. Recursive calls do not overwrite each other; they stack.

The library's pre-order tree traversal is the canonical example:

    void _preOrder(TreeNode<T>* node, void(T) fn)
    {
        fn(node->value);
        for (u64 i = 0; i < node->children.count(); i++)
            self._preOrder(node->children.at(i), fn);
    }

The function recurses for each child. The recursion mirrors the data: a tree is a node with child trees. The leading underscore marks a private helper; the public entry handles empty trees.

Each call pushes a frame with its own node and loop counter, and the previous frame is intact on return. Depth is limited by the stack, so deep recursion overflows it. The library balances recursion with iteration: depth recurses, length iterates.

Euclid's algorithm shows a recursion whose depth is tiny and whose base case is the natural end:

    u64 gcd(u64 a, u64 b)
    {
        if (b == 0) return a;
        return gcd(b, a % b);
    }

For gcd(48, 18): 48 % 18 is 12, then gcd(18, 12), then gcd(12, 6), then 12 % 6 is 0 and the base case returns 6. The operands shrink every step, so depth is bounded by the numbers. The recursive call is the entire return value, tail position.

Structure-counting recursion: a tree's node count is one for the node plus the counts of its subtrees.

    u64 countNodes(TreeNode* node)
    {
        if (node == null) return 0;
        return 1 + countNodes(node->left) + countNodes(node->right);
    }

The null check is the base case at every level: an empty subtree contributes zero, a leaf contributes one. Depth is the tree's depth, so a balanced tree is shallow regardless of node count. The recursive code is the data's shape.

5.16 Tail Calls and Accumulators

A tail call is a call made as the last thing a function does before returning. A tail-recursive function can run in constant stack space when the language optimizes tail calls.

Every unfinished call holds a stack frame, so deep recursion can exhaust memory. A tail call is the special case where nothing remains to remember, so the compiler can reuse the frame.

Coral supports tail-call optimization. A call in tail position can be turned into a loop reusing the frame, so the recursion runs with a flat stack. The optimizer is simple and applies where safe; write the recursion in transformable form.

The accumulator pattern makes a recursion tail-recursive: pass the accumulated value forward as an extra parameter, so the call returns it directly.

    u64 sumRange(u64 n, u64 acc)
    {
        if (n == 0) return acc;
        return sumRange(n - 1, acc + n);
    }

In factorial, `n * fact(n - 1)` cannot return immediately; it must multiply after the call. In sumRange, the recursive call is the entire return value, `return sumRange(...)`, so the frame can be recycled and the compiler can turn it into a loop reassigning n and acc.

Each call passes the running total, and the final call returns it. The recursion is a loop in recursive clothing.

Coral does not require tail-recursive style. The tree traversal recurses non-tail and runs fine because its depth is the tree's depth. Use the accumulator when a recursion must go deep.

5.17 Generators, Lazy Sequences, and Iteration

A generator is a function that can pause, yield a value, and resume. Coral has no generators and no yield statement.

The reason is the same as for closures: a generator has hidden state, a frame that survives calls and a suspended stack, invisible in the signature.

The nearest tool is the @iter protocol of Chapter 4, but it is not a generator: @iter is index based and eager, walking a container that already holds its elements by calling count() once and at(i) per index. It computes nothing on demand and has no hidden suspension point; the state of an iteration is a plain index.

There is therefore no lazy sequence and no lines() iterator that materializes a file one line at a time. When a source produces values as you go, drive it with a loop and keep the state yourself:

    while (true)
    {
        str line = readLine();
        if (line.len == 0) break;   // end of input
        process(line);
    }

The loop reads one line per turn and stops when the source ends, buffering nothing up front. Because @iter is structural and eager, there is no protocol for sending a value back into a running sequence; operations that feed a stream take explicit parameters.

5.18 Async, Await, and Threads

Some languages have async and await, with an event loop, futures, cancellation, and backpressure. Coral has neither, and no event loop in the language.

Async and await graft suspension onto functions, requiring hidden suspended frames, a scheduler, and a runtime. Coral's concurrency is threads, with explicit synchronization, covered in a later chapter.

The trade is consistent: an async signature does not say whether it suspends, how long it runs, or whether it can be cancelled. A Coral thread function has a plain signature. The model is less convenient for I/O-bound work, and the language accepts the cost for explicitness.

5.19 Mutual Recursion

Two functions that call each other are mutually recursive. The pattern appears in parsers alternating between constructs and in state machines whose states call each other.

The classic example decides whether a number is even or odd:

    bool isEven(u64 n)
    {
        if (n == 0) return true;
        return isOdd(n - 1);
    }

    bool isOdd(u64 n)
    {
        if (n == 0) return false;
        return isEven(n - 1);
    }

isEven(3) calls isOdd(2), then isEven(1), then isOdd(0), returning false. Only the base case n == 0 stops the alternation.

Mutual recursion requires each function to know the other's declaration. Coral collects a module's declarations before typechecking, so functions can call each other in any order, removing C's declaration-order annoyance.

It works like ordinary recursion, pushing a frame per call. Stack depth is the call chain's depth, and the same guidance applies: deep alternations are better expressed as explicit state or loops.

5.20 Methods and the self Receiver

A method is a function attached to a type: a named operation on a value of that type. The library is built from methods such as push, pop, find, append, isOk, and unwrap.

The difference is only in the call. `lengthOf(text)` is a plain function taking a value; `text.length()` is a method called on the value itself. Inside the method, that value is named `self`.

Methods are declared inside the type's definition, after the fields, in the same type-first form: return type, name, parameters.

    pub struct Vec<T>
    {
        T* data;
        usize len;
        usize cap;

        void push(T val)
        {
            if (self.len >= self.cap) self.reserve(self.cap > 0 ? self.cap * 2 : 4);
            self.data[self.len] = val;
            self.len++;
        }
    }

This is the vector's real shape: data pointer, length, capacity, with push growing if needed, storing the value, and bumping the length.

The body reaches the receiver through self: self.len, self.data, self.cap. Each push operates on the vector it was called on.

self is a keyword resolved to the current method's receiver. Without it a method could not name its own fields; with it, the receiver is always explicit.

The receiver is not a hidden argument. v.push(x) passes v as the receiver and x as the argument, both named in the call. There is no other hidden state.

5.21 The Receiver and self

Every method has a receiver, named self inside the body. It does not appear in the parameter list, and a method reaches its fields with the dot. It is the one thing a method gets that an ordinary function does not.

Because self is always the receiver, a method never writes it as a parameter. push takes only its value:

    void push(T val)
    {
        self.data[self.len] = val;   // self is the receiver
        self.len++;
    }

A method that modifies the receiver assigns through self. A read-only method can say so with the const form, which the compiler enforces:

    #[[const]]
    usize count() { return self.len; }

or, equivalently, the trailing form:

    usize count() const { return self.len; }

Both spellings mark the method const: the body may read self but not write through it, and a caller knows the call cannot change the receiver.

The receiver is visible at the call site, consistent with the language's explicitness.

5.22 Static Methods and Constructors

A static method belongs to the type rather than a value. It is declared with the static keyword and called through the type name.

A static method is something the type can do before a value exists. "Make me a new vector with this capacity" happens before any vector exists. Call it with `::`, as in `Vec<u32>::withCap(16)`, the sign that no particular value is involved.

    static Vec<T> withCap(usize capacity)
    {
        return Vec<T> {
            .data = alloc<T>(capacity),
            .len = 0,
            .cap = capacity
        };
    }

withCap is the pattern behind a constructor, the code that builds a value. There is no automatic constructor. withCap allocates capacity elements, sets length zero, records capacity, and returns a struct literal. The type name in `static Vec<T> withCap` says it returns a Vec. alloc<T>(capacity) is generic and imported from std::mman; this is real std code.

A static method has no receiver. It creates a value or provides an operation that needs no instance. Its most important use is construction.

Construction is explicit: no special syntax, no constructor operator. Constructors are static methods with ordinary names. Vec has new and withCap; variants such as Result and Option are built with variant literals naming the case and fields. Each constructor is called through the type name.

    Vec<u32> v = Vec<u32>::withCap(16);
    String greeting = String::from("hello");
    Result<u64, i32> ok = Result<u64, i32>::Ok { .value = 7 };
    Option<u64> none = Option<u64>::None;

The double-colon call names the type and constructor, so withCap is unambiguously the vector's. This is how constructors and type-level methods are invoked throughout the library.

5.23 Method Blocks

Methods can also be declared outside a type's definition in an extend block, which names the type the methods belong to.

    pub extend User
    {
        void print()
        {
            // ...
        }
    }

The block names the type and declares its methods. The receiver is the same implicit self, and the methods behave exactly like those declared inside the type.

Extend blocks keep a type's definition focused on fields and group related methods by concern. A type in one module can have methods in another, and the library uses this to keep core types small. The syntax matches trait implementation blocks.

A point type with a distance method defined outside its definition:

    pub extend Point
    {
        f64 distanceTo(const Point* other)
        {
            f64 dx = self.x - other->x;
            f64 dy = self.y - other->y;
            return sqrt(dx * dx + dy * dy);
        }
    }

Point.crl shows the fields; the behavior is grouped in the block. Definition and behavior are separated into the places easiest to navigate.

5.24 Traits

A trait is a promise a type makes: a named set of method signatures it agrees to implement. Traits give Coral interfaces and type classes in type-first style.

    trait Serializable
    {
        u64 serialize(u8* buffer);
        u64 deserialize(const u8* buffer);
    }

A trait is a checklist of abilities, and a type signs up by providing every method. Code can then work with any type that signed up, without knowing which type it is.

The trait states the promise without an implementation. serialize takes a buffer and returns bytes written; deserialize reads from one. The signatures are the whole promise, and the compiler checks the match.

A type implements a trait in an extend block naming the trait after a colon. The block names the type, the trait, and provides the bodies.

    pub extend User : Serializable
    {
        u64 serialize(u8* buffer)
        {
            // write the user's fields into buffer
        }
        u64 deserialize(const u8* buffer)
        {
            // read the user's fields from buffer
        }
    }

The colon names the pair: User extends Serializable. The methods use the implicit self, and the compiler verifies that every trait method is implemented.

Traits are the language's ad-hoc polymorphism. A function written against a trait works for every type supplying its methods. Coral does not spell the requirement as a bound; there is no `T : Shape`. The requirement is the operations the body names, checked where the function is used. The direct way to take "any shape" is a trait object, the `any Trait` type from Chapter6:

    trait Shape
    {
        f64 area();
        f64 perimeter();
    }

    pub f64 largestArea(const Vec<any Shape>* shapes)
    {
        f64 best = 0.0;
        for (u64 i = 0; i < shapes->count(); i++)
        {
            f64 a = shapes->at(i).area();
            if (a > best) best = a;
        }
        return best;
    }

The parameter is `const Vec<any Shape>*`: a vector of trait objects. The body may call exactly the methods `Shape` declares, because `any Shape` is a window framing those methods. A generic `largestArea<T>(const Vec<T>* shapes)` would also compile, checked at instantiation; every `T` that has `area` works, and a `T` without it is rejected.

The difference is where the requirement lives and its cost. The trait-object form states it in the signature and dispatches through the trait's table at run time. The generic form discovers it in the body and monomorphizes to direct calls with no table.

Trait declaration, implementation block, and use form a pair of promises, each a named declaration with a visible signature, and the compiler checks the connections.

5.25 Method Dispatch: Static and Dynamic

Method dispatch is how a call chooses which function runs. Coral's dispatch is static by default: a call on a value of known type resolves at compile time, with no runtime lookup or table walk.

The type system drives static dispatch. The compiler resolves the call against the type's methods, checks types, and emits a direct call. Generic specialization works the same way: a trait method on a concrete instantiation resolves statically.

Dynamic dispatch happens where behavior is stored in data: function pointers. A struct of function pointers, a hash map's comparison function, or an allocator table dispatches through the stored function, which can vary at runtime. This is the vtable model in explicit form: the table is a struct, its fields are methods, and a call through a field is indirect.

Coral has no multiple dispatch, where a call chooses by the runtime types of several arguments. Methods attach to one receiver type, and generics resolve statically. Behaviors routed through multiple dispatch are expressed with traits and generics at compile time.

5.26 Overloading and Its Absence

Overloading means several functions share a name and the call chooses by arguments. Coral does not have it: a name should mean one thing.

A function's name identifies it, and its signature pins the meaning. A call is unambiguous by name, and argument types must match the one signature. There is no candidate selection and no inference of which function a name means.

Generics and naming do overloading's work. A function for several types is generic, and genuinely different functions get different names, such as find and findIndex. The type system carries the generality; the names carry the distinction.

5.27 Generics and Specialization

Generic functions compile by specialization. When called with concrete types, the compiler instantiates the body with the type parameters replaced and typechecks it against those types. Each instantiation is a complete, concrete function.

Specialization is where checks happen. Calling max with two u64s checks the body with T as u64; calling with f64 checks it again. A type lacking the comparison fails at the call site. Generality is checked per use.

Specialization is also where performance comes from. Each instantiation is concrete and optimized like hand-written code. The comparison is a hardware comparison, not a table call. The cost of generality is paid at compile time; runtime cost is zero.

The cost is code size: each instantiation is real code, and many instantiations of a large function are many copies. The library accepts this because a single runtime-typed body would be slower. Compile-time cost buys runtime speed.

5.28 The Extern Boundary

Functions outside Coral, in C libraries or the operating system, are declared with extern. An extern declaration states the name and signature, and the compiler trusts it, generating a call to the external symbol.

`extern` calls a function someone else wrote, usually in C or the OS. You promise that it exists with the signature you wrote; the compiler cannot check outside code.

    extern i32 pthread_mutex_init(void* mutex, const void* attr);

The declaration is a promise the Coral code depends on. The compiler cannot check the external body, so responsibility rests on the declaration and its author. The signature is the interface, and that is all either side knows.

Extern declarations bridge to C, and the library uses them heavily: POSIX for processes, pthreads for threading, libc for files and memory. Each names the C symbol and its Coral signature, and each call checks against it.

Inline extern declarations let a function declare an external function in its body, keeping the declaration next to its use and scoped to the function.

5.29 Composition and Design

The chapter's patterns compose into a style: explicit signatures, everything typed, no hidden machinery.

A few habits make a Coral codebase pleasant to read.

First, write small functions with honest signatures. A u64 return, a str parameter, and a clear name can be trusted without opening the body. A void validateConfig is a warning sign: it probably prints its own errors and cannot signal failure, which is what Result is for.

Second, let the return type set expectations: void for "did a thing," Option for "may be absent," Result for "can fail," and a value or struct for "this is the answer." The return type is the first line of documentation, checked by the compiler.

Third, thread state through parameters, never around them. No closures means the needed state is in the signature, so you can always see where a function gets its data.

Fourth, prefer iteration for flat problems and recursion for nested ones. A long list is a loop; a tree is a function calling itself. Depth recurses, length iterates.

Fifth, use higher-order functions where they name an operation, not to show off. "Filter these" is clearer than a handwritten loop when the predicate is already a named function. A freshly invented callback for a one-off call is often better as a plain loop.

These are not compiler-enforced rules but patterns the library demonstrates and the language rewards. The signature says what runs, the body says how, and the caller never reverse-engineers a hidden effect.

5.30 What a Function Is: Names and Abstraction

We have covered how functions are declared, called, specialized, and composed. Here is why the mechanics exist.

A function is first a name. Before countLines existed, "count the lines" was explanation and handwork. Afterward it is a word, and every call site is a sentence built from such words. Naming is the cheapest abstraction, and the most important, because a good name carries the function's meaning.

A function is also a boundary. Inside the braces is the function's world; outside is the caller's. The signature stands at the boundary and is all either side needs to know. That is why functions can be written by one person and used by another, written once and called a thousand times.

And a function is a unit of trust. Small, well named, and honestly typed, it can be believed because you can read everything it might do. A big program is a web of small trustworthy functions, each checked against its neighbors: many small things you understand instead of one big thing you hope works.
