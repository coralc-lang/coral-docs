Live Examples: Dynamic Programming and Greedy

Two Ways to Be Shortsighted, and Two Ways to Fix It

Chapter28 ended with the memoized Fibonacci, a good start: dynamic programming (DP) is recursion plus memory. The recursion splits a problem into smaller ones; the memory stops you from solving the same subproblem twice.

Greedy algorithms never look ahead or remember; they make the best local choice and never reconsider. Sometimes that yields the global optimum; sometimes it is quietly wrong. A failure teaches what property the greedy rule needs.

This chapter sets the techniques side by side: DP remembers answers, greedy makes irreversible choices, and the last problem shows both. Ask: does the same subproblem recur (then remember), and is a choice safe now and forever (then be greedy)?

A note on the imports these examples use. The growable list is `import(lib) std::vec { Vec };`, the min-heap is `import(lib) std::collections::priorityqueue { PriorityQueue };`, tree allocation uses `import(lib) std::mman { alloc, dealloc };`, and sorting uses `sortI32` from `import(lib) std::collections::sort { sortI32 };`. The string type `str` is built in. Each code block assumes those imports and is otherwise complete.

30.1 The Two Ingredients of Dynamic Programming

A problem needs two ingredients for DP.

The first is overlapping subproblems. Factorial solves each subproblem once, so there is nothing to remember; Fibonacci recomputes F(3) many times, so remembering pays.

The second is optimal substructure: the best whole answer is assembled from the best answers to its parts. A shortest route A to C through B is the shortest A-to-B plus B-to-C. When a locally great choice makes the whole worse, DP does not apply directly.

Top-down, or memoization, writes the natural recursion and caches results. Bottom-up, or tabulation, fills a table from the smallest subproblems upward. Top-down is easier to derive; bottom-up usually has a smaller constant factor and no recursion stack. Most examples here are bottom-up because the table exposes the subproblem structure.

30.2 Climbing Stairs: The Smallest Useful DP

The problem. You climb n steps, moving 1 or 2 at a time. How many distinct ways reach the top?

Picture this. The last move came from step n−1 or n−2, so ways(n) = ways(n−1) + ways(n−2), which is Fibonacci with one way to stand at the bottom.

Brute force, then better. The double recursion recomputes steps by many paths. A small bottom-up table solves each once:

    u64 climbStairs(u64 n) {
        // base cases: 0 or 1 steps can be done exactly one way
        if (n <= 1) return 1;
        // ways[i] will hold the number of ways to reach step i
        Vec<u64> ways = Vec<u64>::withCap((usize)n + 1);
        ways.push(1);    // ways[0] = 1: one way to stand at the bottom
        ways.push(1);    // ways[1] = 1: one way to reach step 1
        // fill bottom-up: each entry depends only on the two before it
        for (u64 i = 2; i <= n; i += 1) {
            u64 prev1 = ways.at((usize)(i - 1));
            u64 prev2 = ways.at((usize)(i - 2));
            ways.push(prev1 + prev2);
        }
        return ways.at((usize)n);
    }

`ways` holds one entry per step, each the sum of the two before it. The first two are the base cases; every later entry uses entries that already exist. Read backwards, the table is a proof.

Time and space. Θ(n) time and Θ(n) space, but each entry needs only the two before it, so two variables would give O(1) space. The full table is shown because most DP problems need it.

Edge cases. n = 0 and n = 1 return 1; n = 2 returns 2. The values grow like Fibonacci, so u64 overflows around n = 93.

A variation. With moves 1, 2, or 3, sum the previous three and use base cases 1, 1, 2. Only the number of predecessors changes. "The last move could have come from here" is the general trick for counting paths to a target.

30.3 Coin Change: The Minimum Number of Coins

The problem. Given coin denominations and a target amount, find the fewest coins summing exactly to the target, or report impossibility.

Picture this. The last coin was some denomination c, and before it you made a−c optimally. So fewest(a) is one plus the minimum fewest(a−c) over coins that fit. That is the recurrence and the smallest statement of optimal substructure.

Brute force, then better. The recursion tries every coin as the last and re-solves amounts through many orderings. Filling amounts from 0 upward solves each once:

    i64 coinChange(Vec<i32>* coins, i32 amount) {
        // a sentinel meaning "not yet reachable"
        i64 impossible = 1000000000;
        // dp[a] = fewest coins summing exactly to a
        Vec<i64> dp = Vec<i64>::withCap((usize)amount + 1);
        dp.push(0);                                  // 0 coins make amount 0
        for (i32 a = 1; a <= amount; a += 1) {
            dp.push(impossible);                     // start assuming unreachable
        }
        // fill amounts from 0 upward, so every predecessor already exists
        for (i32 a = 1; a <= amount; a += 1) {
            // try each coin as the last coin used
            for (usize c = 0; c < coins->count(); c += 1) {
                i32 coin = coins->at(c);
                // prune: the coin must fit in the amount
                if (coin <= a) {
                    i64 before = dp.at((usize)(a - coin));
                    if (before + 1 < dp.at((usize)a)) {
                        dp.set((usize)a, before + 1);
                    }
                }
            }
        }
        i64 answer = dp.at((usize)amount);
        // still the sentinel means no combination exists
        if (answer >= impossible) return -1;
        return answer;
    }

`dp[a]` is the fewest coins for amount a; `impossible` means "no way found yet." For each amount, every coin is tried as the last, keeping the smallest result. The `coin <= a` guard prevents negative amounts; a final `impossible` returns −1.

Time and space. Θ(amount × number_of_coins) time and Θ(amount) space, turning an exponential recursion into a polynomial loop.

Edge cases. amount = 0 returns 0. If no coin fits, every entry stays impossible and the answer is −1. Denominations must be positive. This computes the minimum count, not the coins; store the best coin per amount to reconstruct them.

A variation. To count distinct combinations instead of the minimum, change "minimise" to "sum": `dp[a] += dp[a - coin]`, with coins in the outer loop and amounts in the inner. Loop direction distinguishes combinations (order irrelevant) from sequences (order matters).

30.4 0/1 Knapsack: Take It or Leave It, Once

The problem. Given n items with weights and values and a knapsack capacity, choose a subset maximising total value without exceeding capacity. Each item may be taken at most once.

Picture this. You pass exhibits one by one and either take an item, if it fits in the remaining capacity, or leave it. Unlike coin change, there is only one of each, and that "once" is the difference.

Brute force, then better. Enumerating all 2^n subsets is exponential. DP processes items one at a time, tracking the best value at every capacity using the items seen so far:

    i32 knapsack(Vec<i32>* weights, Vec<i32>* values, i32 capacity) {
        usize n = weights->count();
        // dp[c] = best value achievable with capacity c
        Vec<i32> dp = Vec<i32>::withCap((usize)capacity + 1);
        for (i32 c = 0; c <= capacity; c += 1) {
            dp.push(0);
        }
        // process the items one at a time
        for (usize i = 0; i < n; i += 1) {
            i32 w = weights->at(i);
            i32 val = values->at(i);
            // run capacities downward so dp[c-w] stays in the previous row
            for (i32 c = capacity; c >= w; c -= 1) {
                i32 withItem = dp.at((usize)(c - w)) + val;
                // take the better of leaving or taking this item
                if (withItem > dp.at((usize)c)) {
                    dp.set((usize)c, withItem);
                }
            }
        }
        return dp.at((usize)capacity);
    }

After item i, `dp[c]` is the best value at capacity c using items 0 through i. The inner loop runs downward so `dp[c - w]` still reads the previous row; upward would reuse the item, which is unbounded knapsack.

Time and space. Θ(n × capacity) time and Θ(capacity) space, because only the current row is kept. The downward loop is the price of that collapse.

Edge cases. No items or zero capacity yields 0. An item heavier than the capacity is skipped by `c >= w`. Weights and values should be non-negative. Fractional knapsack is a different problem, solved greedily by value density (29.10).

A variation. To recover the chosen items, keep a boolean table `taken[i][c]` and walk backwards from `taken[n][capacity]`. The value is only half the answer when the question asks which items.

30.5 Longest Common Subsequence

The problem. Find the length of the longest common subsequence of two strings: characters appearing in both, in order, not necessarily consecutively. For "ABCBDAB" and "BDCABA" the length is 4.

Picture this. Walk both strings together. Matching characters extend the common subsequence and advance both; otherwise skip one side, taking the better result. That is the recurrence.

Brute force, then better. Generating every subsequence of the first string is exponential. DP builds a table indexed by prefix lengths, each cell holding the LCS length of those prefixes:

    i32 lcs(str a, str b) {
        usize m = a.len;
        usize n = b.len;
        // the 2-D table is stored flat, one row of width n+1 per prefix
        usize width = n + 1;
        Vec<i32> dp = Vec<i32>::withCap((m + 1) * width);
        // row 0 and column 0 stay zero: an empty prefix shares nothing
        for (usize i = 0; i < (m + 1) * width; i += 1) {
            dp.push(0);
        }
        // fill by increasing prefix length on both strings
        for (usize i = 1; i <= m; i += 1) {
            for (usize j = 1; j <= n; j += 1) {
                if (a.at(i - 1) == b.at(j - 1)) {
                    // matching characters extend the diagonal by one
                    dp.set(i * width + j, dp.at((i - 1) * width + (j - 1)) + 1);
                } else {
                    // otherwise drop a character from whichever side is better
                    i32 up = dp.at((i - 1) * width + j);
                    i32 left = dp.at(i * width + (j - 1));
                    dp.set(i * width + j, up > left ? up : left);
                }
            }
        }
        return dp.at(m * width + n);
    }

The table is flat: cell (i, j) is at `i * width + j` with `width = n + 1`. A match adds one to the diagonal; a mismatch takes the larger of dropping from either string. Row 0 and column 0 are zero.

Time and space. Θ(m × n) for both. Only the previous row is needed for the length, giving Θ(min(m, n)) space, but the full table is kept when you also want to reconstruct the subsequence.

Edge cases. An empty string gives 0 and the loops do not run. Identical strings return their length. Duplicates are handled because the recurrence looks only at positions. A subsequence allows gaps; a substring is contiguous and has a different recurrence.

A variation. Edit distance is a near cousin: same layout and two-pointer walk, but cells add a cost. LCS and edit distance underlie diff, the algorithm behind every "compare two versions" tool.

30.6 Edit Distance: How Different Are Two Strings

The problem. Find the minimum number of insertions, deletions, and substitutions turning one string into the other (Levenshtein distance).

Picture this. Each fix is a delete, insert, or replace. Matching characters cost nothing; on a mismatch, spend one fix and choose whichever action leaves the cheapest remainder.

Brute force, then better. The recursion branches three ways per mismatch, about 3^(m+n). DP collapses it into a table of prefix distances:

    i32 editDistance(str a, str b) {
        usize m = a.len;
        usize n = b.len;
        usize width = n + 1;
        // the flat table stores cell (i, j) at index i*width + j
        Vec<i32> dp = Vec<i32>::withCap((m + 1) * width);
        for (usize i = 0; i < (m + 1) * width; i += 1) {
            dp.push(0);
        }
        // first column border: deleting i characters to reach empty
        for (usize i = 0; i <= m; i += 1) {
            dp.set(i * width, (i32)i);          // turning a prefix into empty: i deletions
        }
        // first row border: inserting j characters to build the prefix
        for (usize j = 0; j <= n; j += 1) {
            dp.set(j, (i32)j);                   // turning empty into a prefix: j insertions
        }
        // fill the interior in increasing prefix order
        for (usize i = 1; i <= m; i += 1) {
            for (usize j = 1; j <= n; j += 1) {
                if (a.at(i - 1) == b.at(j - 1)) {
                    // matching characters cost nothing
                    dp.set(i * width + j, dp.at((i - 1) * width + (j - 1)));
                } else {
                    // one edit plus the cheapest of delete/insert/substitute
                    i32 del = dp.at((i - 1) * width + j);
                    i32 ins = dp.at(i * width + (j - 1));
                    i32 sub = dp.at((i - 1) * width + (j - 1));
                    i32 best = del < ins ? del : ins;
                    if (sub < best) best = sub;
                    dp.set(i * width + j, best + 1);
                }
            }
        }
        return dp.at(m * width + n);
    }

The borders are the base cases: empty to a length-j prefix costs j insertions, and a length-i prefix to empty costs i deletions. An interior cell copies the diagonal on a match, or adds one to the cheapest of up, left, and diagonal.

Time and space. Θ(m × n) for both, like LCS. Reconstructing the edit script walks backward from the bottom-right, mirroring the choices. Only the previous row is needed for the distance alone.

Edge cases. "" to "abc" costs 3, set by the first-row border; identical strings give 0. Every operation costs 1 here. Weighted edit distance assigns keyboard-near substitutions a lower cost, and Damerau–Levenshtein counts a transposition as 1 rather than 2.

A variation. The same table underlies dynamic time warping for sequences that stretch (audio, motion capture, genes); only the cost between aligned elements changes. A whole family of alignment algorithms is this picture with a different ruler.

30.7 Longest Increasing Subsequence

The problem. Find the length of the longest strictly increasing subsequence. For [10, 9, 2, 5, 3, 7, 101, 18] the answer is 4 (2, 3, 7, 101).

Picture this. Think of each element as the possible last link of a chain. The longest chain ending at i is one plus the longest chain ending at an earlier, smaller element.

Brute force, then better. Trying all 2^n subsequences is exponential. The DP is O(n^2): `dp[i]` holds the longest increasing subsequence ending exactly at i.

    i32 lis(Vec<i32>* nums) {
        usize n = nums->count();
        if (n == 0) return 0;
        // dp[i] = length of the longest increasing chain ending exactly at i
        Vec<i32> dp = Vec<i32>::withCap(n);
        for (usize i = 0; i < n; i += 1) {
            dp.push(1);                         // any single element is a chain of one
        }
        i32 best = 1;
        // for each end position, look back for a smaller value to extend
        for (usize i = 1; i < n; i += 1) {
            for (usize j = 0; j < i; j += 1) {
                // a smaller earlier value lets the chain grow by one
                if (nums->at(j) < nums->at(i)) {
                    i32 candidate = dp.at(j) + 1;
                    if (candidate > dp.at(i)) {
                        dp.set(i, candidate);
                    }
                }
            }
            // the answer can end anywhere, so track the table's maximum
            if (dp.at(i) > best) best = dp.at(i);
        }
        return best;
    }

Every position starts as a chain of 1. For each i, look back at every earlier j with a smaller value and extend that chain. The answer is the table's maximum, not necessarily the last entry, because the longest chain can end anywhere.

Time and space. Θ(n^2) time and Θ(n) space, fine for thousands of elements but not millions. An O(n log n) version keeps `tails[k]`, the smallest possible tail of an increasing subsequence of length k+1, and uses binary search to place each element.

Edge cases. An empty list returns 0; a single element returns 1. Strictly increasing means duplicates do not extend a chain; use `<=` for non-decreasing. Negative numbers are fine because only relative order matters.

A variation. Flip the comparison for the longest decreasing subsequence. The longest bitonic subsequence pairs an increasing length ending at each position with a decreasing length starting there, then takes the maximum sum.

30.8 Minimum Path Sum: Walking a Grid

The problem. In a grid of non-negative numbers, find the minimum path sum from top-left to bottom-right, moving only right or down.

Picture this. Each cell charges a toll. The cheapest cost to a cell is its toll plus the cheaper of the costs above and to the left. That is the two-dimensional cousin of climbing stairs.

Brute force, then better. Trying all paths is exponential. DP fills the cheapest costs cell by cell:

    i32 minPathSum(Vec<Vec<i32>>* grid) {
        usize rows = grid->count();
        if (rows == 0) return 0;
        // read the row width without copying the row
        Vec<i32>* firstRow = grid->atPtr(0);
        usize cols = firstRow->count();
        if (cols == 0) return 0;
        // a single row of the table: dp[j] is the cost to reach column j
        Vec<i32> dp = Vec<i32>::withCap(cols);
        for (usize j = 0; j < cols; j += 1) {
            dp.push(0);
        }
        // fill cell by cell in row-major order
        for (usize i = 0; i < rows; i += 1) {
            Vec<i32>* row = grid->atPtr(i);
            for (usize j = 0; j < cols; j += 1) {
                i32 cell = row->at(j);
                if (i == 0 && j == 0) {
                    // the start cell is just its own toll
                    dp.set(j, cell);
                } else if (i == 0) {
                    // top row: only came from the left
                    dp.set(j, dp.at(j - 1) + cell);
                } else if (j == 0) {
                    // left column: only came from above
                    dp.set(j, dp.at(j) + cell);
                } else {
                    // interior: cell toll plus the cheaper predecessor
                    i32 fromLeft = dp.at(j - 1);
                    i32 fromUp = dp.at(j);
                    dp.set(j, (fromLeft < fromUp ? fromLeft : fromUp) + cell);
                }
            }
        }
        return dp.at(cols - 1);
    }

The table is one-dimensional although the grid is not, because only the left neighbour and the cell above are needed. `grid->atPtr(i)` reads row i without copying, which also avoids freeing memory the grid still points at. Three branches handle the top row, left column, and interior.

Time and space. Θ(rows × cols) time and Θ(cols) space, since only one row of DP values is kept. The naive DP would use the full grid.

Edge cases. A 1×1 grid returns its single cell. A single row or column has one path, followed by the boundary branches. All-zero weights return 0. Negative weights break the "min of two predecessors" reasoning, since a path could loop to exploit them; non-negativity is a real precondition.

A variation. To count distinct paths instead, make `dp[j]` a count and use `dp[j] = dp[j] (from above) + dp[j-1] (from left)`, seeding the first row and column to 1. That is unique paths: same table, addition instead of minimisation.

30.9 Greedy: Interval Scheduling

The problem. Given intervals with starts and ends, select the largest subset that does not overlap. This is activity selection: one room, many meetings.

Picture this. Accepting the earliest-starting request can lock you into a long meeting. The rule that works is to accept the request that ends earliest, because it frees the room soonest and no other choice can free it sooner.

Brute force, then better. Trying every subset is exponential. Greedy sorts by end time and sweeps once, accepting any interval starting at or after the last accepted end:

    struct Interval {
        i32 start;
        i32 end;
    }

    bool byEnd(Interval a, Interval b) {
        // greedy key: order by finishing time
        return a.end < b.end;
    }

    i32 maxNonOverlapping(Vec<Interval>* intervals) {
        // sorting by end time is the whole algorithm
        intervals->sortBy(byEnd);
        i32 count = 0;
        bool haveLast = false;
        i64 lastEnd = 0;
        // one sweep: accept anything that starts after the last accepted end
        for (usize i = 0; i < intervals->count(); i += 1) {
            Interval cur = intervals->at(i);
            // the greedy choice: take the earliest-ending compatible interval
            if (!haveLast || (i64)cur.start >= lastEnd) {
                count += 1;
                lastEnd = cur.end;
                haveLast = true;
            }
        }
        return count;
    }

Sorting by end time is the whole algorithm; the rest is a linear sweep. An interval is accepted when it starts no earlier than the last end, so accepted intervals are disjoint and ordered. `haveLast` avoids a sentinel, and the `(i64)` cast keeps the comparison signed.

Time and space. Sorting dominates at Θ(n log n); the sweep is Θ(n), with O(1) extra space. Greedy turns an exponential search into n log n because the exchange argument proves the local choice safe.

Why greedy works here. If an optimal solution's first meeting is not the earliest-ending one, swap it for that one; the replacement finishes no later, so the rest stays valid. Repeating shows an optimal solution makes the greedy first choice, and induction finishes it.

Edge cases. An empty list returns 0. Touching intervals are allowed by `>=`; use `>` if touching conflicts. Zero-length intervals are accepted and count. Start greater than end is malformed input and unhandled.

A variation. With weighted intervals, greedy by end time fails and you need DP: sort by end and binary-search the latest compatible prior interval. Weighted interval scheduling bridges the greedy and DP halves of this chapter.

30.10 Greedy: Huffman Coding, with a Priority Queue

The problem. Given symbol frequencies, build an optimal prefix code: no code is a prefix of another, and total encoded length is minimised.

Picture this. Common letters get short codes and rare letters long ones. Huffman repeatedly merges the two least frequent symbols into a parent whose frequency is their sum. Rarer symbols end deeper, so their codes are longer; every symbol is a leaf, so no code prefixes another.

Brute force, then better. Searching all binary trees is exponential. Huffman's greedy merge is optimal: take the two lightest nodes each step. A min-heap priority queue is exactly the tool.

    struct HuffNode {
        i32 freq;
        i32 symbol;          // 0..symbols-1 for leaves, -1 for internal
        HuffNode* left;
        HuffNode* right;
    }

    bool lighterFirst(HuffNode* a, HuffNode* b) {
        // the heap is a min-heap on frequency
        return a->freq < b->freq;
    }

    HuffNode* buildHuffman(Vec<i32>* freqs, usize symbols) {
        PriorityQueue<HuffNode*> pq = PriorityQueue<HuffNode*>::new(lighterFirst);
        // one leaf per symbol that actually appears
        for (usize s = 0; s < symbols; s += 1) {
            if (freqs->at(s) > 0) {
                HuffNode* leaf = alloc<HuffNode>(1);
                leaf->freq = freqs->at(s);
                leaf->symbol = (i32)s;
                leaf->left = null;
                leaf->right = null;
                pq.push(leaf);
            }
        }
        // the greedy merge: repeatedly combine the two lightest nodes
        while (pq.count() > 1) {
            HuffNode* a = pq.pop();
            HuffNode* b = pq.pop();
            HuffNode* parent = alloc<HuffNode>(1);
            parent->freq = a->freq + b->freq;
            parent->symbol = -1;
            parent->left = a;
            parent->right = b;
            pq.push(parent);
        }
        // the single remaining node is the root
        if (pq.count() == 0) return null;
        return pq.pop();
    }

    void codeLengths(HuffNode* root, i32 depth, Vec<i32>* lengths) {
        // base case: nothing here
        if (root == null) return;
        // a leaf's code length is its distance from the root
        if (root->left == null && root->right == null) {
            lengths->set((usize)root->symbol, depth);
            return;
        }
        codeLengths(root->left, depth + 1, lengths);
        codeLengths(root->right, depth + 1, lengths);
    }

The queue starts with one leaf per symbol, ordered by frequency. Each pass pops the two lightest and pushes their parent with the combined frequency. The last node is the root. `codeLengths` records each leaf's depth, and the objective is the sum of `freq[s] * lengths[s]`.

Time and space. At most n pushes and n−1 merges, each O(log n), give Θ(n log n) for n distinct symbols. The tree has at most 2n−1 nodes, so Θ(n) space. A one-time sort cannot handle the new frequencies created by merges, hence the heap.

Why greedy works here. In an optimal tree, the two least frequent symbols can be siblings at the deepest level: swapping them with a deepest pair does not increase the weighted path length. Removing that pair and treating the parent as a new symbol reduces the problem by one.

Edge cases. One distinct symbol gives a single-node tree with code length 0, though most encoders assign 1 because a zero-bit code cannot be represented. Zero symbols returns null. Ties can produce different trees with the same optimal total length. Negative frequencies are nonsense and unguarded.

A variation. Adaptive Huffman and arithmetic coding update frequencies as data streams past instead of assuming a fixed distribution. Arithmetic coding encodes the message as a single fraction and approaches the entropy limit at more arithmetic cost. Huffman remains the classic optimal prefix code.

30.11 When Greedy Fails: Coin Change, Revisited

The problem. Solve coin change (29.3) greedily, always taking the largest coin that fits, and understand exactly when that fails.

Picture this. With US coins 1, 5, 10, 25, greedy is correct for every amount. With coins 1, 3, 4 and amount 6, greedy takes 4 + 1 + 1, but 3 + 3 is better. Taking the largest coin now forecloses a better combination later.

Brute force, then better. The greedy version is short and tempting:

    i32 coinChangeGreedy(Vec<i32>* coins, i32 amount) {
        // sort ascending so we can walk from the largest coin down
        sortI32(coins);
        i32 count = 0;
        i32 remaining = amount;
        for (i64 i = (i64)coins->count() - 1; i >= 0; i -= 1) {
            i32 coin = coins->at((usize)i);
            // the greedy choice: take as many of the largest coin as fit
            while (coin <= remaining) {
                remaining -= coin;
                count += 1;
            }
        }
        // any remainder means this greedy pass failed to hit the target
        if (remaining != 0) return -1;
        return count;
    }

Sort ascending and take as many of each coin as fit. This works when each coin is a multiple of the next, but not for {1, 3, 4} and 6 (3 instead of 2). DP is always correct in Θ(amount × coins) time.

Why greedy fails here. The largest coin leaves the smallest remainder for that coin, but it is not safe: no exchange argument shows an optimal solution contains it. Amount 6 with {1, 3, 4} is the counterexample. Without a safety proof, greedy is a heuristic.

Time and space. Greedy is Θ(coins × (amount / min-coin)) worst case, effectively linear for typical coins, with O(1) extra space. DP is Θ(amount × coins) time and Θ(amount) space. For large amounts and non-canonical systems, DP is the price of correctness.

Edge cases and the diagnostic. Prove a greedy rule with an exchange argument or test it exhaustively against DP on small inputs. Coin-change canonicality has a known test (Pearson's). Greedy also needs a local choice proven safe for every input.

30.12 House Robber

The problem. Given a row of houses each holding money, choose non-adjacent houses maximising the total robbed.

Picture this. At each house, rob it and skip its neighbour, or leave it. The best loot up to i is the better of the best up to i−1 and house i's value plus the best up to i−2. That is climbing stairs with a maximum instead of a sum.

Brute force, then better. Trying all 2^n non-adjacent subsets is exponential. DP keeps the best total for each prefix, and each house needs only the two previous answers, so one pass with constant state suffices.

    i32 rob(Vec<i32>* nums) {
        // only the last two answers are ever needed
        i32 prev2 = 0;      // best loot up to two houses back
        i32 prev1 = 0;      // best loot up to the previous house
        for (usize i = 0; i < nums->count(); i += 1) {
            // the recurrence: rob this house plus the i-2 answer, or skip it
            i32 take = prev2 + nums->at(i);
            i32 skip = prev1;
            i32 cur = take > skip ? take : skip;
            // slide the two-variable window forward
            prev2 = prev1;
            prev1 = cur;
        }
        return prev1;
    }

Two variables carry the table. `prev1` is the best loot using houses seen so far; `prev2` is the best two houses back, the only state needed when robbing the current house. Each house compares `prev2 + value` with `prev1` and slides the window forward.

Time and space. Θ(n) time and O(1) space, against O(2^n) brute force. This is the space optimisation from climbing stairs applied to a maximum.

Edge cases. An empty street yields 0, one house its value, two houses the larger. Non-negative values are assumed; negatives would make "rob nothing" better and shift the base cases. The answer is `prev1`, the best over the whole street.

A variation. To report which houses were robbed, keep the choice made at each index and walk it backward, or keep a boolean per house. The total is only half the answer when the question asks which ones.

30.13 Unique Paths on a Grid

The problem. A robot starts top-left in an m × n grid and moves only right or down. How many distinct paths reach the bottom-right?

Picture this. The ways to reach a cell equal the ways to reach the cell above plus the ways to reach the cell to its left. The first row and column each have exactly one path.

Brute force, then better. Walking every path is exponential; the count is the binomial coefficient C(m+n−2, m−1). DP fills the counts in one pass, and one row of the table suffices because each cell needs only above and left.

    i64 uniquePaths(i32 m, i32 n) {
        if (m <= 0 || n <= 0) return 0;
        // one row of the count table
        Vec<i64> dp = Vec<i64>::withCap((usize)n);
        for (i32 j = 0; j < n; j += 1) {
            dp.push(1);                 // the first row reaches each cell exactly one way
        }
        // each later row: count from above plus count from the left
        for (i32 i = 1; i < m; i += 1) {
            for (i32 j = 1; j < n; j += 1) {
                dp.set((usize)j, dp.at((usize)j) + dp.at((usize)(j - 1)));
            }
        }
        return dp.at((usize)(n - 1));
    }

The vector holds the current row. The first row is all ones; each later row is computed in place, since `dp[j]` is the count from above and `dp[j-1]` the count from the left. This is minimum-path-sum row collapsing with addition.

Time and space. Θ(m × n) time and Θ(n) space, or Θ(min(m, n)) if you iterate along the shorter dimension. Answers grow quickly, so i64 delays the overflow point.

Edge cases. m = 1 or n = 1 gives exactly one path from the initialisation. A zero or negative dimension returns 0. i64 overflows around 34 × 34, requiring big integers or modular arithmetic.

A variation. With obstacles, mark blocked cells and set their count to zero, skipping them in the recurrence; the first row and column stop contributing past the first obstacle. Diagonal moves add a third predecessor and change the seeds, but the grid shape and row-collapsing remain.

30.14 Best Time to Buy and Sell Stock

The problem. Given daily prices, choose one day to buy and a later day to sell for maximum profit, or return 0 when no profitable trade exists.

Picture this. Moving forward, the best buy so far is the cheapest price seen, and the best trade ending today is today's price minus that minimum. Keep a running minimum and a running best profit.

Brute force, then better. Checking every (buy, sell) pair is O(n^2). One pass records the lowest price and best profit so far, giving O(n) time and O(1) space. This is a greedy scan, not a table: a lower buy price can only help.

    i32 maxProfit(Vec<i32>* prices) {
        i32 best = 0;
        // the running minimum replaces the unknown best buy day
        i64 lowest = 9223372036854775807;   // larger than any possible price
        for (usize i = 0; i < prices->count(); i += 1) {
            i64 p = (i64)prices->at(i);
            // greedy: the cheapest buy so far pairs best with today
            if (p < lowest) lowest = p;      // you could have bought today
            i64 gain = p - lowest;
            if (gain > (i64)best) best = (i32)gain;
        }
        return best;
    }

`lowest` starts above any possible price, so the first day sets a new minimum. Each day updates the minimum, then computes and keeps the best profit. Updating first allows same-day buy and sell for zero profit; to require a day between, compute profit first.

Edge cases. Fewer than two days yields 0. A steadily falling price yields 0, the correct "do not trade" answer. Prices are non-negative and i64 arithmetic prevents subtraction overflow. Short selling would break the running-minimum trick.

A variation. The single-transaction constraint makes the greedy scan sufficient. Unlimited transactions sum every upward daily move; at most k transactions needs DP over days and transaction counts.

30.15 Word Break

The problem. Given a string and a dictionary, decide whether the string can be split into a sequence of dictionary words matching contiguous pieces.

Picture this. Mark each position you can reach. If the string up to an earlier position is segmentable and the piece between there and here is a word, the string up to here is segmentable. The whole string works once the mark reaches its end.

Brute force, then better. The recursion tries every word at every position and re-attempts the same suffix from many splits. DP records, for each prefix length, whether that prefix can be segmented, filling left to right.

    bool endsWithWordAt(str s, i32 end, str w) {
        // where would this word start if it ended at `end`?
        i32 start = end - (i32)w.len;
        // prune: it would start before the string
        if (start < 0) return false;
        for (usize k = 0; k < w.len; k += 1) {
            if (s.at((usize)(start + (i32)k)) != w.at(k)) return false;
        }
        return true;
    }

    bool wordBreak(str s, Vec<str>* dict) {
        usize n = s.len;
        // dp[i] = can the first i characters be split into dictionary words?
        Vec<bool> dp = Vec<bool>::withCap(n + 1);
        for (usize i = 0; i <= n; i += 1) {
            dp.push(false);
        }
        dp.set(0, true);                     // the empty prefix is segmentable
        // extend the reachable frontier one character at a time
        for (usize i = 1; i <= n; i += 1) {
            // try every word as the final piece ending at i
            for (usize d = 0; d < dict->count(); d += 1) {
                str w = dict->at(d);
                // the word must fit and the prefix before it must be reachable
                if ((usize)w.len > i) continue;
                if (!dp.at(i - w.len)) continue;
                if (endsWithWordAt(s, (i32)i, w)) {
                    dp.set(i, true);
                    break;
                }
            }
        }
        return dp.at(n);
    }

`dp[i]` asks whether the first i characters segment. From `dp[0] = true`, the outer loop extends the reachable frontier. A word is usable if it fits, the prefix before it is reachable, and its bytes match ending at i. The first success stops the inner loop.

Time and space. O(n × d × L) for d words of maximum length L, and O(n) space, against the exponential recursion.

Edge cases. The empty string returns true from `dp[0]`. A word longer than the prefix is skipped by the length guard. Repeated words are harmless. Comparison is byte by byte, so this is an ASCII-level split; Unicode needs code points. Zero-length words are forbidden by convention.

A variation. To reconstruct the segmentation, record which word reached each endpoint and walk back from n to 0. With a large dictionary, replace the word scan with a hash set and test substrings by increasing length; the recurrence is unchanged.

30.16 Partition Equal Subset Sum

The problem. Given positive integers, decide whether they can be split into two groups of equal sum.

Picture this. The total must be even, and each share is half. The question becomes subset-sum: is there a subset summing to half the total? If so, the rest sums to the other half.

Brute force, then better. Trying all 2^n subsets is exponential. The DP is 0/1 knapsack asking yes/no: a boolean table marks each reachable sum. Each number is offered once, so the sum loop runs downward.

    bool canPartition(Vec<i32>* nums) {
        i64 total = 0;
        for (usize i = 0; i < nums->count(); i += 1) {
            total += (i64)nums->at(i);
        }
        if (total % 2 != 0) return false;    // an odd total can never split evenly
        i64 target = total / 2;
        // reachable[s] = can some subset sum exactly to s?
        Vec<bool> reachable = Vec<bool>::withCap((usize)target + 1);
        for (i64 s = 0; s <= target; s += 1) {
            reachable.push(false);
        }
        reachable.set(0, true);              // the empty subset sums to zero
        // offer each number once
        for (usize i = 0; i < nums->count(); i += 1) {
            i64 x = (i64)nums->at(i);
            // downward so this number cannot be reused in the same pass
            for (i64 s = target; s >= x; s -= 1) {
                if (reachable.at((usize)(s - x))) {
                    reachable.set((usize)s, true);
                }
            }
        }
        return reachable.at((usize)target);
    }

The parity check rejects impossible cases. Sum 0 is reachable by taking nothing. Each number is offered once, and the inner loop runs downward so `reachable[s - x]` reflects the state before this number. Upward would reuse it, which is the unbounded version.

Time and space. O(n × total) time and O(total) space. This is pseudo-polynomial: polynomial in the total's value rather than the item count, fine for small totals and hopeless for huge ones.

Edge cases. An empty list has total 0 and returns true. A single non-zero number has no partner and returns false. An odd total returns false immediately. A number above the target is skipped by `s >= x`. Numbers should be positive; a zero is a harmless no-op.

A variation. To recover the groups, mark which item achieved each sum and walk back from the target. Running the inner loop upward allows repeated use, answering a different question and showing how one direction change alters the meaning.

30.17 Longest Palindromic Subsequence

The problem. Find the length of the longest subsequence reading the same forwards and backwards, characters not necessarily contiguous. For "bbbab" the answer is 4 ("bbbb").

Picture this. Put a finger at each end. Equal ends can both join the palindrome, so the answer is two plus the best answer for the inside. Differing ends mean dropping one, taking the better result. The subproblem is always a range.

Brute force, then better. Trying all 2^n subsequences is exponential. DP fills a table indexed by the two range ends, from short ranges up to the whole string, so every dependency is already available.

    i32 longestPalindromicSubseq(str s) {
        usize n = s.len;
        if (n == 0) return 0;
        // flat table: cell (i, j) lives at i*n + j
        Vec<i32> dp = Vec<i32>::withCap(n * n);
        for (usize i = 0; i < n * n; i += 1) {
            dp.push(0);
        }
        for (usize i = 0; i < n; i += 1) {
            dp.set(i * n + i, 1);            // one character is a palindrome of length 1
        }
        // fill by increasing range length so shorter ranges are ready
        for (usize len = 2; len <= n; len += 1) {
            for (usize i = 0; i + len <= n; i += 1) {
                usize j = i + len - 1;
                if (s.at(i) == s.at(j)) {
                    // matching ends wrap the inside, adding two
                    i32 inner = (len == 2) ? 0 : dp.at((i + 1) * n + (j - 1));
                    dp.set(i * n + j, inner + 2);
                } else {
                    // otherwise drop whichever end is better
                    i32 dropLeft = dp.at((i + 1) * n + j);
                    i32 dropRight = dp.at(i * n + (j - 1));
                    dp.set(i * n + j, dropLeft > dropRight ? dropLeft : dropRight);
                }
            }
        }
        return dp.at(n - 1);                 // the cell (0, n-1)
    }

The flat table stores `(i, j)` at `i * n + j`, with the diagonal seeded to 1. Ranges fill by increasing length because each cell needs three shorter ranges. Matching ends add two to the inside; `len == 2` avoids reading an empty inside.

Time and space. Θ(n^2) for both; the cost lives in the table because the answer is a single number.

Edge cases. An empty string returns 0; a single character returns 1. Identical strings reach their full length. A palindromic substring must be contiguous and asks a different question. The longest palindromic subsequence of `s` equals the LCS of `s` and its reverse.

A variation. That equivalence means the LCS code of 29.5 solves this problem: reverse the string and compute the LCS. Seeing one table from two directions shows you understand the structure.

30.18 Jump Game (Greedy)

The problem. Given maximum jump lengths per position, decide whether you can reach the last index from the first.

Picture this. You only need the furthest reachable stone. Starting from the first, that frontier is its jump range; as you advance through reachable stones, their ranges extend it. If the frontier reaches the last stone, the answer is yes.

Brute force, then better. Exploring every jump sequence is exponential. The greedy scan keeps one number, the furthest index reachable, and sweeps left to right, checking each position is reachable and extending the frontier. One pass settles it.

    bool canJump(Vec<i32>* nums) {
        usize n = nums->count();
        if (n == 0) return true;
        // the furthest index any earlier stone can reach
        usize farthest = 0;
        for (usize i = 0; i < n; i += 1) {
            // prune: a gap the frontier cannot cross ends the search
            if (i > farthest) return false;          // this stone is out of reach
            // greedy: extend the frontier as far as this stone allows
            usize reach = i + (usize)nums->at(i);
            if (reach > farthest) farthest = reach;
            // the last stone is reachable, so we can stop
            if (farthest >= n - 1) return true;      // the last stone is reachable
        }
        return true;
    }

`farthest` is the rightmost index any earlier stone can reach. If stone i lies beyond it, a gap blocks the path and the answer is false. Otherwise its jump range extends the frontier; once it covers the last index, the answer is true. No table is needed.

Why greedy works here. The frontier only grows, and a larger frontier never makes a later stone less reachable, so extending it as far as possible is always safe. This monotonicity is the exchange argument in miniature.

Time and space. Θ(n) time and O(1) space. Brute force is exponential, and even a naive DP marking reachable positions is O(n^2); the frontier is all the state needed.

Edge cases. An empty array is vacuously reached, and a single element is already at the last index. A zero is fine if an earlier jump passed it; a run of zeros the frontier cannot cross returns false. Negative jump lengths break the cast to usize.

A variation. "Jump Game II" asks for the minimum number of jumps and uses the same sweep plus one variable: count a jump whenever the frontier must advance, tracking the current jump's end separately. The greedy spirit is identical.
