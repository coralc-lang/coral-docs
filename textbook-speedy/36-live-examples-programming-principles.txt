Chapter36

Live Examples: Programming Principles

The Rules Behind the Rules

Every language feature here serves a principle older than the syntax: SOLID, DRY, cohesion, coupling, composition over inheritance, failure discipline. These shapes make code easy to change and hard to break.

Principles are stated abstractly and learned concretely. Each gets a before and an after, both in Coral: the before works but carries a debt; the after reshapes it. Coral's lack of inheritance is a gift, leaving composition, traits, and error discipline.

The before is competent deadline code, not a straw man; the after is not always right. Principles trade one cost for another, and each example says when the before is fine.

Almost every example is one move: giving duplicated knowledge a single home with a name. A duplicated loop has no name to change; a named function does. A public field cannot enforce its contract; a constructor can.

36.1 Naming: The Cheapest Documentation

The principle. A name should tell the reader what a thing is or does at the reader's level of abstraction. If you must read the body, the name has failed.

The intuition. Names are documentation that cannot go stale, because the compiler forces every use to change with them. Test: can someone who has never seen this file read the call site and know what happens?

The before.

    pub f64 calc(f64 a, f64 b) {
        // what is 0.85? the reader has to guess
        return a * b * 0.85;
    }

    pub bool chk(u32 n) {
        // and what does the range 3..24 mean?
        return n >= 3 && n <= 24;
    }

    pub void proc(Vec<f64>* d) {
        // "proc" says nothing about the 1.2 multiplier
        for (usize i = 0; i < d->count(); i += 1)
            d->set(i, d->at(i) * 1.2);
    }

Every one works, but `calc(x, y)`, `chk(n)`, and `proc(v)` say nothing about `0.85` or the range `3..24`.

The after.

    // the magic number now has a name that states the business rule
    pub const f64 WHOLESALE_MARKUP = 0.85;

    pub f64 retailPrice(f64 cost, f64 quantity) {
        // the call site reads as a sentence
        return cost * quantity * WHOLESALE_MARKUP;
    }

    // bounds carry their meaning
    pub const u32 MIN_USERNAME_LENGTH = 3;
    pub const u32 MAX_USERNAME_LENGTH = 24;

    pub bool isValidUsernameLength(u32 length) {
        return length >= MIN_USERNAME_LENGTH && length <= MAX_USERNAME_LENGTH;
    }

    pub const f64 TAX_RATE = 1.2;

    pub void applyTax(Vec<f64>* prices) {
        // the rate is named, so the intent is visible at the loop
        for (usize i = 0; i < prices->count(); i += 1)
            prices->set(i, prices->at(i) * TAX_RATE);
    }

Call sites now read as sentences: `retailPrice(cost, qty)`, `isValidUsernameLength(len)`, `applyTax(prices)`. The named constants explain the business rules, so no reader has to open a body.

Cost and notes. Longer names cost keystrokes, but `theLengthOfTheUsernameEnteredByTheUser` is worse than `usernameLength`. Short library names work because their types make the meaning obvious. Carry what the reader needs and no more.

When the before is fine. Local loop variables can be `i`, `j`, and `n` in a short, obvious loop. The principle applies to names that cross a boundary: functions, types, public fields, exported constants.

Variation. Rename a function containing `do`, `process`, `handle`, or `data` to say precisely what it does to precisely what. If you cannot, it probably does more than one thing.

36.2 DRY: Don't Repeat Yourself

The principle. Every piece of knowledge should have one authoritative representation. When a rule is written twice, the copies eventually disagree.

The intuition. The enemy is a change needed in five places and made in four. DRY gives duplicated knowledge one home, and it is about knowledge, not text: similar-looking functions with different rules stay separate.

The before. Registration validates a username in three places with slightly different rules.

    pub bool registerUser(str name) {
        // this copy of the username rule...
        if (name.len < 3 || name.len > 24) return false;      // rule A
        if (name.len == 0) return false;
        return true;
    }

    pub bool renameUser(str newName) {
        // ...is duplicated here...
        if (newName.len < 3 || newName.len > 24) return false;  // rule A again
        return true;
    }

    pub bool createGuest(str label) {
        // ...and has already drifted in this third copy
        if (label.len < 2 || label.len > 24) return false;      // rule A', drifted
        return true;
    }

The first two agree; the third has drifted to a minimum of two. When the minimum becomes four, a developer will find two of the three checks and ship a bug.

The after. One function owns the rule, and every call site asks it.

    // one authoritative home for the rule
    pub const u32 MIN_USERNAME_LENGTH = 4;
    pub const u32 MAX_USERNAME_LENGTH = 24;

    pub bool isValidUsername(str name) {
        return name.len >= MIN_USERNAME_LENGTH && name.len <= MAX_USERNAME_LENGTH;
    }

    // every caller now asks the same function
    pub bool registerUser(str name) {
        return isValidUsername(name);
    }

    pub bool renameUser(str newName) {
        return isValidUsername(newName);
    }

    pub bool createGuest(str label) {
        return isValidUsername(label);
    }

The rule now lives in one place. If guests need a different rule, that is different knowledge and earns its own function; the point is to avoid two copies of the same knowledge.

Cost and notes. The extra hop is free because the compiler inlines it. The real risk is merging functions that look alike but exist for different reasons, which couples them.

When the before is fine. Code used exactly once is not duplicated and needs no extraction. DRY is about repetition, not length.

Variation. Grep for a literal constant that appears in more than one file. Each hit is a candidate for a named constant and a place where the next change might be missed.

36.3 Single Responsibility, Cohesion, and Coupling

The principle. A module, type, or function should have one reason to change. Cohesion is how strongly the parts belong together; coupling is how much one thing depends on another. Aim for high cohesion and low coupling.

The intuition. A function that reads a file, parses it, computes a statistic, formats it, and prints it has five reasons to change, and every edit risks the other four. Split it, and a report-format change touches only the report code.

The before. A single `reportSales` does everything.

    pub struct SalesSummary {
        // the summary value the function computes then prints
        f64 total;
        f64 average;
        u32 count;
    }

    pub f64 totalOf(const Vec<f64>* values) {
        f64 sum = 0.0;
        for (usize i = 0; i < values->count(); i += 1) sum += values->at(i);
        return sum;
    }

    // this one function carries five reasons to change
    pub void reportSales(const Vec<f64>* values) {
        // load (pretend it happens here)
        // the statistic is computed inline, not returned
        f64 total = totalOf(values);
        f64 average = values->count() > 0 ? total / (f64)values->count() : 0.0;

        // format and print, all tangled with the computation
        println("Sales report");
        println("  count:   {}", values->count());
        println("  total:   {}", total);
        println("  average: {}", average);
    }

The name promises a report, but the function computes the summary, chooses a format, and writes to stdout. Reusing the summary or changing the destination means editing this function.

The after. Each concern gets a name and a home.

    pub struct SalesSummary {
        // the pure result, with no formatting attached
        f64 total;
        f64 average;
        u32 count;
    }

    // pure computation: one reason to change (the definition of the statistic)
    pub SalesSummary summarise(const Vec<f64>* values) {
        f64 total = 0.0;
        for (usize i = 0; i < values->count(); i += 1) total += values->at(i);
        u32 n = (u32)values->count();
        f64 average = n > 0 ? total / (f64)n : 0.0;
        return SalesSummary { .total = total, .average = average, .count = n };
    }

    // formatting: one reason to change (the presentation)
    pub String formatSummary(const SalesSummary* s) {
        String out = String::new();
        out.appendView("Sales report\n");
        out.appendView("  count:   " + formatInt((i64)s->count, 10, false) + "\n");
        out.appendView("  total:   " + formatFloat(s->total, 2) + "\n");
        out.appendView("  average: " + formatFloat(s->average, 2) + "\n");
        return out;
    }

    // delivery: one reason to change (the destination)
    pub void reportSales(const Vec<f64>* values) {
        // three-line composition of the three concerns
        SalesSummary s = summarise(values);
        print(formatSummary(&s));
    }

The statistic can be reused without printing, the format can change without touching the arithmetic, and the destination without touching either. `summarise` is pure and easy to test.

Cost and notes. Splitting adds types and names; too fine a split adds indirection. Use one reason to change per piece; concerns that always change together belong together.

When the before is fine. A throwaway script that runs once and is deleted needs no structure. Structure is an investment against future change.

Variation. Add `formatSummaryCSV` to the after without touching `summarise` or the arithmetic. The ease of that change measures the split.

36.4 Composition over Inheritance

The principle. Prefer combining small parts over arranging types in a hierarchy. Inheritance couples a subtype to its parent's implementation; composition couples it only to the interface it uses.

The intuition. Coral has no inheritance, removing the temptation. The employee hierarchy turns a coincidence (a contractor paid like a manager) into a kind of being. Composition says an employee has a role, a pay type, and a schedule, each independent. A type is a bag of parts, not a position in a family tree.

The before. One struct carries union-ish fields selected by a kind tag.

    enum RoleKind { Engineer, Manager, Contractor }

    pub struct Employee {
        // the tag selects which of the fields below are even meaningful
        str name;
        RoleKind kind;
        f64 baseSalary;      // meaningful for Engineer and Manager
        f64 hourlyRate;      // meaningful for Contractor
        u32 reports;         // meaningful for Manager
        u32 hoursThisWeek;   // meaningful for Contractor
    }

    pub f64 pay(const Employee* e) {
        // every new role means another branch here
        if (e->kind == RoleKind::Contractor)
            return e->hourlyRate * (f64)e->hoursThisWeek;
        return e->baseSalary;
    }

Half the fields are meaningless for any employee, and nothing stops code from reading `hourlyRate` off an engineer. Adding a role means adding fields and editing every switch on `kind`.

The after. Compose a role and a pay arrangement, each its own small value.

    variant Pay {
        // each case carries exactly the fields it needs
        Salaried { f64 base; }
        Hourly   { f64 rate; u32 hours; }
    }

    variant Role {
        // roles are a closed set of cases
        Engineer,
        Manager   { u32 reports; }
        Contractor,
    }

    pub struct Employee {
        // composed parts, not a family tree
        str name;
        Role role;
        Pay pay;
    }

    pub f64 weeklyPay(const Employee* e) {
        // depends only on the pay arrangement
        return switch (e->pay) {
            Pay::Salaried { base } => { base; },
            Pay::Hourly { rate, hours } => { rate * (f64)hours; }
        };
    }

    pub bool managesOthers(const Employee* e) {
        // depends only on the role
        return switch (e->role) {
            Role::Manager { reports } => { reports > 0; },
            else => { false; }
        };
    }

Fields travel with the case that owns them: a `Pay::Hourly` has hours, and a salaried employee has no hourly rate to ask for. `weeklyPay` depends only on pay, `managesOthers` only on role. Adding a case forces every relevant switch to handle it.

Cost and notes. Composition adds named types and makes decisions explicit and checked. That is the point. Wrapping one `f64` in a one-case variant is ceremony.

When the before is fine. A small closed set of records that share all their fields and never diverge is fine as a plain struct. Reach for composition when fields are conditionally meaningful.

Variation. Add `Role::Intern` and route it through `weeklyPay` via `Pay::Stipend { f64 amount; }`. Each place the compiler forces an update would have silently done the wrong thing before.

36.5 Open/Closed with Traits

The principle. Code should be open for extension but closed for modification: add behaviour without editing working code.

The intuition. A switch over shape kinds must be edited for every new shape, risking the old ones. A trait inverts the dependency: each shape knows its own area, and the function is written against the trait. Adding a shape is a new `extend` block; no existing line changes.

The before. One switch knows every shape.

    enum ShapeKind { Circle, Rectangle, Triangle }

    pub struct Shape {
        // one generic pair of numbers reused by every shape kind
        ShapeKind kind;
        f64 a;
        f64 b;
    }

    pub f64 area(const Shape* s) {
        // adding a shape means editing this very function
        switch (s->kind) {
            ShapeKind::Circle => { return 3.14159 * s->a * s->a; },
            ShapeKind::Rectangle => { return s->a * s->b; },
            ShapeKind::Triangle => { return 0.5 * s->a * s->b; }
        }
    }

Adding a `Pentagon` means editing this function, recompiling, and retesting everything that touches `area`. A bug here affects circles.

The after. A trait the shapes satisfy, and code written against the trait.

    import(lib) std::math::math { pi, sqrt };

    trait Shape {
        // the contract every shape must satisfy
        f64 area();
        f64 perimeter();
    }

    // each shape supplies its own area and perimeter
    pub struct Circle { f64 radius; }
    pub extend Circle : Shape {
        f64 area() { return pi * self.radius * self.radius; }
        f64 perimeter() { return 2.0 * pi * self.radius; }
    }

    pub struct Rectangle { f64 width; f64 height; }
    pub extend Rectangle : Shape {
        f64 area() { return self.width * self.height; }
        f64 perimeter() { return 2.0 * (self.width + self.height); }
    }

    // written against the contract, not against any concrete shape
    pub f64 totalArea<T>(const Vec<T>* shapes) {
        f64 sum = 0.0;
        // the compiler checks every T really satisfies Shape
        for (usize i = 0; i < shapes->count(); i += 1) sum += shapes->at(i).area();
        return sum;
    }

A third shape is a new struct and a new `extend ... : Shape` block. `totalArea` is untouched and need not be retested. A missing method or wrong signature is an E12xx diagnostic at the extend block.

Cost and notes. The trait makes new cases cheap but new operations expensive: adding `volume()` edits every implementor. Also, `totalArea<T>` is generic, so one `Vec` holds one shape type; a heterogeneous collection needs a `variant Shape`. Choose by which direction you expect to grow.

When the before is fine. A genuinely closed set with one operation and one call site is fine as a switch. The trait pays off when new cases are expected and the operation has many call sites.

Variation. Add `Square` with `extend Square : Shape`, and confirm `totalArea` works with `Vec<Square>` unchanged. Then add `describe()` to the trait and list every implementor the compiler forces you to update.

36.6 Dependency Inversion and Interface Segregation

The principle. High-level code should depend on abstractions, not concrete implementations. An interface should be small and specific, so no type is forced to implement methods it does not use.

The intuition. A registration function taking a concrete database cannot be tested without one and cannot swap it without editing. Define a small trait for exactly the operations needed and take a generic; production satisfies it, and a test uses an in-memory stand-in. Small traits keep test doubles cheap.

The before. High-level registration welded to a concrete database, and a fat trait that forces useless methods.

    trait Database {
        // the fat interface: six methods, most of them irrelevant here
        bool connect(str url);
        bool save(User u);
        Option<User> find(i32 id);
        bool delete(i32 id);
        void migrate();
        void vacuum();
    }

    // the high-level function is welded to the concrete interface
    pub bool registerUser(const User* u, Database* db) {
        return db->save(*u);        // needs only save, demands six methods
    }

Testing `registerUser` requires implementing all six methods, five of them irrelevant. Any type usable here must carry the whole fat interface.

The after. Two small traits, and a function that depends only on the one it needs.

    pub struct User { i32 id; str name; }

    trait UserWriter {
        // the one ability this consumer actually needs
        bool save(User u);
    }

    trait UserReader {
        // a separate, equally small ability
        Option<User> find(i32 id);
    }

    // Coral has no super-trait clause (`trait A : B`); when a function truly needs
    // both abilities it takes both, or takes a single trait that names both methods.

    // depends only on the ability to write
    pub bool registerUser<T>(T* store, User u) {
        return store->save(u);
    }

    // production store
    pub struct MemoryStore {
        Vec<User> users;
    }

    pub extend MemoryStore : UserWriter {
        bool save(User u) {
            self.users.push(u);
            return true;
        }
    }

    // test stand-in: implements only what the test touches
    pub struct FailingStore { bool failNext; }
    pub extend FailingStore : UserWriter {
        bool save(User u) {
            // the contract permits returning false, so this is substitutable
            if (self.failNext) return false;
            return true;
        }
    }

`registerUser` now depends on a one-method abstraction. Production passes a `MemoryStore`; a test passes a `FailingStore` that can make `save` fail on demand. The function cannot call `delete` or `vacuum` because it never asked for that ability.

Cost and notes. Define traits for what a consumer needs, not everything a type has. Liskov substitutability is the companion rule: honour the contract, not merely the signatures. `FailingStore` is substitutable because `UserWriter` permits `save` to return false; silently dropping writes while returning true would violate it.

When the before is fine. A single concrete implementation with no prospect of a second and no isolation need is fine to pass directly. The abstraction pays off with a second implementation or a real chance of swapping.

Variation. Add a `UserDeleter` trait and a `manageUser` function constrained to a `UserStore` that composes writing and deleting. Make `registerUser` take `UserWriter` and `manageUser` the composed trait; explain why the narrower function is easier to test.

36.7 Error-Handling Discipline

The principle. Failure is a value. An operation that can fail says so in its return type, and the caller must deal with the failure to get the result. A sentinel that collides with real data is a bug waiting to happen.

The intuition. Returning `-1` for not found or `null` for failed is fast and lies to the type system: an `i64` that is sometimes a failure is two things wearing one type. Callers forget to check, real data equals the sentinel, and the failure surfaces far from its cause. Use `Option` when there is nothing to say, `Result` when you can say why.

The before. Sentinels everywhere.

    pub i32 parseAge(str s) {
        // returns -1 on failure, but -1 is not a valid age, so it seems safe
        bool ok;
        i64 value = parseI64(s, &ok);
        if (!ok) return -1;
        return (i32)value;
    }

    pub void showAge(str s) {
        // the caller must remember to check the sentinel
        i32 age = parseAge(s);
        if (age == -1) {
            println("bad age");
            return;
        }
        println("age {}", age);
    }

The `-1` convention is checked nowhere. A caller that forgets prints '-1 years old'; a caller with a negative input gets 'bad age' for the wrong reason; and a legal `-1` triggers a false alarm.

The after. A `Result` whose error variant names the cause.

    import(lib) std::io::ios { parseI64 };

    pub variant AgeError {
        // each failure mode is a distinct, nameable case
        NotANumber { str text; },
        Negative   { i32 value; },
        TooLarge   { i32 value; },
    }

    pub Result<i32, AgeError> parseAge(str s) {
        bool ok;
        i64 value = parseI64(s, &ok);
        // the failure and the reason travel in the return type
        if (!ok) return Result<i32, AgeError>::Err { .error = AgeError::NotANumber { .text = s } };
        if (value < 0) return Result<i32, AgeError>::Err { .error = AgeError::Negative { .value = (i32)value } };
        if (value > 150) return Result<i32, AgeError>::Err { .error = AgeError::TooLarge { .value = (i32)value } };
        return Result<i32, AgeError>::Ok { .value = (i32)value };
    }

    pub void showAge(str s) {
        // the switch is exhaustive: no success path can ignore the error
        switch (parseAge(s)) {
            Result::Ok { value } => { println("age {}", value); },
            Result::Err { error } => {
                switch (error) {
                    AgeError::NotANumber { text } => { println("'{}' is not a number", text); },
                    AgeError::Negative { value } => { println("age {} is negative", value); },
                    AgeError::TooLarge { value } => { println("age {} is implausibly large", value); }
                }
            }
        }
    }

The type now carries the failure and the reason. The compiler will not let `showAge` reach the value without handling the error, and the three failure modes can be handled differently.

Cost and notes. `Result` is more verbose, and if `Err` is always replaced by a default, the machinery is overhead. If a caller can respond reasonably, return `Result`; if the only response is 'the program is wrong,' assert.

When the before is fine. A private helper whose sentinel is impossible in its domain and whose callers are all in one file is survivable. Once the function crosses a module boundary, the type must carry the truth.

Variation. Add `parseAges` for a `Vec<str>` returning `Result<Vec<i32>, AgeError>` and stopping at the first failure. Then collect failures into a `Vec<AgeError>` and return both successes and errors; explain which signature is kinder to the caller.

36.8 Invariants, Assertions, and Defensive Programming

The principle. An invariant must always hold for a value to be meaningful. Establish it at creation and enforce it there; use assertions to catch violations that indicate bugs. Defensive programming, checking every argument against every bad value, hides bugs rather than finding them.

The intuition. A range has the invariant `lo <= hi`. With public fields, every method must defend against a broken range forever. With a constructor as the only door, every method can assume it. Assertions state internal assumptions; defensive checks are for external input.

The before. Public fields, no constructor, defensive checks scattered everywhere.

    pub struct Range {
        // public fields: nothing enforces lo <= hi
        i32 lo;
        i32 hi;
    }

    pub i32 rangeLength(const Range* r) {
        if (r->lo > r->hi) return 0;          // one of many defensive checks
        return r->hi - r->lo;
    }

    pub bool rangeContains(const Range* r, i32 x) {
        if (r->lo > r->hi) return false;       // and another
        return x >= r->lo && x <= r->hi;
    }

Every operation defends against an illegal state that should never exist. The checks are inconsistent (one returns zero, one false), slow every call, and camouflage the real bug.

The after. A constructor establishes the invariant, accessors assume it, and assertions name the contract.

    pub struct Range {
        // fields stay private so only make() can create a Range
        i32 lo;
        i32 hi;

        static Option<Range> make(i32 lo, i32 hi) {
            // the one door: the invariant is checked exactly here
            if (lo > hi) return Option<Range>::None;
            return Option<Range>::Some { .value = Range { .lo = lo, .hi = hi } };
        }

        // the invariant is established by make(); these methods may assume it
        i32 length() {
            @assertOut(self.lo <= self.hi, "Range invariant violated: lo > hi");
            return self.hi - self.lo;
        }

        bool contains(i32 x) {
            // the assertion is a bug check, not input validation
            @assertOut(self.lo <= self.hi, "Range invariant violated: lo > hi");
            return x >= self.lo && x <= self.hi;
        }
    }

The illegal range cannot be built through the one door, so the methods need no defensive branch. The assertion checks that the code which built this range honoured its contract; if it fires, it points at a bug. Outside input is handled at the boundary, where `make` returns an `Option`.

Cost and notes. Private fields buy the invariant at the cost of direct access. The checks are cheap and may be compiled away in release. `Result` is for what the world does to you; assertions for what your own code should never do.

When the before is fine. A throwaway struct constructed in one place and never escaping is fine with public fields. The invariant earns its constructor when the value crosses module boundaries or is built in many places.

Variation. Add `union(const Range* a, const Range* b)` returning the smallest range containing both. Prove in a comment that it preserves `min(lo) <= max(hi)`, so no caller needs to defend against it.

36.9 Testing with std::testing

The principle. Tests are executable specifications. A property test is worth more than one that merely exercises the code, because it catches inputs you did not think to try.

The intuition. Printing results and squinting works once and rots: output changes, expected values are not updated, and nobody notices. A real test states an expectation and fails loudly. Property tests check a property across many inputs.

The before. Verification by printing.

    pub u64 gcd(u64 a, u64 b) {
        // Euclid's algorithm, untouched by the "test" below
        while (b != 0) { u64 t = a % b; a = b; b = t; }
        return a;
    }

    pub void main() {
        // printing a result is not testing it: no expectation is checked
        println("{}", gcd(12, 18));    // expect 6
        println("{}", gcd(18, 12));    // expect 6
        println("{}", gcd(17, 5));     // expect 1
    }

A human must compare the output to a remembered expectation, and nothing fails automatically. Change `gcd` to return `b` by mistake and the program still exits zero.

The after. Tests with a runner, including a property that spans many inputs.

    import(lib) std::testing::test {
        _testBegin, _testEnd, assertEq, assertTrue, testSummary, testAllPassed
    };

    pub u64 gcd(u64 a, u64 b) {
        // the unit under test, unchanged between the two versions
        while (b != 0) { u64 t = a % b; a = b; b = t; }
        return a;
    }

    #[[test]]
    void gcdKnownValues() {
        _testBegin("gcd known values");
        // the same examples as before, now with assertions that can fail
        assertEq(6u, gcd(12, 18), "gcd(12,18)");
        assertEq(6u, gcd(18, 12), "gcd(18,12)");
        assertEq(1u, gcd(17, 5), "gcd(17,5)");
        assertEq(0u, gcd(0, 0), "gcd(0,0)");
        _testEnd();
    }

    #[[test]]
    void gcdIsCommutative() {
        _testBegin("gcd is commutative");
        // a property checked across a range, not a single example
        for (u64 a = 0; a < 200; a += 1)
            for (u64 b = 0; b < 200; b += 1)
                assertTrue(gcd(a, b) == gcd(b, a), "commutativity in range");
        _testEnd();
    }

    #[[test]]
    void gcdDividesBoth() {
        _testBegin("gcd divides both inputs");
        // the defining property of a GCD, over a quarter million pairs
        for (u64 a = 1; a < 500; a += 1) {
            for (u64 b = 1; b < 500; b += 1) {
                u64 g = gcd(a, b);
                assertTrue(a % g == 0 && b % g == 0, "g divides a and b");
            }
        }
        _testEnd();
    }

    pub i32 main() {
        // run every test, then exit non-zero if any failed
        gcdKnownValues();
        gcdIsCommutative();
        gcdDividesBoth();
        testSummary();
        return testAllPassed() ? 0 : 1;
    }

The tests say far more than the printed numbers. `gcdIsCommutative` covers forty thousand pairs and `gcdDividesBoth` states the defining property across a quarter of a million, either catching a subtly wrong implementation. The `#[[test]]` attribute lets `coralc test` discover them.

Cost and notes. Property tests use exhaustive small ranges rather than random large ones. The harness is deliberately minimal: no fixtures, no mocking. `assertEq` compares `usize`, so signed checks use `assertTrue`.

When the before is fine. A quick experiment while you are still deciding what the code should do is fine to verify by printing. The mistake is shipping the print-and-squint version as the test.

Variation. Add a test for the modular exponentiation from Chapter32.4 that checks `(base^exp) mod m` against a slow repeated-multiplication reference for small values. Note that the property test catches off-by-one errors in the exponent's bit loop that a few examples would miss.

36.10 Refactoring a Messy Example: From Script to Module

The principle. Refactoring changes the shape of code without changing what it does. The goal is to make the next change easy; success means identical behaviour and a name for each idea.

The intuition. This capstone uses every principle. The script reads comma-separated name-and-score pairs, computes an average, and prints a summary: forty lines with single-letter variables, magic numbers, a sentinel, and duplicated parsing. The refactor names things, separates concerns, replaces the sentinel with a `Result`, and leaves `main` as six lines of composition.

The before.

    pub void main() {
        // parsing, validation, statistics and formatting all in one function
        Vec<f64> scores = Vec<f64>::new();
        u32 bad = 0;

        String line = String::new();
        while (readLine(&line)) {
            // opaque single-letter names: s, v, comma
            str s = line.asView();
            usize comma = s.findByte(',');
            if (comma >= s.len) { bad += 1; continue; }
            str scoreText = str::fromParts(s.ptr + comma + 1, s.len - comma - 1);
            bool ok;
            f64 v = parseF64(scoreText, &ok);
            if (!ok) { bad += 1; continue; }
            // the bound 100.0 is a magic number buried inline
            if (v < 0.0 || v > 100.0) { bad += 1; continue; }
            scores.push(v);
        }

        f64 total = 0.0;
        for (usize i = 0; i < scores.count(); i += 1) total += scores.at(i);
        // -1.0 is a sentinel for "no scores", indistinguishable from a real -1
        f64 avg = scores.count() > 0 ? total / (f64)scores.count() : -1.0;

        // the report format is tangled with everything above
        println("=== Report ===");
        println("records: {}", scores.count());
        println("bad:     {}", bad);
        if (avg < 0.0) {
            println("average: n/a");
        } else {
            println("average: {}", avg);
        }
    }

Every problem is present: `line`, `s`, `v`, and `comma` are opaque; `-1.0` collides with a legitimate average; parsing, validation, statistics, and formatting are one knot; `100.0` is inline; and the average cannot be tested alone.

The after.

    import(lib) std::io::ios { readLine, parseF64, println };
    import(lib) std::text::string { String };
    import(lib) std::vec { Vec };

    // the bounds are named constants instead of inline magic numbers
    pub const f64 MIN_SCORE = 0.0;
    pub const f64 MAX_SCORE = 100.0;

    pub struct Record {
        f64 score;      // the name is validated here; a real program would keep
                        // an owned copy, since a str would view the reused line
    }

    pub variant ParseError {
        // every rejection reason is a distinct case
        NoComma      { str text; },
        BadScore     { str text; },
        OutOfRange   { f64 value; },
    }

    // one concern: turn a line into a record or an error
    pub Result<Record, ParseError> parseRecord(str line) {
        usize comma = line.findByte(',');
        if (comma >= line.len)
            return Result<Record, ParseError>::Err { .error = ParseError::NoComma { .text = line } };

        str scoreText = str::fromParts(line.ptr + comma + 1, line.len - comma - 1);

        bool ok;
        f64 value = parseF64(scoreText, &ok);
        if (!ok)
            return Result<Record, ParseError>::Err { .error = ParseError::BadScore { .text = scoreText } };
        // range check against the named bounds
        if (value < MIN_SCORE || value > MAX_SCORE)
            return Result<Record, ParseError>::Err { .error = ParseError::OutOfRange { .value = value } };

        return Result<Record, ParseError>::Ok { .value = Record { .score = value } };
    }

    pub struct Summary {
        // the computed statistics, ready for display
        u32 valid;
        u32 rejected;
        f64 sum;
    }

    // one concern: the statistics, with no I/O and no formatting
    pub Summary summarise(const Vec<Record>* records, u32 rejected) {
        f64 sum = 0.0;
        for (usize i = 0; i < records->count(); i += 1) sum += records->at(i).score;
        return Summary { .valid = (u32)records->count(), .rejected = rejected, .sum = sum };
    }

    // one concern: the presentation; "no scores" is a real case, not a sentinel
    pub void printReport(const Summary* s) {
        println("=== Report ===");
        println("records: {}", s->valid);
        println("bad:     {}", s->rejected);
        // valid == 0 is the honest test; a zero average prints as zero
        if (s->valid == 0)
            println("average: n/a");
        else
            println("average: {}", s->sum / (f64)s->valid);
    }

    pub void main() {
        // main is now composition: parse, summarise, print
        Vec<Record> records = Vec<Record>::new();
        u32 rejected = 0;
        String line = String::new();
        while (readLine(&line)) {
            // the Result forces us to count the rejected lines
            switch (parseRecord(line.asView())) {
                Result::Ok { value } => { records.push(value); },
                Result::Err { error } => { rejected += 1; }
            }
        }
        Summary s = summarise(&records, rejected);
        printReport(&s);
    }

The same behaviour, restructured. `parseRecord` owns parse-and-validate and returns a `Result` naming each failure, so an unknown error is impossible. `summarise` is pure arithmetic. `printReport` handles no-scores explicitly, and `valid == 0` is the honest test. `main` is six lines of composition.

Cost and notes. The refactor is longer, which is normal: named ideas take more text. New fields, error variants, formats, or isolated tests now cost one line instead of surgery. If the script is never touched again, the refactor was not worth it.

When the before is fine. A script that runs once, on one file, and is deleted should stay a script. Refactor code that will live, change, and be read by someone else.

Variation. Add `printReportCSV` and change `main`'s last line. Then add filtering below a threshold, which means filtering `Vec<Record>` before `summarise`. Notice that neither change touches the parser, and say which principle that shows.

36.11 The Law of Demeter

The principle. Code should talk only to its immediate collaborators, through their interfaces, not through their collaborators' collaborators. Ask the object that owns the data.

The intuition. A long navigation chain is a public statement of how types are wired. `a->customer.address.city` depends on `Order` having `Customer`, `Customer` having `Address`, and `Address` having `city`; any can change and break this line. Move the question down the chain.

The before. A function that reaches through two levels to compare two orders.

    pub struct Address { str city; str postalCode; }
    pub struct Customer { Address address; }
    pub struct Order { Customer customer; f64 total; }

    pub bool shipsToSameCity(const Order* a, const Order* b) {
        // a train wreck: three dots deep into the object graph
        return a->customer.address.city.equals(b->customer.address.city);
    }

The comparison knows the entire object graph. Introduce a `Region` between `Customer` and `Address` and every function that made the same reach fails to compile.

The after. Each type answers a question at its own level, reaching one step at most.

    pub struct Address {
        str city;
        str postalCode;

        bool sameCity(const Address* other) {
            // each type answers the question at its own level
            return self.city.equals(other->city);
        }
    }

    // each layer hides the one below it
    pub struct Customer {
        Address address;

        bool livesInSameCityAs(const Customer* other) {
            return self.address.sameCity(&other->address);
        }
    }

    pub struct Order {
        Customer customer;

        bool shipsToSameCityAs(const Order* other) {
            // reaches exactly one step, no further
            return self.customer.livesInSameCityAs(&other->customer);
        }
    }

`Order::shipsToSameCityAs` knows only that it has a `Customer`, and `Customer` only that it has an `Address`; the call site is `a->shipsToSameCityAs(b)`. A later `Region` type changes only `Address`.

Cost and notes. The refactor adds one method per level. The dependency graph becomes shallow: each method is testable with one fake collaborator, and internal changes do not ripple outward. This is the mirror image of DRY: it refuses to let knowledge leak.

When the before is fine. Plain data-transfer structs exist to be read field by field; reaching into a `Point` for its `x` is not a violation. The rule is about behaviour and deep chains, not a single field access.

Variation. Find a line with three or more dots and give the type a method that answers the underlying question. Put the method at the lowest level that can answer it.

36.12 Immutability and Pure Functions

The principle. Prefer values that do not change after creation, and functions that compute from their arguments without touching anything outside. A pure function is easier to test, safe to call twice, safe to parallelize, and safe to cache.

The intuition. The enemy is state that drifts. Two pieces of information kept in agreement by hand invite a bug when one changes and the other does not. A pure function has no agreement to maintain, and an immutable value can be shared freely.

The before. A cart caches its own total and mutates in place.

    import(lib) std::vec { Vec };

    pub struct Cart {
        // two pieces of state that must be kept in agreement by hand
        Vec<f64> prices;
        f64 total;      // kept in step with prices by hand
    }

    pub void addItem(Cart* c, f64 price) {
        // mutating both fields together is a contract nothing enforces
        c->prices.push(price);
        c->total += price;
    }

    pub f64 applyDiscount(Cart* c, f64 percent) {
        // mutates in place: calling twice discounts twice
        c->total = c->total * (1.0 - percent);
        return c->total;
    }

Calling `applyDiscount` twice discounts twice. Adding an item after a discount loses it because `total` and `prices` have fallen out of agreement; nothing enforces the contract.

The after. A value, plus functions that read it through a `const` pointer and return a new value.

    import(lib) std::vec { Vec };

    // the only field; total is derived, never stored
    pub struct Cart { Vec<f64> prices; }

    pub f64 cartTotal(const Cart* c) {
        // pure: depends only on c and never mutates it
        f64 sum = 0.0;
        for (usize i = 0; i < c->prices.count(); i += 1) sum += c->prices.at(i);
        return sum;
    }

    pub Cart withItem(const Cart* c, f64 price) {
        // returns a new cart; the original is untouched
        Cart next;
        next.prices = Vec<f64>::new();
        for (usize i = 0; i < c->prices.count(); i += 1) next.prices.push(c->prices.at(i));
        next.prices.push(price);
        return next;
    }

    pub Cart discounted(const Cart* c, f64 percent) {
        // discounting is a value transformation, not an in-place edit
        Cart next;
        next.prices = Vec<f64>::new();
        for (usize i = 0; i < c->prices.count(); i += 1)
            next.prices.push(c->prices.at(i) * (1.0 - percent));
        return next;
    }

`cartTotal` is pure: it returns the same answer every time and cannot change the cart. `discounted` returns a new cart, so discounting twice is explicit. The `const` parameter stops mutation even by mistake.

Cost and notes. Immutability copies: `withItem` and `discounted` allocate a new vector, where the mutating version edited in place. That is nothing for ten prices and real for a million-element hot loop, which is why performance-critical code mutates a local buffer it owns or uses a persistent structure. The trade removes a class of bugs.

When the before is fine. A tight numeric loop mutating a buffer it created and will discard is exactly right. The discipline is about shared, long-lived values. The mistake is exposing mutation on a value callers hold and reuse.

Variation. Take `summarise` from 35.3, which is already pure, and add a memoised wrapper that caches the last result for repeated identical input. Explain why caching is safe only because the function is pure.

36.13 The Strategy Pattern with Function Pointers

The principle. When code has several interchangeable algorithms, give the algorithm a name and pass it in rather than selecting with a type switch. The consuming code stops knowing which one it has.

The intuition. A switch over an operation enum welds the caller to the whole family: every new operation edits the function. Passing the operation as a value inverts that: adding an operation is adding a function, with no edit to the consumer. The lightest such value is a function pointer.

The before. A calculator that switches on an operation tag.

    enum Op { Add, Sub, Mul }

    pub f64 compute(Op op, f64 a, f64 b) {
        // every new operation is a new arm here
        switch (op) {
            Op::Add => { return a + b; },
            Op::Sub => { return a - b; },
            Op::Mul => { return a * b; }
        }
    }

Every new operation edits `compute` and the enum, and every edit risks the operations that already worked.

The after. The operation is a function value; the consumer knows only its shape.

    import(lib) std::vec { Vec };

    // each algorithm is a plain function of the same shape
    pub f64 addOp(f64 a, f64 b) { return a + b; }
    pub f64 subOp(f64 a, f64 b) { return a - b; }
    pub f64 mulOp(f64 a, f64 b) { return a * b; }

    pub f64 compute(f64(f64, f64) op, f64 a, f64 b) {
        // the consumer knows only the function's shape
        return op(a, b);
    }

    pub f64 reduce(const Vec<f64>* xs, f64(f64, f64) op) {
        @assertOut(xs->count() > 0, "reduce needs at least one element");
        // the same strategy value drives a fold
        f64 acc = xs->at(0);
        for (usize i = 1; i < xs->count(); i += 1) acc = op(acc, xs->at(i));
        return acc;
    }

`compute(addOp, 3.0, 4.0)` and `compute(mulOp, 3.0, 4.0)` choose the algorithm at the call site, and `compute` is one line. A fourth operation is a new function. `reduce` reuses the strategy for a fold, which is why `sortBy` takes a comparison function of this shape.

Cost and notes. A function-pointer call is indirect and may not inline unless the target is known; the switch version inlines easily. The benefit is openness and runtime choice. The cost is lost exhaustiveness.

When the before is fine. A small, closed set of operations used in one place is fine as a switch; exhaustiveness is worth more than openness there. Use a function pointer when the set will grow or the choice is data-driven.

Variation. Add a `bool(f64, f64) less` strategy to a manual sort and observe that it is the same pattern as `Vec::sortBy`. Compare it with the trait strategy of 35.5: use the pointer for stateless algorithms, the trait when the strategy carries state.

36.14 The Null Object Pattern

The principle. When a collaborator may be absent, do not make every caller check. Provide an object that implements the same interface and does nothing.

The intuition. A nullable collaborator puts a check at every use, and one forgotten check is a crash. A null object makes the interface always callable: 'do nothing' is explicit behaviour rather than an absence to remember.

The before. A process that must check its logger everywhere.

    pub struct ConsoleLogger {
        void log(str msg) { println("{}", msg); }
    }

    pub void process(ConsoleLogger* logger, u64 taskId) {
        // every use must re-check for null; one miss is a crash
        if (logger != null) logger->log("start");
        // ... do the work ...
        if (logger != null) logger->log("done");
    }

The check repeats at every call, and a caller with no logger must pass `null` and hope every site checks. One missed check is a null dereference far from the call that allowed it.

The after. A trait, a real implementation, and a silent one.

    trait Logger {
        // the callable interface, always present
        void log(str msg);
    }

    pub struct ConsoleLogger { str label; }
    pub extend ConsoleLogger : Logger {
        void log(str msg) { println("[{}] {}", self.label, msg); }
    }

    pub struct NullLogger { str label; }
    pub extend NullLogger : Logger {
        void log(str msg) { }          // stays silent, on purpose
    }

    pub void process<T>(T* logger, u64 taskId) {
        // no null check anywhere: absence is a real object
        logger->log("start");
        // ... do the work ...
        logger->log("done");
    }

There is now no null and no check. A caller wanting logs passes a `ConsoleLogger`; one wanting silence passes a `NullLogger`; a test passes a recording logger. `process` does not change.

Cost and notes. The null object requires constructing a value and adds one struct and one no-op method per interface. Use it only for benign absence: a silent logger is fine, a silent database is a lie. A no-op is not for hiding failure.

When the before is fine. When absence means something the caller must branch on (a required service, a file that must exist), use `Result` or `Option`; a null object would swallow the problem. Use it where 'off' is a real mode.

Variation. Add a `RecordingLogger` that appends to `Vec<str>` and use it in a test without a console or mock framework. Then add a `FanoutLogger` that forwards to two loggers; composition makes it easy.

36.15 Backwards-Compatible API Design

The principle. When a widely used type or function must gain a capability, extend the surface without reshaping it, so existing callers keep compiling and behaving as before.

The intuition. The most common breakage comes from a helpful feature. A struct with public fields is built by literal everywhere, so adding a field breaks all call sites. Own construction: a constructor with defaults, private fields, and capabilities as functions or builder steps.

The before. A request struct every caller builds with a literal.

    pub struct Request {
        // public fields mean every caller writes a literal
        str url;
        u32 timeoutMs;
    }

    pub void send(const Request* r) { /* ... */ }

Every caller writes `Request { .url = "...", .timeoutMs = 1000 }`. Adding a `u32 retries` field with a default of zero breaks every literal in the codebase.

The after. A constructor owns the defaults, and new options are additive.

    pub struct Request {
        str url;
        u32 timeoutMs;
        // new capability added without breaking existing literals
        u32 retries;
    }

    pub Request request(str url) {
        // the constructor owns the defaults; a new field is one line here
        return Request { .url = url, .timeoutMs = 1000, .retries = 0 };
    }

    pub Request withTimeout(Request r, u32 ms) {
        // additive builder step, so existing call sites never move
        r.timeoutMs = ms;
        return r;
    }

    pub Request withRetries(Request r, u32 n) {
        r.retries = n;
        return r;
    }

    pub void send(const Request* r) { /* ... */ }

Callers write `send(&withRetries(request(url), 3))` or `send(&request(url))` for defaults. Adding `retries` was one line in `request`, and no call site moved. Private fields stop callers from skipping the defaults.

Cost and notes. The type is no longer a transparent record, and callers must use the constructor and builder steps. The payoff is free additive change once callers are outside your control. For functions, add `sendWithOptions`; for an enum, adding a variant breaks every exhaustive switch, which argues for an `else` arm or a second function.

When the before is fine. An internal struct with one or two call sites in one file is cheaper to change directly. The discipline earns its keep at a boundary between teams, where you cannot edit the callers.

Variation. Add a fourth case to the `AgeError` variant from 35.7 and count the `switch` statements that must change. Then add the same information as a new function and count again; the difference is the cost of a breaking change.
