Chapter7

Generics and Compile-Time Computation

Write It Once, For Every Type

You have likely written the same function for `i32`, `f64`, and `char`, changing only the type. The bodies are identical, and copying is a maintenance hazard.

Generic programming writes each once, parameterised by what varies, and lets the compiler produce per-type versions. Coral's generics are monomorphised: each concrete use gets its own machine code, with no runtime cost and no boxing.

This chapter covers three tools. Value generics parameterise code by a compile-time constant, a size or count that becomes part of the type's identity. `comptime` runs ordinary Coral during the build, selecting code and rejecting bad instantiations. It is not a separate macro language.

7.1 Generic Functions

A generic function declares its type parameters in angle brackets between its name and its parameter list:

    T max<T>(T a, T b) {
        return a > b ? a : b;
    }

Read `<T>` as "for any type T." The function takes two values of some type `T` that supports `>` and returns the larger.

    i32 n = max(3, 7);          // compiler makes max<i32>
    f64 f = max(1.5, 0.5);      // compiler makes max<f64>
    char c = max('a', 'z');     // compiler makes max<char>

The `<T>` is a blank labelled T. Call `max` with integers and the compiler fills in `i32`; call it with floats and it fills in `f64`.

Nothing here is dynamic. `max(3, 7)` emits `max<i32>`; `max(1.5, 0.5)` emits `max<f64>`. That is what "monomorphised" means: one generated copy per shape.

The call site deduces type arguments from the arguments, so you rarely write `max<i32>(3, 7)`. Spell them out when deduction is ambiguous or a parameter does not appear in the argument list.

Type deduction is a matching problem: the compiler lines up declared parameter types against argument types and solves for the parameters.

    struct(A, B) makePair<A, B>(A first, B second) {
        return (first, second);
    }

    struct(str, i32) named = makePair("answer", 42);

The compiler unifies `A` with `str` and `B` with `i32`, producing `makePair<str, i32>`. Conflicting constraints make the call ambiguous, and Coral does not silently promote arguments; write the conversion explicitly, as in `max<i32>((i32)a, b)`.

What does `T` know how to do? In `max`, the body uses `a > b`, so the function only compiles for types that support `>`. Coral has no `T : Comparable` bound: the requirement lives in the body and is checked at instantiation. To assert capabilities up front, use a `comptime` block with `@typeof(T)` and `@compileError`.

7.2 Generic Types

Types can be generic too, and this is where the standard library lives: `Vec<T>`, `Map<K, V>`, `Option<T>`, `Result<T, E>`. The simplest useful one is a box holding exactly one value:

    struct Box<T> {
        T value;
    }

    pub extend<T> Box<T> {
        static Box<T> of(T value) {
            return Box<T> { .value = value };
        }

        T get() const {
            return self.value;
        }

        void set(T value) {
            self.value = value;
        }
    }

    Box<i32> b = Box<i32>::of(42);
    i32 v = b.get();

Every use with a concrete type parameter produces a concrete type. `Box<i32>` differs from `Box<str>`, with a field of the appropriate type and specialised methods. The parameter is in scope throughout the extend block, and generic types nest: `Box<Box<i32>>` generates both layers.

A generic type is a container whose contents are not decided until you use it. `Box<T>` says "a box of something"; `Box<i32>` says "a box of integers."

The standard library's `Vec` is the canonical generic type: generic over the element type, with an extend block generic in the same parameter. A `Vec<f64>` is a real array of `f64`, not a boxed array of `void*`, with no per-element indirection.

7.3 Value Generics: When the Size Is Part of the Type

Sometimes what varies is a number that belongs in the type. A matrix is 3x3 or 4x4, and mixing the two silently is a bug. Coral lets a type be parameterised by a value:

    struct Matrix<T, usize Rows, usize Cols> {
        T data[Rows * Cols];
    }

`Rows` and `Cols` are compile-time constants, so `Rows * Cols` is a compile-time expression. The compiler knows the size without running anything, and literal indexing can be bounds-checked before the program runs.

    Matrix<f64, 3, 3> identity = ...;

A value generic puts a number into the type's name. `Matrix<f64, 3, 3>` and `Matrix<f64, 4, 4>` are different types, so they cannot be swapped.

The size is exact, so you cannot pass a 3x3 where a 4x4 is expected, and every method sees it as a constant the compiler can use.

The standard library uses the same idea. `Arr<T, N>` is a fixed-size array with `N` in the type, `Bitset<N>` a bit set with a declared width. The size is part of the type, so it cannot disagree with the storage.

If the size were an ordinary field, matrices of different sizes would be the same type, and the guarantee that the array holds exactly Rows times Cols elements would be a convention. A convention can be violated; a type cannot. A 3x3 times a 4x4 becomes a compile error.

A value generic is checked when the type is instantiated, so an impossible instantiation can be rejected at compile time, the subject of 7.7.

7.4 comptime: Running Ordinary Code Early

`comptime` computes at compile time, and its principle is simple: it is the same language you already write, evaluated during the build. A comptime block contains ordinary assignments, `if`s, `switch`es, loops, and calls.

    comptime {
        const TABLE_SIZE = 256;
        const STEP = 0x9E3779B9;
    }

There is no macro syntax to learn and no expansion output to decode. The block is Coral. The difference is when it runs.

`comptime` means "do this while building the program, not while running it." The results are ready before the program starts.

A comptime block may also choose which code is emitted. Values and types inside it are known at compile time, so a `switch` resolves to a single arm:

    void makeParser<comptime Token>() {
        comptime {
            switch (Token) {
                Token::Ident  => { /* emit identifier parsing */ }
                Token::Number => { /* emit number parsing */ }
                Token::String => { /* emit string parsing */ }
            }
        }
    }

The type `Token` is a compile-time value; the switch is decided during compilation; only the matching arm is generated. The others are never generated, not merely dropped as dead code. The generator is the language, and its mistakes use the language's own diagnostics.

7.5 comptime Type Parameters and Deduction: How print Works

A generic parameter may be marked `comptime`, which changes who supplies it. An ordinary type parameter is supplied by the caller, deduced from an argument's type. A `comptime` type parameter is deduced by the function itself, from a comptime block in its body:

    void print<comptime T>(T fmt, ...) {
        comptime {
            // derive T from the arguments, then decide how to render each
        }
    }

`print` must accept a format string and any number of arguments of any types, and must know each argument's type to convert it to text. The caller passes the format string but never writes the argument types, so the function works them out inside the comptime block.

The standard library's real `print` has this signature:

    pub void print<comptime T>(T fmt, ...) { ... }

The `...` is a variadic tail. When you call `println("x = {}, y = {}", x, y)`, the compiler has the literal format and the argument types, and the comptime logic walks the format, matching each `{}` to the next argument and choosing a renderer by type. None of this is a runtime scan.

A function whose generic list uses a `comptime` parameter must contain a `comptime` block, or there is nowhere for the type to be derived. The compiler rejects it.

`println` is not a C-style variadic function with erased argument types and a runtime-trusted format, and not a preprocessor macro. It is an ordinary generic function whose type argument is computed at compile time.

7.6 Format Strings, @isFormatLiteral, and Checked Printing

In C, `printf("%d", "hello")` compiles, runs, and prints garbage, because the format is a runtime string and arguments are erased. Coral closes that hole with `@isFormatLiteral(fmt)`, true when the argument is a literal known at compile time.

If the format is a literal, Coral can read the `{}` placeholders and compare them to the values at build time, turning a class of runtime bugs into messages while you type.

The check walks the format at comptime and produces E09xx diagnostics. A placeholder with no matching argument, an argument with no placeholder, an unknown specifier, or a specifier demanding the wrong kind of argument is a compile error.

    println("{} {}", a);        // error E0901: too few arguments for 2 placeholders
    println("{q}", value);      // error E0903: unknown specifier `q`; did you mean `{}`?
    println("{:d}", someString);// error E0902: `:d` requires an integer argument

The normal cases simply work:

    println("name = {}\n", name);
    println("x = {:x}, bits = {:b}", flags, flags);
    println("pi is about {:.3}", 3.14159);
    println("items = {..}", values);      // spread an iterable, separated by ", "

When `@isFormatLiteral` is false, the format was built at runtime, so the compiler cannot see it. Every argument is rendered through its built-in or `@toStr` path, with no placeholder checking. Most format strings are literals, and for those the check is free.

Because the format and arguments are both visible during the build, a class of error that is a runtime crash in C is a build failure reported at the line.

7.7 Asking the Compiler Questions: @sizeof, @typeof, and alignof

To specialise or reject based on a type, a comptime block needs to ask the compiler questions about it. Three queries cover most of the ground, all evaluated during compilation.

`@sizeof` asks how many bytes a type takes, `@typeof` asks what type an expression has, and `alignof` asks what memory boundary a type prefers.

`@sizeof(T)` is the size of a type in bytes. Use it to branch on layout and to assert layout assumptions:

    comptime {
        if (@sizeof(Header) != 16) {
            @compileError("Header must be exactly 16 bytes on the wire");
        }
    }

`@typeof(expr)` is the type of an expression. It lets a comptime block discover what it was handed and is the workhorse of the printing machinery, where dispatch is a switch over `@typeof(T)`.

`alignof(T)` is the alignment the type requires. It matters when placing things in memory by hand and you need the boundary the hardware wants:

    usize stride = alignUp(count * @sizeof(Item), alignof(Item));

With these three, a generic can specialise or reject based on the concrete layout of its type parameter, which erased runtime generics cannot do.

7.8 Rejecting Bad Instantiations: @compileError

A generic that cannot support an instantiation should fail at compile time. `@compileError` takes a message and stops the build at the offending instantiation:

`@compileError` plants a tripwire: if someone uses the function in a way it cannot handle, the build stops with your sentence at the line that caused it.

    T firstElement<T>(Vec<T> v) {
        comptime {
            if (@sizeof(T) == 0) {
                @compileError("firstElement cannot be called for a zero-sized type");
            }
        }
        return v.at(0);
    }

The compiler evaluates the comptime block during instantiation; if the condition holds, the build fails with the given sentence at the call site. The E11xx diagnostics stand behind it: a comptime loop that never terminates is cut off with the macro call stack shown (E1103), and a comptime block reading runtime-only memory is reported (E1101).

7.9 When to Use Which

Four mechanisms can look interchangeable and are not.

Ask what changes from use to use. If it is a type, use a generic type parameter. If it is a number known while building, use a value generic. If it is known only at runtime, use `any Trait`.

Use a generic type parameter when the code works for any type and produces a value of that type. `max<T>`, `Box<T>`, and `Vec<T>` only require the operations they use.

Use a value generic when a size or count is part of the type's identity. `Arr<T, N>`, `Matrix<T, R, C>`, and `Bitset<N>` need `N` at compile time; two values that must not be confused belong in the type.

Use `comptime` when the function must inspect its type arguments and choose behaviour, especially when the caller does not supply them, as with `print` and the other variadic formatters.

Use `any Trait` (Chapter6) when the type is not known until runtime. A generic is monomorphised and static; a trait object is dynamic. A heterogeneous collection needs `any Trait`.

One question settles almost every case: is this known at compile time or at runtime? If at compile time, prefer a generic; if not, it must be `any`.

7.10 A Worked Example: A Compile-Time Lookup Table

A fast lookup table whose contents are fixed before the program runs, computed during compilation instead of filled at startup:

    const TABLE_SIZE = 256;
    const KEY = 0x9E3779B97F4A7C15;

    struct HashTable<usize N> {
        u32 slots[N];
    }

    pub extend<usize N> HashTable<N> {
        static HashTable<N> build() {
            var table = HashTable<N> { .slots = {} };
            comptime {
                for (usize i = 0; i < N; i += 1) {
                    table.slots[i] = hash32((u32)i, KEY);
                }
            }
            return table;
        }

        #[[inline]]
        u32 at(usize i) const {
            return self.slots[i];
        }
    }

    const HashTable<256> GLOBAL = HashTable<256>::build();

`N` is a value generic, so the type carries its capacity. The table is built in a comptime block, so the loop runs during compilation and the generated program contains a fully populated constant array, with no startup cost. Indexing with a constant is bounds-checked against `N` at compile time. `var` lets the compiler infer `HashTable<N>` from the initialiser.

7.11 A Worked Example: A Generic Ring Buffer

A ring buffer stores a fixed number of elements and overwrites the oldest when full, the shape of a fixed-size event log, an audio delay line, or a bounded work queue.

    struct Ring<T, usize N> {
        T buffer[N];
        usize head;
        usize count;
    }

    pub extend<T, usize N> Ring<T, N> {
        static Ring<T, N> new() {
            return Ring<T, N> { .buffer = {}, .head = 0, .count = 0 };
        }

        void push(T value) {
            usize tail = (self.head + self.count) % N;
            self.buffer[tail] = value;
            if (self.count == N) {
                self.head = (self.head + 1) % N;
            } else {
                self.count += 1;
            }
        }

        T pop() {
            @assertOut(self.count > 0, "pop() on an empty Ring");
            T value = self.buffer[self.head];
            self.head = (self.head + 1) % N;
            self.count -= 1;
            return value;
        }

        bool isFull() const { return self.count == N; }
        bool isEmpty() const { return self.count == 0; }
    }

Both `T` and `N` are parameters, so `Ring<i32, 64>` and `Ring<str, 8>` are distinct generated types. The modulo arithmetic uses the constant `N`, so bounds are checkable and storage is exact. This is the standard library's `RingBuf`.

The value generic and type generic cooperate. `N` is used in the array declaration, the modulo, and the fullness test; because it is a constant, all three agree by construction.

7.12 A Larger Worked Example: Units That Check Themselves

The final example combines type generics, value generics, and comptime rejection: a physical quantity whose arithmetic is checked at compile time. Multiplying a speed by a time gives a distance; adding a distance to a time is a mistake.

Encode the unit as a compile-time structure and let arithmetic track it. This compact version carries one exponent as a value generic:

    struct Quantity<usize M, usize S> {
        f64 value;
    }

    // A length has M = 1, S = 0; a time has M = 0, S = 1.
    typedef Length = Quantity<1, 0>;
    typedef Time   = Quantity<0, 1>;

    pub extend<usize M, usize S> Quantity<M, S> {
        static Quantity<M, S> of(f64 v) {
            return Quantity<M, S> { .value = v };
        }

        // Multiplying adds exponents; the result is a new quantity type.
        Quantity<M + AM, S + AS> mul<usize AM, usize AS>(Quantity<AM, AS> other) const {
            return Quantity<M + AM, S + AS> { .value = self.value * other.value };
        }

        // Adding is legal only between identical quantities.
        Quantity<M, S> add(Quantity<M, S> other) const {
            return Quantity<M, S> { .value = self.value + other.value };
        }
    }

The types do the work. `Length::of(3.0).mul(Time::of(2.0))` has type `Quantity<1, 1>`: multiplying `Quantity<1, 0>` by `Quantity<0, 1>` adds the exponents. The exponents are value generics, so units cost no runtime storage; the `value` field is the only thing in memory.

Now the payoff: an illegal operation is a type error, reported before the program runs.

    void broken() {
        Length d = Length::of(3.0);
        Time t = Time::of(2.0);
        Length wrong = d.add(t);      // error: add expects Quantity<1, 0>, got Quantity<0, 1>
    }

`d.add(t)` cannot compile because `add` requires the same `M` and `S` on both sides, and `Length` and `Time` differ in both. The mistake is caught by the type system, not a test or a wrong number at runtime.

In a full implementation, exponent arithmetic is a comptime computation, and the type can reject instantiations that make no physical sense:

    void derive<usize M, usize S>(Quantity<M, S> q) {
        comptime {
            if (M == 0 && S == 0) {
                @compileError("a dimensionless quantity is not a physical result; check your units");
            }
        }
        use(q.value);
    }

Value generics make the shape of the data part of the type; comptime computes over that shape during the build; and `@compileError` turns an impossible instantiation into a sentence at the line that caused it. There is no macro language and no runtime cost.

7.13 Exercises

1. Comprehension. Why is a monomorphised generic free at runtime while a trait object is not? Name where the trait object's extra work happens.

2. Comprehension. What is the difference between a type parameter `T` and a value parameter `N`? Give a declaration needing each, and explain what goes wrong if you swap them.

3. Implementation. Write `map<T, U>(const Vec<T>* v, U(T) fn) Vec<U>` that applies a function to each element and returns a new vector. Use it to turn a `Vec<i32>` into a `Vec<str>`.

4. Implementation. Write `minMax<T>(Vec<T> v) struct(T, T)` returning the smallest and largest elements. What operation does the body require of `T`, and where is that checked at instantiation?

5. Value generics. Declare a fixed-size square `Matrix<T, N>` with an identity constructor. How do you ensure the diagonal loop has a compile-time bound? What goes wrong if the size is an ordinary field?

6. comptime. Write a comptime block that computes the first twenty Fibonacci numbers into a const array. Confirm the generated program does no work to produce them, and explain where the numbers live.

7. Deduction. Why does `print` have a `comptime` type parameter rather than an ordinary one? What would break at the call site if `T` had to be supplied by the caller?

8. Format checking. Write three calls that trigger E0901, E0902, and E0903, then the corrected call for each. Why does a format string built at runtime give up the check?

9. Rejection. Write a generic that computes the number of bits in its type parameter and rejects any non-integer type with `@compileError`. Use `@sizeof`, `@typeof`, or `alignof` as needed.

10. Layout. Use `@sizeof` and `alignof` to write a comptime assertion that a wire struct is exactly twelve bytes and aligned to four. What happens at build time if a field is added and the assertion is wrong?

11. Design. Should a serialiser take a generic `T` (whose body calls the serialise method) or an `any Serializable`? Answer for a list of mixed types, then for one known type.

12. Units. Extend the units example with a `divide` that subtracts exponents, and add a `Speed` type. What is the type of `Length / Time`, and how would the compiler react to adding a `Speed` to a `Time`?

13. Meta. comptime blocks are ordinary code evaluated early. Name one advantage over a separate macro language and one disadvantage. Where would you draw the line between comptime and runtime code?
