Chapter35

Live Examples: Systems and Concurrency

The Machinery You Can See

Chapter19 covered threads, races, happens-before, mutexes, and condition variables. This chapter builds eleven structures from them: a lost update, a producer-consumer queue, a thread pool, a parallel map, an async pipeline, a semaphore, a reader-writer lock, a barrier, a parallel sum, dining philosophers, and a token bucket.

The machinery is visible. Coral does not hide the thread behind a keyword, the queue behind a runtime, or the scheduler behind magic. `threadCreate` returns a real operating-system thread and a `Result`; a mutex is a struct you `init` and `lock`. Correctness is auditable lock by lock and signal by signal.

Two habits carry through every example. Shared mutable state is touched only under its lock, visibly in one reading. Every condition-variable wait sits in a `while` loop that rechecks the predicate: wakeups can be spurious, and another thread may have taken what you waited for.

Every Coral thread runs a function taking one `rawptr` and returning one `rawptr` (pool tasks return `void`). That pointer points at a struct carrying everything the worker needs, and the lifetime contract begins there: pointing at a local that dies before the join is a use-after-free. Every example outlives the join or frees the job when done.

35.1 The Lost Update: Why a Counter Needs an Atomic

The problem. Two threads each add one to a shared counter a million times. The answer should be two million; the obvious code usually gives less, and the shortfall changes every run.

The intuition. `count += 1` is three actions: load, add, store. Two threads can both load seven, both store eight, and one increment is lost. That is a data race, and its result is unpredictable. The fix is a single-word atomic: `AtomicU64` does read-modify-write indivisibly.

The approach. Write the broken version first, because the failure is the lesson and never reproduces on demand. Then use an `AtomicU64`.

The implementation.

    import(lib) std::concurrent::thread {
        threadCreate, threadJoin, Thread, ThreadError, AtomicU64
    };

    // the same field, once plain and once atomic
    struct PlainCounter { u64 value; }
    struct AtomicCounter { AtomicU64 value; }

    rawptr bumpPlain(rawptr arg) {
        PlainCounter* c = (PlainCounter*)arg;
        // read-modify-write as three separate steps: the race lives here
        for (u64 i = 0; i < 1000000u; i += 1) c->value += 1;
        return null;
    }

    rawptr bumpAtomic(rawptr arg) {
        AtomicCounter* c = (AtomicCounter*)arg;
        // one indivisible instruction, so no increment can be lost
        for (u64 i = 0; i < 1000000u; i += 1) c->value.fetchAdd(1u);
        return null;
    }

    pub void main() {
        PlainCounter plain = PlainCounter { .value = 0 };
        // both threads write through the same pointer; the counter must outlive them
        Result<Thread, ThreadError> a = threadCreate(bumpPlain, (rawptr)&plain);
        Result<Thread, ThreadError> b = threadCreate(bumpPlain, (rawptr)&plain);
        if (a.isOk()) threadJoin(a.unwrap(), null);
        if (b.isOk()) threadJoin(b.unwrap(), null);
        println("plain  {}", plain.value);          // often less than 2000000

        AtomicCounter atomic = AtomicCounter { .value = AtomicU64 { .value = 0 } };
        Result<Thread, ThreadError> c = threadCreate(bumpAtomic, (rawptr)&atomic);
        Result<Thread, ThreadError> d = threadCreate(bumpAtomic, (rawptr)&atomic);
        if (c.isOk()) threadJoin(c.unwrap(), null);
        if (d.isOk()) threadJoin(d.unwrap(), null);
        println("atomic {}", atomic.value.load());  // always 2000000
    }

Cost and notes. `fetchAdd` is one locked instruction on x86-64 (`lock xadd`), a few tens of cycles. The plain increment is faster and wrong. Use an atomic for one integer, counter, flag, or ticket, and a mutex once the state is larger: an atomic guards a cell, a mutex a region.

Edge cases. The plain version is a genuine data race and undefined, not merely imprecise; it may occasionally print two million, which is why it is dangerous. The counter must outlive both joins. `load`, `store`, `fetchAdd`, `fetchSub`, and `compareExchange` are the vocabulary. Forgetting `AtomicU64 { .value = 0 }` leaves stack garbage.

Variation. Run two incrementing threads and one decrementing, printing after all join; the total is one million regardless of interleaving. Confirm the atomic always reaches it, then build an increment-only-if-below-a-cap with `compareExchange`.

35.2 Producer and Consumer with a Mutex and a Condition Variable

The problem. One thread produces values and another consumes them, meeting without overrunning a fixed-size buffer or spinning on an empty one.

The intuition. This is the most reusable concurrent structure: a thread pool is this queue with tasks, a channel is this queue with a protocol. It is a fixed-size ring, a mutex, and two condition variables, for item-ready and room-free. The producer waits while full, writes, signals; the consumer waits while empty, reads, signals. Each wakes the other when it can progress.

The approach. A ring buffer with `head` and `count`, one mutex, two condition variables, and a `closed` flag so the consumer can drain and stop. Waits sit in `while` loops against lost wakeups, spurious wakeups, and stale predicates.

The implementation.

    import(lib) std::concurrent::mutex { Mutex };
    import(lib) std::concurrent::thread {
        ConditionVar, threadCreate, threadJoin, Thread, ThreadError
    };
    import(lib) std::mman { alloc, dealloc };

    pub struct Queue {
        // all fields below are guarded by this one mutex
        Mutex mutex;
        ConditionVar itemReady;
        ConditionVar roomFree;
        u64* items;
        usize cap;
        usize head;          // index of the oldest live slot
        usize count;         // how many slots are currently live
        bool closed;

        bool init(usize capacity) {
            // one contiguous block of ring slots
            self.items = alloc<u64>(capacity);
            if (self.items == null) return false;
            self.mutex.init();
            self.itemReady.init();
            self.roomFree.init();
            self.cap = capacity;
            self.head = 0;
            self.count = 0;
            self.closed = false;
            return true;
        }

        void destroy() {
            // tear down synchronisation, then free the ring
            self.mutex.destroy();
            self.itemReady.destroy();
            self.roomFree.destroy();
            dealloc<u64>(self.items);
        }

        void push(u64 value) {
            // take the lock before touching any shared field
            self.mutex.lock();
            // wait in a loop: recheck the full condition after every wake
            while (self.count == self.cap && !self.closed)
                self.roomFree.wait(&self.mutex);
            // shutdown wins over a pending push
            if (self.closed) { self.mutex.unlock(); return; }

            // ring write at the tail; count tracks the live slots
            self.items[(self.head + self.count) % self.cap] = value;
            self.count += 1;
            self.itemReady.signal();
            self.mutex.unlock();
        }

        bool pop(u64* out) {
            self.mutex.lock();
            // same loop protocol, this time for the empty condition
            while (self.count == 0 && !self.closed)
                self.itemReady.wait(&self.mutex);
            if (self.count == 0) { self.mutex.unlock(); return false; }

            // the output pointer receives one value on success
            *out = self.items[self.head];
            // advance head and free a slot, which wakes the producer
            self.head = (self.head + 1) % self.cap;
            self.count -= 1;
            self.roomFree.signal();
            self.mutex.unlock();
            return true;
        }

        void close() {
            self.mutex.lock();
            // set the flag under the lock so the wake cannot be missed
            self.closed = true;
            // broadcast, not signal: every waiter must see the closure
            self.itemReady.broadcast();
            self.roomFree.broadcast();
            self.mutex.unlock();
        }
    }

    rawptr producer(rawptr arg) {
        Queue* q = (Queue*)arg;
        // push one through one hundred, then poison-pill the queue
        for (u64 i = 1; i <= 100; i += 1) q->push(i);
        q->close();
        return null;
    }

    rawptr consumer(rawptr arg) {
        Queue* q = (Queue*)arg;
        u64 value;
        u64 sum = 0;
        // drains until pop reports the queue closed and empty
        while (q->pop(&value)) sum += value;
        println("sum {}", sum);
        return null;
    }

    pub i32 main() {
        Queue q;
        if (!q.init(16)) return 1;
        // two threads share the queue; both must join before destroy
        Result<Thread, ThreadError> p = threadCreate(producer, (rawptr)&q);
        Result<Thread, ThreadError> c = threadCreate(consumer, (rawptr)&q);
        if (p.isOk()) threadJoin(p.unwrap(), null);
        if (c.isOk()) threadJoin(c.unwrap(), null);
        q.destroy();
        return 0;
    }

The sum prints 5050 every time, though the interleaving differs. The ring arithmetic `(head + count) % cap` is the whole discipline: `head` is the oldest slot, `count` the live slots, and the modulo keeps indices in range. The `close` broadcast, the poison pill, wakes both waiters.

Cost and notes. Each push and pop takes one lock, one or two signals, and O(1) bookkeeping, released before work on the item. Backpressure is the point: a fast producer blocks when full instead of growing memory until the machine dies.

Edge cases. Never touch the buffer outside the locked region; one unlocked read of `count` reintroduces the race. Both waits recheck after waking, because `signal` wakes one waiter and the predicate may be false. `close` uses `broadcast`. A producer closing during `pop` is fine, because `pop` rechecks `count`.

Variation. Generalise the element type to `rawptr` so the queue carries arbitrary jobs, exactly what the thread pool does. A second consumer still produces 5050: correctness depends on lock discipline, not consumer count.

35.3 A Thread-Pool Task Queue

The problem. `threadCreate` per task does not scale: each costs a kernel object, a stack, and a scheduler slot. A pool creates a fixed set of workers once and feeds them tasks from a queue.

The intuition. A pool is the 34.2 queue with tasks as items and workers as consumers. A thread calling `submit` produces; each worker locks, waits for a task or stop, takes one, unlocks, runs it, repeats. The queue is a linked list, needing no fixed capacity. Shutdown sets the stop flag under the lock and broadcasts, so workers wake, recheck, and exit after draining.

The approach. A compact pool built on `Mutex`, `ConditionVar`, and `threadCreate`. `std::concurrent::threadpool::ThreadPool` is the production version; reading its source shows there is no hidden machinery.

The implementation.

    import(lib) std::concurrent::mutex { Mutex };
    import(lib) std::concurrent::thread {
        ConditionVar, threadCreate, threadJoin, Thread, ThreadError
    };
    import(lib) std::mman { alloc, dealloc };

    struct Task {
        // a function, its argument, and the next link in the list
        void(rawptr) work;
        rawptr arg;
        Task* next;
    }

    pub struct MiniPool {
        // every field here is protected by mutex
        Mutex mutex;
        ConditionVar cond;
        Thread* workers;
        Task* head;
        Task* tail;
        u32 nthreads;
        bool stop;

        bool init(u32 numThreads) {
            // refuse a pool that could never make progress
            if (numThreads == 0) return false;
            self.mutex.init();
            self.cond.init();
            self.head = null;
            self.tail = null;
            self.stop = false;
            self.nthreads = numThreads;
            self.workers = alloc<Thread>((usize)numThreads);
            if (self.workers == null) return false;
            // start the fixed set of workers once; they then consume the queue
            for (u32 i = 0; i < numThreads; i += 1) {
                Result<Thread, ThreadError> r = threadCreate(miniEntry, (rawptr)self);
                if (r.isErr()) { self.shutdown(); return false; }
                self.workers[i] = r.unwrap();
            }
            return true;
        }

        bool submit(void(rawptr) work, rawptr arg) {
            if (work == null) return false;
            // the task lives on the heap because it must outlive submit
            Task* t = alloc<Task>(1);
            if (t == null) return false;
            t->work = work;
            t->arg = arg;
            t->next = null;

            // link the task at the tail under the lock, then signal one worker
            self.mutex.lock();
            if (self.stop) { self.mutex.unlock(); dealloc<Task>(t); return false; }
            if (self.tail != null) self.tail->next = t;
            else self.head = t;
            self.tail = t;
            self.mutex.unlock();
            // signal after unlocking; one worker wakes and takes it
            self.cond.signal();
            return true;
        }

        void workerLoop() {
            loop {
                self.mutex.lock();
                // sleep until there is work or a shutdown, then recheck
                while (self.head == null && !self.stop) self.cond.wait(&self.mutex);
                if (self.stop && self.head == null) { self.mutex.unlock(); return; }

                // pop the head task while still holding the lock
                Task* t = self.head;
                self.head = t->next;
                if (self.head == null) self.tail = null;
                self.mutex.unlock();

                // run the task and free it outside the lock
                t->work(t->arg);
                dealloc<Task>(t);
            }
        }

        void shutdown() {
            self.mutex.lock();
            // set the stop flag under the lock, broadcast after releasing it
            self.stop = true;
            self.mutex.unlock();
            self.cond.broadcast();
            for (u32 i = 0; i < self.nthreads; i += 1) threadJoin(self.workers[i], null);
            // drain any tasks queued just before shutdown
            self.mutex.lock();
            while (self.head != null) {
                Task* t = self.head;
                self.head = t->next;
                dealloc<Task>(t);
            }
            self.mutex.unlock();
            self.workers = null;
            self.mutex.destroy();
            self.cond.destroy();
        }
    }

    rawptr miniEntry(rawptr arg) {
        // thread entry: hand the pool to its worker loop
        ((MiniPool*)arg)->workerLoop();
        return null;
    }

Cost and notes. Submission is O(1): allocate, link under the lock, signal. An idle worker costs nothing, sleeping until signalled. Concurrency is bounded by the worker count: one per core for CPU-bound work, more for I/O, fewer when tasks contend. The pool replaces one thread creation per task with one per worker.

Edge cases. The stop path sets the flag under the lock and broadcasts after releasing it, so a worker about to wait does not miss the wake. A task submitted just before shutdown is run or freed, never stranded. If creation fails partway, `shutdown` joins the workers already made. `submit` returns `false` rather than dropping a task.

Variation. Add `pending()` under the lock and use it to build `drain()`, which blocks until the queue is empty. It is the missing piece for a batch program that submits jobs and waits.

35.4 Parallel Map over a Vec

The problem. Apply a function to every element of a large vector using every core. It is the simplest parallel pattern.

The intuition. Split the vector into contiguous chunks, hand each to a task, and let the pool run them at once. Each task writes only its own slice, so no lock is needed; the chunk boundaries are the coordination. Drain the pool and the vector is mapped. Share nothing unnecessary.

The approach. Use the standard `ThreadPool`. A job carries pointers to input and output, a range, and the function. Allocate an array of jobs, submit each, then `deinit`, which drains queued work before workers exit. Disjoint ranges mean no further synchronisation.

The implementation.

    import(lib) std::concurrent::threadpool { ThreadPool };
    import(lib) std::vec { Vec };
    import(lib) std::mman { alloc, dealloc };

    struct MapJob {
        // one chunk's inputs, its output range, and the function to apply
        const Vec<f64>* input;
        Vec<f64>* output;
        usize start;
        usize end;
        f64(f64) func;
    }

    void runMapChunk(rawptr arg) {
        MapJob* job = (MapJob*)arg;
        // each task writes only its own disjoint slice: no lock needed
        for (usize i = job->start; i < job->end; i += 1)
            job->output->set(i, job->func(job->input->at(i)));
    }

    pub f64 square(f64 x) { return x * x; }

    pub bool parallelMap(const Vec<f64>* input, Vec<f64>* output, f64(f64) func, u32 workers) {
        usize n = input->count();
        // preallocate one output slot per input element
        output->clear();
        for (usize i = 0; i < n; i += 1) output->push(0.0);   // reserve the slots

        // never make more chunks than there are elements to give them
        usize chunks = (usize)workers;
        if (chunks > n) chunks = n;
        if (chunks == 0) return true;

        // one job struct per chunk, owned by this function
        MapJob* jobs = alloc<MapJob>(chunks);
        if (jobs == null) return false;

        // the pool owns the worker threads for the duration
        ThreadPool pool;
        if (!pool.init(workers)) { dealloc<MapJob>(jobs); return false; }

        // spread the remainder so the chunks cover every element exactly
        usize per = n / chunks;
        usize extra = n % chunks;
        usize start = 0;
        for (usize c = 0; c < chunks; c += 1) {
            usize len = per + (c < extra ? 1 : 0);
            jobs[c] = MapJob {
                .input = input,
                .output = output,
                .start = start,
                .end = start + len,
                .func = func
            };
            // enqueue the chunk; the pool decides which worker runs it
            pool.enqueue(runMapChunk, (rawptr)&jobs[c]);
            start += len;
        }

        pool.deinit();        // drains every queued task, then joins the workers
        dealloc<MapJob>(jobs);
        return true;
    }

The chunking gives the first `extra` chunks one more element, covering the vector exactly when the length is not a multiple of the worker count. Without `deinit`, the function would return while workers still wrote, and the caller would read a half-mapped vector.

Cost and notes. Wall-clock time approaches the single-threaded time divided by workers, up to submission overhead and uneven finishing. Each task carries a struct and a queue push, so for tiny vectors the parallel version is slower. Parallelism pays when each chunk dwarfs the coordination.

Edge cases. The output vector must already have `n` slots, because `set` writes into existing positions. Each job's range must be disjoint, or two threads race; the `start`/`len` arithmetic guarantees it. The function must be safe on many threads. The jobs and pool must be cleaned up on every failure path.

Variation. Replace the map with a parallel reduction: each chunk computes a partial sum and the caller combines the partials. Write partials to distinct slots, because a shared accumulator needs an atomic or lock.

35.5 An Async Pipeline with spawn, await, and a Channel

The problem. Coordinate several I/O-shaped stages, fetch, transform, store, so that while one waits the others progress, without a thread per wait.

The intuition. A sleeping thread blocks a thread; a sleeping async task frees its context. Coral's runtime uses lightweight stacks called fibers, driven by whoever calls `run`. `spawn(fn, arg)` puts a function on its own fiber and returns a `Future*`; `await(future)` suspends the calling fiber until ready; `sleep(ms)` resolves later without blocking a thread. The top level is not a fiber, so it spawns and calls `run`.

The approach. A producer fiber pushes values into an `AsyncChannel` with a sleep to model latency; a consumer receives and accumulates. The top level spawns both and runs the scheduler.

The implementation.

    import(lib) std::concurrent::async;
    import(lib) std::io::ios { println };

    pub void producerStage(rawptr arg) {
        async::AsyncChannel* ch = (async::AsyncChannel*)arg;
        // the producer emits five values with a pause between them
        for (u64 i = 1; i <= 5; i += 1) {
            async::await(async::sleep(10));       // pretend to do I/O
            ch->send((rawptr)i);
        }
    }

    pub void consumerStage(rawptr arg) {
        async::AsyncChannel* ch = (async::AsyncChannel*)arg;
        // the consumer accumulates whatever it receives
        u64 total = 0;
        for (u64 i = 0; i < 5; i += 1) {
            // await suspends this fiber, freeing its thread for other work
            Result<rawptr, async::AsyncError> got = async::await(ch->recv());
            if (got.isOk()) total += (u64)got.unwrap();
        }
        println("async total {}", total);
    }

    pub i32 main() {
        // bring up the runtime, then a buffered channel
        async::init();
        async::AsyncChannel ch;
        if (!ch.init(4)) return 1;

        // spawn both stages as fibers; each returns a future
        Result<async::Future*, async::AsyncError> p = async::spawn(producerStage, (rawptr)&ch);
        Result<async::Future*, async::AsyncError> c = async::spawn(consumerStage, (rawptr)&ch);
        if (p.isErr() || c.isErr()) return 1;

        async::run();     // drive until every spawned fiber has finished
        // scheduler drained; tear the channel down
        ch.deinit();
        return 0;
    }

The producer sleeps, then sends; the consumer awaits and adds. `send((rawptr)i)` casts the integer to the channel's raw-pointer type, and the consumer casts back with `(u64)got.unwrap()`. Capacity four lets sends and receives drift; zero would be a rendezvous.

Cost and notes. A fiber switch is a stack swap, cheaper than a kernel context switch, and stacks are recycled. `sleep` consumes no thread; the scheduler idles in a timed wait. The gain appears when many tasks mostly wait: one driver can hold thousands of suspended fibers.

Edge cases. Calling `await` outside a fiber returns an error, which is why the top level spawns and drives. A pending receive nobody sends to can stall the scheduler; v1 futures are not cancellable. A blocking call inside a fiber stalls the runtime: never block in a task.

Variation. Add a second consumer and channel, routing values round-robin. It is the skeleton of a worker pipeline, one channel per stage.

35.6 Bounding Concurrency with a Semaphore

The problem. You have a hundred tasks and four database connections. If all grab one, the database falls over. At most four tasks may use the connection region at once.

The intuition. A mutex lets one through; a semaphore lets a fixed number through. `wait` decrements and blocks at zero, `post` increments and wakes a waiter. Initialise to four and exactly four proceed, the rest queue without spinning. The semaphore has no owner: any thread may `post`, even for another thread's `wait`.

The approach. A shared counter of finished tasks, a semaphore of four permits, and a worker that waits, works, and posts back. The pool is larger than the permits on purpose.

The implementation.

    import(lib) std::concurrent::semaphore { Semaphore };
    import(lib) std::concurrent::thread {
        threadCreate, threadJoin, Thread, ThreadError
    };

    struct Gate {
        // a permit count and a tally of finished tasks
        Semaphore permits;
        u64* completed;
    }

    rawptr limitedTask(rawptr arg) {
        Gate* gate = (Gate*)arg;
        // acquire a permit: at most maxConcurrent tasks pass this point
        gate->permits.wait();
        // only four threads are ever inside this region at once
        *gate->completed += 1;        // caller guarantees this is the only writer
        // always release the permit, even conceptually on the way out
        gate->permits.post();
        return null;
    }

    pub void runLimited(u32 maxConcurrent, u32 taskCount) {
        // one shared gate for every task
        Gate gate;
        if (!gate.permits.init(maxConcurrent)) return;
        u64 completed = 0;
        gate.completed = &completed;

        // in a real program the tasks come from the pool; here they run directly
        Thread* threads = null;       // placeholder for a pool in production
        for (u32 i = 0; i < taskCount; i += 1) {
            // join each task before the next, so the counter has a single writer
            Result<Thread, ThreadError> t = threadCreate(limitedTask, (rawptr)&gate);
            if (t.isOk()) threadJoin(t.unwrap(), null);
        }
        // all tasks are joined, so the gate can be torn down
        gate.permits.destroy();
        // every task finished; report the tally
        println("completed {}", completed);
    }

This example joins a thread per task for clarity; in production tasks go to the pool from 34.3, and the semaphore caps the guarded section. The essential lines are `wait`, do, `post`; everything between runs under the cap.

Cost and notes. `wait` and `post` are cheap kernel operations, far cheaper than creating a thread, and blocked waiters queue without spinning. The promise is a maximum, provided no path skips the post: use RAII or a single exit. A binary semaphore is almost a mutex, but any thread can release it.

Edge cases. A `post` without a matching `wait` raises the count and lets more through, so pair them on every path. Initialising to zero makes a pure signal. The shared counter is safe only because tasks join one at a time; parallelism needs an `AtomicU64`.

Variation. Use the MiniPool from 34.3: submit all tasks, each does `wait`, work, `post`, and an `AtomicU64` counts completions. It combines a pool, a semaphore, and an atomic.

35.7 A Reader-Writer Lock

The problem. Many threads read shared data and few write it. A plain mutex makes every reader wait for every other reader, serialising the common case. You want many readers but a writer alone.

The intuition. Readers may share; a writer must be alone. Track the reader count and whether a writer is active: a reader waits for an active writer, a writer waits for any reader. Starvation is the subtlety: if readers keep arriving, a waiting writer never gets in. Making new readers wait whenever a writer waits fixes it, at a little reader latency.

The approach. One mutex for bookkeeping, two condition variables for the two groups, a reader count, a writer-active flag, and a count of waiting writers for the priority rule.

The implementation.

    import(lib) std::concurrent::mutex { Mutex };
    import(lib) std::concurrent::thread { ConditionVar };

    pub struct RwLock {
        // one mutex guards the bookkeeping; two condition variables split the waiters
        Mutex mutex;
        ConditionVar canRead;
        ConditionVar canWrite;
        u32 readers;
        bool writerActive;
        u32 writersWaiting;

        void init() {
            // start unlocked with no readers and no waiting writers
            self.mutex.init();
            self.canRead.init();
            self.canWrite.init();
            self.readers = 0;
            self.writerActive = false;
            self.writersWaiting = 0;
        }

        void destroy() {
            // release the synchronisation primitives
            self.mutex.destroy();
            self.canRead.destroy();
            self.canWrite.destroy();
        }

        void readLock() {
            self.mutex.lock();
            // block while a writer runs, or while one waits (anti-starvation)
            while (self.writerActive || self.writersWaiting > 0)
                self.canRead.wait(&self.mutex);
            // count ourselves in before releasing the mutex
            self.readers += 1;
            self.mutex.unlock();
        }

        void readUnlock() {
            self.mutex.lock();
            // one fewer reader inside
            self.readers -= 1;
            // last reader out lets a waiting writer in
            if (self.readers == 0) self.canWrite.broadcast();
            self.mutex.unlock();
        }

        void writeLock() {
            self.mutex.lock();
            // announce ourselves before waiting so readers yield to us
            self.writersWaiting += 1;
            while (self.writerActive || self.readers > 0)
                self.canWrite.wait(&self.mutex);
            self.writersWaiting -= 1;
            // we are the only writer now
            self.writerActive = true;
            self.mutex.unlock();
        }

        void writeUnlock() {
            self.mutex.lock();
            self.writerActive = false;
            self.canWrite.broadcast();      // a waiting writer goes next
            self.canRead.broadcast();       // otherwise the readers may enter
            self.mutex.unlock();
        }
    }

The `writersWaiting > 0` term in `readLock` is the whole anti-starvation policy; remove it and readers barge past writers forever. Waking both groups and letting them recheck under the mutex is simpler than choosing which goes next.

Cost and notes. O(1) per operation, but read performance is the point: any number of readers run at once. The mutex is still held during bookkeeping, so this shrinks contention from every access to every transition. Prefer `std::concurrent::rwlock` in production.

Edge cases. Taking the read lock twice can deadlock if a writer arrives between: the second `readLock` blocks, the writer is stuck behind the first. A writer must not call `readLock` while holding the write lock, or vice versa. A reader that crashes without releasing leaves writers waiting forever. A lock released by a non-owner corrupts the counts.

Variation. Remove the `writersWaiting` term for a reader-preference lock and observe a writer starve; put it back and watch it get a turn. Neither policy is universally right.

35.8 A Barrier (Rendezvous)

The problem. A group computes in phases, and no thread may begin phase two until every thread has finished phase one. You need a reusable meeting point that holds all until the last arrives.

The intuition. Count arrivals: early threads wait, the last releases everyone and resets the count. Reuse is the hazard: a fast thread may arrive again and be woken by the previous release. A generation number fixes it: each release increments it, and waiters sleep until it changes from their arrival generation.

The approach. A mutex, one condition variable, the number of parties, the waiting count, and a generation counter.

The implementation.

    import(lib) std::concurrent::mutex { Mutex };
    import(lib) std::concurrent::thread { ConditionVar };

    pub struct Barrier {
        // parties is fixed; waiting and generation change every round
        Mutex mutex;
        ConditionVar cond;
        u32 parties;
        u32 waiting;
        u64 generation;

        bool init(u32 count) {
            // a barrier of zero parties could never open
            if (count == 0) return false;
            self.mutex.init();
            self.cond.init();
            self.parties = count;
            // start at generation zero with nobody waiting
            self.waiting = 0;
            self.generation = 0;
            return true;
        }

        void destroy() {
            // release mutex and condition variable
            self.mutex.destroy();
            self.cond.destroy();
        }

        void waitAt() {
            self.mutex.lock();
            // remember which round we arrived in
            u64 myGen = self.generation;
            // announce our arrival in this generation
            self.waiting += 1;
            if (self.waiting == self.parties) {
                // last arrival: reset, bump the generation, release everyone
                self.waiting = 0;
                self.generation += 1;         // releases everyone waiting on myGen
                self.cond.broadcast();
            } else {
                // sleep until the generation changes under us
                while (self.generation == myGen)
                    self.cond.wait(&self.mutex);
            }
            self.mutex.unlock();
        }
    }

The last arrival resets the count and wakes the others. The generation test `while (self.generation == myGen)` makes the barrier reusable; without it, a fast thread could fall through on an old signal.

Cost and notes. Each `waitAt` is O(1): one lock, one comparison, and a broadcast by the last arriver. The broadcast costs O(parties) wakeups. A barrier separates phases when each must see the full result of the last.

Edge cases. `count` of zero is refused. Every party must call `waitAt` the same number of times; an extra call blocks waiting for parties that are not coming, correct but easy to mistake for a hang. The condition is broadcast, because every waiter must be released. The mutex's unlock and re-lock provide the happens-before edge for phase two.

Variation. Add `phase()` returning the current generation, and run a three-phase pipeline. Then write a sense-reversing barrier using a boolean sense flag instead of a generation counter.

35.9 Parallel Sum by Divide and Conquer

The problem. Sum a large array with a recursive division that mirrors the algorithm mathematically, rather than fixed chunking. It adds the reduction pattern: combining partial answers.

The intuition. To sum a range, split it, sum each half, and add. Do one half on a new thread and the other on the current thread. Stop when a thread costs more than adding the rest; that cutoff is the only tuning knob. The halves are disjoint and read-only, so no lock is needed. Partial sums combine after both join.

The approach. A job carries the data, range, cutoff, and an output slot. A recursive function fills it; a thread entry calls it. The parent spawns the right half, computes the left, joins, and adds.

The implementation.

    import(lib) std::vec { Vec };
    import(lib) std::mman { alloc, dealloc };
    import(lib) std::concurrent::thread {
        threadCreate, threadJoin, Thread, ThreadError
    };

    struct SumJob {
        // data is read-only; the range is disjoint from every sibling range
        const Vec<f64>* data;
        usize start;
        usize end;
        usize cutoff;
        f64 result;
    }

    void sumRange(SumJob* job) {
        // below the cutoff, just add the numbers sequentially
        if (job->end - job->start <= job->cutoff) {
            f64 s = 0.0;
            // plain sequential sum over this small range
            for (usize i = job->start; i < job->end; i += 1) s += job->data->at(i);
            job->result = s;
            return;
        }

        // split the range in half at the midpoint
        usize mid = job->start + (job->end - job->start) / 2;
        SumJob* left = alloc<SumJob>(1);
        SumJob* right = alloc<SumJob>(1);
        // allocation failure falls back to a sequential sum
        if (left == null || right == null) {
            if (left != null) dealloc<SumJob>(left);
            if (right != null) dealloc<SumJob>(right);
            f64 s = 0.0;
            for (usize i = job->start; i < job->end; i += 1) s += job->data->at(i);
            job->result = s;
            return;
        }

        left->data = job->data;
        left->start = job->start;
        left->end = mid;
        left->cutoff = job->cutoff;
        left->result = 0.0;

        right->data = job->data;
        right->start = mid;
        right->end = job->end;
        right->cutoff = job->cutoff;
        right->result = 0.0;

        // one thread does the right half; the current thread does the left
        Result<Thread, ThreadError> t = threadCreate(sumEntry, (rawptr)right);
        sumRange(left);                                // the current thread takes the left half
        if (t.isOk()) threadJoin(t.unwrap(), null);

        // combine only after the join: that is the happens-before edge
        job->result = left->result + right->result;
        dealloc<SumJob>(left);
        dealloc<SumJob>(right);
    }

    rawptr sumEntry(rawptr arg) {
        // thread entry wraps the recursive routine
        sumRange((SumJob*)arg);
        return null;
    }

    pub f64 parallelSum(const Vec<f64>* data, usize cutoff) {
        @assertOut(cutoff >= 1, "a cutoff of zero never terminates");
        // the root job covers the whole vector on the current thread
        SumJob root = SumJob {
            .data = data, .start = 0, .end = data->count(),
            .cutoff = cutoff, .result = 0.0
        };
        sumRange(&root);
        return root.result;
    }

Each internal node spawns one thread for the right half and uses the current thread for the left, so live threads are bounded by recursion depth. The `right` job outlives the `threadJoin`, so freeing it afterward is safe.

Cost and notes. The arithmetic is O(n); parallelism comes from disjoint halves. The overhead is one thread creation per internal node, which is why the cutoff exists: below a few thousand elements, creation dominates. In production, use a thread pool or work-stealing scheduler.

Edge cases. A cutoff of zero recurses without end, because a one-element range keeps splitting; the assertion refuses it. An empty input is handled by the sequential branch and returns zero. Allocation failure falls back to a sequential sum. The final add happens after the join.

Variation. Replace `threadCreate` with the `ThreadPool` from 34.3 so the thread count is fixed and the fork becomes a queue push, then time both and find where recursion stops paying.

35.10 The Dining Philosophers, and How to Avoid Deadlock

The problem. Five philosophers sit around a table with one fork between each pair. To eat, each needs both neighbours' forks, alternating thinking and eating. If everyone takes the left fork first and waits for the right, all five hold one fork forever. That is deadlock.

The intuition. Deadlock is a cycle of waiting: each thread holds one resource and waits for the next until the wait wraps around. Break the cycle and it cannot form. Impose a global order and always acquire in it. Number the forks and take the lower first, so nobody holds fork four while waiting for fork zero.

The approach. A table of five mutexes. Each philosopher computes the two fork indices and locks the smaller before the larger. A fixed menu keeps the run finite.

The implementation.

    import(lib) std::mman { alloc, dealloc };
    import(lib) std::concurrent::mutex { Mutex };
    import(lib) std::concurrent::thread {
        threadCreate, threadJoin, Thread, ThreadError
    };

    const u32 PHILOSOPHERS = 5;
    // five diners, each eats a fixed number of meals
    const u64 MEALS = 3;

    pub struct Table {
        // one fork (mutex) between each pair of neighbours
        Mutex forks[PHILOSOPHERS];

        void init() {
            for (u32 i = 0; i < PHILOSOPHERS; i += 1) self.forks[i].init();
        }

        void destroy() {
            for (u32 i = 0; i < PHILOSOPHERS; i += 1) self.forks[i].destroy();
        }
    }

    struct Seat {
        // each philosopher's seat and its own fork indices
        Table* table;
        u32 index;
    }

    rawptr dine(rawptr arg) {
        Seat* seat = (Seat*)arg;
        Table* table = seat->table;
        u32 i = seat->index;

        u32 left = (i + PHILOSOPHERS - 1) % PHILOSOPHERS;
        u32 right = (i + 1) % PHILOSOPHERS;
        // global order: always take the lower-numbered fork first
        u32 first = left < right ? left : right;
        u32 second = left < right ? right : left;

        for (u64 meal = 0; meal < MEALS; meal += 1) {
            // acquire both forks in the fixed order, then release in reverse
            table->forks[first].lock();
            table->forks[second].lock();
            // eat, holding both forks
            table->forks[second].unlock();
            table->forks[first].unlock();
            // think
        }
        return null;
    }

    pub bool dinner() {
        Table table;
        // build the five forks before any philosopher starts
        table.init();

        // per-thread seat, handle, and a flag to track successful creation
        Seat* seats = alloc<Seat>((usize)PHILOSOPHERS);
        Thread* threads = alloc<Thread>((usize)PHILOSOPHERS);
        bool* created = alloc<bool>((usize)PHILOSOPHERS);
        // if any allocation failed, undo what succeeded and bail out
        if (seats == null || threads == null || created == null) {
            if (seats != null) dealloc<Seat>(seats);
            if (threads != null) dealloc<Thread>(threads);
            if (created != null) dealloc<bool>(created);
            table.destroy();
            return false;
        }

        for (u32 i = 0; i < PHILOSOPHERS; i += 1) {
            seats[i].table = &table;
            seats[i].index = i;
            // record success so a failed creation is never joined
            created[i] = false;
            Result<Thread, ThreadError> t = threadCreate(dine, (rawptr)&seats[i]);
            if (t.isOk()) {
                threads[i] = t.unwrap();
                created[i] = true;
            }
        }

        // join only the threads that were actually created
        for (u32 i = 0; i < PHILOSOPHERS; i += 1)
            if (created[i]) threadJoin(threads[i], null);

        // all joins done, release the bookkeeping
        dealloc<bool>(created);
        dealloc<Thread>(threads);
        dealloc<Seat>(seats);
        table.destroy();
        return true;
    }

The two lines that prevent disaster are `first = left < right ? left : right` and `second = left < right ? right : left`. Swapping them back to left-then-right can hang the program; the ordering is the correctness proof. The `created` array avoids joining a failed creation.

Cost and notes. Lock and unlock are O(1); ordering adds a comparison. It buys the absence of a bug invisible in testing and visible under load. Alternatives are a waiter granting both forks, or seating four philosophers; both need more machinery.

Edge cases. Every path taking both forks must use the ordering, or the cycle reappears. Release in reverse of acquisition. This removes deadlock but not starvation: a fair implementation adds a queue. A thread that dies holding a fork leaves it locked forever.

Variation. Implement the waiter solution: one mutex guards a bitmask of free forks, and the waiter grants both only when both are free. It removes starvation and replaces lock ordering with a serialisation point.

35.11 A Token-Bucket Rate Limiter

The problem. Allow at most a fixed rate of operations, say four queries per second, while permitting a short burst. How do you enforce a rate without a background timer thread?

The intuition. A bucket holds tokens. Tokens drip in at a constant rate up to a maximum, and every operation takes one; an empty bucket waits. Capacity is the largest burst, the drip rate the sustained rate. Tokens are computed lazily from elapsed time, so no timer thread is needed.

The approach. A mutex protects tokens and the last-refill time, a monotonic clock measures elapsed time, and a wait loop sleeps until the next token. `tryAcquire` is the non-blocking form.

The implementation.

    import(lib) std::concurrent::mutex { Mutex };
    import(lib) std::time {
        Timespec, nowMonotonic, subTimespec, timespecToF64, sleepMs
    };

    pub struct TokenBucket {
        // mutex guards tokens and last together; rate and capacity are read-only
        Mutex mutex;
        f64 rate;          // tokens added per second
        f64 capacity;      // maximum burst
        f64 tokens;
        Timespec last;

        void init(f64 ratePerSecond, f64 burst) {
            // a non-positive rate would divide by zero later
            @assertOut(ratePerSecond > 0.0, "rate must be positive");
            self.mutex.init();
            self.rate = ratePerSecond;
            self.capacity = burst;
            self.tokens = burst;              // start full, so the first burst is allowed
            // remember the refill epoch
            self.last = nowMonotonic();
        }

        void destroy() {
            self.mutex.destroy();
        }

        // caller must hold the mutex; adds accrued tokens, capped at capacity
        void refill() {
            Timespec now = nowMonotonic();
            // tokens accrue lazily from elapsed time; no timer thread exists
            f64 elapsed = timespecToF64(subTimespec(now, self.last));
            self.last = now;
            self.tokens += elapsed * self.rate;
            // a long pause cannot bank more than one full bucket
            if (self.tokens > self.capacity) self.tokens = self.capacity;
        }

        bool tryAcquire() {
            self.mutex.lock();
            self.refill();
            // take one token if there is one, otherwise report failure
            bool ok = self.tokens >= 1.0;
            if (ok) self.tokens -= 1.0;
            self.mutex.unlock();
            return ok;
        }

        void acquire() {
            // retry loop: sleep, refill, and recheck until a token is available
            while (true) {
                // re-check under the lock on every attempt
                self.mutex.lock();
                self.refill();
                if (self.tokens >= 1.0) {
                    self.tokens -= 1.0;
                    self.mutex.unlock();
                    return;
                }
                // compute the exact wait until the next token is due
                f64 deficit = (1.0 - self.tokens) / self.rate;   // seconds until a token
                self.mutex.unlock();
                u64 waitMs = (u64)(deficit * 1000.0) + 1u;       // round up a millisecond
                sleepMs(waitMs);
            }
        }
    }

`refill` runs only under the lock, separate so `tryAcquire` and `acquire` share the accounting. The clock is monotonic, so adjustments cannot create or destroy tokens. The wait sleeps for the computed deficit rather than a condition-variable wait, because the API has no timed wait.

Cost and notes. Each call is O(1) arithmetic plus, in the blocking case, one sleep until the next token. No polling loop, no timer thread. Capacity controls burstiness and rate the average: a large bucket is burst-tolerant, a bucket of one a strict metronome.

Edge cases. A non-positive rate divides by zero; the assertion refuses it. Several waiters can wake and find one token; losers sleep again, a small thundering herd, never a correctness problem because check and decrement are locked. Starting full allows an immediate burst; a long suspension caps tokens at capacity. `sleepMs` may oversleep, so the limiter errs slow.

Variation. Add `tryAcquireN(u64 n)` for multi-token operations, and a fairness counter so callers are served in arrival order. Then move the sleeping into a background refiller thread and compare CPU wake-ups and rate accuracy.
