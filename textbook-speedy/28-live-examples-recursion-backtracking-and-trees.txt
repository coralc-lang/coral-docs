Chapter28

Live Examples: Recursion, Backtracking, and Trees

The Problem That Contains Itself

Some problems are not a straight line of steps: the answer is built out of smaller answers to the same problem. How tall is this folder tree? One plus the tallest child, and each child is a folder tree itself. How many ways to arrange these letters? Pick one for the front, then arrange the rest. That is the whole idea: a problem that contains a smaller copy of itself.

This chapter covers that idea and two companions: recursion, a function that calls itself on the smaller copy; backtracking, where you try a choice, walk the path it opens, and if it dead-ends you walk back and try another; and trees, the data structure defined in terms of itself and so the natural home of recursion.

If you have not read Chapter5's section on recursion (base case, stack frame, tail calls), do so first. When a data shape has cases we use the variants of Chapter13 and the Option and Result of Chapter15; when a search needs a stack or queue we use the collections of Chapter16.

Every problem here follows a rhythm: get the answer by brute force, notice what it wastes, fix the waste, state the better cost, and check the edges (empty list, single element, straight-line tree, input that makes the search explode). An algorithm you have never broken is one you do not yet understand.

A note on imports. The growable list is `import(lib) std::vec { Vec };`, tree-node allocation is `import(lib) std::mman { alloc, dealloc };`, and sorting candidates uses `import(lib) std::collections::sort { sortI32 };`. The string type `str` and the integer and boolean types are built in and need nothing. Each code block assumes those imports and is otherwise complete.

28.1 The Anatomy of a Recursion: Factorial

The problem. Given a non-negative integer n, compute n! ("n factorial"), the product of 1 through n. By convention, 0! is 1.

Picture this. To line up n boxes, put any one at the front, then line up the remaining n−1. A recursive function asks the same question with fewer boxes, but must know when to stop: there is exactly one way to arrange zero boxes, doing nothing.

Brute force, then better. The brute-force version is a plain loop:

    u64 factLoop(u64 n) {
        // start the running product at the multiplicative identity
        u64 result = 1;
        // fold in every integer from 2 up to n
        for (u64 i = 2; i <= n; i += 1) {
            result = result * i;
        }
        return result;
    }

That is correct, uses no stack, and is the better version here, but the loop hides the definition: n! is n times (n−1)!.

    u64 fact(u64 n) {
        // base case: 0! and 1! are both 1, stop here
        if (n <= 1) return 1;
        // recursive case: n! = n * (n-1)!
        return n * fact(n - 1);
    }

Read it as two sentences. The base case: "if n is 0 or 1, the answer is 1; stop." The recursive case: "otherwise the answer is n times the answer for n−1." The function only knows how to do two things: stop, or ask a smaller version of itself and then multiply. It does not hold the whole multiplication in its head; it stacks up the pending multiplications and lets them unwind as the calls return.

The Coral implementation is the second snippet above, complete. The import surface is nothing at all, factorial needs only arithmetic. For a fancier example that needs collections, see 27.2.

Time and space. The loop runs n−1 times, so it is O(n) time and O(1) space. The recursion also does O(n) multiplications, so the same O(n) time, but every nested call needs a stack frame, and there are n of them, so the recursion costs O(n) extra space. That is the trade: recursion buys readability and pays in stack, and the stack is a finite resource. Push n to a few hundred thousand on a machine with a small stack and the recursive version will crash where the loop would not.

Edge cases. n = 0 and n = 1 both return 1 through the base case. n = 2 returns 2 * fact(1) = 2. The real edge case is overflow: u64 blows up at 21! (20! is the largest factorial that fits in 64 bits), and after that the answer silently wraps. If you need exact factorials of large n, you need a big-integer type, not u64; no accumulation strategy saves you, because the number itself is too big for the register.

A variation. Rewrite the recursion so the multiplication happens before the call instead of after it, by carrying a running product forward as a parameter:

    u64 factTail(u64 n, u64 acc) {
        // base case: hand back the product carried so far
        if (n <= 1) return acc;
        // carry the product forward; the call is the whole return value
        return factTail(n - 1, acc * n);
    }

Now the recursive call is the entire return value, there is nothing left to do when it comes back, and this is a tail call, which Chapter5 explains the compiler can turn into a loop that reuses one stack frame. The accumulator `acc` is the running product, and passing it forward is the standard trick for turning a stack-eating recursion into a constant-stack one.

28.2 Fibonacci: When the Same Answer Is Computed Twice

The problem. The Fibonacci numbers are defined by F(0) = 0, F(1) = 1, and F(n) = F(n−1) + F(n−2) for n ≥ 2. Compute the nth Fibonacci number.

Picture this. Imagine two rabbits, and every month each pair produces another pair. The number of pairs next month is the number this month plus the number last month. The trouble is that to count this month you must count both previous months, and to count last month you count the month before it and the one before that, and the same month's count gets requested over and over by different lines of questioning. The recursion is a family tree of questions in which the same person is asked the same question many times.

Brute force, then better. The definition translates directly into a function:

    u64 fibSlow(u64 n) {
        // base case: F(0)=0 and F(1)=1
        if (n < 2) return n;
        // two recursive calls; the same n is recomputed all over again
        return fibSlow(n - 1) + fibSlow(n - 2);
    }

This is correct and disastrous. To compute fibSlow(5) it computes fibSlow(4) and fibSlow(3). But fibSlow(4) also computes fibSlow(3). So fibSlow(3) is computed twice, fibSlow(2) three times, and so on. The number of calls grows like the Fibonacci numbers themselves, which is exponential, roughly 1.6^n. fibSlow(40) makes about a billion calls, and fibSlow(50) would make more calls than you have seconds.

The better approach is to remember answers you have already computed. This is called memoization, and in Coral the memory is an explicit object, a Vec for the answers and a Vec of flags for which answers exist, passed through the recursion:

    u64 fibMemo(u64 n, Vec<u64>* memo, Vec<bool>* seen) {
        // base case: F(0)=0 and F(1)=1, never cached
        if (n < 2) return n;
        // already solved: hand back the remembered answer, no recursion
        if (seen->at((usize)n)) return memo->at((usize)n);
        // genuine miss: recurse once and remember the result below
        u64 value = fibMemo(n - 1, memo, seen) + fibMemo(n - 2, memo, seen);
        memo->set((usize)n, value);
        seen->set((usize)n, true);
        return value;
    }

    u64 fib(u64 n) {
        // allocate the answer table and the "already computed" flags
        Vec<u64> memo = Vec<u64>::withCap((usize)n + 1);
        Vec<bool> seen = Vec<bool>::withCap((usize)n + 1);
        // every entry starts unsolved
        for (u64 i = 0; i <= n; i += 1) {
            memo.push(0);
            seen.push(false);
        }
        // share the table across all recursive calls by address
        return fibMemo(n, &memo, &seen);
    }

The `&memo` at the call site is the address of the vector, because the memo table must be shared across every recursive call, not copied into each one. Inside, the first thing the function does is check whether the answer is already known: if the flag is set, hand back the stored value and stop. Only on a genuine miss does it recurse, and before returning it stores the answer so that no later call computes it again.

Time and space. The slow version is O(2^n) time, exponential, unusable past about n = 40, and O(n) stack space because the deepest chain of calls is n deep. The memoized version is O(n) time: each distinct argument is computed exactly once, and every other visit is a constant-time lookup, so the number of real computations is n and the extra work is a constant per call. The extra memory is the two Vecs, O(n), plus the same O(n) call stack. We traded an exponential amount of time for a linear amount of memory, which is almost always a good trade. Chapter30 turns this same table into an even cleaner loop, but the idea, remember what you have already paid for, is the heart of dynamic programming.

Edge cases. n = 0 returns 0 and n = 1 returns 1 from the first line, before the memo is ever consulted, so those do not need to be stored. The try-`at`-the-memo path uses `seen` rather than a sentinel like −1, because for an unsigned type there is no spare value to mean "not yet computed"; a separate flag vector keeps the meaning honest. Overflow returns at n = 94 (F(93) is the largest Fibonacci number that fits in 64 bits).

A variation. Iterate from the bottom up instead of recursing from the top down:

    u64 fibLoop(u64 n) {
        // base case: the first two Fibonacci numbers
        if (n < 2) return n;
        // a holds F(i-2), b holds F(i-1)
        u64 a = 0;
        u64 b = 1;
        // walk the recurrence bottom-up, keeping only the last two
        for (u64 i = 2; i <= n; i += 1) {
            u64 c = a + b;
            a = b;
            b = c;
        }
        return b;
    }

This is O(n) time and O(1) space, no memo table, no stack, because it computes the values in the order they are needed and only ever keeps the last two. Whenever a memoized recursion fills a table in a simple order, you can usually rewrite it as a loop over that order and drop the recursion entirely.

28.3 Palindromes: Two Hands Walking Toward the Middle

The problem. Given a string, decide whether it reads the same forwards and backwards. "racecar" and "abba" are palindromes; "abc" and "abca" are not.

Picture this. You hold a strip of paper with letters on it, and you have a finger of each hand. You press your left finger on the leftmost letter and your right finger on the rightmost, and you ask: are these the same? If not, it is not a palindrome and you are done. If they are, both fingers step inward and you ask again. When the fingers meet or cross, every pair matched, and it is a palindrome. That is the entire algorithm, and both the loop version and the recursive version are just ways of driving the two fingers.

Brute force, then better. The naive approach builds the reversed string and compares it to the original. That allocates a whole second copy of the string for an answer that often becomes clear after one glance. The two-finger walk is better: it stops the moment a mismatch appears and allocates nothing.

    bool isPalindrome(str s) {
        // two fingers start at the two ends
        i64 lo = 0;
        i64 hi = (i64)s.len - 1;
        // while the fingers have not met or crossed
        while (lo < hi) {
            // any mismatch ends the question at once
            if (s.at((usize)lo) != s.at((usize)hi)) return false;
            lo += 1;
            hi -= 1;
        }
        // every pair matched
        return true;
    }

The indices are declared i64 rather than usize on purpose. For an empty string, `s.len - 1` on an unsigned type would wrap around to a gigantic number, and `lo < hi` would be true and the function would read out of bounds. Signed indices make `hi` equal to −1 for the empty string, the loop condition `0 < -1` is false immediately, and everything is correct. This is a recurring bug in string and array code, and using a signed index for a range that can be empty is the simplest cure.

The recursive version keeps the same two fingers but passes them as parameters:

    bool palindromeRange(str s, usize lo, usize hi) {
        // base case: the fingers met or crossed, all pairs matched
        if (lo >= hi) return true;
        // mismatch ends the branch
        if (s.at(lo) != s.at(hi)) return false;
        // step both fingers inward and recurse
        return palindromeRange(s, lo + 1, hi - 1);
    }

    bool isPalindromeRec(str s) {
        // guard the empty string so s.len - 1 is never evaluated on nothing
        if (s.len == 0) return true;
        return palindromeRange(s, 0, s.len - 1);
    }

Each call examines one pair and delegates the rest to a call that has stepped both fingers inward. The empty-string guard lives in the outer function so that `s.len - 1` is never evaluated on nothing.

Time and space. Both versions are O(n) time in the worst case, where n is the length, because in the best case, a mismatch near the ends, they stop after a constant number of comparisons, or O(1) if the very first pair differs. The loop is O(1) space. The recursion is O(n) space for the call stack, one frame per pair, which is wasteful for a problem whose loop is this simple; the recursion is shown here because it is the cleanest possible illustration of "handle one step, recurse on the rest."

Edge cases. The empty string is a palindrome (vacuously, there are no mismatches). A single character is a palindrome because `lo >= hi` is immediately true. Even and odd lengths both work: for "abba" the fingers stop after matching the two pairs; for "abcba" they meet in the middle on the unmatched 'c' and the condition `lo < hi` ends the loop before comparing a character with itself (comparing it with itself would be free and harmless, but stopping is cleaner).

A variation. Suppose you are allowed to delete at most one character to make the string a palindrome, LeetCode's "Valid Palindrome II." The two-finger walk tells you exactly where to try: the first mismatch is at (lo, hi), and the only two candidates are "delete the left one" or "delete the right one." Check whether either of those two substrings is a palindrome and you are done. The brute force tries deleting every character; the walk narrows it to two possibilities in one pass.

28.4 All Subsets: Include or Skip

The problem. Given a list of distinct integers, produce every subset, every combination that keeps the original order. For the list [1, 2, 3] the answer is the eight lists [], [1], [2], [3], [1,2], [1,3], [2,3], and [1,2,3].

Picture this. You walk down the row of numbers with a shopping basket. At each number you face the same two questions: do I put this one in the basket, or do I leave it out? Then you move to the next number and ask again. At the end of the row, whatever is in your basket is one subset; write it down. Then you back up and make the other choice somewhere, and walk to the end again. Every distinct pattern of yes/no choices you can make over the row produces exactly one subset, and there are 2^n patterns for n numbers.

Brute force, then better. The brute force counts from 0 to 2^n − 1 and reads each counter as a bitmap: bit i says whether number i is in the subset. That is perfectly correct and even elegant in a language with good bit operations. The recursive version is what generalizes to harder problems, permutations, mazes, constraint puzzles, so it is the one worth learning, even though for subsets alone the bit version is shorter.

    void subsetsFrom(Vec<i32>* nums, usize i, Vec<i32>* current, Vec<Vec<i32>>* out) {
        // base case: walked off the end, current is a complete subset
        if (i == nums->count()) {
            out->push(copyVec(current));
            return;
        }
        // branch one: leave nums[i] out
        subsetsFrom(nums, i + 1, current, out);
        // branch two: put nums[i] in
        current->push(nums->at(i));
        subsetsFrom(nums, i + 1, current, out);
        // backtrack: remove the choice so the sibling branch starts clean
        current->pop();
    }

    Vec<Vec<i32>> subsets(Vec<i32>* nums) {
        // out collects the finished subsets, current is the shared basket
        Vec<Vec<i32>> out = Vec<Vec<i32>>::new();
        Vec<i32> current = Vec<i32>::new();
        subsetsFrom(nums, 0, &current, &out);
        return out;
    }

    Vec<i32> copyVec(Vec<i32>* v) {
        // allocate the copy up front so no reallocation is needed
        Vec<i32> c = Vec<i32>::withCap(v->count());
        // copy every element, because the source will keep changing
        for (usize i = 0; i < v->count(); i += 1) {
            c.push(v->at(i));
        }
        return c;
    }

The helper `subsetsFrom` is where the whole idea lives. It takes the position `i` it is standing on, the basket `current`, and the list `out` it is filling. The base case fires when `i` has walked off the end of the list; at that moment `current` holds a complete subset, and `copyVec` makes a private copy to store (we must copy, because `current` will keep changing as the search continues). The two recursive calls are the two branches. The second branch pushes, recurses deeper, then pops, which is the walk-back: after exploring everything that includes nums[i], we remove it so that the sibling branch starts from the state before the choice was made. That push-then-pop pairing is the signature of backtracking, and you will see it in every remaining problem in this chapter.

Time and space. There are 2^n subsets, and every leaf of the recursion tree produces one. The recursion tree has about 2^(n+1) nodes total, so the running time is O(n · 2^n) if you count the cost of copying each subset (each copy is up to n long), or O(2^n) if you count only the tree's nodes. The memory is dominated by the output: 2^n subsets, each up to n long, so O(n · 2^n). The working stack is just the basket's depth, O(n). Output can be truly enormous, n = 20 gives over a million subsets, so this is a function whose output size, not its cleverness, is the limit.

Edge cases. An empty input list has exactly one subset, the empty one: the recursion immediately hits the base case and stores the empty basket. Duplicate elements are not handled by this version. If the input can contain duplicates (say [1, 1, 2]), the same subset appears more than once, and the standard fix is to sort the list and, at each level, skip a value equal to the one before it at the same depth.

A variation. The bitmask version, for comparison:

    Vec<Vec<i32>> subsetsByBits(Vec<i32>* nums) {
        usize n = nums->count();
        // there are 2^n bit patterns, one per subset
        u64 total = (u64)1 << n;
        Vec<Vec<i32>> out = Vec<Vec<i32>>::new();
        // each counter value is one yes/no pattern over the list
        for (u64 mask = 0; mask < total; mask += 1) {
            Vec<i32> one = Vec<i32>::new();
            // bit i says whether nums[i] belongs to this subset
            for (usize i = 0; i < n; i += 1) {
                if ((mask & ((u64)1 << i)) != 0) {
                    one.push(nums->at(i));
                }
            }
            out.push(one);
        }
        return out;
    }

Notice the shape of the trade. With the bitmask, the "state" (which numbers are chosen) is a single integer, and the whole search is a plain loop; there is no recursion and no walk-back. That works because every subset corresponds to exactly one counter value. The moment the choices are not independent bits, say you can choose at most two numbers, or the order matters, the counter trick stops covering the space, and you need the recursive walk-back.

28.5 All Permutations: Choosing a Seat

The problem. Given a list of distinct integers, produce every ordering of them. For [1, 2, 3] the six orders are 123, 132, 213, 231, 312, 321.

Picture this. You are seating n people in n chairs in a row. You seat the first chair by choosing any of the n people. Then you seat the second chair by choosing any of the n−1 who remain. You keep choosing, each time from the shrinking pool, until every chair is filled; that seating is one permutation. Then you take the last person out and try a different choice for the last chair, and so on, backing up whenever a row is complete. The key difference from subsets is that here you may not reuse a person: once someone is seated, they are off the market.

Brute force, then better. The brute force generates all n^n sequences of choices and throws away the ones with repeats. That is wildly wasteful, n^n is far larger than n!, because most of the sequences it builds are illegal. Backtracking avoids the waste by never choosing a person who is already seated, so every branch it explores is already a partial valid permutation.

    void permuteFrom(Vec<i32>* nums, Vec<bool>* used, Vec<i32>* current, Vec<Vec<i32>>* out) {
        // base case: every chair is filled, record the ordering
        if (current->count() == nums->count()) {
            out->push(copyVec(current));
            return;
        }
        for (usize i = 0; i < nums->count(); i += 1) {
            // skip anyone already seated
            if (used->at(i)) continue;
            // mark the choice, seat them, and recurse
            used->set(i, true);
            current->push(nums->at(i));
            permuteFrom(nums, used, current, out);
            // backtrack: unseat and unmark so siblings see a clean table
            current->pop();
            used->set(i, false);
        }
    }

    Vec<Vec<i32>> permutations(Vec<i32>* nums) {
        Vec<Vec<i32>> out = Vec<Vec<i32>>::new();
        Vec<i32> current = Vec<i32>::new();
        // nobody is seated yet
        Vec<bool> used = Vec<bool>::new();
        for (usize i = 0; i < nums->count(); i += 1) {
            used.push(false);
        }
        permuteFrom(nums, &used, &current, &out);
        return out;
    }

The `used` vector is the "who is already seated" book. At every level, the loop considers every person, skips the ones already used with `continue`, and for each available person marks them used, seats them, recurses, and then un-marks them and removes them from the row. The un-marking is essential: the `used` vector is shared across the whole search, and a choice only "owns" its mark for as long as its branch is being explored. Forget the un-mark and later branches see a table that is half-full for no reason. This is the single most common bug in hand-written backtracking, and it is exactly what the push/pop pairing prevents.

Time and space. There are n! permutations, and producing each costs a copy of n elements, so the output alone is O(n · n!). The search tree has fewer than e · n! nodes, so the total work is O(n · n!), dominated by writing the answers down, not by finding them. The `used` vector and the current row are O(n). Again, the output size is the wall: 12! is about 479 million, so anything past a dozen elements is measured in hours or in disk space.

Edge cases. A list with one element has one permutation, itself. An empty list has one permutation, the empty ordering. If the input has duplicates, the brute version produces the same order several times; the fix is, at each level, to skip choosing a value that is equal to a value already tried at that same level (sort first, then skip `nums[i] == nums[i-1]` when `i-1` was a sibling choice, not a parent choice).

A variation. To produce only the permutations of length k drawn from n items ("k-permutations," sometimes called partial permutations), change the base case from "row is full" to "row has reached length k," and keep everything else. The number of such orderings is n!/(n−k)!, and the search prunes itself naturally once each path is k long.

28.6 N-Queens: Backtracking with a Reason to Stop Early

The problem. Place n chess queens on an n×n board so that no two attack each other. Queens attack along rows, columns, and both diagonals. For n = 8 the classic puzzle has 92 solutions; for any n, print every valid arrangement.

Picture this. You are placing queens one row at a time, from the top. In each row you will put exactly one queen, because two queens in a row would attack. So when you are on row r, the only real question is which column to use. But before you place it, you check the queen against every queen already placed above: is its column already taken? Is it on the same diagonal as an earlier queen? If yes, this column is illegal and you try the next. If no, you place it and move down a row. When you reach a row below the last, you have a full solution. When every column in a row fails, you back up a row and move that row's queen over.

Brute force, then better. The brute force tries all n^n placements and checks each for attacks. Backtracking is dramatically better for two reasons: it places exactly one queen per row by construction, killing n^n / n! of the search immediately, and it rejects a partial placement the instant a conflict appears, so it never finishes building a board that was already doomed. This early rejection, pruning, is what makes backtracking more than "recursion with a for loop."

    bool queenSafe(Vec<i32>* cols, usize row, usize col) {
        // only the rows already filled can attack this candidate
        for (usize r = 0; r < row; r += 1) {
            i32 c = cols->at(r);
            // same column is an attack
            if ((usize)c == col) return false;
            i64 rowGap = (i64)(row - r);
            i64 colGap = (i64)c - (i64)col;
            // same diagonal means the gaps are equal in magnitude
            if (colGap == rowGap || colGap == -rowGap) return false;
        }
        return true;
    }

    void solveNFrom(Vec<i32>* cols, usize row, usize n, Vec<Vec<i32>>* out) {
        // base case: placed a queen on every row, so this board is a solution
        if (row == n) {
            out->push(copyVec(cols));
            return;
        }
        for (usize col = 0; col < n; col += 1) {
            // prune: an unsafe column is abandoned before recursing
            if (!queenSafe(cols, row, col)) continue;
            // place, descend to the next row, then backtrack
            cols->push((i32)col);
            solveNFrom(cols, row + 1, n, out);
            cols->pop();
        }
    }

    Vec<Vec<i32>> solveNQueens(usize n) {
        // out collects the solution boards; cols is the shared row->column map
        Vec<Vec<i32>> out = Vec<Vec<i32>>::new();
        Vec<i32> cols = Vec<i32>::new();
        solveNFrom(&cols, 0, (usize)n, &out);
        return out;
    }

The board itself is stored as a Vec of column numbers: `cols[r]` is the column of the queen in row r. That encoding throws away the rows (there is always exactly one queen per row) and keeps only the information that matters, which is a general lesson, the right data structure shrinks the search. `queenSafe` checks only the rows above, because no queens exist below yet. Two queens share a diagonal precisely when the difference between their columns equals the difference between their rows, so the diagonal test is `|col − previousCol| == row − previousRow`, written out with an explicit sign comparison to avoid needing an absolute-value call.

Time and space. The number of solutions grows fast (92 for n = 8, 147,725,088 for n = 14), so the output dominates and the bound is exponential in n. But the useful measurement is how many partial boards the search examines, and that is where pruning shines: the naive n^n collapses to roughly O(n!) at worst and far less in practice, because most branches die after one or two placements. Space is O(n) for the current row plus the output.

Edge cases. n = 0 and n = 1 are degenerate: n = 0 produces the single empty arrangement, and n = 1 produces the single cell. n = 2 and n = 3 have no solutions at all, and the function returns an empty `out` without error, that is the correct answer, not a failure. The diagonal check must use signed arithmetic: `row - r` and `c - col` involve a comparison across rows, and doing it in unsigned would turn a negative column gap into a huge positive one and miss the attack.

A variation. Instead of testing a candidate against all earlier queens, keep three boolean arrays, one for used columns, one for the "/" diagonals (indexed by row + col), and one for the "\" diagonals (indexed by row − col + n − 1). Checking a candidate becomes three array reads, O(1) instead of O(n), and placing a queen sets three flags, unplacing clears them. The whole solver becomes O(1) per node of the search tree, and for larger n this constant-factor win is enormous. The trade is more state to maintain correctly, and the same push/pop discipline as before.

28.7 Combination Sum: Backtracking with a Budget

The problem. Given a list of distinct positive integers ("candidates") and a target number, list every combination of candidates that sums exactly to the target. Each candidate may be used any number of times. For candidates [2, 3, 6, 7] and target 7, the answers are [2, 2, 3] and [7].

Picture this. You are filling a shopping bag exactly to a budget, and the store allows you to take as many of any item as you like. You walk the shelves in order. At each item you decide whether to take a copy and keep shopping with what is left of your budget, or to move on to the next item and never come back to this one. If your budget reaches exactly zero, you have a valid bag; if it goes negative, you overspent and turn back. Because you always move forward through the shelf, you never record the same bag twice in a different order.

Brute force, then better. The naive approach tries every multiset of candidates whose size is unknown, which is unbounded. Backtracking bounds the search by the budget: the moment a partial sum exceeds the target, the branch is abandoned, because adding more positive numbers only makes it worse. Sorting the candidates ascending lets us abandon even earlier: once a candidate is too big for the remaining budget, every later candidate is at least as big, so the entire rest of the shelf is hopeless and we can break, not merely continue.

    void combSumFrom(Vec<i32>* cand, usize start, i32 target, Vec<i32>* current, Vec<Vec<i32>>* out) {
        // base case: the budget hit exactly zero, so current is a valid bag
        if (target == 0) {
            out->push(copyVec(current));
            return;
        }
        for (usize i = start; i < cand->count(); i += 1) {
            i32 c = cand->at(i);
            if (c > target) break;      // sorted ascending; every later one is also too big
            current->push(c);
            // recurse from i, not i+1, so this candidate may be reused
            combSumFrom(cand, i, target - c, current, out);
            // backtrack
            current->pop();
        }
    }

    Vec<Vec<i32>> combinationSum(Vec<i32>* candidates, i32 target) {
        // sort so the `break` prune inside the search is legal
        sortI32(candidates);
        Vec<Vec<i32>> out = Vec<Vec<i32>>::new();
        Vec<i32> current = Vec<i32>::new();
        combSumFrom(candidates, 0, target, &current, &out);
        return out;
    }

Two things distinguish this from the permutations of 27.5. The recursion passes `i`, not `i + 1`, so the current candidate can be reused, that is how [2, 2, 3] is built, by taking 2, then taking 2 again from the same shelf position. And the loop starts at `start` rather than 0, so a combination is built with its values in non-decreasing order and each distinct multiset is produced exactly once. Sorting first is not for correctness, only for speed: it makes the `break` legal and prunes hard.

Time and space. The time is O(number of nodes in the search tree) times the copy cost, which is hard to state in terms of n alone because it depends on how the target divides into the candidates; the honest answer is "proportional to the number of combinations found, times the target divided by the smallest candidate." The space is O(target / min(candidate)) for the current bag, plus the output. The pruning is what keeps this from being truly hopeless: an unbounded space becomes a search bounded by the budget.

Edge cases. A target of 0 has exactly one combination, the empty one, and the base case catches it immediately. If the smallest candidate is larger than the target, the first loop iteration breaks at once and the answer is empty. A candidate equal to the target contributes the single-element combination [c]. Duplicated candidates in the input would produce duplicated combinations, so the convention is that candidates are distinct.

A variation. "Combination Sum II" forbids reusing a candidate. There the recursive call passes `i + 1`, and to avoid duplicate answers from duplicated input values you sort and then, within a level, skip a candidate equal to the one before it that had the same `start`. The change from `i` to `i + 1` is one character, and it flips the problem from "unlimited copies" to "at most one of each", a nice demonstration of how precisely backtracking encodes the rules of the problem.

28.8 Binary Trees: The Data Structure That Is Its Own Definition

The problem. A binary tree is either empty or a value with a left subtree and a right subtree. Build a small one and write the three standard traversals: preorder (value, left, right), inorder (left, value, right), and postorder (left, right, value).

Picture this. A family tree. Each person has at most two documented descendants. To list everyone "in order" you can visit a person before you visit their descendants (preorder), after them (postorder), or between the two sides (inorder). The crucial thing is that a branch of the family is just a smaller family tree, so the same instructions apply at every level. You do not need special rules for "go into a subtree"; you just walk the same rule again.

Brute force, then better. There is not really a brute force for traversals, the recursive definition is the algorithm, but there is a wrong instinct, which is to try to hold the whole traversal in a loop with an explicit index per level. The recursive version is not merely shorter; it is the only version that scales to trees whose shape you do not know in advance.

The tree node. A binary tree node is a value plus two pointers to more nodes. We declare it as a struct, the same shape the standard library's own tree modules use:

    import(lib) std::mman { alloc, dealloc };

    struct TreeNode {
        i32 value;
        TreeNode* left;      // the left subtree, or null for none
        TreeNode* right;     // the right subtree, or null for none
    }

    TreeNode* makeNode(i32 value) {
        // allocate room for one heap node
        TreeNode* n = alloc<TreeNode>(1);
        n->value = value;
        // a fresh node has no subtrees yet
        n->left = null;
        n->right = null;
        return n;
    }

The `alloc<TreeNode>(1)` asks for room for one node on the heap and returns a pointer. The three fields are then filled in by hand, with the children set to `null`, the empty pointer that stands for "no subtree here." The type is self-referential: `TreeNode` mentions `TreeNode*`. That pointer is what makes the definition finite; without it the compiler would need to know how big a node is in terms of itself, which is impossible (Chapter13's section on recursive variants explains why the compiler refuses such a type).

The traversals. Here are all three, each a mirror of its name:

    void preorder(TreeNode* root, Vec<i32>* out) {
        // base case: the empty subtree contributes nothing
        if (root == null) return;
        // value first, then the two subtrees
        out->push(root->value);
        preorder(root->left, out);
        preorder(root->right, out);
    }

    void inorder(TreeNode* root, Vec<i32>* out) {
        if (root == null) return;
        // left subtree, then this value, then the right subtree
        inorder(root->left, out);
        out->push(root->value);
        inorder(root->right, out);
    }

    void postorder(TreeNode* root, Vec<i32>* out) {
        if (root == null) return;
        // both subtrees first, then this value last
        postorder(root->left, out);
        postorder(root->right, out);
        out->push(root->value);
    }

Only the position of the `push` moves. That is the whole difference between the three traversals, and it is worth dwelling on: the recursion does not change at all, because the recursion is about the shape of the data, not about the order in which you want to print it. Each function's first line is the base case, `root == null`, and the two recursive calls are the two subtrees. The `out` vector is threaded through by pointer because it accumulates across the whole traversal; it is the one piece of state that is not part of the tree.

For a tree whose inorder we want first, we build the smallest interesting example:

    TreeNode* root  = makeNode(4);
    root->left      = makeNode(2);
    root->right     = makeNode(6);
    root->left->left  = makeNode(1);
    root->left->right = makeNode(3);

    Vec<i32> order = Vec<i32>::new();
    // inorder visits this shape in ascending value order
    inorder(root, &order);       // order is now [1, 2, 3, 4, 6]

The same tree, as a variant. There is a second way to write these nodes, and it is the one Chapter13 would reach for first, because "a tree is a leaf or a node with children" is literally a variant. The empty subtree becomes a case instead of a null pointer:

    variant Tree {
        Leaf,                                   // the empty subtree as a named case
        Node { i32 value; Tree* left; Tree* right; }
    }

The `Tree*` fields are still pointers, for the same reason as before, a variant that stored whole `Tree` values would be infinitely large. What changes is that "empty" is now a named case, `Tree::Leaf`, rather than a null pointer, so a switch over a tree value is exhaustive and the compiler can prove you handled the empty case. The two constructors make nodes the same way the struct version did, by allocating one and writing through the pointer:

    Tree* leaf() {
        Tree* t = alloc<Tree>(1);
        *t = Tree::Leaf;                        // write the empty case through the pointer
        return t;
    }

    Tree* branch(i32 value, Tree* left, Tree* right) {
        Tree* t = alloc<Tree>(1);
        *t = Tree::Node { .value = value, .left = left, .right = right };
        return t;
    }

And a recursion over it is a switch rather than a null check, which is the payoff of the variant, there is no pointer to forget to check:

    i32 treeDepth(Tree* t) {
        Tree node = *t;
        switch (node) {
            // base case: a leaf has depth 0
            Tree::Leaf => return 0,
            Tree::Node { left, right } => {
                // recurse into both subtrees
                i32 l = treeDepth(left);
                i32 r = treeDepth(right);
                // one for this node plus the deeper subtree
                return 1 + (l > r ? l : r);
            }
        }
    }

Both representations are correct and the choice is a matter of taste and of which tool the surrounding code already uses. The struct version matches the standard library's own trees and is marginally leaner in memory (no tag); the variant version makes "empty" impossible to forget and pairs naturally with the pattern matching of Chapter13. In this chapter the later problems use the struct form, because that is what the rest of the book uses, but everything here translates to the variant form with a switch in place of each null check.

Time and space. Every traversal is O(n) time, where n is the number of nodes, because each node is visited exactly once and the work per visit (push the value, make two calls) is constant. The extra space is O(h), where h is the height of the tree, for the call stack, one frame per level of depth, not per node. For a balanced tree of n nodes, h is about log n; for a tree that is a straight line of n nodes, h is n and the recursion uses O(n) stack. The intuition is the rule from Chapter5: depth recurses, length iterates.

Edge cases. The empty tree (`root == null`) is the base case itself, so all three traversals return an empty `out` without complaint; a null tree is a valid tree. A single node produces one-element output in every order. A degenerate "tree" that is a chain of n nodes still traverses correctly, but the stack grows to depth n, so a chain of a million nodes can overflow the stack even though the answer is only a million elements, a good argument for an iterative traversal with an explicit stack when the shape is untrusted.

A variation. A tree whose values are themselves a variant, say each node holds a JSON value, or a token, is just `TreeNode<T>` for a generic T, exactly as `Vec<T>` is generic. The traversals become `preorder<T>(TreeNode<T>* root, Vec<T>* out)`. And if you want to free a tree, the destruction order matters: you must free the children before the parent, because the parent's pointers point at the children. That is postorder, which is why every well-written `freeTree` is a postorder walk:

    void freeTree(TreeNode* root) {
        // base case: nothing to free
        if (root == null) return;
        // free the children before the parent, i.e. postorder
        freeTree(root->left);
        freeTree(root->right);
        dealloc<TreeNode>(root);
    }

28.9 Tree Depth and Balance

The problem. Given a binary tree, compute its maximum depth (the number of nodes on the longest path from the root down to a leaf), and decide whether it is height-balanced (every subtree's left and right heights differ by at most one).

Picture this. Depth is "how many floors is the building." The building's height is one floor plus the taller of its two wings, and each wing is a building of its own. Balance is a structural worry: a building where one wing is far taller than the other is lopsided and would topple; a balanced one can be searched efficiently because it does not sprawl into a long thin line.

Brute force, then better. The brute-force balance check asks, at every node, "is the left height and right height within one?", recomputing the height of each subtree from scratch, and then recursively re-checking every subtree. That is O(n^2) because the height of each node is recomputed once for every ancestor that asks. The better way computes the height and the balance verdict in a single pass, returning both up the recursion.

    i32 maxDepth(TreeNode* root) {
        // base case: the empty tree has depth 0
        if (root == null) return 0;
        // the two subtree depths...
        i32 l = maxDepth(root->left);
        i32 r = maxDepth(root->right);
        // ...plus one for the current node
        return 1 + (l > r ? l : r);
    }

Depth is the textbook single-pass recursion: an empty tree has depth 0; otherwise the answer is one plus the deeper of the two subtrees' depths. The `(l > r ? l : r)` is the ternary conditional, a compact "the larger of these two", and `1 +` counts the current node.

For balance, the trick is to compute depths and detect imbalance in the same walk, using a `bool` flag that the caller passes by address so that once the flag is set to false, the work can stop early on every level:

    i32 checkHeight(TreeNode* root, bool* balanced) {
        // base case: empty subtree has height 0
        if (root == null) return 0;
        i32 l = checkHeight(root->left, balanced);
        // the flag is shared, so an early stop ripples up
        if (!*balanced) return 0;
        i32 r = checkHeight(root->right, balanced);
        if (!*balanced) return 0;
        // imbalance is a height difference of more than one
        i64 diff = (i64)l - (i64)r;
        if (diff > 1 || diff < -1) *balanced = false;
        return 1 + (l > r ? l : r);
    }

    bool isBalanced(TreeNode* root) {
        // pass the verdict by address so every frame agrees
        bool balanced = true;
        checkHeight(root, &balanced);
        return balanced;
    }

The `*balanced` notation reads the value behind the pointer; `*balanced = false` writes through it. Passing the flag by pointer rather than by value is the whole point: a value copy would let each call detect its own imbalance and then throw the finding away when it returned. The early `if (!*balanced) return 0;` after each recursive call is a small optimisation, once we know the tree is unbalanced we no longer care about exact heights, so we stop.

Time and space. Both functions are O(n) time, because each node is visited once. The balance check is O(n) rather than the brute force's O(n^2) precisely because it does the height and the verdict in one traversal instead of re-deriving heights. Space is O(h) for the stack, as in 27.8: logarithmic for a balanced tree, linear for a chain.

Edge cases. A null tree has depth 0 and is balanced by definition (there is nothing to be lopsided). A single node has depth 1 and is balanced. The `(i64)l - (i64)r` cast matters: heights are i32, and subtracting two non-negative i32s is safe here, but casting to i64 before the subtraction makes the intent (a signed comparison) explicit and immune to any surprise if heights ever grow. Note also that a balanced tree guarantees O(log n) depth, which is exactly why balanced search trees exist; an unbalanced one degrades to O(n) depth per operation, which is 27.8's "degenerate chain" wearing a different hat.

A variation. The diameter of a tree, the longest path between any two nodes, measured in edges, is a near-cousin. It is the maximum, over every node, of the sum of the left depth and the right depth, and it is computed in one pass by having the recursive helper return the height up while updating a running maximum of that sum. The pattern "compute one thing on the way up, track a second thing through a pointer" is the general shape of tree problems that need a per-node property and a global extremum at once.

28.10 Lowest Common Ancestor

The problem. Given a binary tree and two values a and b that both appear in it, find the lowest (deepest) node that is an ancestor of both. An ancestor of a node is the node itself, its parent, its parent's parent, and up to the root.

Picture this. Two people in a family tree want to know their most recent shared ancestor. You ask each branch: "has the common ancestor turned up yet, or do you contain one of the two people?" If the left branch contains a and the right branch contains b, then the current node is where the two lines meet and it is the answer. If only one branch contains anything relevant, the meeting point is further down in that branch. If the current node is one of the two people, then it is trivially an ancestor of both once the other one shows up below it.

Brute force, then better. A brute-force approach computes the root-to-node path for each value and finds the last shared element; that is O(n) to build each path and O(n) to compare, fine but clunky, and it requires storing two paths. The recursive version is a single traversal and needs no auxiliary storage.

    TreeNode* lca(TreeNode* root, i32 a, i32 b) {
        // base case: nothing relevant down this branch
        if (root == null) return null;
        // this node is one target, so it is a candidate ancestor
        if (root->value == a || root->value == b) return root;
        // ask both subtrees
        TreeNode* left  = lca(root->left, a, b);
        TreeNode* right = lca(root->right, a, b);
        // one target on each side means this node is the meeting point
        if (left != null && right != null) return root;
        if (left != null) return left;
        return right;
    }

The logic reads as three lines. If this node is empty, there is nothing here. If this node is one of the two targets, this node is a candidate ancestor, return it upward. Otherwise, ask the left subtree and the right subtree. If both come back non-null, each subtree found one of the targets, so this node is the meeting point: return it. If only one came back non-null, both targets live on that side, and the answer is whatever that side reported. The `null` return is the "there is nothing relevant here" signal, and it is what makes the answer bubble up without any extra bookkeeping.

Time and space. The function visits each node at most once, so it is O(n) time. The space is O(h) for the recursion stack, logarithmic for a balanced tree and linear for a chain. Compare this to the two-paths approach, which is also O(n) time but uses O(n) extra memory for the paths; the recursive version is strictly leaner.

Edge cases. If a is an ancestor of b, the function returns a, which is correct by the definition that a node is its own ancestor. If a and b are the same value, the first matching node is returned, which is again correct. If either value is absent, the function returns `null` when the other present value has no relevant sibling, callers that cannot guarantee presence should check the result for null (or wrap it in `Option` and have the function never return a bare null). The function assumes "ordinary" values; if the tree is a binary search tree, there is a much faster O(h) version that walks down comparing values, which is the variation below.

A variation. For a binary search tree, the LCA can be found without recursion over the whole tree. Walk down from the root: if both a and b are less than the current value, the meeting point is to the left; if both are greater, it is to the right; otherwise the current node is where their paths split, and it is the answer. That is O(h) time, logarithmic for a balanced tree, and O(1) space with a plain loop. It is a striking illustration of the core lesson: when the data has extra structure (here, the ordering), the algorithm can be dramatically better than the general one.

28.11 Word Search on a Grid

The problem. Given a rectangular grid of characters and a target word, decide whether the word can be traced through the grid by moving between horizontally or vertically adjacent cells, using each cell at most once.

Picture this. You are playing a word game on a lettered board. You start on any cell that matches the first letter, then walk to a neighbouring cell matching the next letter, and so on. You may not step on a cell you have already used in the current word, so you leave a footprint behind you and wipe it away when you back out. If you ever complete the whole word, you win.

Brute force, then better. A brute force would enumerate every path of the right length, most of which die on the first mismatch. Backtracking with rollback prunes those immediately: at each step you extend the path only if the next letter matches, and the "used" mark is set before the recursive call and cleared after it, so the board returns to its original state when you retreat.

    import(lib) std::vec { Vec };

    bool searchFrom(Vec<str>* board, str word, usize r, usize c, usize k, Vec<Vec<bool>>* used, usize rows, usize cols) {
        // base case: every letter matched
        if (k == word.len) return true;
        // prune: off the board
        if (r >= rows || c >= cols) return false;
        // prune: this cell is already used in the current path
        if (used->atPtr(r)->at(c)) return false;
        // prune: the letter does not match
        if (board->at(r).at(c) != word.at(k)) return false;

        // mark the footprint before descending
        used->atPtr(r)->set(c, true);
        bool found = false;
        // try all four neighbours, stopping as soon as one succeeds
        if (r > 0)                  found = searchFrom(board, word, r - 1, c, k + 1, used, rows, cols);
        if (!found && r + 1 < rows) found = searchFrom(board, word, r + 1, c, k + 1, used, rows, cols);
        if (!found && c > 0)        found = searchFrom(board, word, r, c - 1, k + 1, used, rows, cols);
        if (!found && c + 1 < cols) found = searchFrom(board, word, r, c + 1, k + 1, used, rows, cols);
        used->atPtr(r)->set(c, false);      // rollback: wipe the footprint
        return found;
    }

    bool wordSearch(Vec<str>* board, str word) {
        usize rows = board->count();
        // an empty word is trivially found; an empty board cannot be
        if (word.len == 0) return true;
        if (rows == 0) return false;
        usize cols = board->at(0).len;
        // a fresh all-false visited grid for the search
        Vec<Vec<bool>> used = Vec<Vec<bool>>::new();
        for (usize i = 0; i < rows; i += 1) {
            Vec<bool> row = Vec<bool>::new();
            for (usize j = 0; j < cols; j += 1) {
                row.push(false);
            }
            used.push(row);
        }
        // try every cell as the starting point
        for (usize i = 0; i < rows; i += 1) {
            for (usize j = 0; j < cols; j += 1) {
                if (searchFrom(board, word, i, j, 0, &used, rows, cols)) return true;
            }
        }
        return false;
    }

The recursion carries the whole state it needs: where it stands (`r`, `c`), how far into the word it has got (`k`), and the shared `used` grid. The first three checks are the base cases and the fast rejections, off the board, already stepped on, wrong letter, and any one of them returning false unwinds the branch immediately. The four conditional calls are the four directions, and the named `found` short-circuits them so that once a direction succeeds, the others are not tried. The single line that clears the mark is the whole difference between a search for simple paths and a search that may trample its own trail.

Time and space. Each cell is tried as a starting point, and each start can branch in up to four directions for each of the word's L letters, so the worst case is O((rows × cols) × 4^L), although the letter check prunes it heavily on real boards. The `used` grid is O(rows × cols), and the recursion stack is O(L).

Edge cases. An empty word returns true at once, and an empty board returns false. A word longer than the number of cells can never be found; the recursion discovers that by running out of fresh neighbours rather than by any explicit test. The rollback is what enforces "each cell at most once": delete it and a board containing a single 'a' will happily spell "aa".

A variation. To return all distinct paths instead of a yes/no, keep a growing list of cells and push a copy of it whenever `k` reaches the word's length, then pop as you retreat. To allow a cell to be reused, the "no used rule" variant, delete both the `used` check and the rollback line together; the walk then explores every walk up to length L and still terminates, because `k` grows to the word's length regardless.

28.12 Letter Combinations of a Phone Number

The problem. Given a string of digits from 2 to 9, return every letter string the digits could spell on a telephone keypad. The digits 2 through 6 and 8 each carry three letters, and 7 and 9 carry four.

Picture this. You are old enough to remember texting on a numeric keypad. To spell a word you press one key per letter, and each key offers a small menu of letters. Building every possible word is a walk over the digits where, at each digit, you branch over its menu and continue to the next digit. When the digits run out, the letters you chose make one word.

Brute force, then better. There is no cleverer idea than generating the combinations, there are 3^L or 4^L of them and the answer is all of them. The work is in doing it cleanly: a recursive walk that appends one letter per digit into a growing buffer, instead of loops nested to a depth that depends on the input.

    import(lib) std::vec { Vec };

    void buildCombos(str digits, usize i, Vec<str>* keypad, String* current, Vec<String>* out) {
        // base case: every digit has a letter, the buffer is one word
        if (i == digits.len) {
            out->push(current->clone());
            return;
        }
        u8 d = digits.at(i);
        // map the digit to its menu of letters
        str letters = keypad->at((usize)(d - (u8)'2'));
        for (usize j = 0; j < letters.len; j += 1) {
            current->pushChar(letters.at(j));      // choose a letter
            buildCombos(digits, i + 1, keypad, current, out);
            current->truncate(current->len - 1);   // undo the choice
        }
    }

    Vec<String> letterCombinations(str digits) {
        // the keypad table, indexed by digit - '2'
        Vec<str> keypad = Vec<str>::new();
        keypad.push("abc");
        keypad.push("def");
        keypad.push("ghi");
        keypad.push("jkl");
        keypad.push("mno");
        keypad.push("pqrs");
        keypad.push("tuv");
        keypad.push("wxyz");

        Vec<String> out = Vec<String>::new();
        // the empty digit string yields no combinations by convention
        if (digits.len == 0) return out;
        String current = String::new();
        buildCombos(digits, 0, &keypad, &current, &out);
        return out;
    }

The keypad is a small table indexed by the digit minus the byte `'2'`, so `'2'` lands on "abc", `'7'` on "pqrs", and `'9'` on "wxyz". The buffer `current` is shared across the whole walk, and each level appends its chosen byte, recurses, then truncates it away. The `truncate` is the rollback: it is the string-building equivalent of the `pop` in every other problem in this chapter. At the base case the buffer is complete, so we clone it, `clone` copies the bytes, because the buffer is about to be overwritten by the next combination.

Time and space. If the digits yield c combinations each of length L, the time is O(c × L), dominated by the copying at each leaf, and the space is O(c × L) for the output plus O(L) for the recursion, the buffer, and the keypad. As with the other enumerations, the size of the answer is the true limit.

Edge cases. An empty digit string yields no combinations, not one empty string, which is the common convention. A digit outside 2..9 would index the keypad out of range, so callers must pass only valid digits. Forget the `truncate` and every combination is polluted by the letters of its siblings, which is exactly the "forgot the undo" failure seen throughout this chapter.

A variation. The number of combinations is the product of each pressed key's letter count, and that count needs no recursion at all: multiply the lengths as you walk the digits once. It is a good sanity check on the generator and a reminder that sometimes the count is the easy half of "enumerate them all".

28.13 Generate All Balanced Parentheses

The problem. Given n pairs of parentheses, produce every string of n openers and n closers that is well-formed. For n = 3 the five strings are "((()))", "(()())", "(())()", "()(())", and "()()()".

Picture this. You are writing brackets from left to right, and at every position you face the same two choices: write an opener, or write a closer. But not every sequence of choices is legal. You may write a closer only if some opener is still waiting to be closed, and you may write an opener only while unplaced openers remain. Those two rules keep you on the path of valid strings, and when both budgets reach zero you have one complete balanced string.

Brute force, then better. The brute force writes all 2^(2n) strings of n openers and n closers and tests each for balance, wasteful, since most candidates are illegal. The backtracking keeps two counters and only makes choices that keep both non-negative, so every leaf it reaches is already a valid string and no final balance check is needed.

    import(lib) std::vec { Vec };

    void parenFrom(i32 open, i32 close, String* current, Vec<String>* out) {
        // base case: both budgets empty, so the string is balanced
        if (open == 0 && close == 0) {
            out->push(current->clone());
            return;
        }
        // prune: write an opener only while openers remain
        if (open > 0) {
            current->pushChar((u8)'(');
            parenFrom(open - 1, close + 1, current, out);
            current->truncate(current->len - 1);
        }
        // prune: write a closer only when one is waiting to be closed
        if (close > 0) {
            current->pushChar((u8)')');
            parenFrom(open, close - 1, current, out);
            current->truncate(current->len - 1);   // rollback
        }
    }

    Vec<String> generateParentheses(i32 n) {
        Vec<String> out = Vec<String>::new();
        String current = String::new();
        // start with n openers unplaced and none waiting to be closed
        parenFrom(n, 0, &current, &out);
        return out;
    }

The two counters carry the state. `open` is how many openers are still unwritten, and `close` is how many openers are currently unmatched and may therefore be closed. Writing an opener spends one of the former and creates one of the latter (`open - 1, close + 1`); writing a closer spends one of the latter (`close - 1`), and the guard `close > 0` is what forbids a closer with nothing to close. The base case fires only when both are zero, which can happen only after all n pairs have been placed and matched.

Time and space. The number of valid strings is the nth Catalan number, about 4^n / (n^1.5), so the work is proportional to the output times n, and the space is the output plus O(n) for the buffer and the recursion. Catalan growth is still exponential, but it is dramatically smaller than 2^(2n): the pruning refuses to build the illegal strings at all.

Edge cases. n = 0 yields one string, the empty one, because the base case fires immediately. A negative n is nonsense and is not guarded; nothing would ever be placed. The two `if` guards are the entire correctness argument: remove the `close > 0` guard and the walk writes unclosable closers, and remove both guards and it writes every arrangement, balanced or not.

A variation. The same two-counter walk counts the Catalan numbers without building strings: return 1 at the base and add the results of the two branches. To generalise to several kinds of bracket at once, all three of `()`, `[]`, and `{}`, the two counters become a stack that must be popped in matching order, which is the valid-parentheses check of Chapter27 folded into the generator.

28.14 Validate a Binary Search Tree

The problem. Given a binary tree of integers, decide whether it is a valid binary search tree: every node's value is greater than every value in its left subtree and less than every value in its right subtree.

Picture this. A binary search tree is a building with a strict rule: everything in a left wing must be smaller than the floor above it, and everything in a right wing must be larger. The trap is that checking a node against only its two children is not enough. A value deep in the right wing could still be smaller than an ancestor several floors up, so each node must be checked against a whole allowed range, not just against its parent.

Brute force, then better. The tempting wrong answer checks, at each node, that the left child is smaller and the right child is larger. That accepts trees that are not search trees, because it never relates a node to its grandparent. The correct method threads an open interval (low, high) down the recursion; a node is valid only if its value lies strictly inside the interval, and then the left subtree inherits (low, value) and the right subtree inherits (value, high).

    bool validRange(TreeNode* root, i64 low, i64 high) {
        // base case: an empty subtree is valid
        if (root == null) return true;
        i64 v = (i64)root->value;
        // the value must lie strictly inside the inherited interval
        if (v <= low || v >= high) return false;
        // left inherits (low, v); right inherits (v, high)
        return validRange(root->left, low, v) && validRange(root->right, v, high);
    }

    bool isValidBst(TreeNode* root) {
        // start outside the whole i32 range so extremes are still legal
        return validRange(root, -2147483649, 2147483648);
    }

This reuses the `TreeNode` introduced in 27.8. The bounds start just outside the range of every possible i32 value, so even a node holding the smallest or largest legal integer can be validated. Each recursive call narrows the interval: a left child's upper bound becomes its parent's value, and a right child's lower bound becomes it. A node that violates its interval is caught no matter how deep it sits, which is precisely the case the naive child-only test misses.

Time and space. Every node is visited once, so the time is O(n), and the recursion descends to the tree's height, so the space is O(h), logarithmic for a balanced tree, linear for a chain. No auxiliary table is allocated.

Edge cases. A null tree is a valid search tree by definition. The comparisons are strict, so duplicate values are rejected; a tree that should allow equal values on one side relaxes that side to `<=` or `>=`. The i64 interval is deliberate: with i32 bounds there is no spare value outside the legal range to use as a sentinel, so a tree containing the extreme integer could not be validated.

A variation. An inorder walk of a search tree visits values in strictly increasing order, so a second valid method walks the tree in order while remembering the previous value and checks that each is larger. That version is also O(n), and it is really the same interval reasoning seen from a different angle; the interval version stays local to each node, the inorder version keeps one running state.

28.15 Level-Order Traversal

The problem. Given a binary tree, return its values level by level, top to bottom and left to right: the root, then all its children, then all its grandchildren, and so on. Each level is returned as its own group.

Picture this. You are reading a building floor by floor. On each floor you note everyone standing there before moving up, and while you do you write down where the people on the next floor can be found. A queue is exactly the right shape for this: first in, first out means the oldest waiting node is always handled next, so an entire floor is finished before anyone on the floor above is touched.

Brute force, then better. The recursive traversals of 27.8 cannot produce level order directly, because recursion dives to the bottom of a branch before it returns. A queue does it in a single pass: hold the root, and repeatedly remove a node, record it, and enqueue its children. Because the queue is FIFO, the children of the current level line up behind one another, ahead of the next level's children.

    import(lib) std::collections::queue { Queue };

    Vec<Vec<i32>> levelOrder(TreeNode* root) {
        Vec<Vec<i32>> out = Vec<Vec<i32>>::new();
        // base case: the empty tree has no levels
        if (root == null) return out;
        // a FIFO queue makes the traversal breadth-first
        Queue<TreeNode*> q = Queue<TreeNode*>::new();
        q.enqueue(root);
        while (!q.isEmpty()) {
            // snapshot the current level's width before adding children
            usize levelSize = q.count();
            Vec<i32> level = Vec<i32>::new();
            for (usize i = 0; i < levelSize; i += 1) {
                TreeNode* node = q.dequeue();
                level.push(node->value);
                // enqueue the next level's nodes behind this one
                if (node->left != null) q.enqueue(node->left);
                if (node->right != null) q.enqueue(node->right);
            }
            out.push(level);
        }
        return out;
    }

The one subtle line is `usize levelSize = q.count();`. At the top of the outer loop the queue holds exactly the nodes of the current level, so snapshotting its size before the inner loop marks where the level ends. Enqueuing children grows the queue during the inner loop, and without the snapshot those new nodes would be consumed in the same level and the floors would smear together.

Time and space. Each node is enqueued and dequeued exactly once, so the time is O(n). The queue holds at most the widest level, up to about n/2 nodes, and the output holds every value, so the space is O(n).

Edge cases. A null tree returns an empty vector. A single node returns one level holding one value. A partly filled last level is handled with no special case, because only children that actually exist are enqueued. A tree that is a straight chain is still valid input; it yields one value per level and a queue that never exceeds one.

A variation. For a flat list of values rather than groups, drop the inner batching: enqueue the root and, on each dequeue, record the value and enqueue both children. To return the levels bottom-up, reverse the outer vector at the end with `out.reverse()`; the levels themselves are untouched.

28.16 Kth Smallest Element in a BST

The problem. Given a binary search tree and an integer k, return the kth smallest value in the tree, counting from 1.

Picture this. A search tree is already arranged so that an inorder walk visits its values from smallest to largest, that is the defining property of the structure. So the kth smallest is simply the kth value you meet on such a walk. You need not sort anything or examine the whole tree; you can stop the instant you have counted k values.

Brute force, then better. The brute force collects every value, sorts the collection, and indexes k − 1, which is O(n log n) and ignores the ordering the tree already encodes. An inorder walk is O(h + k): it descends to the smallest value, then yields values in increasing order and can stop as soon as k of them have been seen. The better method exploits the structure instead of flattening it.

    void inorderCount(TreeNode* root, i32 k, i32* seen, i32* answer) {
        // base case: nothing here
        if (root == null) return;
        // prune: already counted k, no need to descend further
        if (*seen >= k) return;
        inorderCount(root->left, k, seen, answer);
        // the left subtree may have found the answer
        if (*seen >= k) return;
        // visit this node: inorder makes values emerge sorted
        *seen += 1;
        if (*seen == k) {
            *answer = root->value;
            return;
        }
        inorderCount(root->right, k, seen, answer);
    }

    i32 kthSmallest(TreeNode* root, i32 k) {
        // a shared counter and the answer slot, both passed by address
        i32 seen = 0;
        i32 answer = -1;
        inorderCount(root, k, &seen, &answer);
        return answer;
    }

The walk is the ordinary inorder of 27.8 with two additions: a counter `seen`, passed by pointer so it is shared across the whole traversal, and an early `if (*seen >= k) return;` at the top and after the left subtree. The counter is bumped when the current node is visited, after its left subtree, before its right, which is exactly the position that makes the values emerge in sorted order. Once the count reaches k the answer is recorded and every remaining frame returns without descending further.

Time and space. The best case visits O(h + k) nodes and stops; the worst case, when k is the largest value, visits all n. The recursion stack is O(h). Nothing is sorted and no auxiliary collection is built, which is the whole point relative to the brute force.

Edge cases. A null tree returns the sentinel −1, meaning "not enough nodes." A k below 1 or above the node count is outside the problem's contract and produces that same sentinel rather than an error, a quiet failure rather than a crash. Duplicate values are counted normally, though a strict search tree does not contain them.

A variation. If k is queried repeatedly, or the tree changes between queries, store at each node the number of nodes in its subtree. Then the kth smallest is found by descending once: compare k with the left subtree's size and go left, right, or stop. That is an order-statistic tree, and it is the same "carry one extra number in each node" trick used for the tree diameter in 27.9.
