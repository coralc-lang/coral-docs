Chapter21

The Build System and Tooling

From One File to a Project

Real programs span many files, so something must decide compile order, dependencies, what changed, and the artifact name. That is the build system, and Coral's is small by design.

A city has a planning office with a map of lots and roads. Builders work from the map instead of wandering the city, and a record of what changed avoids rebuilding everything for a small alteration.

Coral's build system is that office and is astonishingly small: the `coralc` compiler, the `coral.crlb` build file, and the generated module map. There is no separate linker driver or makefile dialect. This chapter covers project creation, build-file fields, compilation, the module map, and the language server, which is the same compiler in another role.

The module system and build system are two faces of one mechanism; after this chapter they should read as one design.

21.1 Naming

Names to fix:

    Coral           the language, extension .crl
    Coral Build     the build file, extension .crlb
    coralc          the compiler and the builder, one executable
    modules.map     the generated module table
    .coral/         the per-project cache and generated files

One binary plays every role. `coralc` compiles a single file, builds a project, and serves an editor under a flag. No separate tools means a short learning curve.

21.2 Creating a Project

The fast path is `coralc init`:

    $ coralc init myproject
    $ cd myproject

This scaffolds a working project:

    myproject/
    ├── coral.crlb          # the build file
    ├── .gitignore          # ensures **/.coral/ is ignored
    ├── .coral/             # cache and generated files
    └── src/
        └── lib.crl         # a hello-world main, so `coralc run` works

`init` refuses to overwrite an existing `coral.crlb`, and it appends `**/.coral/` to `.gitignore` if absent. The generated project runs immediately:

    $ coralc run
    Hello, World!

That is the whole ceremony. Add files under `src/`, and the build finds them.

21.3 The Build File

The build file is `coral.crlb`, a small declarative configuration language. It describes the project rather than performing steps. A complete example:

    build "myproject" {
        root       = "."
        entry      = "src"
        target     = "native-x86_64"
        opt        = "debug"
        output     = "build/myproject"
        module_map = ".coral/modules.map"
        cache_dir  = ".coral/cache"

        flags = ["--strict"]

        modules = ["src", "src/log", "src/text"]
        skip    = ["vendor", "target"]
    }

`root` is the base directory. `entry` names the module containing `main`. `target` selects `native-x86_64`, `native-arm64`, `wasm32`, or `bytecode`. `opt` is `debug`, `release`, or `size`. `output` is the binary path, and `module_map` and `cache_dir` place generated files.

The build file describes the map, not the steps. It says which folders are part of the project and where the front door is; the compiler works out order from imports.

Two list fields matter most. `modules` is the required list of build folders; only listed folders are scanned, so `vendor` trees and stray `lib.crl` files stay invisible. `skip` excludes subfolders during any scan. Together they control exactly what the build sees.

`modules` is a guest list: only listed names get in, so a stray `lib.crl` in a scratch folder does not become a guest. The price is keeping the list current, which `coralc map` handles.

Why an explicit list? A build graph that changes by accident cannot be trusted. If any folder containing `lib.crl` joined the build silently, a backup, vendored copy, or experiment would join without a decision. The explicit list makes the graph something a person wrote down, and `coralc map` keeps it fresh.

A build block may carry per-module overrides:

    override "src/parser" {
        opt   = "release"
        flags = ["--no-inline"]
    }

Overrides merge over the base build, with the child winning. This lets a hot parser use release optimization while the rest stays in debug with symbols.

21.4 Aliases

Imports use short names, and aliases define them. A module folder often has a long, prefixed name; an alias gives it a name source code writes:

    alias lexer  = "compiler/coral-lexer/lib.crl";
    alias parser = "compiler/coral-parser/lib.crl";
    alias common = "compiler/coral-common/lib.crl";

With these in the build file, source writes:

    import lexer::table { TokenTable };
    import common::token { Token };

and not:

    import coral-lexer::table { TokenTable };
    import coral-common::token { Token };

The builder applies aliases when writing the module map, so the compiler sees only short names. An alias must point at a folder in `modules`, and its name must not collide with another alias or bare folder name. `coralc doctor` catches both errors.

21.5 Tasks

A task is a named unit of work with an optional command and optional dependencies.

    task "run" {
        after = ["build"];
        exec  = "build/myproject";
    }

    task "test" {
        after = ["build"];
        exec  = "build/myproject --self-test";
    }

`after` names tasks that must finish first; the pseudo-task `"build"` is satisfied once the project builds. `exec` names a command; if it names a directory, output is redirected there. Run a task by name:

    $ coralc run            # runs the task "run", or the output binary
    $ coralc test

When a `"run"` task exists, `coralc run` executes it; otherwise `coralc run` builds and launches the binary. `coralc NAME` runs any task. Tasks keep entry points (`run`, `test`, `bench`, `clean`) in the build file instead of an unmaintained shell script.

A task turns a project's unwritten rituals into a command anyone can run. "Run `coralc test`" welcomes newcomers; "ask someone how to run the tests" does not.

21.6 Running the Build

The build pipeline:

    coralc build
      1. read coral.crlb
      2. resolve root, modules, skip, and aliases
      3. for each module, read its lib.crl surface
      4. resolve every re-export and register it in the module table
      5. detect duplicate module identities and aliases pointing nowhere
      6. write .coral/modules.map
      7. scan each source file's module imports, build the dependency graph
      8. detect unresolved imports and cycles (with a trace)
      9. topologically sort the modules
     10. for each module in order, hash its inputs; skip if unchanged
     11. compile the modules that changed
     12. link the entry module into the output

Step ten is the cache. Each module's fingerprint comes from its `lib.crl`, every source file in its folder, and its dependencies' fingerprints. An unchanged fingerprint skips the module; a dependency change invalidates dependents transitively. The cache is conservative, never optimistic. `coralc build --force` ignores it.

Everyday subcommands:

    coralc init [dir]          scaffold a project
    coralc build               build using the cache
    coralc build --force       ignore the cache
    coralc build --module M    build one module and its dependencies
    coralc build --emit-map    write modules.map and stop
    coralc run                 build, then run
    coralc map                 rescan the tree, refresh modules
    coralc clean               wipe the cache and the build directory
    coralc graph               dump .coral/graph.dot
    coralc doctor              validate the build file, aliases, and cycles
    coralc --serve             run the language server on stdio (LSP)

`coralc map` walks `root`, finds every folder with a `lib.crl`, adds missing folders to `modules`, removes listed folders without a surface, refreshes `modules.map`, and reports the diff:

    $ coralc map
    + added   src/log
    ~ updated modules.map  (14 entries, 3 aliases)

`--dry` prints the diff without writing. This keeps the explicit modules list honest as the project grows: you decide what is in the build, and the tool keeps the list matching the tree.

`coralc graph` writes `.coral/graph.dot`, a Graphviz module-dependency graph. `coralc doctor` validates the build file, checks aliases, and hunts cycles with actionable errors.

21.7 The Module Map

The generated `.coral/modules.map` bridges imports and the build. It is a plain-text table from module identity to implementing file:

    # coral modules.map v1, generated by `coralc build`, do not edit
    lexer::base     ->  compiler/coral-lexer/base.crl
    lexer::ident    ->  compiler/coral-lexer/ident.crl
    lexer::lexer    ->  compiler/coral-lexer/lexer.crl
    lexer::table    ->  compiler/coral-lexer/table.crl
    parser::expr    ->  compiler/coral-parser/expr.crl

    # aliases (from the build file)
    @common::token  ->  compiler/coral-common/token.crl

The compiler resolves `import lexer::table` through this map. The text form diffs cleanly, is greppable, needs no parser, and loads in one scan. It is a build artifact, regenerated every build, and belongs in `.gitignore` with `.coral/`.

The compiler never walks the directory tree. The builder walks once and writes the map; the compiler asks the map where a name lives. That division keeps single-file compilation fast and gives the module graph one source of truth.

The module map is a phone book. The compiler looks up an address instead of knocking on doors; the builder walks the streets once per build.

21.8 The Language Server: the Compiler as an Editor Backend

`coralc` also has a language-server mode, and it is the compiler rather than a separate program reimplementing half of one.

Launch it with a flag:

    $ coralc --serve

It is `--serve`, a flag, not a subcommand: `coralc --serve`, never `coralc serve`. `coralc --help` describes it as `--serve  run the language server on stdio (LSP)`. It speaks LSP over stdin/stdout with `Content-Length` framing, using only the standard library's I/O, so nothing but protocol bytes reaches stdout.

Because it is the same compiler, editor diagnostics match build diagnostics. There is no parallel grammar or second type checker. The server handles lifecycle, document synchronization, and diagnostics. It rejects requests before `initialize` with `-32002`, a second `initialize` with `-32600`, malformed JSON with `-32700`, and uses UTF-16 code units for positions. `shutdown` exits zero; without it, one. Closing a document clears its markers.

The server reports whole-project errors. Opening any file analyzes the build entry and publishes diagnostics for every file in the import closure, including files the buffer never mentions and files that import it if reachable from the entry. Fixed problems are cleared on the next report.

Hover returns real types. The compiler sets a resolved type on every identifier expression, so hovering a variable, field, function, generic parameter, `self`, import, or libc binding shows its declaration or type. Go-to-definition uses the same resolution.

`PROTOCOL.md` is normative: wire format, framing, error codes, payloads, and capabilities. `LANGUAGE-SERVER.md` is the status companion and explicitly not normative, because the wire format changes rarely while integration state changes often.

Diagnostics, hover, and definition work today. Completion, document symbols, semantic tokens, inlay hints, references, and code actions are planned. Unimplemented requests get `-32601` (MethodNotFound), which editors handle by hiding the affordance; ignoring them would look broken.

Because editor and build share one compiler, a mistake the editor underlines is the same one the build refuses.

21.9 Editors

Editor support exists for the two most requested editors.

A Zed extension (`coral-zed`) and a VS Code extension (`coral-vscode`) exist, plus forks. They share compiler resolution and protocol, so features work the same.

In Zed, nothing needs configuring. The extension declares its language server command, resolves `coralc` on `PATH`, and passes `--serve`, so it starts automatically. There is deliberately no `settings.json` entry, which would only fix one machine. Semantic tokens default to off and are worth enabling:

    "languages": {
      "Coral": {
        "semantic_tokens": "combined"
      }
    }

`combined` layers type-aware coloring over tree-sitter syntax highlighting; `full` replaces it. Start with `combined` while type information fills in.

In VS Code, nothing needs configuring either. The extension activates on `.crl`, probes for the compiler, and shows `coralc not found` if absent. Command-palette commands can set the compiler path or restart the server, but the default works.

With the compiler installed, open a project in Zed or VS Code and diagnostics, hover, and go-to-definition work without setup. Porting to another editor is genuinely small: `PROTOCOL.md` documents a plain stdio LSP. Neovim, Pulsar, Helix, Emacs, or Sublime can spawn the process and speak JSON-RPC. The client launches the process, sends `initialize`, forwards open/change/close notifications, and displays diagnostics and hovers. The hard part, understanding Coral, is already done.

21.10 Diagnostics and Warnings

Diagnostics are first-class. Every one carries a code, such as `E0103` for a Unicode homoglyph, `E0201` for a cyclic type layout, or `E0608` for a non-exhaustive switch. Codes make diagnostics searchable, suppressible, and testable. `--strict` promotes warnings to errors; unused-variable warnings are always on; `--explain CODE` prints a longer explanation.

Adopt `E0801` (unused variable) and `E0802` (unused import) early. They catch refactor debris. Enabling them from the start is cheaper than drowning in existing warnings later. Because the language server uses the same diagnostics, `E0608` means the same thing in a build or an editor.

21.11 A Worked Build

Here is a small program with a library module. The layout:

    myapp/
    ├── coral.crlb
    └── src/
        ├── lib.crl
        ├── main.crl
        └── math/
            ├── lib.crl
            └── vec2.crl

The build file lists both modules:

    build "myapp" {
        root   = "."
        entry  = "src"
        target = "native-x86_64"
        opt    = "debug"
        output = "build/myapp"
        modules = ["src", "src/math"]
    }

The math module declares a vector type and its surface:

    // src/math/vec2.crl
    import(lib) std::math::math { sqrt };

    pub struct Vec2 { f64 x; f64 y; }

    pub Vec2 vec2Add(Vec2 a, Vec2 b) {
        return Vec2 { .x = a.x + b.x, .y = a.y + b.y };
    }

    pub f64 vec2Length(Vec2 v) {
        return sqrt(v.x * v.x + v.y * v.y);
    }

    // src/math/lib.crl
    pub mod vec2 = import vec2;

The entry imports it by module identity:

    // src/main.crl
    import(lib) std::io::ios { println };
    import math::vec2 { Vec2, vec2Add, vec2Length };

    void main() {
        Vec2 a = Vec2 { .x = 3.0, .y = 4.0 };
        Vec2 b = Vec2 { .x = 1.0, .y = 2.0 };
        Vec2 c = vec2Add(a, b);
        println("sum = ({}, {}), length = {}", c.x, c.y, vec2Length(c));
    }

    // src/lib.crl
    pub mod main = import main;

Build and run:

    $ coralc build
    $ coralc run
    sum = (4, 6), length = 7.211102550927978

After changing `vec2.crl`, only the math module and its dependent main module recompile. Adding a folder under `src/` is absorbed by `coralc map`. The build file stays a dozen lines because it describes the tree's shape, not commands. Imports are the dependency graph, and the build system reads that graph instead of duplicating it. The language server reads the same graph, so editor and build are one story.

21.12 Exercises

1. Comprehension. Distinguish the `modules` and `skip` lists. Give a layout needing both, and explain what a stray `lib.crl` in a scratch folder does under each.

2. Comprehension. Why is `modules.map` plain text rather than binary or JSON? Name three properties the text form preserves and one it gives up.

3. Implementation. Run `coralc init`, add a second module with a `lib.crl`, run `coralc map`, and confirm it appears in `modules.map`. Then confirm `coralc run` still builds.

4. Build. Write a `coral.crlb` with release optimization for a hot module and debug for the rest. Which field does the override set, and which value wins?

5. Tasks. Add a `"lint"` task that builds then runs the output with `--check`, and a `"clean"` task that wipes the build directory. Show both blocks and how to invoke them.

6. Caching. You edit a comment in an unimported file. What recompiles? What if you edit a file whose module another imports? Why is the cache "conservative, never optimistic"?

7. Aliases. A module folder is `coral-lexer`. Write the alias letting source say `import lexer::table`, explain what the builder does with it, and what happens if it points outside `modules`.

8. Language server. Launch `coralc --serve` and describe the two things needed for a valid session. Why `--serve` rather than `serve`, and what happens to a request before `initialize`?

9. Whole project. Open a file whose import closure includes an erroneous file you did not write. Where does the error appear, and how is that different from an open-buffer-only server? What clears the marker?

10. Editors. Point an editor at `coralc --serve` and hover a variable, field, and function call. What does each show? Then enable semantic tokens in Zed and describe the change.

11. Porting. Sketch a minimal language-server client for your editor: the four messages it must send and the one notification it must display. Why does "a plain stdio LSP" make this feasible?

12. Meta. Dependencies come from source imports, while the module list is explicit and tool-refreshed. Describe one bug class each choice eliminates and one each makes harder to diagnose.
