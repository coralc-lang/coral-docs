Chapter 18

Input, Output, and the Filesystem

A Program That Cannot Reach Outside Is a Calculator

Programs must cross the process boundary: printing, reading input, opening files, walking directories, reading the environment, launching processes, and logging. Coral calls that boundary I/O.

The outside world can fail unpredictably: deleted files, denied permissions, full disks, closed pipes. `Result` makes those failures explicit, so nearly every I/O function returns one.

This chapter tours `std::io`: the tree, console I/O, files, buffering and binary I/O, paths and directories, environment and processes, logging and terminals, errors, and a worked program.

18.0 The Whole I/O Surface at a Glance

Every module below lives under `std::io`. The compiler prelude loads `std::io::ios` (with `std::text::string`, `std::option`, `std::result`, `std::vec`, `std::collections::arr`, and `core::str`), so `print`, `println`, `readLine`, `read`, `readVal`, the parsers, the manipulators, and `String` need no import.

    module              purpose                          headline names
    std::io::ios        console I/O and parsing          print println eprint vaprint readLine read readVal spaces hex parseI64
    std::io::fs         files, dirs, metadata            fileOpen fileRead fileWrite readFileToString
    std::io::bio        typed binary readers/writers     FileReader FileWriter readU32Le writeU32Be
    std::io::fios       C FILE* buffered streams         FileHandle fileOpen fileReadAll fileWriteString
    std::io::path       path string manipulation         join normalize extension stem parent filename
    std::io::process    subprocesses                     spawn waitFor readStdout run exit
    std::io::env        environment variables            get getInto set unset all
    std::io::cmd        command-line arguments           ArgParser commandLine
    std::io::log        structured logging               Logger LogLevel
    std::io::term       ANSI terminal control            reset bold red cursorPos clearScreen

Three facts hold. `fs` is the base module; it defines `IoError`, which the others return. The tree is layered: `fs` issues raw system calls, `fios` wraps buffered C `FILE*`, `bio` adds typed encoding, and `ios` provides console conveniences. The portable surface is identical across platforms; only the raw error codes in `IoError` differ.

18.1 The Shape of the I/O Library

Where does a printed value go?

C uses the variadic `printf`, which trusts a runtime format string. Coral uses ordinary compile-time-checked functions in `std::io::ios`:

    pub void print<comptime T>(T fmt, ...)
    pub void println<comptime T>(T fmt, ...)
    pub void eprint<comptime T>(T fmt, ...)
    pub void eprintln<comptime T>(T fmt, ...)

`print` writes to stdout with no newline; `println` adds one. The `e` variants write to stderr, which survives piping. `vaprint(... args)` prints values with no format string.

`comptime T` lets the compiler see the format literal and argument types together, so a mismatch is a build error. `println("{} {}", a)` fails at build time; C's `printf` would read a stray stack word.

`fs` is the filesystem, `bio` and `fios` move bytes through it, and `ios` is the usual entry point. The chapter proceeds top-down.

18.2 Console Output: print, println, and the Manipulators

Formatting a line is the first job of most programs.

    import(lib) std::io::ios { println, eprintln };

    void main() {
        i32 x = 255;
        str name = "ada";
        f64 pi = 3.14159;

        // {} consumes the next argument and dispatches on its type
        println("hello, {}", name);              // hello, ada
        // {:x} and {:b} are integer-only specifiers
        println("dec {} hex {:x} bin {:b}", x, x, x);
        eprintln("wrote {} bytes", 42);          // to stderr, not stdout
    }

`{}` consumes the next argument and dispatches on its type. It handles built-in scalars, `bool`, `cchar`, `char`, both C string types, `str`, `String`, `rawptr`, manipulators, and any type implementing `@toStr`. Anything else is a compile error, so a struct cannot be printed as raw bytes.

`{{` prints a literal `{`, `}}` a literal `}`, and placeholder count must equal trailing argument count. `{:d}` is decimal, `{:x}` hexadecimal, `{:b}` binary, and `{:p}` a pointer. `{..}` spreads an iterable, separating elements with a comma and space.

    // {:d} is decimal; {..} spreads an iterable, separating with ", "
    println("value = {:d} hex = {:x} bin = {:b}", 255, 255, 255);
    println("items: {..}", numbers);

Integer specifiers are integer-only; `char` counts as an integer and renders its codepoint. A float with `{:x}` is a compile error. `{..}` requires a range-for iterable, also checked at build time.

Pass a manipulator when you want special rendering through plain `{}`. `ios` defines five:

    import(lib) std::io::ios { _spaces, _repeat, _hex, _bin, _fixed };

    // a manipulator renders specially through the plain {} placeholder
    println("{}right-aligned", _spaces(10));   // ten spaces, then the text
    println("{}", _repeat('-', 30));           // a rule of thirty dashes
    println("{}", _hex(0xDEADBEEF));           // 0xdeadbeef
    println("{}", _bin(0b1010));               // 0b1010
    println("{}", _fixed(3.14159, 2));         // 3.14

The signatures are `_spaces(u64 count)`, `_repeat(u8 ch, u64 count)`, `_hex(u64 value)`, `_bin(u64 value)`, and `_fixed(f64 value, u64 precision)`. The manipulator structs are module-internal; the underscore-prefixed constructors are the public API. `_repeat` takes a byte; `fmt::repeat` takes a `str` and a count.

Two caveats:

**`std::fmt::format` is a stub.** Declared `String format(str f, ...)`, it deletes exact `{}` pairs and substitutes nothing; `{:x}` is left literally. `format("x = {}", 3)` returns `"x = "`. Use `print`, `println`, `eprint`, or `eprintln` to interpolate, and the `formatX` family (`formatInt`, `formatFloat`, `formatHex`, and the rest) to build a `String`.

**Output is unbuffered, and `flush` is a no-op.** Each `print` builds a line in a 1024-byte stack buffer and issues one `write(2)`, so a line is never split across syscalls. `flush()` exists for symmetry and does nothing. A line printed before a crash is already on the terminal.

18.3 Console Input: Reading a Line and Reading Values

Reading is the mirror image of printing, and more delicate: input may be malformed.

`readLine` reads one line into a `String` you own:

    pub bool readLine(String* out)

    import(lib) std::io::ios { readLine, println };
    import(lib) std::text::string { String };

    void main() {
        String line = String::new();
        // readLine returns false once the stream has ended
        while (readLine(&line)) {
            if (line.isEmpty()) break;
            println("you said: {}", line);
        }
        line.free();   // readLine fills a String you own
    }

`readLine` clears `out`, reads bytes until a newline, and drops carriage returns so CRLF input works. It returns `false` only when the stream has ended and nothing was read; a final unterminated line returns `true`, then the next call returns `false`. `String` grows, so lines can be arbitrarily long.

`readChar` returns a single `u8`, or zero at end of input:

    pub u8 readChar()

`read` parses the next line according to the type of its output parameter:

    pub void read<comptime T>(T* out)
    pub T    readVal<T>()

    import(lib) std::io::ios { read, readVal };

    // read dispatches on the type of its output parameter
    i32 n = readVal<i32>();      // reads a line, parses an integer
    f64 g;
    read(&g);                    // reads a line, parses a double
    String s;
    read(&s);                    // reads a line into a String

`read` dispatches on `@typeof(T)` at compile time. Integers and floats parse a line, `bool` accepts `true`, `1`, or `yes` as true and anything else as false, `cchar` reads a character, and `String` reads a line. `readVal<T>` reads into a local and returns it.

`readVal` returns the parse result through the same channel as the `parseX` functions, so malformed input is not distinguishable by return value alone. Use `readLine` plus a `parseX` function when failure matters.

18.4 Parsing Text into Values

The three `ios` parsers report success through an out-parameter:

    pub i64 parseI64(str sv, bool* ok)
    pub u64 parseU64(str sv, bool* ok)
    pub f64 parseF64(str sv, bool* ok)

    import(lib) std::io::ios { parseI64, parseF64 };

    bool ok = false;
    // success is reported through the out-parameter, not the return value
    i64 n = parseI64("-42", &ok);       // ok is true, n is -42
    i64 bad = parseI64("12x", &ok);     // ok is false, bad is 0

On success `*ok` is true and the value is returned; on failure `*ok` is false and the result is zero. `parseI64` accepts an optional `+` or `-` then decimal digits, rejecting empty input, a lone sign, non-digits, and overflow, including the `-9223372036854775808` boundary. `parseU64` accepts an optional `+` and digits. `parseF64` uses `strtod` on a bounded copy and requires only trailing whitespace, so `" 3.5"` and `"3.5  "` parse but `"3.5x"` fails.

Use this lightweight form when yes-or-no is enough and failure needs no detail. Use `Result` when the caller needs to know why. Never ignore `ok`: `parseI64("abc", &ok)` returns `0`, indistinguishable from a real zero.

18.5 Files: Opening, Reading, Writing, Closing

A file begins with an open call that returns a handle or an error.

    import(lib) std::io::fs { fileOpen, fileClose, File, IoError };
    import(lib) std::result { Result };

    // fileOpen returns a Result, never a sentinel value
    Result<File, IoError> opened = fileOpen("notes.txt", "r");
    if (opened.isErr()) {
        eprintln("could not open notes.txt");
        return;
    }
    File f = opened.unwrap();
    // ... use f ...
    fileClose(f);   // every successful open needs exactly one close

`File` wraps the operating system descriptor, so a bare integer cannot be used as a file. `fileOpen` takes a stdio-style mode:

    mode    open flag combination                       effect
    "r"     read only                                   file must exist
    "w"     write only, create, truncate                existing content is lost
    "a"     write only, create, append                  writes always land at EOF

Adding `+` widens the mode to read-and-write, for example `"r+"`.

Three operations move bytes:

    // fileRead returns how many bytes were read; zero means end of file
    pub Result<isize, IoError> fileRead(File f, u8* buf, usize count)
    pub Result<isize, IoError> fileWrite(File f, const u8* buf, usize count)
    // whence is SEEK_SET, SEEK_CUR, or SEEK_END
    pub Result<isize, IoError> fileSeek(File f, isize offset, i32 whence)

`fileRead` reads up to `count` bytes and returns how many it read; zero means end of file, which is success. `fileWrite` returns how many bytes it wrote. `fileSeek` moves the position and returns the new offset; `whence` is `SEEK_SET`, `SEEK_CUR`, or `SEEK_END`. All three translate a negative system result into `IoError`.

The library provides whole-file helpers, the first functions to reach for:

    pub Result<String, IoError> readFileToString(str path)
    pub Result<bool, IoError>   writeFileFromString(str path, const String* data)

    import(lib) std::io::fs { readFileToString, writeFileFromString };
    import(lib) std::text::string { String };

    Result<String, IoError> loaded = readFileToString("notes.txt");
    if (loaded.isOk()) {
        String text = loaded.unwrap();
        println("{} bytes", text.len);
        text.free();   // the returned String is owned by the caller
    }

    String out = String::from("hello, file\n");
    // "w" mode truncates at open, so a failure mid-write truncates the file
    (void)writeFileFromString("out.txt", &out).unwrap();
    out.free();

`readFileToString` opens read-only, reads in 4096-byte chunks into a growable `String`, and on error closes the handle and frees the partial buffer. `writeFileFromString` opens with truncation and loops until every byte is written, returning `Ok(true)`. Because `"w"` truncates at open, a mid-write failure leaves a truncated file; when that matters, write a temporary file and rename it over the target.

For existence or accessibility checks, and for deletion or renaming, no open is needed:

    pub bool   fileExists(str path)
    pub bool   canAccess(str path, i32 mode)
    pub Option<bool> statPath(str path, Stat* out)
    pub Result<bool, IoError> deleteFile(str path)
    pub Result<bool, IoError> renameFile(str oldPath, str newPath)

    import(lib) std::io::fs { fileExists, canAccess, deleteFile, renameFile, R_OK, W_OK };

    // absence is not an error here: fileExists simply returns false
    if (fileExists("config.txt")) { /* ... */ }
    if (canAccess("config.txt", W_OK)) { /* writable */ }
    (void)renameFile("a.txt", "b.txt").unwrap();
    (void)deleteFile("old.txt").unwrap();

`fileExists` returns a plain `bool`; absence is the answer, not an error. `canAccess` takes `F_OK`, `R_OK`, `W_OK`, or `X_OK`. `statPath` fills a `Stat` (size, mode, link count, timestamps) and returns `Some(true)` on success or `None` on failure; `getFileType` classifies it in 18.7.

Handle every `Result`: check or switch on `Err`, and use `unwrap` only after the failure is genuinely handled.

Every successful `fileOpen` needs exactly one `fileClose` on every path out, including error paths.

18.6 Buffered and Binary I/O: bio and fios

The raw `fs` functions issue one system call per operation. Two higher layers exist.

`std::io::fios` wraps C's buffered `FILE*` in a distinct `FileHandle`:

    // a distinct handle over the C library's opaque buffered FILE*
    pub distinct FileHandle = rawptr;

    pub Result<FileHandle, IoError> fileOpen(str path, str mode)
    pub void   fileClose(FileHandle fh)
    pub Result<usize, IoError> fileWrite(FileHandle fh, str data)
    pub Result<usize, IoError> fileRead(FileHandle fh, u8* buf, usize maxLen)
    pub Result<usize, IoError> fileWriteString(FileHandle fh, const String* s)
    pub Result<bool, IoError>  fileReadAll(str path, String* out)
    pub bool   fileEof(FileHandle fh)
    pub bool   fileError(FileHandle fh)
    pub void   fileFlush(FileHandle fh)

Buffering accumulates small reads and writes in user space, replacing many syscalls with one per buffer-full. For many short operations, this is the first performance lever.

`std::io::bio` handles encoding, not buffering. It wraps an open `File` in `FileReader` or `FileWriter` for typed values in a chosen byte order:

    pub struct FileReader { i32 fd; ... }   // FileReader::fromFd(f)
    pub struct FileWriter { i32 fd; ... }   // FileWriter::fromFd(f)

    import(lib) std::io::bio { FileReader, FileWriter };
    import(lib) std::io::fs { fileOpen, fileClose, File };

    // "rb" opens the file in binary mode
    File f = fileOpen("data.bin", "rb").unwrap();
    FileReader r = FileReader::fromFd(f);

    u32 magic  = r.readU32Le();       // little-endian, four bytes
    u16 version = r.readU16Be();      // big-endian, two bytes
    f64 sample = r.readF64Le();
    r.skip(8);                        // advance over a reserved field

    fileClose(f);   // the wrapper borrows the descriptor, it does not own it

Each scalar width and byte order has reader and writer methods: `readU8`/`writeU8`, `readU16Le`/`readU16Be`, `readU32Le`/`readU32Be`, `readU64Le`/`readU64Be`, the signed variants, and `readF32`/`readF64` in both orders. `fromFd` borrows an open `File`: it owns the position, not the lifetime, so you still close the `File`. Byte-swap helpers are `bswapU16`, `bswapU32`, and `bswapU64`.

Typed readers and writers do not report errors: `readU32Le` yields zero on a short read and `writeU32Le` ignores a failed write. Only `readBytes` and `writeBytes` return `Result<bool, IoError>` and guarantee exact counts. For possibly truncated files, use `readBytes` and decode yourself. `bio` does not buffer, so a ten-field struct costs ten small syscalls; combine it with `fios` or read whole records at once.

What is slow is crossing into the kernel, and the number of crossings depends on how you read. `fs` gives control, `fios` reduces crossings, and `bio` provides encoding.

18.7 Paths, Directories, and Metadata

A path is a string with grammar, and `path` parses it without touching the disk. Every function is a pure string operation, so it works on paths that do not exist.

    import(lib) std::io::path {
        join, normalize, absolute, changeExtension,
        extension, stem, parent, filename, isAbsolute, hasExtension
    };

    str p = "/home/ada/notes/today.txt";
    // the path accessors are pure string operations; no disk is touched
    println("{}", filename(p));      // today.txt
    println("{}", stem(p));          // today
    println("{}", extension(p));     // .txt
    println("{}", parent(p));        // /home/ada/notes

    // join inserts a separator only when one is actually needed
    String full = join("/home/ada", "notes/today.txt");   // /home/ada/notes/today.txt
    String clean = normalize("/home/ada/./notes//today.txt"); // /home/ada/notes/today.txt
    String abs = absolute("/home/ada", "notes/today.txt");    // resolve relative to base
    String md = changeExtension(full.asView(), ".md");        // /home/ada/notes/today.md

`findLastSep` returns the last separator index or `p.len + 1`; use the named accessors built on it instead. `join` inserts a separator only when needed. `normalize` collapses repeated separators and `.` segments but does not resolve `..`. `absolute` resolves against a base and normalizes. None of these check the filesystem, so path equality is not file identity.

Linux uses `/` and accepts `\`; Windows is the reverse. Use `join` and the accessors instead of writing separators in portable code.

`fs` manipulates directories:

    pub Result<bool, IoError> createDir(str path, i32 mode)
    pub Result<bool, IoError> createDirRecursive(str path, i32 mode)
    pub Result<bool, IoError> removeDir(str path)
    pub Result<Dir, IoError>  openDir(str path)
    pub bool readDirEntry(Dir dir, Dirent* out)
    pub void closeDir(Dir dir)

`createDir` makes one directory; `createDirRecursive` creates missing components like `mkdir -p` and treats an existing directory as success. `mode` carries permission bits (`448` for owner-only `rwx`, `493` for `0755`). `removeDir` removes only an empty directory; walk and delete contents first. `openDir` returns a `Dir` read one entry at a time:

    import(lib) std::io::fs {
        openDir, readDirEntry, closeDir, Dirent, getFileType, statPath, Stat
    };

    void listDir(str path) {
        Result<Dir, IoError> od = openDir(path);
        if (od.isErr()) {
            eprintln("cannot list {}", path);
            return;
        }
        Dir dir = od.unwrap();
        Dirent entry;
        // readDirEntry returns false at the end of the stream
        while (readDirEntry(dir, &entry)) {
            str name = str::fromCstr((cchar*)entry.d_name);
            // "." and ".." are real entries and must be skipped by hand
            if (name.equals(".") || name.equals("..")) continue;
            println("{}", name);
        }
        closeDir(dir);
    }

`readDirEntry` copies the next entry into `Dirent` and returns `false` at the end. `d_name` is NUL-terminated, hence `str::fromCstr`. `.` and `..` are real entries and must be skipped by hand.

To classify an entry, stat it and read its mode:

    pub struct Stat { /* size, mode, link count, timestamps */ }
    pub enum FileType {
        Unknown, Regular, Directory, CharDevice,
        BlockDevice, Fifo, Symlink, Socket
    }
    pub Option<bool> statPath(str path, Stat* out)
    pub FileType getFileType(const Stat* s)

    Stat st;
    if (statPath("notes.txt", &st).isSome()) {
        println("size = {}", st.st_size);
        // getFileType reads st_mode for you, so no magic numbers appear
        switch (getFileType(&st)) {
            FileType::Regular   => println("a regular file"),
            FileType::Directory => println("a directory"),
            else                => println("something else"),
        }
    }

`Stat` follows POSIX, so its fields are platform-defined numbers: `st_size` is bytes, `st_mode` is raw mode bits, and timestamps are seconds and nanoseconds. `getFileType` maps `st_mode` to `FileType`, so no magic numbers are needed. Timestamps use the platform epoch and resolution, so comparing them across platforms is a bug.

18.8 Environment, Processes, and Arguments

Three modules connect a program to its surroundings.

`std::io::env` reads and writes environment variables:

    pub Option<String> get(str name)
    pub bool getInto(str name, String* out)
    pub Result<bool, IoError> set(str name, str value)
    pub Result<bool, IoError> unset(str name)
    pub usize all(Vec<String>* out)

    import(lib) std::io::env { get, getInto, set, unset, all };
    import(lib) std::option { Option };
    import(lib) std::text::string { String };

    Option<String> home = get("HOME");
    if (home.isSome()) {
        String value = home.unwrap();
        println("HOME = {}", value);
        value.free();   // get returns an owned String; the caller frees it
    }

    String pathVar = String::new();
    // getInto writes into a String you already own
    if (getInto("PATH", &pathVar)) { /* ... */ }
    pathVar.free();

    // set and unset can fail, so both return a Result
    (void)set("MY_APP_MODE", "debug").unwrap();
    (void)unset("MY_APP_MODE").unwrap();

`get` returns an owned `String` in an `Option`; the caller frees it. `getInto` writes into a `String` you own, freeing its old contents first, and returns whether the variable was set. Absence is `None` or `false`, never an error. `set` and `unset` return `Result` because changing the environment can fail. `all` appends every `"NAME=VALUE"` entry to a `Vec<String>` and returns the count; free each string before disposing the vector.

`std::io::process` runs other programs:

    pub struct Process { i32 pid; i32 stdinFd; i32 stdoutFd; i32 stderrFd; }
    pub struct ProcessResult { i32 exitCode; bool signaled; i32 termSignal; }

    pub Result<Process, IoError>       spawn(str cmd, Vec<str>* args)
    pub Result<ProcessResult, IoError> waitFor(Process* p)
    pub Result<isize, IoError>         writeStdin(Process* p, const cchar* data, usize len)
    pub Result<isize, IoError>         readStdout(Process* p, u8* buf, usize maxLen)
    pub Result<isize, IoError>         readStderr(Process* p, u8* buf, usize maxLen)
    pub Result<i32, IoError>           run(str cmd, Vec<str>* args)
    pub void                           exit(i32 code)

`spawn` creates a child with pipes on stdin, stdout, and stderr, and returns without waiting. `writeStdin` sends bytes, `readStdout` and `readStderr` receive them, and `waitFor` blocks until exit and closes the pipes. Read what you need before `waitFor`, or the child may block on a full pipe.

`run` spawns, drains both output pipes, waits, and returns the exit code. Use it when you only need success or failure.

    import(lib) std::io::process { spawn, run, waitFor, readStdout, Process, ProcessResult };
    import(lib) std::vec { Vec };

    // run spawns, drains both pipes, waits, and returns the exit code
    i32 status = run("grep", args).unwrap();
    println("grep exited with {}", status);

    // Or stream the child's output yourself:
    Vec<str> argv = Vec<str>::new();
    argv.push("-l");
    argv.push("TODO");
    Process p = spawn("grep", &argv).unwrap();
    u8 buf[512];
    while (true) {
        isize n = readStdout(&p, buf, 512).unwrap();
        if (n <= 0) break;
        // ... use buf[0 .. n) ...
    }
    // drain the pipes before waitFor, or the child may block on a full pipe
    ProcessResult result = waitFor(&p).unwrap();
    println("exit {}", result.exitCode);

Arguments are a `Vec<str>`. `spawn` searches `PATH` like a shell; a path containing a slash is used as given. `ProcessResult` distinguishes a normal exit (`exitCode`, `signaled` false) from a signal death (`signaled` true, `termSignal` set). `exit(code)` terminates the current process immediately; prefer returning a code from `i32 main` when possible.

`std::io::cmd` offers `ArgParser`, but its methods take `argc` and `argv` directly:

    // parse, hasFlag, and getOption all take argc/argv directly
    pub struct ArgParser {
        Vec<String> positional;
        bool error;
        String errMsg;
        usize pos;

        static ArgParser new()
        void dispose()
        void parse(i32 argc, cchar** argv)
        bool hasFlag(i32 argc, cchar** argv, str shortFlag, str longFlag)
        bool getOption(i32 argc, cchar** argv, str shortFlag, str longFlag, String* out)
        usize count()
        str get(usize idx)
    }
    pub Option<str> commandLine()

`parse` collects non-flag arguments as positionals, skipping anything starting with `-` and stopping at bare `--`. `hasFlag` tests a short or long flag. `getOption` reads the following value into a `String` you own. `count` and `get` read positionals, and `dispose` frees owned strings. The catch is `argc`/`argv`: `void main()` does not receive them, so `ArgParser` pairs naturally with `i32 main(i32 argc, cchar** argv)`.

For `void main()`, use `commandLine()`, which returns the raw process command line as an `Option<str>`. On Linux it is `/proc/self/cmdline` with NUL separators; on Windows it is the string from `GetCommandLineA`. Reading `argv[1]` on Linux is a small scan:

    import(lib) std::io::cmd { commandLine };
    import(lib) std::option { Option };

    // Linux: argv[0]\0argv[1]\0...\0, return argv[1], or "" if absent.
    str firstArg() {
        // commandLine returns the raw argv[0]\0argv[1]\0...\0 buffer
        Option<str> cl = commandLine();
        if (cl.isNone()) return "";
        str all = cl.unwrap();
        usize i = 0;
        while (i < all.len && all.ptr[i] != 0) i += 1;   // skip argv[0]
        if (i >= all.len) return "";
        i += 1;                                          // step over the NUL
        usize start = i;
        while (i < all.len && all.ptr[i] != 0) i += 1;
        if (i == start) return "";
        return str::fromParts(all.ptr + start, i - start);
    }

Returning a `str` view is safe because the command-line buffer lives for the whole process. Windows returns one space-separated string, so a portable `firstArg` would split on spaces; use `#[[cfg]]` or a `flag` block for the difference.

Do not assume `main` receives `argv` as in C. A `void main()` ignores the runtime's C arguments; the portable accessor is `commandLine()`.

18.9 Logging and the Terminal

Two convenience modules remain.

`std::io::log` provides a leveled logger:

    pub variant LogLevel { Debug, Info, Warn, Error, Fatal }

    pub struct Logger {
        LogLevel minLevel;
        String name;

        static Logger new(str name, LogLevel minLevel)
        void dispose()
        void setLevel(LogLevel level)
        bool enabled(LogLevel level)
        void debug(str msg)
        void info(str msg)
        void warn(str msg)
        void error(str msg)
        void fatal(str msg)
    }

    import(lib) std::io::log { Logger, LogLevel };

    Logger log = Logger::new("server", LogLevel::Info);
    log.debug("starting");            // dropped: below the minimum
    log.info("listening on port {}", 8080);
    // Error and Fatal go to stderr; the rest go to stdout
    log.error("connection dropped");
    log.dispose();

`new` copies `name`, so `dispose` must free it; forgetting leaks one buffer. `enabled` tells whether a level passes the filter, letting callers skip expensive formatting. `Error` and `Fatal` go to stderr; the rest go to stdout. Lines are formatted `[LEVEL][name] message` through `println`/`eprintln`; there is no file sink or structured encoding.

`std::io::term` emits ANSI escapes for color and cursor control:

    pub void black() red() green() yellow() blue() magenta() cyan() white()

    green();
    println("this line is green");

ANSI is rendered by capable terminals; a pipe or file receives raw escape bytes because the functions do not test for a terminal. Decide once whether to emit color. Cursor and clear helpers are raw material for a TUI, and for a mess if unconfined.

18.10 Errors: Reading IoError Honestly

Every outside-world function here returns `Result`, and every `Err` carries the same type:

    pub variant IoError {
        Os       { i32 code; str op; },   // errno (Linux) / GetLastError (Windows)
        Eof      { str op; },             // stream ended before the requested bytes
        BadUsage { str msg; }             // caller-side problem, no system call
    }
    // os(op) captures the calling thread's current error number
    pub extend IoError {
        static IoError os(str op)
    }

The cases split failures by responsibility. `Os` means the operating system refused; `code` is the raw platform number and `op` names the operation (`"open"`, `"read"`, `"mkdir"`). `Eof` means the stream ended early, mainly from `bio`'s exact-count reads. `BadUsage` means the caller asked for something nonsensical, such as an invalid mode; no system call was made. `IoError::os(op)` is a library-internal constructor; user code inspects errors.

Inspect one with an ordinary variant switch:

    import(lib) std::io::fs { IoError };

    void reportIoError(str path, IoError e) {
        // the three cases split failures by who is responsible
        switch (e) {
            IoError::Os { code, op }  => { eprintln("{}: {} (os error {})", path, op, code); },
            IoError::Eof { op }       => { eprintln("{}: unexpected end of file during {}", path, op); },
            IoError::BadUsage { msg } => { eprintln("{}: {}", path, msg); },
        }
    }

`Os.code` is platform-specific. On Linux it is `errno`: 2 is missing, 13 is permission denied, 21 is a directory, 17 is already exists. Windows uses `GetLastError` values. The number is preserved for callers who need it; `op` gives portable context. Portable code cannot switch on the number, so check with `canAccess` or treat it as platform-specific.

Common failure modes:

    symptom                        usual cause                         first check
    open of a file that should exist fails   wrong working directory    paths are relative to CWD, not the source
    read returns 0 immediately      file is empty, or offset at EOF     a zero result is success, not failure
    write "succeeds" but file is short   old content truncated at open   "w" truncates before the first write
    open fails with a permission code    mode was never granted          canAccess(path, R_OK/W_OK)
    removeDir fails                 directory is not empty              walk and delete entries first
    child never returns             nobody drained its output pipe      read before waitFor, or use run

Handle the `Err` or propagate it; `unwrap` is the last resort, not a strategy. An I/O failure is the world misbehaving, not necessarily a program bug, so the same error may warrant a retry in one context and a fatal report in another.

18.11 Putting It Together: A Word-Count Tool

This complete `wc` uses console I/O, file reading, argument access, string scanning, and error handling.

    import(lib) std::io::ios { println, eprintln };
    import(lib) std::io::fs { IoError, readFileToString };
    import(lib) std::io::cmd { commandLine };
    import(lib) std::text::string { String };
    import(lib) std::option { Option };
    import(lib) std::result { Result };

    // Linux: the raw command line is argv[0]\0argv[1]\0...\0.
    // Returns argv[1] as a view, or "" when there is none.
    str firstArg() {
        Option<str> cl = commandLine();
        if (cl.isNone()) return "";
        str all = cl.unwrap();
        usize i = 0;
        while (i < all.len && all.ptr[i] != 0) i += 1;   // skip argv[0]
        if (i >= all.len) return "";
        i += 1;
        usize start = i;
        while (i < all.len && all.ptr[i] != 0) i += 1;
        if (i == start) return "";
        return str::fromParts(all.ptr + start, i - start);
    }

    void reportIoError(str path, IoError e) {
        switch (e) {
            IoError::Os { code, op }  => { eprintln("{}: {} (os error {})", path, op, code); },
            IoError::Eof { op }       => { eprintln("{}: unexpected end of file during {}", path, op); },
            IoError::BadUsage { msg } => { eprintln("{}: {}", path, msg); },
        }
    }

    bool isSpaceByte(u8 c) {
        return c == ' ' || c == '\t' || c == '\n' || c == '\r';
    }

    i32 main() {
        str path = firstArg();
        if (path.len == 0) {
            eprintln("usage: wc <file>");
            return 1;
        }

        Result<String, IoError> loaded = readFileToString(path);
        if (loaded.isErr()) {
            reportIoError(path, loaded.unwrapErr());
            return 1;
        }

        String text = loaded.unwrap();
        usize lines = 0;
        usize words = 0;
        bool inWord = false;
        // one byte-based pass: a newline ends a line, whitespace ends a word
        for (usize i = 0; i < text.len; i += 1) {
            u8 c = text.at(i);
            if (c == '\n') lines += 1;
            if (isSpaceByte(c)) {
                inWord = false;
            } else if (!inWord) {
                words += 1;
                inWord = true;
            }
        }

        // {:d} prints the counts as decimal, then the byte size and path
        println("{:d} {:d} {:d} {}", lines, words, text.len, path);
        text.free();   // release the String returned by readFileToString
        return 0;
    }

`firstArg` steps over the program name and returns the first argument as a view valid for the process lifetime. `reportIoError` handles all three `IoError` cases. `main` returns `i32`: zero on success, one for a missing argument or unreadable file.

The counting loop walks bytes once, incrementing `lines` at each newline and `words` on each whitespace-to-non-whitespace transition, matching `wc`. `text.at(i)` is bounds-checked, but the loop guarantees `i < text.len`. The byte count is `text.len`; no `strlen` walk occurs.

`readFileToString` returned an owned `String`, so `text.free()` releases it. Library files use `#[[no_drop_all]]` and free by hand; ordinary code relies on `String`'s `@drop`, so never free twice.

Three extensions remain as exercises: handle a final line without a newline, stream instead of reading the whole file, and count UTF-8 characters rather than bytes.
