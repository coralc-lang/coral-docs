Live Examples: Warm-Up and Fundamentals

Learning to Swim by Getting in the Water

This chapter works problems end to end, interview style. Each follows the same arc: problem, picture, brute force, better approach, a complete Coral program, cost, edge cases, and a variation.

When you read a solution, ask which line carries the weight. Every problem here holds exactly one idea that turns a slow answer into a fast one; the rest is bookkeeping.

24.1 Running Sum of an Array

The problem

Given an array, produce a second array where entry i is the sum of the first i + 1 entries. For `[1, 2, 3, 4]` the answer is `[1, 3, 6, 10]`.

Picture this

Keep a running total. Each day, add today's deposit to yesterday's total; never re-add the whole history.

Brute force

For each position i, loop from 0 to i and re-add. The total work is 1 + 2 + ... + n, roughly n² / 2: double the array, quadruple the work. It throws away everything already computed.

The better approach

Keep one variable holding the sum so far. Walk once, add the current element, record it. One addition per entry, previous work reused: a running accumulator.

The implementation

    import(lib) std::vec { Vec };
    import(lib) std::io::ios { println };

    Vec<i32> runningSum(const Vec<i32>* nums) {
        Vec<i32> out = Vec<i32>::withCap(nums->count());
        i32 sum = 0;
        for (usize i = 0; i < nums->count(); i++) {
            sum = sum + nums->at(i);
            out.push(sum);
        }
        return out;
    }

    void main() {
        Vec<i32> nums = Vec<i32>::new();
        nums.push(1); nums.push(2); nums.push(3); nums.push(4);
        Vec<i32> out = runningSum(&nums);
        for (i32 x : out) {
            println("{}", x);
        }
    }

`withCap` reserves exactly the room needed, so the vector never reallocates while filling. The loop reads `nums->count()` each pass, the checked way to walk a `Vec` by index (Chapter16). `sum` is a plain local, no allocation.

The cost

Time is linear: one pass, one addition per element. Space is linear because we return a new array of the same length; the accumulator itself is one integer.

Edge cases and a variation

An empty array produces an empty array. The first output entry always equals the first input entry, a good sanity check. Large sums can overflow `i32`; promote the accumulator to `i64` if needed. Variation: store running sums as a prefix-sum array, then any range sum `[lo, hi]` is `prefix[hi] - prefix[lo - 1]` in constant time. One preprocessing pass buys constant-time queries, a trick we reuse in Chapter26.

24.2 The Maximum and the Second Maximum

The problem

Find the largest and second-largest elements of an array. Return both.

Picture this

Keep the champion in mind. Whenever someone beats the champion, the old champion becomes second-best.

Brute force

Find the maximum in one pass, then the maximum of everything except it in a second. Still linear, but awkward when the maximum appears more than once, and it revisits data the first pass already understood.

The better approach

One pass, two variables: `best` and `second`. If a number beats `best`, the old `best` slides into `second`; otherwise, if it beats `second`, it becomes `second`.

The comparison must be strict. Second-largest must be strictly smaller than the largest, or you would report two copies of the same value.

The implementation

    import(lib) std::vec { Vec };
    import(lib) std::io::ios { println };

    struct TopTwo {
        i32 best;
        i32 second;
        bool hasSecond;
    }

    TopTwo topTwo(const Vec<i32>* nums) {
        i32 best = nums->at(0);
        i32 second = 0;
        bool hasSecond = false;
        for (usize i = 1; i < nums->count(); i++) {
            i32 x = nums->at(i);
            if (x > best) {
                second = best;
                best = x;
                hasSecond = true;
            } else if (x < best && (!hasSecond || x > second)) {
                second = x;
                hasSecond = true;
            }
        }
        return TopTwo { .best = best, .second = second, .hasSecond = hasSecond };
    }

`hasSecond` matters: if every element is equal, no second-largest exists, and the function must say so. An `Option<i32>` from Chapter15 is the more idiomatic answer; the flag keeps the struct self-contained here.

The cost

Time is linear: one pass, constant comparisons per element. Space is constant, two numbers and a flag regardless of size. The first problem here where memory beats "proportional to input," but not the last.

Edge cases and a variation

One element, or all-equal elements, has a largest and no second, which is why the strict comparison matters. An empty array is invalid input; guard at the top or document it. Variation: find the third-largest in the same pass, one more variable and branch. Generalizing to the k-th largest gets ugly fast; for large k use a heap, Chapter16's `PriorityQueue`.

24.3 Reverse an Integer (and the Palindrome Test)

The problem

Given a 32-bit signed integer, reverse its digits: `123` becomes `321`, `-123` becomes `-321`. If the reversal overflows, return `0`. Companion: decide whether a number reads the same forwards and backwards.

Picture this

Peel digits off the end and append each to a new number. `123`: peel 3, then 2 to make `32`, then 1 to make `321`.

Brute force

Convert to a string, reverse, convert back. Easy, but it allocates and drags the text layer into an arithmetic problem. A fine fallback, not the expected answer.

The better approach

Peel and append with integer arithmetic: the last digit is `n % 10`, append with `rev = rev * 10 + d`, chop with `n = n / 10`. Repeat until zero. Accumulate in a 64-bit integer and check against the 32-bit bounds before returning; overflowed `i32` arithmetic is a silent bug.

The implementation

    import(lib) std::io::ios { println };

    i32 reverse(i32 x) {
        i64 n = (i64)x;
        i64 rev = 0;
        while (n != 0) {
            i64 digit = n % 10;
            n = n / 10;
            rev = rev * 10 + digit;
        }
        if (rev > 2147483647 || rev < -2147483648) {
            return 0;
        }
        return (i32)rev;
    }

    bool isPalindromeNumber(i32 x) {
        if (x < 0) return false;
        if (x != 0 && x % 10 == 0) return false;
        i32 rev = 0;
        while (x > rev) {
            rev = rev * 10 + x % 10;
            x = x / 10;
        }
        return x == rev || x == rev / 10;
    }

The palindrome test reverses only the last half, stopping when the reversed half catches the front, avoiding overflow. For `1221`, peeling gives `rev = 12` and `x = 12`: equal, so it is a palindrome. For `12321`, the halves cross with the middle digit in `rev`, so we also accept `x == rev / 10`. Negative numbers are never palindromes, and neither is a positive number ending in zero (except zero), since its reverse would start with zero. Both are rejected up front.

The cost

Time is proportional to the number of digits, the base-ten logarithm; for a 32-bit int, at most ten iterations. Space is constant, a handful of integers. First appearance of logarithm-time, which returns in 23.8.

Edge cases and a variation

Watch `x = 0`, a palindrome whose reversal is `0`; the overflow guard; and negative values, where the sign must survive. Since `n % 10` is negative for negative `n`, digits accumulate with the correct sign. Variation: reverse the bits instead of the digits. Peel with `& 1`, append with `<< 1 | bit`; a number is a sequence of symbols in any base.

24.4 FizzBuzz

The problem

Print 1 to n, but multiples of three print "Fizz", multiples of five print "Buzz", and multiples of both print "FizzBuzz".

Picture this

The whole game is the overlap: fifteen is divisible by both and must print the combined word, not "Fizz" then "Buzz."

Brute force

A chain of `if`s checking 15 first, then 3, then 5. Works, but only if you remember the ordering: check 3 before 15 and fifteen prints "Fizz" and never reaches "FizzBuzz." The compiler does not check that rule.

The better approach

Two independent questions ("divisible by 3?", "divisible by 5?") give four combinations. Chapter13's switch over a tuple makes the compiler check all four, so the ordering trap cannot happen.

The implementation

    import(lib) std::io::ios { println };

    void fizzBuzz(i32 n) {
        for (i32 i = 1; i <= n; i++) {
            switch ((i % 3 == 0, i % 5 == 0)) {
                (true, true)   => println("FizzBuzz"),
                (true, false)  => println("Fizz"),
                (false, true)  => println("Buzz"),
                (false, false) => println("{}", i),
            }
        }
    }

No `else` arm is needed. The four arms are exhaustive, and the compiler knows it.

The cost

Time is linear in n: one iteration per number with two remainders and a dispatch. Space is constant. The point is the control flow: four ordered `if`s become a table the compiler verifies.

Edge cases and a variation

`n <= 0` prints nothing, which the loop already does. Variation: make the rules data, a list of `(divisor, word)` pairs configured at runtime. The tuple switch becomes a loop over the rules and the exhaustive checking is gone, the same trade Chapter13 draws between variants and raw integers.

24.5 Greatest Common Divisor and Least Common Multiple

The problem

Given two integers, find their greatest common divisor, the largest integer dividing both evenly. Companion: their least common multiple.

Picture this

Euclid's insight, twenty-three centuries old: the shared factors of `a` and `b` are exactly the shared factors of `b` and `a mod b`. Shrink the pair without losing the answer.

Brute force

Walk every integer up to the smaller number, remembering the last that divides both. Linear in the smaller value, hopeless for many digits.

The better approach

Euclid's algorithm: replace `(a, b)` with `(b, a mod b)` until the remainder is zero; the other number is the answer. The pair halves in the worst case, so the steps are logarithmic.

The implementation

    import(lib) std::io::ios { println };

    i64 gcd(i64 a, i64 b) {
        if (a < 0) a = -a;
        if (b < 0) b = -b;
        while (b != 0) {
            i64 r = a % b;
            a = b;
            b = r;
        }
        return a;
    }

    i64 lcm(i64 a, i64 b) {
        i64 g = gcd(a, b);
        if (g == 0) return 0;
        i64 left = a / g;
        return left * b;
    }

In `lcm`, `(a * b) / g` overflows at scale. Divide first, `(a / g) * b`, keeping the intermediate small because `g` divides `a` exactly.

The cost

Time is logarithmic: each step replaces the larger number with a remainder smaller than the other, shrinking the pair geometrically in the worst case. Space is constant, three reused integers. `lcm` adds a fixed number of operations, so the same complexity.

Edge cases and a variation

`gcd(a, 0)` is `a`, and `gcd(0, 0)` is zero; decide what the all-zero case should do. Negative inputs use absolute values, since a divisor's sign is irrelevant. Variation: fold the two-argument version across an array, `gcd(a, b, c) = gcd(gcd(a, b), c)`, via Chapter16's `reduce`.

24.6 Fibonacci and the Cost of Naive Recursion

The problem

Compute the n-th Fibonacci number: `fib(0) = 0`, `fib(1) = 1`, and each later value is the sum of the two before it.

Picture this

This is the clearest place to watch a program run catastrophically slow for a reason invisible in the code: two lines of arithmetic become a tree of redundant work.

Brute force

The literal definition, written literally:

    i64 fibNaive(i64 n) {
        if (n < 2) return n;
        return fibNaive(n - 1) + fibNaive(n - 2);
    }

Correct and unusable. `fib(n-1)` recomputes `fib(n-2)` all over again, so subproblems are recomputed an exponential number of times; calls roughly double per increment of n. `fib(50)` takes on the order of a billion operations, and `fib(100)` would outlast a human lifetime.

The better approach

Two fixes. Memoize: store each computed value in an array and check it before recursing, so each is computed once. Simpler here: the dependence reaches back only one or two, so keep a running pair and walk forward from the bottom.

The implementation

    import(lib) std::vec { Vec };
    import(lib) std::io::ios { println };

    i64 fib(i64 n) {
        if (n < 2) return n;
        i64 prev = 0;
        i64 cur = 1;
        for (i64 i = 2; i <= n; i++) {
            i64 next = prev + cur;
            prev = cur;
            cur = next;
        }
        return cur;
    }

    i64 fibMemo(i64 n, Vec<i64>* memo) {
        if (n < 2) return n;
        if (memo->at((usize)n) >= 0) return memo->at((usize)n);
        i64 value = fibMemo(n - 1, memo) + fibMemo(n - 2, memo);
        memo->set((usize)n, value);
        return value;
    }

`fibMemo` uses `-1` for "not computed yet," safe because Fibonacci numbers are never negative. This is the sentinel-versus-`Option` trade from Chapter15: compact and provably safe here, while `Option<i64>` is more general at the cost of a tag byte per slot.

The cost

The naive recursion is exponential, roughly the golden ratio to the n, because each subproblem expands into its whole subtree. Its space is only linear (recursion depth), so it fails on time, not memory. The iterative version is linear time and constant space, keeping only the last two. Memoization is also linear time but linear space, since it keeps every value. The iterative one wins here; memoization generalizes when dependencies are not the last two.

Edge cases and a variation

Reject or define negative `n`. Values overflow `i64` around `fib(93)`, so large n needs big integers or modular arithmetic. Variation: compute only `fib(n) mod m`; take a remainder each step and the iterative version never overflows.

24.7 Count Primes (the Sieve of Eratosthenes)

The problem

Given n, count the primes strictly less than n.

Picture this

Cross out numbers on a long list: from 2, cross out every second number (4, 6, 8...); from 3, every third (6, 9, 12...); then 5, then 7. What survives is exactly the primes. You eliminate composites wholesale instead of testing each number.

Brute force

For each number, trial-divide by every integer up to its square root. Roughly n to the power three-halves overall, slow for n in the millions.

The better approach

The sieve lets each prime cross out its multiples instead of testing each number. For each prime p, mark `p*p, p*p + p, ...` composite. Starting at `p*p` skips multiples already crossed out by smaller primes. Total work is n log log n, nearly linear in practice.

The implementation

    import(lib) std::vec { Vec };
    import(lib) std::io::ios { println };

    i32 countPrimes(i32 n) {
        if (n < 2) return 0;
        Vec<bool> composite = Vec<bool>::new();
        for (i32 i = 0; i < n; i++) composite.push(false);

        i32 count = 0;
        for (i32 p = 2; (i64)p * (i64)p < (i64)n; p++) {
            if (!composite.at((usize)p)) {
                for (i64 m = (i64)p * (i64)p; m < (i64)n; m += (i64)p) {
                    composite.set((usize)m, true);
                }
            }
        }
        for (i32 i = 2; i < n; i++) {
            if (!composite.at((usize)i)) count++;
        }
        return count;
    }

The casts to `i64` in the loop bounds matter: `p * p` can overflow a 32-bit multiply and make the loop condition silently wrong. Whenever you multiply two possibly large values, check that the product fits the type.

The cost

Time is n log log n, nearly linear: each composite is crossed out once per distinct prime factor, which averages very small. Space is linear, one byte per number. If memory is tight, Chapter16's `Bitset` stores one bit per number, sixty-four times smaller, at slightly less direct indexing.

Edge cases and a variation

`n < 2` returns zero before touching the array; 2 is handled naturally. Variation: push each uncrossed number into a `Vec<i32>` to return the primes themselves. A second: the linear-time sieve, marking each composite once by its smallest prime factor, more code but a better base for factorization problems.

24.8 Fast Exponentiation

The problem

Compute `base` to the power `exp` for a non-negative integer exponent, without `exp` multiplications when `exp` is large.

Picture this

2 to the 10th is (2 to the 5th) squared, and so on down: repeated squaring reaches the answer in about four multiplications. Squaring turns the exponent's binary digits into a recipe.

Brute force

Multiply `base` into an accumulator `exp` times: exactly `exp` multiplications, and `exp` can be a billion.

The better approach

Binary exponentiation: read the exponent's bits from least to most significant. A set bit multiplies the result by the current power; each step squares that power. Steps equal the bits in `exp`, about thirty instead of a billion for a near-billion exponent.

The implementation

    import(lib) std::io::ios { println };

    i64 power(i64 base, u32 exp) {
        i64 result = 1;
        i64 factor = base;
        u32 e = exp;
        while (e > 0) {
            if ((e & 1u) != 0u) {
                result = result * factor;
            }
            factor = factor * factor;
            e = e >> 1u;
        }
        return result;
    }

The three lines inside the loop are the whole algorithm: if the low bit is set, take the factor into the result; square the factor; shift the exponent right. For `base = 3`, `exp = 5` (binary 101): bit set gives `result = 3`, `factor = 9`; bit clear gives `factor = 81`; bit set gives `result = 243`.

The cost

Time is proportional to the exponent's bits, its base-two logarithm; at most thirty-two iterations for a 32-bit exponent. Space is constant, three integers, no matter the exponent. The sharpest example here of a huge gain from a small change in perspective.

Edge cases and a variation

Exponent zero returns one, including for `base = 0` by convention. Negative exponents are excluded by the `u32` type, visible in the signature. Overflow is the real risk, since intermediate squares grow quickly. For modular exponentiation, take a remainder after every multiply; the algorithm is unchanged. That is the version inside every RSA implementation.

24.9 Armstrong (Narcissistic) Numbers

The problem

A number is *Armstrong* (narcissistic) when it equals the sum of its digits, each raised to the power of the digit count. `153` has three digits and `1³ + 5³ + 3³ = 153`. Given a bound `n`, list every Armstrong number up to and including `n`. Companion: test a single number.

Picture this

Each digit is weighted by itself raised to the digit count. Peel the digits, weigh each, and add. The exponent depends on the number being tested, so count the digits first.

Brute force

For each candidate, peel each digit and raise it by multiplying `d` times. That is about `d²` work per number, and it recomputes the same tiny powers over and over.

The better approach

Count the digits once, then reuse 23.8's squaring `power` helper so each `digit^d` costs a handful of multiplications. The digit loop is unchanged.

The implementation

    import(lib) std::vec { Vec };
    import(lib) std::io::ios { println };

    i64 ipow(i64 base, i64 exp) {
        i64 result = 1;
        i64 factor = base;
        i64 e = exp;
        while (e > 0) {
            if ((e & 1) != 0) {
                result = result * factor;
            }
            factor = factor * factor;
            e = e >> 1;
        }
        return result;
    }

    i32 digitCount(i32 n) {
        if (n == 0) return 1;
        i32 d = 0;
        while (n > 0) {
            d++;
            n = n / 10;
        }
        return d;
    }

    bool isArmstrong(i32 n) {
        if (n < 0) return false;
        i32 digits = digitCount(n);
        i32 m = n;
        i64 sum = 0;
        while (m > 0) {
            i64 d = m % 10;
            sum = sum + ipow(d, (i64)digits);
            m = m / 10;
        }
        return (i64)n == sum;
    }

    Vec<i32> armstrongUpTo(i32 n) {
        Vec<i32> out = Vec<i32>::new();
        for (i32 x = 1; x <= n; x++) {
            if (isArmstrong(x)) out.push(x);
        }
        return out;
    }

`ipow` is the 23.8 loop with the exponent widened to `i64`. `sum` is `i64` because the running total may not fit 32 bits even when the final answer would.

The cost

Testing one number costs `O(d log d)`, effectively constant for a 32-bit value; listing up to `n` costs `O(n log n)`. Space is constant apart from the output, which stays tiny because the numbers are rare.

Edge cases and a variation

Zero is Armstrong by convention (`0¹ = 0`); the listing starts at one to keep "positive" honest. Single digits 1 through 9 are trivially Armstrong. Negative numbers are rejected, since the minus sign is not a digit. Variation: precompute `power[d][digit]` for `d` up to ten, then each test is a table lookup, the computing-versus-caching trade of Chapter16.

24.10 The Collatz Sequence

The problem

Start with a positive integer `n`: halve it if even, replace it with `3n + 1` if odd. Repeat until 1 and return the step count. Companion: among starts up to a limit, find the longest chain.

Picture this

The hailstone sequence rises and falls unpredictably before settling at 1. Nobody has proved every chain reaches 1. The useful part: different starts share tails, so once two chains meet the rest is identical.

Brute force

Simulate each start independently. Fast per number, but across a range it recomputes shared tails again and again.

The better approach

Memoize each value's chain length in a table indexed by value; before stepping, check the table and add the known length. This is 23.6's memoization, with a shared tail instead of a shared head. Values above the limit are computed but not stored.

The implementation

    import(lib) std::vec { Vec };
    import(lib) std::io::ios { println };

    i64 collatzSteps(i64 n, Vec<i32>* memo) {
        if (n == 1) return 0;
        if (n > 0 && n < (i64)memo->count()) {
            i32 cached = memo->at((usize)n);
            if (cached >= 0) return (i64)cached;
        }
        i64 next = 0;
        if (n % 2 == 0) {
            next = n / 2;
        } else {
            next = 3 * n + 1;
        }
        i64 steps = 1 + collatzSteps(next, memo);
        if (n > 0 && n < (i64)memo->count()) {
            memo->set((usize)n, (i32)steps);
        }
        return steps;
    }

    i32 longestCollatz(i32 limit) {
        if (limit < 1) return 0;
        Vec<i32> memo = Vec<i32>::withCap((usize)limit + 1);
        for (i32 i = 0; i <= limit; i++) memo.push(-1);
        memo.set(1, 0);

        i32 bestStart = 1;
        i64 bestLen = 0;
        for (i32 i = 1; i <= limit; i++) {
            i64 len = collatzSteps((i64)i, &memo);
            if (len > bestLen) {
                bestLen = len;
                bestStart = i;
            }
        }
        return bestStart;
    }

The sentinel `-1` means "not computed yet," safe because a chain length is never negative. Arithmetic runs in `i64`: the odd step triples a value that has already grown, so `3n + 1` can exceed 32 bits even when the start fits.

The cost

With memoization the work is nearly linear in the limit: each table value is computed once, and above-limit values appear only as transient links. Without it, the cost is the sum of all chain lengths. Space is linear in the limit, one integer per start; recursion depth stays in the hundreds for millions.

Edge cases and a variation

`n = 0` is not legal; `limit < 1` returns zero. `n = 1` takes no steps. The numerical trap is overflow on the odd branch, which is why everything is `i64`; a 32-bit `3n + 1` wraps and can bounce forever. Variation: record each chain's peak value and find the highest climb, one more running maximum.

24.11 Perfect Numbers and Amicable Pairs

The problem

A *perfect* number equals the sum of its proper divisors (strictly smaller): `28 = 1 + 2 + 4 + 7 + 14`. An *amicable pair* has each number equal to the sum of the other's proper divisors: `220` and `284`. Given `n`, list perfect numbers up to `n` and amicable pairs below it.

Picture this

The work is computing a divisor sum. Divisors come in pairs: if `d` divides `n`, so does `n / d`. Search only to the square root, adding both members of each pair, and avoid double-counting the square root when `n` is a perfect square.

Brute force

Test every integer from 1 to `n - 1` and add the divisors. Linear per number, so listing up to `n` costs about `n²`, and the amicable scan does that twice per candidate. It stalls in the tens of thousands.

The better approach

Compute the divisor sum in `O(sqrt n)`: walk `d` from 2 while `d * d <= n`, add both `d` and `n / d`, skipping the second when equal, and seed the sum at 1. A perfect test is then one comparison; an amicable test, two divisor sums.

The implementation

    import(lib) std::vec { Vec };
    import(lib) std::io::ios { println };

    i64 divisorSum(i64 n) {
        if (n < 2) return 0;
        i64 sum = 1;
        for (i64 d = 2; d * d <= n; d++) {
            if (n % d == 0) {
                sum = sum + d;
                i64 other = n / d;
                if (other != d) sum = sum + other;
            }
        }
        return sum;
    }

    bool isPerfect(i64 n) {
        return n > 1 && divisorSum(n) == n;
    }

    Vec<i64> perfectUpTo(i64 n) {
        Vec<i64> out = Vec<i64>::new();
        for (i64 x = 2; x <= n; x++) {
            if (isPerfect(x)) out.push(x);
        }
        return out;
    }

    Vec<i64> amicableFlat(i64 n) {
        Vec<i64> out = Vec<i64>::new();
        for (i64 a = 2; a <= n; a++) {
            i64 b = divisorSum(a);
            if (b > a && b <= n && divisorSum(b) == a) {
                out.push(a);
                out.push(b);
            }
        }
        return out;
    }

The `other != d` guard catches the square-root case: for `n = 16`, `d = 4` and `16 / 4` are the same, so adding twice would overcount. The `b > a` test emits each amicable pair once, never as `(284, 220)`.

The cost

One divisor sum is `O(sqrt n)`; listing perfect numbers up to `n` and the amicable scan are both `O(n sqrt n)`. Space is constant beyond the output. For millions, build a divisor-sum sieve filling every value in `O(n log n)`, the inversion 23.7 uses.

Edge cases and a variation

One is not perfect: its only proper divisor sum is zero, and `n < 2` returns zero. Primes have divisor sum one, so they never satisfy `isPerfect` and never pair except with one, which `b > a` filters. Variation: sieve the divisor sums for the whole range, adding `d` to every multiple of `d` in `O(n log n)`, turning the amicable scan from `O(n sqrt n)` into `O(n)`.

3. Implementation. Write `bool isArmstrong(i32 n)` returning whether n equals the sum of its digits each raised to the digit count (153 = 1³ + 5³ + 3³). Which helper do you reuse?

4. Implementation. Write `i32 singleNumber(const Vec<i32>*)` where every element appears twice except one; return it. (Hint: `x ^ x == 0` and `x ^ 0 == x`; fold the array.) Then write the `Set` version and compare space cost.

5. Implementation. Write `i32 missingNumber(const Vec<i32>*)` for 0 through n with one missing. Solve with the arithmetic sum and with XOR. Which is safer against overflow, and why?

6. Analysis. In 23.6, `memo->at(n) >= 0` means "already computed." Why is this sentinel safe for Fibonacci but unsafe in general? Rewrite it with `Option<i64>` from Chapter15.

7. Analysis. In 23.7, why does the sieve's inner loop start at `p * p`, and why does that skip no composite? Then start at `2 * p` and say what becomes redundant.

8. Implementation. Write `u64 powerMod(u64 base, u64 exp, u64 mod)` using the squaring loop of 23.8, taking a remainder after every multiply. Test against the naive method and explain why it never overflows for 64-bit inputs.

9. Math. Write `bool isPerfectSquare(i32 n)` without a square-root function, using the squares as partial sums 1, 1+3, 1+3+5, and so on. What is the complexity versus binary search for the root?

10. Meta. Name the one idea in each of 23.1, 23.5, 23.6, 23.7, and 23.8 that turned a slow solution fast, and say what they share. Naming the load-bearing idea is the habit that transfers.
