Chapter12

Tuples and Destructuring

Two Answers for the Price of One Call

Functions often need to return more than one thing: a quotient and remainder, a value and its status, a hit flag and a position. Every language answers this differently.

C uses out-parameters: the answer lives in arguments you had to declare first, and the call site does not distinguish inputs from outputs. C++ and Java invent a named class. Python and Rust use the tuple, and so does Coral.

A tuple is several values travelling together as one value, identified by position and nothing else.

This chapter covers what a tuple is, how to make and take one apart, and when a struct is better. Map lookups, iterator adaptors, and later examples rely on it.

12.1 What a Tuple Actually Is

A tuple is the smallest aggregate: a value made of several values, with no field names, no methods, and no identity beyond its shape. A pair is two values; a triple is three.

The trouble with a struct for every pair is naming, not typing. Every throwaway struct needs a name, a file, an import, and a spot in the public API, and once named, readers assume it is part of the domain model. A tuple refuses that: these values travel together briefly and stop being a thing.

Tuples are for ephemeral, positional, local structure. In a struct, order does not matter because fields are reached by name. In a tuple, position is the only identifier, and that is what `.0` means.

A `Receipt` struct for two numbers on their way to a printer claims a concept exists. If you meant only "two numbers, right now," a tuple is honest and the struct is a small lie.

The one-line version:

    var point = (3.0, 4.0);      // a pair: two values in one

That is a tuple. `.0` is `3.0`, `.1` is `4.0`. It has no name, was not declared, and will not survive past the function that made it unless handed on.

A two-element tuple is a pair; three is a triple. The general term is "n-tuple," and nobody says it aloud.

12.2 Writing a Tuple Type

A tuple type is the `struct` keyword followed by a comma-separated list of element types in parentheses:

    struct(i32, f64)                 // a pair: an integer and a float
    struct(u8, u8, u8)               // three bytes, perhaps a colour
    struct(String, usize)            // an owned string and a length
    struct(i32, struct(i32, i32))    // a pair whose second element is itself a pair
    struct(f64, f64, f64, f64)       // four floats

This is the only spelling. A bare parenthesised type means grouping, and a statement beginning with `(` is read as a cast, so `struct` makes a tuple type unmistakable in every position. Whenever you see `struct(`, it is a tuple.

The keyword is a signpost: these parentheses bundle types rather than group one or start a cast.

Each is a distinct type. `struct(i32, f64)` is not `struct(f64, i32)`: order is part of the identity because position is the only name an element has. Tuples match only when the element count and each position's type match, turning a swapped-argument mistake into a compile error.

A common mistake is building in the wrong order: `struct(f64, i32) swapped = (1, 2.5);` fails.

A single-element tuple uses the same syntax:

    struct(i32)                // a one-element tuple containing an i32

There is no trailing-comma rule and no ambiguity: `struct` already says "aggregate." One-element tuples are rare, useful when a generic must return "a T, wrapped as a tuple" or when a type must be structurally distinct. Mostly you will read them, not write them.

The empty tuple has a value and a type, spelled the same way:

    struct()                   // the unit type

A `struct()` has exactly one value, `()`, meaning "no information." A function returning nothing returns unit under the hood; write `void` when it reads better. But `struct()` is a real usable type when a generic construct needs "a type whose values carry no data": `Map<str, struct()>` is a set of strings, a channel of `struct()` is a signal. Unit is not nothing; its only value takes zero bytes.

Underneath, a tuple is a struct whose fields are numbered. `struct(i32, f64)` has a field `0` of type `i32` and a field `1` of type `f64`. That is why access is `.0` and `.1`: field accesses with numbers for names. Layout is a struct's: declaration order with natural alignment, no header, no heap. A tuple is a struct that forgot to name its fields.

A tuple and a struct have the same bytes; only the field names differ. That is why a tuple costs nothing extra and `t.0` feels like `p.x`: the same field access with a number for a name.

12.3 Writing a Tuple Value

A tuple literal is a comma-separated list of values in parentheses. Its type is inferred element by element:

    var pair = (1, 2.5);              // inferred struct(i32, f64)
    var rgb = (255u8, 128u8, 0u8);    // struct(u8, u8, u8)
    var origin = (0.0, 0.0);          // struct(f64, f64)
    var nested = (1, (2, 3));         // struct(i32, struct(i32, i32))
    var swapped = (origin.1, origin.0);  // struct(f64, f64)

The compiler sees `1` as `i32` and `2.5` as `f64`, so `pair` is `struct(i32, f64)`. There is no promotion from `1` to `1.0`; each element keeps its own type.

Two tuple literals with the same shape but different element types do not unify:

    var a = (1, 2);        // struct(i32, i32)
    var b = (1, 2.0);      // struct(i32, f64), not the same type as a

You cannot assign `b` to `a`'s type or put them in one vector: `Vec<struct(i32, i32)>` and `Vec<struct(i32, f64)>` differ as much as `i32` and `f64`. That is what you want, since a function taking integer pairs should not accept an (integer, float) pair. Writing `2` for `2.0` becomes a compile error, not a silent truncation.

To be explicit, put the tuple type in front, as with any local:

    struct(i32, f64) reading = (70, 0.55);
    struct(str, i32) entry = ("ada", 1815);

The unit literal is `()`:

    var nothing = ();      // the one value of the unit type

Tuples are values: they live on the stack, are copied on assignment subject to the usual move rules, and are passed by value. There is no implicit boxing or heap allocation unless the tuple owns heap data. A `struct(i32, i32)` is eight bytes; a `struct(f64, f64, f64)` is twenty-four. Nothing is hidden.

That is why tuples suit hot paths: no constructor, no reference counting, no object header. A `struct(i32, i32)` and two `i32` locals occupy the same memory and cost the same instructions.

12.4 Getting the Pieces Out by Position

Tuples are indexed by position with a dot and a decimal integer:

    var t = (10, 20, 30);
    var first  = t.0;      // 10
    var second = t.1;      // 20
    var third  = t.2;      // 30

Two things distinguish this from array indexing. The index is part of the syntax, not an expression: `t.0` is valid, `t.i` is not. And the index is fixed at compile time, so the compiler knows every element's exact type. If `t` is `struct(i32, f64, bool)`, then `t.0` is `i32`, `t.1` is `f64`, and `t.2` is `bool`, with no runtime lookup or bounds check. An array has one element type and a runtime index.

    var pair = (1, 2.5);
    var first  = pair.0;     // an i32
    var second = pair.1;     // an f64

Each read knows its type before the program runs, which is why a tuple can hold values of different types where an array cannot.

A literal index lets the compiler turn each access into a fixed offset: `t.0` means "the first field," not "look up field zero." A runtime index would force a type table and a runtime check, and every access would return "one of these, we are not sure which." Because the index is a constant, tuples mix types freely and every access is a plain typed field read.

You can assign a whole tuple to a mutable variable and reassign it:

    var p = (1, 2);
    p = (5, 6);            // p is now (5, 6); the types still match

A tuple is replaced wholesale, not edited piece by piece. `p.0 = 5` is legal because `.0` is a field of a mutable local, but changing one piece usually means you wanted a struct with named mutable fields, or a fresh tuple. When you find yourself nudging `.1`, ask whether the value has quietly become a concept.

12.5 Taking a Tuple Apart

Reading `t.0`, `t.1`, `t.2` is the only way to pull one piece out at a time, and it suits one or two pieces. Can you bind all pieces in one line, as Rust and Python do with `let (x, y) = pair;`?

No. There is no multi-name binding declaration: `var (x, y) = pair;` is invalid, and a parenthesised pattern cannot go where a variable name goes. A statement beginning with `(` is a cast, and `(a, b)` in expression position is a tuple literal, so parentheses cannot also mean binding. A tuple is taken apart one piece at a time, or all at once by a pattern in a `switch`.

The everyday recipe is positional access:

    var pair = divide(17, 5);      // pair : struct(i32, i32)
    var quotient = pair.0;
    var remainder = pair.1;

For one piece this is the clearest form. There is also no underscore discard: `_` is not a wildcard, so Rust's `let (keep, _) = pair;` has no translation. Read `.0` directly:

    var pair = (10, 20);
    var keep = pair.0;        // just read the first element

Coming from Rust or Python, this can feel backwards. Think of `.0` and `.1` as labels on the bucket's compartments: reach into the one you want; there is no shorthand naming every compartment. When you want *all* the pieces, use a `switch` pattern.

Patterns live where values are matched, not declared. A tuple pattern asks "does this value have this shape, and if so, name the pieces."

12.6 Patterns: Matching Tuples in a switch

A `switch` tries its arms in order and runs the first matching pattern. A tuple pattern uses parentheses and commas like a tuple literal, and each position holds a sub-pattern or a fresh name to bind:

    switch (divide(10, 0)) {
        (value, true)  => println("ok: {}", value),
        (value, false) => println("division failed"),
    }

Each arm matches position by position and binds the pieces it names. Because `bool` has exactly two values and both arms are present, the switch is exhaustive and the compiler confirms it. If `divide` later reports an error string, the type changes and the compiler walks you through every switch, the benefit Chapter13 describes at length.

For `divide(10, 0)` returning `(0, false)`, the first arm `(value, true)` fails because the second component is `false`. The second arm matches, binds `value` to `0`, and runs its body. First match wins.

Patterns nest, because the type nests:

    switch (bounds(values)) {
        (lo, hi, 0) => println("no data"),
        (lo, hi, n) => println("{} readings span {}", n, lo, hi),
    }

The first arm matches only when the count is zero, binding both zeroes into `lo` and `hi`, which you ignore by not using them. The second names all three. With no wildcard, ignore a piece by naming it and not using it, or pin it with a literal. Coral's patterns are about shape and value, not discarding.

`else` is the catch-all when you do not want to enumerate:

    switch (signOf(x), signOf(y)) {
        (1, 1)   => println("both positive"),
        (0, 0)   => println("both zero"),
        else     => println("something else"),
    }

The idiom: `(signOf(x), signOf(y))` is built at the switch and immediately taken apart, never stored. When a decision depends on several small closed facts, package them into a tuple and match, and the compiler checks completeness. Chapter13 builds on this.

One subtlety: a binding pattern copies or moves the value into the new name by the usual ownership rules. Matching `struct(String, usize)` moves the `String` out, leaving the original partially moved and unusable as a whole. A pattern that binds a piece takes it unless the piece is trivially copyable like a number.

12.7 Returning Several Values

This is the best reason tuples exist. A function returns one value; a tuple lets it be several. A division reports its quotient and whether it succeeded:

    struct(i32, bool) divide(i32 a, i32 b)
    {
        if (b == 0) return (0, false);
        return (a / b, true);
    }

Call it, then read the pieces by position or match them:

    struct(i32, bool) r = divide(10, 3);
    if (r.1) {
        println("quotient is {}", r.0);
    }

Compare C's `i32 divide(i32 a, i32 b, bool* ok)`: the caller declares a `bool`, passes its address, and remembers which argument is the output. The tuple keeps the answer in one place and reads left to right.

The pattern scales to `struct(String, usize)` for an owned buffer and length, `struct(i32, i32, i32)` for a colour, `struct(T, T)` for a swap, or `struct(bool, T)` for a found flag and value. A swap:

    struct(i32, i32) swap(i32 a, i32 b)
    {
        return (b, a);
    }

    var pair = swap(x, y);
    x = pair.0;
    y = pair.1;

A lookup that also reports the found index:

    struct(usize, bool) indexOf(const i32[] data, i32 needle)
    {
        for (usize i = 0; i < data.count(); i++) {
            if (data[i] == needle) return (i, true);
        }
        return (0, false);
    }

A caller who found what they wanted reads both pieces:

    var hit = indexOf(readings, 99);
    if (hit.1) {
        println("found 99 at position {}", hit.0);
    }

A caller who only cares whether it was found reads just the flag:

    var found = indexOf(readings, 99).1;    // read just the flag

One warning. `(0, false)` is a sentinel: a real index of `0` that means nothing, paired with a flag saying "ignore it." A caller who forgets the flag silently searches at position zero. That is the weakness of encoding failure as a tuple: the caller can ignore the failure path. Express "an index, or nothing" as `Option<usize>`, and "a value, or a reason it failed" as `Result<T, E>`, both in Chapter15. A tuple is right when every piece is always meaningful; when one piece is conditional, a variant says so in the type.

12.8 Tuples in Generics and Containers

A tuple is a type like any other, so it can be an element type, map value, generic argument, or generic return type. This is where tuples earn their keep in the standard library:

    Vec<struct(str, i32)> scores = Vec<struct(str, i32)>::new();
    scores.push(("ada", 92));
    scores.push(("grace", 97));

    for (var entry : scores) {
        println("{} scored {}", entry.0, entry.1);
    }

A `struct(str, i32)` is a good key-value pair. When the concept does not need a name, a tuple is honest about being two things together. If the pair later deserves a name, promote it to a struct; the change is local to the definition, construction site, and field accesses.

Tuple-shaped returns are common in generic algorithms. A split returns `struct(Vec<T>, Vec<T>)` rather than mutating out-parameters. A single-pass min and max returns `struct(T, T)`. A partition returns `struct(Vec<T>, Vec<T>)`. In each case the tuple is the natural "two answers" shape:

    var split = splitAt(values, pivot);
    var before = split.0;
    var after  = split.1;

Tuples nest and compose: a map whose values are tuples, or a tuple of vectors such as `struct(Vec<i32>, Vec<str>)`. A `Map<str, struct(f64, f64)>` might map a city to latitude and longitude; a `Map<str, struct(u32, u32)>` might map a word to wins and losses. The tuple does a lightweight struct's job without the name.

You cannot give a tuple methods: no `extend` block for `struct(i32, i32)`, no trait implementation for a bare tuple. A tuple's only behaviour is its layout. That boundary is Section12.9.

A tuple is data and nothing more. When you want it to print, compare, or clean up after itself, it has grown beyond a tuple and wants to be a struct.

Because tuples are plain data, they are the cheapest way to return several answers and the easiest to use in a hot loop. A `struct(str, i32)` inside a `Vec` costs exactly what a two-field struct costs: no methods, no vtable, no hidden allocation. That same lightness prevents adding behaviour later, so choose tuples when the data is just passing through.

12.9 Tuple or Struct?

The two look similar and serve the same job at different scales. A decision you can apply without agonising:

Reach for a tuple when all of these hold:

    - there are two or three elements,
    - the order is obvious at the call site from context,
    - the tuple does not travel far from where it is created,
    - and you would not want a type name for it in the API documentation.

Reach for a struct when any of these hold:

    - there are more than three or four elements,
    - callers would need to remember which position means what,
    - the value crosses a module boundary or appears in a public signature,
    - the fields have different lifetimes or ownership rules,
    - or you want to add methods, drop semantics, or trait implementations.

The decisive difference: you cannot add a method to a tuple. No `extend` block for `struct(i32, i32)`, no trait implementation for a bare tuple. A tuple's only behaviour is its layout. When a value needs a `drop`, a `toStr`, a comparison, or a `clone`, it needs a struct or a `distinct` type.

Wrong way: a tuple that has quietly become a concept, with comments standing in for field names.

    // a "user" is (id, name, email, active), good luck remembering which is which
    struct(i64, str, str, bool) user = (1, "ada", "ada@example.com", true);
    if (user.3) { ... }        // what is .3 again?

Right way: a struct, because the value has a name and a meaning.

    struct User {
        i64  id;
        str  name;
        str  email;
        bool active;
    }

    User user = User { .id = 1, .name = "ada", .email = "ada@example.com", .active = true };
    if (user.active) { ... }   // unambiguous, and it survives a reorder of the fields

The tuple is not wrong because it is short; it is wrong because the value has a name in your head, and the language should have it too. A tuple that has grown a concept is a struct not yet written down.

A five-second test: read the construction site aloud. If it sounds like a sentence about your problem, "a user is an id, a name, an email, and whether they are active," the names belong in the code and a struct is right. If it sounds like plumbing, "give me this number and this flag so the next function can look," a tuple is right.

12.10 distinct: The Named Tuple

A middle ground matters because tuple-shaped quantities are where confusion bites. Two `f64` measurements, a distance in meters and one in feet, are interchangeable, and one day someone adds meters to feet and gets a plausible, wrong number.

    f64 meters = 100.0;
    f64 feet = meters;         // compiles; wrong, but nothing stops it

A `distinct` type gives the tuple's data layout a real name and type identity, so the two cannot be mixed:

    pub distinct Meters = f64;
    pub distinct Feet   = f64;
    pub distinct Point  = struct(f64, f64);

    Meters distance = (Meters) 100.0;
    Feet wrong = (Feet) distance;      // error: distinct types do not convert

`(Meters) 100.0` is a cast: `100.0` is an `f64`, deliberately treated as `Meters`. Coral has no `as`; a cast puts the target type in parentheses before the value. A `distinct` type is a new nominal type whose representation is the underlying type. It has the tuple's bytes and the struct's identity, so use it when the compiler must stop you mixing two same-shaped things, not a struct wrapper you unwrap at every use.

The conversion that makes the types useful:

    Meters toMeters(Feet f) {
        return (Meters) (f.0 * 0.3048);
    }

Yes, `f.0`. When a `distinct` type's representation is a tuple, the value has positional access because underneath it is still a tuple. `pub distinct Point = struct(f64, f64);` gives `p.0` and `p.1` while refusing to let a `Point` stand where an unrelated `struct(f64, f64)` is expected. You get positional convenience and nominal safety. For a scalar representation there is nothing to index; cast to the underlying type when you need the bytes, a visible reminder that a unit conversion may be happening.

Think of `distinct` as a sticky note on a type. Underneath, `Meters` is an eight-byte `f64`, but the compiler reads the note and refuses arithmetic between values whose notes differ, and refuses to hand a `Meters` to code asking for `f64` without a cast.

`distinct` says two things that look alike are not the same. Dollars and euros, meters and feet, a user id and an order id: same number underneath, dangerous to mix. You keep the cheap layout and gain a real name's safety at no runtime cost.

12.11 A Worked Example: Bounds and Statistics

A small realistic problem shows the pieces fitting together. Read sensor samples, a slice of `i32`, and want the smallest, largest, and count in one pass. That is one function producing three answers:

    struct(i32, i32, usize) bounds(const i32[] data)
    {
        if (data.count() == 0) return (0, 0, 0);
        i32 lo = data[0];
        i32 hi = data[0];
        for (var v : data) {
            if (v < lo) lo = v;
            if (v > hi) hi = v;
        }
        return (lo, hi, data.count());
    }

The empty case returns `(0, 0, 0)`, a sentinel the caller must interpret. Later chapters fix this: `Result` or `Option` would say "no data" honestly instead of pretending the bounds are zero.

Callers get all three numbers with no out-parameters and no pre-declared storage:

    struct(i32, i32, usize) b = bounds(values);
    println("{} readings, range {}..{}", b.2, b.0, b.1);

A caller who only cares about the range reads the two positions it wants:

    struct(i32, i32, usize) b = bounds(values);
    println("range {}..{}", b.0, b.1);

A caller who wants to branch on emptiness matches the tuple directly:

    switch (bounds(values)) {
        (lo, hi, 0) => println("no data"),
        (lo, hi, n) => println("{} readings span {}", n, lo, hi),
    }

A second function turns the bounds into a report string, showing the tuple flow through a pipeline:

    str describe(const i32[] data)
    {
        var b = bounds(data);
        if (b.2 == 0) return "no readings";
        return "min " + toStr(b.0) + ", max " + toStr(b.1) + ", n " + toStr(b.2);
    }

`describe` reads by position because it reuses all three pieces across two branches; reading `b.0` three times is clearer than three bindings. The judgement call made concrete.

A third function splits the samples at a threshold, returning two vectors:

    struct(Vec<i32>, Vec<i32>) partition(const i32[] data, i32 threshold)
    {
        Vec<i32> low  = Vec<i32>::new();
        Vec<i32> high = Vec<i32>::new();
        for (var v : data) {
            if (v < threshold) low.push(v);
            else               high.push(v);
        }
        return (low, high);
    }

The call site reads like a sentence:

    var split = partition(samples, 50);
    println("{} below the threshold, {} above", split.0.count(), split.1.count());

Finally, a summary function composes the three helpers and returns one flattened tuple:

    struct(i32, i32, usize, usize, usize) summarize(const i32[] data)
    {
        var b = bounds(data);
        var split = partition(data, 0);
        return (b.0, b.1, b.2, split.0.count(), split.1.count());
    }

    var s = summarize(samples);
    println("{} readings, min {}, max {}, {} below zero, {} above",
            s.2, s.0, s.1, s.3, s.4);

Three functions, each with its own tuple type, compose into a fourth without an out-parameter, a pre-declared buffer, or a comment explaining an input. Every piece has a name where it is used.

The pattern: one function returns a tuple, the caller reads the pieces by position, and positional access replaces out-parameters and pre-declared storage. Where meaning stops being obvious, which happens once a tuple holds three or more same-typed values across a function boundary, promote it to a struct. `struct(i32, i32, usize, usize, usize)` is about the largest tuple to tolerate before a named `Summary` struct. Chapter15's `Option` and `Result` cover pieces that might be missing.

Most tasks ask a function for more than one thing: a value and its status, a slice and its length, a minimum and a maximum. A tuple is the cheap answer that keeps the call site readable.

12.12 Exercises

1. Comprehension. What is the difference between `struct(i32)` and `i32` as a type? Why does the language spell tuple types with `struct(...)` rather than a bare `(...)`?

2. Comprehension. Given `var t = (1, 2.0, true)`, what is the type of `t`, and what is the type of `t.2`? Explain why `t.x` (with a letter) is a syntax error rather than something the compiler resolves at runtime.

3. Comprehension. Coral has no multi-name binding declaration and no underscore discard in patterns. Given `var counts = (3, 7, 11)`, write the line that gives you only the third value, and explain why you cannot write it as a binding form.

4. Implementation. Write `struct(i32, i32)` `minMax(const i32[] data)` returning the minimum and maximum in a single pass. Decide what to return for empty input and justify the choice in a comment. Then write the call site that reads both pieces.

5. Implementation. Write `struct(str, str)` `splitAt(str s, u8 delim)`: the part before the first `delim` and the part after it. Return `(s, "")` when the delimiter is absent. Use a byte-scanning helper or `str`'s search from the core library.

6. Patterns. Given a `Vec<struct(str, i32)>` of (name, score) pairs, write a loop that prints only the pairs above 90 by reading `.1`, and a `switch` over one pair that binds both pieces. Which reads better for which job?

7. Design. You have a function returning `struct(bool, String)` where the bool says whether parsing succeeded and the String holds either the value or an error message. Rewrite the API so the success path cannot read the error message as a value by accident. (Hint: this is a case for a `Result`, which Chapter15 covers; explain in two sentences why a tuple is the wrong shape here.)

8. Distinct. Define `pub distinct Celsius = f64;` and `pub distinct Fahrenheit = f64;`, plus a `toCelsius(Fahrenheit) Celsius` converter. Then try to pass a `Celsius` where a `Fahrenheit` is expected and describe the error. Why is `distinct` better than two raw `f64`s here, and better than a one-field struct?

9. Containers. Build a `Vec<struct(u8, u8)>` of twenty pairs, sort it by the first element, then check that no two adjacent pairs share a first element. Which parts get simpler when you read the pairs by position in a loop?

10. Meta. The chapter claims "if you are writing comments next to `.0` and `.1`, you wanted a struct." Find a place in the code you have written recently where a tuple carried a concept. Rewrite it as a struct. What broke, what got clearer, and was the trade worth it?
