Chapter12

Tuples and Destructuring

Two Answers for the Price of One Call

Functions often need to return more than one thing: a quotient and remainder, a value and its status, a hit flag and a position. Every language answers this differently.

C uses out-parameters: the answer lives in arguments you had to declare first, and the call site does not distinguish inputs from outputs. C++ and Java invent a small class and a name. Python and Rust use the tuple, a few values travelling together with no name and no ceremony. Coral does too.

A tuple is several values travelling together as one value, identified by position and nothing else.

This chapter covers what a tuple is, how to make and take one apart, and when a struct is the better tool. The standard library's map lookups, iterator adaptors, and later examples rely on it.

12.1 What a Tuple Actually Is

A tuple is the smallest aggregate: a value made of several values, with no field names, no methods, and no identity beyond its shape. A pair is two values; a triple is three.

The trouble with a struct for every pair is naming, not typing. Every throwaway struct needs a name, a file, an import, and a spot in the public API, and once named, a reader assumes it is part of the domain model. A tuple refuses all that: these values travel together briefly and then stop being a thing.

Tuples are for ephemeral, positional, local structure. In a struct, order does not matter because fields are reached by name. In a tuple, position is the only identifier: the first element is the first element, and that is what `.0` means.

If you invent a `Receipt` struct for two numbers on their way to a printer, you claim a concept exists. If you meant only "two numbers, right now," a tuple is honest and the struct is a small lie.

The one-line version:

    var point = (3.0, 4.0);      // a pair: two values in one

That is a tuple. `.0` is `3.0`, `.1` is `4.0`. It has no name, it was not declared anywhere, and it will not survive past the function that made it unless you hand it to someone. That lightness is the entire point.

One more piece of vocabulary, because it comes up constantly. A tuple with two elements is a pair. Three is a triple. The general term is "n-tuple," and nobody says it out loud. When this chapter says "pair," it means a two-element tuple, and no more.

12.2 Writing a Tuple Type

A tuple type is written with the `struct` keyword and a comma-separated list of element types in parentheses:

    struct(i32, f64)                 // a pair: an integer and a float
    struct(u8, u8, u8)               // three bytes, perhaps a colour
    struct(String, usize)            // an owned string and a length
    struct(i32, struct(i32, i32))    // a pair whose second element is itself a pair
    struct(f64, f64, f64, f64)       // four floats

This is the only way to write a tuple type. No second spelling drops the outer `struct`, and that is deliberate rather than an oversight. A bare parenthesised type already means something else in the language, grouping, and a statement that begins with `(` is read as a cast, so a parenthesised type cannot do the aggregating job without ambiguity. The `struct` keyword is what makes a tuple type unmistakable in every position: declarations, parameters, return types, and generic arguments alike. When you see `struct(` you are looking at a tuple, everywhere, always.

In plain words, the `struct` keyword in front is a signpost. It tells the compiler, and you, "the parentheses that follow are a bundle of types, not a grouped type or a cast." Without the signpost the compiler could not tell the tuple `struct(i32, f64)` from a grouped `i32`.

Each of those is a distinct type. `struct(i32, f64)` is not the same type as `struct(f64, i32)`, even though the two contain the same components, order is part of the identity, because position is the only name a tuple element has. Two tuples are the same type only when they have the same number of elements and each position has the same type. This is stricter than it might first appear, and it is a feature: the compiler will not let you feed a `struct(f64, i32)` where a `struct(i32, f64)` is expected, so a "swap the arguments" mistake becomes a compile error instead of a silent corruption.

A common mistake is to build a tuple in the wrong order and expect it to fit a variable declared the other way. `struct(i32, f64)` and `struct(f64, i32)` hold the same two kinds of value, but the compiler treats them as unrelated types, so `struct(f64, i32) swapped = (1, 2.5);` fails. The position is the name, and a name in the wrong place is the wrong name.

A single-element tuple is written the same way:

    struct(i32)                // a one-element tuple containing an i32

No trailing-comma rule to memorise here, and no ambiguity with grouping: the `struct` keyword already said "this is an aggregate." The one-element tuple is rare but not useless. It shows up when a generic function must return "a T, wrapped as a tuple" to fit a shape, and it shows up when you want a tuple type to be structurally distinct from the bare type. Mostly you will not write one. But you will read one, and you should not be surprised that it takes exactly one type between the parentheses.

The empty tuple has a value and a type, and they are spelled the same way:

    struct()                   // the unit type

A `struct()` has exactly one value, written `()`, and it means "no information." A function that returns nothing is, under the hood, returning the unit type. Coral lets you write `void` for that role in most places, and usually you should, because `void` reads as "this returns nothing." But `struct()` has a job that `void` cannot do: it is a real, usable type when a generic construct needs "a type whose values carry no data." A `Map<str, struct()>` is a set of strings. A channel of `struct()` is a signal. A state-machine transition that yields nothing can yield `struct()`. Unit is not nothing; it is a type whose only value takes zero bytes.

There is one more idea here, and it explains a lot of the rest. Underneath, a tuple is a struct whose fields happen to be numbered. `struct(i32, f64)` is a struct with a field named `0` of type `i32` and a field named `1` of type `f64`. That is why access is `.0` and `.1`: they are field accesses, the same syntax you use for a named field, with numbers for names because the tuple never gave them names. It is also why the tuple's layout is exactly a struct's layout: declaration order, each element aligned to its natural boundary. No hidden header, no heap, no bookkeeping. If you remember only one sentence from this section, remember this one: a tuple is a struct that forgot to name its fields.

Simply put, a tuple and a struct are the same bytes; the only difference is whether the fields were given names. A struct says "the first field is called `x`"; a tuple says "the first field is just first." That is why a tuple costs nothing extra and why `t.0` feels so much like `p.x`, it is the very same field access, with a number standing in for a name.

12.3 Writing a Tuple Value

A tuple literal is a comma-separated list of values in parentheses. Its type is inferred from the elements, element by element:

    var pair = (1, 2.5);              // inferred struct(i32, f64)
    var rgb = (255u8, 128u8, 0u8);    // struct(u8, u8, u8)
    var origin = (0.0, 0.0);          // struct(f64, f64)
    var nested = (1, (2, 3));         // struct(i32, struct(i32, i32))
    var swapped = (origin.1, origin.0);  // struct(f64, f64)

Read `var pair = (1, 2.5);` the way the compiler reads it. It sees an integer literal `1`, so the first element is `i32`. It sees a floating literal `2.5`, so the second element is `f64`. The type of `pair` is therefore `struct(i32, f64)`. There is no hidden promotion from `1` to `1.0`; the tuple simply takes each element at its own type. This is worth pausing on, because it is the seed of a common mistake.

Two tuple literals with the same shape but different element types are different types, and they do not unify:

    var a = (1, 2);        // struct(i32, i32)
    var b = (1, 2.0);      // struct(i32, f64), not the same type as a

You cannot assign `b` to a variable of `a`'s type, and you cannot put them in the same vector, because `Vec<struct(i32, i32)>` and `Vec<struct(i32, f64)>` are as different as `i32` and `f64`. The good news is that this is exactly what you want: a function that takes a pair of integers should not silently accept a pair of (integer, float). The mistake you are most likely to make is writing `2` where you meant `2.0`, and the compiler catches it immediately rather than letting a truncation happen quietly at runtime.

Where does the type go if you want to be explicit? The same place it always goes for a local: in front. You write the tuple type with `struct`:

    struct(i32, f64) reading = (70, 0.55);
    struct(str, i32) entry = ("ada", 1815);

The unit literal is `()`:

    var nothing = ();      // the one value of the unit type

Tuples are values, and they behave like values. They live on the stack. They are copied when assigned, subject to the move rules you met in the chapters on memory. They are passed by value. No implicit boxing, and no heap allocation unless you deliberately put a tuple that owns heap data inside something that owns it. A `struct(i32, i32)` is eight bytes and moves like eight bytes. A `struct(f64, f64, f64)` is twenty-four bytes and moves like twenty-four bytes. Nothing is hidden.

That "nothing is hidden" quality is why tuples are the right tool for hot paths and low-level code. No constructor call, no reference counting, no object header. It is just bytes laid out in order. When you hear someone say a feature "compiles away to nothing," a tuple is one of the few features that genuinely does: a `struct(i32, i32)` and two `i32` locals occupy the same memory and cost the same instructions.

12.4 Getting the Pieces Out by Position

Tuples are indexed by position with a dot and a decimal integer:

    var t = (10, 20, 30);
    var first  = t.0;      // 10
    var second = t.1;      // 20
    var third  = t.2;      // 30

Two things distinguish this from array indexing. First, the index is not an expression; it is part of the syntax. `t.0` is valid, `t.i` is not, the compiler will reject the letter. Second, because the index is fixed at compile time, the compiler always knows the exact type of every element. If `t` is `struct(i32, f64, bool)`, then `t.0` is `i32`, `t.1` is `f64`, and `t.2` is `bool`, known at compile time with no runtime lookup and no bounds check. Compare an array, where `arr[i]` has one element type and the index is computed at runtime.

    var pair = (1, 2.5);
    var first  = pair.0;     // an i32
    var second = pair.1;     // an f64

Each read knows its type before the program runs, which is why a tuple can hold values of different types where an array cannot.

Hold on, why does it matter that the index is a literal and not a variable? Because that is precisely what lets the compiler turn each access into a fixed offset. `t.0` compiles to "the first field," not "look up field number zero." If the index could be a runtime value, the compiler would have to keep the types of the fields in some table and check the index at run time, and a tuple could hold elements of different types only if every access returned "one of these, we are not sure which." Because the index is a compile-time constant, a tuple can mix types freely and every access is a plain, typed field read. That is why a tuple access is free, and why tuples can be heterogeneous while arrays cannot.

You can assign a whole tuple to a mutable variable, and you can reassign a tuple-valued location:

    var p = (1, 2);
    p = (5, 6);            // p is now (5, 6); the types still match

A tuple is not a place you reach into and edit piece by piece so much as a value you replace wholesale. Can you write `p.0 = 5`? The syntax exists, `.0` is a field access, and a field of a mutable local can be assigned, but reaching in to change one piece of a tuple is usually a sign that you wanted a struct with named mutable fields, or that you should build a fresh tuple. When you find yourself nudging `.1` and leaving the rest alone, stop and ask whether the value has quietly become a concept. Which, as we are about to see, is often the moment a pattern should take over.

12.5 Taking a Tuple Apart

Reading `t.0`, `t.1`, `t.2` is the only way to pull one piece out of a tuple at a time, and it is exactly what you want when you need one or two of the pieces. But there is a hard question hiding here that surprises people coming from Rust and Python: can you bind all the pieces to names in one line, the way `let (x, y) = pair;` does there?

In Coral, the answer is no. The language has no multi-name binding declaration. You cannot write `var (x, y) = pair;`, and you cannot put a parenthesised pattern where a variable name goes. This is the same restraint you have already met twice: a statement that begins with `(` is a cast, and `(a, b)` in expression position is a tuple literal, so there is no room for a third reading of parentheses as a binding form. Rather than overload the syntax, Coral keeps the rule simple, a tuple is taken apart either one piece at a time by position, or all at once by a pattern in a `switch`, which is the subject of the next section.

That means the everyday recipe is positional access, and it reads perfectly well:

    var pair = divide(17, 5);      // pair : struct(i32, i32)
    var quotient = pair.0;
    var remainder = pair.1;

If you only want one piece, this is not a compromise; it is the clearest thing you can write. And here is a related fact you must internalise early, because the muscle memory is strong: there is no underscore discard placeholder in Coral. `_` is not a wildcard. In Rust you would write `let (keep, _) = pair;` to ignore the second piece; you cannot translate that line. So you reach for `.0` directly, which is exactly what you wanted anyway:

    var pair = (10, 20);
    var keep = pair.0;        // just read the first element

If you are coming from Rust or Python, this restriction can feel like a step backwards, so here is the intuition to put in place of the missing syntax. A tuple is a bucket of values identified by position, and `.0` and `.1` are the labels printed on the bucket's compartments. You reach into the compartment whose label you want; there is no shorthand that names every compartment at once. When you want *all* the pieces, you use a `switch` pattern, which is the next section.

Now, when do you want *all* the pieces at once? That is what patterns are for, and they live where values are matched rather than where they are declared. A tuple is a value, and a tuple pattern is a way to ask the question "does this value have this shape, and if so, name the pieces." The next section is entirely about that.

12.6 Patterns: Matching Tuples in a switch

A `switch` takes a value, tries its arms in order, and runs the first one whose pattern matches. A tuple pattern is written with parentheses and the same commas as a tuple literal, and each position holds either a sub-pattern or a fresh name to bind:

    switch (divide(10, 0)) {
        (value, true)  => println("ok: {}", value),
        (value, false) => println("division failed"),
    }

Each arm is a tuple pattern: it matches the tuple position by position and binds the pieces it names. Because a `bool` has exactly two values and both arms are present, this switch is exhaustive and the compiler confirms it. If you later decide `divide` must also report an error string, the type changes and the compiler walks you through every switch that has to change, the same exhaustiveness benefit Chapter13 describes at length.

Here is that switch walked through slowly. Suppose `divide(10, 0)` returns the tuple `(0, false)`. The switch tries the first arm, `(value, true)`: it needs the second component to be `true`, but it is `false`, so this arm does not match. It tries the second arm, `(value, false)`: the second component is `false`, so it matches, binding `value` to `0` and running `println("division failed")`. First match wins, and the rest are skipped.

Patterns nest, because the type nests:

    switch (bounds(values)) {
        (lo, hi, 0) => println("no data"),
        (lo, hi, n) => println("{} readings span {}", n, lo, hi),
    }

The first arm matches only when the count is exactly zero and binds the two zeroes into `lo` and `hi` (which you ignore by not using them). The second arm is a catch-all binding pattern that names all three pieces. Because there is no wildcard, when you want to ignore a piece you name it and simply do not use it, or you write it as a literal that pins the value. Coral's patterns are about *shape and value*, not about discarding, and the habit of naming a piece you will not read is the small price of having no `_`.

And `else` still works as the catch-all when you do not want to enumerate:

    switch (signOf(x), signOf(y)) {
        (1, 1)   => println("both positive"),
        (0, 0)   => println("both zero"),
        else     => println("something else"),
    }

Notice the trick quietly at work here. We built a tuple out of two small values purely so that we could match on them. `(signOf(x), signOf(y))` is not stored in a variable or returned from a function; it is constructed at the moment of the switch and immediately taken apart. That is a recurring Coral idiom: when a decision depends on several small closed facts at once, package them into a tuple and match, and the compiler will check completeness for you. Chapter13, where patterns over tuples and variants are the main tool for taking data apart, builds on exactly this.

One subtlety worth naming, because it trips people up. A binding pattern asks for the value at that position, and the value is copied or moved into the new name according to the usual ownership rules. Matching a tuple that owns heap data, say a `struct(String, usize)`, moves the `String` out of the tuple and into the new name. After that, the original tuple is partially moved and cannot be used as a whole. If you have not met move semantics yet, all you need for now is the rule of thumb: a pattern that binds a piece takes it, and does not copy it unless the piece is trivially copyable like a number.

12.7 Returning Several Values

This is the single best reason tuples exist, so it gets its own section. A function returns one value; a tuple lets that one value be several. The canonical example is a division that reports both the quotient and whether it succeeded:

    struct(i32, bool) divide(i32 a, i32 b)
    {
        if (b == 0) return (0, false);
        return (a / b, true);
    }

Call it, then read the pieces by position or match them:

    struct(i32, bool) r = divide(10, 3);
    if (r.1) {
        println("quotient is {}", r.0);
    }

Compare the C convention: `i32 divide(i32 a, i32 b, bool* ok)`. The caller must declare a `bool` first, pass its address, and remember which argument was the output. The tuple puts the whole answer in one place and makes the call site read left to right. If you have ever written code where the out-parameters are threaded through three helper calls, you know exactly why this is better.

The pattern scales. A function can return `struct(String, usize)` to hand back an owned buffer and its length, `struct(i32, i32, i32)` for a colour, `struct(T, T)` for a swap, or `struct(bool, T)` for a found-flag and a found value. Here is a swap:

    struct(i32, i32) swap(i32 a, i32 b)
    {
        return (b, a);
    }

    var pair = swap(x, y);
    x = pair.0;
    y = pair.1;

And here is a lookup that also reports the index it found, which is the shape you want for a search:

    struct(usize, bool) indexOf(const i32[] data, i32 needle)
    {
        for (usize i = 0; i < data.count(); i++) {
            if (data[i] == needle) return (i, true);
        }
        return (0, false);
    }

A caller who found what they wanted can read both pieces:

    var hit = indexOf(readings, 99);
    if (hit.1) {
        println("found 99 at position {}", hit.0);
    }

A caller who only cares whether it was found reads just the flag:

    var found = indexOf(readings, 99).1;    // read just the flag

One warning that will save you a bug later. The `(0, false)` above is a sentinel: when the search fails, the function returns a real index of `0` that means nothing, paired with a flag that says "ignore it." If a caller forgets to check `found` and uses the index anyway, they will silently search at position zero. That is the weakness of encoding failure as a tuple: the failure path is a value the caller can ignore. The honest way to express "an index, or nothing" is `Option<usize>`, and the honest way to express "a value, or a reason it failed" is `Result<T, E>`. Both are the subject of Chapter15. A tuple is the right shape when every piece is always meaningful; the moment one piece is conditional, a variant says so in the type.

12.8 Tuples in Generics and Containers

Because a tuple is a type like any other, it can be an element type, a map value, a generic argument, or a return type from a generic helper. This is where tuples earn their keep in the standard library:

    Vec<struct(str, i32)> scores = Vec<struct(str, i32)>::new();
    scores.push(("ada", 92));
    scores.push(("grace", 97));

    for (var entry : scores) {
        println("{} scored {}", entry.0, entry.1);
    }

A `struct(str, i32)` is a perfectly good key-value pair. When you genuinely do not want to name the concept "score," a tuple is honest about the fact that it is just two things together. If you later decide the pair deserves a name, you promote it to a struct, and the change is local: a definition, a construction site, and the field accesses.

Tuple-shaped return types are common in generic algorithms. A function that splits a vector at the first match can return `struct(Vec<T>, Vec<T>)`, everything before, everything after, rather than mutating two out-parameters. A function that finds the minimum and maximum in a single pass returns `struct(T, T)`. A partition operation returns `struct(Vec<T>, Vec<T>)` for the elements that passed and failed a test. In each case the tuple is the natural "this algorithm produces two answers" shape, and the caller reads the two halves out:

    var split = splitAt(values, pivot);
    var before = split.0;
    var after  = split.1;

Because tuples nest and compose, you can also have a map whose values are tuples, or a tuple of vectors: `struct(Vec<i32>, Vec<str>)`. The type system keeps them straight. A `Map<str, struct(f64, f64)>` might map a city to its latitude and longitude; a `Map<str, struct(u32, u32)>` might map a word to its wins and losses. In both cases the tuple is doing the same job a lightweight struct would do, without the ceremony of a name.

The one thing you cannot do is give a tuple methods, and we should be honest about how far this reaches. You cannot write an `extend` block for `struct(i32, i32)`, and you cannot implement a trait for a bare tuple. A tuple's only behaviour is its layout. That is the boundary line between tuples and structs, and it is Section12.9.

In plain words, a tuple is data and nothing more. It has no methods, no name, and no behaviour beyond the bytes it holds. The moment you want a tuple to *do* something, to print itself, compare itself, or clean up after itself, it has grown beyond a tuple and wants to be a struct.

Why this matters: because tuples are plain data, they are the cheapest way to return several answers and the easiest to use in a hot loop. A `struct(str, i32)` inside a `Vec` costs exactly what a two-field struct costs and nothing more, no methods, no vtable, no hidden allocation. The lightness you gain is the same lightness that stops you adding behaviour later, so choose it when the data really is just passing through.

12.9 Tuple or Struct?

The two look similar and get used for the same job at different scales. The question "should this pair be a tuple or a struct?" comes up constantly, so here is a decision you can apply without agonising.

Reach for a tuple when all of these hold:

    - there are two or three elements,
    - the order is obvious at the call site from context,
    - the tuple does not travel far from where it is created,
    - and you would not want a type name for it in the API documentation.

Reach for a struct when any of these hold:

    - there are more than three or four elements,
    - callers would need to remember which position means what,
    - the value crosses a module boundary or appears in a public signature,
    - the fields have different lifetimes or ownership rules,
    - or you want to add methods, drop semantics, or trait implementations.

There is also a hard technical difference, and it is the one that settles most arguments: you cannot add a method to a tuple. You cannot write an `extend` block for `struct(i32, i32)`, and you cannot implement a trait for a bare tuple. A tuple's only behaviour is its layout. When a value needs behaviour, a `drop`, a `toStr`, a comparison, a `clone`, it needs to be a struct, or (as we will see) a `distinct` type.

Here is the wrong way and the right way, side by side. Wrong way: a tuple that has quietly become a concept, with comments standing in for field names.

    // a "user" is (id, name, email, active), good luck remembering which is which
    struct(i64, str, str, bool) user = (1, "ada", "ada@example.com", true);
    if (user.3) { ... }        // what is .3 again?

Right way: a struct, because the value has a name and a meaning.

    struct User {
        i64  id;
        str  name;
        str  email;
        bool active;
    }

    User user = User { .id = 1, .name = "ada", .email = "ada@example.com", .active = true };
    if (user.active) { ... }   // unambiguous, and it survives a reorder of the fields

The tuple version is not wrong because it is short; it is wrong because the moment a value has a name in your head, the language should have that name too. A tuple that has grown a concept is a struct that has not been written down yet.

Let me give you a test you can run in five seconds. Read the construction site out loud. If it sounds like a sentence about your problem, "a user is an id, a name, an email, and whether they are active", then the names belong in the code, and a struct is right. If it sounds like a sentence about plumbing, "give me this number and this flag so the next function can look", then a tuple is right. The tuple is not the junior version of the struct; they are two tools for two different jobs, and the common mistake is reaching for the tuple when the job is the struct.

12.10 distinct: The Named Tuple

There is a middle ground between an anonymous tuple and a struct, and it is worth knowing because tuple-shaped quantities are the most common place the confusion bites. Suppose you have two measurements, both stored as `f64`: a distance in meters and a distance in feet. As raw floats, they are interchangeable, and one day someone will add meters to feet and get a plausible, wrong number.

    f64 meters = 100.0;
    f64 feet = meters;         // compiles; wrong, but nothing stops it

A `distinct` type gives you the tuple's data layout with a real name and real type identity, so the two can no longer be mixed:

    pub distinct Meters = f64;
    pub distinct Feet   = f64;
    pub distinct Point  = struct(f64, f64);

    Meters distance = (Meters) 100.0;
    Feet wrong = (Feet) distance;      // error: distinct types do not convert

Read `(Meters) 100.0` as a cast: `100.0` is an `f64`, and you are deliberately saying "treat this as a Meters value." There is no `as` cast in Coral; a cast is written by putting the target type in parentheses before the value. A `distinct` type is a new nominal type whose representation is the underlying type. It has the tuple's bytes and the struct's identity. When you want the compiler to stop you from mixing up two same-shaped things, `distinct` is the right tool, not a struct wrapper you would have to unwrap at every use site.

Here is the conversion that makes the two types useful rather than merely separate:

    Meters toMeters(Feet f) {
        return (Meters) (f.0 * 0.3048);
    }

Wait, `f.0`? Yes. When a `distinct` type's representation is a tuple, the value has positional access, because underneath it is still a tuple. `pub distinct Point = struct(f64, f64);` gives you `p.0` and `p.1` while still refusing to let a `Point` stand where an unrelated `struct(f64, f64)` is expected. You get positional convenience and nominal safety at the same time. For a `distinct` whose representation is a single scalar, there is nothing to index; you cast to the underlying type when you need the bytes, which is a visible reminder at every use site that a unit conversion could be happening.

Think of `distinct` as a sticky note you put on a type. Under the note, `Meters` is just an `f64`, laid out in eight bytes. But the compiler reads the note, and it refuses to do arithmetic between two values whose notes differ, and it refuses to hand a `Meters` to code that asked for `f64` without a deliberate cast. You keep the tuple's cheap layout and gain the struct's identity.

Why this matters: `distinct` is how a program says two things that look alike are not the same thing. Money in dollars and money in euros, a distance in meters and a distance in feet, a user id and an order id, all of them are the same number underneath and all of them are dangerous to mix. The `distinct` type gives you the cheap layout of the underlying value with the safety of a real name, and costs nothing at run time.

12.11 A Worked Example: Bounds and Statistics

Put the pieces together on a small, realistic problem, and watch how many of them appear at once.

Suppose you are reading sensor samples, a slice of `i32`, and you want the smallest reading, the largest reading, and how many there were, in one pass. That is one function producing three answers, which is exactly a tuple's job:

    struct(i32, i32, usize) bounds(const i32[] data)
    {
        if (data.count() == 0) return (0, 0, 0);
        i32 lo = data[0];
        i32 hi = data[0];
        for (var v : data) {
            if (v < lo) lo = v;
            if (v > hi) hi = v;
        }
        return (lo, hi, data.count());
    }

Notice the empty case returns `(0, 0, 0)`, which is a sentinel the caller must interpret. That is a weakness, and later chapters fix it: a `Result` or an `Option` would say "no data" honestly instead of pretending the bounds are zero. For now, let the caller carry the convention.

Callers get all three numbers with no out-parameters and no pre-declared storage:

    struct(i32, i32, usize) b = bounds(values);
    println("{} readings, range {}..{}", b.2, b.0, b.1);

A caller who only cares about the range reads the two positions it wants and ignores the count entirely:

    struct(i32, i32, usize) b = bounds(values);
    println("range {}..{}", b.0, b.1);

Now a caller who wants to branch on emptiness matches the tuple directly:

    switch (bounds(values)) {
        (lo, hi, 0) => println("no data"),
        (lo, hi, n) => println("{} readings span {}", n, lo, hi),
    }

Now add a second function that turns the bounds into a report string, to see the tuple flow through a pipeline:

    str describe(const i32[] data)
    {
        var b = bounds(data);
        if (b.2 == 0) return "no readings";
        return "min " + toStr(b.0) + ", max " + toStr(b.1) + ", n " + toStr(b.2);
    }

`describe` reads by position rather than matching, because it uses all three pieces but reuses them across two branches, and reading `b.0` three times is clearer than three separate bindings. That is the judgement call the earlier sections described, made concrete.

And a third function that splits the samples at a threshold, returning two vectors, the generic tuple return in action:

    struct(Vec<i32>, Vec<i32>) partition(const i32[] data, i32 threshold)
    {
        Vec<i32> low  = Vec<i32>::new();
        Vec<i32> high = Vec<i32>::new();
        for (var v : data) {
            if (v < threshold) low.push(v);
            else               high.push(v);
        }
        return (low, high);
    }

The call site reads like a sentence:

    var split = partition(samples, 50);
    println("{} below the threshold, {} above", split.0.count(), split.1.count());

Finally, let us put the tuples to work together, which is the reason to write any of this. A summary function composes the three helpers and returns one flattened tuple for the caller:

    struct(i32, i32, usize, usize, usize) summarize(const i32[] data)
    {
        var b = bounds(data);
        var split = partition(data, 0);
        return (b.0, b.1, b.2, split.0.count(), split.1.count());
    }

    var s = summarize(samples);
    println("{} readings, min {}, max {}, {} below zero, {} above",
            s.2, s.0, s.1, s.3, s.4);

Look at what has happened. Three functions, each with its own tuple type, compose into a fourth without a single out-parameter, without a single pre-declared buffer, and without a single comment explaining which argument was an input. Every piece of the answer has a name at the point where it is used, and a reader can follow the data from `bounds` and `partition` into the print in one glance.

This is the pattern to internalise for the whole chapter: one function returns a tuple, the caller reads the pieces it needs by position, and positional access replaces a pile of out-parameters and pre-declared storage. Where the tuple's meaning stops being obvious, which happens as soon as it holds three or more same-typed values and travels across a function boundary, you promote it to a struct, and the compiler starts helping you again. The worked example above is right at the edge of that trade-off: `struct(i32, i32, usize, usize, usize)` is the largest tuple you should tolerate before reaching for a `Summary` struct with named fields. Chapter15's `Option` and `Result` are what you reach for when a piece of the answer might not be there at all.

Why this matters: nearly every programming task begins by asking a function for more than one thing, a value and its status, a slice and its length, a minimum and a maximum. A tuple is the small, cheap answer that keeps the call site readable, and the habit of returning several values in one place instead of threading out-parameters is the one that makes the later chapters' code feel tidy.

12.12 Exercises

1. Comprehension. What is the difference between `struct(i32)` and `i32` as a type? Why does the language spell tuple types with `struct(...)` rather than a bare `(...)`?

2. Comprehension. Given `var t = (1, 2.0, true)`, what is the type of `t`, and what is the type of `t.2`? Explain why `t.x` (with a letter) is a syntax error rather than something the compiler resolves at runtime.

3. Comprehension. Coral has no multi-name binding declaration and no underscore discard in patterns. Given `var counts = (3, 7, 11)`, write the line that gives you only the third value, and explain why you cannot write it as a binding form.

4. Implementation. Write `struct(i32, i32)` `minMax(const i32[] data)` returning the minimum and maximum in a single pass. Decide what to return for empty input and justify the choice in a comment. Then write the call site that reads both pieces.

5. Implementation. Write `struct(str, str)` `splitAt(str s, u8 delim)`: the part before the first `delim` and the part after it. Return `(s, "")` when the delimiter is absent. Use a byte-scanning helper or `str`'s search from the core library.

6. Patterns. Given a `Vec<struct(str, i32)>` of (name, score) pairs, write a loop that prints only the pairs above 90 by reading `.1`, and a `switch` over one pair that binds both pieces. Which reads better for which job?

7. Design. You have a function returning `struct(bool, String)` where the bool says whether parsing succeeded and the String holds either the value or an error message. Rewrite the API so the success path cannot read the error message as a value by accident. (Hint: this is a case for a `Result`, which Chapter15 covers; explain in two sentences why a tuple is the wrong shape here.)

8. Distinct. Define `pub distinct Celsius = f64;` and `pub distinct Fahrenheit = f64;`, plus a `toCelsius(Fahrenheit) Celsius` converter. Then try to pass a `Celsius` where a `Fahrenheit` is expected and describe the error. Why is `distinct` better than two raw `f64`s here, and better than a one-field struct?

9. Containers. Build a `Vec<struct(u8, u8)>` of twenty pairs, sort it by the first element, then check that no two adjacent pairs share a first element. Which parts get simpler when you read the pairs by position in a loop?

10. Meta. The chapter claims "if you are writing comments next to `.0` and `.1`, you wanted a struct." Find a place in the code you have written recently where a tuple carried a concept. Rewrite it as a struct. What broke, what got clearer, and was the trade worth it?
