Chapter29

Live Examples: Sorting, Searching, and Complexity

How Do You Measure a Program?

Two programs can sort a list correctly and still differ in speed. Timing measures the whole machine, compiler, load, and input at once, so the result changes from run to run and tells you nothing stable about the algorithm.

Instead, computer science measures work as a function of input size n. Doubling n might double the steps (O(n)) or quadruple them (O(n^2)); that relationship is the algorithm's time complexity and is independent of the machine.

This chapter spends several sections on theory first, because growth rates, best and worst cases, and amortised cost are the vocabulary for every analysis that follows.

Complexity simply asks what happens to the work when the input gets big: a linear phone-book scan slows in proportion to the names, while halving your way in barely slows at all.

A note on the imports these examples use. The growable list is `import(lib) std::vec { Vec };`, and the sorting variations use `sortI32` from `import(lib) std::collections::sort { sortI32 };`. The integer and boolean types are built in. Each code block assumes those imports and is otherwise complete.

29.1 Counting Steps: The Naive Idea, and Why It Nearly Works

Start by counting operations on the simplest algorithm, summing a list:

    i64 sumAll(Vec<i32>* v) {
        // accumulate in 64 bits so the sum cannot overflow i32
        i64 total = 0;
        // one pass, one add per element: the work is proportional to n
        for (usize i = 0; i < v->count(); i += 1) {
            total += (i64)v->at(i);
        }
        return total;
    }

For n elements, the loop does one comparison, read, addition, and increment per element, plus setup and return, so a consistent accounting gives 4n + 2.

Different accounting choices give 4n + 2, 3n + 5, or 4.5n + 1, all correct under some definition. The constants are accidents of counting; the stable fact is the shape: twice the input, twice the work.

Keep the shape and discard the constants.

29.2 Big-O, Big-Omega, and Big-Theta: Three Bounds

Big-O, O(...), is an upper bound on growth: f(n) is O(g(n)) if some positive c and threshold n₀ satisfy f(n) ≤ c · g(n) for all n ≥ n₀.

This is weaker than many people assume. 4n + 2 is O(n) because 5n ≥ 4n + 2 for n ≥ 2, but it is also O(n^2) and O(2^n); O only says g eventually dominates up to a constant. Programmers usually quote the tightest simple bound they know.

Big-Omega, Ω(...), is the matching lower bound: f(n) ≥ c · g(n) for all sufficiently large n. A comparison sort needing at least n log n comparisons in the worst case has worst-case cost Ω(n log n).

Big-Theta, Θ(...), is the tight bound: f is both O(g) and Ω(g), so c₁ · g(n) ≤ f(n) ≤ c₂ · g(n) eventually. The sum function is Θ(n), not merely O(n).

Use O for an upper bound, Ω for a lower bound, and Θ only when both match. Saying "binary search is O(n)" is true but useless; its point is Θ(log n).

29.3 Growth Rates: The Table You Should Memorise

These are the common complexity classes and their growth; read the last column for the difference.

    n          log2 n   n        n log2 n    n^2         2^n
    --------------------------------------------------------------
    10         3.3      10       33          100         1,024
    100        6.6      100      664         10,000      1.27 × 10^30
    1,000      10       1,000    9,966       1,000,000   ~10^301
    10,000     13.3     10,000   132,877     100,000,000 unthinkable
    1,000,000  19.9     10^6     19,931,569  10^12       no

At a billion operations per second and n = 10^6, the classes take:

    Complexity      steps for n = 10^6   time at 10^9 steps/sec
    -----------------------------------------------------------
    O(log n)        ~20                   instant
    O(n)            10^6                  ~1 millisecond
    O(n log n)      ~2 × 10^7             ~20 milliseconds
    O(n^2)          10^12                 ~17 minutes
    O(2^n)          astronomically large  longer than the universe

Ordering matters more than constants: an O(n log n) sort beats an O(n^2) sort for large inputs no matter how tight the inner loop. Cheap classes are nearly free and expensive ones hopeless.

In increasing order: O(1) constant, O(log n) logarithmic, O(n) linear, O(n log n) linearithmic, O(n^2) quadratic, O(n^3) cubic, O(2^n) exponential, O(n!) factorial. Exponential work explodes with every added item, so brute force over subsets or permutations only works for small n.

29.4 Best, Worst, and Average Case

Cost depends on input contents as well as size, so we distinguish three cases.

Worst case is the maximum work over all inputs of size n, and the usual promise. Best case is the minimum, usually a curiosity. Average case is the expected work over a distribution, honest only if you know that distribution.

Quicksort (29.8) is Θ(n log n) best and average, but Θ(n^2) worst, triggered by already-sorted input. That is why the standard library's `partitionI32` uses a median-of-three pivot rather than the last element.

Amortised is not the same as average, as the next section shows.

29.5 Amortised Analysis: Why Vec::push Is O(1)

`Vec<T>::push` usually writes one element and bumps the length, but when full it doubles capacity and copies everything, which is O(n). Is `push` O(1) or O(n)?

    void push(T val) {
        // the rare expensive case: the backing array is full
        if (self.len >= self.cap) {
            // double the capacity, which is what makes the cost amortised O(1)
            usize newCap = self.cap > 0 ? self.cap * 2 : 4;
            self.reserve(newCap);
        }
        // the common case: write and bump the length, both constant time
        self.data[self.len] = val;
        self.len++;
    }

Usually `push` is constant work; when the vector is full it reallocates to twice the size and copies every element, which is O(n). So it is sometimes each.

The answer is O(1) amortised: spread the total cost of a worst-case sequence over that sequence. A sequence of n pushes costs O(n) total, so the average per push is O(1), regardless of order.

With doubling from capacity 1, growth copies 1 + 2 + 4 + ... + n/2 < n elements total.

    1 + 2 + 4 + ... + n/2 < n.

The geometric series is bounded by about n moves, and the n pushes add n writes, so n pushes cost fewer than 2n operations, or O(1) each on average. The rare expensive pushes are paid for by the cheap ones before them.

Doubling is why a dynamic array is the default container. Growing by a fixed amount instead would make every push copy the whole array, giving O(n) amortised cost.

29.6 Linear Search: The Baseline

The problem. Find the index of a target in a list, or report that it is absent.

Picture this. Scan a stack of unordered forms one by one until you find the name or run out.

Brute force, then better. Linear search is the brute force, and no better general method exists for an unsorted list. For repeated lookups, sort once and use binary search; for one lookup, the scan is optimal.

    i64 linearSearch(Vec<i32>* v, i32 key) {
        // scan from the front until the key turns up
        for (usize i = 0; i < v->count(); i += 1) {
            if (v->at(i) == key) return (i64)i;
        }
        // -1 is not a legal index, so it can carry "not found"
        return -1;
    }

The return type is i64 because every usize is a legal index, while −1 can mean "not found." `Option<usize>` is the fully honest alternative.

Time and space. The loop runs at most n times: Θ(n) worst and average, O(1) best, and O(1) extra space. Any correct algorithm must inspect all elements in the worst case, since an unseen element could be the target.

Edge cases. An empty list returns −1 at once. Duplicates return the first match; scan backwards for the last. An absent target costs the full n steps.

A variation. Sort once with `sortI32` and binary-search every query: Θ(n log n) setup, then Θ(log n) per search instead of Θ(n). After about log n queries the sort pays for itself.

29.7 Binary Search: Halving the Problem

The problem. In a sorted list, find the index of a target or report it absent without touching every element.

Picture this. Open a dictionary in the middle, learn which half holds the word, discard the other half, and repeat. A thousand pages take about ten steps, since 2^10 ≈ 1000.

Brute force, then better. Linear search is Θ(n). Binary search discards half the remaining elements per comparison, so it needs log₂ n comparisons.

    i64 binarySearch(Vec<i32>* v, i32 key) {
        // inclusive window of positions that might still hold the key
        i64 lo = 0;
        i64 hi = (i64)v->count() - 1;
        // keep halving while the window is non-empty
        while (lo <= hi) {
            // written as lo + (hi-lo)/2 to avoid overflow of lo + hi
            i64 mid = lo + (hi - lo) / 2;
            i32 val = v->at((usize)mid);
            if (val == key) return mid;
            // discard the half that cannot contain the key
            if (val < key) lo = mid + 1;
            else hi = mid - 1;
        }
        return -1;
    }

The bounds are inclusive: `lo` and `hi` might still hold the target, and the loop runs while `lo <= hi`. Compute the midpoint as `lo + (hi - lo) / 2`; `(lo + hi) / 2` can overflow when both are large, a famous binary-search bug. Move `hi` below `mid` for a smaller target, `lo` above it for a larger one. When they cross, the target is absent.

Time and space. Each iteration halves the window, so Θ(log n) iterations (about 20 for a million elements, 30 for a billion) and O(1) space. A recursive version pays Θ(log n) stack for no benefit.

Edge cases. The list must be sorted, or the result is nonsense without error. An empty list gives `hi = -1` and returns −1. Duplicates return some matching index, not necessarily the first; keep searching left after a hit for the first occurrence.

A variation. Binary search on the answer: when a problem asks for the smallest value satisfying a monotone condition, binary-search the candidate range and test each candidate with a linear scan. The candidate space is a virtual sorted list.

29.8 Quicksort

The problem. Sort a list in place, ascending, fast on typical inputs, without allocating a second array.

Picture this. Pick a pivot, partition the rest into smaller and larger, place the pivot between them, then recurse on each side. The pivot never moves again.

Brute force, then better. Repeated selection is Θ(n^2). Partitioning places one element permanently and divides the work; balanced splits give log n levels of n work, or Θ(n log n).

    i64 partition(Vec<i32>* v, i64 lo, i64 hi) {
        // take the last element as the pivot
        i32 pivot = v->at((usize)hi);
        // i marks the end of the "smaller than pivot" region
        i64 i = lo - 1;
        for (i64 j = lo; j < hi; j += 1) {
            // grow the small region whenever a small element appears
            if (v->at((usize)j) <= pivot) {
                i += 1;
                swapAt(v, i, j);
            }
        }
        // the pivot's final home is just past the small region
        swapAt(v, i + 1, hi);
        return i + 1;
    }

    void quickSortRange(Vec<i32>* v, i64 lo, i64 hi) {
        // base case: a range of length 0 or 1 is already sorted
        if (lo >= hi) return;
        // place one pivot, then sort the two independent sides
        i64 p = partition(v, lo, hi);
        quickSortRange(v, lo, p - 1);
        quickSortRange(v, p + 1, hi);
    }

    void quickSort(Vec<i32>* v) {
        // sort the whole array; empty gives hi = -1 and returns at once
        quickSortRange(v, 0, (i64)v->count() - 1);
    }

    void swapAt(Vec<i32>* v, i64 a, i64 b) {
        // classic three-step exchange through a temporary
        i32 tmp = v->at((usize)a);
        v->set((usize)a, v->at((usize)b));
        v->set((usize)b, tmp);
    }

`partition` takes the last element as pivot and walks `j` across the range, keeping everything at or below index `i` smaller than the pivot. Each small element advances `i` and is swapped into the small region; the pivot then swaps to `i + 1` and returns that index. `quickSortRange` recurses on the two independent sides.

Time and space. Average and best are Θ(n log n); worst is Θ(n^2) when the pivot is always the smallest or largest, exactly what a last-element pivot does to sorted or reverse-sorted input. Recursion uses O(log n) average and O(n) worst space. The library's `partitionI32` uses median-of-three to avoid the bad case.

Edge cases. Empty or single-element ranges return via `lo >= hi`. With `<=`, all-equal input makes every element join the small region and produces the lopsided worst case; randomising the pivot or median-of-three fixes it. Quicksort is not stable, which is why mergesort is preferred when ties must keep input order.

A variation. For small ranges, switch to insertion sort (say below 16 elements) and stop recursing; one final insertion-sort pass finishes the nearly sorted array in linear time. Real library sorts do this.

29.9 Mergesort

The problem. Sort ascending in guaranteed Θ(n log n) time in every case, stably.

Picture this. Merging two sorted piles takes the smaller front repeatedly, which is linear. Split the unsorted pile in half, sort each half, and merge: log n levels of linear work.

Brute force, then better. Selection sort is Θ(n^2). Mergesort always splits at the midpoint, so it beats that in the worst case too, at the price of a second array.

    void merge(Vec<i32>* v, Vec<i32>* scratch, i64 lo, i64 mid, i64 hi) {
        // i walks the left run, j the right run, k the merged output
        i64 i = lo;
        i64 j = mid + 1;
        i64 k = lo;
        // two-cards-at-a-time: take the smaller front from each run
        while (i <= mid && j <= hi) {
            if (v->at((usize)i) <= v->at((usize)j)) {
                scratch->set((usize)k, v->at((usize)i));
                i += 1;
            } else {
                scratch->set((usize)k, v->at((usize)j));
                j += 1;
            }
            k += 1;
        }
        // one run is exhausted; copy whatever remains of the other
        while (i <= mid) { scratch->set((usize)k, v->at((usize)i)); i += 1; k += 1; }
        while (j <= hi)  { scratch->set((usize)k, v->at((usize)j)); j += 1; k += 1; }
        // copy the merged run back into the original
        for (i64 t = lo; t <= hi; t += 1) {
            v->set((usize)t, scratch->at((usize)t));
        }
    }

    void mergeSortRange(Vec<i32>* v, Vec<i32>* scratch, i64 lo, i64 hi) {
        // base case: zero or one element is already sorted
        if (hi - lo <= 0) return;
        // always split at the midpoint, so there is no bad case
        i64 mid = lo + (hi - lo) / 2;
        mergeSortRange(v, scratch, lo, mid);
        mergeSortRange(v, scratch, mid + 1, hi);
        // merge the two now-sorted halves
        merge(v, scratch, lo, mid, hi);
    }

    void mergeSort(Vec<i32>* v) {
        usize n = v->count();
        // one scratch buffer reused by every merge, keeping space O(n)
        Vec<i32> scratch = Vec<i32>::withCap(n);
        for (usize t = 0; t < n; t += 1) {
            scratch.push(0);
        }
        mergeSortRange(v, &scratch, 0, (i64)n - 1);
    }

`mergeSortRange` splits at the midpoint, sorts each half, and merges. `merge` takes the smaller front while both runs remain, then copies the rest. One `scratch` vector is reused, keeping auxiliary space O(n) rather than O(n log n). The `<=` comparison makes the sort stable: ties take the left run first.

Time and space. There are log n levels, each merging every element once, so Θ(n log n) in all cases, with no pathological input. Space is O(n) for `scratch` plus O(log n) recursion. Mergesort is the safe sort: slightly slower in memory than quicksort, but stable with no bad cases.

Edge cases. An empty list allocates a zero-length scratch and returns; a single element does nothing. Stability keeps equal scores in their original name order, which quicksort does not promise.

A variation. Mergesort is the canonical external sort: sort chunks that fit in memory, write them to disk, then merge the sorted chunks. The merge streams, needing only a few elements of each run in memory.

29.10 Heapsort

The problem. Sort in place in guaranteed Θ(n log n) time with no auxiliary array.

Picture this. Arrange the numbers as a max-heap, where every parent exceeds its children. The maximum is at the top; swap it to the end, shrink the heap, and restore the property. Each removal and re-heap costs logarithmic time.

Brute force, then better. Repeatedly scanning for the maximum is Θ(n^2). A heap keeps the maximum available with a logarithmic sift-down, stored directly in the array with no extra memory.

    void siftDown(Vec<i32>* v, i64 n, i64 i) {
        // repeatedly push the current node down toward the bottom
        while (true) {
            i64 largest = i;
            // children of i live at 2i+1 and 2i+2 in the array
            i64 l = 2 * i + 1;
            i64 r = 2 * i + 2;
            if (l < n && v->at((usize)l) > v->at((usize)largest)) largest = l;
            if (r < n && v->at((usize)r) > v->at((usize)largest)) largest = r;
            // the heap property holds here, stop
            if (largest == i) break;
            // otherwise swap with the larger child and continue below
            swapAt(v, i, largest);
            i = largest;
        }
    }

    void heapSort(Vec<i32>* v) {
        i64 n = (i64)v->count();
        // build a max-heap in place, sifting from the last internal node
        for (i64 i = n / 2 - 1; i >= 0; i -= 1) {
            siftDown(v, n, i);
        }
        // repeatedly move the maximum to the end and shrink the heap
        for (i64 end = n - 1; end > 0; end -= 1) {
            swapAt(v, 0, end);
            siftDown(v, end, 0);
        }
    }

An array heap needs no pointers: children of index i are at 2i+1 and 2i+2, and the parent is at (i−1)/2. `siftDown` swaps with the larger child until the heap property holds or it reaches the bottom. The first loop builds a max-heap from the last internal node up; the second swaps the top to the end and sifts down over the shrinking heap.

Time and space. Building the heap is O(n); n removals at O(log n) each give Θ(n log n) in all cases. Space is O(1), which distinguishes it from mergesort. Its cache-unfriendly accesses make it slower than tuned quicksort in practice, but its worst case is the good case.

Edge cases. An empty list has `n / 2 - 1 = -1`, so neither loop runs; a single element is untouched. Heapsort is not stable. The `l < n` and `r < n` checks are essential to avoid reading past the array.

A variation. Reversing the comparison gives a min-heap, which is how `PriorityQueue` in `std::collections` is built. A priority queue supports push and pop-the-minimum; heapsort is push everything, then pop everything.

29.11 Counting Sort: When You Can Beat n log n

The problem. Sort integers known to lie between 0 and a maximum k not much larger than n.

Picture this. For survey answers from 1 to 5, make five boxes and drop each response into its box, then read the boxes in order. No comparisons are made.

Brute force, then better. Any comparison sort needs Ω(n log n) comparisons. Counting sort sidesteps that by counting occurrences and writing values out in order; when k is close to n, it beats every comparison sort.

    void countingSort(Vec<i32>* v, i32 maxValue) {
        // one counter slot per possible value in 0..maxValue
        usize k = (usize)maxValue + 1;
        Vec<i32> count = Vec<i32>::withCap(k);
        for (usize i = 0; i < k; i += 1) {
            count.push(0);
        }
        // tally how often each value appears: no comparisons at all
        for (usize i = 0; i < v->count(); i += 1) {
            i32 value = v->at(i);
            count.set((usize)value, count.at((usize)value) + 1);
        }
        // emit the values in increasing order of value
        usize out = 0;
        for (usize value = 0; value < k; value += 1) {
            i32 howMany = count.at(value);
            for (i32 r = 0; r < howMany; r += 1) {
                v->set(out, (i32)value);
                out += 1;
            }
        }
    }

`count[value]` ends up holding the number of copies of `value`; the second loop writes each value that many times. Ordering comes from the loop direction, not from comparisons.

Time and space. Time is Θ(n + k), one pass to count and one over the value range to emit; when k is O(n), this is Θ(n), better than the comparison lower bound. Space is Θ(k), so a huge value range makes it a poor choice, as does non-integer data.

Edge cases. Negative values need an offset from the minimum. `maxValue` must be the true maximum, or elements above it write past `count`. An empty list does nothing. When k is much larger than n, avoid counting sort.

A variation. Radix sort sorts one digit at a time with a stable counting sort, from least to most significant, in Θ(d · (n + b)) for d digits in base b. Each pass must preserve the previous pass's order, so stability is essential.

29.12 Choosing a Sort

The five sorts side by side:

    algorithm      best        average      worst        space     stable
    ----------------------------------------------------------------------
    quicksort      n log n     n log n      n^2          log n     no
    mergesort      n log n     n log n      n log n      n         yes
    heapsort       n log n     n log n      n log n      1         no
    counting sort  n + k       n + k        n + k        k         yes
    insertion      n           n^2          n^2          1         yes

Choose mergesort for a guaranteed worst case plus stability; quicksort for in-place speed with a median-of-three or randomised pivot; heapsort for a guaranteed worst case with minimal memory; counting sort for small integer keys; insertion sort for tiny lists.

The Ω(n log n) lower bound applies to all comparison sorts; only counting sort escapes it, by exploiting a small key range. The right question is what you know about the data: size, key range, ties, and memory.

29.13 Binary Search on the Answer

The problem. Packages must ship in order within `days` days, each day carrying a contiguous run. Find the smallest ship capacity that finishes on time.

Picture this. Choose a truck size. If capacity C works, every larger capacity works, so "enough" flips from no to yes once; binary search finds that boundary.

Brute force, then better. Testing every capacity from the heaviest package to the total weight costs O(total × n). Binary search needs only O(log(total)) tests, each a linear feasibility check.

    import(lib) std::vec { Vec };

    bool canShip(Vec<i32>* weights, i64 capacity, i32 days) {
        // greedy fill: always load as many packages as fit today
        i32 used = 1;
        i64 load = 0;
        for (usize i = 0; i < weights->count(); i += 1) {
            i64 w = (i64)weights->at(i);
            // the constraint: the next package must not overflow today's load
            if (load + w > capacity) {
                used += 1;             // this package does not fit today
                load = 0;
            }
            load += w;
        }
        // the predicate: did that greedy fill finish within the days allowed?
        return used <= days;
    }

    i64 shipWithinDays(Vec<i32>* weights, i32 days) {
        // seed the search bounds from the problem itself
        i64 lo = 0;
        i64 hi = 0;
        for (usize i = 0; i < weights->count(); i += 1) {
            i64 w = (i64)weights->at(i);
            if (w > lo) lo = w;        // the heaviest package sets the floor
            hi += w;                   // everything in one day sets the ceiling
        }
        // binary-search the smallest capacity that satisfies the predicate
        while (lo < hi) {
            i64 mid = lo + (hi - lo) / 2;
            if (canShip(weights, mid, days)) {
                hi = mid;              // mid works; try to do better
            } else {
                lo = mid + 1;          // mid fails; the answer is larger
            }
        }
        // lo is the first capacity that satisfies the predicate
        return lo;
    }

`canShip` greedily loads as many packages as fit each day, which is correct because order is fixed and capacity is the only limit. The search is binary search over a virtual array of capacities; `lo < hi` with `hi = mid` and `lo = mid + 1` finds the first capacity satisfying the predicate.

Time and space. O(n) per check and O(log(total)) checks give O(n log(total)) time and O(1) extra space. The predicate must be monotone, or halving is meaningless.

Edge cases. One package makes floor and ceiling equal its weight. If `days` is at least the package count, the answer is the heaviest package; if `days` is 1, it is the total weight. Seeding bounds from the problem is safest.

A variation. Any "smallest value satisfying a monotone condition" problem fits: slowest speed, smallest divisor, smallest radius. Write the predicate, prove monotonicity, and binary-search.

29.14 Search in a Rotated Sorted Array

The problem. A sorted array rotated at a pivot, such as [4,5,6,7,0,1,2], must be searched in logarithmic time, returning the index or −1.

Picture this. A rotated phone book still has one sorted half after any cut. If the key lies in that half, search it; otherwise search the other.

Brute force, then better. A linear scan is O(n). Keep binary search and add one test per step to identify the sorted half, so the halving survives.

    i64 searchRotated(Vec<i32>* v, i32 key) {
        // standard inclusive binary-search window
        i64 lo = 0;
        i64 hi = (i64)v->count() - 1;
        while (lo <= hi) {
            i64 mid = lo + (hi - lo) / 2;
            i32 val = v->at((usize)mid);
            if (val == key) return mid;
            // at least one of the two halves is sorted; find it
            if (val >= v->at((usize)lo)) {         // left half is sorted
                if (key >= v->at((usize)lo) && key < val) {
                    hi = mid - 1;
                } else {
                    lo = mid + 1;
                }
            // the right half must be the sorted one; mirrored test
            } else {                               // right half is sorted
                if (key > val && key <= v->at((usize)hi)) {
                    lo = mid + 1;
                } else {
                    hi = mid - 1;
                }
            }
        }
        // the window is empty, so the key is absent
        return -1;
    }

If `val >= v->at(lo)`, the left segment is sorted, and the key either lies inside it or in the right half. Otherwise the right segment is sorted, and the mirrored test applies. Each iteration discards half the window.

Time and space. O(log n) time and O(1) space. The reasoning assumes distinct values; duplicates can make the pivot test ambiguous and degrade the worst case to O(n).

Edge cases. An empty array gives `hi = -1` and returns −1. A single element is compared directly. An unrotated array takes the sorted-left branch as ordinary binary search would. Inclusive comparisons cover keys at endpoints.

A variation. To find the minimum, compare the middle with the right end: if the middle is greater, the minimum is to the right; otherwise search left including the middle.

29.15 First and Last Position

The problem. In a sorted array, return the first and last index of a key, or [−1, −1] if absent. Many copies may exist.

Picture this. The equal values form one contiguous block. Find the first position whose value is at least the key, and the first whose value is greater; those are the block's start and one past its end.

Brute force, then better. A linear scan is O(n). Binary search must keep searching after a match: one variant finds the leftmost valid position, the other the rightmost.

    struct Range {
        i64 first;
        i64 last;
    }

    i64 lowerBound(Vec<i32>* v, i32 key) {
        // half-open window [lo, hi)
        i64 lo = 0;
        i64 hi = (i64)v->count();
        // find the first index whose value is not less than the key
        while (lo < hi) {
            i64 mid = lo + (hi - lo) / 2;
            if (v->at((usize)mid) < key) lo = mid + 1;
            else hi = mid;
        }
        return lo;
    }

    i64 upperBound(Vec<i32>* v, i32 key) {
        // half-open window [lo, hi)
        i64 lo = 0;
        i64 hi = (i64)v->count();
        // find the first index whose value is greater than the key
        while (lo < hi) {
            i64 mid = lo + (hi - lo) / 2;
            if (v->at((usize)mid) <= key) lo = mid + 1;
            else hi = mid;
        }
        return lo;
    }

    Range searchRange(Vec<i32>* v, i32 key) {
        // the equal run is [lowerBound, upperBound)
        i64 first = lowerBound(v, key);
        i64 last = upperBound(v, key) - 1;
        // first pointing past the end or at a larger value means absent
        if (first == (i64)v->count() || v->at((usize)first) != key) {
            return Range { .first = -1, .last = -1 };
        }
        return Range { .first = first, .last = last };
    }

Both helpers use a half-open window `[lo, hi)`, so "not found" naturally becomes `count`. `lowerBound` returns the first value not less than the key; `upperBound` the first value greater. The run `[lowerBound, upperBound)` is exactly the equal values. One existence test separates a real match from the next larger value.

Time and space. Each bound is O(log n) time and O(1) space, so the pair is O(log n). The library's `binarySearchBy` returns an index or −1 and cannot report an insertion point.

Edge cases. An absent key gives `first == count` or a larger value at `first`, both returning [−1, −1]. A key smaller than everything gives `first = 0` and `last = -1`, caught before indexing. A single occurrence gives `first == last`; an empty array returns before touching it.

A variation. `upperBound - lowerBound` counts copies, and `lowerBound` gives the insertion point. Reach for these instead of hand-rolled loops.

29.16 Quickselect: the Kth Largest Element

The problem. Return the kth largest element of an unsorted array without fully sorting it. For [3,2,1,5,6,4] and k = 2, the answer is 5.

Picture this. Find the second tallest person without ordering anyone else. Partition around a pivot; if it lands at the target slot, stop, otherwise keep only the side containing that slot.

Brute force, then better. Sorting costs O(n log n) and computes an unused ordering. Quickselect partitions and keeps one side, with expected work n + n/2 + n/4 + ... = O(n).

    void swapAt(Vec<i32>* v, i64 a, i64 b) {
        i32 tmp = v->at((usize)a);
        v->set((usize)a, v->at((usize)b));
        v->set((usize)b, tmp);
    }

    i64 partitionAt(Vec<i32>* v, i64 lo, i64 hi) {
        // last element is the pivot, as in quicksort
        i32 pivot = v->at((usize)hi);
        i64 i = lo - 1;
        for (i64 j = lo; j < hi; j += 1) {
            // compared with >= so larger values gather on the left
            if (v->at((usize)j) >= pivot) {        // descending: big values first
                i += 1;
                swapAt(v, i, j);
            }
        }
        swapAt(v, i + 1, hi);
        return i + 1;
    }

    i32 findKthLargest(Vec<i32>* v, i32 k) {
        // work in descending order, so the kth largest sits at slot k-1
        i64 target = (i64)k - 1;                   // 0-based slot of the kth largest
        i64 lo = 0;
        i64 hi = (i64)v->count() - 1;
        // partition, then keep only the side that contains the target slot
        while (lo < hi) {
            i64 p = partitionAt(v, lo, hi);
            if (p == target) return v->at((usize)p);
            // narrow to the side that holds the target slot
            if (p < target) lo = p + 1;            // answer is to the right
            else hi = p - 1;                       // answer is to the left
        }
        return v->at((usize)lo);
    }

This is quicksort's partition with the comparison flipped: `>=` gathers larger values on the left, so the kth largest lands at index k − 1. Instead of recursing into both sides, quickselect discards the side without the target.

Time and space. Expected O(n), worst O(n^2) when the pivot is extreme, made unlikely by randomisation or median-of-three. This iterative version uses O(1) extra space; recursion would use O(log n).

Edge cases. k = 1 finds the maximum, k = n the minimum. A single element returns without partitioning. An empty array violates the contract (the caller must ensure 1 ≤ k ≤ n). Duplicates are handled but can force lopsided partitions.

A variation. The same partition answers "the k smallest" (use `<=` and index k − 1) and "the median" (k = n/2). Selection is cheaper than sorting when only one order statistic is wanted.

29.17 Insertion Sort, and Why Real Libraries Use It

The problem. Sort by inserting each element into the already-sorted prefix on its left, as when sorting a hand of cards.

Picture this. Your left hand holds sorted cards; each new card slides left past every larger card until it lands in place.

Brute force, then better. Insertion sort is the brute-force O(n^2) sort, but it is O(n) on nearly sorted input, stable, and has a tight inner loop, which is why production sorts use it for small ranges.

    void insertionSort(Vec<i32>* v) {
        // grow the sorted prefix one element at a time
        for (usize i = 1; i < v->count(); i += 1) {
            i32 key = v->at(i);
            i64 j = (i64)i - 1;
            // slide larger elements right to open a gap for key
            while (j >= 0 && v->at((usize)j) > key) {
                v->set((usize)(j + 1), v->at((usize)j));
                j -= 1;
            }
            // drop key into the gap that opened
            v->set((usize)(j + 1), key);
        }
    }

The outer loop grows the sorted prefix by one. The inner loop shifts larger elements right and drops `key` into the gap. The strict `>` keeps equal elements in their original order, so the sort is stable.

Time and space. Best case O(n) on sorted input; worst and average O(n^2); space O(1). Its best case and constant factor are what make it worth remembering.

Edge cases. Empty or single-element lists do no work. Reverse-sorted input is the worst case. Stability makes it safe for small ranges inside a larger sort.

A variation. On a linked list, insertion into the sorted prefix is a pointer relink rather than a shift, so insertion sort fits naturally.

29.18 Sorting with a Stable Custom Comparator

The problem. Sort records by one field while preserving the input order of records that tie on that field.

Picture this. A careful clerk writes each form's original position in a corner and breaks age ties by that position, so ties come out as they went in.

Brute force, then better. Make the original position an explicit tie-break key. The array's `sortBy` is an unstable median-of-three quicksort, so decorate each record with its index and compare that when the primary keys tie.

    struct Person {
        str name;
        i32 age;
    }

    struct Keyed {
        Person person;
        usize pos;
    }

    bool byAgeThenOrder(Keyed a, Keyed b) {
        // primary key first; only a tie on age consults the position
        if (a.person.age != b.person.age) return a.person.age < b.person.age;
        // distinct positions give a total order, so stability is enforced
        return a.pos < b.pos;
    }

    void sortByAgeStable(Vec<Person>* people) {
        // decorate each person with its original position
        Vec<Keyed> keyed = Vec<Keyed>::new();
        for (usize i = 0; i < people->count(); i += 1) {
            keyed.push(Keyed { .person = people->at(i), .pos = i });
        }
        // the unstable sort now has no genuine ties left to break
        keyed.sortBy(byAgeThenOrder);
        // strip the decoration, copying the sorted records back
        for (usize i = 0; i < keyed.count(); i += 1) {
            people->set(i, keyed.at(i).person);
        }
    }

The comparator returns true only when `a` must come strictly before `b`. Ages come first, and only a tie consults the distinct positions, so the order is total and the unstable sort has no arbitrary choice left. Decorating copies each `Person`, and restoring writes it back.

Time and space. Decorating and restoring are O(n), and the sort is O(n log n) average, so O(n log n) total with an O(n) auxiliary vector. A truly stable mergesort avoids the vector but must thread the comparator through its merge.

Edge cases. Using `<=` for equal elements violates strict weak ordering and can break the sort; the primary test must be strict (`<`). An empty or single-element roster is unchanged. The tie-break is unnecessary when the primary key is unique but harmless.

A variation. For true stability with control over memory, write the mergesort of 29.9 with a custom `less` predicate threaded through the merge, taking the left run on a tie. That is stability by construction.
