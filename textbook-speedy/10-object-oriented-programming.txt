Chapter10

Object-Oriented Programming

Objects Without Classes

Object-oriented programming organises a program around objects: bundles of data and the operations on them, gathered into types and related by inheritance.

Class languages add `class`, constructors, destructors, inheritance, `virtual` and `override`, and `public`, `private`, and `protected`.

Coral has none of that: no `class` keyword, no inheritance, no virtual methods, no overriding, no abstract or sealed classes, and no access modifiers.

The model remains, built from pieces already seen: the struct bundles data with behaviour, the method binds behaviour to a type, the trait is the interface, and `any Trait` requests a runtime decision. Where a class language asks for a constructor, destructor, or inheritance, Coral answers with the factory, the scope, and composition.

10.1 The Question of Objects

Object orientation serves a recurring shape: values that belong together plus the operations on them. A point has x and y; a vector has a buffer and a length; a file has a handle. Keeping them together saves the reader from carrying two pieces of knowledge.

Object orientation makes the type the unit that holds both, and Coral keeps that productive idea. What Coral declines is the set of relationships class languages add on top: inheritance, overriding, and access control.

The map: class becomes struct, instance becomes a value, constructor becomes a static factory, destructor becomes the scope plus `@drop`, inheritance becomes composition, the interface becomes the trait, virtual dispatch becomes `any Trait` or a function pointer, and encapsulation becomes the type plus `pub`.

10.2 Structs Are the Class

A class is a blueprint describing the fields and methods of its instances. Coral's blueprint is the struct, and a value of a struct type is the instance.

The standard library's vector, quoted from `std::vec`:

    pub struct Vec<T> {
        T*    data;
        usize len;
        usize cap;
    }

The struct declares the data. `Vec<i32>` is the type, and a particular vector with three elements, capacity four, and a heap buffer is a value of it. The five-vector and the thousand-vector are two instances carrying their own `data`, `len`, and `cap`.

Behaviour lives in an extend block beside the declaration:

    pub extend<T> Vec<T> {
        static Vec<T> new() {
            return Vec<T> { .data = null, .len = 0, .cap = 0 };
        }

        void push(T val) {
            if (self.len >= self.cap) {
                usize newCap = self.cap > 0 ? self.cap * 2 : 4;
                self.reserve(newCap);
            }
            self.data[self.len] = val;
            self.len += 1;
        }
    }

The struct and extend block are one type to the reader but two declarations to the compiler. Because they are separate, an extend block can add behaviour to any visible type, even one from another module. That is what makes traits and dynamic dispatch possible, since a conformance is an extend block naming a trait.

`pub` makes the struct and extend block visible outside the module; without it they are private to the file. A type that must not be extended says so with `#[[no_extend]]`:

    #[[no_extend]]
    struct SecurityToken {
        u64 secret;
        i64 expiry;
    }

Most types stay open, so sealing requires an annotation.

10.3 Value Semantics and Reference Semantics

A reference type is shared: two variables can name the same object. A value type is copied: each variable holds its own value. In class languages a class is usually a reference type; in Coral the struct is a value, and there is no reference type.

A struct variable holds the struct's fields. Assignment copies them, passing to a function passes them, and returning moves them out. There is no hidden address, no managed identity, and no aliasing you did not write. Two `Point` values with the same x and y are the same point.

A struct variable is a box of pieces, not a pointer to a shared box. A pointer (`T*`) is an address two people can share, and Coral makes you write the pointer when you want that sharing.

    struct Point { f64 x; f64 y; }
    Point a = Point { .x = 1.0, .y = 2.0 };
    Point b = a;          // b gets its own copy of the two fields
    b.x = 9.0;
    println("{} {}", a.x, b.x);   // 1.0 9.0, a is untouched

Two `Point` variables, two independent boxes. Nothing can make `a` change when `b` does.

When a struct owns a resource such as a heap buffer or a file handle, copying its fields would leave two variables freeing one resource. Coral moves instead: `Vec<u32> b = a;` copies the fields, and the compiler cancels `a`'s cleanup, leaving one owner.

Value semantics and moves are two sides of the same idea: a struct is its fields, and ownership is handed over rather than shared. To share on purpose, write it down with a pointer or a counted smart pointer:

    Vec<u32> source = Vec<u32>::withCap(16);
    Vec<u32>* shared = &source;          // an explicit reference, no copy
    shared->push(7);                     // the original sees the change

    SharedPtr<Config> config = ...;      // several holders, one count
    SharedPtr<Config> alias;
    alias.ptr = config.ptr;              // sharing, written by hand
    alias.rc  = config.rc;
    alias.rc->count += 1;

Coral does not lack references; the reference is a type you write (`T*`, `SharedPtr<T>`) instead of a default you inherit. A value parameter is a copy or a move, a pointer parameter is a reference, and the signature says which.

A struct value is a box you own; a pointer is a shared address you chose to write down. Sharing happens only when a `*` appears in the type.

10.4 Methods and the Receiver

A method is a function bound to a type, whose receiver is a value of that type. This section fixes the vocabulary and the two spellings.

The receiver is the value the method was called on. In `c.bump()`, `c` is the receiver, and inside `bump` it is named `self`. A method call is a function call with the receiver as its first argument.

The receiver is supplied by Coral, not written in the parameter list, and the call site names it with a dot:

    pub extend Counter {
        void bump() {
            self.value += 1;
        }

        #[[const]]
        i32 current() {
            return self.value;
        }
    }

`bump` mutates the receiver through `self`; `current` promises not to, and the `#[[const]]` attribute is the promise. A const method that assigns to `self` is an error, and a const method can be called on a read-only value where a mutating one cannot.

A method belonging to the type rather than a value is `static`, and it has no `self`:

    pub extend Counter {
        static Counter start() {
            return Counter { .value = 0 };
        }
    }

Statics are called on the type with `::`; instance methods are called on a value with `.`. The distinction between a type and a value is visible at every call site.

If the thing on the left is a type name, use `::`; if it is a value, use `.`. `Counter::start()` makes a new counter; `c.bump()` changes an existing one.

The receiver is always implicit: there is no `self` parameter and no pointer spelling to declare. A static method has no receiver. To mark an instance method read-only, use `#[[const]]`; the compiler flags any mutation through `self`.

10.5 Encapsulation and Information Hiding

Encapsulation bundles data with its operations and controls how the data is reached. Coral has no `public`, `private`, or `protected`: a field is reachable by any code that can name its type. Coral controls visibility between modules with one switch, `pub` or not.

Coral hides implementation with the type rather than the field. An opaque type hides its storage behind a layout with no meaning to the reader. A distinct type hides its representation behind a name:

    pub distinct File = i32;

A `File` is an `i32` under the hood, but the type system will not let you use one where the other is expected. The representation is hidden by the type and checked by the compiler. When a type's fields really are its interface, as with `Vec`, the library leaves them public on purpose.

The library adds a convention: a leading underscore marks a name internal, as in `_ensure`, `_grow`, `_normalize`, and `_sortByRange`. Nothing enforces it; the library honours it. Encapsulation is therefore structural: a field is hidden when the type makes it meaningless, marked internal when it is the library's business, and otherwise open.

10.6 Constructors

A constructor brings an object into existence and leaves it in a valid state. It matters because of the invariant, a property the type promises always to hold, such as a vector's length never exceeding its capacity. An object built wrong fails later in a method that trusted the invariant.

Coral's only constructor is the static factory. A static method fills the fields and returns the value, and the library's constructors all declare the variable, set every field, and return it.

    pub extend<T> Vec<T> {
        static Vec<T> withCap(usize capacity) {
            return Vec<T> {
                .data = alloc<T>(capacity),
                .len  = 0,
                .cap  = capacity
            };
        }
    }

Because `cap` is the size actually allocated and `len` is zero, the rule that length never exceeds capacity holds from the first instant. The constructor is setup code, named and visible.

Factories are called on the type with `::`: `Vec<i32>::new()`, `Vec<i32>::withCap(1024)`, `Duration::fromSecs(seconds)`, `str::fromCstr(cstr)`. There is no constructor keyword and no overloading; `new` and `withCap` are two constructors named for what they do.

There are no copy or move constructors. A copy is a struct assignment that copies the fields; a move is the same assignment on an owning type. For a deep copy, the type provides a method such as `String::clone`, and the caller writes its name, so no copy happens behind a `=`.

10.7 Destructors and Deterministic Cleanup

A destructor releases what an object held when its life ends. Coral's answer is the scope, in three forms.

The first is the ordinary cleanup method, which the library's owning types call `dispose`:

    pub extend<T> Vec<T> {
        void dispose() {
            dealloc<T>(self.data);
            self.data = null;
            self.len  = 0;
            self.cap  = 0;
        }
    }

The release happens when `dispose` is called, at a line you can point at.

`defer` promises cleanup on every exit from a block, including an early return, and keeps the cleanup next to the acquisition.

The second form is `defer`, which binds a cleanup to a block and guarantees it on every exit:

    void process(File f) {
        defer fileClose(f);
        // ... read the file ...
        // fileClose(f) runs here, on every path out, including an early return
    }

The third form is the compiler-provided `@drop` trait. A conforming type gets its cleanup emitted automatically at the end of every scope where a value dies, once, on every exit path, in reverse order of declaration, like the `defer` statements of the same scope:

    pub extend<T> SmartPtr<T> : @drop {
        void drop() {
            self.dispose();
        }
    }

With this conformance, every `SmartPtr<T>` local is released at its closing brace with no release written.

Most standard library files free by hand and disable automatic cleanup for the whole file with `#[[no_drop_all]]`, which keeps compile times down because every program compiles the library. Application files get automatic release. Never call `drop()` yourself; E1301 forbids it because the scope will also call it. To release early, call the ordinary cleanup method or scope the value.

If a value conforms to `@drop`, the scope fires its `drop` on exit; a hand-written `drop()` call is E1301 because it would release twice. Call `dispose` to release early; otherwise let the scope do it once.

10.8 Inheritance and Its Absence

Inheritance defines one type as an extension of another: the subclass gets the base's members and adds its own. It drags in single and multiple inheritance, mixins, abstract and sealed classes, overriding, virtual methods, the diamond problem, virtual inheritance, and linearisation.

Coral has none of it by design. There is no subtyping: a type is exactly what it is, and no value of one type stands in for another. That empties the list: no inheritance, mixins, classes, overriding, base method, diamond, or hierarchy to linearise. The machinery has no subject.

Composition builds a type from other types, and traits promise operations. Where the class world says a Circle is a Shape, Coral says a Circle has these fields and keeps the Shape promise. Has-a and promise cover what inheritance was for.

10.9 Composition and Delegation

Composition builds a type by containing other types: where inheritance says is-a, composition says has-a. The containing type holds the contained one as a field and builds its behaviour from it. In Coral composition is the only option, and the library proves it is enough.

Delegation is composition in action: a type contains another and forwards operations to it. The library's queue is the cleanest example, a double-ended queue with the far door removed.

    pub struct Queue<T> {
        Deque<T> inner;
    }

    pub extend<T> Queue<T> {
        static Queue<T> new() {
            return Queue<T> { .inner = Deque<T>::new() };
        }

        void enqueue(T val)   { self.inner.pushBack(val); }
        T dequeue()           { return self.inner.popFront(); }
        T peek()              { return self.inner.front(); }
        usize count() const   { return self.inner.count(); }
        bool isEmpty() const  { return self.inner.isEmpty(); }
        void dispose()        { self.inner.dispose(); }
    }

Every operation forwards: `enqueue` is `pushBack`, `dequeue` is `popFront`, and the queue's behaviour is the deque's with fewer doors. The queue reuses the deque's logic, so a fix or speedup in the deque reaches the queue for free.

Inheritance says a queue is a kind of deque; composition says a queue has a deque. The second is truer, because a queue is not interchangeable with a general deque but a deque with a narrower promise. Holding one as a field keeps the queue's own interface and lets the deque change underneath.

A decorator is delegation with behaviour added at the seam. A logging queue wraps a queue, forwards the core operations, and adds an extra:

    pub struct LoggingQueue<T> {
        Queue<T> inner;
    }

    pub extend<T> LoggingQueue<T> {
        void enqueue(T val) {
            println("enqueue");
            self.inner.enqueue(val);
        }

        T dequeue() {
            T v = self.inner.dequeue();
            println("dequeue");
            return v;
        }
    }

`LoggingQueue` is a queue by interface and a wrapper by construction, and the pattern works for any seam you want to observe. The library composes further: the set is a hash map with a restricted interface, and the cache is a map and a list working together. The containing type is built from what it holds, not descended from it.

10.10 Traits as Interfaces

The interface is the trait, covered fully in Chapter6. This chapter gives the object-oriented framing, because the trait replaces the interface and much of inheritance.

A trait is a job description: it lists what a type must be able to do, `area`, `perimeter`, `name`, without saying how. Each type writes its answers in an extend block, and the compiler checks that every duty was filled.

A drawing program that holds a list of shapes and reports the largest area would otherwise inspect each shape's kind and switch, and every new kind would mean editing the measuring code. The trait declares the operations once, and the measuring code is written against them:

    trait Shape {
        f64 area() const;
        f64 perimeter() const;
        str name() const;
    }

    pub extend Circle : Shape {
        f64 area() const      { return 3.14159 * self.radius * self.radius; }
        f64 perimeter() const { return 2.0 * 3.14159 * self.radius; }
        str name() const      { return "circle"; }
    }

The colon reads satisfies: `Circle : Shape` means Circle keeps the Shape promise. Circle stays exactly Circle and merely implements the three methods. Conformance is nominal and checked method by method: a missing method is E1203, a wrong signature is E1202, at the conformance site.

A type may satisfy several traits, one block each, and traits do not form a hierarchy. A type may conform to a given trait only once, so there is exactly one `Shape::area` for Circle; defining it twice is E1201. Shared code is written against the trait, checked at instantiation:

    f64 largestArea<T>(Vec<T> shapes) {
        f64 best = 0.0;
        for (T s : shapes) {
            f64 a = s.area();
            if (a > best) best = a;
        }
        return best;
    }

The body calls `area()` on values of `T` without knowing what `T` is. At instantiation the compiler confirms that `T` has the operation; a type without it fails the build naming the type. The function works for circles, rectangles, and triangles written next week, with no table lookup or runtime cost.

10.11 Dynamic Dispatch: any Trait and Function Pointers

So far every conformance has been static: the concrete type is known and the call resolves to one implementation. When you have a list mixing circles and squares, `any Trait` makes the choice at runtime.

A universal remote holds buttons and controls any television that speaks the standard signal; which television answers is decided when you point it.

    Vec<any Shape> shapes = Vec<any Shape>::new();
    shapes.push(Circle { .radius = 1.0 });
    shapes.push(Square { .side = 2.0 });

    for (any Shape s : shapes) {
        println("{}: area {}", s.name(), s.area());
    }

An `any Shape` is a fat pointer: a reference to the value and a reference to its implementation. `s.area()` dispatches through the second reference, so the call site need not know the concrete type. The costs are an extra indirection, a pointer-sized pair, and no inlining.

The other form of runtime choice is the function pointer, which the collections use. A hash map stores how to hash and compare its keys:

    pub struct HashMap<K, V> {
        usize(K)   hashFn;
        bool(K, K) eqFn;
        // ...
    }

The constructor takes the two functions, and the map calls the stored function when hashing. The ordered map stores a comparison function, `i32(K)`. The behaviour is chosen by value and invoked through the pointer, visible in the field list. Coral shows the pointer and its type, and the compiler checks its shape.

10.12 Polymorphism in Coral

Polymorphism lets one piece of code work with values of many types. Coral has two kinds; the third has no subject.

Parametric polymorphism is the generic: `Vec<T>`, a `HashMap<K, V>`, `largestArea<T>`. Each use instantiates the parameter, and the collections are built on it.

Ad-hoc polymorphism is the same operation meaning different things on different types, such as `area` on a Circle and a Square. Coral's version is the trait, resolved statically at compile time.

Subtype polymorphism, where a subclass value stands in for a base value and dispatch finds the subclass's version, does not exist because Coral has no subtyping. The trait, resolved per type, or `any Trait` when the concrete type is unknown until runtime, serves its purpose. Each kind is checked at compile time and visible in the signature.

10.13 Pattern Matching on Types

The class languages reach pattern matching through the visitor pattern and double dispatch on virtual calls. Coral uses the switch and compile-time comparison.

A switch over a variant dispatches on the shape of a value, and the compiler checks that every case is covered:

    variant Shape {
        Circle    { f64 radius; }
        Rectangle { f64 width; f64 height; }
        Point,
    }

    pub extend Shape {
        f64 area() const {
            switch (self) {
                Shape::Circle { radius }            => { 3.14159 * radius * radius; },
                Shape::Rectangle { width, height }  => { width * height; },
                Shape::Point                        => { 0.0; },
            }
        }
    }

`Shape::Circle { radius }` checks that the value is a circle and binds its radius to a local name. A switch over a variant or enum must be exhaustive or carry an `else`; a missing case is E0608, naming what is missing. Adding a case to a variant is safe, because every switch refuses to compile until it handles the new case.

Given `Shape::Circle { .radius = 2.0 }`, the switch asks each arm in turn: is this a Circle? Yes, so it binds `radius` to `2.0`, computes `3.14159 * 2.0 * 2.0`, and never tries the other arms.

The same dispatch happens on types inside a generic with a `comptime` block. The type parameter is known during the build, so the switch resolves to a single arm and only that arm is generated:

    void render<T>(T value) {
        comptime {
            switch (@typeof(value)) {
                i32  => { printInt(value); },
                f64  => { printFloat(value); },
                else  => { @compileError("render has no case for this type"); },
            }
        }
    }

The switch is decided at build time, and non-matching cases are never generated. `@compileError` lets a generic state a requirement in its own words. A visitor pattern can be built from these pieces: a switch over the variant dispatches by kind, and a function pointer field chosen at construction dispatches the call the way a visitor's vtable would.

10.14 The Object Lifecycle

Every object is created, used, and released. In Coral the stages are the factory, the scope, and the drop.

Construction order is simple because there is no hierarchy: the constructor declares the value, fills the fields in code order, and returns. Destruction order mirrors it: automatic drops run innermost scope first and in reverse order of declaration, exactly like `defer`, so a value that depends on another is torn down first.

Copy and move are the third stage. A plain struct assignment copies fields, and an assignment on an owning type moves the resource by cancelling the source's release. The compiler handles the move; beyond it ownership is the writer's. The factory names the birth, the scope the death, and the assignment says whether the value was copied or handed over.

10.15 Singletons, Pools, and Flyweights

The final patterns manage objects rather than define them.

A singleton permits one instance and gives the whole program one access point; its cost is hidden global state. An object pool keeps prebuilt instances that are borrowed and returned when construction is expensive and churn is high. A flyweight shares a heavy object across many uses, storing shared state once and per-use state with the user.

Coral avoids the singleton idiom because it hides state behind a global accessor, reachable everywhere and accountable to no one. The library keeps a few visible module-level globals, such as the default allocator, accessed through ordinary functions. When a program needs one of something, it creates one value and passes it where needed.

The pool is a real library type. `Pool<T>` holds a region carved into fixed-size blocks linked into a free list, hands a block out on `acquire`, and takes it back on `release`:

    Pool<Node> pool = Pool<Node>::new();
    Node* n = pool.acquire();     // a recycled block, or null if it cannot grow
    // ... use n ...
    pool.release(n);
    pool.dispose();               // return the whole region

Reuse costs two pointer stores instead of an allocator round trip, and the blocks stay in a small, hot region. Chapter11 covers the allocator form.

The flyweight needs no type of its own because Coral's sharing is already explicit: store the pointer and copy the pointer, and the reader sees the sharing.

10.16 A Worked Example: The Shape Library

The pieces assemble into the object model in miniature: a trait for the operations, concrete types, and a client that works through the trait.

The trait states the rules; each concrete shape implements it with its own fields and formulas:

    pub struct Square {
        f64 side;
    }

    pub extend Square : Shape {
        f64 area() const      { return self.side * self.side; }
        f64 perimeter() const { return 4.0 * self.side; }
        str name() const      { return "square"; }
    }

A client that reports on a collection uses the trait object because the collection is heterogeneous:

    pub void report(Vec<any Shape> shapes) {
        for (any Shape s : shapes) {
            println("{}: area {}, perimeter {}", s.name(), s.area(), s.perimeter());
        }
    }

`report` is written once against Shape and runs for circles, squares, or any shape added later. Adding a shape is a new struct and a new conformance; existing code stays unchanged, which is the open-closed idea. `any Shape` is right because the vector mixes concrete types; a generic could report a homogeneous `Vec<T>` but not a mixed one.

This is the shape behind a plugin system, a renderer, or a payment handler: write the walking or drawing code once against the trait, and every new kind is a new type plus a conformance. The cost is the visible runtime indirection of `any Shape`, the same trade a virtual call makes.

If every element is the same type, `Vec<Circle>` plus a generic `report<T>` is faster and checked at compile time; `any` earns its keep only when the elements genuinely differ at runtime.

10.17 The Encapsulation Tradeoff

Encapsulation trades safety against reach. Class languages make members private, forcing the program through the type's methods; the internals are protected, and the cost is going through the interface.

In Coral every field of an ordinary struct is reachable by any code that can name the type, so safety comes from making the internals not worth disturbing. The opaque type hides storage behind a meaningless layout; the distinct type hides its representation behind a name, so `File` and `i32` are not interchangeable; the underscore marks internal methods; `pub` controls module boundaries and nothing else.

The reader pays in discipline: a field is reachable, and whether it should be touched is documented by the declaration, not enforced by a keyword. The reader gains that nothing is hidden and the truth about a value's layout is available to anyone who needs it.

10.18 A Worked Example: The Repository

The repository pattern gathers the model in one place: a trait as the interface, composition for the implementation, and a client written against the trait.

The trait names the operations. `Record` is an ordinary struct with an id and a value, and the repository stores and finds records by id:

    trait Repository {
        Option<Record> findById(u64 id);
        void insert(Record r);
    }

The in-memory implementation composes a `Vec<Record>` and forwards to it:

    pub struct MemoryRepository {
        Vec<Record> records;
    }

    pub extend MemoryRepository : Repository {
        Option<Record> findById(u64 id) {
            for (Record r : self.records) {
                if (r.id == id) return Option<Record>::Some { .value = r };
            }
            return Option<Record>::None;
        }

        void insert(Record r) {
            self.records.push(r);
        }
    }

`findById` returns `Option<Record>` rather than a pointer that might be null, so the caller cannot forget to check. A client written against the trait works for any implementation:

    pub void touch<R>(R repo, u64 id) {
        Option<Record> found = repo.findById(id);
        if (found.isSome()) {
            Record r = found.unwrap();
            r.value += 1;
            repo.insert(r);
        }
    }

`touch` never names `MemoryRepository`; it names the operations the trait declares, and the compiler checks at instantiation that `R` supplies them. Swapping in a database-backed repository is a new struct and a new conformance, with `touch` unchanged. Composition, the trait, and static resolution replace inheritance.

10.19 The OOP Verdict

Coral is not object-oriented in the class sense: no classes, no inheritance, no virtual methods, no overriding, no access modifiers, and no class-style destructor. The `@drop` trait and the scope provide automatic release.

The object model is real: the struct is the class-like type, the method its behaviour, the factory its constructor, the scope and `@drop` its destructor, the trait its interface, and composition its inheritance. Coral keeps data and behaviour in one type, so every relationship is a visible value.

10.20 Chapter10 Summary

Object-oriented programming organises a program around objects, and Coral's object model is the struct, the method, the trait, and composition, with none of the class machinery.

The struct is the class-like type, holding fields and, in an extend block, methods; a value of the type is an instance. `pub` controls visibility across modules, and `#[[no_extend]]` seals a type.

Structs have value semantics: assignment copies fields, and for an owning type it moves the resource. Sharing is written with a pointer or a counted smart pointer, never assumed.

Methods bind through the receiver, implicit as `self` or explicit as a first parameter. Const methods do not mutate; statics are called with `::`; instance methods with `.`.

Coral has no `public`, `private`, or `protected`. Encapsulation is the opaque type, the distinct type, the underscore convention, and `pub`, with the rest a documented interface.

A constructor is a static factory: declare the value, fill every field, return it, called with `::`. It establishes invariants, and there are no copy or move constructors.

A destructor is the scope: release through a cleanup method such as `dispose`, through `defer`, or automatically through `@drop`, once per value in reverse declaration order. Library files opt out with `#[[no_drop_all]]`.

Inheritance does not exist: no subtyping, mixins, abstract or sealed classes, overriding, virtual methods, diamond, or linearisation. Composition replaces is-a with has-a.

Composition and delegation are the model: the queue wraps a deque and forwards, a decorator forwards and adds behaviour, and the set and cache are built from a map and a list.

The trait is the interface: method signatures implemented per type in an extend block, nominal and checked (E1202 and E1203 for a bad or missing method, E1201 for a duplicate). A generic against the trait works for every implementer, resolved statically.

Dynamic dispatch is `any Trait`, a fat pointer carrying the value and its implementation, or a function pointer in a field, as the hash map's hash and equality functions and the ordered map's comparator.

Polymorphism is parametric through generics and ad hoc through traits. There is no subtype polymorphism; the trait and `any Trait` serve its purpose.

Type dispatch is a switch over a variant or enum, checked for exhaustiveness (E0608), and the `comptime` comparison for a generic type parameter, where `@typeof` names the type and `@compileError` rejects an unsupported one.

The lifecycle is explicit: construction follows the factory's code order, destruction reverses declaration order, and copy and move are the two cases of assignment.

There is no singleton idiom; state is passed explicitly, with a few visible module-level globals such as the default allocator. The object pool is `Pool<T>`, and the flyweight is explicit sharing by pointer.

The shape library shows the model whole: a trait, concrete types conforming to it, and a client written against the trait, extended by adding types without touching existing code.

Encapsulation trades barriers for visibility: fields are reachable, and safety comes from opaque and distinct types, the underscore convention, and the documented interface.

The repository pattern shows the model composed: a trait as the interface, a concrete implementation over a vector, and a client written against the trait that works for any implementation.

Coral's object model is the struct, the method, the trait, and composition, assembled from pieces the language already has.

10.21 Exercises

1. Comprehension. Explain the difference between a method in an inherent extend block and one in an extend-trait block. Give one of each for a `Stack<T>`, and say who decides where each goes.

2. Value and reference. Write a `Point` struct with a `Vec<f64>` field, then explain what happens to each on assignment: the copy of the fields and the move of the owning field. Add a line that shares the vector on purpose, and say what you had to write that a class language would give for free.

3. Constructors. Declare a `Duration` struct with a seconds field and factories `fromSecs` and `fromMillis`, and write the invariant each establishes. Add a convenience factory that calls another factory rather than duplicating setup.

4. Diagnostics. Trigger E1201, E1202, E1203, and E1301 with small examples, and write the corrected version beside each. For E1301, explain why the fix is to let the scope finish rather than call drop yourself.

5. Composition. Write a `Stack<T>` that composes a `Vec<T>` and forwards `push`, `pop`, and `isEmpty`. Then write a `CountingStack<T>` that wraps your stack and counts calls to `push`. Which forwards, and which adds behaviour at the seam?

6. Dispatch. Write a `Vec<any Shape>` holding a Circle, a Square, and a Triangle, and print each area. Rewrite the loop as a generic function, and state what each version accepts and costs at runtime.

7. Design. For a serialisation library, decide in one sentence each what should be a trait, a generic function, and a plain concrete function. Name one failure from making the wrong thing a trait, and one from making the wrong thing concrete.

8. Pattern matching. Add a `Triangle` case to the `Shape` variant from Section10.13, then add the arm its `area` method requires, and explain what the compiler would have reported had you forgotten. Then add a fifth case and describe the same effect.

9. Lifecycle. Write a function that opens two smart pointers and returns early on the second failed allocation. Trace the automatic releases on the early return and the normal exit, and explain why the order reverses the declarations.

10. Meta. Coral has no inheritance; a type acquires behaviour only by extending or conforming, and sealing requires `#[[no_extend]]`. Argue that this is a limitation, then a strength. Which is more convincing, and why?

11. Encapsulation. Take a standard library struct with public fields, such as `Vec`, and argue why they are public rather than hidden behind accessors. Then do the same for a type that hides its representation, such as `File` or `Mutex`, and say what the distinct or opaque type buys.
