Chapter6

Traits, Extend, and Polymorphism

Two Ways to Serve Many Types

Think about the wall outlet in your kitchen. It does not know or care whether you plug in a kettle, a lamp, or a phone charger. It promises one thing, three holes of a particular shape, at a particular voltage, and anything that has a matching plug will work. The outlet is an interface. It was designed once, and a thousand appliances were built to meet it.

Now think about a recipe card that says "add ___ cups of flour." The card is not finished. Someone must fill in the blank before it becomes a real recipe, and the same card, filled in differently, makes a cake or a loaf. The recipe is a template. It was written once, and it produces a fresh, complete version for each blank you fill.

Those two ideas, the shared socket, and the fill-in-the-blank template, are the two ways a single piece of code can serve many types, and Coral has a separate tool for each. The socket is a trait: a named set of method signatures that a type promises to satisfy, plus the machinery for writing algorithms against that promise instead of against any one concrete type. The recipe is a generic: a function or type with a blank that the compiler fills in per use. This chapter is about traits and the extend blocks that make them possible. The next chapter is about generics.

Traits in Coral are deliberately small. A trait is a list of method signatures and, optionally, some default bodies. A type satisfies a trait by providing those methods in an extend block. There is no inheritance between types, no class hierarchy, and no virtual table unless you ask for one with `any Trait`. What there is instead is a style of programming that says: name the behaviour you need, write your algorithm against the name, and let each type opt in by keeping the promise. This chapter teaches both halves, declaring a trait and using one, along with the built-in traits `@drop` and `@toStr` that the compiler wires in for you, and the exact moments when you want to turn that automatic behaviour off.

6.1 Methods and Extend: Putting Behaviour Next to Data

Before there can be traits, there must be methods. And before methods, there is a decision Coral makes that is worth understanding, because everything in this chapter grows out of it.

You have probably written a function like this:

    f64 magnitude(Point p) {
        return sqrt(p.x * p.x + p.y * p.y);
    }

It works, and it is perfectly good code. You call it as `magnitude(p)`, passing the point in as the first argument. But notice a small friction: every time you think about a Point, you have two pieces of knowledge to keep together, the struct that defines its fields, and a scattered family of free functions that know how to operate on it. Rename the struct, and you hunt down every helper. Add a field, and you check all of them.

In plain words, a method is just a function that has been filed next to the data it works on. Compare the two ways of calling it: `magnitude(p)` takes the point as an argument, while `p.magnitude()` reads as "ask this point for its magnitude." Same work, but the second keeps the tool beside the thing it is used on.

Coral lets you write that same function as a method, living in an extend block beside the type it belongs to:

    struct Point {
        f64 x;
        f64 y;
    }

    pub extend Point {
        f64 magnitude() {
            return sqrt(self.x * self.x + self.y * self.y);
        }

        Point scaled(f64 factor) {
            return Point { .x = self.x * factor, .y = self.y * factor };
        }

        void translate(f64 dx, f64 dy) {
            self.x += dx;
            self.y += dy;
        }
    }

Three things changed, and each matters.

First, the receiver moved out of the parameter list. You do not write `Point p` as the first parameter; Coral supplies the receiver implicitly, and you reach it through the name `self`. So inside `magnitude`, `self.x` is the x-coordinate of the point you called the method on. The call site reads left to right as an action on a value, `p.magnitude()`, `p.scaled(2.0)`, `p.translate(1.0, 2.0)`, instead of `magnitude(p)`.

Second, methods that mutate the receiver do so through `self` directly. `translate` writes `self.x += dx;`, and that changes the point you called it on. A method that returns a new Point instead of changing `self`, like `scaled`, leaves the original alone. Keeping those two shapes visibly distinct (`translate` mutates, `scaled` does not) is a large part of what makes a type's API readable.

Third, the extend block is separate from the struct declaration. This is the design choice that pays off for the rest of the chapter. The struct declares fields; the extend block declares behaviour. They are two declarations, and a type may have several of them. That split is exactly what lets a trait attach behaviour to a type the trait did not define, and it is why the language can offer "add a method from outside" at all.

Hold on, let me explain that more plainly, because it is the seed of everything that follows. In a language that fuses data and behaviour into a class, a method can only be written by whoever wrote the class. If you are handed a type from a library and it lacks the one method you need, you are stuck: you cannot reach into the library's class and add it. Coral separates the two, so an extend block can add a method to any type you can see, even one that lives in another module. That sounds like a small convenience. It is actually what makes traits and generics possible, because a trait conformance is just an extend block that names a trait, and a generic function is just code written against that name.

One spelling note before we go on. `pub` on an extend block means the methods inside are visible outside the current module; without it, they are private to the file. Exporting behaviour is a deliberate act, and the marker makes it visible at the declaration.

6.2 const Methods: A Promise That You Will Not Change Anything

Imagine a library reading room. You are allowed to take a book off the shelf and read it, but you are not allowed to write in the margins. A librarian who hands you a book marked "reference only" is making a promise on the library's behalf: nothing you do to this book will change it for the next reader.

A `const` method is that promise, made in code. It says: calling this method will not change the receiver, and therefore it is safe to call on a value that a caller considers read-only. You write it either with the attribute `#[[const]]` above the signature, or with the trailing keyword `const` after the parameter list. The two are the same promise spelled two ways:

    pub extend Point {
        #[[const]]
        f64 magnitudeSquared() {
            return self.x * self.x + self.y * self.y;
        }
    }

    // exactly the same meaning
    pub extend Point {
        f64 magnitudeSquared() const {
            return self.x * self.x + self.y * self.y;
        }
    }

Pick one spelling and stay with it; the compiler treats them identically. What matters is that the promise has teeth. A const method that assigns to `self` or to any of its fields is an error, caught at the assignment, not at some caller's surprise:

    pub extend Point {
        f64 bad() const {
            self.x = 0.0;      // error: cannot mutate self in a const method
            return self.y;
        }
    }

Why is this worth the keystrokes? Because it lets a caller reason locally. If you are handed a `const Point*`, a read-only view of a point, the compiler will let you call `magnitudeSquared` on it, because that method promised not to write. It will refuse to let you call `translate`, which makes no such promise. A const method is a promise a reader can trust, and the compiler is the one that checks it. This is the same family as `const` on a parameter or a pointer, and the diagnostics live in the E10xx range.

6.3 Static Methods and Constructors

Some operations belong to a type without belonging to any particular value of it. "Make me a point at the origin" is not something a point does; it is something the Point type produces. Coral spells those with the `static` keyword, and there is no `self` because there is no instance:

    pub extend Point {
        static Point new(f64 x, f64 y) {
            return Point { .x = x, .y = y };
        }

        static Point origin() {
            return Point { .x = 0.0, .y = 0.0 };
        }
    }

In plain words, a static method is something the type can do even when you do not yet have one of its values. "Make a point at the origin" has to happen before any point exists, so it belongs to the type, not to an instance. The choice of `Point::origin()` versus `p.magnitude()` is a visible signal: the double colon means no existing value is involved.

Constructors are static methods by convention, and `new` is the customary name. You call a static method on the type, using the double-colon path: `Point::origin()`, `Point::new(3.0, 4.0)`. You call an instance method on a value, using the dot: `p.magnitude()`. The distinction between `::` and `.` is the distinction between a type and a value, and it is visible at every single call site, which is the whole point. When you see `Point::new(...)`, you know no existing value is involved. When you see `p.scaled(...)`, you know `p` is being operated on.

That visibility is not decoration. It is the same reason Coral writes `self` rather than hiding it: the language would rather your code declare what it is doing than leave the reader to infer it.

6.4 Declaring a Trait: A Contract Without an Implementation

Now we reach the socket.

Picture a job description. It lists what the hire must be able to do, "prepare monthly reports," "call vendors," "operate the forklift", and it attaches no names. It is not a person; it is a set of requirements a person can meet. Any candidate who can do those things can fill the role, and the description does not care who. A trait is a job description for types.

You declare one with the `trait` keyword and a list of method signatures. Each signature is a return type, a name, and parameters, ending in a semicolon because there is no body:

    trait Shape {
        f64 area();
        f64 perimeter();
    }

That is a complete trait. It says: any type that satisfies Shape has an `area` method returning `f64` and a `perimeter` method returning `f64`. It says nothing about circles or squares; it is just the requirements. Notice how little is here. A trait is not a base type, not a parent, not a place where data lives. It is a contract, and it is checked like one.

A trait may also carry default implementations, which are the one place a trait holds logic. A default is a method with a body; a type that satisfies the trait inherits it unless it overrides it:

    trait Named {
        str name();
        str describe() {
            return "an object named " + self.name();
        }
    }

Here `name` has no body, so every implementor must supply it. `describe` has a body, so it is free, an implementor gets it for nothing and may replace it if the default is not right. The default is allowed to call the required methods, which is why the contract's shape is declared first: `describe` is written in terms of `name`, so `name` must already be promised.

`hold on, let me explain that more plainly`, because "default method" is a phrase that hides a simple idea. A trait can require the minimum it needs and then hand you convenience built on top of that minimum. If every "named thing" should be describable as "an object named X," the trait writes that sentence once, and every implementor gets it without retyping it. The required method is the load-bearing wall; the default is the furniture. You must supply the wall, and the furniture comes with the room.

Trait methods may take parameters and may be `const`, exactly like ordinary methods. They may not carry data, and they may not be `static` in the sense of depending on no instance, a trait method is about a value.

6.5 Implementing a Trait: Making the Promise

A trait is a job description; an implementation is a hire. A type satisfies a trait with an extend block that names the trait after a colon:

    struct Circle {
        f64 radius;
    }

    pub extend Circle : Shape {
        f64 area() {
            return 3.14159 * self.radius * self.radius;
        }

        f64 perimeter() {
            return 2.0 * 3.14159 * self.radius;
        }
    }

    struct Square {
        f64 side;
    }

    pub extend Square : Shape {
        f64 area() {
            return self.side * self.side;
        }

        f64 perimeter() {
            return 4.0 * self.side;
        }
    }

The colon reads as "extends as" or simply "satisfies": `Circle : Shape` means Circle satisfies Shape. Two types, one trait, two sets of bodies, the circle's formulas and the square's formulas. Notice what is absent. There is no sentence saying "a Circle is a kind of Shape." Circle remains exactly Circle; the block merely promises the two methods Shape asked for, implemented with the formulas that are the circle's own. There is no inheritance and no hierarchy. A circle is not a descendant of a shape; it keeps a promise next to its other promises.

In plain words, implementing a trait means filling in the blanks of the checklist. The trait named the questions (`area` and `perimeter`); the extend block supplies this type's answers. Once the answers exist, a Circle can be handed to any code that accepts a Shape.

This is a good moment to say something that trips people coming from class-based languages. Coral's conformance is nominal, not structural. In a structural language, a type satisfies an interface simply by happening to have the right methods, whether it intended to or not, which means a conformance can appear or vanish when someone else's code changes. In Coral, you must declare the conformance explicitly, with the extend block. It means to satisfy the trait, and it says so. The payoff is that a conformance is a stable, searchable fact: if you want to find every type that claims to be Shape, you search for `: Shape`, and you get all of them and nothing else.

The conformance is declared, and because it is declared, it can be checked. The compiler compares the trait's signatures against the block, method by method: `area` must exist with the required signature, `perimeter` must exist with the required signature, and the match must be exact. If a method is missing, or its return type is wrong, or its parameters are wrong, the compiler reports it. A type cannot half-implement a trait. This is the E12xx family of diagnostics: E1202 is a signature mismatch, E1203 is a missing required method. They exist so that "does this type really do what the interface says?" is answered by the compiler, at the conformance site, rather than by a crash at some distant call.

A type may satisfy several traits, each in its own block, each an independent promise:

    pub extend Circle : Shape {
        f64 area() { return 3.14159 * self.radius * self.radius; }
        f64 perimeter() { return 2.0 * 3.14159 * self.radius; }
    }

    pub extend Circle : Named {
        str name() { return "circle"; }
    }

Circle now keeps two promises. The trait set is the type's whole menu of abilities, and the traits do not arrange themselves into a hierarchy, Circle does not derive Shape-ness from some ancestor. It just promised twice.

One rule keeps this neat: a type may conform to a given trait only once. There is exactly one implementation of `Shape::area` for Circle. That uniqueness is what lets the compiler resolve a call to `area` in a single step when the concrete type is known: there is no ambiguity to break, so no dispatch decision is needed. It is also what makes the E1201 diagnostic possible, the same method defined twice for one type across different blocks is an error, because the promise would otherwise be ambiguous.

6.6 Inherent Methods and Trait Methods in the Same Type

A useful type usually has two kinds of methods at once. Inherent methods are the type's own vocabulary, the API its author designed because it is useful. Trait methods are the type's obligations, the part of it that some interface requires. Coral keeps them in separate extend blocks, and the separation is meaningful.

In plain words, inherent methods are the type's own features, chosen by whoever wrote it, while trait methods are promises it made to fit an interface. Keeping them apart is like keeping your own to-do list separate from the forms you filed for other people: both are yours, but one is your design and the other is an obligation.

    pub struct Stack<T> {
        Vec<T> items;
    }

    pub extend<T> Stack<T> {
        static Stack<T> new() {
            return Stack<T> { .items = Vec<T>::new() };
        }

        void push(T value) {
            self.items.push(value);
        }

        T pop() {
            return self.items.pop();
        }

        bool isEmpty() const {
            return self.items.isEmpty();
        }
    }

`push`, `pop`, `isEmpty`, and the constructor are Stack's own API. They live in the inherent block. Now suppose Stack should also be iterable, so that you can range-for over it. That is a promise to an interface, and it goes in its own block:

    pub extend<T> Stack<T> : Iterable<T> {
        // the methods the Iterable trait requires, written in terms of self
    }

Why bother splitting? Because the two blocks answer different questions. When a trait changes, you look at the trait blocks: here is exactly how Stack fulfils Iterable. When Stack's own API changes, you look at the inherent block. A reader scanning for "how does this type meet its contracts?" gets a short, auditable answer instead of hunting through thirty methods. The split is a small discipline with a large readability payoff, and it mirrors the earlier split between fields and behaviour: each declaration has one job.

6.7 Generic Traits and Generic Extends

Traits and extends can both be generic, and the standard library's Result is the clearest example of why. A `Result<T, E>` is either an `Ok` carrying a value of type `T` or an `Err` carrying an error of type `E`. The methods that work on it must work for every choice of `T` and `E`, so they are declared in an extend block generic in both:

    pub variant Result<T, E> {
        Ok  { T value; },
        Err { E error; }
    }

    pub extend<T, E> Result<T, E> {
        bool isOk() { ... }
        T unwrap() { ... }
        T unwrapOr(T defaultVal) { ... }
    }

The `pub extend<T, E> Result<T, E>` block matches the type it extends: both are parameterised by `T` and `E`. Every method is available for every instantiation, and the compiler monomorphises each instantiation separately. `Result<i32, IoError>` and `Result<str, ParseError>` get their own copies with their own concrete types, as though you had written two separate types. A generic extend is not a runtime template; it is a family of methods generated per use, with no indirection and no boxing.

How do these methods work when they mention `T`? Inside `unwrap`, the `Ok` variant's field is of type `T`, and the return type is `T`, both refer to the same parameter, so the compiler is satisfied. The type parameter is in scope throughout the extend block, in signatures and in bodies alike.

Two directions are independent and both are common. A generic type can implement a non-generic trait, that is how a container becomes iterable regardless of what it holds. And a non-generic type can implement a generic trait, that is how a type participates in a family of interfaces parameterised by element type. Coral's standard library uses both, and the design space is exactly these two axes.

6.8 The Built-In Traits: @drop and @toStr

Coral defines a small set of traits in the language itself, spelled with a leading `@` to mark them as compiler-known. The two you will meet first are `@drop` and `@toStr`. They are special because the compiler wires them in automatically rather than requiring an explicit call. When a type implements `@drop`, the compiler inserts the call for you at the right moment. When a type implements `@toStr`, the formatting machinery finds it for you. You opt in with an ordinary extend block; the magic is on the compiler's side, at the one place each trait is used.

RAII, and why @drop exists

Start with `@drop`, the destructor trait. In C, whenever you open a file, lock a mutex, or allocate a buffer, you must remember to close, unlock, and free it, and you must do it on every early return, every error path, every `goto cleanup`. The classic bug is the path someone forgot. The discipline that fixes it has a name: RAII, for "resource acquisition is initialisation," and it means tying a resource's lifetime to a variable's scope. When the variable goes out of scope, the resource is released, automatically, on every exit path, with no call site to forget.

In plain words, RAII is a bargain the language keeps on your behalf: the instant you acquire something, a variable takes ownership of it, and the instant that variable's scope ends, the thing is released, whether the code left by finishing normally, by returning early, or by an error path. You write the acquisition, and the cleanup is automatic.

Coral expresses RAII as a trait. A type that implements `@drop` must provide a `void drop()` method, and the compiler invokes it automatically when a value of that type goes out of scope:

    pub extend FileHandle : @drop {
        void drop() {
            close(self.fd);
        }
    }

That is the whole contract: `void drop()`, no parameters, no return. With this conformance, a FileHandle local is closed when its enclosing scope ends, including when the scope ends early because of a `return`, a `break`, or an error path. And this is not limited to plain locals. A `Vec<FileHandle>` frees its handles when the vector is dropped, because the vector's own drop recursively drops its elements. The trait is what turns "the compiler knows when to call a function" from unexplained magic into a nameable contract.

    void copyLogs() {
        FileHandle source = FileHandle::open("access.log");   // acquired
        FileHandle dest   = FileHandle::open("access.bak");   // acquired
        copyContents(&source, &dest);
        // both files close here, at scope end, even if copyContents returned early
    }

Two things to notice. You never wrote `source.drop()` or `dest.drop()`, and you should not, more on that in a moment. And the cleanup happens at a place you can point at: the closing brace. That predictability is RAII's whole value.

There is one more decision to make: which types should implement `@drop` at all. A type that owns a resource, a heap buffer, a file, a lock, a socket, should. A type that is just a bundle of numbers, like a Point or a colour, should not; there is nothing to release, and a `drop` that does nothing is noise. The rule of thumb is: implement `@drop` exactly when the type owns something that must be given back.

@toStr: teaching a type to print itself

`@toStr` is the formatting trait. A type that implements it can be printed, or converted to a `str` where a string is required, and the compiler finds the implementation at the formatting call site:

In plain words, `@toStr` is how you teach a type to describe itself as text. Without it, the printing machinery has no idea what one of your Points should look like on screen; with it, `println("{}", p)` knows exactly what to render.

    pub extend Point : @toStr {
        str toStr() {
            return "Point(" + formatFloat(self.x) + ", " + formatFloat(self.y) + ")";
        }
    }

With this conformance, `println("{}", point)` works: the printing machinery, seeing a Point where it must render text, dispatches to `Point::toStr`. The standard library's `std::io::ios` documents that `toStr` is an inbuilt trait of the same class as `@drop`, nothing is declared there; the `any toStr` case in the formatter is where the compiler auto-wires the call. The two built-ins show the same shape: the language names a capability, the type opts in with a normal extend block, and the compiler special-cases that name at the one place it matters. If you want to know what a type does automatically, look for `@drop` and `@toStr` among its conformances.

6.9 RAII in Practice, and How to Opt Out

Automatic cleanup is the right default, but it is not free and not always wanted. The compiler must track every local that implements `@drop` and generate a cleanup call on every path out of the scope. For most application code that cost is exactly what you paid for, and you leave it on. But some code, the standard library itself is the canonical case, manages memory by hand with explicit `free` calls and does not want the compiler generating destructor calls it would then have to account for. Coral gives you a graduated set of opt-outs, and it is worth knowing each one, because the wrong choice here is a double free or a leak.

In plain words, the opt-outs let you say "I will handle this cleanup myself" over increasingly broad areas: one variable, one block, or an entire file. They exist for code that manages memory by hand, the standard library is the main example, and a beginner almost never needs them, because the automatic behavior is what you want.

`#[[no_drop_all]]`: turn RAII off for a whole file

`#[[no_drop_all]]` is a file-level attribute. Alone among attributes, it does not modify a declaration; it appears once, before the first declaration in the file, and it disables drop-trait auto-RAII for the entire file:

    #[[no_drop_all]]

    pub struct Arr<T, N> {
        // ...
    }

With it present, the compiler resolves no drop methods for locals in this file and emits no unwind calls; ownership is manual, through explicit `free` or `dispose`. Every file under the standard library and the compiler's own sources carries it. There are two reasons. The first is correctness of intent: library code lays its bytes out and frees them deliberately, and it does not want a hidden destructor interleaving with that. The second is build speed: resolving and emitting drops across a large library is work, and the library has already decided it will not use the feature.

A file without `#[[no_drop_all]]`, that is, your ordinary application file, gets automatic RAII for any local whose type implements `@drop`. So the two worlds coexist in one program: library code opts out, application code opts in by default. The attribute rides on each declaration rather than only on the file, a subtle piece of engineering that means when a library file is merged into a user's build unit it keeps its setting. You never accidentally get RAII back into a library file that declined it.

One important consequence: inside a `#[[no_drop_all]]` file, a value's destructor is never called for you, so a type that owns memory must free it explicitly. The std's `String` is a good example of the pattern: it provides a `free()` method, and separately conforms to `@drop` so that user code gets automatic cleanup:

    pub struct String {
        u8* ptr;
        usize len;
        // ...
        void free() {
            dealloc<u8>(self.ptr);
        }
    }

    pub extend String : @drop {
        void drop() { self.free(); }
    }

In a library file with `#[[no_drop_all]]`, calls to `s.free()` are written by hand. In your application file, you write nothing and the String frees itself at scope end.

`#[[no_drop]]`: turn RAII off for one variable or one block

`#[[no_drop_all]]` is the sledgehammer. The one you will actually reach for is `#[[no_drop]]`, which is scoped. On a variable declaration it excludes that one variable from auto-RAII; on a block it excludes every local inside the block, nested blocks included:

    void processInChunks(File* f) {
        #[[no_drop]]
        u8* buffer = alloc<u8>(65536);      // manual lifetime

        defer {
            dealloc<u8>(buffer);
        }

        while (true) {
            usize n = readChunk(f, buffer, 65536);
            if (n == 0) break;
            handle(buffer, n);
        }
    }

The buffer carries `#[[no_drop]]` because its lifetime is managed by the `defer` block, not by RAII on the variable. This is the honest way to hand-manage one allocation: opt out of automatic cleanup for exactly this value, and take responsibility explicitly, in one visible place. The attribute says "I will remember to free this" and the `defer` makes that literal.

When is `#[[no_drop]]` the right tool, and when is it a mistake? Three honest cases:

    - A value whose lifetime is longer than its scope, handed back out of the
      function, stored in a long-lived structure, or moved to another owner.
    - A value managed by an explicit mechanism (defer, a refcount, a pool) so
      that RAII on the variable would be a second, competing owner.
    - A value obtained from a foreign interface that the caller does not own and
      must not release, such as a borrowed C handle.

And the dishonest case: a value whose variable lifetime really is its resource lifetime, annotated out of laziness or a vague fear of the destructor. That annotation says "I will remember," and humans do not always remember. A value that opts out of RAII is a value whose cleanup is now a manual obligation, and obligations accumulate. Use `#[[no_drop]]` where nothing else will do, and let RAII handle everything with no reason to complain.

Sealing a type: #[[extend]] and #[[no_extend]]

Two attributes govern whether a type may be grown by later code, and they connect directly back to the extend machinery. By default a type is open: anyone who can see it may write an extend block adding methods. `#[[extend]]` makes that permission explicit (it is mostly for symmetry at a point where a reader might expect a closure). `#[[no_extend]]` is the interesting half, it forbids further extend blocks:

    #[[no_extend]]
    struct SecurityToken {
        u64 secret;
        i64 expiry;
        // ...
    }

This is how a library seals a type so that its behaviour is exactly the methods it ships. A sealed type is a promise that its interface is closed: no third party can add a method that changes the meaning of an operation, and the set of things you can do with the type is the set its author chose. It is the right choice for a type whose invariants must not be circumvented, an opaque handle, a state machine whose transitions are fixed, a security token. It is a strong statement and a rare one, and making it require an annotation is deliberate: most types want to be open, so sealing should be a decision rather than something that happens to you.

The four drop diagnostics, E1301 to E1304

Drop is subtle, and the compiler guards the four ways it goes wrong. Knowing these four is knowing the ownership model at its deepest point.

E1301, explicit call to a drop method disallowed. If you write `x.drop()` yourself, the compiler reports it. Drop is driven by scope termination; calling it manually invites a double free, because the value's scope will end and the automatic drop will run too. The fix is to let the scope do it, or to opt out with `#[[no_drop]]` and provide a normal cleanup method:

    void broken(FileHandle* f) {
        f->drop();          // error E1301: cannot call drop() explicitly
    }

    void right(FileHandle* f) {
        // let RAII close it at scope end
    }

    pub extend FileHandle {
        void closeNow() {      // a normal method you may call yourself
            close(self.fd);
        }
    }

    void manual(FileHandle* f) {
        #[[no_drop]] FileHandle h = *f;
        h.closeNow();           // explicit cleanup, and RAII was told to stand down
    }

E1302, no drop on a type whose size varies with comptime conditions. A fixed-layout destructor cannot be sound for a type whose size is not known until the comptime block resolves. The error catches a `@drop` implementation on such a type; the fix is to give the type a fixed size, or to manage it without `@drop`.

E1303, field moved out before the drop runs. If you take a field out of a struct and leave the struct to be dropped, the destructor would run on partially uninitialised memory:

    struct Holder {
        String name;
        Vec<String> tags;
    }

    void broken(Holder h) {
        String stolen = h.name;   // moves name out of h
        // h is dropped at scope end, but its name field is gone -> E1303
    }

The fix is to drop or transfer the whole value, or to replace the moved field with a valid one before the scope ends.

E1304, a capability used through a type parameter. This one is about generics and is best understood after the next two sections. In short: a generic body may call any operation on a value of type `T`, but the compiler only checks that the operation exists when it instantiates the generic for a concrete type. Ask a generic to print its `T`, which needs `@toStr`, and then call it with a type that has no `@toStr`, and the error is reported at that instantiation, naming the type:

    void printer<T>(T value) {
        println("{}", value);   // fine here; each instantiation must supply @toStr
    }

    struct Opaque { i32 id; }   // no @toStr

    printer(Opaque { .id = 1 });  // error E1304: Opaque has no toStr capability

Coral does not let you write the requirement on the signature, there is no `T : @toStr` bound. The requirement is a property of the body, and the compiler enforces it wherever the generic is instantiated. When you want to state or check it more directly, you inspect the type in a `comptime` block, as Chapter7 shows.

Together, these four say something clear: every automatic drop either happens and is not called by hand (E1301), is on a type whose layout is fixed (E1302), receives every field it expects (E1303), and the capabilities a generic relies on exist for the type it is instantiated with (E1304). The compiler will not let a lifetime mistake slip through quietly.

6.10 Dynamic Dispatch: any Trait

Every conformance so far has been static. When the concrete type is known, a call to `area` resolves to the one implementation, with no runtime lookup. But sometimes the concrete type is not known. You have a list of different shapes, circles and squares mixed together, and you want to call `area` on each. That is what `any Trait` is for.

Think of a universal remote. It has a row of buttons, and it can control any television that speaks the standard signal. The remote does not contain a television; it holds a reference to one plus enough knowledge to send the right commands. Which television is behind the remote is decided at the moment you point it, not when the remote was made.

In plain words, `any Shape` means "some kind of shape, and we will find out exactly which one when the program runs." The value carries both the object and a way to reach its Shape methods, so one loop can handle a Circle today and a Square tomorrow without being rewritten.

    Vec<any Shape> shapes = Vec<any Shape>::new();
    shapes.push(Circle { .radius = 1.0 });
    shapes.push(Square { .side = 2.0 });

    for (any Shape s : shapes) {
        println("area = {}", s.area());
    }

A value of type `any Shape` is a fat pointer: it carries a reference to the value and a reference to its Shape implementation. Calling `s.area()` dispatches through that second reference to the concrete implementation. This is a trait object, and it is the dynamic half of polymorphism: the call site does not know whether it holds a Circle or a Square, and the decision is made at runtime.

The trade-offs are the usual ones for dynamic dispatch, and Coral makes them visible rather than hiding them. A trait object costs an extra indirection per call and cannot generally be inlined across the boundary, because the callee is not known until the program runs. It is a pointer-sized pair, so storing one stores a reference plus a table pointer, twice the space of a plain reference. And it carries only the methods the trait declares: through an `any Shape` you can call `area` and `perimeter`, but not a method Square happens to have that Shape does not. The trait is the window, and you see exactly what it frames.

The recommended design is to keep dynamic dispatch at the boundary where the concrete type is genuinely unknown, a heterogeneous collection, a plugin registry, a callback, and to keep the internals static. A function with a generic `T` constrained to Shape gets the same behaviour with no indirection when the compiler can see the concrete type; reach for `any Shape` only when it cannot. Because both mechanisms are built on the same trait, moving between them is a change to one signature rather than a rewrite.

One practical note on spelling, since it comes up here. Coral has no `as` cast; a conversion is written with the target type in parentheses, as in `(Circle)x`. And the wildcard in a pattern is `else`, never an underscore, in a `switch` over an `any Shape`, you would write what you need explicitly and let an `else` catch the rest, exactly as in any other switch.

6.11 Static Polymorphism with Generics

A generic function can work for every type that can do what its body asks. The body is the requirement: write `sum += s.area()` and the function works for any `T` whose values have an `area` method. There is no bound to write and no constraint clause on the signature:

    f64 totalArea<T>(Vec<T> shapes) {
        f64 sum = 0.0;
        for (T s : shapes) {
            sum += s.area();
        }
        return sum;
    }

In plain words, this is a recipe written with a blank for the element type: "for any T, if T knows how to `area`, sum them up." The compiler fills the blank separately for each type you actually use, so each version is as fast as one written by hand for that type. The blank is written `<T>`, and you will meet it again in the next chapter.

Inside `totalArea`, the call `s.area()` is checked when the function is instantiated. Call it with `Vec<Circle>` and the compiler generates a `totalArea<Circle>` whose `s.area()` is a direct call to `Circle::area`. Call it with `Vec<str>`, a type with no `area`, and the error is reported naming `str` as missing the operation. The requirement is never declared up front; it is discovered and enforced at each instantiation. If you want to assert it in your own words, or branch on the type, a `comptime` block does that, as Chapter7 develops.

This is static polymorphism, and it is free. `totalArea` is monomorphised for each `T` that calls it, so there is no vtable, no indirection, and no dispatch, the type checking costs nothing at runtime. A generic is the preferred form when the set of types is known at compile time and performance matters; `any Trait` is the fallback when it is not. Compare the two side by side:

    // static: monomorphised, direct calls, chosen at compile time
    f64 totalArea<T>(Vec<T> shapes) { ... }

    // dynamic: one function, indirect calls, chosen at runtime
    f64 totalAreaDyn(Vec<any Shape> shapes) {
        f64 sum = 0.0;
        for (any Shape s : shapes) {
            sum += s.area();
        }
        return sum;
    }

The first cannot accept a mixed vector, because `T` must be a single type. The second can, because every element is the same `any Shape` type. That single sentence is the whole decision: homogeneous and known at compile time means a generic; heterogeneous or known only at runtime means `any`.

Because there are no bounds, a generic's requirements are exactly the operations its body names and nothing more. That has a pleasant consequence: to learn what a generic needs from its type parameter, you read the body rather than a signature. It has a cost too: the requirement is not visible to a caller until an instantiation fails, so a well-written generic documents in a comment the capabilities it expects. The E1304 diagnostic from the previous section is the enforcement, instantiate a generic with a type that cannot do what the body asks, and the compiler refuses, naming the type and the operation it was missing.

6.12 A Worked Example: One Printer for a Whole Tree

Traits earn their keep when one algorithm must work across many shapes. Consider a filesystem tree: a directory holds files and subdirectories together, and you want one printing routine that walks the whole thing. The collection is heterogeneous at runtime, a directory's children are a mixture, so `any` is the right dispatch.

    trait TreeNode {
        str label();
        Vec<any TreeNode> children();
    }

    struct FileNode { str path; Vec<any TreeNode> kids; }

    pub extend FileNode : TreeNode {
        str label() { return self.path; }
        Vec<any TreeNode> children() { return self.kids; }
    }

    struct DirNode { str name; Vec<any TreeNode> kids; }

    pub extend DirNode : TreeNode {
        str label() { return self.name; }
        Vec<any TreeNode> children() { return self.kids; }
    }

The printing algorithm is written once, against the trait:

    void printTree(any TreeNode root, i32 depth) {
        for (i32 i = 0; i < depth; i += 1) {
            print("  ");
        }
        println("{}", root.label());
        for (any TreeNode child : root.children()) {
            printTree(child, depth + 1);
        }
    }

Look at what `printTree` does not know. It does not know about files or directories. It knows the two methods TreeNode declares, and it recurses through them. Add a new node type, a symlink, a device, a network mount, and it participates in printing without a single line of `printTree` changing, provided it conforms to TreeNode. That is the open/closed property polymorphism is supposed to give: open to new types, closed to modification of the algorithm.

Why `any TreeNode` here rather than a generic `printTree<T>`? Because the tree is heterogeneous. A directory holds files and directories together, so the children list must hold values of different concrete types, and the common dynamic type is exactly what makes that possible. A generic could print a homogeneous `Vec<T>`, but not a mixed tree, because `T` would have to be one type. The choice between generic and `any` follows from the data, not from taste.

Now add a second, different behaviour over the same data, counting the nodes, and notice that the shape repeats. The new operation is another recursion through the same two methods, and the node types never change:

    i32 countNodes(any TreeNode root) {
        i32 total = 1;                       // the root itself
        for (any TreeNode child : root.children()) {
            total += countNodes(child);
        }
        return total;
    }

Two operations, one set of node types, and neither operation mentions FileNode or DirNode by name. The lesson is the shape: data defines the cases, traits define the operations, and one algorithm serves every type that keeps the promise. Before traits, `printTree` and `countNodes` would each need a switch over node kind, and every new node kind would mean editing both. After traits, adding a node kind adds a conformance and touches nothing else, the operations are declared once and the compiler checks that every conforming type supplies the methods they are written against. That trade, cases are cheap to add, operations are written once, is the same expression problem from Chapter13, seen from the polymorphism side.

6.13 A Second Worked Example: A Plugin Registry

The tree used `any` because the collection was heterogeneous. A plugin registry is the same shape for a different reason: the plugins are chosen at build or load time, so the program cannot name their types at compile time at all.

    trait Plugin {
        str name();
        void run();
        void shutdown() { }        // default: most plugins have nothing to release
    }

    struct Registry {
        Vec<any Plugin> plugins;
    }

    pub extend Registry {
        void register(any Plugin p) {
            self.plugins.push(p);
        }

        void runAll() {
            for (any Plugin p : self.plugins) {
                println("running {}...", p.name());
                p.run();
            }
        }
    }

The registry never mentions a concrete plugin type. It stores `any Plugin` and calls the methods the trait declares. A new plugin is a new struct plus a conformance, and the registry code is untouched. The `shutdown` method has a default body, so a plugin that holds no resources writes nothing for it, while a plugin that does can override it. That is the same division of labour we saw in the `Named` trait: require the minimum, provide convenience, allow refinement.

Now make teardown automatic. Each concrete plugin that owns something conforms to `@drop` and routes its destructor to `shutdown`:

    struct NetworkPlugin { Socket* sock; }

    pub extend NetworkPlugin : Plugin {
        str name() { return "network"; }
        void run() { self.sock->poll(); }

        void shutdown() {
            self.sock->close();
            dealloc<Socket>(self.sock);
        }
    }

    pub extend NetworkPlugin : @drop {
        void drop() { self.shutdown(); }
    }

The conformance to `Plugin` promises the interface; the conformance to `@drop` makes the cleanup automatic. Neither the registry nor its callers ever call `shutdown` by hand, the destructor does, at scope end. This is the combination that makes a plugin system trustworthy: the interface is small, the lifetime is automatic, and no caller can forget a plugin's cleanup.

6.14 Exercises

1. Comprehension. Explain the difference between a method in an inherent extend block and a method in an extend Trait block. Give one method that belongs in each for a `Stack<T>`, and say who decides which block it goes in.

2. Comprehension. Why can a const method be called on a const value but a non-const method cannot? Write a two-sentence explanation a C programmer would accept, and point at the diagnostic family that enforces it.

3. Implementation. Declare a trait `Comparable` with a method `lessThan(other) bool`, implement it for `Point` (compare by distance from the origin) and for a struct of your choice. Then write a generic `minimum<T>(T a, T b) T` whose body calls `lessThan`, and explain where the requirement that `T` has that method is checked.

4. Implementation. Add a `@toStr` conformance to a struct with three fields so that `println("{}", instance)` prints all three. Then add a wrong-way version where you print the fields in the wrong order and explain why the compiler cannot catch that.

5. Built-ins. Give one type that should implement `@drop` and one that should not, with a one-sentence reason each. For the one that should, write the conformance and the correct usage; for the one that should not, explain what a `drop` would even mean.

6. Drop attributes. You are writing a function that allocates a large buffer, hands it to a C library that frees it later, and returns. Which attribute applies to the buffer, `#[[no_drop]]` or `#[[no_drop_all]]`, and why is the other the wrong tool here? Write the function.

7. Diagnostics. Trigger each of E1301, E1303, and E1304 with a small example, and write the corrected version beside it. For E1302, describe in your own words why a comptime-variable-size type cannot have a fixed destructor.

8. Dispatch. Write a `Vec<any Shape>` holding a Circle, a Square, and a Triangle. Print each area. Why can the vector not have a concrete element type? Then rewrite the loop to use a generic function and explain what changes about the types accepted.

9. Generic versus dispatch. Write the same operation twice: once as a generic `totalArea<T>` and once as `totalAreaDyn(Vec<any Shape>)`. State what each accepts, what each costs at runtime, and which you would choose when the set of shapes is fixed at compile time.

10. Design. You are designing a serialisation library. Decide, with a sentence for each, what should be a trait, what should be a generic function, and what should be a plain concrete function. Then name one thing that goes wrong if you make the wrong one a trait.

11. Defaults. Declare a trait with three methods, one of which has a default body calling the other two. Implement it for a type, override the default, and explain when overriding is right and when it is over-engineering.

12. Meta. Coral has no inheritance; a type acquires behaviour only by extending or conforming, and sealing requires an explicit `#[[no_extend]]`. Argue that this is a limitation, then argue that it is a strength. Which position do you find more convincing, and why?

13. Sealing. Declare a `#[[no_extend]]` opaque handle with a private field and one public accessor, and write what a caller loses when the type is sealed and what the author gains.
