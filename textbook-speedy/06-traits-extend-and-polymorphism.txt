Chapter6

Traits, Extend, and Polymorphism

Two Ways to Serve Many Types

A wall outlet promises three holes at a certain voltage; any appliance with a matching plug works. The outlet is an interface.

A recipe card reading "add ___ cups of flour" is a template: fill the blank and it becomes a complete recipe.

A trait is the socket: a named set of method signatures a type promises to satisfy. A generic is the recipe: a function or type with a blank the compiler fills per use. This chapter covers traits and extend blocks; the next covers generics.

A trait is a list of method signatures, optionally with default bodies. A type satisfies it by providing those methods in an extend block. There is no inheritance, no class hierarchy, and no virtual table unless you ask with `any Trait`. This chapter covers declaring and using traits, the built-in `@drop` and `@toStr`, and when to disable automatic behaviour.

6.1 Methods and Extend: Putting Behaviour Next to Data

Before traits come methods, and before methods comes a design decision.

You have probably written a function like this:

    f64 magnitude(Point p) {
        return sqrt(p.x * p.x + p.y * p.y);
    }

It works, and you call it as `magnitude(p)`. But each Point now needs the struct plus a scattered family of free functions. Rename the struct and you must hunt down every helper.

A method is a function filed next to its data. `magnitude(p)` takes the point as an argument; `p.magnitude()` asks the point for its magnitude.

Coral lets you write the same function as a method in an extend block:

    struct Point {
        f64 x;
        f64 y;
    }

    pub extend Point {
        f64 magnitude() {
            return sqrt(self.x * self.x + self.y * self.y);
        }

        Point scaled(f64 factor) {
            return Point { .x = self.x * factor, .y = self.y * factor };
        }

        void translate(f64 dx, f64 dy) {
            self.x += dx;
            self.y += dy;
        }
    }

Three things changed.

First, the receiver moved out of the parameter list. Coral supplies it implicitly as `self`, so `self.x` is the receiver's x-coordinate. Calls read as actions: `p.magnitude()`, `p.scaled(2.0)`, `p.translate(1.0, 2.0)`.

Second, mutating methods write through `self` directly. `translate` changes the point it was called on; `scaled` returns a new Point and leaves the original alone. Keeping those shapes distinct makes an API readable.

Third, the extend block is separate from the struct. The struct declares fields; the extend block declares behaviour. A type may have several extend blocks.

That split is the seed of everything that follows. In a class-based language, only the class author can add a method. Coral lets an extend block add a method to any type you can see, even from another module. That makes traits and generics possible.

`pub` on an extend block makes its methods visible outside the module; without it, they are private to the file.

6.2 const Methods: A Promise That You Will Not Change Anything

A `const` method promises not to change the receiver, so it is safe on a value the caller considers read-only.

Write it with `#[[const]]` above the signature or `const` after the parameter list. Both spellings mean the same thing:

    pub extend Point {
        #[[const]]
        f64 magnitudeSquared() {
            return self.x * self.x + self.y * self.y;
        }
    }

    // exactly the same meaning
    pub extend Point {
        f64 magnitudeSquared() const {
            return self.x * self.x + self.y * self.y;
        }
    }

Pick one spelling; the compiler treats them identically. The promise has teeth: a const method that assigns to `self` or its fields is an error at the assignment.

    pub extend Point {
        f64 bad() const {
            self.x = 0.0;      // error: cannot mutate self in a const method
            return self.y;
        }
    }

This lets a caller reason locally. Given a `const Point*`, the compiler allows `magnitudeSquared` and refuses `translate`. Diagnostics are in the E10xx range, the same family as `const` on a parameter or pointer.

6.3 Static Methods and Constructors

Some operations belong to a type, not a value. "Make a point at the origin" is something Point produces. Coral spells those `static`, with no `self` because there is no instance:

    pub extend Point {
        static Point new(f64 x, f64 y) {
            return Point { .x = x, .y = y };
        }

        static Point origin() {
            return Point { .x = 0.0, .y = 0.0 };
        }
    }

A static method works before any value exists. `Point::origin()` uses `::`; `p.magnitude()` uses `.`, a visible signal that no existing value is involved.

Constructors are static methods by convention, with `new` the customary name. Call statics with `::` and instance methods with `.`; the distinction is visible at every call site.

The language would rather your code declare what it is doing than leave the reader to infer it.

6.4 Declaring a Trait: A Contract Without an Implementation

Now the socket.

A job description lists what a hire must do without naming anyone. A trait is a job description for types.

Declare one with the `trait` keyword and method signatures: a return type, a name, and parameters, ending in a semicolon because there is no body:

    trait Shape {
        f64 area();
        f64 perimeter();
    }

That is a complete trait. Any type that satisfies Shape has `area` returning `f64` and `perimeter` returning `f64`. A trait is not a base type or a place where data lives; it is a contract, checked like one.

A trait may also carry default implementations, the one place it holds logic. A type inherits a default unless it overrides it:

    trait Named {
        str name();
        str describe() {
            return "an object named " + self.name();
        }
    }

`name` has no body, so every implementor must supply it. `describe` comes free and may be overridden. Defaults may call required methods, which is why the contract is declared first.

A trait can require the minimum and hand you convenience built on top. The required method is the load-bearing wall; the default is the furniture. Supply the wall and the furniture comes with the room.

Trait methods may take parameters and may be `const`, like ordinary methods. They may not carry data or be `static`: a trait method is about a value.

6.5 Implementing a Trait: Making the Promise

A type satisfies a trait with an extend block that names the trait after a colon:

    struct Circle {
        f64 radius;
    }

    pub extend Circle : Shape {
        f64 area() {
            return 3.14159 * self.radius * self.radius;
        }

        f64 perimeter() {
            return 2.0 * 3.14159 * self.radius;
        }
    }

    struct Square {
        f64 side;
    }

    pub extend Square : Shape {
        f64 area() {
            return self.side * self.side;
        }

        f64 perimeter() {
            return 4.0 * self.side;
        }
    }

The colon reads as "satisfies": `Circle : Shape` means Circle satisfies Shape. Nothing says "a Circle is a kind of Shape." Circle remains exactly Circle; the block merely promises the two methods. There is no inheritance or hierarchy.

Implementing a trait means filling in the checklist. The trait names the questions; the extend block supplies this type's answers.

Coral's conformance is nominal, not structural. In a structural language, a type satisfies an interface by happening to have the right methods, so a conformance can appear or vanish when someone else's code changes. Coral requires an explicit extend block. The payoff: searching for `: Shape` returns every type that claims to be Shape, and nothing else.

The compiler checks the declared conformance method by method. Each must exist with the exact signature. E1202 is a signature mismatch; E1203 is a missing required method. A type cannot half-implement a trait.

A type may satisfy several traits, each in its own block, each an independent promise:

    pub extend Circle : Shape {
        f64 area() { return 3.14159 * self.radius * self.radius; }
        f64 perimeter() { return 2.0 * 3.14159 * self.radius; }
    }

    pub extend Circle : Named {
        str name() { return "circle"; }
    }

Circle now keeps two promises. Traits do not form a hierarchy; Circle just promised twice.

A type may conform to a given trait only once: one implementation of `Shape::area` for Circle. That uniqueness lets the compiler resolve `area` in one step when the concrete type is known. E1201 reports the same method defined twice across blocks.

6.6 Inherent Methods and Trait Methods in the Same Type

A useful type usually has two kinds of methods. Inherent methods are its own vocabulary. Trait methods are its obligations to an interface. Coral keeps them in separate extend blocks.

Inherent methods are the type's own features; trait methods are promises made to an interface.

    pub struct Stack<T> {
        Vec<T> items;
    }

    pub extend<T> Stack<T> {
        static Stack<T> new() {
            return Stack<T> { .items = Vec<T>::new() };
        }

        void push(T value) {
            self.items.push(value);
        }

        T pop() {
            return self.items.pop();
        }

        bool isEmpty() const {
            return self.items.isEmpty();
        }
    }

`push`, `pop`, `isEmpty`, and the constructor are Stack's own API, so they live in the inherent block. If Stack should also be iterable, that promise goes in its own block:

    pub extend<T> Stack<T> : Iterable<T> {
        // the methods the Iterable trait requires, written in terms of self
    }

The two blocks answer different questions. A trait change shows in the trait block; an API change shows in the inherent block. A reader asking how the type meets its contracts gets a short, auditable answer.

6.7 Generic Traits and Generic Extends

Traits and extends can both be generic. The standard library's `Result<T, E>` is either `Ok` carrying a `T` or `Err` carrying an `E`, so its methods must work for every choice of both:

    pub variant Result<T, E> {
        Ok  { T value; },
        Err { E error; }
    }

    pub extend<T, E> Result<T, E> {
        bool isOk() { ... }
        T unwrap() { ... }
        T unwrapOr(T defaultVal) { ... }
    }

The block matches the type it extends: both are parameterised by `T` and `E`. Every method is available for every instantiation, and the compiler monomorphises each separately. `Result<i32, IoError>` and `Result<str, ParseError>` get their own copies, as though you had written two types. A generic extend is not a runtime template; it is a family of methods generated per use, with no indirection or boxing.

Inside `unwrap`, the `Ok` field and the return type are both `T`, so the compiler is satisfied. The parameter is in scope throughout the block, in signatures and bodies.

Both directions are common. A generic type can implement a non-generic trait (a container becomes iterable regardless of contents). A non-generic type can implement a generic trait (a type joins a family parameterised by element type).

6.8 The Built-In Traits: @drop and @toStr

Coral defines a few traits in the language, spelled with `@`. `@drop` and `@toStr` are wired in automatically. `@drop` is called at the right moment; `@toStr` is found by the formatter. You opt in with an ordinary extend block; the magic is on the compiler's side.

RAII, and why @drop exists

Start with `@drop`, the destructor trait. In C, opening a file, locking a mutex, or allocating a buffer means remembering to close, unlock, and free on every exit path. RAII (resource acquisition is initialisation) ties a resource's lifetime to a variable's scope, releasing it on every exit path.

RAII is a bargain the language keeps: a variable takes ownership on acquisition and releases it when its scope ends, whether by normal finish, early return, or error path.

Coral expresses RAII as a trait. A type that implements `@drop` provides `void drop()`, and the compiler invokes it when a value goes out of scope:

    pub extend FileHandle : @drop {
        void drop() {
            close(self.fd);
        }
    }

The contract is `void drop()`, no parameters, no return. A FileHandle local is closed at scope end, including early exits via `return`, `break`, or an error path. A `Vec<FileHandle>` frees its handles when the vector is dropped, because its drop recursively drops elements.

    void copyLogs() {
        FileHandle source = FileHandle::open("access.log");   // acquired
        FileHandle dest   = FileHandle::open("access.bak");   // acquired
        copyContents(&source, &dest);
        // both files close here, at scope end, even if copyContents returned early
    }

You never wrote `source.drop()` or `dest.drop()`, and you should not. Cleanup happens at a place you can point at: the closing brace.

Which types should implement `@drop`? One that owns a resource: a heap buffer, file, lock, or socket. A bundle of numbers like a Point should not; an empty `drop` is noise. Implement `@drop` exactly when the type owns something that must be given back.

@toStr: teaching a type to print itself

`@toStr` is the formatting trait. A type that implements it can be printed or converted to a `str`, and the compiler finds the implementation at the call site:

`@toStr` teaches a type to describe itself as text. With it, `println("{}", p)` knows exactly what to render.

    pub extend Point : @toStr {
        str toStr() {
            return "Point(" + formatFloat(self.x) + ", " + formatFloat(self.y) + ")";
        }
    }

With this conformance, `println("{}", point)` dispatches to `Point::toStr`. `std::io::ios` documents `toStr` as an inbuilt trait like `@drop`; the `any toStr` case in the formatter auto-wires the call.

6.9 RAII in Practice, and How to Opt Out

Automatic cleanup is the right default, but it is not free. The compiler must track every local that implements `@drop` and generate cleanup on every path out of scope. Most application code should leave it on. Some code, the standard library above all, manages memory by hand and does not want generated destructors. Coral offers three opt-outs: one variable, one block, or a whole file. Choosing wrong means a double free or a leak.

The opt-outs say "I will handle this cleanup myself" over increasingly broad areas. They exist for hand-managed code; beginners rarely need them.

`#[[no_drop_all]]`: turn RAII off for a whole file

`#[[no_drop_all]]` is a file-level attribute. It does not modify a declaration; it appears once, before the first declaration, and disables drop-trait auto-RAII for the whole file:

    #[[no_drop_all]]

    pub struct Arr<T, N> {
        // ...
    }

With it present, the compiler resolves no drop methods for locals and emits no unwind calls; ownership is manual, through `free` or `dispose`. Every file in the standard library and compiler sources carries it. First, intent: library code frees bytes deliberately, without hidden destructors. Second, build speed: resolving and emitting drops is work the library has declined.

A file without `#[[no_drop_all]]` gets automatic RAII for any local whose type implements `@drop`. Library code opts out, application code opts in. The attribute rides on each declaration, so a library file merged into a user's build unit keeps its setting.

Inside a `#[[no_drop_all]]` file, destructors are never called for you, so a type that owns memory must free it explicitly. The std's `String` is the pattern: a `free()` method plus a separate `@drop` conformance for user code:

    pub struct String {
        u8* ptr;
        usize len;
        // ...
        void free() {
            dealloc<u8>(self.ptr);
        }
    }

    pub extend String : @drop {
        void drop() { self.free(); }
    }

In a `#[[no_drop_all]]` library file, calls to `s.free()` are written by hand. In application code, the String frees itself at scope end.

`#[[no_drop]]`: turn RAII off for one variable or one block

`#[[no_drop_all]]` is the sledgehammer. The scoped tool you will actually reach for is `#[[no_drop]]`. On a variable it excludes that variable from auto-RAII; on a block it excludes every local inside, nested blocks included:

    void processInChunks(File* f) {
        #[[no_drop]]
        u8* buffer = alloc<u8>(65536);      // manual lifetime

        defer {
            dealloc<u8>(buffer);
        }

        while (true) {
            usize n = readChunk(f, buffer, 65536);
            if (n == 0) break;
            handle(buffer, n);
        }
    }

The buffer carries `#[[no_drop]]` because its lifetime is managed by the `defer` block. Opt out for exactly this value and take responsibility in one visible place. The attribute says "I will remember to free this," and the `defer` makes that literal.

When is `#[[no_drop]]` the right tool, and when is it a mistake? Three honest cases:

    - A value whose lifetime is longer than its scope, handed back out of the
      function, stored in a long-lived structure, or moved to another owner.
    - A value managed by an explicit mechanism (defer, a refcount, a pool) so
      that RAII on the variable would be a second, competing owner.
    - A value obtained from a foreign interface that the caller does not own and
      must not release, such as a borrowed C handle.

The dishonest case: a value whose variable lifetime really is its resource lifetime, annotated out of laziness or fear. That annotation says "I will remember," and humans do not always remember. Use `#[[no_drop]]` only where nothing else will do.

Sealing a type: #[[extend]] and #[[no_extend]]

Two attributes govern whether later code may grow a type. By default a type is open: anyone who can see it may add methods with an extend block. `#[[extend]]` makes that permission explicit. `#[[no_extend]]` forbids further blocks:

    #[[no_extend]]
    struct SecurityToken {
        u64 secret;
        i64 expiry;
        // ...
    }

This seals a type so its behaviour is exactly the methods it ships. No third party can add a method that changes an operation's meaning. Use it where invariants must not be circumvented: an opaque handle, a fixed state machine, a security token. Most types want to be open, so sealing should be a decision.

The four drop diagnostics, E1301 to E1304

The compiler guards the four ways drop goes wrong.

E1301, explicit call to a drop method disallowed. Writing `x.drop()` is an error. Drop is driven by scope termination, so a manual call invites a double free. Let the scope do it, or opt out with `#[[no_drop]]` and provide a normal cleanup method:

    void broken(FileHandle* f) {
        f->drop();          // error E1301: cannot call drop() explicitly
    }

    void right(FileHandle* f) {
        // let RAII close it at scope end
    }

    pub extend FileHandle {
        void closeNow() {      // a normal method you may call yourself
            close(self.fd);
        }
    }

    void manual(FileHandle* f) {
        #[[no_drop]] FileHandle h = *f;
        h.closeNow();           // explicit cleanup, and RAII was told to stand down
    }

E1302, no drop on a type whose size varies with comptime conditions. A fixed-layout destructor cannot be sound when the size is unknown until the comptime block resolves. The fix is to give the type a fixed size, or manage it without `@drop`.

E1303, field moved out before the drop runs. Removing a field and leaving the struct to be dropped would run the destructor on partially uninitialised memory:

    struct Holder {
        String name;
        Vec<String> tags;
    }

    void broken(Holder h) {
        String stolen = h.name;   // moves name out of h
        // h is dropped at scope end, but its name field is gone -> E1303
    }

The fix is to drop or transfer the whole value, or to replace the moved field with a valid one before the scope ends.

E1304, a capability used through a type parameter. A generic body may call any operation on a `T`, but the compiler checks that the operation exists only at instantiation. Ask a generic to print its `T` (needing `@toStr`), then instantiate with a type that lacks it; the error names that type:

    void printer<T>(T value) {
        println("{}", value);   // fine here; each instantiation must supply @toStr
    }

    struct Opaque { i32 id; }   // no @toStr

    printer(Opaque { .id = 1 });  // error E1304: Opaque has no toStr capability

Coral does not let you write the requirement on the signature; there is no `T : @toStr` bound. The requirement is a property of the body, enforced at each instantiation. To check it directly, inspect the type in a `comptime` block, as Chapter7 shows.

Together: every automatic drop happens and is not called by hand (E1301), is on a fixed-layout type (E1302), receives every field it expects (E1303), and has the capabilities a generic relies on (E1304).

6.10 Dynamic Dispatch: any Trait

Every conformance so far has been static: with the concrete type known, `area` resolves to one implementation with no runtime lookup. When the concrete type is unknown, as in a mixed list of circles and squares, use `any Trait`.

A universal remote controls any television that speaks the standard signal. It holds a reference to one plus enough knowledge to send commands; which television is decided when you point it.

`any Shape` means "some kind of shape, found out at runtime." The value carries the object and a way to reach its Shape methods, so one loop handles a Circle and a Square without being rewritten.

    Vec<any Shape> shapes = Vec<any Shape>::new();
    shapes.push(Circle { .radius = 1.0 });
    shapes.push(Square { .side = 2.0 });

    for (any Shape s : shapes) {
        println("area = {}", s.area());
    }

An `any Shape` value is a fat pointer: a reference to the value and a reference to its Shape implementation. `s.area()` dispatches through the second. This is a trait object, the dynamic half of polymorphism: the call site does not know the concrete type.

A trait object costs an extra indirection per call and generally cannot be inlined across the boundary. It is a pointer-sized pair, twice the space of a plain reference. It carries only the trait's methods: through `any Shape` you can call `area` and `perimeter`, but not a Square-only method. The trait is the window.

Keep dynamic dispatch at boundaries where the concrete type is genuinely unknown: a heterogeneous collection, a plugin registry, a callback. Keep internals static. A generic `T` constrained to Shape is just as capable with no indirection when the compiler sees the type; use `any Shape` only when it cannot. Both share the trait, so switching changes one signature.

Coral has no `as` cast; write a conversion with the target type in parentheses, as in `(Circle)x`. The wildcard in a pattern is `else`, never an underscore. In a `switch` over `any Shape`, handle what you need and let `else` catch the rest.

6.11 Static Polymorphism with Generics

A generic function works for every type that can do what its body asks. The body is the requirement: `sum += s.area()` works for any `T` with an `area` method. There is no bound clause:

    f64 totalArea<T>(Vec<T> shapes) {
        f64 sum = 0.0;
        for (T s : shapes) {
            sum += s.area();
        }
        return sum;
    }

The compiler fills the blank separately for each type you use, so each version is as fast as one written by hand. The blank is `<T>`, covered next chapter.

Inside `totalArea`, `s.area()` is checked at instantiation. With `Vec<Circle>`, the compiler generates `totalArea<Circle>` with a direct call to `Circle::area`. With `Vec<str>`, the error names `str` as missing the operation.

This is static polymorphism, and it is free. `totalArea` is monomorphised for each `T`: no vtable, no indirection, no dispatch, no runtime type checking. Prefer a generic when the types are known at compile time; use `any Trait` otherwise.

    // static: monomorphised, direct calls, chosen at compile time
    f64 totalArea<T>(Vec<T> shapes) { ... }

    // dynamic: one function, indirect calls, chosen at runtime
    f64 totalAreaDyn(Vec<any Shape> shapes) {
        f64 sum = 0.0;
        for (any Shape s : shapes) {
            sum += s.area();
        }
        return sum;
    }

The first cannot accept a mixed vector because `T` must be a single type. The second can, because every element is `any Shape`. Homogeneous and known at compile time means a generic; heterogeneous or runtime-known means `any`.

With no bounds, a generic's requirements are exactly the operations its body names. To learn what a generic needs, read the body. The cost is that a caller does not see the requirement until an instantiation fails, so document expected capabilities in a comment. E1304 enforces it, naming the type and the missing operation.

6.12 A Worked Example: One Printer for a Whole Tree

Traits earn their keep when one algorithm works across many shapes. A filesystem tree holds files and subdirectories together, and you want one printing routine for all of it. The collection is heterogeneous at runtime, so `any` is the right dispatch.

    trait TreeNode {
        str label();
        Vec<any TreeNode> children();
    }

    struct FileNode { str path; Vec<any TreeNode> kids; }

    pub extend FileNode : TreeNode {
        str label() { return self.path; }
        Vec<any TreeNode> children() { return self.kids; }
    }

    struct DirNode { str name; Vec<any TreeNode> kids; }

    pub extend DirNode : TreeNode {
        str label() { return self.name; }
        Vec<any TreeNode> children() { return self.kids; }
    }

The printing algorithm is written once, against the trait:

    void printTree(any TreeNode root, i32 depth) {
        for (i32 i = 0; i < depth; i += 1) {
            print("  ");
        }
        println("{}", root.label());
        for (any TreeNode child : root.children()) {
            printTree(child, depth + 1);
        }
    }

`printTree` does not know about files or directories. It knows the two methods TreeNode declares and recurses through them. Add a conforming symlink, device, or network mount, and it prints without a line of `printTree` changing.

Why `any TreeNode` rather than a generic? The tree is heterogeneous, so the children list must hold different concrete types. A generic could print a homogeneous `Vec<T>` but not a mixed tree.

Now add a second behaviour over the same data, counting nodes. The shape repeats: another recursion through the same two methods:

    i32 countNodes(any TreeNode root) {
        i32 total = 1;                       // the root itself
        for (any TreeNode child : root.children()) {
            total += countNodes(child);
        }
        return total;
    }

Two operations, one set of node types, and neither mentions FileNode or DirNode. Data defines the cases; traits define the operations; one algorithm serves every type that keeps the promise. Without traits, each operation would need a switch over node kind, and every new kind would mean editing both. With traits, adding a kind adds a conformance and touches nothing else. This is the expression problem from Chapter13.

6.13 A Second Worked Example: A Plugin Registry

The tree used `any` because the collection was heterogeneous. A plugin registry is the same shape because plugins are chosen at build or load time, so the program cannot name their types at compile time.

    trait Plugin {
        str name();
        void run();
        void shutdown() { }        // default: most plugins have nothing to release
    }

    struct Registry {
        Vec<any Plugin> plugins;
    }

    pub extend Registry {
        void register(any Plugin p) {
            self.plugins.push(p);
        }

        void runAll() {
            for (any Plugin p : self.plugins) {
                println("running {}...", p.name());
                p.run();
            }
        }
    }

The registry never mentions a concrete plugin type. It stores `any Plugin` and calls the trait's methods. A new plugin is a struct plus a conformance; registry code is untouched. `shutdown` has a default body, so a plugin with no resources writes nothing.

Now make teardown automatic. Each concrete plugin that owns something conforms to `@drop` and routes its destructor to `shutdown`:

    struct NetworkPlugin { Socket* sock; }

    pub extend NetworkPlugin : Plugin {
        str name() { return "network"; }
        void run() { self.sock->poll(); }

        void shutdown() {
            self.sock->close();
            dealloc<Socket>(self.sock);
        }
    }

    pub extend NetworkPlugin : @drop {
        void drop() { self.shutdown(); }
    }

The `Plugin` conformance promises the interface; the `@drop` conformance makes cleanup automatic. Neither the registry nor its callers call `shutdown` by hand; the destructor does, at scope end. Small interface, automatic lifetime, no forgotten cleanup.

6.14 Exercises

1. Comprehension. Explain the difference between a method in an inherent extend block and a method in an extend Trait block. Give one method that belongs in each for a `Stack<T>`, and say who decides which block it goes in.

2. Comprehension. Why can a const method be called on a const value but a non-const method cannot? Write a two-sentence explanation a C programmer would accept, and point at the diagnostic family that enforces it.

3. Implementation. Declare a trait `Comparable` with a method `lessThan(other) bool`, implement it for `Point` (compare by distance from the origin) and for a struct of your choice. Then write a generic `minimum<T>(T a, T b) T` whose body calls `lessThan`, and explain where the requirement that `T` has that method is checked.

4. Implementation. Add a `@toStr` conformance to a struct with three fields so that `println("{}", instance)` prints all three. Then add a wrong-way version where you print the fields in the wrong order and explain why the compiler cannot catch that.

5. Built-ins. Give one type that should implement `@drop` and one that should not, with a one-sentence reason each. For the one that should, write the conformance and the correct usage; for the one that should not, explain what a `drop` would even mean.

6. Drop attributes. You are writing a function that allocates a large buffer, hands it to a C library that frees it later, and returns. Which attribute applies to the buffer, `#[[no_drop]]` or `#[[no_drop_all]]`, and why is the other the wrong tool here? Write the function.

7. Diagnostics. Trigger each of E1301, E1303, and E1304 with a small example, and write the corrected version beside it. For E1302, describe in your own words why a comptime-variable-size type cannot have a fixed destructor.

8. Dispatch. Write a `Vec<any Shape>` holding a Circle, a Square, and a Triangle. Print each area. Why can the vector not have a concrete element type? Then rewrite the loop to use a generic function and explain what changes about the types accepted.

9. Generic versus dispatch. Write the same operation twice: once as a generic `totalArea<T>` and once as `totalAreaDyn(Vec<any Shape>)`. State what each accepts, what each costs at runtime, and which you would choose when the set of shapes is fixed at compile time.

10. Design. You are designing a serialisation library. Decide, with a sentence for each, what should be a trait, what should be a generic function, and what should be a plain concrete function. Then name one thing that goes wrong if you make the wrong one a trait.

11. Defaults. Declare a trait with three methods, one of which has a default body calling the other two. Implement it for a type, override the default, and explain when overriding is right and when it is over-engineering.

12. Meta. Coral has no inheritance; a type acquires behaviour only by extending or conforming, and sealing requires an explicit `#[[no_extend]]`. Argue that this is a limitation, then argue that it is a strength. Which position do you find more convincing, and why?

13. Sealing. Declare a `#[[no_extend]]` opaque handle with a private field and one public accessor, and write what a caller loses when the type is sealed and what the author gains.
