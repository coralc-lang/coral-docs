Chapter40

Live Examples: Inline Assembly and Clobbers

Telling the Compiler What It Cannot See

Chapter20 gave the FFI `asm`, the escape hatch below the boundary; Section20.8 is the syntax reference and this chapter the workshop. Nine small functions isolate the contract piece by piece: clobbers, outputs, inputs, read-write operands, digit constraints, `volatile`, full clobber lists, and a wrapper that hides every register name.

The template is the easy part: a string emitted verbatim. Correctness comes from the note card beside it, the outputs, inputs, clobbers, and qualifier. An `asm` block is a promise the compiler cannot verify. An honest note card keeps the code correct and fast; a dishonest one fails differently at each optimisation level and on each machine.

Two honesties. Inline assembly is architecture-specific; the target C compiler assembles it, so `%0`, `"=a"`, and `%%rsp` are C inline-assembly spelling, which is why the standard library keeps per-platform files. The examples are x86-64 Linux; the lessons transfer, the register names do not. Second, the compiler does not check the note card: it passes constraints through and never inspects clobbers. A wrong constraint, unlisted clobber, or missing `"memory"` is a silent miscompile. E0401, E0402, and E0403 are intentions, not checks.

The examples use `println`, `alloc`/`dealloc` for raw buffers, and `AtomicU64` for comparison. Each block repeats its imports.

40.1 The Shortest Useful Block: A Compiler Barrier

The problem. Two ordinary stores must reach memory in order. Within one thread the compiler may reorder non-aliasing stores; across threads or against a memory-mapped device, somebody observes the difference. Stop the compiler moving them past each other, without writing an instruction.

The idea. The shortest useful block has an empty template and one clobber, `"memory"`. No instructions are emitted; the block exists for the note card. `"memory"` says the block may read and write any memory, so values cannot stay in registers across it and accesses cannot move past it. `volatile` keeps a promise-only block from being deleted, and `::` skips the empty operand sections.

The implementation.

    // the empty template emits nothing; the block is only its note card
    void compilerBarrier() {
        // volatile keeps a promise-only block from being deleted
        // "memory" is the clobber: the block may touch any memory
        asm volatile { "" ::: "memory" }
    }

    // publish a payload, then raise the flag that announces it
    void publish(u64* data, u64* flag, u64 value) {
        *data = value;          // the payload
        compilerBarrier();      // the compiler may not move the next store above this
        *flag = 1u;             // the announcement
    }

    import(lib) std::io::ios { println };

    void main() {
        u64 data = 0;
        u64 flag = 0;
        // publish keeps the barrier between the two stores
        publish(&data, &flag, 42u);
        println("data {} flag {}", data, flag);
    }

Line by line: `asm volatile` is the statement, `""` the template, the first `:` opens and second closes an empty output section, the third opens empty inputs, and `"memory"` is the clobber list. It lowers to `__asm__ volatile("" ::: "memory")`, forbidding the compiler from moving `*flag = 1u` above `*data = value`. The barrier names no variables; it is about all memory.

Cost and notes. No instructions and no run-time cost, only compile-time reloads the compiler might otherwise avoid. That is the point: a fence in the compiler's model, not the hardware's. If the processor must also observe the order, use a separate fence instruction with its own `"memory"` clobber. This is the standard library's `memoryBarrier`.

Edge cases. `"memory"` is the only clobber because memory is the only thing touched. `"cc"` would be wrong here, since an empty template leaves condition codes alone. A barrier is not a substitute for atomics: it orders the compiler's view, but two unsynchronised stores remain a data race.

Variation. Put the barrier on both sides of a critical region, or between the loads and store of a hand-rolled lock, and reason about which reorderings it forbids. Then write `asm volatile { "mfence" ::: "memory" }` and compare: the hardware fence also orders processor accesses, while the Coral-side contract stays the same.

40.2 Reading a Register Out: An Output Operand

The problem. Some values live only in a register. The stack pointer is the classic case: you want a snapshot, and no Coral expression names a register. The block must hand a register's value back to a Coral variable.

The idea. An output operand has an `=` constraint and binds a Coral lvalue. `"=r"(sp)` says the block writes a general-purpose register whose value then belongs in `sp`. The compiler chooses the register for `%0`; the template writes whatever `%0` is. A literal register uses a doubled percent, `%%rsp`, because a single `%` belongs to the placeholder.

The implementation.

    usize readStackPointer() {
        usize sp;
        // "=r" is an output operand; the compiler picks the register for %0
        asm volatile { "movq %%rsp, %0" : "=r"(sp) }
        return sp;
    }

The output section is `"=r"(sp)`: operand `%0` bound to `sp`. The template names `%%rsp` literally and the operand as `%0`. The compiler picks a register, the block fills it, and afterward the value is stored into `sp`. The `=` says `sp`'s prior value is dead, correct because nothing reads it first.

Cost and notes. One register-to-register move and one store. The cost is in the constraint: `"=r"` lets the compiler fit the block into its existing allocation, which is why `"r"` is the default and a fixed register is reserved for instructions that demand one. `"=a"` here could force a spill.

Edge cases. The value is a snapshot when the block runs, and the compiler may schedule the block around other code; do not assume it lands between surrounding statements. `%%rsp` holds the stack pointer as the compiler arranged its frames, not a human picture of the call stack. An output needs no clobber for its own register, because `=` says it is written.

Variation. Add a second output and watch the numbering: outputs come before inputs, so they are `%0` and `%1`. Then change `"=r"` to a fixed register and observe less scheduling freedom. The looser constraint is better whenever the instruction allows it.

40.3 Two Outputs at Once: The Timestamp Counter

The problem. Some instructions split their result across two registers, and you want both halves at once. A function returning a small struct is the Coral shape, and `asm` can fill both halves from two outputs.

The idea. Name two output operands with the fixed-register constraints the instruction requires. `"=a"` and `"=d"` name the two written registers, each bound to a local. Outputs are numbered first, so they are `%0` and `%1`, though the template mentions neither. A block whose only clobbered registers are outputs needs no clobber list.

The implementation.

    struct Timestamp {
        u32 low;
        u32 high;
    }

    Timestamp readTimestamp() {
        u32 lo;
        u32 hi;
        // two outputs "=a" and "=d"; outputs are numbered %0 and %1
        asm volatile { "rdtsc" : "=a"(lo), "=d"(hi) }
        return Timestamp { .low = lo, .high = hi };
    }

The constraints pin the two halves to the registers the instruction reports through. Nothing is loaded before the block, since both operands are outputs, and afterward each named register is stored into its local. The locals are gathered into the struct, a type a caller can hold without knowing about registers.

Cost and notes. A few cycles and two register-to-memory stores. Fixed constraints cost nothing here, because the instruction has only one place for each half. The signature is entirely Coral, and that is the property to preserve: a register name in a public signature means the abstraction has leaked.

Edge cases. Forgetting one output leaves a destroyed register unaccounted for; bind it as an output or name it as a clobber, depending on whether you want its value. The counter is not a clock: it varies by core and machine, measuring elapsed ticks within a process. For wall-clock time, use `std::time::nowMonotonic()`.

Variation. Combine the halves into one `u64` with shifts and compare two reads to see the counter advance. Then add a third output for a register the instruction touches but you were not capturing; the moment a destroyed register stops being an output, it must become a clobber.

40.4 A Raw Syscall: Digit Constraints and a Full Clobber List

The problem. The kernel's syscall interface has no libc wrapper for what you need, and the argument-to-register mapping is fixed by the ABI. You must place each argument, issue the call, read the result, and tell the compiler about every register the call does not preserve.

The idea. The template moves arguments with no fixed constraint into ABI registers, issues the call, and reads the result. `"=a"(ret)` stores the result. `"0"(number)` ties the call number to output zero, sharing the result register. Three inputs use fixed-register constraints for the first three argument registers; the last three use `"r"` and the template moves them. Every destroyed register not already an operand is clobbered, and `"memory"` says the call may touch arbitrary memory.

The implementation. This is the general six-argument wrapper; the standard library's `mmap` is a specialized form of the same shape.

    i64 rawSyscall6(usize number, usize arg1, usize arg2, usize arg3,
                    usize arg4, usize arg5, usize arg6) {
        i64 ret;
        // the template moves only the args the compiler was free to place
        asm volatile {
            "movq %5, %%r10\n\t"
            "movq %6, %%r8\n\t"
            "movq %7, %%r9\n\t"
            "syscall\n\t"
            "movq %%rax, %0"
            // output %0: "=a" binds the result register to ret
            : "=a"(ret)
            // "0" ties the call number to output %0; "D","S","d" fix ABI regs
            : "0"(number), "D"(arg1), "S"(arg2), "d"(arg3),
              "r"(arg4), "r"(arg5), "r"(arg6)
            // registers destroyed but not already operands, plus memory
            : "rcx", "r8", "r9", "r10", "r11", "memory"
        }
        return ret;
    }

    // a typed wrapper: callers see Coral types, never a register name
    i64 sysWrite(i32 fd, const cchar* buf, usize count) {
        return rawSyscall6(1u, (usize)fd, (usize)buf, count, 0u, 0u, 0u);
    }

    import(lib) std::io::ios { println };

    void main() {
        const cchar* msg = C"hello from a raw syscall\n";
        // fd 1 is standard output
        sysWrite(1, msg, 25u);
        println("done");
    }

Operand numbering is the heart: outputs first, then inputs, so `%0` is `ret`, `%1` `number`, `%2` `arg1`, through `%7` `arg6`. `"D"`, `"S"`, and `"d"` place the first three arguments, so the template moves only `%5`, `%6`, and `%7`. `"0"` makes `number` and `ret` one register: it holds the call number at entry, and the template copies the result back. `"rcx"` and `"r11"` are clobbered because the call uses them; `"r8"`, `"r9"`, and `"r10"` because the template writes them. `"memory"` prevents caching across the block.

Cost and notes. A handful of moves, the call, and register pressure. `"r"` inputs are cheap because the compiler picks; fixed constraints are expensive because a live register may need spilling. Ask for a fixed register only when the instruction requires it. `sysWrite` is what the rest of the program should see, knowing nothing about `%5` or `"r10"`.

Edge cases. The clobber list must name every destroyed register that is not an operand; `"rcx"` and `"r11"` are most often forgotten because the template never mentions them. Omitting them lets the compiler keep a live value there, destroyed silently. Writing `"r"(number)` instead of `"0"(number)` puts the call number in the wrong entry register. `"memory"` is required even without a memory operand, because the call can touch unseen memory.

Variation. Write the one- and three-argument forms and notice that dropping arguments drops moves and clobbers, but never `"rcx"`, `"r11"`, or `"memory"`. Then replace the fixed constraints with `"r"` plus explicit moves and decide which reads more clearly.

40.5 An Atomic Read-Modify-Write: Why volatile and `"memory"` Matter

The problem. You want an atomic read-modify-write on a single word, written out rather than taken from the library. The point is not the instruction but that the compiler must be told, in two ways, about effects it cannot see.

The idea. `volatile` stops the compiler deleting or duplicating the block: a caller ignoring the result would otherwise leave a dead block. `"memory"` stops reordering other accesses across it, making it a fence. The cell carries `"+m"`: `+` says read and write, so the compiler must reload rather than reuse a cached copy. The register carrying the addend in and the old value out is read-write, either `"+r"` or an input tied to the output with a digit constraint.

The implementation.

    import(lib) std::concurrent::thread { AtomicU64 };
    import(lib) std::io::ios { println };

    u64 atomicFetchAdd(u64* cell, u64 delta) {
        u64 previous;
        // volatile: the block must run even when its result is unused
        asm volatile {
            "lock xaddq %0, %1"
            // "=r" output; "+m" says the cell is read as well as written
            : "=r"(previous), "+m"(*cell)
            // "0" ties the addend to output %0, reusing that register
            : "0"(delta)
            // "memory" orders other accesses; "cc" says condition codes die
            : "memory", "cc"
        }
        return previous;
    }

    void main() {
        u64 cell = 10u;
        u64 old = atomicFetchAdd(&cell, 5u);
        println("old {} cell {}", old, cell);   // old 10 cell 15

        // the library's reviewed note card for the same operation
        AtomicU64 counter = AtomicU64 { .value = 0 };
        counter.fetchAdd(1u);                   // the library's version of the same operation
        println("library {}", counter.load());
    }

`"=r"(previous)` is `%0`; `"+m"(*cell)` is `%1`. `"0"(delta)` is tied to operand zero, so the addend arrives in the register that leaves the previous value. The register is both input and output without a separate `"+r"`, and `+` on memory says the cell is read and written. `"cc"` is present because the operation writes condition codes, and `"memory"` orders other accesses.

Cost and notes. One locked instruction, tens of cycles, serialising and indivisible. The `"memory"` clobber forces reloads around the block, exactly what an atomic should force, because another thread may have changed memory. Compare `AtomicU64::fetchAdd`, the same operation with a reviewed note card and the version to use in real programs.

Edge cases. Remove `volatile` and the block becomes deletable when its result is unused, precisely when a lock-free update must still happen. Remove `"memory"` and the compiler may hoist a load above or sink a store below. A bare `"=m"` instead of `"+m"` tells the compiler the old value is dead, and it may discard a store another thread would observe. Each is a silent miscompile.

Variation. Compare-and-swap has the same shape. The instruction reads and writes the accumulator, so the accumulator is a read-write operand, `"+a"`, not a clobber:

    bool compareSwap(u64* cell, u64 expected, u64 desired) {
        u64 seen = expected;
        asm volatile {
            "lock cmpxchgq %2, %1"
            // "+a" is read-write: the accumulator is both input and output
            : "+a"(seen), "+m"(*cell)
            : "r"(desired)
            : "memory", "cc"
        }
        return seen == expected;
    }

Writing `"rax"` in the clobber list instead of binding `"+a"(seen)` claims the accumulator is destroyed while also feeding it an expected value, the contradiction E0402 names. The compiler does not check it today, so the wrong version builds and misbehaves.

40.6 A Read-Only Probe: Four Clobbers, or Four Outputs

The problem. An instruction reports through four registers, and you either want some of the information or only want the instruction to have run. The question is whether those registers are outputs, clobbers, or both.

The idea. They are either outputs or clobbers, never both. If you want the values, bind each register as an output, make selectors read-write, and leave the clobber list empty. If you want only to run the instruction, bind no operands and name all four as clobbers. Writing both is the contradiction E0402 describes.

The implementation. The capturing form, with the two selectors as read-write operands and no clobbers:

    struct CpuLeaf {
        u32 eax;
        u32 ebx;
        u32 ecx;
        u32 edx;
    }

    CpuLeaf cpuProbe(u32 leaf, u32 subleaf) {
        u32 a = leaf;
        u32 b;
        u32 c = subleaf;
        u32 d;
        // all four registers are outputs, so the clobber list is empty
        asm volatile {
            "cpuid"
            // "+a"/"+c" carry the selectors in and the results out
            : "+a"(a), "=b"(b), "+c"(c), "=d"(d)
        }
        return CpuLeaf { .eax = a, .ebx = b, .ecx = c, .edx = d };
    }

    // the same four registers, now described as clobbers instead
    void cpuProbeDiscard() {
        asm volatile { "cpuid" ::: "eax", "ebx", "ecx", "edx" }
    }

In the capturing form the four registers are all operands. The selectors use `+`, so `a` and `c` are initialised before the block and are read-write. Since the whole destroyed set is accounted for, the clobber list is empty. In the discarding form the four registers are clobbers and nothing is captured. Both are honest; writing operands *and* clobbers claims the registers are simultaneously live and destroyed.

Cost and notes. The capturing form costs four stores and constrains the compiler to four fixed registers. The discarding form costs nothing beyond the instruction and constrains nothing, because with no operands there is nothing to allocate. It is rarely what you want, but as a probe or serialising barrier it cleanly demonstrates a clobber-only block.

Edge cases. Binding a `u64` to a 32-bit register constraint is the size mismatch E0401 reserves a code for, a real error the compiler does not catch. One register is reserved for a particular addressing model on some targets, another reason to keep per-platform files. The capturing form needs `+` on selectors because the instruction reads before writing; a bare `"a"(a)` would make the write an unlisted destruction.

Variation. Delete one output, leaving a register destroyed and unaccounted for, then name it as a clobber. You have converted an output into a clobber, the distinction this example is about. Do it for each register and watch the numbering shift.

40.7 The Wrong Ways, Part One: Missing `"memory"` and Missing `volatile`

The problem. These two mistakes make an `asm` block look correct and behave unpredictably: a block that touches memory without saying so, and a block with a side effect the optimizer deletes. Both are invisible at the source and vary with the optimisation level.

The first wrong way: no `"memory"`. Consider a store, then a block that announces it, with no `"memory"` clobber.

    void signalWrong(u64* data, u64* ready) {
        *data = 42u;
        // no "memory" clobber: the block never claims to touch data's memory
        asm volatile { "movq $1, (%0)" : : "r"(ready) }
    }

Because the block does not claim to touch arbitrary memory, the compiler may move `*data = 42u` after the block, or keep a copy in a register and skip the store if nothing reads it. The other thread sees the announcement first or no payload at all. The fix is 39.1's barrier folded in: add `"memory"`, and the store cannot cross. A block writing memory through a pointer must claim *all* memory, because the compiler cannot know what else the write aliases.

The second wrong way: no `volatile`. A block whose purpose is a side effect on a device or shared word, with no outputs and no `volatile`, is dead code to the optimizer.

    void pokeWrong(rawptr mmio) {
        // no output and no volatile: the optimizer sees a dead block
        asm { "movq $1, (%0)" : : "r"(mmio) }
    }

With no output and no `volatile`, the block has no observable result and is removed entirely. The program compiles, runs, and never pokes the device. `asm volatile` marks side effects that must not be dropped, reordered, or duplicated. A block whose output the caller uses is safe without `volatile`; a block whose only result is in memory or the world is not.

Cost and notes. The fixes cost nothing at run time; `"memory"` and `volatile` are notes, not instructions. They do cost optimisation: a `volatile` block with a `"memory"` clobber cannot be hoisted, combined, or elided. The nearest reserved code is E0403, a volatile write defeated by a non-volatile read. The specific mistakes above are not individually coded, and no E04xx check runs today.

Edge cases. `volatile` alone does not fix a missing `"memory"`: ordinary accesses can still be reordered around a volatile block. Conversely, `"memory"` does not keep a block from being deleted if it has no output and no `volatile`. `volatile` on `asm` differs from `#[[const]]`: `volatile` stops movement or removal, while `#[[const]]` promises no mutation. The const check does not look inside `asm` operands.

Variation. Take the working `publish` from 39.1, remove its `"memory"`, and build at `debug` and `release`. The `debug` build behaves correctly; `release` is where reordering appears. Then remove `volatile` from `pokeWrong` and confirm from the generated assembly that the instruction is gone.

40.8 The Wrong Ways, Part Two: Operand and Clobber Contracts

The problem. These mistakes concern the operands: an input the template quietly modifies, and a clobber that collides with a live operand. Both contradict the note card and block, and both are what a checker would catch if one existed.

The first wrong way: an input modified without `+`. The template writes its operand, but the constraint says input-only.

    u64 badIncrement(u64 x) {
        // "r"(x) says input-only, but the template writes that operand
        asm volatile { "addq $1, %0" : : "r"(x) }
        return x;
    }

`"r"(x)` tells the compiler `x` is read, not written, so after the block it may still hold the old value or reuse the register. The block wrote to a register the compiler believed it owned. The fix is `"+r"(x)`, saying the block reads the old value and produces the new one. The nearest reserved code is E0401.

The second wrong way: a clobber overlapping a live operand. A block binds an input to a fixed register and also names that register as a clobber.

    u64 addViaFixedReg(u64 a, u64 b) {
        u64 out;
        // "c" fixes b in RCX, so listing "rcx" as a clobber contradicts it
        asm volatile {
            "addq %%rcx, %0"
            : "=r"(out)
            : "0"(a), "c"(b)      // b lives in RCX
            : "rcx"               // wrong: RCX is also a live input
        }
        return out;
    }

`"c"(b)` places `b` in the fixed register, and `"rcx"` says that register is destroyed. Both cannot be true: the input would be destroyed before the block reads it, and which statement the compiler believes depends on the optimisation level. Delete `"rcx"`: a register that is already an operand is accounted for. This is E0402.

Cost and notes. The correct versions are free, correcting only the compiler's model. The wrong versions build, because constraints are copied through and clobber lists never inspected. The misbehaviour is a stale value, a wrong register, or an optimisation-dependent result, none pointing back to the block.

Edge cases. `+` is not a lighter `=`; it is the only accurate spelling when the template reads before writing, and using `=` leaves the old value undefined. A digit constraint such as `"0"` is an alternative when the operand must share a numbered operand. The rule is one-directional: a register may be an operand without being a clobber, but not both.

Variation. Take the syscall wrapper from 39.4 and move `"r10"` from the clobber list to a fixed-constraint operand, then move it back. The two descriptions are exclusive, and choosing between them is the whole job of a clobber list. Then decide, for each of the four probe registers, whether it is an output or a clobber.

40.9 Quarantining the Target: One Wrapper, No Registers Anywhere Else

The problem. Every block here names x86-64 registers and is wrong on another architecture. Scattered through a program, that knowledge forces wholesale changes when the target does. The standard library keeps it in a file per platform; your program should too, behind a target guard and one small function.

The idea. Put every `asm` block behind a function with an ordinary Coral signature, in a module whose only job is target-specific code. Inside, `flag (arch)` selects the branch that assembles on the current target and provides a fallback. Callers import the module and call the function, never seeing a register, constraint, or clobber. This is Chapter20's FFI wrapper applied one level down.

The implementation. The target-specific module, the only file in the program that mentions a register:

    // cycles.crl, quarantined target code
    pub u64 readCycleCounter() {
        u32 lo = 0u;
        u32 hi = 0u;
        // flag (arch) picks the target branch at compile time
        flag (arch) {
        x86_64 => {
            asm volatile { "rdtsc" : "=a"(lo), "=d"(hi) }
        },
        else => {
            // no counter on this target; the caller gets a defined zero
        }
        }
        // the two halves are gathered into one Coral integer
        return ((u64)hi << 32u) | (u64)lo;
    }

And the program that uses it, which never sees the assembly:

    import cycles;
    import(lib) std::io::ios { println };

    void main() {
        u64 t0 = readCycleCounter();
        // ... work ...
        u64 t1 = readCycleCounter();
        // the caller never sees a register or a constraint
        println("elapsed ticks {}", t1 - t0);
    }

The module exports one function with a pure Coral signature, `u64 readCycleCounter()`. `flag (arch)` decides at compile time whether the target branch is included, so on a non-x86 target the asm is not compiled and the fallback defines the result. The caller writes `readCycleCounter()` and nothing else.

Cost and notes. No run-time cost; if the compiler inlines the small function, the call disappears. The cost is organisational and small: one module, a handful of lines. A port touches one file. For another architecture, only `cycles.crl` changes, or a sibling implementation is added, as the standard library adds platform files. The rest of the program does not change.

Edge cases. The fallback must produce a *defined* value; zero is honest for a counter that does not exist, while an uninitialised local would compile and misbehave. Document the wrapper's contract: what the counter means, whether it can repeat or go backward, and what the fallback does. Keep the exported surface small, and keep the asm in one place, because two clobber lists can drift.

Variation. Move `readStackPointer` from 39.2 and `rawSyscall6` from 39.4 into the same module, give each a register-free Coral signature, and write non-x86 implementations. Confirm a calling program is unchanged. That is the chapter's argument in miniature: unsafe code is small, local, and reviewed once; the program above is ordinary Coral.

40.10 Exercises

1. Comprehension. In one sentence each, what do the output, input, and clobber sections tell the compiler? Which is the only one that binds a Coral variable?

2. Comprehension. Explain `"="`, `"+"`, and a digit constraint such as `"0"`. For each, give a template fragment and operand declaration, and say which ties an input to a specific output.

3. Operand numbering. With two outputs and three inputs, state every operand's number and which one `"1"` refers to. Why are outputs numbered before inputs?

4. Implementation. Write `rawSyscall1(u64 number, u64 arg1)`, the one-argument form of 39.4, with the correct clobber list. Which clobbers are required by the call itself, and which only if you moved more arguments? Then wrap a no-argument syscall.

5. Clobbers. The syscall block in 39.4 names `"rcx"` and `"r11"` though the template never mentions them. Explain why and what goes wrong if you omit them. Why is `"rax"` not listed?

6. Correctness. A colleague writes an input with plain `"r"` and the template modifies it. Show the corrected block, name the closest reserved diagnostic, and explain why the compiler did not report it.

7. Correctness. A block lists `"rcx"` as a clobber and also passes an input with `"c"`. What contradiction is written, which reserved code names it, and what is the one-line fix?

8. Volatility. Write a non-volatile `asm` block whose only effect is a store through a pointer, show why the optimizer may remove it, then fix it with `volatile` and with a used output. Which fix is appropriate when, and why does `volatile` alone not fix a missing `"memory"`?

9. Wrapper design. Put `readCycleCounter` and `readStackPointer` behind one module with Coral signatures and `flag (arch)` guards. State each contract, and explain why a caller in another module can be written once and built for any target.

10. Design and meta. Choose an instruction the compiler will not emit and design the wrapper that hides it: signature, constraints, clobbers, target guards, fallback. Then argue the other side: describe one task where `asm` is the wrong call, and name the library function or ordinary Coral code that should have been used.
