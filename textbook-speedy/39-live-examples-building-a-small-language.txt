Chapter39

Live Examples: Building a Small Language

A Tokenizer, a Parser, and an Interpreter You Can Read

Every program that reads a program, a compiler, an interpreter, a linter, a config loader, the query planner inside a database, is built from the same three parts: a lexer that turns text into tokens, a parser that turns tokens into a tree, and an evaluator that walks the tree and produces a result. The parts sound like folklore, and most courses present them as a single terrifying monolith. They are not. Each is a page of code, and the whole pipeline fits in a chapter you can read in an afternoon.

The language we build here is deliberately tiny. It has integer values, arithmetic, comparison, variables, `if`, `while`, `print`, and nothing else, no types, no functions, no strings, no garbage collector. That is not a limitation of the technique; it is the point. Every real language adds features to these nine sections, but it does not replace them, and the shape of a production parser is the shape of the one below with more cases in the switches. The grammar is small enough to hold in your head, which means you can trace every decision and see why it is there.

The pipeline is a one-way street, and that shape is the lesson. Bytes become tokens (39.1); tokens become an abstract syntax tree (39.2, 39.3); the tree is either walked directly (39.5, 39.6, 39.7) or lowered to a flat instruction stream for a stack machine (39.8). Errors are values that ride along the whole way, carrying the source position that produced them (39.4), and at the end a read-eval-print loop wires the stages together against a real terminal (39.9). Each stage knows nothing about the ones after it: the tokenizer has never heard of a tree, and the evaluator has never seen a byte of source. That decoupling is why each stage can be tested alone.

The section headings are a build order, not a menu. Read them in order the first time. The tokenizer defines the `TokenKind` enum that every later switch reuses; the AST defines the `Expr` variant that the parser constructs and the evaluator matches; the environment that variables need (39.6) is the same hash map introduced in Chapter26. Where a section builds on an earlier declaration, the text says so, and only the new code is shown, so you are never reading the same hundred lines twice. If you want the whole thing at once, the REPL in 39.9 is the union of the parts, and its code block lays out the final assembly.

A word on values. Everything in this language is an `i64`. Booleans are integers too: a comparison yields `1` for true and `0` for false, and a condition is true exactly when it is nonzero. That single decision removes the entire type-checking pass from the interpreter, because there is nothing to check. It also means division by zero has to be given a meaning by hand, we define it as `0`, rather than being caught by a checker that does not exist. The warts are worth naming because they are the same warts every hand-rolled language starts with, and the exercise is to see precisely which chapter of this book you would turn to in order to remove each one.

A note on the imports. The programs use `import(lib) std::vec { Vec };` for growable arrays, `import(lib) std::text::string { String };` for owned mutable text, `import(lib) std::io::ios { println, print };` for output, `import(lib) std::mman { alloc, dealloc };` for the heap nodes of the tree, and `import(lib) std::collections::hashmap { HashMap };` for the environment of 39.6. `Option` and `Result` are in the prelude, as are `str` and the integer types. Each code block repeats the imports it needs. A `str` is a borrowed read-only view; a `String` is owned and mutable, and the REPL is careful about which one survives a line of input.

39.1 The Tokenizer

The problem. Turn a string of source text into a sequence of tokens: a small tagged record per number, name, operator, or delimiter, with the source position of each so that errors can point at it later.

The idea. Walk the bytes exactly once. Whitespace is skipped because it only separates tokens; a run of digits is a number; a run of letters, digits, and underscores is a name, which becomes a keyword if it happens to spell one; and every remaining byte is a one-character operator or delimiter. The output ends with a single sentinel token so the parser can always look one position ahead without checking whether it has run off the end. That sentinel is the one design decision that makes every later stage shorter.

The implementation.

    import(lib) std::vec { Vec };
    import(lib) std::io::ios { println };

    enum TokenKind {
        Number, Ident,
        Plus, Minus, Star, Slash, Less, Greater,
        LParen, RParen, LBrace, RBrace,
        Semi, Assign,
        If, Else, While, Print,
        Eof,
    }

    // a token is a tag, a source offset, a value, and its spelling
    struct Token {
        TokenKind kind;
        usize pos;
        i64 value;
        str text;
    }

    // byte classifiers keep the scanner's branches short
    bool isDigit(u8 c) { return c >= '0' && c <= '9'; }

    bool isAlpha(u8 c) {
        return (c >= 'a' && c <= 'z') || (c >= 'A' && c <= 'Z') || c == '_';
    }

    bool isAlnum(u8 c) { return isAlpha(c) || isDigit(c); }

    void pushToken(Vec<Token>* out, TokenKind kind, usize pos, i64 value, str text) {
        // text is a view into the source; nothing is copied
        out->push(Token { .kind = kind, .pos = pos, .value = value, .text = text });
    }

    Vec<Token> tokenize(str src) {
        Vec<Token> out = Vec<Token>::new();
        // i is the cursor over the source bytes
        usize i = 0;
        // one pass of the loop produces exactly one token
        while (i < src.len) {
            u8 c = src.at(i);
            // whitespace separates tokens but carries no meaning of its own
            if (c == ' ' || c == '\t' || c == '\n' || c == '\r') { i += 1; continue; }
            // a number: fold digits with Horner's rule
            if (isDigit(c)) {
                usize start = i;
                i64 value = 0;
                // consume the whole run of digits, not just the first
                while (i < src.len && isDigit(src.at(i))) {
                    value = value * 10 + (i64)(src.at(i) - '0');
                    i += 1;
                }
                pushToken(&out, TokenKind::Number, start, value, src.slice(start, i));
                continue;
            }
            // a name, or a keyword that looks exactly like one
            if (isAlpha(c)) {
                usize start = i;
                // a name runs until a byte that cannot be part of one
                while (i < src.len && isAlnum(src.at(i))) i += 1;
                str word = src.slice(start, i);
                TokenKind kind = TokenKind::Ident;
                // the four reserved words are recognized by spelling alone
                if (word.equals("if")) kind = TokenKind::If;
                else if (word.equals("else")) kind = TokenKind::Else;
                else if (word.equals("while")) kind = TokenKind::While;
                else if (word.equals("print")) kind = TokenKind::Print;
                pushToken(&out, kind, start, 0, word);
                continue;
            }
            // every other byte is a one-character operator or delimiter
            // the default is overwritten by whichever case matches below
            TokenKind kind = TokenKind::Eof;
            switch (c) {
                '+' => kind = TokenKind::Plus,
                '-' => kind = TokenKind::Minus,
                '*' => kind = TokenKind::Star,
                '/' => kind = TokenKind::Slash,
                '<' => kind = TokenKind::Less,
                '>' => kind = TokenKind::Greater,
                '(' => kind = TokenKind::LParen,
                ')' => kind = TokenKind::RParen,
                '{' => kind = TokenKind::LBrace,
                '}' => kind = TokenKind::RBrace,
                ';' => kind = TokenKind::Semi,
                '=' => kind = TokenKind::Assign,
                // an unknown byte is skipped: this is a tokenizer, not a checker
                else => { i += 1; continue; },
            }
            // record the operator at its own byte, then step past it
            pushToken(&out, kind, i, 0, src.slice(i, i + 1));
            i += 1;
        }
        // the End Of File sentinel never has a real position past the source
        pushToken(&out, TokenKind::Eof, src.len, 0, "");
        return out;
    }

    str kindName(TokenKind k) {
        // a printable name, used for diagnostics and for this demo
        switch (k) {
            TokenKind::Number  => return "Number",
            TokenKind::Ident   => return "Ident",
            TokenKind::Plus    => return "Plus",
            TokenKind::Minus   => return "Minus",
            TokenKind::Star    => return "Star",
            TokenKind::Slash   => return "Slash",
            TokenKind::Less    => return "Less",
            TokenKind::Greater => return "Greater",
            TokenKind::LParen  => return "LParen",
            TokenKind::RParen  => return "RParen",
            TokenKind::LBrace  => return "LBrace",
            TokenKind::RBrace  => return "RBrace",
            TokenKind::Semi    => return "Semi",
            TokenKind::Assign  => return "Assign",
            TokenKind::If      => return "If",
            TokenKind::Else    => return "Else",
            TokenKind::While   => return "While",
            TokenKind::Print   => return "Print",
            TokenKind::Eof     => return "Eof",
        }
    }

    void main() {
        str src = "x = 1 + 2*3; if x < 10 { print x; }";
        Vec<Token> toks = tokenize(src);
        for (usize i = 0; i < toks.count(); i += 1) {
            Token t = toks.at(i);
            // the text column is the exact slice the token covers
            println("{} {}", kindName(t.kind), t.text);
        }
    }

Every token keeps a `str` rather than a copied `String`, because the source outlives the parsing of it and copying each lexeme would be pure waste; the parser reads `t.text` as long as it still holds the source, which is exactly the lifetime rule from Chapter10. The `pos` is the offset of the token's first byte, and it is what an error message will print as a column. The `Eof` sentinel is appended unconditionally, so an empty source produces a one-token vector and the parser's lookahead is total.

Cost and notes. Time is O(n): each byte is consumed by exactly one branch, and no byte is ever examined twice. Space is O(t) for the tokens plus the source, which is not copied. The class of tokenizer that reads one character and then decides is called a single-pass scanner, and it is why compilers are fast at this stage, lexing a megabyte is a memory-bandwidth problem, not a compute problem. A production lexer adds maximal-munch for multi-character operators (`==`, `<=`, `&&`), number literals in several bases, and string literals with escapes; each is one more `while` loop at the top, not a new architecture.

Edge cases and variations. An empty source yields exactly one token, the sentinel, and `main`'s loop prints it as `Eof` with empty text, which is correct. A number too large for `i64` wraps silently in the `value * 10 + digit` step; a real lexer checks for overflow and reports it, which is the same overflow discipline as Chapter3. An unknown byte such as `@` is skipped rather than diagnosed, so the tokenizer can never fail, that is a deliberate simplification, and 39.4 puts the diagnosis where it belongs, in the parser, which is the first stage that knows the grammar. The variation worth trying is maximal munch: before falling back to single characters, peek at the next byte and, if the pair spells `<=` or `==`, emit one two-character token instead of two single ones.

39.2 The AST as a Variant

The problem. Represent a parsed expression as data the evaluator can walk: numbers, variable references, negation, and binary operations, where each operation holds two sub-expressions that may themselves be operations.

The idea. This is a variant from Chapter13, and the self-reference is the whole story. An expression is one of four cases, and two of those cases point back at more expressions. The pointers are not an optimization; they are what makes the type finite, because a variant that contained whole `Expr` values inside `Expr` would be asking the compiler to size a box in terms of itself. Heap pointers break the circle, and the `alloc`/`dealloc` pair from Chapter28's trees frees it again.

The implementation.

    import(lib) std::mman { alloc, dealloc };
    import(lib) std::io::ios { println, print };

    enum Op { Add, Sub, Mul, Div, Less, Greater }

    variant Expr {
        Num { i64 value; }
        Var { str name; }
        Neg { Expr* operand; }
        Bin { Op op; Expr* left; Expr* right; }
    }

    Expr* mkNum(i64 value) {
        // one node per allocation; the tag records which case is live
        Expr* e = alloc<Expr>(1);
        *e = Expr::Num { .value = value };
        return e;
    }

    Expr* mkVar(str name) {
        // the name is a view into the source, not a copy
        Expr* e = alloc<Expr>(1);
        *e = Expr::Var { .name = name };
        return e;
    }

    Expr* mkNeg(Expr* operand) {
        // negation holds a single child pointer
        Expr* e = alloc<Expr>(1);
        *e = Expr::Neg { .operand = operand };
        return e;
    }

    Expr* mkBin(Op op, Expr* left, Expr* right) {
        // a binary node is the only case with two children
        Expr* e = alloc<Expr>(1);
        *e = Expr::Bin { .op = op, .left = left, .right = right };
        return e;
    }

    str opName(Op op) {
        // the symbol, for printing a tree back out
        switch (op) {
            Op::Add => return "+",
            Op::Sub => return "-",
            Op::Mul => return "*",
            Op::Div => return "/",
            Op::Less => return "<",
            Op::Greater => return ">",
        }
    }

    void show(Expr* e) {
        // copy the variant out so its fields are bound by the switch
        Expr node = *e;
        switch (node) {
            Expr::Num { value } => print("{}", value),
            Expr::Var { name } => print("{}", name),
            Expr::Neg { operand } => { print("(- "); show(operand); print(")"); },
            Expr::Bin { op, left, right } => {
                // fully parenthesized so grouping is unambiguous
                print("(");
                show(left);
                print(" {} ", opName(op));
                show(right);
                print(")");
            },
        }
    }

    // deallocate bottom-up: children before the parent that points at them
    void freeExpr(Expr* e) {
        Expr node = *e;
        switch (node) {
            // leaves own nothing beneath them
            Expr::Num | Expr::Var => {},
            Expr::Neg { operand } => freeExpr(operand),
            Expr::Bin { left, right } => { freeExpr(left); freeExpr(right); },
        }
        // children are freed first, so the parent's pointers are dead here
        dealloc<Expr>(e);
    }

    void main() {
        // 1 + 2 * 3, built by hand for now; the parser comes next
        Expr* e = mkBin(Op::Add, mkNum(1), mkBin(Op::Mul, mkNum(2), mkNum(3)));
        // the printed form should read (+ 1 (* 2 3))
        show(e);
        println("");
        freeExpr(e);
    }

The `show` function is the tree printed back in fully parenthesized form, and reading its output is how you confirm that later parsing produced the tree you meant: `(+ 1 (* 2 3))` is different from `(* (+ 1 2) 3)`, and the parentheses make the difference visible. `freeExpr` is a postorder deallocation, exactly the `freeTree` from Chapter28, because a parent's pointers are the only route to its children and they must be followed before the parent's own storage is returned.

Cost and notes. Construction is O(1) per node. `show` and `freeExpr` are both O(n) in the number of nodes, because each visits every node once. A tree of n nodes uses O(n) heap and O(h) stack, where h is the depth, so a right-leaning chain of a million additions would recurse a million frames deep, the same stack-depth warning as every recursive tree walk in this book. There is no sharing and no cycle: every node is allocated once and freed once.

Edge cases and variations. `freeExpr` on a `Num` or `Var` frees only the node, because the leaf holds no owned storage, the `str` name is a view, not an allocation, so there is nothing else to release. Freeing `null` is not supported and never happens, because constructors never return null. The variation that matters for the next section is to add cases: a `Call { str name; Vec<Expr*> args; }` for functions, or `Index` for arrays. Each new case makes the switches in `show`, `freeExpr`, and the evaluator stop compiling until they handle it, which is the exhaustiveness guarantee of Chapter13 doing real work.

39.3 A Recursive-Descent Parser with Precedence

The problem. Turn the flat token vector into a tree that respects operator precedence: `1 + 2 * 3` must group as `1 + (2 * 3)`, and subtraction must be left-associative so `1 - 2 - 3` is `(1 - 2) - 3`.

The idea. Write one function per precedence level, and have each level call the tighter level for its operands. The loosest level is comparison, which calls addition, which calls multiplication, which calls unary negation, which calls the atoms. Multiplication loops while it sees `*` or `/`, so it swallows all the `*`s before returning to addition, that is where precedence comes from. The loop, not recursion, is what makes each level left-associative. This is recursive descent, and the grammar and the code have the same shape.

The implementation. This builds on the `Token`/`TokenKind` definitions of 39.1 and the `Expr`, `Op`, and `mk*` constructors of 39.2. Only the parser is new.

    import(lib) std::vec { Vec };
    import(lib) std::io::ios { println };

    struct Parser {
        Vec<Token> toks;
        usize pos;
    }

    // peek never advances; every level looks before it consumes
    Token peek(Parser* p) { return p->toks.at(p->pos); }

    Token advance(Parser* p) {
        Token t = p->toks.at(p->pos);
        // the Eof sentinel guarantees advance can never run off the end
        if (p->pos + 1 < p->toks.count()) p->pos += 1;
        return t;
    }

    // check combines peek and a comparison; it never consumes
    bool check(Parser* p, TokenKind k) { return peek(p).kind == k; }

    // operator tokens become the tree operators of the AST
    Op toOp(TokenKind k) {
        switch (k) {
            TokenKind::Plus => return Op::Add,
            TokenKind::Minus => return Op::Sub,
            TokenKind::Star => return Op::Mul,
            TokenKind::Slash => return Op::Div,
            TokenKind::Less => return Op::Less,
            TokenKind::Greater => return Op::Greater,
            // reached only for tokens each level has already accepted
            else => return Op::Add,
        }
    }

    // the precedence chain: loosest at the top, atoms at the bottom
    Expr* parseExpr(Parser* p) { return parseComparison(p); }

    Expr* parseComparison(Parser* p) {
        Expr* left = parseAddSub(p);
        // comparison is the loosest level, so it is parsed first
        while (check(p, TokenKind::Less) || check(p, TokenKind::Greater)) {
            Token opTok = advance(p);
            Expr* right = parseAddSub(p);
            left = mkBin(toOp(opTok.kind), left, right);
        }
        return left;
    }

    Expr* parseAddSub(Parser* p) {
        Expr* left = parseMulDiv(p);
        // the loop folds left, which is what makes a - b - c group left
        while (check(p, TokenKind::Plus) || check(p, TokenKind::Minus)) {
            Token opTok = advance(p);
            Expr* right = parseMulDiv(p);
            left = mkBin(toOp(opTok.kind), left, right);
        }
        return left;
    }

    Expr* parseMulDiv(Parser* p) {
        Expr* left = parseUnary(p);
        // multiplying binds tighter than adding, so this level runs first
        while (check(p, TokenKind::Star) || check(p, TokenKind::Slash)) {
            Token opTok = advance(p);
            Expr* right = parseUnary(p);
            left = mkBin(toOp(opTok.kind), left, right);
        }
        return left;
    }

    Expr* parseUnary(Parser* p) {
        // unary minus binds tighter than any binary operator
        if (check(p, TokenKind::Minus)) {
            advance(p);
            // recursion makes --x and -x both legal, unlike the loop levels
            return mkNeg(parseUnary(p));
        }
        return parsePrimary(p);
    }

    Expr* parsePrimary(Parser* p) {
        Token t = peek(p);
        switch (t.kind) {
            TokenKind::Number => { advance(p); return mkNum(t.value); },
            TokenKind::Ident => { advance(p); return mkVar(t.text); },
            TokenKind::LParen => {
                // parentheses re-enter at the loosest level
                advance(p);
                Expr* inner = parseExpr(p);
                if (check(p, TokenKind::RParen)) advance(p);
                return inner;
            },
            // an unexpected token becomes a zero, for now
            else => { advance(p); return mkNum(0); },
        }
    }

    void main() {
        str src = "1 + 2 * 3 - 4 < 2 * -5";
        Parser p = Parser { .toks = tokenize(src), .pos = 0 };
        Expr* e = parseExpr(&p);
        // the tree prints with precedence made explicit
        show(e);
        println("");
        freeExpr(e);
    }

The one non-obvious move is that `parseComparison` calls `parseAddSub` for both sides, not `parseComparison`. That asymmetry, operands always come from a strictly tighter level, never the same level, is what stops left recursion, the infinite regress a grammar like `expr := expr '+' expr` would cause. The `while` loops then handle repetition without recursion. Read the four levels as one idea repeated with different operators, and the precedence table of Chapter3 is suddenly a stack of functions.

Cost and notes. Parsing is O(t) in the number of tokens: every token is consumed by exactly one `advance`, and the lookahead never backtracks. The recursion depth is bounded by the nesting depth of the expression, not its length, because each level returns before the next token is consumed. Recursive descent is the parser you write when the grammar is small; for larger grammars the same code grows to dozens of levels or gives way to a table-driven parser, but the shape, a function per precedence, a loop per repetition operator, never goes away.

Edge cases and variations. The input `1 + 2 * 3 - 4 < 2 * -5` parses as `((1 + (2 * 3)) - 4) < (2 * (-5))`, and printing it is the proof. A missing closing parenthesis is silently accepted: `(1 + 2` returns the tree for `1 + 2` because of the `if (check(...)) advance(p)` guard, which is a bug we fix properly in 39.4. An unexpected token yields a zero node rather than an error, so the parser always returns a tree and never fails, convenient here, wrong in production, and the reason errors need their own section. The variation to try is a precedence table: a single `parseBinary(minPrec)` that loops while `precedence(peek.kind) > minPrec`, which collapses four functions into one and is the version real parsers use.

39.4 Errors That Carry a Position

The problem. When the input is not a valid program, report where and why, instead of silently substituting a zero or dropping a token. The report must point at a byte offset in the original source.

The idea. Make the error a value, not an exception: a `ParseError` variant that carries a message and a position, stored in the parser. Every parse function keeps going after it records an error, so a single run can report the first problem without the code being littered with early returns. The first error wins, because later errors are usually consequences of the first. At the top, a `Result` carries either the tree or the error out to the caller, following the explicit propagation discipline of Chapter15.

The implementation. This adds error state to the parser of 39.3 and changes the entry point; the tokenizer and tree are unchanged.

    import(lib) std::vec { Vec };
    import(lib) std::result { Result };
    import(lib) std::io::ios { println };

    // errors are values, not exceptions: each one carries where it happened
    variant ParseError {
        Unexpected { str what; usize pos; }
        TrailingTokens { usize pos; }
    }

    struct Parser {
        Vec<Token> toks;
        usize pos;
        // failed latches once, so parse can report and still keep going
        bool failed;
        ParseError err;
    }

    void fail(Parser* p, str what, usize pos) {
        // keep the first error; later ones are consequences of it
        if (p->failed) return;
        p->failed = true;
        p->err = ParseError::Unexpected { .what = what, .pos = pos };
    }

    // expect consumes the wanted token, or reports and keeps going
    Token expect(Parser* p, TokenKind k, str what) {
        if (check(p, k)) return advance(p);
        Token t = peek(p);
        fail(p, what, t.pos);
        // return the offending token so callers can keep making progress
        return t;
    }

    Expr* parsePrimary(Parser* p) {
        Token t = peek(p);
        switch (t.kind) {
            // a number's digits were already folded to i64 by the lexer
            TokenKind::Number => { advance(p); return mkNum(t.value); },
            TokenKind::Ident => { advance(p); return mkVar(t.text); },
            TokenKind::LParen => {
                advance(p);
                Expr* inner = parseExpr(p);
                expect(p, TokenKind::RParen, "expected ')'");
                return inner;
            },
            else => { fail(p, "expected an expression", t.pos); advance(p); return mkNum(0); },
        }
    }

    Result<Expr*, ParseError> parse(str src) {
        // err is initialized to a harmless value; failed gates its use
        Parser p = Parser {
            .toks = tokenize(src), .pos = 0, .failed = false,
            .err = ParseError::TrailingTokens { .pos = 0 }
        };
        Expr* e = parseExpr(&p);
        // any token left before the sentinel is input the grammar did not use
        if (!p.failed && !check(&p, TokenKind::Eof)) {
            p.failed = true;
            p.err = ParseError::TrailingTokens { .pos = peek(&p).pos };
        }
        if (p.failed) return Result<Expr*, ParseError>::Err { .error = p.err };
        return Result<Expr*, ParseError>::Ok { .value = e };
    }

    void report(ParseError e) {
        // one arm per failure case, so nothing is forgotten
        switch (e) {
            ParseError::Unexpected { what, pos } => println("error at {}: {}", pos, what),
            ParseError::TrailingTokens { pos } => println("error at {}: unexpected extra tokens", pos),
        }
    }

    void main() {
        str src = "1 + * 3";
        Result<Expr*, ParseError> r = parse(src);
        // explicit propagation: handle the Err before unwrapping
        if (r.isErr()) {
            report(r.unwrapErr());
            return;
        }
        Expr* e = r.unwrap();
        show(e);
        println("");
        freeExpr(e);
    }

The design decision worth naming is that `fail` records only the first error and then ignores every later one. Without that guard, a parser that recovers and continues can pile up dozens of cascading messages, all of them symptoms of the one real mistake. With it, the message points at the first thing that was wrong, which is almost always the thing the programmer needs to see. The `Result<Expr*, ParseError>` never holds a null tree and an error at once; the two cases are mutually exclusive by construction.

Cost and notes. Error handling adds constant work per token and does not change the O(t) bound, because `fail` is O(1) and `expect` replaces the checks the parser already made. The error value is small, a tag, a view, and an offset, so returning it by value through `Result` costs nothing meaningful. The pattern of "record the first failure, keep going, check at the top" is exactly how production parsers batch diagnostics, though the good ones keep a list of errors rather than just the first, and resume at a synchronization point such as the next semicolon.

Edge cases and variations. An empty source parses to `Err TrailingTokens` rather than a tree, because the first token is the sentinel and `parsePrimary` reports "expected an expression" at position zero. A stray closing parenthesis or a trailing operator is caught by `TrailingTokens` at the position of the leftover token. The `else` arm of `toOp` returning `Op::Add` is now defensible in a new way: it is only reachable if the precedence chain already accepted the token, so it never fires. The variation is error recovery with a synchronization token: on a failure, skip tokens until the next `;`, discard the partial statement, and continue, so one run reports every avoidable mistake instead of only the first.

39.5 A Tree-Walking Evaluator

The problem. Given a tree from 39.2, compute its integer value by walking it, handling arithmetic, comparison, and negation.

The idea. The evaluator is a recursion whose structure mirrors the tree's. A number evaluates to itself; a negation evaluates its operand and negates; a binary node evaluates both children and applies the operator. Comparisons yield `1` or `0`, so the entire language has one value type and no coercion rules. This is the smallest possible interpreter, a handful of lines, and the interesting choices are all about what to do at the boundaries, such as division by zero.

The implementation. The tree and constructors come from 39.2; only `eval` and `main` are new.

    import(lib) std::mman { alloc, dealloc };
    import(lib) std::io::ios { println };

    i64 eval(Expr* e) {
        // bind the variant so its fields are visible to the arms
        Expr node = *e;
        switch (node) {
            Expr::Num { value } => return value,
            // no environment yet: every name is zero
            Expr::Var { name } => return 0,
            Expr::Neg { operand } => return -eval(operand),
            Expr::Bin { op, left, right } => {
                // evaluate children first: this is a postorder walk
                i64 l = eval(left);
                i64 r = eval(right);
                switch (op) {
                    // each arm turns two integers into one
                    Op::Add => return l + r,
                    Op::Sub => return l - r,
                    Op::Mul => return l * r,
                    // division by zero has no integer answer; define it as 0
                    Op::Div => return r == 0 ? 0 : l / r,
                    Op::Less => return l < r ? 1 : 0,
                    Op::Greater => return l > r ? 1 : 0,
                }
            },
        }
    }

    void main() {
        // (1 + 2) * (3 - 4) is 3 * -1, which is -3
        Expr* e = mkBin(Op::Mul,
            mkBin(Op::Add, mkNum(1), mkNum(2)),
            mkBin(Op::Sub, mkNum(3), mkNum(4)));
        // show the tree, then its value, on one line
        show(e);
        println(" = {}", eval(e));
        freeExpr(e);
    }

The tree-walking interpreter is the reference implementation every faster engine is measured against. It is slow for a reason worth understanding: the recursion touches the heap once per node, and the same operator is rediscovered by a switch at runtime that a compiler would have resolved at build time. That gap, between interpreting a tree and compiling it once to instructions, is exactly what 39.8 closes, and seeing the two forms side by side is the clearest possible statement of what compilation buys.

Cost and notes. Time is O(n) in the nodes, and each `eval` call is a function call plus a tag switch. Space is O(h) for the recursion, where h is the depth, again bounded by nesting rather than length. Because every node is visited exactly once and no node is evaluated twice, a tree of additions is linear even though it looks recursive; the exponential blowups people fear come from re-evaluating shared sub-trees, which this representation cannot express, because there is no sharing.

Edge cases and variations. Division by zero returns `0` rather than trapping, which is a choice, not a truth: a real language either faults, returns an `Option`, or moves to floating point, and Chapter3 discusses all three. Integer overflow in `l + r` wraps silently, the same wart as the tokenizer's number folding. Deeply left-nested input recurses proportionally to depth and can overflow the stack. The variation worth writing is to have `eval` return `Result<i64, EvalError>` with a `DivisionByZero` case, which turns the undefined divide from a silent zero into a value the caller must confront, the discipline of 39.4 applied to runtime rather than parse-time errors.

39.6 Variables and an Environment

The problem. Make names meaningful: an assignment `x = expr` must store a value under a name, and a later `x` must read it back. This also needs statements, because assignment is not an expression you can nest arbitrarily.

The idea. Keep a hash map from name to value, the environment, and give the language a second tree, the statement tree, beside the expression tree. A program is a sequence of statements; `runStmt` walks them, evaluating expressions with the environment in hand. The map is `HashMap<str, i64>` from Chapter26, and the key is the name as a view into the source, which is safe because the source outlives the run.

The implementation. This adds the `Stmt` variant and an environment parameter threaded through evaluation; the expression tree and constructors are unchanged from 39.2.

    import(lib) std::vec { Vec };
    import(lib) std::collections.hashmap { HashMap };
    import(lib) std::mman { alloc, dealloc };
    import(lib) std::io::ios { println };

    // a program is a list of these; a statement has an effect, not a value
    variant Stmt {
        Assign { str name; Expr* value; }
        Print { Expr* value; }
        ExprStmt { Expr* value; }
    }

    // djb2, the same hash Chapter26 uses for str keys
    usize hashStr(str s) {
        // 5381 is the djb2 seed; any odd constant would do
        usize h = 5381;
        for (usize i = 0; i < s.len; i += 1) {
            h = h * 33 + (usize)s.at(i);
        }
        return h;
    }

    // equality is what disambiguates a hash collision
    bool eqStr(str a, str b) { return a.equals(b); }

    Stmt* mkAssign(str name, Expr* value) {
        // the name stays a view; the source outlives the environment here
        Stmt* s = alloc<Stmt>(1);
        *s = Stmt::Assign { .name = name, .value = value };
        return s;
    }

    Stmt* mkPrint(Expr* value) {
        Stmt* s = alloc<Stmt>(1);
        // printing is a statement because it is an effect
        *s = Stmt::Print { .value = value };
        return s;
    }

    Stmt* mkExprStmt(Expr* value) {
        // an expression used only for its own value
        Stmt* s = alloc<Stmt>(1);
        *s = Stmt::ExprStmt { .value = value };
        return s;
    }

    // evaluation now threads the environment through every call
    i64 eval(Expr* e, HashMap<str, i64>* env) {
        Expr node = *e;
        switch (node) {
            Expr::Num { value } => return value,
            // an unbound name reads as zero, so evaluation is total
            Expr::Var { name } => return env->get(name).unwrapOr(0),
            Expr::Neg { operand } => return -eval(operand, env),
            Expr::Bin { op, left, right } => {
                i64 l = eval(left, env);
                i64 r = eval(right, env);
                switch (op) {
                    Op::Add => return l + r,
                    Op::Sub => return l - r,
                    Op::Mul => return l * r,
                    Op::Div => return r == 0 ? 0 : l / r,
                    Op::Less => return l < r ? 1 : 0,
                    Op::Greater => return l > r ? 1 : 0,
                }
            },
        }
    }

    // statements perform effects; they do not return a value
    void runStmt(Stmt* s, HashMap<str, i64>* env) {
        Stmt st = *s;
        switch (st) {
            Stmt::Assign { name, value } => {
                // the insert result is ignored: i64 values cannot fail to store
                env->insert(name, eval(value, env));
            },
            Stmt::Print { value } => println("{}", eval(value, env)),
            Stmt::ExprStmt { value } => eval(value, env),
        }
    }

    void main() {
        HashMap<str, i64> env = HashMap<str, i64>::new(hashStr, eqStr);
        // the backing store is a plain vector of statement pointers
        Vec<Stmt*> program = Vec<Stmt*>::new();
        // x = 10; y = x * x + 5; print y;
        program.push(mkAssign("x", mkNum(10)));
        program.push(mkAssign("y",
            mkBin(Op::Add, mkBin(Op::Mul, mkVar("x"), mkVar("x")), mkNum(5))));
        program.push(mkPrint(mkVar("y")));
        // run statements in order, all sharing one environment
        for (usize i = 0; i < program.count(); i += 1) {
            runStmt(program.at(i), &env);
        }
        println("x = {}", env.get("x").unwrapOr(0));
        // the map owns heap storage that must be released by hand
        env.dispose();
    }

The environment is threaded as a pointer because every statement shares the same map and mutates it; the map is the one piece of state that lives outside the tree. `runStmt` being separate from `eval` is a small but real design choice: it is the moment the language stops being an expression calculator and becomes a sequence of effects, and it is why the evaluator can no longer be a pure function of the tree alone. In the next section the same split lets control flow exist, because statements can decide which statements run.

Cost and notes. Each assignment and each variable read is an O(1) average-time hash operation, so a program of length p is O(p) evaluations plus O(p) map work. The map grows with the number of distinct variables, not the number of assignments, because an overwrite reuses the slot. The `str` key is safe only because the source outlives the run; the moment the source could be freed or reused, the keys would dangle, which is exactly the problem 39.9 solves with owned `String` keys.

Edge cases and variations. Reading a name before it is assigned yields `0`, not an error, because `unwrapOr(0)` supplies the missing case; a stricter language returns `Result` and forces the caller to handle the unbound variable. Reassigning `x` replaces its value, since `insert` updates in place when the key exists. The environment is disposed by hand at the end, because `HashMap`'s backing storage is not returned automatically. The variation is scope: wrap nested environments in a stack, push on entering a block, pop on leaving, and look a name up the chain of maps from innermost to outermost, which is exactly how every block-structured language from Chapter12 onward resolves names.

39.7 Control Flow: if and while

The problem. Let statements decide what runs next: `if` chooses between two blocks, and `while` repeats a block while a condition holds.

The idea. Add a `Block`, which is a sequence of statements, and two new statement cases whose fields point at blocks. The evaluator reproduces the semantics directly: an `if` evaluates its condition and runs one of two blocks; a `while` re-evaluates its condition before every pass and runs the body while the condition is nonzero. Because the body is itself a list of statements and `runStmt` is recursive, nesting falls out for free, a block can contain an `if` that contains a `while`.

The implementation. This extends the `Stmt` variant and `runStmt` of 39.6; the environment and expression evaluator are unchanged.

    import(lib) std::vec { Vec };
    import(lib) std::collections.hashmap { HashMap };
    import(lib) std::mman { alloc, dealloc };
    import(lib) std::io::ios { println };

    // a block is just a sequence of statements, so nesting is free
    struct Block { Vec<Stmt*> stmts; }

    variant Stmt {
        Assign { str name; Expr* value; }
        Print { Expr* value; }
        ExprStmt { Expr* value; }
        If { Expr* cond; Block* thenBody; Block* elseBody; }
        // while has no else: either the body runs or it does not
        While { Expr* cond; Block* body; }
    }

    Block* mkBlock(Vec<Stmt*> stmts) {
        Block* b = alloc<Block>(1);
        // ownership of the vector moves into the block
        b->stmts = stmts;
        return b;
    }

    Stmt* mkIf(Expr* cond, Block* thenBody, Block* elseBody) {
        // a null elseBody is the "no else clause" case
        Stmt* s = alloc<Stmt>(1);
        *s = Stmt::If { .cond = cond, .thenBody = thenBody, .elseBody = elseBody };
        return s;
    }

    Stmt* mkWhile(Expr* cond, Block* body) {
        Stmt* s = alloc<Stmt>(1);
        *s = Stmt::While { .cond = cond, .body = body };
        return s;
    }

    void runBlock(Block* b, HashMap<str, i64>* env) {
        // statements run left to right, sharing the environment
        for (usize i = 0; i < b->stmts.count(); i += 1) {
            runStmt(b->stmts.at(i), env);
        }
    }

    // now five cases, two of which recurse into blocks
    void runStmt(Stmt* s, HashMap<str, i64>* env) {
        Stmt st = *s;
        switch (st) {
            Stmt::Assign { name, value } => { env->insert(name, eval(value, env)); },
            Stmt::Print { value } => println("{}", eval(value, env)),
            Stmt::ExprStmt { value } => eval(value, env),
            Stmt::If { cond, thenBody, elseBody } => {
                // a null elseBody means there was no else clause
                if (eval(cond, env) != 0) runBlock(thenBody, env);
                else if (elseBody != null) runBlock(elseBody, env);
            },
            Stmt::While { cond, body } => {
                // re-test before every pass, so the condition can change
                while (eval(cond, env) != 0) runBlock(body, env);
            },
        }
    }

    void main() {
        HashMap<str, i64> env = HashMap<str, i64>::new(hashStr, eqStr);
        Vec<Stmt*> program = Vec<Stmt*>::new();
        // sum = 0; i = 1; while (i < 6) { sum = sum + i; i = i + 1; } print sum;
        Vec<Stmt*> body = Vec<Stmt*>::new();
        // the loop body adds i to sum, then advances i
        body.push(mkAssign("sum", mkBin(Op::Add, mkVar("sum"), mkVar("i"))));
        body.push(mkAssign("i", mkBin(Op::Add, mkVar("i"), mkNum(1))));
        program.push(mkAssign("sum", mkNum(0)));
        program.push(mkAssign("i", mkNum(1)));
        program.push(mkWhile(mkBin(Op::Less, mkVar("i"), mkNum(6)), mkBlock(body)));
        program.push(mkPrint(mkVar("sum")));
        for (usize i = 0; i < program.count(); i += 1) {
            runStmt(program.at(i), &env);
        }
        env.dispose();
    }

`runStmt` and `runBlock` call each other, which is mutual recursion and would need a forward declaration in some languages. Here it is written so that `runStmt` inlines the block loop rather than calling `runBlock`, keeping the recursion single-function and the definition order valid. The `elseBody` pointer is `null` when there is no `else`, and the evaluator checks it explicitly; the alternative is to make the field an `Option<Block*>`, which the compiler would force you to unwrap and so make forgetting impossible.

Cost and notes. The interpreter's cost is the cost of the program it runs: each loop iteration costs one condition evaluation plus one block execution, and there is no compilation step to amortize. The recursion depth is the nesting depth of blocks, not the loop count, because a `while` is a loop rather than a recursive call. This is the difference between a language whose loops are cheap and one whose loops are function calls, a real difference in performance and an invisible one in meaning.

Edge cases and variations. A `while` whose condition is initially zero runs its body zero times, which is the standard and the reason the condition is tested first. An `if` with no `else` and a false condition does nothing, because the `elseBody` is null and the branch is skipped. Because conditions are integers, `while 1 { ... }` is an infinite loop with no way to break in this language; adding `break` and `continue` means giving `runBlock` a signal return rather than `void`, which is the variation to attempt. The other variation is `for`: desugar it to a `while` with an initializer block before and an increment block at the end of the body, and the interpreter does not change at all, a small, clean example of a feature implemented entirely in the parser.

39.8 A Tiny Stack-Based Bytecode VM

The problem. Walking a tree is simple but slow, because every node costs a recursive call and a runtime tag switch. Compile the tree once to a flat sequence of instructions and run those instead.

The idea. A stack machine: instructions push values onto a stack, and operators pop their operands and push their result. Compiling an expression is a postorder walk, emit the left subtree, emit the right subtree, then emit the operator, so that by the time an operator instruction runs, its operands are already on the stack. The tree is read once at compile time; at run time there is a loop and an array, no recursion and no tags to interpret.

The implementation. The tree and constructors come from 39.2; the evaluator is replaced by a compiler and a machine.

    import(lib) std::vec { Vec };
    import(lib) std::mman { alloc, dealloc };
    import(lib) std::io::ios { println };

    // one opcode per operation, plus Push and a Halt terminator
    enum OpCode { Push, Neg, Add, Sub, Mul, Div, Less, Greater, Halt }

    struct Instr {
        // arg is used only by Push; every other opcode ignores it
        OpCode op;
        i64 arg;
    }

    struct Compiler {
        Vec<Instr> code;
    }

    void emit(Compiler* c, OpCode op, i64 arg) {
        // append one instruction to the growing program
        c->code.push(Instr { .op = op, .arg = arg });
    }

    // a tree operator and a machine opcode are different types
    OpCode opToCode(Op op) {
        switch (op) {
            Op::Add => return OpCode::Add,
            Op::Sub => return OpCode::Sub,
            Op::Mul => return OpCode::Mul,
            Op::Div => return OpCode::Div,
            Op::Less => return OpCode::Less,
            Op::Greater => return OpCode::Greater,
        }
    }

    void compile(Compiler* c, Expr* e) {
        Expr node = *e;
        switch (node) {
            // a literal becomes a push of its own value
            Expr::Num { value } => emit(c, OpCode::Push, value),
            // variables are not compiled yet: they push zero
            Expr::Var { name } => emit(c, OpCode::Push, 0),
            Expr::Neg { operand } => { compile(c, operand); emit(c, OpCode::Neg, 0); },
            Expr::Bin { op, left, right } => {
                // postorder: operands first, operator last
                compile(c, left);
                compile(c, right);
                emit(c, opToCode(op), 0);
            },
        }
    }

    void apply(Vec<i64>* stack, OpCode op) {
        // operands come off in reverse order of how they were pushed
        // the right operand was pushed last, so it pops first
        i64 r = stack->pop();
        i64 l = stack->pop();
        switch (op) {
            OpCode::Add => stack->push(l + r),
            OpCode::Sub => stack->push(l - r),
            OpCode::Mul => stack->push(l * r),
            OpCode::Div => stack->push(r == 0 ? 0 : l / r),
            OpCode::Less => stack->push(l < r ? 1 : 0),
            OpCode::Greater => stack->push(l > r ? 1 : 0),
            // Push, Neg, and Halt are handled by the machine, not here
            else => stack->push(0),
        }
    }

    i64 run(const Vec<Instr>* code) {
        Vec<i64> stack = Vec<i64>::new();
        // the machine is a flat array, an index, and a value stack
        for (usize i = 0; i < code->count(); i += 1) {
            Instr in = code->at(i);
            switch (in.op) {
                OpCode::Push => stack.push(in.arg),
                // unary negate needs only the top of the stack
                OpCode::Neg => stack.push(-stack.pop()),
                OpCode::Add | OpCode::Sub | OpCode::Mul | OpCode::Div
                    | OpCode::Less | OpCode::Greater => apply(&stack, in.op),
                OpCode::Halt => break,
            }
        }
        // a well-formed program leaves exactly one value on the stack
        return stack.pop();
    }

    void main() {
        // (1 + 2 * 3) - 4 compiles to five pushes and three operators
        Expr* e = mkBin(Op::Sub,
            mkBin(Op::Add, mkNum(1), mkBin(Op::Mul, mkNum(2), mkNum(3))),
            mkNum(4));
        // compilation happens once; the machine then replays the array
        Compiler c = Compiler { .code = Vec<Instr>::new() };
        compile(&c, e);
        println("{} instructions", c.code.count());
        println("result {}", run(&c.code));
        freeExpr(e);
    }

The single multi-case arm, `Add | Sub | Mul | Div | Less | Greater => apply(...)`, is the payoff of flat opcodes: six operators dispatch through one call, and adding a seventh means one new `OpCode` case and one new line in `apply`, not a new recursion. The machine has no idea it is running a tree; it has an array and an index, and that is the entire state of the interpreter between instructions. This is the same split a real compiler makes twice, first from tree to bytecode and then from bytecode to machine code, and the reason the first split is easy is that the tree already encodes the evaluation order the stack machine replays.

Cost and notes. Compilation is a single O(n) postorder pass. Execution is O(k) in the number of instructions, and each instruction is a constant-time stack operation plus one array access, no recursion, no heap per step. The bytecode is O(n) in size. The win over tree-walking is the absence of per-node function calls and per-node tag dispatch, which is why even a simple bytecode VM beats an interpreter by a constant factor that grows with expression size. The loop here is a switch inside a `for`; a production VM threads the next instruction through the end of each case, a technique called direct threading, to remove the loop overhead.

Edge cases and variations. An empty program, or one whose last instruction is not `Halt`, falls off the end of the loop and returns whatever is on top of the stack, which is why a real compiler always appends `Halt`. A `Div` by zero pushes `0` through the same guard as 39.5, so the machine and the tree-walker agree by construction. Popping from an empty stack is a bug the machine does not detect; a defensive version checks the depth before every `pop` and reports a mismatch, which is also how you would validate untrusted bytecode before running it. The variation to attempt is variables: add `Load { usize slot; }` and `Store { usize slot; }` opcodes, compile variable references to slot indices resolved by a scope pass at compile time, and the same machine runs whole programs, which is exactly the step from an expression compiler to a statement compiler.

39.9 A REPL on stdin

The problem. Wire the whole pipeline into a read-eval-print loop that reads a line, parses it as a statement, runs it against a persistent environment, and prints the result, the smallest complete language front end.

The idea. Everything is already written: the tokenizer of 39.1, the tree of 39.2, the error-carrying parser of 39.4 extended with statement parsing, the environment of 39.6, and the evaluator. The only new problem is ownership. A REPL reuses one input buffer for every line, so a name captured during parsing would dangle the moment the next line overwrites the buffer. The environment therefore owns its keys: it stores `String`, not `str`, copying each name the first time it is stored.

The implementation. This is the full assembly. It parses three kinds of statement, `print`, assignment, and a bare expression, which a REPL echoes, and leaves `if`/`while` to 39.7 as an exercise.

    import(lib) std::vec { Vec };
    import(lib) std::text::string { String };
    import(lib) std::collections.hashmap { HashMap };
    import(lib) std::mman { alloc, dealloc };
    import(lib) std::result { Result };
    import(lib) std::io::ios { println, readLine };

    // the tokenizer, tree, and parser helpers are as in 39.1 through 39.6
    variant ParseError {
        Unexpected { str what; usize pos; }
        TrailingTokens { usize pos; }
    }

    // a fresh parser per line; the environment persists across lines
    struct Parser {
        Vec<Token> toks;
        usize pos;
        // failed latches once per line; the first error is kept
        bool failed;
        ParseError err;
    }

    void fail(Parser* p, str what, usize pos) {
        // first error wins; later ones are usually downstream symptoms
        if (p->failed) return;
        p->failed = true;
        p->err = ParseError::Unexpected { .what = what, .pos = pos };
    }

    // expect consumes the wanted token or records an error and moves on
    Token expect(Parser* p, TokenKind k, str what) {
        if (check(p, k)) return advance(p);
        Token t = peek(p);
        fail(p, what, t.pos);
        return t;
    }

    // the statement grammar is deliberately small: three forms
    Stmt* parseStatement(Parser* p) {
        // print is a keyword, so it is recognized before names
        if (check(p, TokenKind::Print)) {
            advance(p);
            Expr* value = parseExpr(p);
            expect(p, TokenKind::Semi, "expected ';' after print");
            return mkPrint(value);
        }
        // a leading name followed by '=' is an assignment
        if (check(p, TokenKind::Ident)) {
            Token name = peek(p);
            if (p->toks.at(p->pos + 1).kind == TokenKind::Assign) {
                advance(p);
                advance(p);
                Expr* value = parseExpr(p);
                expect(p, TokenKind::Semi, "expected ';' after assignment");
                return mkAssign(name.text, value);
            }
        }
        // anything else is an expression statement, which a REPL echoes
        Expr* value = parseExpr(p);
        expect(p, TokenKind::Semi, "expected ';'");
        return mkExprStmt(value);
    }

    Result<Stmt*, ParseError> parseLine(str src) {
        Parser p = Parser {
            .toks = tokenize(src), .pos = 0, .failed = false,
            .err = ParseError::TrailingTokens { .pos = 0 }
        };
        Stmt* s = parseStatement(&p);
        if (!p.failed && !check(&p, TokenKind::Eof)) {
            p.failed = true;
            p.err = ParseError::TrailingTokens { .pos = peek(&p).pos };
        }
        if (p.failed) return Result<Stmt*, ParseError>::Err { .error = p.err };
        return Result<Stmt*, ParseError>::Ok { .value = s };
    }

    // the environment owns its keys, because the input line is reused
    usize hashString(String key) {
        // hash the bytes the String owns, via a borrowed view
        str s = key.asView();
        usize h = 5381;
        for (usize i = 0; i < s.len; i += 1) {
            h = h * 33 + (usize)s.at(i);
        }
        return h;
    }

    // compare contents, not pointers: two copies of "x" are equal
    bool eqString(String a, String b) { return a.equalsView(b.asView()); }

    void assign(HashMap<String, i64>* env, str name, i64 value) {
        // copy the name so it survives the next readLine
        String key = String::from(name);
        bool existed = env->get(key).isSome();
        env->insert(key, value);
        // on overwrite the map keeps its old key, so this copy is redundant
        if (existed) key.free();
    }

    i64 lookup(HashMap<String, i64>* env, str name) {
        // the map is keyed by owned String, so build a temporary key
        String key = String::from(name);
        i64 v = env->get(key).unwrapOr(0);
        // the temporary key is freed as soon as the lookup finishes
        key.free();
        return v;
    }

    // the evaluator is identical to 39.6 except for the key type
    i64 eval(Expr* e, HashMap<String, i64>* env) {
        Expr node = *e;
        switch (node) {
            Expr::Num { value } => return value,
            Expr::Var { name } => return lookup(env, name),
            Expr::Neg { operand } => return -eval(operand, env),
            Expr::Bin { op, left, right } => {
                i64 l = eval(left, env);
                i64 r = eval(right, env);
                switch (op) {
                    Op::Add => return l + r,
                    Op::Sub => return l - r,
                    Op::Mul => return l * r,
                    Op::Div => return r == 0 ? 0 : l / r,
                    Op::Less => return l < r ? 1 : 0,
                    Op::Greater => return l > r ? 1 : 0,
                }
            },
        }
    }

    // three statement forms in the REPL
    void runStmt(Stmt* s, HashMap<String, i64>* env) {
        Stmt st = *s;
        switch (st) {
            Stmt::Assign { name, value } => assign(env, name, eval(value, env)),
            // at a terminal, a print and a bare expression both show a value
            Stmt::Print { value } => println("{}", eval(value, env)),
            Stmt::ExprStmt { value } => println("{}", eval(value, env)),
        }
    }

    void report(ParseError e) {
        // errors report a byte offset into the current line
        switch (e) {
            ParseError::Unexpected { what, pos } => println("error at {}: {}", pos, what),
            ParseError::TrailingTokens { pos } => println("error at {}: trailing tokens", pos),
        }
    }

    void main() {
        HashMap<String, i64> env = HashMap<String, i64>::new(hashString, eqString);
        // one reused buffer holds every line the user types
        String line = String::new();
        println("tiny repl; type statements, ctrl-d to quit");
        // readLine returns false only at end of input
        while (readLine(&line)) {
            // a blank line produces no statement and no output
            if (line.isEmpty()) continue;
            Result<Stmt*, ParseError> r = parseLine(line.asView());
            // a bad line is reported and skipped; the session continues
            if (r.isErr()) {
                report(r.unwrapErr());
                continue;
            }
            runStmt(r.unwrap(), &env);
        }
        line.free();
        env.dispose();
    }

The ownership decision is the heart of this section. The parse tree's names are `str` views into `line`, which is correct for as long as the statement runs, because that happens before the next read. But the environment outlives the line: a variable set on line one must still read back on line fifty. So `assign` copies the name into an owned `String` that the map keeps, while `lookup` builds a temporary owned key only to satisfy the map's `String`-keyed interface and frees it immediately after. This is the borrow-versus-own split of Chapter10 made concrete: the tree borrows, the environment owns, and the boundary is exactly where one lifetime ends and the other begins.

Cost and notes. Each line is lexed, parsed, and run in time proportional to its length, and the environment's cost is the usual O(1) average hash operation per statement. The only new cost is the `String` copy on each assignment and each lookup; assignments are rare and lookups are short, so the copy is negligible, and it buys correctness. The REPL holds no state between lines except the environment, which is what makes it a language rather than a calculator: the same line means different things depending on what came before it.

Edge cases and variations. A blank line is skipped before parsing, so an empty statement does not report an error. A line without a trailing newline at end of input is still processed, because `readLine` returns true when it has read any bytes before hitting the end. A parse error prints its position and does not disturb the environment, so the session continues. Freeing the `line` and disposing the `env` at the end releases everything the loop built. The obvious variations are to add `if` and `while` by reusing 39.7's `parseStatement` arms, to keep a history and re-run the last statement on an empty line, and to switch the evaluator from the tree-walker to the bytecode VM of 39.8, which changes only `runStmt` and leaves the parser, the tree, and the errors entirely untouched, a clear demonstration that the stages really are independent.

Exercises

1. Comprehension. Trace `tokenize("a1 + 12")` by hand and write down every token's `kind`, `pos`, and `text`. Then explain why appending the `Eof` sentinel lets `advance` drop its bounds check, and what would break if the sentinel were removed.

2. Precedence. Add a `==` operator that binds looser than comparison. Decide whether it is left- or right-associative, add one function to the precedence chain, and explain why the choice changes the parse of `a == b < c`.

3. Associativity. Change `parseAddSub`'s loop to a right-recursive form so that `1 - 2 - 3` parses as `1 - (2 - 3)`, then evaluate both forms and state the value each produces. Which one matches the arithmetic you were taught, and why?

4. Errors. Give `fail` a list instead of a single `ParseError`, record every error, and make `parse` return the first. Then add recovery: after a failure, skip tokens to the next `Semi` and parse the following statement, so `1 +; 2 *; 3` reports two errors rather than one.

5. Evaluation. Rewrite `eval` to return `Result<i64, EvalError>` with a `DivisionByZero` case, and update `runStmt` to print the error instead of the value. What does this force the caller to confront that the `0`-on-divide version let it ignore?

6. Environment. Add a `Block` environment stack so that a variable assigned inside an `if` block is visible only within it. Push a map on entering a block, pop on leaving, and search from innermost to outermost. Which programs change meaning, and is that the behavior you want?

7. Compiler. Add `Load` and `Store` opcodes to the VM of 39.8 and a scope pass that assigns each variable an integer slot. Then compile a small program with assignments and run it, and explain where the slot resolution happens and why it cannot happen at run time.

8. REPL. Wrap the REPL line in a `try`-like construct, or, since Coral has none, use the `Result` discipline of Chapter15, so that an evaluation-time error such as an unknown variable is reported rather than defaulting to zero. What is the smallest change to the tree or the environment that makes "unknown variable" detectable?

9. Design. The language has no way to stop a `while` loop from outside. Design a `break` statement, describing exactly what `runStmt` and `runBlock` must return to propagate the signal up through nested blocks, and argue why a plain `void` return cannot express it.

10. Meta. Re-read 39.4's `fail`. It keeps the first error and drops the rest. Find one realistic input where that discards a more informative message in favor of a worse one, and describe the recovery strategy that would report the better message first.
