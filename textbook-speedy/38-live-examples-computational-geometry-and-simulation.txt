Chapter38

Live Examples: Computational Geometry and Simulation

Shapes, Motions, and the Arithmetic That Refuses to Be Exact

Computational geometry is the study of a handful of questions you can ask about points in the plane. Is this point to the left of that line? Do these two segments cross? Is this point inside that polygon? What is the shortest distance between any two of these points? Each question sounds small, and each one, asked naively, hides an O(n²) or worse algorithm underneath. The trick of the field is to answer them with a single invariant expressed as a signed area, and then to notice that the invariant is all most of the hard problems ever needed. The convex hull, the point-in-polygon test, the segment-intersection test, and the closest-pair algorithm in this chapter are, in the end, one cross product wearing four different hats.

Simulation is the other half, and it is geometry that moves. A particle under gravity, a cluster of bodies pulling on each other, a grid of cells blinking between alive and dead: each is a state that you update in small steps, and each has a conservation property or a stability property that decides whether the numbers drift or explode. Verlet integration is the scheme behind almost every game physics engine because it is symplectic, meaning it keeps the energy roughly constant instead of slowly leaking it. The n-body problem is the honest O(n²) force calculation, with a softening term that keeps close encounters from producing infinities. The Game of Life is a state machine where the whole art is a clean neighbourhood count on a wrapping grid.

There is one theme that runs through every section, and it is not geometry at all. It is floating-point error, the subject of Chapter32.9. The cross product that decides left from right is exact for small integer coordinates and quietly wrong for nearly collinear points, because two large products that should cancel leave a residue of rounding. A ray cast from a point exactly on an edge can count the edge zero times or twice depending on which side of zero the rounding lands. An orbit integrated with a large time step drifts outward or inward because the method is only approximately conservative. None of these are bugs in the sense of a wrong line. They are the cost of computing with `f64`, and the honest response is to name them, choose tolerances deliberately, and know when exact integer arithmetic would have saved you. This chapter keeps the mathematics explicit and the error admitted.

A note on the shape of every example. Each is a complete program: the imports it needs, the small struct that carries a point or a body, the algorithm as a free function or a method, and a `void main()` that demonstrates it on a few values so you can watch the output. The examples build on each other only in spirit; each can be read alone, and each repeats the declarations it depends on.

38.1 Points, Vectors, and the Orientation Test

The problem. Represent a point (or a vector) in the plane, and answer the question that every other geometry algorithm is built from: given three points `o`, `a`, and `b`, is `b` to the left of the directed line from `o` to `a`, to the right of it, or exactly on it?

Picture this. You are standing at `o` and facing `a`. Point `b` is somewhere off to the side. If it lies to your left, walking the triangle `o → a → b` turns counter-clockwise; if to your right, clockwise; if dead ahead or directly behind, the three points are collinear and the triangle has no area. That is the entire test, and it is called the orientation of the triple.

Brute force, then better. The naive method computes the angle that the vector `o → a` makes with the x-axis and compares it to the angle of `o → b`. That fails twice over: angles require `atan2`, which is slow and, worse, produces a discontinuity at the point where the angle wraps from `π` to `−π`, so two points just across the seam compare as if they were on opposite sides of the plane. The algebraic test has neither problem. The signed area of the parallelogram spanned by the two vectors is `(a.x − o.x)(b.y − o.y) − (a.y − o.y)(b.x − o.x)`. Its sign is the orientation, it costs a couple of multiplications, and it never has a seam.

The implementation.

    import(lib) std::vec { Vec };
    import(lib) std::io::ios { println };
    import(lib) std::math::math { sqrt };

    struct Pt {
        f64 x;
        f64 y;

        // construct a point from its coordinates
        static Pt new(f64 x, f64 y) {
            return Pt { .x = x, .y = y };
        }

        // difference of two points is the direction vector between them
        Pt sub(Pt other) {
            return Pt { .x = self.x - other.x, .y = self.y - other.y };
        }

        // multiply both components by a scalar
        Pt scale(f64 s) {
            return Pt { .x = self.x * s, .y = self.y * s };
        }

        // dot product measures how aligned two vectors are
        f64 dot(Pt other) {
            return self.x * other.x + self.y * other.y;
        }

        // 2D cross product is the signed area of the parallelogram
        f64 cross(Pt other) {
            return self.x * other.y - self.y * other.x;
        }

        // squared length: avoids a square root when only comparing distances
        f64 lengthSq() {
            return self.x * self.x + self.y * self.y;
        }

        // Euclidean length via the Pythagorean theorem
        f64 length() {
            return sqrt(self.lengthSq());
        }
    }

    f64 crossOf(Pt o, Pt a, Pt b) {
        // shift both vectors to start at o ...
        Pt oa = a.sub(o);
        Pt ob = b.sub(o);
        // ... then cross them; the sign says which way b turns from o to a
        return oa.cross(ob);
    }

    i32 orient(Pt o, Pt a, Pt b) {
        f64 c = crossOf(o, a, b);
        if (c > 0.0) return 1;      // counter-clockwise: b is to the left
        if (c < 0.0) return -1;     // clockwise: b is to the right
        return 0;                   // collinear
    }

    void main() {
        Pt o = Pt::new(0.0, 0.0);
        Pt a = Pt::new(1.0, 0.0);
        Pt b = Pt::new(0.0, 1.0);
        println("{}", orient(o, a, b));          // 1, b is left of o->a

        Pt c = Pt::new(2.0, 0.0);
        Pt d = Pt::new(3.0, 0.0);
        println("{}", orient(o, c, d));          // 0, all three collinear

        Pt v = Pt::new(3.0, 4.0);
        println("{}", v.length());               // 5
        println("{}", v.dot(Pt::new(1.0, 0.0))); // 3
    }

The `Pt` struct is both a point and a vector, because in two dimensions the two are the same collection of numbers and the same arithmetic. The methods are the operations that recur everywhere: `sub` gives a direction, `dot` measures alignment, `cross` measures signed area, and `length` uses the Pythagorean theorem. `crossOf` shifts the pair of vectors to start at `o` and then crosses them, which is the signed area of the triangle `o a b`. `orient` throws away the magnitude and keeps only the sign, because for a decision that is all that matters.

Cost and notes. Every operation here is a constant number of floating-point instructions. The orientation test in particular is four subtractions, two multiplications, and one subtraction, with no division, no square root, and no trigonometry. That is why it is the primitive of choice across the whole field: it is cheap enough to call inside an inner loop a million times, and it needs no special functions from the math library. The `length` method does need `sqrt`, so prefer `lengthSq` whenever you are comparing distances rather than reporting one; the square root is monotonic, so comparing squared lengths gives the same ordering at half the cost, and it avoids a rounding step.

Edge cases and variations. The orientation test is exact for coordinate values that are small integers, because each product is then an exact `f64` and the subtraction is exact while the result fits the fifty-three-bit mantissa. It is not exact in general. With coordinates around a million and points nearly collinear, the two products can be enormous numbers that should cancel, and the real (astronomically small) residue is lost to rounding, so `orient` can return `1` when the true answer is `0` or even `-1`. This is catastrophic cancellation, and it is why robust geometry libraries use exact predicates (Shewchuk's adaptive orientation, for instance) when the input coordinates are large or the caller cannot tolerate a wrong sign. For the algorithms below, whose inputs are small, the plain test is fine. A useful variation is to return the raw cross product as an `f64` rather than a sign, so a caller with a tolerance can compare it against an epsilon; `orient` can then be built on top, reading the sign. The trade is that the raw value has units of area, so the right epsilon depends on the coordinate scale, and choosing it badly reintroduces the very errors the exact test avoided.

38.2 The Convex Hull by Andrew's Monotone Chain

The problem. Given a set of points in the plane, find the smallest convex polygon that contains all of them. The hull is the shape a rubber band would take if you stretched it around the points and let go.

Picture this. The points are nails hammered into a board. You loop an elastic band around the outermost ones. The band touches only the nails on the boundary, and between any two touching nails it runs straight. Points in the interior are not touched at all. The convex hull is exactly the set of nails the band touches, in order around the shape.

Brute force, then better. The brute-force hull tries every pair of points, asks whether all the others lie on one side of the line through them, and keeps the pairs that pass. That is O(n³): O(n²) pairs, each checked against O(n) points. Andrew's monotone chain does it in O(n log n) by the same insight twice. Sort the points by x, then build the hull's lower half by walking left to right and popping any point that would make a clockwise turn; then build the upper half by walking right to left with the same rule. Each point is pushed once and popped at most once, so each pass is linear, and the sort is the only non-linear step. The turn test is the orientation test of 37.1, which is why it earned its own section.

The implementation.

    import(lib) std::vec { Vec };
    import(lib) std::io::ios { println };

    struct Pt {
        f64 x;
        f64 y;
    }

    f64 crossOf(Pt o, Pt a, Pt b) {
        // signed area of triangle o-a-b; positive means a left turn
        return (a.x - o.x) * (b.y - o.y) - (a.y - o.y) * (b.x - o.x);
    }

    bool ptLess(Pt a, Pt b) {
        // order by x, breaking ties by y so the sort is a total order
        if (a.x != b.x) return a.x < b.x;
        return a.y < b.y;
    }

    Vec<Pt> convexHull(Vec<Pt>* pts) {
        usize n = pts->count();
        Vec<Pt> hull = Vec<Pt>::new();
        // fewer than three points cannot enclose an area
        if (n < 3) {
            for (usize i = 0; i < n; i += 1) hull.push(pts->at(i));
            return hull;
        }
        // sorting by x lets each chain be a single left-to-right sweep
        pts->sortBy(ptLess);

        // lower hull: walk sorted points left to right
        Vec<Pt> lower = Vec<Pt>::new();
        for (usize i = 0; i < n; i += 1) {
            Pt p = pts->at(i);
            // drop the middle point while it makes a clockwise or straight turn
            while (lower.count() >= 2 &&
                   crossOf(lower.at(lower.count() - 2), lower.at(lower.count() - 1), p) <= 0.0) {
                lower.pop();
            }
            // p is now a vertex of the lower chain
            lower.push(p);
        }

        // upper hull: the same rule walking right-to-left
        Vec<Pt> upper = Vec<Pt>::new();
        for (usize i = n; i > 0; i -= 1) {
            Pt p = pts->at(i - 1);
            while (upper.count() >= 2 &&
                   crossOf(upper.at(upper.count() - 2), upper.at(upper.count() - 1), p) <= 0.0) {
                upper.pop();
            }
            upper.push(p);
        }

        lower.pop();                       // the last point of each chain is the first of the other
        upper.pop();
        // concatenate the two chains into one closed ring
        for (usize i = 0; i < lower.count(); i += 1) hull.push(lower.at(i));
        for (usize i = 0; i < upper.count(); i += 1) hull.push(upper.at(i));
        return hull;
    }

    void main() {
        Vec<Pt> pts = Vec<Pt>::new();
        pts.push(Pt { .x = 0.0, .y = 0.0 });
        pts.push(Pt { .x = 1.0, .y = 0.0 });
        pts.push(Pt { .x = 0.0, .y = 1.0 });
        pts.push(Pt { .x = 1.0, .y = 1.0 });
        pts.push(Pt { .x = 0.5, .y = 0.5 });   // deep inside; must be dropped

        Vec<Pt> hull = convexHull(&pts);
        println("{}", hull.count());           // 4
    }

The lower chain is built by walking the sorted points left to right. Its last two points and the incoming point form a turn; if the turn is clockwise or straight (`crossOf <= 0`), the middle point is not on the hull's lower edge and is popped. The loop repeats until the last turn is a proper counter-clockwise one, then pushes the new point. The upper chain is the mirror image, walking in reverse. Both chains begin and end at the extreme left and right points, so their final points are duplicates of the first points of the other; the two `pop` calls remove that duplication before the chains are concatenated into one closed ring. The `<= 0.0` is a deliberate choice: it discards collinear points, producing a hull whose vertices are the strict corners. Change it to `< 0.0` and the algorithm keeps collinear boundary points, which some problems want.

Cost and notes. Sorting dominates at O(n log n). Each chain is a single left-to-right pass with a stack; every point is pushed at most once and popped at most once over the whole pass, so both chains together are O(n). The total is therefore O(n log n) time and O(n) space for the two chains and the result. That is asymptotically optimal for hull-finding, since the input might need to be sorted and sorting is a lower bound for the comparison model. The `sortBy` call mutates the caller's vector in place, which is worth knowing.

Edge cases and variations. Fewer than three points cannot enclose an area, and the early return hands the input back unchanged, duplicates and all. A set that is entirely collinear produces a degenerate "hull" of two points, which the `<= 0.0` rule leaves after the two pops; the honest description is a segment, not a polygon, and a caller that needs a true polygon should test for that case. Duplicate points survive the sort and are removed by the same collinearity test, because a duplicate makes a zero-area turn and gets popped. The floating-point caveat from 37.1 applies with force here: the test that decides a pop is a sign test, and near-collinear points with large coordinates can flip it. If your coordinates are large integers, do the orientation in exact integer arithmetic (the products are then exact) by widening to `i64` or `i128` and comparing there. The natural variation is the rotating calipers pass: once the hull is in hand, the farthest pair of points, the minimum-width enclosing rectangle, and the diameter can all be found in linear time by sweeping two tangent lines around the hull, and each of those uses the same cross product again.

38.3 Point in a Polygon by Ray Casting

The problem. Given a polygon as a list of vertices in order, and a query point, decide whether the point is inside the polygon.

Picture this. The polygon is a pond, and you are standing at the query point holding a laser pointer aimed at the horizon. You count how many times the beam crosses the shoreline on its way out. If the crossing count is odd, you are in the water; if even, you are on dry land. That is the entire idea, and it is called the even-odd rule. The beam does not have to be horizontal, but a horizontal one is the easiest to test against, because a polygon edge crosses it exactly when its two endpoints are on opposite sides of the query point's y-coordinate.

Brute force, then better. The brute-force test casts a ray and computes an explicit intersection with every edge, being careful about the ray direction and the angle. It works, but it needs the intersections, not just their count, and every special case (parallel edges, rays through vertices) has to be handled separately. The parity method never forms an intersection point except as a comparison. For each edge, ask whether it straddles the horizontal line through the query point; if it does, compute the x-coordinate where it crosses, and if that crossing is to the right of the query point, flip the parity. An odd total means inside. No angles, no ray direction, one comparison per edge.

The implementation.

    import(lib) std::vec { Vec };
    import(lib) std::io::ios { println };

    struct Pt {
        f64 x;
        f64 y;
    }

    bool pointInPolygon(const Vec<Pt>* poly, Pt p) {
        usize n = poly->count();
        // a polygon needs at least three vertices
        if (n < 3) return false;
        // the parity of crossings to the right of p decides inside or outside
        bool inside = false;
        usize j = n - 1;                        // j trails i, so each edge is (j, i)
        for (usize i = 0; i < n; i += 1) {
            Pt a = poly->at(i);
            Pt b = poly->at(j);
            // true exactly when the edge spans the horizontal line through p
            bool straddles = (a.y > p.y) != (b.y > p.y);
            if (straddles) {
                // x where the edge meets p's y, by linear interpolation
                f64 xHit = a.x + (p.y - a.y) * (b.x - a.x) / (b.y - a.y);
                // a crossing to the right flips the parity
                if (p.x < xHit) inside = !inside;
            }
            // advance the trailing index for the next edge
            j = i;
        }
        return inside;
    }

    void main() {
        Vec<Pt> square = Vec<Pt>::new();
        square.push(Pt { .x = 0.0, .y = 0.0 });
        square.push(Pt { .x = 4.0, .y = 0.0 });
        square.push(Pt { .x = 4.0, .y = 4.0 });
        square.push(Pt { .x = 0.0, .y = 4.0 });

        println("{}", pointInPolygon(&square, Pt { .x = 2.0, .y = 2.0 }));  // true
        println("{}", pointInPolygon(&square, Pt { .x = 5.0, .y = 2.0 }));  // false
    }

The `straddles` test is the half-open rule that makes the vertex cases work out. Comparing `a.y > p.y` to `b.y > p.y` is true exactly when one endpoint is strictly above the query line and the other is at or below it, so an edge that ends exactly on the line is counted by the edge below it and ignored by the edge above it. Each vertex therefore participates in exactly one crossing test, and a ray that passes exactly through a vertex is neither double-counted nor missed. When an edge straddles, the linear interpolation gives the x where it crosses the query's y, and the `p.x < xHit` asks whether that crossing is to the right. The parity flips on each crossing to the right, and the answer is the parity at the end.

Cost and notes. One pass over the vertices, O(n) time and O(1) space. Each edge does two comparisons and, for at most a few of them, one interpolation. The division `(b.y - a.y)` is safe by construction: the straddle test guarantees the two y-values are on opposite sides of `p.y`, so they cannot be equal and the denominator cannot be zero. There is no allocation and no square root. For a single query this is as cheap as it gets; if you must answer many queries against the same polygon, precompute the polygon's bounding box as a quick reject, and for very large polygon counts build an edge index or use a sweep line.

Edge cases and variations. A point exactly on an edge is the ambiguous case, and this code does not define it cleanly: depending on rounding it may report inside or outside, and neither answer is wrong because "on the boundary" is not "inside" for the even-odd rule. A caller that needs boundary points to count as inside should test each edge for a zero cross product and a point within the edge's bounding box before running the parity test. A self-intersecting polygon is handled by the odd-even rule but not by the winding rule; a figure-eight shape has points that are "inside" under winding number and "outside" under parity, and the two notions disagree. The polygon must be given in order, though not necessarily counter-clockwise: reversing the order does not change the parity. And the denominators `b.y - a.y` are the place where floating-point error enters, so a point whose y lies almost exactly on an edge can be classified either way. The standard variation is the winding-number version, which adds `+1` or `−1` per crossing depending on the edge's direction instead of flipping a boolean; it distinguishes the figure-eight, handles the boundary more gracefully, and costs one extra comparison per crossing.

38.4 Do Two Segments Cross?

The problem. Given four points forming two line segments, decide whether the segments intersect, including the cases where an endpoint of one lies on the other.

Picture this. Two straight sticks lie on a table. They cross if the endpoints of the first stick are on opposite sides of the line through the second, and the endpoints of the second are on opposite sides of the line through the first. That double-sidedness is the test, and the side is exactly the orientation sign from 37.1. The only fiddly cases are when an endpoint lies exactly on the other segment, which the side test alone cannot see.

Brute force, then better. The algebra-first method solves the two parametric line equations for the intersection parameters and checks that both lie in `[0, 1]`. It is exact in principle but it divides, introduces floating-point error at the division step, and needs four separate special cases for the parallel, collinear, and touching configurations. The orientation method never divides. It computes four signs, and if two of them are strictly opposite for both segments, the segments cross at an interior point. If any sign is zero, an endpoint is collinear with the other segment, and a short bounding-box test decides whether that endpoint actually lies on it.

The implementation.

    import(lib) std::io::ios { println };
    import(lib) std::math::math { minF64, maxF64 };

    struct Pt {
        f64 x;
        f64 y;
    }

    f64 crossOf(Pt o, Pt a, Pt b) {
        return (a.x - o.x) * (b.y - o.y) - (a.y - o.y) * (b.x - o.x);
    }

    i32 orient(Pt o, Pt a, Pt b) {
        f64 c = crossOf(o, a, b);
        if (c > 0.0) return 1;
        if (c < 0.0) return -1;
        return 0;
    }

    bool onSegment(Pt a, Pt b, Pt p) {
        // p lies within the segment's axis-aligned bounding box
        return p.x <= maxF64(a.x, b.x) && p.x >= minF64(a.x, b.x) &&
               p.y <= maxF64(a.y, b.y) && p.y >= minF64(a.y, b.y);
    }

    bool segmentsIntersect(Pt p1, Pt p2, Pt p3, Pt p4) {
        // four orientation signs relative to the two segment lines
        i32 d1 = orient(p3, p4, p1);
        i32 d2 = orient(p3, p4, p2);
        i32 d3 = orient(p1, p2, p3);
        i32 d4 = orient(p1, p2, p4);

        if (d1 != d2 && d3 != d4) return true;             // proper crossing

        if (d1 == 0 && onSegment(p3, p4, p1)) return true; // collinear touches
        if (d2 == 0 && onSegment(p3, p4, p2)) return true;
        if (d3 == 0 && onSegment(p1, p2, p3)) return true;
        if (d4 == 0 && onSegment(p1, p2, p4)) return true;
        return false;
    }

    void main() {
        Pt a = Pt { .x = 0.0, .y = 0.0 };
        Pt b = Pt { .x = 4.0, .y = 4.0 };
        Pt c = Pt { .x = 0.0, .y = 4.0 };
        Pt d = Pt { .x = 4.0, .y = 0.0 };
        println("{}", segmentsIntersect(a, b, c, d));    // true: the diagonals cross

        Pt e = Pt { .x = 5.0, .y = 5.0 };
        Pt f = Pt { .x = 6.0, .y = 6.0 };
        println("{}", segmentsIntersect(a, b, e, f));    // false: disjoint
    }

The four orientations ask, in order, where `p1` and `p2` lie relative to segment 3–4, and where `p3` and `p4` lie relative to segment 1–2. A proper crossing needs both segments to separate the other's endpoints: `d1 != d2` says 3–4 straddles the line of 1–2 in side terms, and `d3 != d4` says 1–2 straddles the line of 3–4. Because each `d` is a sign, `d1 != d2` is true both when the signs are `1` and `-1` and when one is `0`; the strict proper-crossing test should really require opposite nonzero signs, but the code lets the collinear branch catch the zero cases, which is why the four `if` lines follow. Each of those lines checks a zero orientation together with the bounding-box containment of `onSegment`, which is the standard way to test "the point lies on the segment" without any division.

Cost and notes. Constant time and constant space: four orientation tests, each a few multiplications, plus up to four bounding-box tests that are two comparisons each. There is no division and no square root, which keeps the error analysis simple. The comparisons `minF64` and `maxF64` come straight from `std::math::math`. This function is the inner loop of polygon clipping, sweep-line algorithms, and collision detection, so its constant factor matters, and the orientation formulation beats the parametric one mostly because it moves all the error-producing division out of the hot path.

Edge cases and variations. Collinear overlapping segments are reported as intersecting, because the two endpoints of one lie on the other's bounding box; whether that is the answer you want depends on the problem, and a caller that only wants proper crossings should drop the four `if` lines. Zero-length segments (a point) lie on another segment exactly when the bounding-box test passes and the orientation is zero, which the code handles. The floating-point caveat is the sharp one: `orient` returning `0` is a sign test on a difference of products, and for nearly collinear large coordinates it can return `0` when the true orientation is nonzero, or a nonzero value when the true orientation is zero. Robust collision code uses an epsilon or exact predicates here, precisely because the near-miss cases are the common ones in practice. The natural variation is the segment-segment closest-distance routine, which returns how far apart two non-intersecting segments are; it uses the same orientations to decide which endpoint-to-segment distances to compare, and the answer reduces to four point-to-segment distance computations.

38.5 The Closest Pair of Points

The problem. Given n points in the plane, find the two whose straight-line distance is smallest, and report that distance. This is the geometric cousin of the minimum difference in a sorted array, and it is the classic demonstration of divide and conquer outside of sorting.

Picture this. The points are scattered on a sheet of paper. Draw a vertical line down the middle, solve the problem separately on the left half and the right half, and take the smaller of the two answers as a provisional best. Any pair that beats it must straddle the dividing line, and both of its points must lie within the provisional distance of the line. That narrow strip is the only place left to look, and if you sort the strip by y, each point needs to be compared against only the handful immediately above it. The geometry guarantees at most seven, which is the fact that turns an O(n²) search into a linear merge.

Brute force, then better. Every pair is O(n²) distance computations. The divide-and-conquer algorithm sorts the points by x once, halves the problem, and spends O(n) on the strip merge, giving the recurrence `T(n) = 2T(n/2) + O(n)`, which is O(n log n). The version below sorts the strip at every level rather than merging by y, which costs O(n log n) per level and makes the whole algorithm O(n log² n). That is a factor of log n slower than the optimal merge, and it is the version worth writing first because it is far easier to get right; the merge optimisation is a clean refinement, and it is named in the variations.

The implementation.

    import(lib) std::vec { Vec };
    import(lib) std::io::ios { println };
    import(lib) std::math::math { sqrt };

    struct Pt {
        f64 x;
        f64 y;
    }

    f64 distSq(Pt a, Pt b) {
        f64 dx = a.x - b.x;
        f64 dy = a.y - b.y;
        // squared distance; the inner loop never needs the square root
        return dx * dx + dy * dy;
    }

    bool ptLessX(Pt a, Pt b) {
        // sort by x, tie-broken by y so the order is total
        if (a.x != b.x) return a.x < b.x;
        return a.y < b.y;
    }

    bool ptLessY(Pt a, Pt b) {
        // sort the strip by y so close neighbours in y are adjacent
        if (a.y != b.y) return a.y < b.y;
        return a.x < b.x;
    }

    f64 closestRec(const Vec<Pt>* pts, usize lo, usize hi) {
        // the range [lo, hi) holds n points
        usize n = hi - lo;
        if (n <= 3) {                               // small case: compare every pair
            f64 best = 1e300;
            for (usize i = lo; i < hi; i += 1) {
                for (usize j = i + 1; j < hi; j += 1) {
                    f64 d = distSq(pts->at(i), pts->at(j));
                    if (d < best) best = d;
                }
            }
            return best;                            // squared distance
        }

        // split point; the points are already sorted by x
        usize mid = lo + n / 2;
        f64 midX = pts->at(mid).x;
        // best within each half, then the better of the two
        f64 bestLeft = closestRec(pts, lo, mid);
        f64 bestRight = closestRec(pts, mid, hi);
        f64 best = bestLeft < bestRight ? bestLeft : bestRight;

        // only points within best of the dividing line can beat it
        Vec<Pt> strip = Vec<Pt>::new();
        for (usize i = lo; i < hi; i += 1) {
            f64 dx = pts->at(i).x - midX;
            if (dx * dx < best) strip.push(pts->at(i));
        }
        // y-order means any closer point is one of the few just above
        strip.sortBy(ptLessY);

        for (usize i = 0; i < strip.count(); i += 1) {
            usize limit = i + 8;                    // the geometry caps useful neighbours at seven
            if (limit > strip.count()) limit = strip.count();
            for (usize j = i + 1; j < limit; j += 1) {
                f64 d = distSq(strip.at(i), strip.at(j));
                if (d < best) best = d;
            }
        }
        return best;
    }

    f64 closestPair(Vec<Pt>* pts) {
        usize n = pts->count();
        // fewer than two points has no pair
        if (n < 2) return -1.0;
        // sort once by x, then solve recursively
        pts->sortBy(ptLessX);
        // interior returns squared distances; take the root only at the end
        return sqrt(closestRec(pts, 0, n));
    }

    void main() {
        Vec<Pt> pts = Vec<Pt>::new();
        pts.push(Pt { .x = 0.0, .y = 0.0 });
        pts.push(Pt { .x = 5.0, .y = 5.0 });
        pts.push(Pt { .x = 1.0, .y = 0.0 });
        pts.push(Pt { .x = 9.0, .y = 9.0 });
        println("{}", closestPair(&pts));           // 1
    }

`closestRec` works on the index range `[lo, hi)` of a vector already sorted by x. Ranges with three or fewer points are solved directly, which is the base case that makes the recursion terminate. Otherwise it splits at the midpoint index and recurses on both halves; because the vector is sorted by x, the split index really does separate the left points from the right. The smaller of the two half-answers is the provisional best. The strip holds every point whose x lies within that provisional distance of the dividing line, ignoring the y-coordinate for now, and it is sorted by y so that close neighbours in y are adjacent. The inner loop compares each strip point with the next seven, and the `limit` clamp keeps the last points from reading past the end. The result is a squared distance throughout, and the square root is taken once at the end in `closestPair`.

Cost and notes. The recurrence without the y-merge is `T(n) = 2T(n/2) + O(n log n)` for the strip sort at each level, which solves to O(n log² n) time. The space is O(n) for the recursion's strip vectors, plus the O(log n) stack. The comparison bound of seven is the geometric heart of the algorithm and is worth believing: if the strip is sorted by y, consider a point and the eight-by-eight grid of cells of side `best` around it. Each cell can contain at most one point of the strip on each side of the line, or two points within a cell would be closer than `best`, contradicting the recursive answers. So at most a constant number of points can be within `best` of any given point, and checking seven above it is enough. That constant is why the merge is linear, and why the whole algorithm can be nearly `n log n`.

Edge cases and variations. Fewer than two points has no pair, and `closestPair` returns `-1.0` as an explicit "undefined" marker; a caller that prefers an `Option<f64>` can wrap it. Duplicate points give a distance of zero, which the base case finds immediately and no later comparison beats; a strict `<` means the first such pair is kept, which is fine because the distance is what is returned. Points with identical x are handled by the `ptLessX` tie-break on y, so the sort is a total order and the split index is well defined. Floating-point honesty applies here too: all comparisons are on squared distances, so no square root is taken until the answer is reported, which removes one source of rounding, but `distSq` still subtracts nearly equal coordinates when points are close, and that cancellation is the dominant error for tightly clustered inputs. The important variation is the true O(n log n) version: return the strip already sorted by y from each recursive call (merging two sorted lists, which is linear) instead of re-sorting it, and the `O(n log n)` per level drops to `O(n)`. A second variation, when the points lie on a circle or the coordinate range is small, is to sort by x, sweep, and maintain a sliding window of candidates; for integer coordinates there is even an O(n log log n) grid method.

38.6 Verlet Integration: A Particle Under Gravity

The problem. Simulate a point mass moving under a constant force, and let it bounce off a floor. The simulation must update the position in small time steps without the energy of the motion slowly leaking away or blowing up.

Picture this. A ball is thrown across a room. You know where it is now and where it was a moment ago. Verlet integration says the ball keeps roughly the same step it just took, adjusted by the force: the next position is the current position plus the current-minus-previous position (the velocity, times the step) plus the acceleration times the step squared. You never store a velocity explicitly; it is implied by the difference between the last two positions. That implicitness is the whole trick, and it is why the scheme is stable where a naive Euler update drifts.

Brute force, then better. The obvious update is explicit Euler: `v += a·dt; x += v·dt`. It is the first thing anyone writes, and it is wrong for simulations meant to run long. Each step adds a small error proportional to `dt²`, and over many steps the ball gains or loses energy until it flies off the screen or sinks through the floor. Verlet's update is both more symmetric and more stable. Because the update is time-reversible and symplectic, the energy oscillates slightly around the true value instead of marching in one direction, which is exactly what you want from a physics engine.

The implementation.

    import(lib) std::io::ios { println };

    struct Particle {
        f64 x;
        f64 y;
        f64 px;      // previous position
        f64 py;
        f64 ax;      // acceleration
        f64 ay;
    }

    void step(Particle* p, f64 dt) {
        // the implied velocity is the last change in position
        f64 vx = p->x - p->px;
        f64 vy = p->y - p->py;
        // shift the position history forward before writing the new position
        p->px = p->x;
        p->py = p->y;
        // next position = current + velocity + acceleration term
        p->x = p->x + vx + p->ax * dt * dt;
        p->y = p->y + vy + p->ay * dt * dt;

        if (p->y < 0.0) {                 // hit the floor: reflect and damp
            // capture the downward speed before clamping
            f64 drop = p->y - p->py;
            // rest the ball exactly on the floor
            p->y = 0.0;
            // set py so the next implied velocity reverses and scales by 0.8
            p->py = p->y + drop * 0.8;
        }
    }

    void main() {
        // a small fixed step keeps the integration stable
        f64 dt = 0.01;
        Particle ball = Particle {
            .x = 0.0, .y = 10.0,
            .px = 0.0 - 2.0 * dt, .py = 10.0,   // initial horizontal velocity of 2 per second
            .ax = 0.0, .ay = -9.81
        };
        // advance the simulation 500 steps
        for (usize i = 0; i < 500; i += 1) {
            step(&ball, dt);
            // print only every hundredth step to keep the output short
            if (i % 100 == 0) println("{} {}", ball.x, ball.y);
        }
    }

The step function first reads the implied velocity as the difference of the current and previous positions, then overwrites the previous position with the current one, then writes the new position. The next position is the current plus that same difference plus the acceleration term. Gravity is a constant `ay = -9.81`; there is no drag in this example, so the horizontal motion is a straight line and only the vertical motion curves. The floor is handled after the move: if the ball has dropped below `y = 0`, it is placed exactly on the floor and its previous y is set so that the next implied velocity is the old downward one reversed and scaled by `0.8`, which models a bouncy but lossy surface. Getting the previous position (not the velocity) right is the only subtle part of a Verlet collision, and it is done by writing `py` from `y` and the captured drop.

Cost and notes. Each step is a constant number of additions, subtractions, and multiplications, with no divisions, square roots, or trigonometry, so a step is a handful of nanoseconds and a million-particle simulation runs in real time. The stability is the payoff. The scheme conserves energy up to an oscillation of order `dt²`, and it is time-reversible, meaning running it backward with the same `dt` retraces the path, which is a strong correctness check. The price is that the implied velocity is one step out of date, so the position is, in a sense, reported half a step ahead of the velocity; the leapfrog and velocity-Verlet schemes rearrange the same quantities to fix that, at the cost of a little more bookkeeping.

Edge cases and variations. A large `dt` still breaks the simulation: the acceleration term grows with `dt²`, and if the step is large enough that the ball moves more than its own size per frame, it can tunnel through the floor and end up below it, where the bounce rule then keeps flipping it. The cure is a small enough step, or a continuous collision test that stops the ball at the floor rather than after it has passed through. The bounce coefficient is a modelling choice; `0.8` loses energy on purpose, and `1.0` would be a perfectly elastic bounce. When the ball is exactly on the floor and at rest, `drop` is zero and the fix leaves it there, which is the correct resting state. The natural variation is to add a second particle and a spring between them, which is the beginning of a cloth or a soft-body simulation: the spring applies equal and opposite accelerations that depend on the current distance, and the same step function integrates both ends. A second variation is to replace the constant gravity with a force that varies with position, which turns the example into a general-purpose ordinary-differential-equation integrator.

38.7 The N-Body Problem

The problem. Simulate several massive bodies attracting each other under Newtonian gravity, and advance them all forward in time. With two bodies it is the orbit problem and has a closed-form solution; with three or more there is no general formula, and you must integrate.

Picture this. Every body pulls on every other body with a force that grows with the product of their masses and falls off with the square of the distance. A body with many neighbours feels the sum of all those pulls, which is its acceleration, and its velocity and position follow. The catch is that the force changes as soon as any body moves, so each time step must recompute every pairwise force from scratch. That recomputation is O(n²), and it is the reason the n-body problem is the standard example of an algorithm that is quadratic for a fundamental reason rather than a fixable one.

Brute force, then better. There is no clever trick at the level of this chapter: the honest method computes all pairwise forces each step. What there is to get right is not the asymptotic cost but the shape of the update and the treatment of close encounters. The force is proportional to `1/r²`, so two bodies that come very close produce an enormous acceleration and then a numerical explosion. The standard fix is a softening length `ε`: replace `r²` with `r² + ε²`, which limits the maximum force and keeps the integration finite. The update order also matters. Computing all accelerations from the positions at the start of the step, then applying them, is the leapfrog arrangement, and it is far more stable than updating each body's velocity the instant its force is known.

The implementation.

    import(lib) std::vec { Vec };
    import(lib) std::io::ios { println };
    import(lib) std::math::math { sqrt };

    struct Body {
        f64 x;
        f64 y;
        f64 vx;
        f64 vy;
        f64 mass;
    }

    void nbodyStep(Vec<Body>* bodies, f64 dt) {
        usize n = bodies->count();
        // accumulate accelerations separately so no body sees a half-updated state
        Vec<f64> ax = Vec<f64>::new();
        Vec<f64> ay = Vec<f64>::new();
        // start every acceleration at zero
        for (usize i = 0; i < n; i += 1) {
            ax.push(0.0);
            ay.push(0.0);
        }

        // for each body, sum the pull from every other body
        for (usize i = 0; i < n; i += 1) {
            Body bi = bodies->at(i);
            for (usize j = 0; j < n; j += 1) {
                // a body does not attract itself
                if (i == j) continue;
                Body bj = bodies->at(j);
                // displacement from i to j
                f64 dx = bj.x - bi.x;
                f64 dy = bj.y - bi.y;
                f64 r2 = dx * dx + dy * dy + 0.01;      // softening keeps r2 away from zero
                // gravity needs 1/r^3 times the displacement vector
                f64 invR = 1.0 / sqrt(r2);
                f64 invR3 = invR * invR * invR;
                // Newton: acceleration is mass_j * displacement / r^3
                ax.set(i, ax.at(i) + bj.mass * dx * invR3);
                ay.set(i, ay.at(i) + bj.mass * dy * invR3);
            }
        }

        // apply accelerations only after all have been computed (leapfrog)
        for (usize i = 0; i < n; i += 1) {
            Body b = bodies->at(i);
            // update velocity first, then position with the new velocity
            b.vx += ax.at(i) * dt;
            b.vy += ay.at(i) * dt;
            b.x += b.vx * dt;
            b.y += b.vy * dt;
            // write the updated body back into the vector
            bodies->set(i, b);
        }
    }

    void main() {
        Vec<Body> bodies = Vec<Body>::new();
        bodies.push(Body { .x = 0.0, .y = 0.0, .vx = 0.0, .vy = 0.0, .mass = 10.0 });
        bodies.push(Body { .x = 1.0, .y = 0.0, .vx = 0.0, .vy = 3.0, .mass = 1.0 });
        bodies.push(Body { .x = 0.0, .y = 1.0, .vx = -3.0, .vy = 0.0, .mass = 1.0 });

        // run the simulation for 100 small steps
        for (usize i = 0; i < 100; i += 1) nbodyStep(&bodies, 0.001);

        for (usize i = 0; i < bodies.count(); i += 1) {
            Body b = bodies.at(i);
            println("{} {}", b.x, b.y);
        }
    }

The double loop accumulates each body's acceleration into the `ax` and `ay` arrays. For body `i`, every other body `j` contributes a force along the vector from `i` to `j`, scaled by `mass_j` and by `1/r³` (the `1/r²` from the force, times another `1/r` because the displacement vector is not yet a unit vector). All accelerations are computed from the positions at the beginning of the step, and only after the full pass are the velocities and then the positions updated. That separation is what makes the update symplectic: no body sees another body's half-updated position. The gravitational constant is folded into the chosen units and left as `1`, and the softening `0.01` is a hard floor on `r²` that trades a little physical accuracy near close encounters for numerical survival.

Cost and notes. The double loop is O(n²) per step, dominated entirely by the `sqrt`. There is no way around that with this formulation, which is why the gravitational n-body problem is one of the great consumers of supercomputers: a million bodies is a trillion force terms per step. The space is O(n) for the acceleration arrays, which are reallocated each call; moving them out of the function and clearing them in place would save the allocation churn in a long run. The update is a semi-implicit Euler step, the simplest energy-stable version; the velocity-Verlet and leapfrog variants keep the error smaller for the same `dt`.

Edge cases and variations. Two bodies with exactly the same position produce a zero displacement vector, and without softening the `1/r³` term would be infinite; the `+ 0.01` is what keeps it finite, and the physically honest reading is that the softening models the bodies as extended clouds rather than points. The time step must be small compared to the fastest orbital period in the system, or the integration will drift outward and the bodies will fly apart; an adaptive step that shrinks when two bodies come close is the standard remedy and the beginning of a real integrator. Momentum is conserved by the equal-and-opposite pairwise forces, up to floating-point rounding, and the total is a useful invariant to print while debugging. Energy is only approximately conserved, and watching it drift is the honest way to choose a step size. The natural variation is to use Barnes-Hut: build a quadtree of the bodies, treat distant clusters as single masses at their centre, and drop the cost to O(n log n) at the price of a controllable approximation. That is how galaxy simulations handle billions of stars, and it is the same softening-and-quadtree idea at scale.

38.8 Conway's Game of Life

The problem. On a grid of cells, each cell is alive or dead. At each generation every cell looks at its eight neighbours, and a fixed rule decides its next state under the same rule. The rule is a cellular automaton, and its study is a small universe of surprising complexity from three lines of arithmetic.

Picture this. A huge sheet of graph paper, each square either black or white. At each tick of a clock, every square counts its eight surrounding squares and then, all at once, adopts its next colour. A live square with exactly two or three live neighbours survives; a live square with any other count dies, of loneliness or overcrowding. A dead square with exactly three live neighbours is born. The simultaneous update is the crucial detail: every cell must read the old generation and write the new one, or the cells nearest the scan order would see a partially updated world.

Brute force, then better. The brute-force version reconstructs the whole grid from scratch by, for each cell, scanning all cells to find its neighbours, which is O(n²) per generation. That is needless. The neighbour count only ever involves the eight adjacent cells, so a single pass that consults the offsets is O(n) per generation. The two details that make the code pleasant are a flat one-dimensional buffer indexed by `r * cols + c`, which is cache-friendly and avoids a vector of vectors, and a wrapping neighbourhood, which makes the grid a torus so that a glider flying off one edge reappears on the other.

The implementation.

    import(lib) std::vec { Vec };
    import(lib) std::io::ios { println };
    import(lib) std::text::string { String };

    struct Life {
        usize rows;
        usize cols;
        Vec<u8> cells;

        static Life new(usize rows, usize cols) {
            Life g;
            g.rows = rows;
            g.cols = cols;
            g.cells = Vec<u8>::new();
            // start with a grid of dead cells
            for (usize i = 0; i < rows * cols; i += 1) g.cells.push(0);
            return g;
        }

        void setAlive(usize r, usize c) {
            // a live cell is stored as 1 at its flat index
            self.cells.set(r * self.cols + c, 1);
        }

        u32 neighbors(usize r, usize c) {
            // count the eight surrounding cells
            u32 count = 0;
            isize rr = (isize)r;
            isize cc = (isize)c;
            for (isize dr = -1; dr <= 1; dr += 1) {
                for (isize dc = -1; dc <= 1; dc += 1) {
                    // the cell itself is not its own neighbour
                    if (dr == 0 && dc == 0) continue;
                    // +dim keeps the offset non-negative before the modulo wraps it
                    isize nr = (rr + dr + (isize)self.rows) % (isize)self.rows;
                    isize nc = (cc + dc + (isize)self.cols) % (isize)self.cols;
                    // add the neighbour's state, which is 0 or 1
                    count += (u32)self.cells.at((usize)nr * self.cols + (usize)nc);
                }
            }
            return count;
        }

        void step() {
            usize total = self.rows * self.cols;
            // build the next generation in a separate buffer
            Vec<u8> next = Vec<u8>::new();
            for (usize i = 0; i < total; i += 1) next.push(0);
            for (usize r = 0; r < self.rows; r += 1) {
                for (usize c = 0; c < self.cols; c += 1) {
                    u32 live = self.neighbors(r, c);
                    u8 alive = self.cells.at(r * self.cols + c);
                    // default is death
                    u8 nextAlive = 0;
                    if (alive != 0) {
                        if (live == 2 || live == 3) nextAlive = 1;   // survives
                    } else {
                        if (live == 3) nextAlive = 1;                // born
                    }
                    next.set(r * self.cols + c, nextAlive);
                }
            }
            // commit the new generation only once it is fully computed
            for (usize i = 0; i < total; i += 1) self.cells.set(i, next.at(i));
        }

        void printSelf() {
            for (usize r = 0; r < self.rows; r += 1) {
                String line = String::new();
                for (usize c = 0; c < self.cols; c += 1) {
                    u8 alive = self.cells.at(r * self.cols + c);
                    // render alive cells as '#' and dead cells as '.'
                    line.pushChar(alive != 0 ? (u8)'#' : (u8)'.');
                }
                println("{}", line.asView());
            }
        }
    }

    void main() {
        Life g = Life::new(6, 6);
        g.setAlive(1, 2);              // a glider, the smallest spaceship
        g.setAlive(2, 3);
        g.setAlive(3, 1);
        g.setAlive(3, 2);
        g.setAlive(3, 3);

        g.printSelf();
        println("{}", "---");
        for (usize i = 0; i < 4; i += 1) g.step();
        g.printSelf();
    }

The grid is a flat `Vec<u8>` of length `rows * cols`, and cell `(r, c)` lives at index `r * cols + c`. `neighbors` walks the eight offsets `dr, dc` in `{−1, 0, 1}²`, skipping the centre, and wraps each coordinate with `(value + dim) % dim` so that the neighbourhood is toroidal. The `+ dim` before the modulo is essential: without it, a `−1` would be a negative `isize` and `%` would produce a negative remainder, indexing before the start of the buffer. `step` builds a fresh `next` buffer rather than writing in place, because every cell must see the old generation; only after the whole grid is computed is `next` copied back into `cells`, one element at a time. The four rules are written as two nested `if`s, and the whole automaton is those four lines.

Cost and notes. Each generation visits every cell once and does a constant nine-observation neighbourhood count, so the time is O(rows × cols) per step and O(generations × rows × cols) overall. The space is two grids, O(rows × cols), which is the minimum for a simultaneous update: you need the old state somewhere while you build the new one. The flat buffer is a real speed advantage over `Vec<Vec<u8>>`, because the eight neighbours of a cell are then at neighbouring addresses rather than in eight different allocations, and the cache does its job. The wrapping is free, just a modulo per coordinate.

Edge cases and variations. A one-cell-wide grid makes the torus odd: a cell is its own neighbour in the wrapped direction, which the loop counts more than once, and the result is not the usual Game of Life. That is a consequence of the topology, not a bug, but it is worth knowing. With fewer than two rows or columns the neighbour counts become meaningless, so a real implementation checks for a minimum size. `next.set` writes every cell, so no stale state survives the copy, and the `for (usize i = 0; i < total; i += 1) self.cells.set(i, next.at(i))` line could instead swap the two buffers if the struct kept both, saving the copy at the cost of one more field. Floating-point is absent here, which is a rare pleasure in this chapter: the Game of Life is exact integer and bit operations, and its only numerical decision is a count. The natural variation is to reuse two buffers and swap them, or to use a `Bitset` from `std::collections::bitset` so a cell costs one bit and the neighbour count becomes a shift-and-mask. A second variation is to add more states (the wire-world rule, for instance), which changes only the four `if` lines and leaves the neighbourhood machinery untouched.

38.9 Monte Carlo Estimation

The problem. Estimate a number that is hard to compute by formula, by generating many random samples and averaging. The canonical example estimates π: throw darts at a square, count how many land inside the inscribed circle, and the ratio approaches the ratio of the areas.

Picture this. You have a square dartboard from `(0, 0)` to `(1, 1)`, with a quarter circle of radius one centred at the origin. Throw darts uniformly at the square and count the hits inside the quarter circle. A uniform dart lands in the circle with probability equal to the circle's area divided by the square's, which is `π/4`. So four times the observed hit rate estimates π. Each extra digit needs roughly a hundred times more darts, which is the honest, unglamorous truth about Monte Carlo: it converges, slowly, as the inverse square root of the sample count.

Brute force, then better. There is no better method in this chapter, and that is the point. Monte Carlo earns its place when the region is irregular or the dimension is high, where quadrature grids become intractable; in one dimension a Riemann sum is faster and more accurate, but the same code, with a different test, estimates the volume of a shape no formula describes. The quality of the estimate is governed entirely by the quality of the random source and the number of samples. This version uses the library's `nextF64`, which draws from the operating system's secure random source, so the run is not reproducible; a seeded generator is the honest choice when you need to debug a run twice.

The implementation.

    import(lib) std::io::ios { println };
    import(lib) std::math::random { nextF64 };

    f64 estimatePi(u64 samples) {
        // no samples means no meaningful estimate
        if (samples == 0) return 0.0;
        // count darts that land inside the quarter circle
        u64 inside = 0;
        for (u64 i = 0; i < samples; i += 1) {
            f64 x = nextF64();               // uniform on [0, 1)
            f64 y = nextF64();
            // inside the unit circle; the squared test avoids a square root
            if (x * x + y * y <= 1.0) inside += 1;
        }
        // hit fraction times four estimates pi
        return 4.0 * (f64)inside / (f64)samples;
    }

    void main() {
        println("{}", estimatePi(1000));        // a rough guess
        println("{}", estimatePi(100000));      // closer
        println("{}", estimatePi(10000000));    // closer still, for more darts
    }

Each iteration draws two independent uniforms on `[0, 1)`, treats them as a dart's coordinates, and counts the dart if it lies inside the unit circle. The test `x*x + y*y <= 1.0` is the defining inequality of the circle, and it avoids the square root entirely because both sides are non-negative, so squaring preserves the comparison. The final estimate multiplies the hit fraction by four, the ratio of the square's area to the quarter circle's. `nextF64` is documented to return `[0, 1)`, so the darts are uniform over the square, which is the only distributional requirement.

Cost and notes. Linear in the number of samples, with a constant two random draws, two multiplications, and a comparison per sample. The error of a Monte Carlo estimate falls as `1/√n` in expectation, so a hundredfold increase in samples buys one more correct decimal digit, and a millionfold increase buys three. The `10,000,000` sample call above is still fast because a random draw and a comparison cost a few nanoseconds, but the accuracy is only about three digits. That slow convergence is not a flaw of the code; it is the mathematical law, and the variance of the estimator is what it is. The free functions in `std::math::random` draw from `/dev/urandom`, which is cryptographically strong but slower than a purpose-built PRNG; for a large simulation a seeded `XorShift32` or `Pcg32` is both faster and reproducible, and its statistical quality is more than enough for this purpose.

Edge cases and variations. Zero samples has no meaningful fraction, and the guard returns `0.0` rather than dividing by zero. The darts are uniform but not exactly so, because `nextF64` produces a fixed number of distinct values; for ten million samples that discretisation is far below the statistical noise, so it does not matter here, but a subroutine that needs a continuous distribution should beware of the grid. Points exactly on the circle are counted as inside by the `<=`, and the measure of that boundary is zero, so the choice does not bias the estimate. The estimate is not a deterministic function: run it twice and you get two answers, which is expected and is the point. The natural generalisation replaces the circle test with the indicator of any region, so `estimatePi` becomes `estimateArea(inside)` with a predicate; the same loop then integrates any function by averaging its values on random points, which is the Monte Carlo method proper. A second variation uses antithetic or stratified sampling, pairing each dart with a reflected one or dividing the square into strata, to reduce the variance for the same number of samples. And a serious check is to estimate the standard error, `sqrt(p(1−p)/n)` with `p` the hit fraction, so the reported number carries an honest uncertainty instead of a false precision.
