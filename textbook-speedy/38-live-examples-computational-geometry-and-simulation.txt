Chapter38

Live Examples: Computational Geometry and Simulation

Shapes, Motions, and the Arithmetic That Refuses to Be Exact

Computational geometry asks a handful of planar questions: is this point left of that line, do these segments cross, is this point inside that polygon, which two points are closest? Asked naively, each hides an O(n^2) or worse algorithm. The trick is one invariant, the signed area. The convex hull, point-in-polygon, segment intersection, and closest pair are one cross product wearing four hats.

Simulation is geometry that moves. A particle under gravity, a cluster of attracting bodies, a grid of living and dead cells: each is state updated in steps, with a conservation or stability property deciding whether the numbers drift or explode. Verlet integration keeps energy roughly constant. The n-body problem is the honest O(n^2) force calculation, softened for close encounters. The Game of Life is a state machine built on a clean neighbourhood count.

The theme is floating-point error (Chapter32.9). The cross product is exact for small integers and wrong for nearly collinear points, because large products that should cancel leave a rounding residue. A ray through an edge can count it zero or twice. An orbit with a large step drifts. These are not wrong lines but the cost of `f64`; name them, choose tolerances deliberately, and know when exact integer arithmetic would save you.

Each example is a complete program: imports, the point or body struct, the algorithm, and a `void main()` demonstrating it. Each reads alone and repeats its declarations.

38.1 Points, Vectors, and the Orientation Test

The problem. Represent a point (or vector) and answer the question every geometry algorithm is built from: given `o`, `a`, and `b`, is `b` left of the directed line from `o` to `a`, right of it, or exactly on it?

Picture this. Standing at `o` facing `a`, if `b` is left, triangle `o -> a -> b` turns counter-clockwise; if right, clockwise; if dead ahead or behind, the points are collinear. That is the orientation of the triple.

Brute force, then better. Comparing `atan2` angles is slow and discontinuous where the angle wraps from pi to -pi, so points across the seam compare as if on opposite sides. The signed area of the parallelogram is `(a.x - o.x)(b.y - o.y) - (a.y - o.y)(b.x - o.x)`. Its sign is the orientation, it costs a few multiplications, and it has no seam.

The implementation.

    import(lib) std::vec { Vec };
    import(lib) std::io::ios { println };
    import(lib) std::math::math { sqrt };

    struct Pt {
        f64 x;
        f64 y;

        // construct a point from its coordinates
        static Pt new(f64 x, f64 y) {
            return Pt { .x = x, .y = y };
        }

        // difference of two points is the direction vector between them
        Pt sub(Pt other) {
            return Pt { .x = self.x - other.x, .y = self.y - other.y };
        }

        // multiply both components by a scalar
        Pt scale(f64 s) {
            return Pt { .x = self.x * s, .y = self.y * s };
        }

        // dot product measures how aligned two vectors are
        f64 dot(Pt other) {
            return self.x * other.x + self.y * other.y;
        }

        // 2D cross product is the signed area of the parallelogram
        f64 cross(Pt other) {
            return self.x * other.y - self.y * other.x;
        }

        // squared length: avoids a square root when only comparing distances
        f64 lengthSq() {
            return self.x * self.x + self.y * self.y;
        }

        // Euclidean length via the Pythagorean theorem
        f64 length() {
            return sqrt(self.lengthSq());
        }
    }

    f64 crossOf(Pt o, Pt a, Pt b) {
        // shift both vectors to start at o ...
        Pt oa = a.sub(o);
        Pt ob = b.sub(o);
        // ... then cross them; the sign says which way b turns from o to a
        return oa.cross(ob);
    }

    i32 orient(Pt o, Pt a, Pt b) {
        f64 c = crossOf(o, a, b);
        if (c > 0.0) return 1;      // counter-clockwise: b is to the left
        if (c < 0.0) return -1;     // clockwise: b is to the right
        return 0;                   // collinear
    }

    void main() {
        Pt o = Pt::new(0.0, 0.0);
        Pt a = Pt::new(1.0, 0.0);
        Pt b = Pt::new(0.0, 1.0);
        println("{}", orient(o, a, b));          // 1, b is left of o->a

        Pt c = Pt::new(2.0, 0.0);
        Pt d = Pt::new(3.0, 0.0);
        println("{}", orient(o, c, d));          // 0, all three collinear

        Pt v = Pt::new(3.0, 4.0);
        println("{}", v.length());               // 5
        println("{}", v.dot(Pt::new(1.0, 0.0))); // 3
    }

`Pt` is both point and vector, since in two dimensions they are the same numbers and arithmetic. `sub` gives a direction, `dot` measures alignment, `cross` measures signed area, `length` uses Pythagoras. `crossOf` shifts both vectors to `o`, giving the signed area of triangle `o a b`; `orient` keeps only the sign.

Cost and notes. Every operation is a constant number of floating-point instructions. Orientation is four subtractions, two multiplications, and a subtraction, with no division, square root, or trigonometry, which is why it is the field's primitive. `length` needs `sqrt`, so prefer `lengthSq` when comparing distances: monotonic, same ordering, half the cost, one less rounding step.

Edge cases and variations. Orientation is exact for small integer coordinates, since each product and the subtraction fit the 53-bit mantissa. It is not exact in general: with coordinates around a million and nearly collinear points, two huge products should cancel, and the residue is lost, so `orient` can return `1` when the truth is `0` or `-1`. This is catastrophic cancellation, which is why robust libraries use exact predicates such as Shewchuk's. For small inputs the plain test is fine. A variation returns the raw cross product for an epsilon comparison, but its area units make the right epsilon scale-dependent.

38.2 The Convex Hull by Andrew's Monotone Chain

The problem. Given points in the plane, find the smallest convex polygon containing all of them, the shape a rubber band would take around them.

Picture this. The points are nails in a board. An elastic band touches only the boundary nails and runs straight between them; interior points are untouched. The hull is the touched nails, in order.

Brute force, then better. The brute-force hull tries every pair, checks that all other points lie on one side, and keeps the pairs that pass: O(n^3). Andrew's monotone chain is O(n log n) by the same insight twice. Sort by x, build the lower half left to right, popping any point that makes a clockwise turn; then build the upper half right to left. Each point is pushed once and popped at most once, so each pass is linear and the sort dominates. The turn test is orientation from 37.1.

The implementation.

    import(lib) std::vec { Vec };
    import(lib) std::io::ios { println };

    struct Pt {
        f64 x;
        f64 y;
    }

    f64 crossOf(Pt o, Pt a, Pt b) {
        // signed area of triangle o-a-b; positive means a left turn
        return (a.x - o.x) * (b.y - o.y) - (a.y - o.y) * (b.x - o.x);
    }

    bool ptLess(Pt a, Pt b) {
        // order by x, breaking ties by y so the sort is a total order
        if (a.x != b.x) return a.x < b.x;
        return a.y < b.y;
    }

    Vec<Pt> convexHull(Vec<Pt>* pts) {
        usize n = pts->count();
        Vec<Pt> hull = Vec<Pt>::new();
        // fewer than three points cannot enclose an area
        if (n < 3) {
            for (usize i = 0; i < n; i += 1) hull.push(pts->at(i));
            return hull;
        }
        // sorting by x lets each chain be a single left-to-right sweep
        pts->sortBy(ptLess);

        // lower hull: walk sorted points left to right
        Vec<Pt> lower = Vec<Pt>::new();
        for (usize i = 0; i < n; i += 1) {
            Pt p = pts->at(i);
            // drop the middle point while it makes a clockwise or straight turn
            while (lower.count() >= 2 &&
                   crossOf(lower.at(lower.count() - 2), lower.at(lower.count() - 1), p) <= 0.0) {
                lower.pop();
            }
            // p is now a vertex of the lower chain
            lower.push(p);
        }

        // upper hull: the same rule walking right-to-left
        Vec<Pt> upper = Vec<Pt>::new();
        for (usize i = n; i > 0; i -= 1) {
            Pt p = pts->at(i - 1);
            while (upper.count() >= 2 &&
                   crossOf(upper.at(upper.count() - 2), upper.at(upper.count() - 1), p) <= 0.0) {
                upper.pop();
            }
            upper.push(p);
        }

        lower.pop();                       // the last point of each chain is the first of the other
        upper.pop();
        // concatenate the two chains into one closed ring
        for (usize i = 0; i < lower.count(); i += 1) hull.push(lower.at(i));
        for (usize i = 0; i < upper.count(); i += 1) hull.push(upper.at(i));
        return hull;
    }

    void main() {
        Vec<Pt> pts = Vec<Pt>::new();
        pts.push(Pt { .x = 0.0, .y = 0.0 });
        pts.push(Pt { .x = 1.0, .y = 0.0 });
        pts.push(Pt { .x = 0.0, .y = 1.0 });
        pts.push(Pt { .x = 1.0, .y = 1.0 });
        pts.push(Pt { .x = 0.5, .y = 0.5 });   // deep inside; must be dropped

        Vec<Pt> hull = convexHull(&pts);
        println("{}", hull.count());           // 4
    }

The lower chain walks sorted points left to right. If the last two and the incoming point make a clockwise or straight turn (`crossOf <= 0`), the middle point is popped. Repeat until the turn is counter-clockwise, then push. The upper chain mirrors this in reverse. Both chains share their extreme endpoints, so the two `pop` calls remove the duplicates before concatenation. `<= 0.0` discards collinear points, producing strict corners; `< 0.0` keeps them.

Cost and notes. Sorting dominates at O(n log n). Each chain is one stack pass, each point pushed once and popped at most once, so O(n). Total: O(n log n) time, O(n) space, asymptotically optimal since sorting is a lower bound. `sortBy` mutates the caller's vector.

Edge cases and variations. Fewer than three points cannot enclose an area, so the early return hands the input back unchanged. A collinear set produces a degenerate two-point 'hull', really a segment. Duplicates are removed by the collinearity test, since a duplicate makes a zero-area turn. The sign test can flip for nearly collinear large coordinates; use exact `i64` or `i128` arithmetic for large integers. The natural variation is rotating calipers: farthest pair, minimum-width rectangle, and diameter are linear-time sweeps over the hull using the same cross product.

38.3 Point in a Polygon by Ray Casting

The problem. Given a polygon as ordered vertices and a query point, decide whether the point is inside.

Picture this. The polygon is a pond; you stand at the query point and shine a laser at the horizon, counting shoreline crossings. Odd means in the water, even means dry land. This is the even-odd rule. A horizontal beam is easiest: an edge crosses it exactly when its endpoints lie on opposite sides of the query's y.

Brute force, then better. The brute-force test computes explicit intersections with every edge, needing ray directions, angles, and special handling for parallel edges and rays through vertices. Parity never forms an intersection point except as a comparison. For each edge, ask whether it straddles the horizontal line through the query; if so, compute the crossing x and flip parity if it is to the right. An odd total means inside.

The implementation.

    import(lib) std::vec { Vec };
    import(lib) std::io::ios { println };

    struct Pt {
        f64 x;
        f64 y;
    }

    bool pointInPolygon(const Vec<Pt>* poly, Pt p) {
        usize n = poly->count();
        // a polygon needs at least three vertices
        if (n < 3) return false;
        // the parity of crossings to the right of p decides inside or outside
        bool inside = false;
        usize j = n - 1;                        // j trails i, so each edge is (j, i)
        for (usize i = 0; i < n; i += 1) {
            Pt a = poly->at(i);
            Pt b = poly->at(j);
            // true exactly when the edge spans the horizontal line through p
            bool straddles = (a.y > p.y) != (b.y > p.y);
            if (straddles) {
                // x where the edge meets p's y, by linear interpolation
                f64 xHit = a.x + (p.y - a.y) * (b.x - a.x) / (b.y - a.y);
                // a crossing to the right flips the parity
                if (p.x < xHit) inside = !inside;
            }
            // advance the trailing index for the next edge
            j = i;
        }
        return inside;
    }

    void main() {
        Vec<Pt> square = Vec<Pt>::new();
        square.push(Pt { .x = 0.0, .y = 0.0 });
        square.push(Pt { .x = 4.0, .y = 0.0 });
        square.push(Pt { .x = 4.0, .y = 4.0 });
        square.push(Pt { .x = 0.0, .y = 4.0 });

        println("{}", pointInPolygon(&square, Pt { .x = 2.0, .y = 2.0 }));  // true
        println("{}", pointInPolygon(&square, Pt { .x = 5.0, .y = 2.0 }));  // false
    }

The `straddles` test is the half-open rule that makes vertex cases work. Comparing `a.y > p.y` to `b.y > p.y` is true exactly when one endpoint is strictly above the query line and the other at or below, so an edge ending on the line is counted by the edge below and ignored by the edge above. Each vertex participates in exactly one test, so a ray through a vertex is neither double-counted nor missed. On a straddle, interpolation gives the crossing x, and `p.x < xHit` flips parity.

Cost and notes. One pass over vertices: O(n) time and O(1) space. Each edge does two comparisons and, for a few, one interpolation. The division is safe because a straddle guarantees the y-values are on opposite sides, so the denominator is nonzero. No allocation and no square root. For many queries, precompute a bounding box as a quick reject; for very large polygons, build an edge index or sweep line.

Edge cases and variations. A point exactly on an edge is ambiguous: rounding may report inside or outside, and neither is wrong, since boundary is not inside under the even-odd rule. To count boundary as inside, test each edge for a zero cross product and bounding-box containment first. A self-intersecting polygon follows the odd-even rule but not the winding rule; a figure-eight disagrees between them. Vertex order may be either direction. The `b.y - a.y` denominator is where floating-point error enters. The standard variation is winding number, adding +1 or -1 per crossing by edge direction; it distinguishes the figure-eight and handles boundaries better.

38.4 Do Two Segments Cross?

The problem. Given four points forming two segments, decide whether they intersect, including endpoints lying on the other segment.

Picture this. Two sticks cross if each one's endpoints lie on opposite sides of the other's line. That double-sidedness is the test, and the side is orientation from 37.1. The fiddly cases are endpoints exactly on the other segment, which the side test cannot see.

Brute force, then better. The algebra-first method solves the parametric equations and checks both parameters lie in `[0, 1]`. It divides, introduces error, and needs special cases for parallel, collinear, and touching configurations. The orientation method never divides: four signs, and if both segments separate the other's endpoints, they cross at an interior point. A zero sign means collinearity, and a bounding-box test decides whether the endpoint lies on the segment.

The implementation.

    import(lib) std::io::ios { println };
    import(lib) std::math::math { minF64, maxF64 };

    struct Pt {
        f64 x;
        f64 y;
    }

    f64 crossOf(Pt o, Pt a, Pt b) {
        return (a.x - o.x) * (b.y - o.y) - (a.y - o.y) * (b.x - o.x);
    }

    i32 orient(Pt o, Pt a, Pt b) {
        f64 c = crossOf(o, a, b);
        if (c > 0.0) return 1;
        if (c < 0.0) return -1;
        return 0;
    }

    bool onSegment(Pt a, Pt b, Pt p) {
        // p lies within the segment's axis-aligned bounding box
        return p.x <= maxF64(a.x, b.x) && p.x >= minF64(a.x, b.x) &&
               p.y <= maxF64(a.y, b.y) && p.y >= minF64(a.y, b.y);
    }

    bool segmentsIntersect(Pt p1, Pt p2, Pt p3, Pt p4) {
        // four orientation signs relative to the two segment lines
        i32 d1 = orient(p3, p4, p1);
        i32 d2 = orient(p3, p4, p2);
        i32 d3 = orient(p1, p2, p3);
        i32 d4 = orient(p1, p2, p4);

        if (d1 != d2 && d3 != d4) return true;             // proper crossing

        if (d1 == 0 && onSegment(p3, p4, p1)) return true; // collinear touches
        if (d2 == 0 && onSegment(p3, p4, p2)) return true;
        if (d3 == 0 && onSegment(p1, p2, p3)) return true;
        if (d4 == 0 && onSegment(p1, p2, p4)) return true;
        return false;
    }

    void main() {
        Pt a = Pt { .x = 0.0, .y = 0.0 };
        Pt b = Pt { .x = 4.0, .y = 4.0 };
        Pt c = Pt { .x = 0.0, .y = 4.0 };
        Pt d = Pt { .x = 4.0, .y = 0.0 };
        println("{}", segmentsIntersect(a, b, c, d));    // true: the diagonals cross

        Pt e = Pt { .x = 5.0, .y = 5.0 };
        Pt f = Pt { .x = 6.0, .y = 6.0 };
        println("{}", segmentsIntersect(a, b, e, f));    // false: disjoint
    }

The four orientations ask where `p1` and `p2` lie relative to segment 3-4, and where `p3` and `p4` lie relative to 1-2. A proper crossing needs both segments to separate the other's endpoints: `d1 != d2` and `d3 != d4`. Since each `d` is a sign, inequality is also true when one is zero, so the four `if` lines catch collinear cases. Each checks a zero orientation plus bounding-box containment from `onSegment`, which tests 'point on segment' without division.

Cost and notes. Constant time and space: four orientation tests plus up to four bounding-box tests. No division or square root keeps the error analysis simple. This is the inner loop of clipping, sweep-line algorithms, and collision detection, so its constant factor matters; orientation beats the parametric form by keeping division out of the hot path.

Edge cases and variations. Collinear overlapping segments are reported as intersecting, because one's endpoints lie in the other's bounding box; drop the four `if` lines to report only proper crossings. Zero-length segments are handled by the bounding-box and zero-orientation test. `orient` returning zero is a sign test on a difference of products, so nearly collinear large coordinates can flip it; robust code uses an epsilon or exact predicates. The natural variation is segment-to-segment closest distance, which uses the same orientations to choose among four point-to-segment distances.

38.5 The Closest Pair of Points

The problem. Given n points, find the two with the smallest straight-line distance and report it. This is the geometric cousin of the minimum difference in a sorted array, and the classic divide-and-conquer demonstration outside sorting.

Picture this. Scatter the points on paper. Draw a vertical line down the middle, solve each half, and take the smaller answer as provisional best. Any better pair must straddle the line, with both points within the provisional distance of it. That strip is the only place left to look, and sorting it by y means each point need only be compared with a handful above it. Geometry guarantees at most seven, turning the O(n^2) search into a linear merge.

Brute force, then better. Every pair is O(n^2). Divide and conquer sorts by x once, halves the problem, and spends O(n) on the strip merge, giving `T(n) = 2T(n/2) + O(n)`, which is O(n log n). The version below re-sorts the strip at every level, costing O(n log n) per level and O(n log^2 n) overall. That is a log factor slower but far easier to get right; the merge is named in the variations.

The implementation.

    import(lib) std::vec { Vec };
    import(lib) std::io::ios { println };
    import(lib) std::math::math { sqrt };

    struct Pt {
        f64 x;
        f64 y;
    }

    f64 distSq(Pt a, Pt b) {
        f64 dx = a.x - b.x;
        f64 dy = a.y - b.y;
        // squared distance; the inner loop never needs the square root
        return dx * dx + dy * dy;
    }

    bool ptLessX(Pt a, Pt b) {
        // sort by x, tie-broken by y so the order is total
        if (a.x != b.x) return a.x < b.x;
        return a.y < b.y;
    }

    bool ptLessY(Pt a, Pt b) {
        // sort the strip by y so close neighbours in y are adjacent
        if (a.y != b.y) return a.y < b.y;
        return a.x < b.x;
    }

    f64 closestRec(const Vec<Pt>* pts, usize lo, usize hi) {
        // the range [lo, hi) holds n points
        usize n = hi - lo;
        if (n <= 3) {                               // small case: compare every pair
            f64 best = 1e300;
            for (usize i = lo; i < hi; i += 1) {
                for (usize j = i + 1; j < hi; j += 1) {
                    f64 d = distSq(pts->at(i), pts->at(j));
                    if (d < best) best = d;
                }
            }
            return best;                            // squared distance
        }

        // split point; the points are already sorted by x
        usize mid = lo + n / 2;
        f64 midX = pts->at(mid).x;
        // best within each half, then the better of the two
        f64 bestLeft = closestRec(pts, lo, mid);
        f64 bestRight = closestRec(pts, mid, hi);
        f64 best = bestLeft < bestRight ? bestLeft : bestRight;

        // only points within best of the dividing line can beat it
        Vec<Pt> strip = Vec<Pt>::new();
        for (usize i = lo; i < hi; i += 1) {
            f64 dx = pts->at(i).x - midX;
            if (dx * dx < best) strip.push(pts->at(i));
        }
        // y-order means any closer point is one of the few just above
        strip.sortBy(ptLessY);

        for (usize i = 0; i < strip.count(); i += 1) {
            usize limit = i + 8;                    // the geometry caps useful neighbours at seven
            if (limit > strip.count()) limit = strip.count();
            for (usize j = i + 1; j < limit; j += 1) {
                f64 d = distSq(strip.at(i), strip.at(j));
                if (d < best) best = d;
            }
        }
        return best;
    }

    f64 closestPair(Vec<Pt>* pts) {
        usize n = pts->count();
        // fewer than two points has no pair
        if (n < 2) return -1.0;
        // sort once by x, then solve recursively
        pts->sortBy(ptLessX);
        // interior returns squared distances; take the root only at the end
        return sqrt(closestRec(pts, 0, n));
    }

    void main() {
        Vec<Pt> pts = Vec<Pt>::new();
        pts.push(Pt { .x = 0.0, .y = 0.0 });
        pts.push(Pt { .x = 5.0, .y = 5.0 });
        pts.push(Pt { .x = 1.0, .y = 0.0 });
        pts.push(Pt { .x = 9.0, .y = 9.0 });
        println("{}", closestPair(&pts));           // 1
    }

`closestRec` works on `[lo, hi)` of a vector sorted by x. Ranges of three or fewer points are solved directly, terminating the recursion. Otherwise it splits at the midpoint and recurses; sorted by x, the split index really separates left from right. The smaller half-answer is provisional. The strip holds points within that distance of the dividing line, sorted by y so close neighbours are adjacent. The inner loop compares each strip point with the next seven, and `limit` prevents reading past the end. Squared distances are used throughout; `closestPair` takes the root once at the end.

Cost and notes. Re-sorting the strip at each level gives `T(n) = 2T(n/2) + O(n log n)`, which solves to O(n log^2 n). Space is O(n) for strip vectors plus O(log n) stack. The seven-comparison bound is geometric: with the strip sorted by y, consider the grid of side `best` around a point. Each cell holds at most one point on each side of the line, or two would be closer than `best`, contradicting the recursive answers. So only a constant number can be within `best`, making the merge linear.

Edge cases and variations. Fewer than two points has no pair, so `closestPair` returns `-1.0` as an explicit undefined marker; wrap it in `Option<f64>` if preferred. Duplicates give distance zero, found by the base case; strict `<` keeps the first such pair. Equal x values are ordered by the y tie-break, so the split index is well defined. Squared distances remove one rounding step, but `distSq` still subtracts nearly equal coordinates for clustered points. The important variation returns the strip already sorted by y from each call (merging two sorted lists in linear time), turning O(n log n) per level into O(n).

38.6 Verlet Integration: A Particle Under Gravity

The problem. Simulate a point mass under constant force bouncing off a floor, updating position in small time steps without energy slowly leaking away or blowing up.

Picture this. A ball is thrown across a room. Verlet integration says the next position is the current position plus the current-minus-previous position (velocity times step) plus acceleration times step squared. Velocity is never stored; it is implied by the last two positions. That implicitness is the trick, and why the scheme is stable where naive Euler drifts.

Brute force, then better. Explicit Euler (`v += a*dt; x += v*dt`) is the first thing anyone writes and wrong for long runs: each step adds error proportional to `dt^2`, and over many steps the ball gains or loses energy until it flies off or sinks through the floor. Verlet's update is time-reversible and symplectic, so energy oscillates slightly around the true value instead of marching in one direction.

The implementation.

    import(lib) std::io::ios { println };

    struct Particle {
        f64 x;
        f64 y;
        f64 px;      // previous position
        f64 py;
        f64 ax;      // acceleration
        f64 ay;
    }

    void step(Particle* p, f64 dt) {
        // the implied velocity is the last change in position
        f64 vx = p->x - p->px;
        f64 vy = p->y - p->py;
        // shift the position history forward before writing the new position
        p->px = p->x;
        p->py = p->y;
        // next position = current + velocity + acceleration term
        p->x = p->x + vx + p->ax * dt * dt;
        p->y = p->y + vy + p->ay * dt * dt;

        if (p->y < 0.0) {                 // hit the floor: reflect and damp
            // capture the downward speed before clamping
            f64 drop = p->y - p->py;
            // rest the ball exactly on the floor
            p->y = 0.0;
            // set py so the next implied velocity reverses and scales by 0.8
            p->py = p->y + drop * 0.8;
        }
    }

    void main() {
        // a small fixed step keeps the integration stable
        f64 dt = 0.01;
        Particle ball = Particle {
            .x = 0.0, .y = 10.0,
            .px = 0.0 - 2.0 * dt, .py = 10.0,   // initial horizontal velocity of 2 per second
            .ax = 0.0, .ay = -9.81
        };
        // advance the simulation 500 steps
        for (usize i = 0; i < 500; i += 1) {
            step(&ball, dt);
            // print only every hundredth step to keep the output short
            if (i % 100 == 0) println("{} {}", ball.x, ball.y);
        }
    }

`step` reads implied velocity as the difference of current and previous positions, overwrites the previous with the current, then writes the new position. Gravity is constant `ay = -9.81`; with no drag, horizontal motion is a straight line. The floor is handled after the move: if `y < 0`, the ball is placed at `y = 0` and `py` is set so the next implied velocity reverses the old downward speed scaled by `0.8`, a bouncy but lossy surface. Getting the previous position, not the velocity, right is the subtle part of a Verlet collision.

Cost and notes. Each step is a constant number of additions, subtractions, and multiplications, with no division, square root, or trigonometry, so a million particles run in real time. Energy is conserved up to an oscillation of order `dt^2`, and the scheme is time-reversible, so running backward retraces the path. The price is that implied velocity is one step out of date; leapfrog and velocity-Verlet rearrange the same quantities to fix that.

Edge cases and variations. A large `dt` still breaks the simulation: the acceleration term grows with `dt^2`, and a ball moving more than its own size per frame can tunnel through the floor, where the bounce rule keeps flipping it. Use a smaller step or a continuous collision test. The bounce coefficient is a modelling choice: `0.8` loses energy, `1.0` is perfectly elastic. A ball at rest on the floor has zero `drop` and stays put. The natural variation adds a second particle and a spring, the beginning of cloth or soft-body simulation; another replaces constant gravity with a position-dependent force, making a general ODE integrator.

38.7 The N-Body Problem

The problem. Simulate massive bodies attracting each other under Newtonian gravity, advancing all forward in time. Two bodies have a closed-form solution; three or more have no general formula, so you integrate.

Picture this. Every body pulls on every other with force proportional to the product of masses and falling off as the square of distance. A body's acceleration is the sum of those pulls, and its velocity and position follow. The force changes as soon as any body moves, so each step recomputes every pairwise force: O(n^2) for a fundamental reason, not a fixable one.

Brute force, then better. There is no clever trick at this level; compute all pairwise forces each step. What matters is the update shape and close encounters. Force scales as `1/r^2`, so two bodies that come very close produce an enormous acceleration and a numerical explosion. The fix is a softening length: replace `r^2` with `r^2 + epsilon^2`. The update order also matters: compute all accelerations from the positions at the start of the step, then apply them, a leapfrog arrangement far more stable than updating velocities as each force is found.

The implementation.

    import(lib) std::vec { Vec };
    import(lib) std::io::ios { println };
    import(lib) std::math::math { sqrt };

    struct Body {
        f64 x;
        f64 y;
        f64 vx;
        f64 vy;
        f64 mass;
    }

    void nbodyStep(Vec<Body>* bodies, f64 dt) {
        usize n = bodies->count();
        // accumulate accelerations separately so no body sees a half-updated state
        Vec<f64> ax = Vec<f64>::new();
        Vec<f64> ay = Vec<f64>::new();
        // start every acceleration at zero
        for (usize i = 0; i < n; i += 1) {
            ax.push(0.0);
            ay.push(0.0);
        }

        // for each body, sum the pull from every other body
        for (usize i = 0; i < n; i += 1) {
            Body bi = bodies->at(i);
            for (usize j = 0; j < n; j += 1) {
                // a body does not attract itself
                if (i == j) continue;
                Body bj = bodies->at(j);
                // displacement from i to j
                f64 dx = bj.x - bi.x;
                f64 dy = bj.y - bi.y;
                f64 r2 = dx * dx + dy * dy + 0.01;      // softening keeps r2 away from zero
                // gravity needs 1/r^3 times the displacement vector
                f64 invR = 1.0 / sqrt(r2);
                f64 invR3 = invR * invR * invR;
                // Newton: acceleration is mass_j * displacement / r^3
                ax.set(i, ax.at(i) + bj.mass * dx * invR3);
                ay.set(i, ay.at(i) + bj.mass * dy * invR3);
            }
        }

        // apply accelerations only after all have been computed (leapfrog)
        for (usize i = 0; i < n; i += 1) {
            Body b = bodies->at(i);
            // update velocity first, then position with the new velocity
            b.vx += ax.at(i) * dt;
            b.vy += ay.at(i) * dt;
            b.x += b.vx * dt;
            b.y += b.vy * dt;
            // write the updated body back into the vector
            bodies->set(i, b);
        }
    }

    void main() {
        Vec<Body> bodies = Vec<Body>::new();
        bodies.push(Body { .x = 0.0, .y = 0.0, .vx = 0.0, .vy = 0.0, .mass = 10.0 });
        bodies.push(Body { .x = 1.0, .y = 0.0, .vx = 0.0, .vy = 3.0, .mass = 1.0 });
        bodies.push(Body { .x = 0.0, .y = 1.0, .vx = -3.0, .vy = 0.0, .mass = 1.0 });

        // run the simulation for 100 small steps
        for (usize i = 0; i < 100; i += 1) nbodyStep(&bodies, 0.001);

        for (usize i = 0; i < bodies.count(); i += 1) {
            Body b = bodies.at(i);
            println("{} {}", b.x, b.y);
        }
    }

The double loop accumulates each body's acceleration into `ax` and `ay`. For body `i`, every other body `j` contributes a force along the vector from `i` to `j`, scaled by `mass_j` and `1/r^3` (the `1/r^2` of the force times another `1/r` because the displacement is not a unit vector). All accelerations come from the positions at the start of the step, and only after the full pass are velocities and positions updated, making the update symplectic: no body sees a half-updated state. Gravity is folded into the units as `1`; softening `0.01` trades accuracy near close encounters for survival.

Cost and notes. The double loop is O(n^2) per step, dominated by the `sqrt`. There is no way around it with this formulation, which is why the gravitational n-body problem consumes supercomputers: a million bodies is a trillion force terms per step. Space is O(n) for the acceleration arrays, reallocated each call; moving them out and clearing in place saves churn. The update is semi-implicit Euler; velocity-Verlet and leapfrog keep the error smaller for the same `dt`.

Edge cases and variations. Two bodies at exactly the same position give zero displacement; without softening `1/r^3` would be infinite, so `+ 0.01` keeps it finite, modelling bodies as extended clouds. The time step must be small compared with the fastest orbital period, or the integration drifts outward and bodies fly apart; an adaptive step that shrinks on close approach is the standard remedy. Momentum is conserved by equal-and-opposite forces up to rounding, a useful invariant to print. Energy is only approximately conserved; watching it drift is how to choose a step size. The natural variation is Barnes-Hut: a quadtree treating distant clusters as single masses, dropping cost to O(n log n) for controllable approximation.

38.8 Conway's Game of Life

The problem. On a grid, each cell is alive or dead. Every generation, each cell examines its eight neighbours, and a fixed rule decides its next state. That rule is a cellular automaton, a small universe of surprising complexity from three lines of arithmetic.

Picture this. A sheet of graph paper, each square black or white. At each tick, every square counts its eight neighbours and then, all at once, adopts its next colour. A live square with two or three live neighbours survives; otherwise it dies. A dead square with exactly three live neighbours is born. The simultaneous update is crucial: every cell must read the old generation and write the new, or cells near the scan order see a partly updated world.

Brute force, then better. The brute-force version scans all cells to find each cell's neighbours: O(n^2) per generation. Needlessly. The count involves only eight adjacent cells, so one pass over offsets is O(n). Two details make the code pleasant: a flat buffer indexed by `r * cols + c`, which is cache-friendly, and a wrapping neighbourhood, making the grid a torus so a glider leaving one edge reappears on the other.

The implementation.

    import(lib) std::vec { Vec };
    import(lib) std::io::ios { println };
    import(lib) std::text::string { String };

    struct Life {
        usize rows;
        usize cols;
        Vec<u8> cells;

        static Life new(usize rows, usize cols) {
            Life g;
            g.rows = rows;
            g.cols = cols;
            g.cells = Vec<u8>::new();
            // start with a grid of dead cells
            for (usize i = 0; i < rows * cols; i += 1) g.cells.push(0);
            return g;
        }

        void setAlive(usize r, usize c) {
            // a live cell is stored as 1 at its flat index
            self.cells.set(r * self.cols + c, 1);
        }

        u32 neighbors(usize r, usize c) {
            // count the eight surrounding cells
            u32 count = 0;
            isize rr = (isize)r;
            isize cc = (isize)c;
            for (isize dr = -1; dr <= 1; dr += 1) {
                for (isize dc = -1; dc <= 1; dc += 1) {
                    // the cell itself is not its own neighbour
                    if (dr == 0 && dc == 0) continue;
                    // +dim keeps the offset non-negative before the modulo wraps it
                    isize nr = (rr + dr + (isize)self.rows) % (isize)self.rows;
                    isize nc = (cc + dc + (isize)self.cols) % (isize)self.cols;
                    // add the neighbour's state, which is 0 or 1
                    count += (u32)self.cells.at((usize)nr * self.cols + (usize)nc);
                }
            }
            return count;
        }

        void step() {
            usize total = self.rows * self.cols;
            // build the next generation in a separate buffer
            Vec<u8> next = Vec<u8>::new();
            for (usize i = 0; i < total; i += 1) next.push(0);
            for (usize r = 0; r < self.rows; r += 1) {
                for (usize c = 0; c < self.cols; c += 1) {
                    u32 live = self.neighbors(r, c);
                    u8 alive = self.cells.at(r * self.cols + c);
                    // default is death
                    u8 nextAlive = 0;
                    if (alive != 0) {
                        if (live == 2 || live == 3) nextAlive = 1;   // survives
                    } else {
                        if (live == 3) nextAlive = 1;                // born
                    }
                    next.set(r * self.cols + c, nextAlive);
                }
            }
            // commit the new generation only once it is fully computed
            for (usize i = 0; i < total; i += 1) self.cells.set(i, next.at(i));
        }

        void printSelf() {
            for (usize r = 0; r < self.rows; r += 1) {
                String line = String::new();
                for (usize c = 0; c < self.cols; c += 1) {
                    u8 alive = self.cells.at(r * self.cols + c);
                    // render alive cells as '#' and dead cells as '.'
                    line.pushChar(alive != 0 ? (u8)'#' : (u8)'.');
                }
                println("{}", line.asView());
            }
        }
    }

    void main() {
        Life g = Life::new(6, 6);
        g.setAlive(1, 2);              // a glider, the smallest spaceship
        g.setAlive(2, 3);
        g.setAlive(3, 1);
        g.setAlive(3, 2);
        g.setAlive(3, 3);

        g.printSelf();
        println("{}", "---");
        for (usize i = 0; i < 4; i += 1) g.step();
        g.printSelf();
    }

The grid is a flat `Vec<u8>` of length `rows * cols`, with cell `(r, c)` at index `r * cols + c`. `neighbors` walks the eight offsets, skips the centre, and wraps each coordinate with `(value + dim) % dim` so the neighbourhood is toroidal. The `+ dim` before the modulo is essential: without it, `-1` is a negative `isize`, `%` gives a negative remainder, and the index falls before the buffer. `step` builds a fresh `next` buffer because every cell must see the old generation; only after the full grid is computed is it copied back. The four rules are two nested `if`s.

Cost and notes. Each generation visits every cell once and does a constant nine-observation count: O(rows x cols) per step and O(generations x rows x cols) overall. Space is two grids, the minimum for a simultaneous update. The flat buffer beats `Vec<Vec<u8>>` because the eight neighbours sit at nearby addresses rather than in eight allocations. Wrapping costs one modulo per coordinate.

Edge cases and variations. A one-cell-wide grid makes the torus odd: a cell becomes its own neighbour in the wrapped direction and is counted more than once, so the result is not the usual Game of Life. With fewer than two rows or columns, neighbour counts are meaningless, so a real implementation checks for a minimum size. `next.set` writes every cell, so no stale state survives. The natural variation reuses two buffers and swaps them, or uses a `Bitset` so a cell costs one bit and the count becomes shift-and-mask. Another adds more states, changing only the four `if` lines.

38.9 Monte Carlo Estimation

The problem. Estimate a number that is hard to compute by formula, by generating many random samples and averaging. The canonical example estimates pi: throw darts at a square, count those inside the inscribed circle, and the ratio approaches the ratio of areas.

Picture this. A square dartboard from `(0, 0)` to `(1, 1)` with a quarter circle of radius one at the origin. Uniform darts land in the circle with probability `pi/4`, so four times the observed hit rate estimates pi. Each extra digit needs roughly a hundred times more darts: Monte Carlo converges slowly, as the inverse square root of the sample count.

Brute force, then better. There is no better method in this chapter, and that is the point. Monte Carlo earns its place when the region is irregular or the dimension high, where quadrature grids become intractable; in one dimension a Riemann sum is faster and more accurate. The estimate's quality is governed entirely by the random source and the sample count. This version uses `nextF64`, which draws from the operating system's secure source, so runs are not reproducible; use a seeded generator when debugging.

The implementation.

    import(lib) std::io::ios { println };
    import(lib) std::math::random { nextF64 };

    f64 estimatePi(u64 samples) {
        // no samples means no meaningful estimate
        if (samples == 0) return 0.0;
        // count darts that land inside the quarter circle
        u64 inside = 0;
        for (u64 i = 0; i < samples; i += 1) {
            f64 x = nextF64();               // uniform on [0, 1)
            f64 y = nextF64();
            // inside the unit circle; the squared test avoids a square root
            if (x * x + y * y <= 1.0) inside += 1;
        }
        // hit fraction times four estimates pi
        return 4.0 * (f64)inside / (f64)samples;
    }

    void main() {
        println("{}", estimatePi(1000));        // a rough guess
        println("{}", estimatePi(100000));      // closer
        println("{}", estimatePi(10000000));    // closer still, for more darts
    }

Each iteration draws two independent uniforms on `[0, 1)` and counts the dart if `x*x + y*y <= 1.0`, the circle inequality with no square root because both sides are non-negative. The estimate multiplies the hit fraction by four, the ratio of the square's area to the quarter circle's. `nextF64` returns `[0, 1)`, so the darts are uniform.

Cost and notes. Linear in samples, with two random draws, two multiplications, and a comparison each. Error falls as `1/sqrt(n)` in expectation, so a hundredfold increase buys one more decimal digit and a millionfold buys three. Ten million samples is fast but accurate to only about three digits. That slow convergence is the mathematical law. `std::math::random` draws from `/dev/urandom`, strong but slower than a purpose-built PRNG; a seeded `XorShift32` or `Pcg32` is faster and reproducible.

Edge cases and variations. Zero samples has no meaningful fraction, so the guard returns `0.0` instead of dividing by zero. The darts are uniform but discrete, because `nextF64` produces a fixed set of values; at ten million samples that is far below statistical noise. Points exactly on the circle count as inside via `<=`, but the boundary has measure zero, so there is no bias. The estimate is intentionally nondeterministic. The natural generalisation replaces the circle test with any region predicate, making `estimateArea(inside)`; the same loop integrates any function by averaging values at random points. Antithetic or stratified sampling reduces variance, and a serious check estimates the standard error `sqrt(p(1-p)/n)`.
