Chapter 32

Live Examples: Bits, Bytes, and Bit Manipulation

The Layer Under the Layer

Some problems are about bits: file formats pack fields into one word, network flags live in a nibble, permission masks are sets of bits, hash tables round to powers of two, and games pack entity flags. There the bit is the subject, and bit code is shorter, smaller, and clearer.

Coral uses the C operators: `&`, `|`, `^`, `~`, `<<`, `>>`. They act on fixed-width integers and mean exactly what the hardware means. This chapter covers seeing bytes, setting bits by name, counting them, recognising special shapes, endianness, and the edges: shifts by the type width, `>>` on negatives, and the aliasing bug in a famous trick.

Width matters: a `u8` is eight bits, a `u32` thirty-two, a `u64` sixty-four. Bits number from the right at zero. Unsigned types hold zero through two-to-the-width minus one; signed types use two's complement, where the top bit is the sign, `-1` is all ones, and adding one to the largest positive wraps to the most negative. Shifts and masks are defined against this machine representation.

32.1 Seeing Bits and Bytes

The problem. Decimal tells you almost nothing about bits: `255` and `256` look alike and are utterly different patterns. You need hex and binary views long enough to count.

The intuition. Hex is shorthand for binary, four bits per digit, so a byte is two digits: `0xB4` is `B` (1011) and `4` (0100). Binary is the honest view for small fields and offsets; hex is the compact view for addresses and dumps.

The approach. `println` accepts `{:d}`, `{:x}`, and `{:b}`. For fixed-width binary with leading zeros, write a helper that walks the bits high to low.

The implementation.

    import(lib) std::io::ios { println };
    import(lib) std::text::string { String };

    pub String bits8(u8 x) {
        // eight characters, one per bit
        String s = String::withCap(8);
        // walk the bits from high to low
        for (i32 i = 7; i >= 0; i -= 1) {
            // isolate bit i with a shift and a mask
            u8 bit = (u8)((x >> (u32)i) & 1u);
            // append '0' or '1'
            s.pushChar((u8)((u8)'0' + bit));
        }
        return s;
    }

    pub String bits32(u32 x) {
        String s = String::withCap(32);
        // same idea, one character per bit of a u32
        for (i32 i = 31; i >= 0; i -= 1) {
            u8 bit = (u8)((x >> (u32)i) & 1u);
            s.pushChar((u8)((u8)'0' + bit));
        }
        return s;
    }

    pub void show() {
        // a sample byte: 1011 0100
        u8 flags = 0xB4;
        println("hex  {:x}", flags);          // b4
        println("dec  {:d}", flags);          // 180
        println("bin  {:b}", flags);          // 10110100
        println("padded {}", bits8(flags));   // 10110100
    }

Cost and notes. The format specifiers cost nothing extra. The helper allocates a small `String` and writes one character per bit, O(width), which is irrelevant for a log line. The subtlety is the shift amount: the loop counts with an `i32` so it can stop below zero, and shifts by `(u32)` because the operators take an unsigned count.

Edge cases. `{:b}` and `{:x}` render only significant bits, so `1` prints as `1`; the helper exists for leading zeros. `{:x}` on a negative signed value prints its two's-complement pattern. `String::withCap` is a capacity hint, not an exact size.

Variation. Write `dumpBytes(const u8* data, usize n)` printing offset, sixteen hex bytes, and printable ASCII with dots for non-printing bytes.

32.2 Masks: Set, Clear, Toggle, Test

The problem. You have a bit at an index and want to set, clear, toggle, or test it. Raw shifts at every call site invite off-by-one errors.

The intuition. Four identities form the alphabet: set `x | (1 << i)`, clear `x & ~(1 << i)`, toggle `x ^ (1 << i)`, test `(x & (1 << i)) != 0`.

The approach. Wrap each in a named function over a `u64` word and a `u32` index, and state the index's valid range.

The implementation.

    pub u64 setBit(u64 x, u32 i) {
        // valid bit position
        @assertOut(i < 64u, "setBit: index must be below 64");
        // OR turns bit i on
        return x | ((u64)1 << i);
    }

    pub u64 clearBit(u64 x, u32 i) {
        @assertOut(i < 64u, "clearBit: index must be below 64");
        // AND with the complement turns bit i off
        return x & ~((u64)1 << i);
    }

    pub u64 toggleBit(u64 x, u32 i) {
        @assertOut(i < 64u, "toggleBit: index must be below 64");
        // XOR flips bit i
        return x ^ ((u64)1 << i);
    }

    pub bool testBit(u64 x, u32 i) {
        @assertOut(i < 64u, "testBit: index must be below 64");
        // shift bit i down, then mask it
        return ((x >> i) & 1u) != 0;
    }

    pub void run() {
        // all lights off
        u64 lights = 0;
        lights = setBit(lights, 0);
        lights = setBit(lights, 3);
        println("{}", testBit(lights, 0));   // true
        println("{}", testBit(lights, 1));   // false
        lights = toggleBit(lights, 0);
        println("{}", testBit(lights, 0));   // false
        lights = clearBit(lights, 3);
        println("{:b}", lights);             // 0
    }

Cost and notes. Each is one machine instruction. Wrapping costs nothing and buys clarity: the name states intent, the function states the boundary. In a fixed type `1 << 32` is undefined; the assertion turns that into a diagnostic.

Edge cases. The index must be strictly below the width; shifting by the width or more is undefined. In `setBit` and `clearBit`, `(u64)1` matters: a `u32` literal would make `1 << 40` evaluate to zero and silently do nothing.

Variation. Write `applyMask(x, mask, op)` over a `BitOp { Set, Clear, Toggle }` enum, the right shape when a permissions system records operations from data.

32.3 Counting Bits: Popcount and Parity

The problem. Count the one bits (popcount) and determine whether that count is even or odd (parity). They appear in hashes, error-detecting codes, chess engines, and cryptography.

The intuition. The obvious loop costs one step per bit. Better: `x & (x - 1)` clears the lowest set bit, so looping on that visits only set bits. Parity is the count modulo two, and it folds by XORing halves until one bit remains.

The approach. Kernighan's popcount, then folding parity, then a byte-table popcount for constant time with a small table.

The implementation.

    pub u32 popcount(u64 x) {
        // number of set bits
        u32 count = 0;
        // one iteration per set bit
        while (x != 0) {
            x &= x - 1;          // clear the lowest set bit
            count += 1;
        }
        return count;
    }

    pub u32 parity(u64 x) {
        // fold the high half onto the low half, repeatedly
        x ^= x >> 32;
        x ^= x >> 16;
        x ^= x >> 8;
        x ^= x >> 4;
        x ^= x >> 2;
        x ^= x >> 1;
        // the answer is now in bit zero
        return (u32)(x & 1u);
    }

    pub u32 popcountTable(const u8* table, u64 x) {
        // one table lookup per byte
        return (u32)table[(u8)(x)] +
               (u32)table[(u8)(x >> 8)] +
               (u32)table[(u8)(x >> 16)] +
               (u32)table[(u8)(x >> 24)] +
               (u32)table[(u8)(x >> 32)] +
               (u32)table[(u8)(x >> 40)] +
               (u32)table[(u8)(x >> 48)] +
               (u32)table[(u8)(x >> 56)];
    }

The parity fold works because XOR is associative and commutative: the parity of a word is the XOR of all its bits, so halves combine in any order. Six folds leave the answer in bit zero. The table version splits the word into eight bytes, each a constant-time lookup; the table is built once:

    pub Vec<u8> buildPopcountTable() {
        // popcount of every byte value
        Vec<u8> t = Vec<u8>::withCap(256);
        for (u32 i = 0; i < 256; i += 1) {
            u32 c = 0;
            u32 v = i;
            // count bits with the same trick
            while (v != 0) { v &= v - 1; c += 1; }
            t.push((u8)c);
        }
        return t;
    }

Cost and notes. Kernighan is O(number of set bits), one to sixty-four steps. The fold is always six steps. The table is eight lookups and additions, plus building 256 bytes once. Kernighan suits a handful of words; the table wins in a hot loop.

Edge cases. `popcount(0)` is zero; the loop does not run. Mask each byte with `(u8)` before indexing, or high bits can index out of the table. All fold shifts are below the width. A table with fewer than 256 entries or wrong values is a bug the compiler cannot catch.

Variation. Implement `popcount32` and `popcount8` by folding with masks (`x = (x & 0x55555555) + ((x >> 1) & 0x55555555)` and so on), computing the count in parallel with no loop and no table.

32.4 Power-of-Two Checks and the Low Bit

The problem. Recognise recurring shapes: is a number a power of two (so a mask replaces a modulo), what is its lowest set bit, and what is the next power of two above a request?

The intuition. A power of two has one bit set, and one less is a run of low ones, so `x != 0 && (x & (x - 1)) == 0` tests it. The lowest set bit is `x & (0 - x)` in unsigned arithmetic. The next power smears the highest bit downward with shifts, then adds one.

The approach. Three tiny functions plus the shift-smear trick, with a note on the overflow boundary.

The implementation.

    pub bool isPowerOfTwo(u64 x) {
        // nonzero and exactly one bit set
        return x != 0 && (x & (x - 1)) == 0;
    }

    pub u64 lowestSetBit(u64 x) {
        return x & ((u64)0 - x);         // unsigned wraparound gives the two's complement
    }

    pub u64 nextPowerOfTwo(u64 x) {
        // 0 and 1 round up to 1
        if (x <= 1) return 1;
        // set every bit below the top set bit...
        x -= 1;
        // ...doubling the run of ones each shift
        x |= x >> 1;
        x |= x >> 2;
        x |= x >> 4;
        x |= x >> 8;
        x |= x >> 16;
        x |= x >> 32;
        // carry into the next power of two
        return x + 1;
    }

The smear: after subtracting one, OR the number with itself shifted by one, then by two, four, eight, sixteen, and thirty-two, doubling the run of ones each time. Adding one carries it into a single higher bit. The shifts cover a sixty-four-bit word.

Cost and notes. The test and the low-bit isolate are single arithmetic operations. The smear is seven shifts and ORs, the fastest portable version without a hardware instruction. The low-bit identity relies on unsigned wraparound; the same expression on a signed type can overflow and is not portable.

Edge cases. Zero is not a power of two, so the explicit `x != 0` guard is required and must short-circuit before `x - 1` underflows. `lowestSetBit(0)` is zero. `nextPowerOfTwo` overflows above two to the sixty-third; production code returns an error or saturates.

Variation. Write `isPowerOfTwoMask(x)` returning zero when `x` is not a power of two and `x - 1` when it is, exactly what a hash table uses as `hash & (tableSize - 1)`.

32.5 Endianness

The problem. An integer is a sequence of bytes, least significant first on little-endian machines or most significant first on big-endian ones. Data crossing a file, socket, or shared segment must agree on the order.

The intuition. `0x01020304` is bytes 01, 02, 03, 04 from most to least significant; little-endian stores the 04 first, big-endian the 01. Both are conventions, and the difference is invisible until data crosses a boundary. Choose one order for anything leaving the machine (big-endian is the network convention) and convert explicitly there.

The approach. Detect the host order once, write byte-swap routines, and extract and assemble bytes explicitly rather than through a union.

The implementation.

    pub bool isLittleEndian() {
        // 1 is 01 00 00 00 or 00 00 00 01
        u32 probe = 1;
        // first byte is the least significant
        return *(u8*)&probe == 1;
    }

    pub u32 bswap32(u32 x) {
        // move each byte to the opposite end
        return ((x & 0x000000FFu) << 24) |
               ((x & 0x0000FF00u) << 8)  |
               ((x & 0x00FF0000u) >> 8)  |
               ((x & 0xFF000000u) >> 24);
    }

    pub u64 bswap64(u64 x) {
        return ((u64)bswap32((u32)x) << 32) | (u64)bswap32((u32)(x >> 32));
    }

    pub void toBigEndianBytes(u32 value, u8* out) {
        // most significant byte first
        out[0] = (u8)(value >> 24);
        out[1] = (u8)(value >> 16);
        out[2] = (u8)(value >> 8);
        // least significant byte last
        out[3] = (u8)value;
    }

    pub u32 fromBigEndianBytes(const u8* in) {
        // rebuild from big-endian order
        return ((u32)in[0] << 24) |
               ((u32)in[1] << 16) |
               ((u32)in[2] << 8)  |
               (u32)in[3];
    }

Cost and notes. The probe is one load and compare, done once. The swaps are a few shifts and masks, constant time, often a single instruction. Explicit pack and unpack have well-defined behaviour on every target, which is why serious serialisation never puns a struct over a byte buffer.

Edge cases. The probe reads a `u32` through a `u8*` and tests exactly that assumption, so keep it isolated. `fromBigEndianBytes` casts each byte to `u32` before shifting; without it a `u8` shifted by twenty-four loses all bits. Casting an arbitrary `u8*` to `u32*` can also be misaligned and fault.

Variation. Write `readU32OrBigEndian(u32 value, bool hostIsLittle)` to convert a host value to canonical big-endian and back, and round-trip values to test it.

32.6 The Bitset

The problem. You need a set over a dense bounded universe: which sockets are open, which frames arrived. Membership, insertion, and counting should be cheap and memory small.

The intuition. A `Set<u32>` pays dozens of bytes and a hash per element. For the numbers zero through `n`, one bit per element gives one machine instruction per operation: bit `i` is on exactly when `i` is a member. This is not general purpose; the universe must be a fixed dense range, and within it nothing beats it.

The approach. Coral's `std::collections::bitset` provides exactly this. Build a sieve, the canonical dense-membership problem, then use the richer operations.

The implementation.

    import(lib) std::collections::bitset { Bitset };

    pub void bitsetTour(u64 limit) {
        // one bit per number
        Bitset composite = Bitset::new(limit + 1);

        // mark composites: the sieve of 31.2, but one bit per number
        for (u64 p = 2; p <= limit / p; p += 1) {
            // p was already marked composite
            if (composite.test(p)) continue;
            // mark the multiples of p
            for (u64 m = p * p; m <= limit; m += p) composite.set(m);
        }

        u64 primes = composite.countZeros() - 1;   // zero is not prime
        println("primes below {}: {}", limit, primes);

        // set operations are word-at-a-time
        // a second bitset for even numbers
        Bitset evens = Bitset::new(limit + 1);
        for (u64 i = 0; i <= limit; i += 2) evens.set(i);
        Bitset evenComposites = Bitset::new(limit + 1);
        evenComposites.or(&composite);             // union with the composites
        evenComposites.and(&evens);                // intersect with the evens
        println("even composites: {}", evenComposites.countOnes());
    }

Cost and notes. `set`, `clear`, `toggle`, and `test` are O(1): a divide, a shift, one instruction. Whole-set `and`, `or`, `xor`, and `not` are O(n/64), one operation per word. `countOnes` and `countZeros` use `x & (x - 1)` per word. Memory is `n/8` bytes plus a header.

Edge cases. `Bitset::new(n)` covers bits zero through `n - 1`, and every indexed operation asserts the range, so an out-of-bounds bit is a loud diagnostic. The constructor rounds up to whole 64-bit words, and `_maskPadding` keeps the padding clear; use the whole-set operations rather than poking words. `and`, `or`, and `xor` require equal declared bit counts.

Variation. Implement a Bloom filter: a bitset plus `k` hash functions, insertion setting `k` bits and membership testing them all. It has false positives, no false negatives, and is why bitsets are used to avoid costly lookups.

32.7 The XOR Swap, and the Bug in the Cleverest Trick

The problem. Swap two integers with three XORs and no temporary. It is famous, and it has a bug that bites when both operands are the same place.

The intuition. XOR undoes itself: replace `a` with `a ^ b`, then `b` with `b ^ (a ^ b)` (the original `a`), then `a` with `(a ^ b) ^ a` (the original `b`). Correct for distinct storage. If the caller passes the same pointer, `*a` becomes `*a ^ *a`, which is zero, and every later line operates on zero. A temporary swap is idempotent when the locations coincide; the XOR version is not.

The approach. Show the trick, show the guard, and show why you would almost never use it: the temporary swap is as fast on modern machines and has no aliasing hazard.

The implementation.

    import(lib) std::io::ios { println };

    pub void swapTemp(i32* a, i32* b) {
        // classic swap through a temporary
        i32 t = *a;
        *a = *b;
        *b = t;
    }

    pub void xorSwap(i32* a, i32* b) {
        if (a == b) return;      // the guard that makes it correct
        // three XORs exchange the values
        *a ^= *b;
        *b ^= *a;
        *a ^= *b;
    }

    pub void demo() {
        i32 x = 3;
        i32 y = 5;
        xorSwap(&x, &y);
        println("{} {}", x, y);      // 5 3

        i32 z = 7;
        xorSwap(&z, &z);             // same location
        println("{}", z);            // 7, because of the guard
    }

Cost and notes. The XOR swap avoided a load and a store on 1970s machines. Today the temporary version optimises to the same or better instructions, and the XOR version's dependency chain is no win. Write the temporary version; teach the XOR version for what it reveals about XOR and pointers.

Edge cases. The guard must compare pointers, not values: two variables holding the same number must still swap. The locations must be distinct storage of the same type. On a signed type the intermediate values can be negative and have no arithmetic meaning; the trick is about bits, not numbers.

Variation. Write a generic temporary swap for `T`, noting that XOR swapping cannot be generic because not every type has bitwise operations. Then reverse an array with the temporary form; `reverse` in the standard library is exactly that loop.

32.8 Gray Code

The problem. Enumerate values so consecutive values differ in exactly one bit. Gray code is used in rotary encoders, error-correcting codes, Karnaugh maps, and bit-reflection stages of fast transforms.

The intuition. Binary three (`011`) to four (`100`) changes three bits at once, and a sensor reading mid-transition can be wildly wrong. Gray code orders values so each step flips one bit. The rule: `n XOR (n >> 1)`. Decoding folds the value with itself shifted down until zero.

The approach. The two conversions, plus a demonstration that consecutive Gray values differ by one bit, verified with the tools from 32.3.

The implementation.

    pub u64 grayEncode(u64 n) {
        // Gray = binary XOR half-shifted binary
        return n ^ (n >> 1);
    }

    pub u64 grayDecode(u64 g) {
        // recovered binary value
        u64 n = 0;
        // fold the Gray bits back
        while (g != 0) {
            // accumulate the running XOR
            n ^= g;
            // move to the next bit
            g >>= 1;
        }
        return n;
    }

    pub bool adjacentDifferByOneBit(u64 a, u64 b) {
        // bits where the two values differ
        u64 diff = a ^ b;
        // exactly one bit differs
        return diff != 0 && (diff & (diff - 1)) == 0;
    }

    pub void tour() {
        // start at zero
        u64 previous = grayEncode(0);
        for (u64 n = 1; n < 8; n += 1) {
            u64 g = grayEncode(n);
            println("{:b} -> {:b}  one bit: {}",
                    previous, g, adjacentDifferByOneBit(previous, g));
            previous = g;
        }
    }

Cost and notes. `grayEncode` is one shift and one XOR. `grayDecode` is one XOR per bit, O(log n). The difference test is the power-of-two check from 32.4 applied to the XOR: two values differ in one bit exactly when their XOR is a power of two.

Edge cases. The conversions are exact inverses for every `u64`, including zero. The difference test must reject `diff == 0`, since zero is not a power of two. The decoder terminates in at most the type width.

Variation. Generate the sequence by the reflected construction: start with `[0]`, copy the list in reverse, set the new high bit on each copy, and append. Seeing both makes the name clear.

32.9 The Single Number (XOR)

The problem. Every value in an array appears twice except one, which appears once. Find the loner without a set, a sort, or memory proportional to the input.

The intuition. XOR with itself is zero, XOR with zero is itself, and XOR is commutative and associative. XOR the whole array and every pair annihilates, leaving the singleton. The operation is the bookkeeping.

The approach. Fold the array with XOR: one accumulator, one pass, constant memory.

The implementation.

    import(lib) std::vec { Vec };

    pub u64 singleNumber(const Vec<u64>* xs) {
        // identity for XOR
        u64 acc = 0;
        // pairs cancel, leaving the singleton
        for (usize i = 0; i < xs->count(); i += 1) acc ^= xs->at(i);
        return acc;
    }

    // every value appears three times except one, which appears once:
    // track bits seen once and bits seen twice; a third sighting clears both
    pub u64 singleNumberTriple(const Vec<u64>* xs) {
        // bits seen 1 (mod 3) times
        u64 ones = 0;
        // bits seen 2 (mod 3) times
        u64 twos = 0;
        for (usize i = 0; i < xs->count(); i += 1) {
            u64 x = xs->at(i);
            ones = (ones ^ x) & ~twos;      // add x to the once-seen bits
            twos = (twos ^ x) & ~ones;      // add x to the twice-seen bits
        }
        return ones;
    }

In the three-times version, `ones` holds bits seen one more time than a multiple of three and `twos` bits seen twice, with the masks moving a bit between them on each sighting. The first function shows XOR as a parity machine: everything cancels except one.

Cost and notes. `singleNumber` is O(n) time and O(1) space, one register XOR per step. A hash set is also O(n) time but O(n) space and a hash per element.

Edge cases. An empty array returns zero, the identity but not a real answer; the caller guarantees a singleton exists. More than one singleton yields the XOR of all of them. The function is defined on unsigned values; XOR is a bit operation.

Variation. Find two singletons: XOR everything to get `a ^ b`, isolate a set bit, partition the array by that bit, and run the same function on each part. Two passes, constant memory.

32.10 Enumerating Subsets with a Bitmask

The problem. Given `n` items, visit all `2^n` subsets for a brute-force search, knapsack, subset-sum, or any problem small enough to try every option.

The intuition. A subset is a bitmask of `n` bits, so the subsets are the numbers zero through `2^n - 1`, each once. Membership is a shift and an AND, and peeling with `x & (x - 1)` walks only the members.

The approach. Loop the mask from zero to `2^n - 1` and walk its `n` bits, wrapped in a small brute-force maximum.

The implementation.

    import(lib) std::vec { Vec };

    pub u64 subsetSum(const Vec<u64>* items, u32 n, u64 mask) {
        // sum of the items selected by mask
        u64 sum = 0;
        for (u32 i = 0; i < n; i += 1)
            // include item i when bit i is set
            if (((mask >> i) & 1u) != 0) sum += items->at((usize)i);
        return sum;
    }

    pub u64 bestSubsetSum(const Vec<u64>* items, u32 n) {
        @assertOut(n <= 32u, "2^n enumeration needs a small n");
        // empty subset scores zero
        u64 best = 0;
        // 2^n masks in total
        u64 total = 1 << n;
        // every subset exactly once
        for (u64 mask = 0; mask < total; mask += 1) {
            u64 s = subsetSum(items, n, mask);
            // keep the largest sum so far
            if (s > best) best = s;
        }
        return best;
    }

Mask zero is the empty subset, summing to zero, so `best` starts there rather than at a negative sentinel. The mask counts in ordinary binary, and the bit pattern is the subset.

Cost and notes. `bestSubsetSum` is O(2^n * n): the outer loop doubles with `n`, and each mask costs a walk over `n` bits. About twenty is fine; thirty is a billion. The `n <= 32` assertion keeps `1 << n` inside the `u64`, but time sets the real limit.

Edge cases. `n` must not exceed the word width; the assertion refuses it. The vector must hold at least `n` elements. The mask is `u64` while the index is `u32`, and `& 1u` against a `u64` is the pattern from 32.2. Early exit when `best` reaches the sum of all items saves nothing for a maximum but matters for a threshold predicate.

Variation. Replace the per-mask walk with the set-bit peel from 32.3: `u64 bits = mask; while (bits != 0) { u32 i = lowBitIndex(bits); sum += items->at((usize)i); bits &= bits - 1; }`. It visits only members, a real saving for sparse masks.

32.11 Reversing the Bits of a Word

The problem. Reverse the bits of a word: bit 0 becomes bit 31, and so on. It underlies bit-reversal permutations in fast Fourier transforms, some hashing and scrambling schemes, and CRC variants.

The intuition. Work in stages like sorting a deck: swap adjacent bits, then pairs, nibbles, bytes, and finally halves. Each stage moves every bit twice as far, and after the half swap the word is reversed. Every stage is a mask, a shift, and an OR.

The approach. The five-stage masked version for `u32`, a bit-by-bit loop for comparison, and a `u64` built from two `u32` reversals.

The implementation.

    pub u32 reverseBits32(u32 x) {
        x = ((x & 0x55555555u) << 1) | ((x >> 1) & 0x55555555u);   // swap adjacent bits
        x = ((x & 0x33333333u) << 2) | ((x >> 2) & 0x33333333u);   // swap pairs
        x = ((x & 0x0F0F0F0Fu) << 4) | ((x >> 4) & 0x0F0F0F0Fu);   // swap nibbles
        x = ((x & 0x00FF00FFu) << 8) | ((x >> 8) & 0x00FF00FFu);   // swap bytes
        x = (x << 16) | (x >> 16);                                  // swap halves
        return x;
    }

    pub u32 reverseBitsLoop(u32 x) {
        // build the reversal one bit at a time
        u32 result = 0;
        for (u32 i = 0; i < 32u; i += 1) {
            // shift in the current low bit
            result = (result << 1) | (x & 1u);
            // drop the bit just consumed
            x >>= 1;
        }
        return result;
    }

    pub u64 reverseBits64(u64 x) {
        // reverse each half...
        u64 low = (u64)reverseBits32((u32)x);
        u64 high = (u64)reverseBits32((u32)(x >> 32));
        // ...then swap the halves
        return (low << 32) | high;
    }

Read the masks as pairs. `0x55555555` selects the low bit of every pair; shifting and ORing swaps each pair. `0x33333333` selects the low two bits of every four, doubling the distance. `0x0F0F0F0F` handles nibbles, `0x00FF00FF` bytes, and the last line swaps the sixteen-bit halves. The `u64` version reverses each half and places them low-then-high.

Cost and notes. `reverseBits32` is five stages, no loop, constant time, roughly twenty instructions. `reverseBitsLoop` is O(width) and shows the masked version unrolled. `reverseBits64` is two calls and a swap.

Edge cases. Every shift is below the width, so nothing is undefined. The `u` suffix keeps the masks unsigned; a signed top mask would be a mistake. The loop shifts `result` left each step, so after thirty-two steps the first bit read is last. The `u64` composition needs a true 32-bit reversal.

Variation. Reverse four bytes at once with a 256-entry table of reversed bytes, then reorder the bytes: `table[(u8)x] << 24 | table[(u8)(x>>8)] << 16 | ...`. It pays when reversing millions of words.

32.12 Addition Without +, Using Bits

The problem. Add two integers using only bitwise operations and shifts, making the ripple-carry adder inside every CPU visible.

The intuition. Addition is XOR for the sum and AND for the carry. XOR the operands for the sum without carries, AND and shift left one for the carries, then add those, repeating until no carry remains. The carry walks up the word and stops.

The approach. Replace `(a, b)` with `(a ^ b, (a & b) << 1)` until `b` is zero.

The implementation.

    pub u32 addBits(u32 a, u32 b) {
        // loop while a carry remains
        while (b != 0) {
            // carry where both bits are one
            u32 carry = a & b;
            a = a ^ b;             // sum of the bits with no carry
            b = carry << 1;        // the carries move up one position
        }
        return a;
    }

    pub u32 subtractBits(u32 a, u32 b) {
        return addBits(a, addBits(~b, 1u));   // a + (-b), two's complement
    }

Subtraction is the two's-complement negation `-b = ~b + 1` fed back into the adder; a CPU has one adder and derives subtraction exactly this way.

Cost and notes. The loop runs once per carry propagation, worst case the word width: adding `0xFFFFFFFF` to `1` walks the carry across, O(width) iterations. Hardware uses a parallel carry-lookahead circuit, but this serial version is the honest model.

Edge cases. The carry out of the top bit is discarded, matching machine wraparound, so `addBits(0xFFFFFFFF, 1)` is zero. The loop terminates within the width because the lowest set bit of `b` moves higher each iteration. The version is for unsigned types; signed bits are identical but the arithmetic interpretation is two's complement. `subtractBits` needs a full-width `~b`.

Variation. Write `multiplyBits(a, b)` as repeated shift-and-add: for each set bit of `b`, shift `a` left and feed it into `addBits`. Then check `subtractBits` against `a - b` over a range.

32.13 Nim: The Game of XOR

The problem. Nim has several piles of stones. On your turn remove any positive number from one pile; whoever takes the last stone wins. Decide whether the first player can force a win and which move to make. It is the cleanest game whose solution is one XOR.

The intuition. The nim-sum is the XOR of all pile sizes. A position is losing exactly when the nim-sum is zero. From zero, any move makes it nonzero. From nonzero, reduce a pile larger than its size XORed with the nim-sum to that value, restoring zero. So every nonzero position hands a zero position to the opponent, and the player who can always do that wins.

The approach. XOR the pile sizes, then find the pile that can be reduced to restore a zero nim-sum.

The implementation.

    import(lib) std::vec { Vec };

    pub bool nimWins(const Vec<u64>* piles) {
        // XOR of all pile sizes
        u64 nimSum = 0;
        for (usize i = 0; i < piles->count(); i += 1) nimSum ^= piles->at(i);
        // losing exactly when the nim-sum is zero
        return nimSum != 0;
    }

    pub i32 nimWinningMove(const Vec<u64>* piles) {
        u64 nimSum = 0;
        for (usize i = 0; i < piles->count(); i += 1) nimSum ^= piles->at(i);
        if (nimSum == 0) return -1;               // losing; there is no winning move
        for (usize i = 0; i < piles->count(); i += 1) {
            u64 target = piles->at(i) ^ nimSum;   // the size that zeroes the nim-sum
            // legal only if it actually reduces the pile
            if (target < piles->at(i)) return (i32)i;
        }
        return -1;                                // unreachable for a nonzero nim-sum
    }

Check the move rule: leaving pile `i` at `target` makes the new nim-sum `nimSum ^ pile_i ^ target`, which is zero when `target = pile_i ^ nimSum`. Requiring `target < pile_i` guarantees a legal reduction, and a nonzero nim-sum always has one such pile.

Cost and notes. Both functions are O(n) with constant extra space: one XOR fold, plus one pass to find the move. A game that minimax would explore exponentially is decided by one pass over the piles.

Edge cases. No piles is a loss, and the nim-sum of nothing is zero, which agrees. A zero pile can never be the winning move. `nimWinningMove` returns `-1` for both a loss and the impossible no-pile case; production code would use `Option<usize>` and reserve `None` for the genuine loss. The `i32` cast is safe for any realistic pile count.

Variation. Solve misere Nim, where taking the last stone loses. The strategy is identical except when every pile has size one: then the position is a win iff the number of piles is even. Test both on `(1, 1)`, `(1, 1, 1)`, and `(1, 2, 3)`.
