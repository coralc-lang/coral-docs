Chapter9: The Type System

9.1 Where Rigor Lives

Coral's rigor lives in its types: a typechecked program has its mistakes found before it runs. This chapter covers the types Coral has, how the compiler checks them, and the boundaries around what it will and will not infer.

Coral is statically typed, the types are explicit, and the compiler checks every program before it runs. There is no runtime type dynamism, no runtime type tags, no reflection, and no runtime type errors.

A dynamic language checks types as the program runs, so failures land on the user's machine. Coral decides a variable's type once, at the declaration, and verifies every use before the program runs. C is statically typed too, but `void*` and implicit conversions let types slip past the compiler; Coral closes both doors.

Take a function that computes a monthly average and a caller who passes the year-to-date total by mistake. In an untyped language the average is silently wrong; in a typed one the compiler stops the build where the types meet. The type is the program's description of a value, and the compiler checks every line against it.

9.2 Type Declarations

A type is declared as a named statement in the module: `struct`, `variant`, `union`, `enum`, `trait`, `typedef`, and `distinct`. Each names a type and states what it is, and the compiler collects them before checking code.

The `struct` is the product type holding several fields. `variant` and `union` are sum forms: a `variant` is a tagged union whose alternatives carry fields plus a tag, while a `union` is an untagged overlay sharing storage. The `enum` is a sum of named alternatives with no payload. A `trait` names methods a type may implement; `typedef` names an existing type; `distinct` builds a new type from an existing one.

Declarations are type-first: keyword, name, then body or definition. The compiler records the type, and the name means the type from then on. The standard library uses these keywords throughout: `struct` for collections, `variant` for result and option types, `distinct` for platform handles, `enum` for log levels and error kinds, `typedef` for named function signatures.

9.3 Primitive Types

The primitive types are the fixed-width integers, the floating-point types, the boolean, and the character. Every other type is built from them.

The signed integers are `i8`, `i16`, `i32`, and `i64`; the unsigned are `u8`, `u16`, `u32`, and `u64`. Each has a fixed width and range, and signed types use two's complement, so an `i8` holds -128 through 127 and a `u8` holds 0 through 255. An `i32` is thirty-two bits on every platform.

Think of each fixed-width type as a container of a set size. A `u8` holds 0 through 255; pour in one more and the value wraps to zero. The type's size is a budget you choose.

Where C says `int`, Coral says `i32`, exactly thirty-two bits on every compiler and machine. C's `int` is a moving target. In JavaScript every number is a double until something overflows, while Coral's fixed width enforces the decision you made. The standard library uses `usize` for element counts and `i64` for nanosecond counts that might go negative.

The floating-point types are `f32` and `f64`, single and double precision IEEE 754. `bool` holds `true` or `false`, with no truthiness: an `if` requires a `bool`, so `if (x = 5)` does not compile. `char` is a 32-bit Unicode code point, `u8` is one byte of UTF-8 text, and `void` is the absence of a value.

The compiler knows each primitive's size, range, alignment, and behavior, and the `limits` module spells out the limits as constants. The type's name is its width, and its width is its range.

A `u8` holds 0 through 255, so a counter for temperatures, byte counts, or buffer offsets that can exceed 255 must use a wider type. The standard library uses `u64` for counts because the budget is roomy enough that width never becomes the bug. The width you choose is the risk you accept.

A dynamic number grows until it cannot; a typed number is fixed at declaration. A line counter declared `u64` is safe for any file; declared `u8`, it breaks silently at line 256. The width in the name tells the reader how far the value may go, and the compiler checks arithmetic that would go further.

9.4 Type Inference

Coral is explicit about types but infers where explicitness buys nothing, through the `var` declaration and type parameters.

`var` infers a variable's type from its initializer. Ranged `for` loops use `var` for the loop variable:

    for (var arg : args) _fprintOne(1, arg);

`arg` is typed by the argument pack, and the compiler knows its type before checking the loop body.

Coral has no Hindley-Milner or global type inference. Inference is local and declaration-directed: the type is stated, or inferred from a stated expression, and the compiler never guesses across a program. A type the compiler guesses is a type the reader does not see.

Explicit where it matters, inferred where the initializer decides:

    var count = 42u;          // unsigned, from the literal. it can hold up to u64, unless the compiler proves that never uses that much space
    var ratio = 3.14;         // f64, from the literal
    var total = a + b;        // the type of a + b, which is the operand type
    var item = lookup(key);   // the return type of lookup

Each `var` names its type through its initializer, so a reader can retype it from the line alone. Inference is a convenience for writing the obvious type, which is always right there in the text.

`var` does not mean the type can change later. `var count = 42u;` fixes `count` to that unsigned type for its whole life; a later `count = "hello";` is a type error.

9.5 Generic Types

A generic type takes other types as parameters.

Without generics, a vector of u64s, a vector of string views, and a vector of dates would each need a separate struct, or one void-pointer version that gives up type checking. Neither is acceptable.

A generic is the third option: write the structure once with a placeholder for the element type, and let the compiler stamp out a concrete version for each use. By convention the first parameter is T and the second U.

Picture a cookie cutter shaped like a vector with a hole for the element type. Pressing it into `u32` gives `Vec<u32>`; pressing it into `str` gives `Vec<str>`. One cutter, many complete types.

Three real recipes from the standard library (`Vec` from `collections/vec.crl`, `Pair` from `collections/iter.crl`, `Arr` from `collections/arr.crl`), with one field elided:

    pub struct Vec<T>
    {
        T* data;
        usize len;
        usize cap;

        ...
    }

    pub struct Pair<T, U>
    {
        T first;
        U second;
    }

    pub struct Arr<T, N>
    {
        T data[N];

        ...
    }

Read them field by field.

`Vec` takes one parameter, the element type. `T* data` becomes `u32* data` for `Vec<u32>`, the length and capacity stay `usize`, and every method mentioning T follows the same substitution.

`Pair` takes two parameters, one per field. `Pair<str, u64>` fills both.

`Arr` takes two different kinds of parameters: T is a type, and N is a compile-time count. `Arr<u8, 64>` is sixty-four bytes, and `Arr<u8, 64>` and `Arr<u8, 128>` are different types with different sizes.

A generic becomes a real type at the use: `Vec<u32>`, `Map<str, i64>`, `Arr<u8, 64>`. Each instantiation is a complete, ordinary type, as fast as a hand-written struct.

Instantiation happens at compile time, so arguments must be compile-time values. `Arr<u8, someVariable>` fails because the compiler cannot know `someVariable` while building.

Generics compose. A vector of maps is `Vec<Map<str, u64>>`, a map of vectors is `Map<str, Vec<f64>>`, and a pair of containers is `Pair<Vec<u8>, Vec<u8>>`. Read nested generics from the inside out.

    Vec<Pair<str, JsonValue>> fields;   // a JSON object's list of name-value pairs

`JsonValue` is the element, `Pair` adds its string key, and `Vec` makes the list. The type states a JSON object's structure in one line, and a mismatch at any layer is an error at that layer.

Each instantiation is its own type: `Vec<u64>` is not interchangeable with `Vec<str>`, and a function taking one will not accept the other. A void-pointer design would absorb that confusion at runtime; here it is a compile error.

This stops a vector of the wrong element type from reaching a function written for another: a runtime corruption in a void-pointer design becomes a compile error naming both types.

`Option<T>` is a recipe for a T or nothing, `Result<T, E>` for a T or an E, and `Map<K, V>` for key-value storage. Each is a struct with type parameters, instantiated, checked, and compiled the same way.

9.6 Monomorphization

Generic types and functions are compiled by monomorphization: each use with concrete arguments produces a concrete instance. `Vec<u32>` and `Vec<f64>` are two different compiled types generated from one `Vec` definition.

For `Vec<u32>`, the compiler copies the definition with every `T` replaced by `u32`: `T* data` becomes `u32* data`, `push` takes a `u32`, and `pop` returns one. The copy is an ordinary struct with no hidden type, no runtime tag, and no element table. `Vec<f64>` runs the substitution again.

The compiler checks each instance against its arguments. A use with incompatible arguments fails at the use, on the line that named it. `Vec<str>` is checked for copying, comparison, and storage with `str` in place of T before the program continues.

Each instance is a concrete type the compiler optimizes like any other. A `Vec<u32>`'s push is a `u32` push: a move and a length increment, with no indirection or table lookup. Generality in the source, specialization in the binary.

The cost is code size: each instance is real code. A program using `Vec` with four element types carries four copies of the vec machinery. The library accepts that trade because the alternative, one generic body consulting runtime type information, is slower, and most programs use a handful of instances.

The compiler may share an instance when the arguments are the same, so two functions using `Vec<u32>` compile to the same instance. The sharing is invisible and keeps many generic uses from growing without bound.

9.7 Variance

Variance describes how a generic type relates to its arguments as the arguments relate to each other. Coral's generics are invariant, and the language has no subtyping.

Variance needs subtyping. Coral has none: an `i32` is not a subtype of `i64`, a struct is not a subtype of another struct, and there is no inheritance hierarchy. A type is exactly what it is.

So generics are invariant: `Vec<i32>` is not interchangeable with `Vec<i64>`, because there is no parent type. A function taking `Vec<i32>` receives exactly that, with no covariance to reason about. Unlike Java or C#, you cannot pass a `List<Circle>` where a `List<Shape>` is expected, which prevents putting a `Square` into a list of shapes and later finding a `Circle`.

Use-site and declaration-site variance both need a subtype relationship. Coral has neither and needs neither, because its types are exact.

9.8 Where Requirements Are Checked

A `Vec<T>` works with any type because it only stores and copies. A generic function that calls `area` or compares values needs its parameter to support those operations.

Most languages write a bound such as `T : Comparable`. Coral does not spell bounds: the requirement is a property of the body, checked at each instantiation.

Take a function that finds the largest area by calling `area()` on every element. Coral accepts the definition and defers the check. Instantiated for `Circle`, the compiler confirms `Circle` has `area`; instantiated for a type without it, the compiler refuses, naming the type and the missing operation at the point of use.

The bound is the set of operations the body performs. The benefit is no bound grammar and a requirement exactly as wide as the code. The cost is that the requirement is invisible from the signature, so a well-written generic documents it in a comment.

To make a requirement visible in the signature, pass the capability by value: the library sorts by taking `bool less(T, T)` rather than requiring a `Sortable` trait. A trait object (`any Shape`) is the other way to put a capability into a type. Both make the requirement explicit without a `T : Trait` clause.

Coral checks what the body uses. If it calls `area()`, that is the requirement, verified when the generic is used with a concrete type.

9.9 Type Aliases

A type alias names an existing type. The `typedef` declaration gives a type an alternative spelling.

    pub typedef SigHandler = void(i32);

`SigHandler` names a function taking an `i32` and returning nothing, and the two names mean the same type. The library uses `typedef`s to name function types used as parameters and fields.

A `typedef` introduces no new type: a `SigHandler` and a `void(i32)` are interchangeable. It exists for readability and for writing a complex type once. Nothing is protected, unlike the next section's `distinct`.

The library's generic pointer handle appears throughout the language's conventions. A helper module wraps a raw pointer in a one-field struct:


    pub struct Any
    {
        rawptr p;

        rawptr ptr()
        {
            return p;
        }

        bool isNull()
        {
            return p == null;
        }

        T* as<T>()
        {
            return (T*)p;
        }
    }

    pub Any wrap(rawptr value)
    {
        Any a;
        a.p = value;
        return a;
    }

The struct gives the pointer a name and a home for its operations. `wrap` builds an `Any` from a `rawptr`; `ptr` reads it back; `isNull` tests it; `as<T>` returns it as `T*`. Because `Any` is its own type, nothing converts implicitly: a `rawptr` becomes an `Any` only through `wrap`, and an `Any` becomes a typed pointer only through `as<T>` or `ptr`. It carries no provenance, bounds, or type tag, but it has a surface for the handle's operations, unlike a `typedef`.

9.10 Distinct Types

A distinct type creates a new type from an existing one. It is not interchangeable with its base type even though the two share a representation.

The standard library is full of them:

    pub distinct File = i32;         // io/fs.crl
    pub distinct Dir = void*;        // io/fs.crl
    pub distinct TcpSocket = i32;    // io/net.crl
    pub distinct Thread = void*;     // concurrent/thread.crl

A `File` is an `i32` under the hood but not an `i32` in the type system, and the same is true of `TcpSocket`. A file descriptor, a TCP socket, a process id, and a raw error integer can all be the same number, and distinct types make the distinction real. A function taking a `File` accepts neither a raw `i32` nor a `TcpSocket`.

A distinct type is the newtype of other languages. Unlike a one-field `struct`, whose fields you reach through `.field`, a `distinct` keeps the base type's operations: you can compare two `File`s and cast one to the platform's `i32`.

A distinct type has its base type's representation, size, and layout, so it crosses the FFI boundary for free and costs nothing at runtime. The library uses distinct wrappers around platform handles and casts to the base when the OS needs an int.

The classic example is two prices that look identical, dollars and euros, both `u64` cents. As plain u64s, nothing stops you from adding one to the other; as distinct types, the confusion is impossible:

    pub distinct USD = u64;   // cents
    pub distinct EUR = u64;   // cents

    USD subtotal = USD(3499);
    EUR vat = EUR(700);
    EUR total = subtotal + vat;   // error: USD is not EUR

The compiler rejects the addition: the values have the same bits, size, and speed but different types. The cost is saying which is which at every boundary; the benefit is never mixing currencies.

A `distinct` type is a sticky label. Under the label, `USD` is just a `u64` and costs nothing extra at runtime, but the compiler refuses to mix values whose labels disagree.

At the FFI boundary, the library casts the handle to its base:

    File cfg = openConfig();
    i32 raw = (i32)cfg;      // the distinct File, reduced to its base at the FFI boundary
    libc.close(raw);

Inside the program the handle is a `File`; at the platform's edge it becomes the `i32` the platform wants, and the conversion is written in the code. Nothing converts on its own, so the type stays distinct until the line that says otherwise.

A `typedef` gives a complex type a shorter name and protects nothing. A `distinct` gives a new name a new identity and enforces it: a `USD` is not a `EUR`, even though both are u64s. The library uses `typedef` where a name is all that is needed and `distinct` where mixing must be impossible.

Ask one question: must the two values be impossible to confuse? If yes, use `distinct`; if you only want a shorter spelling, use `typedef`. Overusing `distinct` adds casts for safety you did not need; using `typedef` where safety was needed leaves the confusion you meant to prevent.

9.11 Opaque Types

An opaque type hides its implementation. The user sees the type's name and operations, never its internals.

In Coral the pattern is a struct whose fields are a fixed block of storage. `Regex` is the canonical example, from `text/regex.crl`:

    pub struct Regex
    {
        rawptr impl[8];
        bool compiled;
        usize groupCount;
        u8* findBuf;
        usize findBufCap;
    }

The regex holds eight void pointers and a handful of working fields: an opaque handle to the compiled pattern, a compiled flag, the capture-group count, and a find buffer. The methods interpret that storage; the user calls `compile`, `matches`, and `find` and never touches the fields.

An opaque type is the boundary between a library and its clients. Because the details are hidden, the library can change them without changing the type or the client's code. For the C programmer, `rawptr impl[8]` is the classic handle pattern behind `FILE*`, except Coral makes the handle a type you can name, size, and store by value.

9.12 The Sum Type: Enums

The enum is the sum type: a value is exactly one of a named set of alternatives.

A real enum from `io/log.crl`:

    pub enum LogLevel
    {
        Debug,
        Info,
        Warn,
        Error,
        Fatal
    }

A `LogLevel` value is exactly one of the five levels. The enum removes the strings a dynamic program would check, and with them the typos: the alternatives are written once, the compiler knows them all, and a value cannot be anything else.

An enum is a list of the only allowed values, written once and given a name. You write `TrafficLight::Green`, and the compiler checks the spelling.

A `variant` is the same idea with payloads: each alternative carries its own fields, so a value is a tag plus data. The variants chapter develops them fully; here the enum stands in as the representative sum type.

The enum is exhaustive: a value is always one of its alternatives, which makes exhaustive checking possible. A `switch` over an enum is checked against every variant, and adding a sixth level flags every switch that handled the old five.

    if (level == LogLevel.Error) { ... }

Variants are compared with equality, and the compiler checks those comparisons. An enum value cannot be a variant that is not in the type.

A protocol handler that says whether it is reading text, JSON, or raw bytes shows why the enum deserves a type. With strings, the kind could be `"json"`, `"Json"`, a typo, or anything else; with an enum, the alternatives exist once and comparisons are checked:

    pub enum ProtocolKind
    {
        Text,
        Json,
        Binary
    }

    void handle(ProtocolKind kind)
    {
        if (kind == ProtocolKind.Json) { /* one parser */ }
        else if (kind == ProtocolKind.Binary) { /* another */ }
        // Text needs no special branch: both others were visited
    }

A value is one of the three, and the typos and invented formats do not exist because the type does not contain them. Adding a fourth format turns every site that handles kinds into a compile-time question again.

9.13 The Product Type: Structs

The struct is the product type: a value holds several named fields together. It is the shape of the language's data.

The `Timespec` from the time module:

    pub struct Timespec
    {
        i64 sec;
        i64 nsec;
    }

`Timespec` is the product of a second and a nanosecond. The product composes: a field can be a struct, a vector, an option, a result, or an enum. `JsonValue` composes a type tag with fields for each kind of value, exactly one of which is meaningful for the tag.

The fields are named, and the names carry the meaning. `ts.sec` and `ts.nsec` tell a reader which is which; `ts[0]` and `ts[1]` would force everyone to guess.

Names are the cheapest documentation a type can carry. A reader who sees `ts.sec` never has to remember whether seconds come first.

9.14 Null Safety

Coral's null safety is the option type from the error handling chapter.

A pointer can be null, and its type does not say whether it is. A `T*` may point at a `T` or be null. This is the C model, kept because pointers are the raw memory interface, and the raw interface cannot promise non-null.

When absence should be checked, use `Option<T>`: either `Some`, carrying a `T`, or `None`, carrying nothing, and the caller must handle both. A map lookup returns an option. An `Option<u64>` says plainly that it holds a number or nothing, and it is a value, not a pointer. The pointer demands the same reasoning, but the option spells it in the type and the compiler enforces it.

An `Option` is a box that is either holding a value or visibly empty. A nullable pointer is a claim that something is at an address, and the claim can be wrong with no warning in the type.

A phone directory shows the everyday shape:

    Option<u64> findNumber(str name);

    Option<u64> hit = findNumber("ada");
    if (hit.isSome())
        println("found: {}", hit.unwrap());
    else
        println("no such entry");

The function returns no sentinel, no 0, no null, and no -1. It returns a value whose type says a number or nothing, and the `if` decides what each answer means. C's alternatives, a return code plus an out-parameter, a special value, or a null pointer, are conventions the next programmer must learn. The option writes the convention in the type, and a caller that forgets to look inside is refused.

Coral has no non-null assertion operator and no safe navigation operator. Operations are explicit methods: `unwrap` asserts, and `unwrapOr` supplies a default.

9.15 What Coral Does Not Have

Several advanced types are absent by design.

No higher-kinded types: a Coral generic is parameterized by types and compile-time values, not by type constructors. There are no functors or monads. A `Vec<u32>` is a concrete, checkable, optimizable thing.

No existential types: types are fully named, and a type's arguments are part of its name. No Coral type says it is a vec of something without saying what.

No phantom types, dependent types, or refinement types. A `u64` is a `u64`; there is no positive `u64` or even `u64`. A function that needs such a rule documents and checks it.

Every absence is the same absence: Coral's types are concrete, named, and checked, and the advanced abstractions belong to languages that reason about types abstractly. For a beginner this is a mercy; for a C programmer it is a familiar floor with safety added.

9.16 Implicit Conversions

Coral's matrix of implicit coercions is empty, and that is the design.

Coral does not inherit C's implicit conversion rules. Every conversion between distinct types is an explicit cast: a `u32` to `u64` before a shift, a `char` to `u8` and then `i32` for a memory fill, seconds to `f64` before adding nanoseconds. The casts are everywhere because there are no implicit conversions to rely on. C's silent short-to-int wrap or integer division truncation is a cost Coral declines to charge.

A `u8` does not convert to a `u16`, a `u32` does not convert to a `u64`, an `i32` does not convert to an `i64`, and an integer does not convert to a float. Widening and narrowing are both explicit. The compiler never shuffles a value's type behind your back.

The one implicit adaptation is the literal. An integer literal takes the type its context requires: a plain `0` is a `u64` where a `u64` is expected. Literals adapt; variables never do.

Because a literal adapts, `u64 big = 5;` compiles, but a stored `u32` does not widen:

    u32 small = 5;
    u64 big = small;      // error: u32 is not u64, write (u64)small

The literal `5` could be either type, so it takes what the context asks. The variable `small` already has a type, and the compiler will not change it for you.

The empty matrix is the type-first principle applied to conversion: every type change is written and checked.

9.17 Explicit Conversions

Every conversion is written explicitly, in one of two forms.

The C-style cast puts the type in parentheses before the expression:

    (u32)code
    (char)('A' + digit - 10)
    (const T*)self.data

The cast covers widening, narrowing, sign changes, float to integer, integer to pointer, pointer to integer, and pointer conversions. Each states its target type, and the compiler checks it for validity. The library writes `(i32)descriptor` when handing an OS call an integer and `(u64)hi` when changing a shift width.


9.18 Integer and Floating-Point Promotion

A Coral expression has no promotion step.

C's integer promotions do not exist. A `char` does not widen to an `int` before arithmetic, narrow types do not widen, and no usual arithmetic conversion brings two operands to a common type. A `u32` times a `u64` stays mixed unless the writer makes it uniform. Arithmetic stays in the type you declared, so overflow is your responsibility.

The library writes mixed-type arithmetic explicitly: it casts the high half to `u64` before shifting by `32u`, and casts seconds to `f64` before float arithmetic. An operation's operands have one type, and the writer states it.

The suffixed literal is the shorthand: a shift by `32u` writes the type into the literal, and a literal multiplied by two adapts to its context. Neither is a promotion.

An expression's type is the type of its operands, and the operands' types are written. No hidden widening, no silent common type, no surprising result type.

9.19 String Conversion

Coral's string conversions are the formatting functions and the view operations.

A value converts to text through the formatting functions. `fmt::formatUint(255, 16, false)` builds `"ff"`, `fmt::formatInt` handles signed forms, and `fmt::formatFloat` handles doubles. The pad and join functions shape the text. Each conversion is an explicit call whose name states what it does.

Text converts to a view or a string through constructors. A string literal is a view, a C string is a view through `fromCstr`, and a buffer with a length is a view through `fromParts`. A view becomes a string through the string's `from` constructor, which copies the text. Value-to-text is a formatting call, text-to-value is a parsing call, and nothing happens by adjacency the way `"" + x` pretends.

The print functions convert their arguments to text and write them. The parsers convert text to values. Each conversion is a named function checked by the compiler.

A table of powers prints with the numbers right-aligned, every step an explicit call:

    for (u64 i = 1; i <= 10; i++)
    {
        u64 sq = i * i;
        print("{}  {}\n",
              fmt::padRight(fmt::formatUint(i, 10, false), 3, ' '),
              fmt::padRight(fmt::formatUint(sq, 10, false), 6, ' '));
    }

`fmt::formatUint` converts each number and says what it does in its name, and `fmt::padRight` shapes the columns. No concatenation operator pretends to turn a number into text. The conversion and the padding are visible in the same line where they happen.

9.20 Compile-Time Type Reasoning

A `comptime` block runs during compilation and can compare types.

    comptime
    {
        switch (@typeof(T))
        {
            i32 => { ... },
            f64 => { ... }
        }
    }

The pattern `i32` asks whether the type parameter is `i32`, and only the selected arm is compiled. This is how the generic print functions choose a formatter per argument type. Inside a generic function, `T` is a compile-time fact.

In miniature, the recognizer the print machinery uses:

    comptime
    {
        switch (@typeof(T))
        {
            u64 => { _printU64(val); return; },
            f64 => { _printF64(val); return; },
            str => { _printView(val); return; },
            else => { @compileError("print: unsupported type"); }
        }
    }

For a `u64` argument, the compiler evaluates the block with `T` known to be `u64`, takes the matching arm, and compiles exactly that call. The other branches vanish before the program exists. The decision is about the type, at build time.

`comptime` is not reflection: it does not run at runtime, and the compiled program contains only the selected code. No runtime type tag, no lookup, no value carrying its type.

9.21 Static and Dynamic, and the Boundary

Coral has no reflection, no runtime type checking, and no `typeof` or `instanceof`.

A running program cannot ask a value its type, enumerate fields, or invoke a method by name, because no type information survives to runtime. The hazards those operators pose do not exist because the operators do not exist. Coral's `x` already has one type, known at compile time.

Coral is statically typed with no dynamic typing aspects. The rigor is at compile time, the runtime is the compiled program, and the type system does not leak into it.

9.22 Protocol-Oriented Design

Coral's answer to duck typing and structural typing is protocol-oriented design: behavior is defined by protocols, and the type system checks them.

Duck typing checks behavior at runtime: if it quacks like a duck, it is a duck, and a string with no `area()` fails at the call. Coral has no duck typing because its checks happen at compile time and a value's behavior is established by its type.

Protocol-oriented design is the compile-time version. A protocol is a named set of rules, conformance is declared and checked, and a generic function over the trait calls the protocol's methods. The duck-ness is a declared fact, checked when the type is defined.

A storefront calls its payment providers through one door. The door is a trait, and each provider declares that it implements it:

    trait PaymentProvider
    {
        void charge(u64 cents);
    }

    struct PayPal { /* provider-specific state */ }

    extend PayPal : PaymentProvider
    {
        void charge(u64 cents) { /* one gateway's protocol */ }
    }

    struct Stripe { /* other state */ }

    extend Stripe : PaymentProvider
    {
        void charge(u64 cents) { /* the other gateway's protocol */ }
    }

The checkout function takes the protocol, not a provider:

    void checkout(any PaymentProvider provider, u64 cents)
    {
        provider.charge(cents);
    }

The duck-typed version would check that `charge` exists at every call, at runtime. Coral declares conformance once, and `checkout(paypal, 2500)` is checked at build time. A third provider without the trait, or a string, does not compile.

Structural typing, where a type qualifies by having the right shape without declaring it, is not Coral's model. Conformance is nominal: a type implements a trait because it has an implementation block, not because it happens to have the right methods. Two structs with a `name` field do not implement `Named` unless they say so.

9.23 What a Type Is

A type is an agreement between the program and the compiler: it says what operations exist, what memory a value occupies, and what it can become. The type promises what the value is, and the compiler promises that every use is checked.

A type is also a promise to the reader:

    Result<Config, ParseError> loadConfig(str path)   // and its call sites

The signature says the function takes text and produces a configuration or a parse error, so the reader sees the paths and outcomes without executing a line. The types say what the program means; the explanation says why. An `Option<u64>` return type says there may be no answer, and you must look.

The type is finally a promise the machine keeps. A `u64` is sixty-four bits, an `f64` is the IEEE double format, a pointer is an address, and a struct is its fields laid out in order. The type determines the representation, and the representation determines the cost.

9.24 The Type Checker at Work

The type checker walks the program, gives every expression a type, and verifies that every use matches.

A literal has its type, a variable its declared type, a call its return type, and an operator the type its operands produce. The checker verifies the seams: assignments, arguments, and operations. A mismatch is an error at the seam, reported with the code that caused it.

A mismatch caught:

    usize n = v.count();      // correct: usize from usize
    u64* p = v.count();       // error: usize is not u64*, and no conversion exists

The second line fails because a `u64` is not a pointer to `u64`, and there is no implicit conversion. The checker reports the mismatch where the types meet and names both types. In a dynamic language the line would run and crash, or corrupt memory, at the first `*p`; here it never ships.

The type checker is a proofreader: wherever two values meet, it asks whether they are the same type and never guesses what you meant.

The same seam catches the near miss, where both sides are close but not the same:

    u64 total = 0;
    u64* slot = &total;     // correct: u64* receives the address of a u64
    i32 count = 3;
    u64 c = count;          // error: i32 is not u64, and no implicit widening exists

C compilers wave the last line through with a warning, and a negative count becomes four billion. Coral refuses it, and the writer must write the cast, which states that the widening was intended.

Checking is total: every expression is typed, every seam is verified, and every function is checked against its signature before use. A program that compiles has been checked everywhere.

9.25 A Worked Example: Modeling With Types

Designing types is the first act of a Coral program. A small inventory tracks items with a name, a quantity, and a category, and the categories are fixed.

The categories are an enum:

    pub enum Category
    {
        Tool,
        Material,
        Consumable
    }

The item is a struct with the category as an enum field:

    pub struct Item
    {
        str name;
        u64 quantity;
        Category category;
    }

A lookup may find an item or nothing, so it returns an option, and restock chains through the option's methods:

    Option<Item> findItem(str name)
    {
        return Option<Item>::None;
    }

    void restock(str name, u64 amount)
    {
        Option<Item> found = findItem(name);
        if (found.isSome())
        {
            Item it = found.unwrap();
            it.quantity += amount;
            saveItem(it);
        }
        else
        {
            // the item has vanished; the caller is told, loudly
        }
    }

The category report shows the enum's payoff: the alternatives are the type's own values and the comparison is plain equality:

    u64 tools = 0;
    u64 materials = 0;
    u64 consumables = 0;
    for (u64 i = 0; i < items.count(); i++)
    {
        Item it = items.at(i);
        if (it.category == Category::Tool)        tools += it.quantity;
        else if (it.category == Category::Material) materials += it.quantity;
        else if (it.category == Category::Consumable) consumables += it.quantity;
    }
    println("tools: {}  materials: {}  consumables: {}",
            tools, materials, consumables);

The comparisons are checked. A category value is always one of the three, so the chain covers the world without an else, and no typo can invent a "gadget" variant.

The types carry the program's meaning. The enum prevents a typo from inventing a category, the option forces the restock code to handle absence, and the struct names the fields and their types. The model is the plan, and the types hold it.

9.26 Types and the Machine: Layout

A type is also a layout. The machine stores values as bytes, and the type decides how they are arranged.

A struct's fields are laid out in declaration order, each at the address alignment requires, with padding between them. The order of fields decides the padding, so put wider fields first when memory matters. Two structs with the same fields in a different order can differ by several bytes each, and a million of them by millions of bytes.

Alignment is the machine's demand that a value start at an evenly spaced address. The compiler leaves gaps, called padding, between some fields. The gaps are invisible in the source but real in memory.

The same three fields in two orders move eight bytes:

    struct Interleaved
    {
        u8 tiny;
        u64 big;
        u8 tiny2;
    }

    struct Grouped
    {
        u8 tiny;
        u8 tiny2;
        u64 big;
    }

Interleaved puts a `u64` between two one-byte fields, paying seven bytes of padding on each side: twenty-four bytes. Grouped puts the small fields together and pays six bytes: sixteen bytes. Same fields, same types, eight bytes of difference, and `@sizeof` prints 24 and 16 on the platforms Coral targets. A million Interleaved values hold eight million bytes of padding the Grouped form never pays.

The fixed-width integers are their widths: `u8` one byte, `u16` two, `u32` four, `u64` eight, and a pointer the platform's word size. An `f32` is four bytes and an `f64` eight. An enum is an integer wide enough for its variants, and a distinct type has its base type's layout. A `Vec` is three fields and its size is the header, not the elements, which live on the heap.

The `@sizeof` operator reports a type's size. The library's memory pool computes its block size as the maximum of the element size and a pointer size. The layout is the C ABI, so a Coral struct has the same layout the platform's C compiler would give it.

9.27 Reading Types

Reading types is the habit a type-first language rewards. A signature reads as a sentence: the return type is the result, the parameters are the inputs.

A `HashMap<K, V>` names keys and values, a `Vec<T>` the elements, and an `Arr<T, N>` the elements and the count. An `any Shape` reads the requirement in the type itself: the value must implement the trait, and the trait's methods are what the body may call. A plain generic `largestArea<T>` says less in the signature and more in the body, where the operations it calls are the requirement.

An option reads the possibility of absence, and a `Result` the possibility of failure. The types say what a function may not produce, which matters as much as what it does produce. Read the types as the program's honest description.

9.28 The Type System and the Type-First Principle

The type system is the type-first principle in full: every type is declared and named, every value has a type, every signature states its types, and every program is checked before it runs.

Every design choice follows from the philosophy. Types are concrete and named, with no subtyping and no variance. Inference is local, not global. Enums are exhaustive sums and structs are named products. Options are checked absence, and casts are visible conversions. `comptime` reasons about types at compile time, and the runtime stays clean.

A program that compiles is a program whose types are consistent, and that consistency has had its class of errors found before it runs.

Chapter9 Summary

Coral is statically typed: types are explicit, checked before the program runs, and absent from the runtime.

The type declarations are `struct`, `enum`, `typedef`, and `distinct`, each naming a type in the module.

The primitives are the fixed-width signed and unsigned integers, `f32` and `f64`, `bool`, `char`, and `void`.

`var` infers a variable's type from its initializer; inference is local, not Hindley-Milner.

Generics are parameterized by types and compile-time values: `Vec<T>`, `Map<K, V>`, `Arr<T, N>`, `Pair<T, U>`, `Option<T>`, `Result<T, E>`.

Monomorphization compiles each concrete use into a concrete, checked, optimized instance, and identical instances may be shared.

Coral has no subtyping, so generics are invariant and there is no variance at the use site or the declaration site.

A generic's requirement is the set of operations its body performs, checked at instantiation. To put the requirement in the signature, use `any Trait` or a function-pointer parameter.

`typedef` names an existing type as an alternative spelling.

`distinct` creates a new type from a representation, so `File` and `TcpSocket` are not interchangeable `i32`s.

An opaque type hides its implementation behind storage and methods, as `Regex` hides the compiled pattern.

The enum is the sum type: a value is exactly one named variant, and exhaustive switches are checked, as `LogLevel` is one of five.

The struct is the product type: a value is its named fields, as `Timespec` is a second and a nanosecond.

Pointers may be null; `Option<T>` is checked absence, with `unwrap` and `unwrapOr`. There is no non-null assertion or safe navigation operator.

Coral has no higher-kinded, existential, phantom, dependent, or refinement types.

The implicit coercion matrix is empty; the only implicit adaptation is the integer literal, which takes the type its context requires.

Explicit conversions use the C-style cast, and every widening and narrowing is written.

There are no C-style promotions or usual arithmetic conversions: an operation's operands have one type, stated by casting or by a suffixed literal.

Values convert to text through formatting functions; text converts to views and strings through constructors.

`comptime` compares types at compile time and selects code by type parameter, with no runtime reflection.

Coral has no reflection, runtime type checking, `typeof`, or `instanceof`.

A type is an agreement with the compiler, the reader, and the machine about what a value is, what can be done with it, and how it is stored.

The type checker types every expression and verifies every seam, so a compiled program has been checked in full.

Modeling with types uses enums for fixed alternatives, structs for products, and options for possible absence, all compiler-checked.

A type is a layout: fields lie in declaration order with platform alignment, fixed-width integers are their widths, `@sizeof` reports the exact size, and the layout is the C ABI.

Reading a signature reads a sentence: the return type is the result, the parameters are the inputs, and option and `Result` state absence and failure.

Protocol-oriented design replaces duck typing: traits are declared promises, conformance is nominal and checked, and generics over traits call the protocol's methods.

The type system is the type-first principle in full: a program that compiles has consistent types.
