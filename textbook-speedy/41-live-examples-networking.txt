Chapter41

Live Examples: Networking

Talking to Other Programs Over a Socket

Appendix G lists the whole of Coral's networking surface in a page and a half. There is `tcpListen`, `tcpAccept`, `tcpConnect`, `tcpSend`, `tcpRecv`, and `tcpClose`; there is `udpSocket`, `udpBind`, `udpSendTo`, `udpRecvFrom`, and `udpClose`; there is `sockaddr_in`, though you will almost never touch it. That is all of it, and it is deliberately all of it. `std::io::net` is a thin, honest wrapper over the four or five operating-system calls that every socket program is built from. It does not hide the socket behind a connection object, it does not buffer for you, and it does not pretend a blocking call is something else. This chapter is the workshop for that surface: nine small programs that carry bytes between two endpoints, each one short enough to hold in your head, chosen so that a different part of the contract is the lesson.

The honesty matters more here than anywhere else in the book, so let me state what this API does not do before the first example, and never sell it otherwise. It is IPv4 only; there is no DNS resolution, so you connect to a dotted-quad literal, not to a hostname. There is no TLS, no certificate handling, and no HTTP library; whatever protocol you speak, you spell out in bytes yourself. There are no timeouts: `tcpConnect` may block for the operating system's own default, and `tcpRecv` and `tcpSend` block until they have done what they promised or the connection has failed. There is no non-blocking mode and no `select` or `poll`, so a single thread cannot multiplex many sockets. There is no "read whatever bytes are available" primitive. Every one of those absences is a real limitation, and each example below says which one it is standing on rather than wishing it away.

Two properties of `tcpRecv` and `tcpSend` deserve naming now, because every example is shaped by them. `tcpSend(sock, buf, len)` sends exactly `len` bytes; it loops until they are all accepted or an error occurs, and a short count from it means the peer closed. `tcpRecv(sock, buf, len)` is its mirror: it reads until it has filled `buf` or the peer has closed, and `Ok(n)` with `n < len` means end of stream, never "nothing to read right now." A socket is a byte stream with no message boundaries of its own; if you want lines or requests, you impose the framing yourself, and the third section is about exactly that. A UDP socket is the opposite: datagrams keep their boundaries, but nothing about them is ordered, retried, or even guaranteed to arrive.

A note on the imports. Everything here comes from `import(lib) std::io::net`, which exports `TcpSocket`, `UdpSocket`, and the functions above, and `IoError` comes from `import(lib) std::io::fs` because that is where the error variant lives. Buffers come from `import(lib) std::mman { alloc, dealloc };`, owned text from `String` (prelude), and the thread examples add `import(lib) std::concurrent::thread` and `import(lib) std::concurrent::mutex`. `println` and `print` are prelude names from `std::io::ios`. Each block repeats the imports it needs so it can be read on its own.

41.1 A TCP Echo Server

The problem. You want two programs to exchange bytes over a network reliably, in order, with a connection that either side can end. A TCP echo server is the smallest useful such program: it listens on a port, accepts one client at a time, and sends back every byte it receives.

The idea. `tcpListen(port)` creates a listening socket bound to every IPv4 interface and puts it in accept mode; the port is a `u16`, and ports below 1024 need privileges. `tcpAccept(listener)` blocks until a client connects and hands back a brand-new socket that belongs to that one conversation, leaving the listener free to accept the next. `tcpRecv` reads, `tcpSend` writes, `tcpClose` closes the descriptor. The one rule that shapes the code: `tcpRecv` is a read-exactly primitive. Ask it for a hundred bytes and it will wait for a hundred bytes or the end of the connection. So a server that wants to reply promptly reads in the smallest useful unit, one byte, and echoes it straight back.

The implementation.

    // Socket calls, the handle type, and the shared error variant.
    import(lib) std::io::net {
        tcpListen, tcpAccept, tcpRecv, tcpSend, tcpClose, TcpSocket
    };
    import(lib) std::io::fs { IoError };

    // Echo one connection to completion, one byte at a time.
    void echoLoop(TcpSocket client)
    {
        u8 b = 0;
        // tcpRecv is read-exactly, so ask for a single byte: that is the
        // only request that returns as soon as one byte has arrived.
        while (true)
        {
            Result<isize, IoError> r = tcpRecv(client, &b, 1);
            if (r.isErr()) break;                  // the connection broke
            if (r.unwrap() == 0) break;            // the peer closed cleanly

            // Send the byte straight back; a send failure also ends the loop.
            Result<isize, IoError> w = tcpSend(client, &b, 1);
            if (w.isErr()) break;
        }
    }

    i32 main()
    {
        // Create the listening socket on port 8080 for every IPv4 interface.
        Result<TcpSocket, IoError> server = tcpListen((u16)8080);
        if (server.isErr()) { println("could not listen on port 8080"); return 1; }

        TcpSocket listener = server.unwrap();
        println("echo server listening on port 8080");

        // Accept connections forever; each one is a separate conversation.
        while (true)
        {
            Result<TcpSocket, IoError> conn = tcpAccept(listener);
            if (conn.isErr()) break;

            // Service this client, then close only its socket, not the listener.
            TcpSocket client = conn.unwrap();
            echoLoop(client);
            tcpClose(client);
        }

        tcpClose(listener);
        return 0;
    }

`echoLoop` reads a byte, sends it back, and repeats until either a receive fails or `tcpRecv` returns zero, which is how a stream says "the other side is done." Each accepted connection gets its own socket, so closing it does not disturb the listener, which goes straight back to waiting in `tcpAccept`.

Cost and notes. Every call to `tcpRecv` and `tcpSend` is a system call, so a byte-at-a-time echo costs two system calls per byte. That is the price of promptness with an API that has no "read what is available" call: the only way to return before the buffer is full is to ask for one byte. `tcpListen` quietly sets `SO_REUSEADDR`, so restarting the server does not fail on a port still in the operating system's `TIME_WAIT` state. `tcpSend` loops internally until every byte is handed to the kernel, so the code here is not responsible for partial writes.

Edge cases and variations. `tcpRecv` answers with `Ok(0)` at end of stream, and an `Ok(n)` with `n` smaller than the requested length means the same thing, not "try again later." An `Err` means the connection was reset or the descriptor is bad, which is a different event from a clean close. The accept loop runs forever; the only thing that ends it is an accept that fails, and a bare `break` there means the program exits with success even though the listener died, which a real server would report. A client that connects and sends nothing will hold the single-threaded server in `echoLoop` indefinitely, because this server handles one conversation at a time; section41.7 fixes that with threads. Variation: echo whole lines instead of bytes by reading until a newline arrives and sending the completed line back, which is the subject of 40.3.

41.2 A TCP Client That Connects and Sends a Line

The problem. You want a program that reaches out to a server, sends it a line of text, and prints whatever comes back. This is the other half of every client–server pair, and the half that has to cope with the server not being there.

The idea. `tcpConnect(ip, port)` takes a dotted-quad string and a port, opens a socket, and performs the TCP handshake. It returns a `Result`, and the failure case is the ordinary one in a network program: nothing is listening, or the address is wrong, or the route is gone. Once connected, the socket behaves exactly like an accepted one: send bytes, receive bytes, close. The client below sends one line to the echo server of 40.1 and reads the echoed line back a byte at a time, for the same read-exactly reason.

The implementation.

    import(lib) std::io::net {
        tcpConnect, tcpRecv, tcpSend, tcpClose, TcpSocket
    };
    import(lib) std::io::fs { IoError };
    import(lib) std::text::string { String };

    i32 main()
    {
        // Connect to the echo server of 40.1 on the loopback address.
        Result<TcpSocket, IoError> opened = tcpConnect("127.0.0.1", (u16)8080);
        if (opened.isErr())
        {
            println("connect failed, is the echo server from 40.1 running?");
            return 1;
        }
        TcpSocket sock = opened.unwrap();

        // The request is a str; ptr and len give tcpSend its bytes and count.
        str line = "hello from the client\n";
        Result<isize, IoError> sent = tcpSend(sock, line.ptr, line.len);
        if (sent.isErr()) { tcpClose(sock); return 1; }

        // The reply length is unknown, so grow an owned String as bytes land.
        String reply = String::new();
        u8 b = 0;
        // Read one byte at a time until newline or close, capping the result.
        while (reply.len < 256)
        {
            Result<isize, IoError> r = tcpRecv(sock, &b, 1);
            if (r.isErr()) break;
            if (r.unwrap() == 0) break;
            // Accumulate the byte, then stop once the terminator is seen.
            reply.pushByte(b);
            if (b == (u8)'\n') break;              // the line is complete
        }

        // asView() prints exactly the bytes received, NUL and all.
        println("client received: {}", reply.asView());
        tcpClose(sock);
        return 0;
    }

The request is a `str`, so `line.ptr` and `line.len` give `tcpSend` the bytes and the count without any conversion; there is no NUL terminator involved and none is wanted. The reply is accumulated into an owned `String` because its length is not known in advance and `String` grows as bytes arrive. Printing `reply.asView()` hands the byte range to `println` as a length-carrying view, not a C string, so it is safe even if the server echoed a NUL.

Cost and notes. `tcpConnect` is the one call that can take real wall-clock time, because the handshake involves both machines and every router between them. A successful connect is the moment the connection exists; there is no separate "open" step. The send is one loop inside the library; the receive loop is one system call per byte, again because the API will not return a partial buffer.

Edge cases and variations. Connections are refused immediately when the host is reachable and nothing is listening; they hang for the operating system's default timeout, potentially minutes, when packets are being silently dropped, which is the timeout problem of 40.9. This client hard-codes the address and port; a real one reads them from the command line or builds them from a `Uri`. The name `127.0.0.1` is the loopback address, so this client only talks to a server on the same machine; section41.4 points at the same loopback literal. Variation: send several lines in one `tcpSend` and read several back; the framing rule is yours to define, and the next section is about getting it right.

41.3 Reading Until a Newline or Close

The problem. TCP gives you a stream of bytes, but protocols are usually built out of units: a line, a request header, a message. You need a function that reads one unit, and you need to understand why the obvious version of that function is wrong.

The idea. Because `tcpRecv(sock, buf, n)` blocks until it has `n` bytes or the stream ends, "read a line into a 256-byte buffer" is not `tcpRecv(sock, buf, 256)`, that call waits for 256 bytes even when the line is five bytes long and the sender is waiting for a reply. The correct primitive is to read one byte at a time and stop at the delimiter. That is slow, and the slowness is a real cost, but it is correct, and it is the only framing tool the API offers without a timeout or a non-blocking mode. The helper below returns the number of bytes read, treating both a newline and a clean close as the end of the unit.

The implementation.

    import(lib) std::io::net {
        tcpListen, tcpAccept, tcpConnect, tcpSend, tcpRecv, tcpClose, TcpSocket
    };
    import(lib) std::io::fs { IoError };
    import(lib) std::text::string { String };

    // Reads bytes into `out` until '\n' arrives, the peer closes, or `max`
    // bytes have been read. Returns the number of bytes appended.
    Result<isize, IoError> readLine(TcpSocket sock, String* out, usize max)
    {
        // Reset the accumulator so callers can reuse the same String.
        out.clear();
        while (out.len < max)
        {
            u8 b = 0;
            // One-byte reads are the only framing tool this blocking API offers.
            Result<isize, IoError> r = tcpRecv(sock, &b, 1);
            if (r.isErr()) return r;
            if (r.unwrap() == 0) break;            // peer closed: end of unit

            // Keep the delimiter in the result; the caller may strip it.
            out.pushByte(b);
            if (b == (u8)'\n') break;              // delimiter reached
        }
        return Result<isize, IoError>::Ok { .value = (isize)out.len };
    }

    i32 main()
    {
        // Listen first; the connection below queues in the backlog, needing no thread.
        Result<TcpSocket, IoError> server = tcpListen((u16)8090);
        if (server.isErr()) return 1;
        TcpSocket listener = server.unwrap();

        // A connection made to our own listener is queued by the kernel as
        // soon as listen() has run, so accept() below returns at once and the
        // whole exchange can run in one thread.
        Result<TcpSocket, IoError> opened = tcpConnect("127.0.0.1", (u16)8090);
        if (opened.isErr()) { tcpClose(listener); return 1; }
        TcpSocket client = opened.unwrap();

        Result<TcpSocket, IoError> accepted = tcpAccept(listener);
        if (accepted.isErr()) { tcpClose(client); tcpClose(listener); return 1; }
        TcpSocket peer = accepted.unwrap();

        // Two sends become one stream; readLine slices it back into units.
        str first = "first line\n";
        str second = "second line\n";
        tcpSend(client, first.ptr, first.len);
        tcpSend(client, second.ptr, second.len);

        // One accumulator reused for both lines; readLine clears it each call.
        String line = String::new();
        readLine(peer, &line, 256);
        println("server got: {}", line.asView());
        readLine(peer, &line, 256);
        println("server got: {}", line.asView());

        // Close all three descriptors: the accepted peer, the client, and the listener.
        tcpClose(peer);
        tcpClose(client);
        tcpClose(listener);
        return 0;
    }

The program is its own client and server, which is possible because `listen` puts the listener into accept mode immediately: a `tcpConnect` to that port completes the handshake and the connection waits in the backlog until `tcpAccept` collects it, so no second thread is needed. Two sends land in the kernel's buffer as a single stream; `readLine` slices it back into units by stopping at each `\n`, which is the entire content of "framing."

Cost and notes. `readLine` makes one receive system call per byte and copies each byte twice, once into the small local and once into the `String`. For a protocol with a small maximum unit this is acceptable; for a bulk transfer it is not, and you would read fixed-size chunks and split them yourself. The `max` bound is what stops a peer from making you allocate without limit; a line that never ends is a denial-of-service attempt, and a real server caps the unit and rejects the connection when the cap is hit.

Edge cases and variations. An empty line is a single `'\n'`, which `readLine` returns with length one; a line longer than `max` is truncated and the rest remains in the stream, desynchronising the parser, so the caller must treat "reached `max` without a delimiter" as an error rather than a short read. The delimiter is left in the returned bytes, which is fine for printing and must be stripped before comparing field values. `readLine` returning `Ok` does not mean a delimiter was seen: a partial line returned at close is also `Ok`, and the caller must look at whether the last byte was `'\n'` if that distinction matters. Variation: parameterise the delimiter, or read until a two-byte `\r\n` sequence, which is what the HTTP examples implicitly rely on when they scan for the blank line ending a request.

41.4 A Minimal HTTP/1.0 GET Client

The problem. You want to fetch a web page with no HTTP library, understanding every byte you send and every byte you receive. This is the smallest thing that a browser does, and it demonstrates that HTTP is just a text protocol on top of a TCP socket.

The idea. An HTTP/1.0 request is a request line, a set of headers, and a blank line, all separated by CRLF pairs. Ask for `Connection: close` and the server will send the whole response and then close the socket; because `tcpRecv` reports the close as `Ok(0)`, "read until close" is a simple loop that needs no `Content-Length` parsing. The response is printed exactly as it arrives, headers and all. The one compromise forced by the API is the address: with no DNS resolver, the target must be an IPv4 literal, which is why the example points at the local server of 40.5.

The implementation.

    import(lib) std::io::net {
        tcpConnect, tcpSend, tcpRecv, tcpClose, TcpSocket
    };
    import(lib) std::io::fs { IoError };
    import(lib) std::text::string { String };
    import(lib) std::mman { alloc, dealloc };

    i32 main()
    {
        // Speak HTTP/1.0 by hand over one plain TCP connection.
        Result<TcpSocket, IoError> opened = tcpConnect("127.0.0.1", (u16)8080);
        if (opened.isErr()) { println("connect failed"); return 1; }
        TcpSocket sock = opened.unwrap();

        // Assemble the exact request bytes; HTTP requires CRLF line endings.
        String request = String::from("GET / HTTP/1.0\r\n");
        request.appendView("Host: 127.0.0.1\r\n");
        request.appendView("Connection: close\r\n");
        request.appendView("\r\n");

        // Send the whole request head in one call; short writes are handled.
        str head = request.asView();
        Result<isize, IoError> sent = tcpSend(sock, head.ptr, head.len);
        if (sent.isErr()) { tcpClose(sock); return 1; }

        // A single reusable buffer: the response streams out, not stored.
        u8* buf = alloc<u8>(4096);
        if (buf == null) { tcpClose(sock); return 1; }

        // Read until tcpRecv returns zero, the server's close after the body.
        while (true)
        {
            Result<isize, IoError> r = tcpRecv(sock, buf, 4096);
            if (r.isErr()) { println("recv failed"); break; }
            isize n = r.unwrap();
            if (n == 0) break;                     // server closed: response done
            // Emit exactly the bytes just received, whatever they encode.
            print("{}", str::fromParts(buf, (usize)n));
        }

        // Release the buffer and the socket; the program owns both.
        dealloc<u8>(buf);
        tcpClose(sock);
        return 0;
    }

The request is assembled in a `String` so the exact CRLF bytes are under the program's control; `\r\n`, not `\n`, is the HTTP line ending. `str::fromParts(buf, n)` wraps the received bytes in a length-carrying view so `print` writes exactly `n` of them, including any byte that is not valid text. The loop ends when `tcpRecv` returns zero, which is the server's close after the body.

Cost and notes. The receive loop asks for 4096 bytes each time and gets all 4096 until the final partial buffer, because that is what `tcpRecv` promises; a response smaller than 4096 therefore arrives in one partial call followed by a zero. The whole response is not accumulated; it is printed as it streams, so memory stays at one buffer regardless of page size. Building the request allocates once and copies a handful of short views into it.

Edge cases and variations. There is no DNS: `tcpConnect` accepts only dotted-quad strings, so connecting to `example.com` by name is not possible and would have to be preceded by a resolver the library does not provide. There is no TLS, so `https` is out of reach and the port is plain 80. There are no redirects and no parsing of the status line; this program prints the response and leaves interpretation to the reader. A `Content-Length` that lies, or a server that never closes, will leave the loop waiting, and the API's lack of timeouts means the program can hang there. Variation: scan the first `\r\n` to extract the status code, or stop the print at the byte offset of the blank line to show only the body, which is the beginning of a real HTTP client.

41.5 A Tiny HTTP Server That Returns a Fixed Page

The problem. You want to answer an HTTP GET with a fixed HTML page, speaking the protocol by hand so that you can see exactly what a server sends. This is the counterpart to 40.4, and the smallest server that a browser can load.

The idea. Read the request headers until the blank line that ends them; the request's method and path do not matter here, because every request gets the same page. Build a response with a status line, a `Content-Length`, and the body, send it, and close the connection. HTTP/1.0 closes after each response by default, so one connection carries exactly one request, which is what makes a single-threaded accept loop sufficient for correctness at low traffic.

The implementation.

    import(lib) std::io::net {
        tcpListen, tcpAccept, tcpSend, tcpRecv, tcpClose, TcpSocket
    };
    import(lib) std::io::fs { IoError };
    import(lib) std::text::string { String };
    import(lib) std::fmt::fmt { formatInt };
    import(lib) std::mman { alloc, dealloc };

    // Read request headers until CRLFCRLF, or the peer closes, or the cap.
    void readHeaders(TcpSocket client, u8* hdr, usize cap)
    {
        // Track how many head bytes have been collected so far.
        usize used = 0;
        while (used < cap)
        {
            u8 b = 0;
            // One byte at a time so the CRLFCRLF boundary cannot be overshot.
            Result<isize, IoError> r = tcpRecv(client, &b, 1);
            if (r.isErr()) break;
            if (r.unwrap() == 0) break;
            // Store the byte, then test the last four for the blank line.
            hdr[used] = b;
            used += 1;
            if (used >= 4 &&
                hdr[used - 4] == (u8)'\r' && hdr[used - 3] == (u8)'\n' &&
                hdr[used - 2] == (u8)'\r' && hdr[used - 1] == (u8)'\n')
                break;
        }
    }

    // Answer one request with a fixed page and close the connection.
    void serveOnce(TcpSocket client)
    {
        // The page never changes; the request path is ignored.
        str body = "<!doctype html><title>hi</title><p>Hello from Coral.</p>\n";
        // Read and discard the request head; only its ending blank line matters.
        u8* hdr = alloc<u8>(4096);
        if (hdr == null) { tcpClose(client); return; }
        readHeaders(client, hdr, 4096);
        dealloc<u8>(hdr);

        // Derive Content-Length from the body so the two can never disagree.
        String response = String::from("HTTP/1.0 200 OK\r\n");
        response.appendView("Content-Type: text/html; charset=utf-8\r\n");
        response.appendView("Content-Length: ");
        String length = formatInt((i64)body.len, 10u, false);
        response.appendView(length.asView());
        response.appendView("\r\nConnection: close\r\n\r\n");
        response.appendView(body);

        // One send for status line, headers, and body; the library loops.
        str out = response.asView();
        tcpSend(client, out.ptr, out.len);
        tcpClose(client);
    }

    i32 main()
    {
        Result<TcpSocket, IoError> server = tcpListen((u16)8080);
        if (server.isErr()) { println("could not listen on port 8080"); return 1; }
        TcpSocket listener = server.unwrap();
        println("serving a fixed page on http://127.0.0.1:8080/");

        // HTTP/1.0 sends one request per connection, so a serial loop suffices.
        while (true)
        {
            Result<TcpSocket, IoError> conn = tcpAccept(listener);
            if (conn.isErr()) break;
            serveOnce(conn.unwrap());
        }
        tcpClose(listener);
        return 0;
    }

The header reader is a rolling four-byte test for the `\r\n\r\n` that ends the request head. `Content-Length` is computed from the body at runtime with `formatInt`, so the number always matches the bytes that follow it, the single most common way a hand-written server breaks. The response is one `tcpSend`, which the library turns into as many underlying writes as the kernel needs.

Cost and notes. This server handles one client at a time and blocks in `readHeaders` for each; a slow or silent client stalls everyone behind it. The request body, if any, is not read, which is fine for GET and wrong for POST. `formatInt` allocates a small `String` for the length; it is a local and is released automatically at the end of `serveOnce`.

Edge cases and variations. A client that opens a connection and sends nothing holds the server in `readHeaders` until it times out or the cap is hit, and there is no timeout in the API to bound it. A request larger than 4096 bytes has its head truncated, and the connection should really be rejected at that point. Only one request per connection is served, which matches HTTP/1.0's default `close`; keep-alive would require a loop and parsing `Content-Length`. Variation: route on the request line, read the first line, split it on spaces, and choose a different body per path, which turns this into a real, if tiny, web server. Because the address is bound to all interfaces, this example is reachable from the network; binding to `INADDR_LOOPBACK` alone is not exposed by the API, which binds `0.0.0.0` unconditionally.

41.6 A UDP Send and Receive Pair

The problem. You want the fire-and-forget style of the datagram sockets: no connection, no handshake, each message independent. A pair of UDP sockets that send and receive one message is the whole idea.

The idea. `udpSocket()` creates an unbound datagram socket. `udpBind(&sock, port)` gives it a local port so that datagrams addressed to that port arrive. `udpSendTo(&sock, buf, len, ip, port)` sends one datagram to an address, and `udpRecvFrom(&sock, buf, len)` receives one datagram. Unlike TCP, a datagram is a unit: the receiver gets exactly the bytes the sender wrote, in one call, and a short read is normal rather than a sign of end-of-stream. The order is not guaranteed, delivery is not guaranteed, and none of that is a bug in the library, it is what UDP is.

The implementation.

    import(lib) std::io::net {
        udpSocket, udpBind, udpSendTo, udpRecvFrom, udpClose, UdpSocket
    };
    import(lib) std::io::fs { IoError };
    import(lib) std::mman { alloc, dealloc };

    i32 main()
    {
        // Receiver: a datagram socket bound to a known local port.
        Result<UdpSocket, IoError> receiverRes = udpSocket();
        if (receiverRes.isErr()) return 1;
        UdpSocket receiver = receiverRes.unwrap();
        if (udpBind(&receiver, (u16)9999).isErr())
        {
            udpClose(&receiver);
            return 1;
        }

        // Sender: unbound; the OS assigns a source port on the first send.
        Result<UdpSocket, IoError> senderRes = udpSocket();
        if (senderRes.isErr()) { udpClose(&receiver); return 1; }
        UdpSocket sender = senderRes.unwrap();

        // A datagram keeps its boundary; the bytes travel as one unit.
        str message = "ping over udp\n";
        // A UDP send reports only local errors; loss on the wire is silent.
        Result<isize, IoError> sent =
            udpSendTo(&sender, message.ptr, message.len, "127.0.0.1", (u16)9999);
        if (sent.isErr())
        {
            println("send failed");
            udpClose(&sender);
            udpClose(&receiver);
            return 1;
        }

        // A datagram larger than this buffer is truncated with no error.
        u8* buf = alloc<u8>(512);
        if (buf == null)
        {
            udpClose(&sender);
            udpClose(&receiver);
            return 1;
        }

        // Exactly one datagram is received per call, or the call blocks.
        Result<isize, IoError> got = udpRecvFrom(&receiver, buf, 512);
        if (got.isErr())
        {
            println("receive failed");
        }
        else
        {
            isize n = got.unwrap();
            println("received {} bytes: {}", n, str::fromParts(buf, (usize)n));
        }

        // Release the buffer and both socket handles.
        dealloc<u8>(buf);
        udpClose(&sender);
        udpClose(&receiver);
        return 0;
    }

The sender socket is never bound; the operating system assigns it an ephemeral source port the first time it sends. The datagram travels over loopback into the receiver's queue, where `udpRecvFrom` collects exactly one message. Because the two sockets are in the same process, the send and receive proceed in order without a second thread: the kernel holds the datagram until the receiver asks for it.

Cost and notes. `udpSendTo` is one system call for one datagram, and `udpRecvFrom` is one for one; there is no library-level retry or buffering, because there is nothing to retry, if the network drops the datagram, no error is reported and nothing happens. That is the entire performance advantage and the entire reliability disadvantage of UDP in the same sentence.

Edge cases and variations. `udpRecvFrom` does not tell you who sent the datagram: the implementation passes `null` for the source address, so a server built on it cannot reply to the sender, only observe the payload. That is a genuine gap, not a subtlety, and a real UDP service needs the source address, which this module does not expose. Datagrams larger than the receive buffer are truncated by the kernel and the excess is silently lost. The example relies on both sockets being in one process; across machines, a dropped packet means `udpRecvFrom` blocks forever, because there is no timeout. A zero-length datagram is legal and is delivered. Variation: make the receiver a server for one datagram and have it echo the payload back by hard-coding the sender's known address, which works only because the address is known in advance, the limitation above, made concrete.

41.7 Handling Several Clients with Threads

The problem. The single-threaded echo server of 40.1 serves one client at a time. A second client waits in the accept queue until the first disconnects, which is unacceptable for anything but a toy. You want each connection handled independently.

The idea. Accept a connection, hand its socket to a new thread, and go straight back to accept the next. The connection socket is the only thing the worker needs, so it travels in a small allocated struct whose lifetime the worker owns; the worker frees it when the conversation ends. This is thread per connection, the oldest scalable-server pattern. The API has no way to detach a thread, so this example accepts a bounded number of clients and joins the workers at the end; a server that ran forever would instead feed a thread pool (Chapter35), which is what production code uses.

The implementation.

    import(lib) std::io::net {
        tcpListen, tcpAccept, tcpRecv, tcpSend, tcpClose, TcpSocket
    };
    import(lib) std::io::fs { IoError };
    import(lib) std::concurrent::thread {
        threadCreate, threadJoin, Thread, ThreadError
    };
    import(lib) std::mman { alloc, dealloc };

    // Bound the number of concurrent clients; each gets one thread.
    const u32 MAX_CLIENTS = 4;

    // Hand a heap-owned socket to a worker across the thread boundary.
    struct ClientJob { TcpSocket sock; }

    // Worker entry point: own the job, echo its socket, then close it.
    rawptr handleClient(rawptr arg)
    {
        // Recover the job, copy the socket out, and free the job at once.
        ClientJob* job = (ClientJob*)arg;
        TcpSocket sock = job->sock;
        dealloc<ClientJob>(job);                   // the worker owns the job

        u8 b = 0;
        // Same byte-at-a-time echo as 40.1, but on this worker's own socket.
        while (true)
        {
            // A recv error, a clean close, or a failed send all end the worker.
            Result<isize, IoError> r = tcpRecv(sock, &b, 1);
            if (r.isErr()) break;
            if (r.unwrap() == 0) break;
            if (tcpSend(sock, &b, 1).isErr()) break;
        }
        tcpClose(sock);
        return null;
    }

    i32 main()
    {
        Result<TcpSocket, IoError> server = tcpListen((u16)8080);
        if (server.isErr()) return 1;
        TcpSocket listener = server.unwrap();

        // Keep one join handle per client so the stacks can be reclaimed.
        Thread* workers = alloc<Thread>((usize)MAX_CLIENTS);
        if (workers == null) { tcpClose(listener); return 1; }

        // Accept a bounded batch; the server drains it before exiting.
        u32 accepted = 0;
        while (accepted < MAX_CLIENTS)
        {
            Result<TcpSocket, IoError> conn = tcpAccept(listener);
            if (conn.isErr()) break;

            // Package the accepted socket so the worker can take ownership.
            ClientJob* job = alloc<ClientJob>(1);
            if (job == null) { tcpClose(conn.unwrap()); break; }
            job->sock = conn.unwrap();

            // Spawn the worker; on failure reclaim both socket and job here.
            Result<Thread, ThreadError> t = threadCreate(handleClient, (rawptr)job);
            if (t.isErr()) { tcpClose(job->sock); dealloc<ClientJob>(job); continue; }
            workers[accepted] = t.unwrap();
            accepted += 1;
        }

        // Join every worker so no thread outlives the buffers it used.
        for (u32 i = 0; i < accepted; i += 1) threadJoin(workers[i], null);
        dealloc<Thread>(workers);
        tcpClose(listener);
        return 0;
    }

The worker copies the socket out of the job and frees the job before doing any work, so there is no question about what owns the allocation while the thread runs. On the failure path where `threadCreate` returns an error, the socket is closed and the job is freed by the accept loop itself, so no resource is stranded. Joining each worker makes their completion observable and their stacks reclaimable.

Cost and notes. One thread per connection means one stack and one kernel object per client, which is memory and scheduler pressure that grows with the number of connections; the pool in Chapter35 replaces the per-connection thread with a queue push. The threads genuinely run in parallel, so this server uses every core when the clients are active. The join loop means the server drains every accepted conversation before it exits, which is why the example is bounded.

Edge cases and variations. If a client connects and then stays silent, its worker blocks in `tcpRecv` forever, and the join at the end blocks with it; a timeout would help, and the API has none. If `MAX_CLIENTS` connections are accepted and none closes, the server stops accepting long before its workers finish, which is a poor shape for production but correct for a demonstration. The worker does not synchronise with anything, because each holds its own socket and touches no shared state; the moment they share something, as in the next section, a mutex enters the picture. Variation: replace the fixed accept count with an infinite loop and submit each job to a `ThreadPool` from Chapter35, which bounds the thread count while still accepting without limit; the missing `detach` is then no longer a problem because the pool owns its workers.

41.8 A Line-Based Chat Broadcast Server

The problem. Several clients connect, each types lines, and every line one client sends is delivered to all the others. This is the first protocol in the chapter in which the connections must know about each other, which is exactly where shared mutable state appears.

The idea. A `Room` holds the list of connected sockets behind a mutex. When a client connects it joins the room; when it disconnects it leaves; when it sends a line, the room broadcasts that line to every socket except the sender. The mutex protects the list itself, not the sockets, so a send can never race a join or a leave. The chat server keeps the same thread-per-connection shape as 40.7, with the room as the one shared object.

The implementation.

    import(lib) std::io::net {
        tcpListen, tcpAccept, tcpRecv, tcpSend, tcpClose, TcpSocket
    };
    import(lib) std::io::fs { IoError };
    import(lib) std::concurrent::thread { threadCreate, Thread, ThreadError };
    import(lib) std::concurrent::mutex { Mutex };
    import(lib) std::text::string { String };
    import(lib) std::mman { alloc, dealloc };

    // Cap the room; a joining client beyond this is refused.
    const u32 ROOM_CAPACITY = 8;

    // The shared state: the set of connected sockets behind one mutex.
    struct Room
    {
        // Guards the client list; only list operations happen under it.
        Mutex mutex;
        // Fixed-size array of live sockets; their order does not matter.
        TcpSocket* clients;
        u32 count;

        bool init()
        {
            // Allocate the list and start with no members.
            self.clients = alloc<TcpSocket>((usize)ROOM_CAPACITY);
            if (self.clients == null) return false;
            self.mutex.init();
            self.count = 0;
            return true;
        }

        bool join(TcpSocket sock)
        {
            // Under the lock, check for room and append the socket.
            self.mutex.lock();
            bool ok = self.count < ROOM_CAPACITY;
            if (ok) { self.clients[self.count] = sock; self.count += 1; }
            self.mutex.unlock();
            return ok;
        }

        void leave(TcpSocket sock)
        {
            self.mutex.lock();
            // Find the socket, then compact by moving the last entry into its slot.
            u32 i = 0;
            while (i < self.count && (i32)self.clients[i] != (i32)sock) i += 1;
            if (i < self.count)
            {
                self.clients[i] = self.clients[self.count - 1];
                self.count -= 1;
            }
            self.mutex.unlock();
        }

        void broadcast(TcpSocket from, str line)
        {
            self.mutex.lock();
            // Send the line to every member except its originator.
            for (u32 i = 0; i < self.count; i += 1)
            {
                if ((i32)self.clients[i] != (i32)from)
                    tcpSend(self.clients[i], line.ptr, line.len);
            }
            self.mutex.unlock();
        }
    }

    struct ClientJob { Room* room; TcpSocket sock; }

    // The same one-byte framing helper used in 40.3.
    Result<isize, IoError> readLine(TcpSocket sock, String* out, usize max)
    {
        out.clear();
        while (out.len < max)
        {
            u8 b = 0;
            Result<isize, IoError> r = tcpRecv(sock, &b, 1);
            if (r.isErr()) return r;
            if (r.unwrap() == 0) break;
            out.pushByte(b);
            if (b == (u8)'\n') break;
        }
        return Result<isize, IoError>::Ok { .value = (isize)out.len };
    }

    rawptr chatClient(rawptr arg)
    {
        // Unpack the job and take ownership of its socket.
        ClientJob* job = (ClientJob*)arg;
        Room* room = job->room;
        TcpSocket sock = job->sock;
        dealloc<ClientJob>(job);

        // Refuse and close if the room is already full.
        if (!room->join(sock)) { tcpClose(sock); return null; }

        // One reusable line buffer for the client's whole session.
        String line = String::new();
        while (true)
        {
            Result<isize, IoError> r = readLine(sock, &line, 512);
            if (r.isErr()) break;
            if (r.unwrap() == 0) break;
            room->broadcast(sock, line.asView());
        }

        // Leave before closing so no broadcast targets a dead socket.
        room->leave(sock);
        tcpClose(sock);
        return null;
    }

    i32 main()
    {
        // The room lives in main's frame, so it outlives every worker.
        Room room;
        if (!room.init()) return 1;

        // Listener for the chat; one worker thread per connection.
        Result<TcpSocket, IoError> server = tcpListen((u16)8080);
        if (server.isErr()) { return 1; }
        TcpSocket listener = server.unwrap();
        println("chat server listening on port 8080");

        while (true)
        {
            Result<TcpSocket, IoError> conn = tcpAccept(listener);
            if (conn.isErr()) break;

            // Each job carries a pointer to the shared room and its own socket.
            ClientJob* job = alloc<ClientJob>(1);
            if (job == null) { tcpClose(conn.unwrap()); break; }
            job->room = &room;
            job->sock = conn.unwrap();

            Result<Thread, ThreadError> t = threadCreate(chatClient, (rawptr)job);
            if (t.isErr()) { tcpClose(job->sock); dealloc<ClientJob>(job); }
        }
        tcpClose(listener);
        return 0;
    }

`Room` protects its list with a single mutex, and every method takes and releases it around a handful of instructions. `leave` swaps the departing socket with the last element before shrinking the count, so removal is O(1) and the array stays compact; order among clients does not matter, which is what makes the swap legal. `broadcast` holds the lock while sending, so a line cannot slip past a client that has just joined or target one that has just left.

Cost and notes. Every broadcast is O(clients) sends under one lock. Holding the lock during `tcpSend` is the sharp edge: a slow or stalled client whose socket buffer is full blocks the send, and because the lock is held, every other client waits behind it. The honest fix is a per-client outgoing queue and a dedicated writer, which is more machinery than this example carries; the cost of the simple version should be stated, not discovered.

Edge cases and variations. The room is bounded at eight clients; a ninth is refused and its socket closed, rather than being left half-joined. A client that disconnects is removed on the way out, so the room does not accumulate dead sockets, but a client that hangs without disconnecting holds a slot forever. The broadcast includes the sender's own line only if another client sent it; the sender's echo is omitted, which is a product decision, not a requirement. The `Room` outlives every worker because it lives in `main`'s frame and `main` never returns, so the pointers passed to the workers stay valid. Variation: prefix each broadcast line with a client number so readers can tell senders apart, or send a join and leave notice to the room; both turn the primitive into something usable, and both need only the existing lock.

41.9 Error Handling: Refused and Timed-Out Connections

The problem. Network operations fail for reasons the program cannot prevent: nothing is listening, the route is gone, the peer never answers. A network program that ignores its `Result` values throws away the only information it has about the outside world.

The idea. `tcpConnect` returns `Result<TcpSocket, IoError>`, and the error is an `IoError`, whose `Os` case carries the operating system's error number and the name of the operation that failed. A refused connection is immediate: the host is reachable and answers with a reset, and the code is `ECONNREFUSED` (111 on Linux). A dropped or filtered address produces no answer at all, so `connect` blocks for the kernel's default timeout and then fails with `ETIMEDOUT` (110). Because the socket module exposes no timeout knob, the only thing an application can control is how many times it tries; the delay of a single attempt belongs to the operating system.

The implementation.

    import(lib) std::io::net { tcpConnect, tcpClose, TcpSocket };
    import(lib) std::io::fs { IoError };
    import(lib) std::time { sleepMs };

    i32 main()
    {
        // Three attempts; each tcpConnect may block for the kernel timeout.
        for (u32 attempt = 1; attempt <= 3; attempt += 1)
        {
            // Port 9 is the conventional discard port; nothing is listening,
            // so this connect is refused immediately on a local host.
            Result<TcpSocket, IoError> opened = tcpConnect("127.0.0.1", (u16)9);
            if (opened.isOk())
            {
                println("connected on attempt {}", attempt);
                tcpClose(opened.unwrap());
                return 0;
            }

            // Pull the error apart by case; naming all three keeps it exhaustive.
            IoError e = opened.unwrapErr();
            switch (e)
            {
                IoError::Os { code, op } =>
                    println("attempt {}: {} failed, errno {}", attempt, op, code),
                IoError::BadUsage { msg } =>
                    println("bad address: {}", msg),
                IoError::Eof { op } =>
                    println("unexpected end of stream in {}", op),
            }
            // Fixed short back-off; a real client would widen it each round.
            sleepMs(250);
        }

        println("gave up after three attempts");
        return 1;
    }

The switch names all three cases of `IoError`, so it is exhaustive and needs no `else`. `Os { code, op }` binds the error number and the operation string, which is enough to distinguish "refused, try again somewhere else" from "timed out, the host is unreachable." The back-off here is a fixed sleep; a real client would widen it and give up on the errors that retrying cannot fix.

Cost and notes. The failed `tcpConnect` costs one round trip when the host answers with a reset, and the whole kernel timeout when it does not; that asymmetry is the reason a network program feels fast on a healthy network and hangs on a broken one. `sleepMs` sleeps for at least the requested time, so the retry loop's spacing is approximate. Reading `errno` means the code is platform-specific: the same failure has a different number on Windows, which is why the field is reported rather than hard-coded into the logic.

Edge cases and variations. `IoError::BadUsage` is the library's own complaint, a malformed IP address such as `"999.1.2.3"`, and is not a network failure at all. Because there is no timeout parameter, the loop cannot bound the time a single `tcpConnect` spends; the only honest statement is that the attempt will return when the kernel decides, which is typically around a minute for a filtered host. There is no asynchronous cancellation either, so a program cannot abandon an in-progress connect. Variation: drive the retry from the error code, retrying only on `ETIMEDOUT` and giving up immediately on `ECONNREFUSED`, and add a max attempt count as a wall-clock budget rather than a fixed number.
