Chapter31

Live Examples: Graphs

The Shape Behind Half of Computer Science

A graph is the simplest interesting thing after a list: a set of points, and a set of connections between them. We call the points vertices and the connections edges. Once you have both, you have a model for an astonishing range of problems. Roads between cities. Friendships between people. Links between web pages. Dependencies between build tasks. Wires between chips. Moves in a game. Reactions in a cell. Each of those is vertices and edges, and each has been attacked with the same handful of algorithms. Learn those algorithms once, and they pay off in every domain you touch.

There are two kinds of graph, and the distinction matters from the very first line of code. In an undirected graph an edge goes both ways: a road from A to B is also a road from B to A, and a friendship is mutual. In a directed graph an edge has a direction. A dependency means "task A must finish before task B starts," and it does not mean the reverse. Many algorithms work on both with a one-line change. Others care deeply which kind they are handed, and figuring out which is your job.

Then there is the question of how to store a graph, and the trade is worth stating plainly. An adjacency list is one list per vertex, holding that vertex's neighbours. It uses memory proportional to the number of edges, and it makes "who are my neighbours" fast, which is what almost every traversal asks. An adjacency matrix is a grid of booleans (or weights), where entry (u, v) says whether u and v are connected. It turns "are these two connected" into a single lookup, but it uses memory proportional to the square of the number of vertices. For sparse graphs, meaning few edges relative to vertices, which is what the real world usually produces, the adjacency list wins by a mile. Unless a problem specifically needs constant-time edge queries, reach for the list. This chapter uses `Vec<Vec<...>>`: an outer vector indexed by vertex, each entry an inner vector of neighbours. That is the adjacency list, expressed with the containers of Chapter16.

A word on the size of these algorithms, so the rest of the chapter reads easily. Almost every traversal here is O(V + E): the cost of looking at every vertex and every edge once. Dijkstra adds a heap and becomes O((V + E) log V). Kruskal adds a sort and a union-find and becomes O(E log E). That small vocabulary of costs describes nearly everything in this chapter. After Chapter29, you can read every one of them as "what happens when the input grows."

A note on the imports. The graph is built from `import(lib) std::vec { Vec };`. BFS and Kahn's algorithm use `import(lib) std::collections::queue { Queue };`. The heaps in Dijkstra and Prim use `import(lib) std::collections::priorityqueue { PriorityQueue };`. Sorting edges by weight uses the `sortBy` method on `Vec`. Each relevant code block repeats the import it needs so it can be read on its own.

31.1 Representing a Graph

The problem. Build a graph type in Coral that can hold an undirected or directed graph with integer-named vertices, supports adding edges, and exposes each vertex's neighbours efficiently.

Picture this. A graph is a city map, and every intersection has a signpost listing the streets that leave it. An adjacency list is a filing cabinet with one drawer per intersection, and the drawer holds exactly the streets from that intersection. To find where you can go next, you open one drawer, not the whole cabinet.

Brute force, then better. The naive representation is an adjacency matrix: an n×n grid of booleans, where `matrix[u][v]` is true if u and v are connected. It is simple, and it gives O(1) edge queries, but it stores n^2 entries whether or not there are that many edges. For a million-vertex, few-edge graph that is a trillion booleans, which is absurd. The adjacency list stores only the edges that exist, and every traversal in this chapter walks neighbours. So the list is both smaller and better shaped for the work.

    import(lib) std::vec { Vec };

    // adjacency list: one list of neighbours per vertex
    struct Graph {
        // number of vertices
        usize n;
        // adj[u] is the neighbour list of vertex u
        Vec<Vec<i32>> adj;

        // build n empty drawers, so isolated vertices are still valid
        static Graph new(usize n) {
            Graph g = Graph {
                .n = n,
                .adj = Vec<Vec<i32>>::new()
            };
            for (usize i = 0; i < n; i += 1) {
                // one empty inner vector per vertex
                g.adj.push(Vec<i32>::new());
            }
            return g;
        }

        // an undirected edge is mutual
        void addUndirectedEdge(i32 u, i32 v) {
            // record each endpoint in the other's list
            self.adj.atPtr((usize)u)->push(v);
            self.adj.atPtr((usize)v)->push(u);
        }

        // a directed edge is one-way: only u -> v
        void addDirectedEdge(i32 u, i32 v) {
            self.adj.atPtr((usize)u)->push(v);
        }
    }

The struct holds the vertex count and a `Vec<Vec<i32>>`: an outer vector with one slot per vertex, each slot itself a vector of neighbour indices. `new` allocates n empty inner vectors, so `adj[u]` is always a valid drawer, even for an isolated vertex. `addUndirectedEdge` pushes each endpoint into the other's list, which is what makes the edge mutual. `addDirectedEdge` pushes only from u to v, which is what makes it one-way. The `atPtr` in both methods is deliberate: it returns a pointer to the inner vector without copying it, and pushing through that pointer is safe. Write `self.adj.at(u)->push(v)` instead and you copy the inner `Vec`, which owns heap memory, and risk the copy and the original both being freed. That is the classic double-free footgun, waiting whenever a container of owning containers is accessed by value.

Time and space. Building a graph with V vertices costs O(V) to create the drawers, and each `addEdge` is O(1). The storage is O(V + E), where E is the number of edges: the outer vector holds V drawers, and for an undirected graph the inner vectors together hold 2E entries. The matrix, by contrast, would be O(V^2) storage. For any graph that is not nearly complete, the list wins.

Edge cases. A graph with zero vertices is legal and empty; loops over its vertices simply do not run. The code handles an undirected self-loop (u, u) correctly, though whether it means anything depends on the problem. Duplicate edges are not deduplicated. If a problem can supply them, either deduplicate at insert time, or write the traversal to tolerate revisiting, which most do anyway.

A variation. For weighted graphs, store a struct per edge instead of a bare int:

    // weighted edge: destination plus cost
    struct Edge {
        i32 to;
        // the cost of travelling this edge
        i32 weight;
    }

Then the adjacency list becomes `Vec<Vec<Edge>>`, and each neighbour carries its edge weight. Dijkstra (30.5) and Prim (30.8) use exactly this. The alternative, a Map from a pair to a weight, is far clumsier for the at-neighbours traversal these algorithms do. That is why weighted edges usually live alongside the neighbour, not in a separate structure.

31.2 BFS: Shortest Paths in an Unweighted Graph

The problem. Given an unweighted graph and a source vertex, find the number of edges on the shortest path from the source to every other vertex. This is the "fewest hops" distance, and it is the foundation of an enormous number of graph problems.

Picture this. You are in a strange city and you want the fewest street-crossings to reach each corner. You start at your corner and mark it "zero." Then you visit every corner one step away and mark them "one." Then every unvisited corner two steps away and mark them "two," and so on. You never revisit a corner, because the first time you reach it is necessarily by the shortest route. If a shorter route existed, you would have found it in an earlier ring. That expanding-ring process is breadth-first search.

Brute force, then better. The brute force explores every possible walk, which is exponential because walks can loop forever. BFS is smarter. It visits vertices in order of distance and stops as soon as a vertex is first reached: the first visit is the shortest visit. No edge ever needs to be examined again for that vertex. The tool that makes this happen is a queue, first-in first-out, so every vertex at distance d is dequeued before any at distance d+1.

    import(lib) std::collections::queue { Queue };

    void bfs(Graph* g, i32 source, Vec<i32>* dist) {
        for (usize i = 0; i < g->n; i += 1) {
            dist->push(-1);                       // -1 means "not reached yet"
        }
        // the source is zero hops from itself
        dist->set((usize)source, 0);
        // FIFO order is what lets BFS find shortest paths
        Queue<i32> q = Queue<i32>::new();
        // seed the frontier with the source
        q.enqueue(source);
        // process vertices in non-decreasing distance order
        while (!q.isEmpty()) {
            // take the next vertex to expand
            i32 u = q.dequeue();
            Vec<i32>* neighbors = g->adj.atPtr((usize)u);
            for (usize i = 0; i < neighbors->count(); i += 1) {
                i32 v = neighbors->at(i);
                // the first visit is necessarily the shortest visit
                if (dist->at((usize)v) == -1) {
                    // record one hop more than u's distance
                    dist->set((usize)v, dist->at((usize)u) + 1);
                    // discover v so it is expanded in a later ring
                    q.enqueue(v);
                }
            }
        }
    }

The `dist` vector doubles as the visited marker: −1 means "never seen," and any non-negative number means "seen, at this distance." The source starts at distance 0 and goes into the queue. The loop pulls a vertex, walks its neighbours, and whenever it finds an unvisited one, records its distance as one more than the current vertex's and enqueues it. The queue is FIFO, so a vertex is discovered by the closest possible predecessor, and its recorded distance is therefore the true shortest.

Time and space. Every vertex is enqueued at most once, and every edge is examined once from each endpoint (twice total for an undirected graph), so the time is O(V + E). The distance vector is O(V), and the queue holds at most O(V) vertices. BFS is linear in the size of the graph, which is the best any traversal can do, since it must at least look at every vertex and edge.

Edge cases. The source is distance 0 from itself. Vertices in other connected components stay at −1, which is the correct report: they are unreachable. A graph with no edges gives every non-source vertex −1. Negative distances never arise, so a signed type for `dist` is natural, and the −1 sentinel is safe because real distances are non-negative. If the graph is weighted, BFS's distances are wrong. It counts edges, not weights, and what you want is Dijkstra.

A variation. To reconstruct the actual shortest path rather than just its length, keep a `parent` vector alongside `dist` and record `parent[v] = u` when you discover v. Then walk backward from any target to the source. This "parent pointer" trick is how route-finding programs produce not just "how far" but "which way." It costs only O(V) memory.

31.3 DFS: Connected Components and Cycle Detection

The problem. Two tasks that share one algorithm. First, count the connected components of an undirected graph (the groups of mutually reachable vertices). Second, detect whether a directed graph contains a cycle.

Picture this. Connected components are groups of islands joined by bridges. Stand on one island and you can walk to some set of other islands and no further; that set is its component. To count components, visit every island you can from a starting point, then find the next one you have not visited and start again. Depth-first search is one way to do the walking. You go as deep as you can along one path before backing up, like exploring a maze by always taking the first unexplored corridor.

Brute force, then better. There is no better-than-linear way to visit every vertex, so DFS is the algorithm. Its shape is a recursion that marks the current vertex, then recurses into every unvisited neighbour. The recursion stack plays the role the queue played in BFS. Only the order of exploration differs.

    void dfsFrom(Graph* g, i32 u, Vec<bool>* visited) {
        // mark before recursing, or cycles never terminate
        visited->set((usize)u, true);
        Vec<i32>* neighbors = g->adj.atPtr((usize)u);
        for (usize i = 0; i < neighbors->count(); i += 1) {
            i32 v = neighbors->at(i);
            // recurse only into neighbours not yet seen
            if (!visited->at((usize)v)) {
                dfsFrom(g, v, visited);
            }
        }
    }

    i32 countComponents(Graph* g) {
        Vec<bool> visited = Vec<bool>::new();
        for (usize i = 0; i < g->n; i += 1) {
            visited.push(false);
        }
        // each restart from an unseen vertex is a new component
        i32 count = 0;
        for (usize u = 0; u < g->n; u += 1) {
            if (!visited.at(u)) {
                // count it, then flood-fill it away
                count += 1;
                dfsFrom(g, (i32)u, &visited);
            }
        }
        return count;
    }

`dfsFrom` visits one vertex and floods outward through every unvisited neighbour, marking as it goes. `countComponents` restarts that flood from every vertex not yet reached, and each restart is a new component. The `&visited` at each call is essential. The visited set must be the same set across the entire flood, not a fresh copy per call, or the algorithm revisits vertices forever.

For cycle detection in a directed graph, DFS needs to know more than "visited." A vertex is white (untouched), gray (on the current recursion path), or black (finished). A cycle exists exactly when an edge leads to a gray vertex, a back edge into the path we are still walking. An edge to a black vertex is harmless: that vertex is done and cannot close a loop back to us. Three named states, and never a fourth, is exactly what an enum is for (Chapter13):

    // white = untouched, gray = on the current path, black = done
    enum Color {
        White,
        Gray,
        Black,
    }

    bool dfsCycle(Graph* g, i32 u, Vec<Color>* state) {
        state->set((usize)u, Color::Gray);        // on the current path
        Vec<i32>* neighbors = g->adj.atPtr((usize)u);
        for (usize i = 0; i < neighbors->count(); i += 1) {
            i32 v = neighbors->at(i);
            // what state is this neighbour in?
            Color c = state->at((usize)v);
            if (c == Color::Gray) return true;    // back edge: a cycle
            // recurse only into vertices never explored
            if (c == Color::White && dfsCycle(g, v, state)) return true;
        }
        state->set((usize)u, Color::Black);       // finished
        return false;
    }

    bool hasCycle(Graph* g) {
        // every vertex starts white
        Vec<Color> state = Vec<Color>::new();
        for (usize i = 0; i < g->n; i += 1) {
            state.push(Color::White);
        }
        for (usize u = 0; u < g->n; u += 1) {
            // start a search from each still-uncoloured vertex
            if (state.at(u) == Color::White && dfsCycle(g, (i32)u, &state)) return true;
        }
        return false;
    }

The three-colour scheme is the whole idea, and it is worth stating plainly. White means "not yet explored." Gray means "currently on the path from the start." Black means "explored completely." An edge into gray closes a loop; an edge into black does not. Using an `enum` rather than bare integers means the comparison reads as the concept, `c == Color::Gray`, and a mistyped `2 == 3` can never masquerade as a colour test.

Time and space. Both algorithms visit every vertex once and every edge once, so both are O(V + E) time. The recursion stack is O(V) deep in the worst case (a long chain of vertices), and the visited or state array is O(V). That stack depth is why DFS on a very large graph may need an explicit stack instead of recursion, exactly as Chapter28 warned for deep trees.

Edge cases. An empty graph has zero components and no cycle. A graph of isolated vertices has one component per vertex and no cycle. For undirected cycle detection the three-colour scheme is wrong: the edge back to your own parent looks like a cycle. The usual fix is to ignore the parent when recursing. The directed version is what this code implements. A self-loop is a cycle of length one, and it is detected because the vertex is gray while examining its own edge.

A variation. DFS also produces a topological order of a directed acyclic graph: push each vertex onto a list after all its neighbours finish (a postorder), then reverse it. That is the DFS cousin of the queue-based topological sort in 30.4. Know both, because interviewers and libraries use both.

31.4 Topological Sort: An Order That Respects Dependencies

The problem. Given a directed acyclic graph, produce a linear ordering of the vertices such that every edge points from earlier to later. If the graph has a cycle, no such ordering exists, and the algorithm should say so. The motivating example is a build system: "compile A before B" is an edge A→B, and the topological order is a legal build order.

Picture this. You are getting dressed, and some garments depend on others: socks before shoes, shirt before jacket. You want a list of all garments in an order with no contradictions. Here is a workable rule. Repeatedly take any garment whose prerequisites are all already on, and add it to the list; removing it from the pile may free up others. If at some point nothing is free and items remain, those items depend on each other in a cycle, and no order exists.

Brute force, then better. The brute force builds an order by trial and error, which is exponential. Kahn's algorithm is the elegant linear method. Count each vertex's incoming edges (its "indegree"), repeatedly output a vertex with indegree zero, and decrement its neighbours' indegrees as if removing it. A vertex becomes available exactly when its last prerequisite has been removed.

    bool topologicalSort(Graph* g, Vec<i32>* order) {
        // indegree[v] counts v's not-yet-removed prerequisites
        Vec<i32> indegree = Vec<i32>::new();
        for (usize i = 0; i < g->n; i += 1) {
            indegree.push(0);
        }
        for (usize u = 0; u < g->n; u += 1) {
            Vec<i32>* neighbors = g->adj.atPtr(u);
            for (usize i = 0; i < neighbors->count(); i += 1) {
                i32 v = neighbors->at(i);
                // every edge u->v adds one prerequisite to v
                indegree.set((usize)v, indegree.at((usize)v) + 1);
            }
        }
        // seed the queue with vertices that have no prerequisites
        Queue<i32> q = Queue<i32>::new();
        for (usize u = 0; u < g->n; u += 1) {
            if (indegree.at(u) == 0) q.enqueue((i32)u);
        }
        while (!q.isEmpty()) {
            i32 u = q.dequeue();
            // emit u into the topological order
            order->push(u);
            Vec<i32>* neighbors = g->adj.atPtr((usize)u);
            for (usize i = 0; i < neighbors->count(); i += 1) {
                i32 v = neighbors->at(i);
                // removing u satisfies one prerequisite of v
                indegree.set((usize)v, indegree.at((usize)v) - 1);
                // v's last prerequisite is gone, so it is free
                if (indegree.at((usize)v) == 0) {
                    q.enqueue(v);
                }
            }
        }
        // a short order means a cycle locked some vertices
        return order->count() == g->n;
    }

The first pass computes every vertex's indegree by walking all edges. The queue is seeded with the zero-indegree vertices, the ones with no prerequisites, which may be one or many. The main loop removes a vertex, appends it to the order, and "deletes" its outgoing edges by decrementing each neighbour's indegree. A neighbour whose count hits zero has had all its prerequisites satisfied, so it is enqueued. The final check is the clever part. If the order does not contain every vertex, some vertices never became free, and that can only happen if they are locked in a cycle. One pass detects acyclicity, with no separate cycle check.

Time and space. Computing indegrees is O(V + E), and the main loop processes each vertex and edge once, so the total is O(V + E). The indegree vector is O(V) and the queue is O(V). If the graph has several valid topological orders, the algorithm returns one of them; the order vertices were enqueued breaks the tie, and that is deterministic for a given input.

Edge cases. An empty graph produces an empty order and reports success. A graph with a cycle produces an order shorter than V and returns false, the correct "impossible" signal. Multiple valid orders are expected, not a bug; any of them is a correct answer. Self-loops are immediate cycles: a vertex with a self-edge has indegree at least one and can never be freed.

A variation. The DFS postorder version of topological sort (mentioned in 30.3) pushes vertices after their descendants finish, then reverses the result. Its advantage is that it comes for free if you are already doing a DFS. Its disadvantage: detecting a cycle requires the three-colour machinery of 30.3, whereas Kahn's detects it from the output length alone. 30.9 shows the canonical application, deciding whether a set of courses can all be taken given their prerequisites.

31.5 Dijkstra: Shortest Paths with Positive Weights

The problem. Given a weighted graph with non-negative edge weights and a source vertex, find the length of the shortest path from the source to every other vertex.

Picture this. You are driving between cities, and each road has a travel time. The shortest route to a city is the shortest route to one of its neighbours, plus the road from that neighbour, minimised over all neighbours. That is optimal substructure again, and it suggests DP. But the graph has no natural order for filling a table, because a city can be reached through any of many predecessors. Dijkstra's insight is to always finalise the nearest unfinalised vertex next, which turns the unordered graph into an ordered process.

Brute force, then better. The brute-force way to find shortest paths is to consider all paths, which is exponential because of loops. A simpler correct method, Bellman–Ford, relaxes every edge V−1 times and handles even negative weights, at O(V × E). Dijkstra is faster, O((V + E) log V), but only for non-negative weights. It uses a priority queue to always pull the vertex with the smallest tentative distance, the one whose distance can no longer improve.

    struct Edge {
        i32 to;
        i32 weight;
    }

    struct QNode {
        i64 dist;
        i32 node;
    }

    bool qNodeLess(QNode a, QNode b) {
        return a.dist < b.dist;
    }

    void dijkstra(Vec<Vec<Edge>>* adj, usize n, i32 source, Vec<i64>* dist) {
        i64 infinity = 1000000000000000000;      // a stand-in for "unreachable"
        for (usize i = 0; i < n; i += 1) {
            dist->push(infinity);
        }
        // the source costs nothing to reach
        dist->set((usize)source, 0);
        // the smallest tentative distance always comes out first
        PriorityQueue<QNode> pq = PriorityQueue<QNode>::new(qNodeLess);
        pq.push(QNode { .dist = 0, .node = source });
        while (!pq.isEmpty()) {
            QNode top = pq.pop();
            i32 u = top.node;
            if (top.dist > dist->at((usize)u)) continue;   // a stale, outdated entry
            Vec<Edge>* neighbors = adj->atPtr((usize)u);
            for (usize i = 0; i < neighbors->count(); i += 1) {
                Edge e = neighbors->at(i);
                // cost of reaching e.to by going through u
                i64 candidate = top.dist + (i64)e.weight;
                // relax the edge if this route is shorter
                if (candidate < dist->at((usize)e.to)) {
                    dist->set((usize)e.to, candidate);
                    // remember the improvement for a later pop
                    pq.push(QNode { .dist = candidate, .node = e.to });
                }
            }
        }
    }

The `dist` vector holds the best known distance to each vertex, starting at infinity for all but the source, which is distance 0. The priority queue is ordered so the smallest distance comes out first, and it holds pairs of (tentative distance, vertex). Pulling the smallest such pair finalises that vertex: because all weights are non-negative, no later path can ever be shorter, so its distance is settled. Then the algorithm "relaxes" each outgoing edge. If going through u gives a shorter route to a neighbour, record it and push the new pair. The line `if (top.dist > dist->at(u)) continue;` discards stale entries, pairs that were pushed before a better distance was found. That is the standard "lazy deletion" approach, and it avoids needing a decrease-key operation on the heap.

Time and space. Each edge causes at most one push, so there are O(E) heap operations, each O(log E), and the total is O((V + E) log V). The distance array and heap are O(V) and O(E). The log factor is the price of always knowing the nearest unfinished vertex. Without a heap, Dijkstra is O(V^2), which is fine for dense graphs and worse for sparse ones.

Edge cases. Unreachable vertices stay at infinity, which is the correct report. The non-negative-weight requirement is a hard precondition. With a negative edge, a "finalised" vertex might later be improved, and the algorithm silently returns wrong answers. If negative weights are possible, use Bellman–Ford. Distances are i64 even though weights are i32, which prevents overflow when many edges are added and provides a safe infinity. A single-vertex graph returns just the source at distance 0.

A variation. Dijkstra returns distance only. To return the path, add a `parent` array set when a vertex's distance improves, then walk backward from the target. This is the same parent-pointer trick as BFS. A* is Dijkstra plus a heuristic that estimates distance to the goal, which lets it explore toward the target instead of uniformly in all directions. It is the algorithm inside most game pathfinding, and a direct extension of this one.

31.6 Union-Find: Keeping Track of Groups

The problem. Maintain a collection of disjoint groups that changes over time. Support two operations: `find(x)`, which reports which group x is in, and `unite(a, b)`, which merges the groups containing a and b. A third operation, "are a and b in the same group," falls out of `find`.

Picture this. You are running a mixer and people keep forming into conversation circles. `find(person)` asks which circle someone is in. `unite(a, b)` merges two circles when their members start talking. To answer quickly, you do not reassign everyone's group label by hand. Instead each circle has one designated leader, and every person remembers only who told them which circle they were in, a pointer toward the leader. To find someone's circle, follow the pointers to the leader. Merging two circles just points one leader at the other.

Brute force, then better. The naive method relabels every member when two groups merge, which is O(n) per merge and O(n^2) overall. Union-find keeps the labels indirect: each element points to a parent, and only the roots are meaningful group labels. Two refinements make it fast. Union by rank attaches the smaller tree under the larger, keeping trees shallow. Path compression, during `find`, points every element on the path directly at the root, flattening the tree for future lookups.

    struct DSU {
        // parent[x] points toward x's group root
        Vec<i32> parent;
        // rank is an upper bound on the depth of a tree
        Vec<i32> rank;

        static DSU new(usize n) {
            DSU d = DSU {
                .parent = Vec<i32>::new(),
                .rank = Vec<i32>::new()
            };
            for (usize i = 0; i < n; i += 1) {
                d.parent.push((i32)i);            // each element starts as its own root
                d.rank.push(0);
            }
            return d;
        }

        i32 find(i32 x) {
            // first pass: walk up to the root
            i32 root = x;
            while (self.parent.at((usize)root) != root) {
                root = self.parent.at((usize)root);
            }
            // second pass: flatten the path straight to the root
            i32 cur = x;
            while (self.parent.at((usize)cur) != root) {
                i32 next = self.parent.at((usize)cur);
                self.parent.set((usize)cur, root);   // compress: point straight at the root
                cur = next;
            }
            return root;
        }

        bool unite(i32 a, i32 b) {
            // find the roots of both elements
            i32 ra = self.find(a);
            i32 rb = self.find(b);
            if (ra == rb) return false;              // already together
            i32 rankA = self.rank.at((usize)ra);
            i32 rankB = self.rank.at((usize)rb);
            // hang the shallower tree under the deeper one
            if (rankA < rankB) {
                self.parent.set((usize)ra, rb);
            } else if (rankA > rankB) {
                self.parent.set((usize)rb, ra);
            } else {
                self.parent.set((usize)rb, ra);
                // tie: only here does depth grow
                self.rank.set((usize)ra, rankA + 1);
            }
            return true;
        }
    }

Each element's `parent` points to another element; a root points to itself, which is how you recognise it. `find` walks up to the root (first loop), then walks the same path again and repoints every element directly at the root (second loop), the compression that keeps future finds short. `unite` finds both roots and hangs the shallower tree under the deeper one, using `rank` as a proxy for depth. Only when the ranks tie does the depth actually increase, and the rank is bumped. The `false` return when the roots already match reports that a and b were already connected, which is exactly what Kruskal's algorithm needs.

Time and space. With both union by rank and path compression, the amortised cost of each operation is O(α(n)), the inverse Ackermann function, which stays below 5 for every n that fits in the universe. For all practical purposes, that is O(1). The storage is O(n) for the two arrays. Union-find is one of the rare data structures whose analysis is a genuine theorem, and the surprising conclusion is that its operations are effectively free.

Edge cases. Every element starts in its own singleton group, which is why `new(n)` initialises n groups. `find` on an out-of-range index is a bug the code does not guard, so callers must respect the bounds. A `unite(a, a)` returns false because the roots already match. The rank array is only a heuristic. Omit path compression and you still get O(log n) per operation. Omit union by rank and the worst case can become O(n), so keep both.

A variation. Union-find answers "connected?" for a graph as edges are added, which is the online version of 30.3's connected components. If the graph only ever grows, union-find is faster and simpler than re-running DFS for each query. If edges can also be removed, neither union-find nor DFS handles it directly, and you need a more elaborate structure. A good reminder that every data structure has a direction it does not go.

31.7 Kruskal's Minimum Spanning Tree

The problem. Given a connected undirected weighted graph, find a subset of edges that connects all vertices with the minimum possible total weight. Such a subset is always a tree (it has exactly V−1 edges and no cycles) and is called a minimum spanning tree.

Picture this. You are wiring a new office. Every desk must be reachable from the network, but cable is expensive and you never want to run more than you must. You consider all possible cables in order of cost, cheapest first, and lay each one down if it connects two previously separate clusters. When a cable would just loop back into an already-connected cluster, you skip it. The cheapest cables come first, and the "skip anything that closes a loop" rule guarantees you never pay for a redundant connection.

Brute force, then better. Trying every subset of V−1 edges is exponential. Kruskal's algorithm is greedy and correct: sort the edges by weight, then add each to the tree unless it would create a cycle. The "would it create a cycle" test is exactly union-find's `unite`-returns-false test, and that is what makes Kruskal fast.

    struct WEdge {
        i32 u;
        i32 v;
        i32 weight;
    }

    bool wEdgeLess(WEdge a, WEdge b) {
        return a.weight < b.weight;
    }

    i64 kruskal(usize n, Vec<WEdge>* edges) {
        if (n == 0) return 0;
        // cheapest edges first
        edges->sortBy(wEdgeLess);
        // tracks what is already connected
        DSU dsu = DSU::new(n);
        i64 total = 0;
        usize used = 0;
        for (usize i = 0; i < edges->count(); i += 1) {
            WEdge e = edges->at(i);
            // unite is false when this edge would close a cycle
            if (dsu.unite(e.u, e.v)) {
                total += (i64)e.weight;
                used += 1;
                if (used == n - 1) break;         // a spanning tree has n-1 edges
            }
        }
        if (n > 0 && used != n - 1) return -1;    // the graph was not connected
        return total;
    }

The algorithm is almost entirely in its two lines of English. Sorting by weight puts the cheap edges first. The loop tries each edge; `unite` returns true only when the edge joins two different components, in which case the edge is added and the running total updated. The moment n−1 edges have been added, the tree is complete and the loop breaks early. If the loop finishes without reaching n−1, some vertices were never connectable, and −1 reports exactly that.

Time and space. The sort is O(E log E), and the loop does at most E union-find operations, each effectively O(1), so the total is O(E log E). The space is O(V + E) for the graph and the DSU arrays. Kruskal is the sort-heavy MST algorithm, and it is the right choice when the edge list is what you have. When the adjacency structure is already in hand, Prim (30.8) may fit better.

Why greedy works here. The cut property: for any partition of the vertices into two non-empty sets, the cheapest edge crossing the cut belongs to some minimum spanning tree. Kruskal's "add the cheapest edge that connects two components" is always adding a cheapest crossing edge for the cut between those components, so it never makes an unsafe choice. As with interval scheduling, the correctness rests on a proof, and the proof is what separates a greedy algorithm from a greedy guess.

Edge cases. An empty or single-vertex graph has total 0 with no edges. A disconnected graph cannot have a spanning tree, so the function returns −1. Negative weights are fine. Kruskal never relies on weights being positive, only on their order. Duplicate edges of equal weight are fine: whichever is tried first may be taken, and the total is the same. Self-loops are rejected automatically, because `unite(u, u)` returns false.

A variation. The maximum spanning tree is the same algorithm with the sort reversed. One character changes and the greedy proof flips with it. And if the graph is complete and you want the MST by edge count rather than weight, Kruskal still works, but Prim with a heap is often the faster implementation in practice.

31.8 Prim's Minimum Spanning Tree

The problem. The same minimum spanning tree as 30.7, but grown differently: start from one vertex and repeatedly add the cheapest edge that reaches a vertex not yet in the tree.

Picture this. You are lighting a town street by street, and you can only build from where you already have power. You start at one house, and at each step you light the nearest dark house reachable by a single wire from the lit area. The lit region grows like a snowball, and the wire you add each time is the cheapest one joining lit to dark. When every house is lit, the wires you laid are an MST.

Brute force, then better. The brute force for the next cheapest crossing edge is a linear scan of all edges, giving O(V^2) for the whole algorithm. A priority queue turns each step's scan into a heap extraction. Push every edge from the newly lit house to a dark one, then pop the cheapest overall, skipping edges whose dark endpoint has since been lit. That gives O((V + E) log V).

    i64 prim(Vec<Vec<Edge>>* adj, usize n) {
        if (n == 0) return 0;
        // which vertices have already joined the tree
        Vec<bool> inTree = Vec<bool>::new();
        for (usize i = 0; i < n; i += 1) {
            inTree.push(false);
        }
        PriorityQueue<QNode> pq = PriorityQueue<QNode>::new(qNodeLess);
        pq.push(QNode { .dist = 0, .node = 0 });       // start anywhere; no edge is "free"
        // running weight of the tree
        i64 total = 0;
        // vertices joined so far
        i32 reached = 0;
        while (!pq.isEmpty() && reached < (i32)n) {
            QNode top = pq.pop();
            i32 u = top.node;
            if (inTree.at((usize)u)) continue;          // already connected; stale entry
            inTree.set((usize)u, true);
            total += top.dist;
            reached += 1;
            Vec<Edge>* neighbors = adj->atPtr((usize)u);
            for (usize i = 0; i < neighbors->count(); i += 1) {
                Edge e = neighbors->at(i);
                // offer each still-dark neighbour as a candidate
                if (!inTree.at((usize)e.to)) {
                    pq.push(QNode { .dist = (i64)e.weight, .node = e.to });
                }
            }
        }
        // not every vertex joined: the graph was disconnected
        if (reached != (i32)n) return -1;
        return total;
    }

The priority queue holds (cost of the edge that would reach this vertex, vertex). It starts with the source at cost 0, an artificial "edge" so the source is added first. Each iteration pops the cheapest way to reach a new vertex. If that vertex is already in the tree, the entry is stale and gets discarded. Otherwise the vertex joins the tree, its incoming cost is added to the total, and all its edges to still-dark neighbours are pushed as candidate ways in. The `reached` counter double-checks that every vertex made it in; if one did not, the graph is disconnected and −1 is returned.

Time and space. Each edge is pushed at most once from each endpoint, so up to twice, and each heap operation is O(log V), for O((V + E) log V). The space is O(V + E). On dense graphs, where E is around V^2, the heap version's advantage over the O(V^2) scan shrinks, and implementations sometimes switch. On sparse graphs the heap version is clearly better.

Edge cases. An empty graph returns 0. A disconnected graph returns −1 because `reached` falls short. A start vertex is arbitrary; the MST total is the same whichever vertex you begin from. Negative edges are handled correctly, as in Kruskal. The `dist = 0` initial entry is a harmless seed, not a real edge, so it contributes nothing to the total.

A variation. Dijkstra and Prim are nearly the same code, and the difference is worth spotting. Dijkstra's heap key is the total distance from the source; Prim's key is the weight of the single edge that reaches the vertex. One accumulates a path cost, the other just takes the cheapest connecting edge. Same priority queue, same loop shape, different meaning of the key. It is a small change with a large conceptual distance, and a good test of whether you have understood both.

31.9 A Worked Application: Course Schedule

The problem. Given the number of courses and a list of prerequisite pairs [a, b] meaning "b must be taken before a," decide whether it is possible to finish every course. This is LeetCode's "Course Schedule," and it is pure topological sort in disguise.

Picture this. You are planning a degree, and some courses list prerequisites. You want to know if there is an order that satisfies everyone. If two courses each require the other, a circular prerequisite, then no schedule exists and the answer is no. Otherwise some order exists, and it is exactly a topological order of the prerequisite graph.

Brute force, then better. The brute force tries every possible order of courses and checks them, which is factorial. The graph formulation reduces it instantly. Build a directed edge from each prerequisite to the course that requires it, then run Kahn's algorithm. The graph is schedulable exactly when the topological sort includes every vertex.

    bool canFinish(i32 numCourses, Vec<Vec<i32>>* prerequisites) {
        Graph g = Graph::new((usize)numCourses);
        // one directed edge per prerequisite pair
        for (usize i = 0; i < prerequisites->count(); i += 1) {
            Vec<i32>* pair = prerequisites->atPtr(i);
            i32 course = pair->at(0);
            i32 prereq = pair->at(1);
            g.addDirectedEdge(prereq, course);       // prereq -> course
        }
        Vec<i32> order = Vec<i32>::new();
        // schedulable exactly when every course makes it into the order
        return topologicalSort(&g, &order);
    }

The function builds the graph, adding one directed edge per prerequisite in the direction "must come first → depends on it," then delegates entirely to `topologicalSort`, whose boolean return is exactly the answer. `prerequisites->atPtr(i)` returns a pointer to the pair, so the inner vector is read without copying. If a cycle exists, whether two courses requiring each other or a longer loop, Kahn's algorithm cannot free every vertex, `order` comes up short, and the function returns false.

Time and space. Building the graph is O(V + E), and the topological sort is O(V + E), so the whole thing is O(V + E) time and O(V + E) space, where V is the number of courses and E the number of prerequisite pairs. An exponential problem became linear because the right structure, a directed graph ordering, was recognised.

Edge cases. Zero courses is trivially finishable: empty order, returns true. Zero prerequisites means every course is independent, so every course is emitted immediately. Duplicate prerequisites are harmless; they only add parallel edges, and the indegree counts them twice, which still works out. A self-prerequisite, a course requiring itself, is an immediate cycle and returns false.

A variation. The natural follow-up, "Course Schedule II," asks for an actual order rather than a yes or no. The answer is the `order` vector Kahn's algorithm already builds. When the function returns true, `order` is a valid schedule; when false, `order` holds the courses that could be freed before the cycle was hit. This is a recurring pattern. The decision version and the construction version share all their machinery, and the construction just hands you the object the decision ignored.

31.10 A Worked Application: Number of Islands

The problem. Given a 2D grid of '1' (land) and '0' (water), count the islands, where an island is a group of land cells connected horizontally or vertically (not diagonally).

Picture this. A satellite image with land and sea, and you want to count the continents. You scan cell by cell. When you hit land, you have found a new island; then you flood the whole island so you never count it again, walking from each land cell to its four neighbours and marking everything reachable. Each flood is one island.

Brute force, then better. The brute force checks every land cell against every other to group them, which is quadratic in the number of cells and easy to get wrong. The graph view makes it linear. Each land cell is a vertex connected to its land neighbours, so counting islands is counting connected components: 30.3's problem on a grid, where the neighbours are the four adjacent cells instead of an adjacency list.

    import(lib) std::collections::queue { Queue };

    void exploreDir(Vec<str>* grid, Vec<bool>* visited, Queue<i64>* q, i64 r, i64 c, usize rows, usize cols) {
        // reject negative coordinates
        if (r < 0 || c < 0) return;
        // reject off-grid coordinates
        if ((usize)r >= rows || (usize)c >= cols) return;
        usize flat = (usize)r * cols + (usize)c;
        if (visited->at(flat)) return;
        str row = grid->at((usize)r);
        // water, not land
        if (row.at((usize)c) != (u8)'1') return;
        visited->set(flat, true);
        q->enqueue((i64)flat);
    }

    void floodFill(Vec<str>* grid, Vec<bool>* visited, usize sr, usize sc, usize rows, usize cols) {
        Queue<i64> q = Queue<i64>::new();
        visited->set(sr * cols + sc, true);
        q.enqueue((i64)(sr * cols + sc));
        // expand until the whole island is consumed
        while (!q.isEmpty()) {
            i64 flat = q.dequeue();
            i64 r = flat / (i64)cols;
            i64 c = flat % (i64)cols;
            exploreDir(grid, visited, &q, r - 1, c, rows, cols);
            exploreDir(grid, visited, &q, r + 1, c, rows, cols);
            exploreDir(grid, visited, &q, r, c - 1, rows, cols);
            exploreDir(grid, visited, &q, r, c + 1, rows, cols);
        }
    }

    i32 numIslands(Vec<str>* grid) {
        usize rows = grid->count();
        // an empty grid has no islands
        if (rows == 0) return 0;
        str firstRow = grid->at(0);
        usize cols = firstRow.len;
        Vec<bool> visited = Vec<bool>::new();
        for (usize i = 0; i < rows * cols; i += 1) {
            visited.push(false);
        }
        // one flood per island discovered
        i32 count = 0;
        for (usize i = 0; i < rows; i += 1) {
            for (usize j = 0; j < cols; j += 1) {
                str row = grid->at(i);
                if (row.at(j) == (u8)'1' && !visited.at(i * cols + j)) {
                    count += 1;
                    // consume this island so it is never counted again
                    floodFill(grid, &visited, i, j, rows, cols);
                }
            }
        }
        return count;
    }

The grid is stored as a `Vec<str>`, one string per row. `str` is a borrowed view, so reading a row never copies the data and never risks the double-free that copying an owning `Vec` would. The `visited` flag is a single flat `Vec<bool>` indexed by `r * cols + c`, which is faster and smaller than a vector of vectors. `floodFill` is BFS from a starting cell: mark it, enqueue it, then repeatedly dequeue a cell and try its four neighbours through `exploreDir`, which bounds-checks, skips visited cells, skips water, and marks and enqueues land. `numIslands` calls `floodFill` once per unvisited land cell, and each call consumes a whole island.

Time and space. Every cell is examined a constant number of times: once by the outer scan, at most four times as a neighbour. So the total time is O(rows × cols), linear in the size of the grid. The visited vector is O(rows × cols), and the BFS queue holds at most that many cells. This is the graph O(V + E) bound with V = cells and E at most 4V, so O(V).

Edge cases. An empty grid returns 0. A grid that is all water returns 0, and the inner condition never fires. A single land cell is one island. Diagonal land does not connect, by the problem's definition; if diagonals counted, four more `exploreDir` calls would be added. A grid whose rows have different lengths would break the flat indexing. The problem guarantees a rectangular grid, and the code assumes it.

A variation. The same flood fill answers "maximum island area" (count the cells the flood consumes and track the maximum), "perimeter of an island" (count exposed cell edges), and "number of closed islands" (an island not touching the border). The graph is identical; only what you do during the flood changes. That is the signature of a well-chosen model: the hard part, the traversal, is shared, and the different questions are small variations on what the traversal records.

31.11 Bipartite Check (Two-Colouring)

The problem. Given an undirected graph, decide whether its vertices can be coloured with two colours so that every edge joins opposite colours. Such a graph is called bipartite.

Picture this. You want to split a group of people into two teams so that no two people who dislike each other share a team. You put one person on team A, then everyone they dislike must go to team B, then everyone each of those dislikes must go back to A, and so on, alternating. If you ever meet someone who would have to be on both teams at once, no such split exists.

Brute force, then better. The brute force tries all 2^V colourings, which is exponential. A single BFS does it in linear time: colour a starting vertex, then flood outward, giving every neighbour the opposite of its parent's colour. The first contradictory edge, one joining two vertices of the same colour, proves the graph is not bipartite.

    import(lib) std::vec { Vec };
    import(lib) std::collections::queue { Queue };

    bool isBipartite(Vec<Vec<i32>>* adj) {
        usize n = adj->count();
        Vec<i32> color = Vec<i32>::new();
        for (usize i = 0; i < n; i += 1) {
            color.push(-1);                  // -1 means "not coloured yet"
        }
        // restart per component so disconnected graphs are handled
        for (usize start = 0; start < n; start += 1) {
            if (color.at(start) != -1) continue;
            // colour the component's seed 0
            color.set(start, 0);
            Queue<i32> q = Queue<i32>::new();
            q.enqueue((i32)start);
            while (!q.isEmpty()) {
                i32 u = q.dequeue();
                Vec<i32>* neighbors = adj->atPtr((usize)u);
                for (usize i = 0; i < neighbors->count(); i += 1) {
                    i32 v = neighbors->at(i);
                    // an uncoloured neighbour gets the opposite colour
                    if (color.at((usize)v) == -1) {
                        color.set((usize)v, 1 - color.at((usize)u));
                        q.enqueue(v);
                    } else if (color.at((usize)v) == color.at((usize)u)) {
                        return false;        // an edge inside one colour: not bipartite
                    }
                }
            }
        }
        return true;
    }

The `color` vector holds 0, 1, or the −1 sentinel for "uncoloured". The outer loop restarts the flood from every vertex not yet coloured, and that is what makes the check correct on a disconnected graph: each component is coloured independently and all of them must pass. Inside the flood, an uncoloured neighbour receives the opposite colour and is enqueued; a neighbour that is already coloured must be the opposite, and if it is not, an edge joins two equal colours and the answer is false. The expression `1 - color` flips neatly between 0 and 1.

Time and space. Every vertex is enqueued once and every edge is examined once from each endpoint, so O(V + E) time, with the colour array and queue at O(V). This is BFS with one extra check, so the cost is exactly BFS's.

Edge cases. An empty graph is bipartite, since there is nothing to colour. A self-loop makes the graph not bipartite, because a loop joins a vertex to itself and its two ends would need opposite colours; the same-colour test catches it. Any graph containing an odd-length cycle is not bipartite, and the colouring discovers that exactly when it reaches the edge that closes the odd cycle. A graph with no edges is bipartite: each component is a lone vertex.

A variation. The two colours are exactly the two sides of a partition, so the same code produces the split when the answer is true: collect the vertices by colour. Checking bipartiteness is equivalent to checking for no odd cycle, and one useful special case is that every tree is bipartite, which is a handy fact when a problem's graph turns out to be a tree.

31.12 Multi-Source BFS

The problem. In a grid, some cells start "rotten" and the rest "fresh". Every minute, each rotten cell infects its fresh horizontal and vertical neighbours. Report the number of minutes until no fresh cell remains, or −1 if some fresh cell can never be reached.

Picture this. Several fires break out at once in different parts of a field, and each minute the fire spreads one step in every direction. Because there is no single source, all the rotten cells are sources from the first minute and their fronts advance together. The time a cell catches fire is the smallest of its distances to any source, which is precisely what a BFS started from all the sources at once computes.

Brute force, then better. Running BFS once from every rotten cell and taking the per-cell minimum is O(V × (V + E)), quadratic and wasteful. The better method seeds the queue with every rotten cell before the main loop begins. BFS processes cells in non-decreasing distance order, so the first time a fresh cell is reached it is by the nearest source, and one pass does the whole job.

    import(lib) std::vec { Vec };
    import(lib) std::collections::queue { Queue };

    void rotCell(Vec<Vec<i32>>* grid, Queue<i64>* q, i32* fresh, i64 nr, i64 nc, usize rows, usize cols) {
        // reject negative coordinates
        if (nr < 0 || nc < 0) return;
        // reject off-grid coordinates
        if ((usize)nr >= rows || (usize)nc >= cols) return;
        if (grid->atPtr((usize)nr)->at((usize)nc) != 1) return;   // not fresh
        grid->atPtr((usize)nr)->set((usize)nc, 2);                // rot it
        *fresh -= 1;
        q->enqueue(nr * (i64)cols + nc);
    }

    i32 orangesRotting(Vec<Vec<i32>>* grid) {
        usize rows = grid->count();
        if (rows == 0) return 0;
        usize cols = grid->atPtr(0)->count();
        Queue<i64> q = Queue<i64>::new();
        i32 fresh = 0;
        for (usize r = 0; r < rows; r += 1) {
            for (usize c = 0; c < cols; c += 1) {
                i32 cell = grid->atPtr(r)->at(c);
                if (cell == 2) {
                    q.enqueue((i64)(r * cols + c));               // every source at once
                } else if (cell == 1) {
                    fresh += 1;
                }
            }
        }
        // counts rounds of simultaneous spread
        i32 minutes = 0;
        // stop once the last fresh cell rots
        while (!q.isEmpty() && fresh > 0) {
            // snapshot: one whole BFS level per minute
            usize levelSize = q.count();
            for (usize k = 0; k < levelSize; k += 1) {
                i64 flat = q.dequeue();
                i64 r = flat / (i64)cols;
                i64 c = flat % (i64)cols;
                rotCell(grid, &q, &fresh, r - 1, c, rows, cols);
                rotCell(grid, &q, &fresh, r + 1, c, rows, cols);
                rotCell(grid, &q, &fresh, r, c - 1, rows, cols);
                rotCell(grid, &q, &fresh, r, c + 1, rows, cols);
            }
            // finishing a level is one minute
            minutes += 1;
        }
        // some fresh cell was unreachable
        if (fresh > 0) return -1;
        return minutes;
    }

All rotten cells enter the queue before anything is processed, and that seeding is the entire difference from ordinary BFS. The `fresh` counter lets the loop stop as soon as the last fresh cell rots and also detects the impossible case. The inner loop drains one whole BFS level, and `minutes` is incremented once per level, so it counts rounds of simultaneous spread rather than individual cell steps. `rotCell` mirrors the four-neighbour flood of 30.10: it bounds-checks, ignores anything that is not fresh, and otherwise rots the cell, decrements the counter, and enqueues it.

Time and space. Each cell enters the queue at most once and is examined by at most four neighbour checks, so O(rows × cols) time. The queue and counters are O(rows × cols) in the worst case, and `minutes` is at most that. The rot is written into the grid itself, which doubles as the visited marker.

Edge cases. A grid with no fresh cells returns 0 at once, because the loop condition `fresh > 0` is false from the start. A grid with no rotten cells returns −1 whenever any fresh cell exists, since the empty queue spreads nothing. Fresh cells walled off by empty cells stay fresh, and the final check reports −1. An empty grid returns 0. If the original grid must be preserved, keep a separate visited array instead of rotting in place.

A variation. Multi-source BFS answers every "nearest source" question: distance to the nearest hospital, the time for a flood to cover a map, the number of rounds for an infection with several index cases. The whole trick is to seed every source before the loop, which turns a search per source into a single pass.

31.13 Bellman-Ford: Negative Edge Weights

The problem. Given a directed weighted graph and a source, find the shortest distance to every vertex while allowing negative edge weights, and report whether a negative cycle is reachable from the source.

Picture this. Dijkstra finalises a vertex the moment it is popped, trusting that no later path can be shorter, and that trust needs every edge to be non-negative. Bellman-Ford assumes nothing about the signs. It simply relaxes every edge again and again: if the path to u is known and the edge u→v shortens the path to v, update v. Each full pass extends the reach of known-shortest paths by one more edge, so after V−1 passes every simple path has been considered.

Brute force, then better. The brute force considers all paths, exponential. Bellman-Ford is the systematic version: V−1 rounds of relaxing every edge, which is O(V × E). It is slower than Dijkstra on non-negative graphs but strictly more general, and it is the tool that detects negative cycles.

    struct WEdge {
        i32 u;
        i32 v;
        i32 weight;
    }

    bool bellmanFord(i32 n, Vec<WEdge>* edges, i32 source, Vec<i64>* dist) {
        i64 infinity = 1000000000000000000;
        for (i32 i = 0; i < n; i += 1) {
            dist->push(infinity);
        }
        // the source costs nothing
        dist->set((usize)source, 0);
        // V-1 rounds cover every simple path
        for (i32 round = 0; round < n - 1; round += 1) {
            bool changed = false;
            for (usize e = 0; e < edges->count(); e += 1) {
                WEdge edge = edges->at(e);
                i64 du = dist->at((usize)edge.u);
                if (du == infinity) continue;             // u is not reachable yet
                i64 candidate = du + (i64)edge.weight;
                // relax: a shorter route through u
                if (candidate < dist->at((usize)edge.v)) {
                    dist->set((usize)edge.v, candidate);
                    changed = true;
                }
            }
            if (!changed) break;                          // no improvement: finish early
        }
        for (usize e = 0; e < edges->count(); e += 1) {
            WEdge edge = edges->at(e);
            i64 du = dist->at((usize)edge.u);
            if (du == infinity) continue;
            // still relaxable after all rounds means a negative cycle
            if (du + (i64)edge.weight < dist->at((usize)edge.v)) {
                return false;                             // still improvable: negative cycle
            }
        }
        return true;
    }

After k passes the distances are correct for every path that uses at most k edges, so V−1 passes cover every simple path, and a shortest path never needs to repeat a vertex unless a negative cycle exists. The `changed` flag ends the run early once a pass improves nothing. The final loop is the negative-cycle test: if any edge can still be relaxed after all the passes, a cycle of negative total weight is reachable from the source, and the shortest distances are undefined (they would be unbounded below).

Time and space. O(V × E) time in the worst case, and O(V) space for the distance array. The `du == infinity` guard matters on graphs with unreachable vertices, because adding a negative weight to the sentinel would otherwise manufacture a bogus reachable distance; the sentinel is chosen large enough that no real distance collides with it.

Edge cases. A single-vertex graph needs no relaxations and reports no negative cycle. An unreachable vertex keeps the sentinel. A negative cycle reachable from the source makes the function return false; a negative cycle the source cannot reach is irrelevant and is skipped by the reachability guard. Weights may be negative, zero, or positive.

A variation. When the graph is known to have no negative edges, Dijkstra is the better choice, with its heap and its O((V + E) log V). Bellman-Ford's other life is in distributed routing: a router can run it knowing only its own links and the estimates its neighbours send, which is essentially the distance-vector protocol.

31.14 Floyd-Warshall: All-Pairs Shortest Paths

The problem. Given a weighted directed graph, find the shortest distance between every pair of vertices at once, allowing negative edge weights but assuming no negative cycles.

Picture this. You have a road atlas and want the shortest route between every pair of cities, not merely from one city. The insight is to admit intermediate cities one at a time. First consider only direct roads; then allow city 0 as a possible stop; then allow city 1 as well; and so on. When every city has been allowed as an intermediate, every shortest route has been found, because the stops on any shortest route are some subset of the cities.

Brute force, then better. Running Dijkstra from every vertex is one option, but it cannot tolerate negative edges. Running Bellman-Ford from every vertex is O(V^2 × E), which is O(V^4) on a dense graph. Floyd-Warshall fills a single V × V table in O(V^3), and its three nested loops are the entire algorithm.

    import(lib) std::vec { Vec };

    void floydWarshall(Vec<Vec<i64>>* dist) {
        usize n = dist->count();
        // k is the set of vertices allowed as intermediates
        for (usize k = 0; k < n; k += 1) {
            for (usize i = 0; i < n; i += 1) {
                // best known path from i to k
                i64 throughK = dist->atPtr(i)->at(k);
                if (throughK == 1000000000000000000) continue;   // no path i..k yet
                for (usize j = 0; j < n; j += 1) {
                    // cost of routing i -> k -> j
                    i64 candidate = throughK + dist->atPtr(k)->at(j);
                    if (candidate < dist->atPtr(i)->at(j)) {
                        dist->atPtr(i)->set(j, candidate);
                    }
                }
            }
        }
    }

The table begins as the adjacency matrix: `dist[i][j]` is the direct edge weight, zero on the diagonal, and the large sentinel where no edge exists. The outer loop `k` is the set of vertices allowed as intermediates. For each pair `(i, j)` the code asks whether going through `k` beats the best route found so far, and updates if it does. The ordering is not incidental: `k` must be outermost, so that when `k` is processed the table already accounts for every lower-numbered intermediate, making `dist[i][k]` and `dist[k][j]` optimal over that smaller allowed set.

Time and space. Three nested loops over the vertices give Θ(V^3) time, and the table is V × V, so Θ(V^2) space. The cubic cost is fine up to a few hundred vertices and painful beyond; Dijkstra from each vertex is faster on sparse graphs, while Floyd-Warshall is the choice for dense graphs and for graphs that may have negative edges.

Edge cases. Vertices with no path between them keep the sentinel, and the `throughK == sentinel` check keeps two sentinels from being added into an overshoot. A negative cycle shows up as a negative entry on the diagonal after the run: if any `dist[i][i] < 0`, a negative cycle passes through i. Initialise the diagonal to 0 and non-edges to the sentinel, and guard the sentinel as shown, because it is a finite number and adding it carelessly can overflow.

A variation. The same triple loop computes transitive closure: swap the arithmetic for boolean reachability (`reach[i][j] = reach[i][j] || (reach[i][k] && reach[k][j])`) and it answers "is j reachable from i?". Swap `+` for `max` and `<` for `>` and it finds the minimax path. Recognising the triple-loop shape as a reusable engine is worth more than memorising any one application.

31.15 Word Ladder

The problem. Given a begin word, an end word, and a dictionary, transform the begin word into the end word one letter at a time, where every intermediate word must be in the dictionary and must differ from its predecessor by exactly one letter. Return the number of words in the shortest transformation, or 0 if none exists.

Picture this. Each word is a vertex, and two words are adjacent when they differ in exactly one letter. The shortest transformation is then a shortest path in an unweighted graph, which is BFS. Start from the begin word, expand to every dictionary word one letter away, and stop the moment the end word appears. The number of layers you passed through is the length of the shortest ladder.

Brute force, then better. The brute force builds the whole graph by comparing every pair of words for the one-letter difference, which is O(N^2 × L) just to build it, and then runs BFS. Since a word's neighbours can be generated on demand by scoring each unused dictionary word, the graph need not be built at all: BFS generates neighbours as it goes, and a visited flag stops a word from being enqueued twice.

    import(lib) std::vec { Vec };
    import(lib) std::collections::queue { Queue };

    bool oneLetterApart(str a, str b) {
        // different lengths cannot differ by one
        if (a.len != b.len) return false;
        usize diff = 0;
        for (usize i = 0; i < a.len; i += 1) {
            if (a.at(i) != b.at(i)) diff += 1;
            // already too different to recover
            if (diff > 1) return false;
        }
        return diff == 1;
    }

    i32 wordLadder(str begin, str end, Vec<str>* words) {
        usize n = words->count();
        Vec<bool> used = Vec<bool>::new();
        for (usize i = 0; i < n; i += 1) {
            used.push(false);
        }
        // BFS frontier of the ladder
        Queue<str> q = Queue<str>::new();
        q.enqueue(begin);
        // the begin word is the first rung
        i32 steps = 1;
        while (!q.isEmpty()) {
            usize levelSize = q.count();
            for (usize k = 0; k < levelSize; k += 1) {
                str cur = q.dequeue();
                // reached the target: report the ladder length
                if (cur.equals(end)) return steps;
                for (usize i = 0; i < n; i += 1) {
                    // never enqueue a word twice
                    if (used.at(i)) continue;
                    str w = words->at(i);
                    if (oneLetterApart(cur, w)) {
                        // mark before enqueueing
                        used.set(i, true);
                        q.enqueue(w);
                    }
                }
            }
            // finish a level, then count a new rung
            steps += 1;
        }
        return 0;
    }

The queue holds words and the `used` flags mark dictionary words already enqueued, so each word enters at most once. Rather than precomputing the graph, the inner loop scores every unused dictionary word against the current one with `oneLetterApart`, comparing byte by byte. The `levelSize` snapshot makes BFS finish a whole layer of the ladder before `steps` is increased, so `steps` counts words in the ladder rather than expansions. Checking for the end word on dequeue, rather than on enqueue, also handles the case where the begin word already equals the end word.

Time and space. Every dictionary word is dequeued once, and each dequeue scans the whole dictionary, so the time is O(N^2 × L) for N words of length L, the same asymptotic order as building the graph, but with far less memory and much simpler code. The queue and visited array are O(N).

Edge cases. If the begin word equals the end word, the first dequeue returns 1. If the end word is not in the dictionary it can never be enqueued, so the queue drains and the function returns 0. Words of different lengths cannot be one letter apart, which `oneLetterApart` reports at once. The dictionary need not contain the begin word, because the search starts from it regardless. All words are assumed to be the same length, as the problem guarantees.

A variation. For large dictionaries, generating a word's neighbours by changing each position through 'a'..'z' and looking up each result in a hash set is much faster than scanning the list, at the cost of a hash set and its key functions. Reconstructing the actual ladder rather than measuring it uses the parent-pointer trick of 30.2. Searching forward from the begin word and backward from the end word at the same time, bidirectional BFS, shrinks the explored set sharply and is the usual high-performance answer.

31.16 Clone a Graph

The problem. Given a connected undirected graph whose vertices are nodes holding a value and a list of neighbour pointers, produce a deep copy: new nodes with the same values and the same connectivity, sharing no node with the original.

Picture this. You are duplicating a web of friendships. You cannot simply copy one person's list of friends, because each friend must also be a fresh person whose own list points at the fresh versions. The trick is to keep a map from each original node to its copy: the first time you meet a node you make its copy and record it, and every later reference resolves to the recorded copy. That map is what stops the recursion from chasing a cycle forever.

Brute force, then better. Without a map, a recursive copy would follow an edge and then follow it back, looping forever on any cycle. The map breaks the cycle: each node is cloned once, the clone is recorded before its neighbours are visited, and any later visit returns the recorded clone. This is memoization applied to a graph traversal.

    import(lib) std::vec { Vec };
    import(lib) std::collections.hashmap { HashMap };
    import(lib) std::mman { alloc };

    struct GNode {
        i32 val;
        Vec<GNode*> neighbors;
    }

    usize hashI32(i32 k) { return (usize)k; }
    bool eqI32(i32 a, i32 b) { return a == b; }

    GNode* cloneNode(GNode* node, HashMap<i32, GNode*>* seen) {
        Option<GNode*> found = seen->get(node->val);
        if (found.isSome()) return found.unwrap();      // already cloned
        // allocate the fresh copy
        GNode* copy = alloc<GNode>(1);
        copy->val = node->val;
        copy->neighbors = Vec<GNode*>::new();
        seen->insert(node->val, copy);                  // record before recursing
        for (usize i = 0; i < node->neighbors.count(); i += 1) {
            // clone each neighbour; seen resolves cycles
            copy->neighbors.push(cloneNode(node->neighbors.at(i), seen));
        }
        return copy;
    }

    GNode* cloneGraph(GNode* start) {
        if (start == null) return null;
        HashMap<i32, GNode*> seen = HashMap<i32, GNode*>::new(hashI32, eqI32);
        return cloneNode(start, &seen);
    }

The map ties each original value to its copy. The order of the two middle lines is the whole trick: the copy goes into the map *before* the loop that visits the neighbours. Insert it afterward and a cycle would recurse back to the original node, fail to find a copy, and clone it again, forever. Inserting first means that when a neighbour's neighbour leads back to this node, the lookup returns the copy already under construction. `node->neighbors` is a `Vec<GNode*>` field reached through the pointer, and the same auto-dereferencing lets the count and the indexed read work.

Time and space. Every node is cloned once and every edge is crossed once in each direction, so O(V + E) time. The map holds one entry per vertex and each clone owns its neighbour list, so O(V + E) space, with recursion depth up to O(V) for a long path.

Edge cases. A null start returns null. A single node with no neighbours clones to a node with an empty neighbour list. Self-loops and repeated edges are copied as they are, because the algorithm duplicates each neighbour list faithfully rather than deduplicating. Keying the map by value assumes values are unique, which is the usual contract; if values could repeat, key by node identity (a pointer) instead.

A variation. The same clone-with-memo pattern copies any pointer-linked structure that contains cycles: linked lists with loops, doubly linked structures, persistent trees. An iterative version uses a queue: clone the start, put it in the map and the queue, then repeatedly dequeue, clone each not-yet-seen neighbour, and append the clone, recorded or fresh, to the current copy's list. Recursion and the explicit queue are the same traversal, with the bookkeeping moved from the call stack into a container.

1. Comprehension. Explain the difference between an adjacency list and an adjacency matrix in terms of both memory and the cost of the two most common operations: iterating a vertex's neighbours, and testing whether two vertices are adjacent. When is each the better choice?

2. Comprehension. BFS uses a queue and DFS uses a stack (or the recursion stack). Describe, in words, what each data structure does to the order in which vertices are explored, and give a problem where that order makes one of them correct and the other wrong.

3. Trace. Run BFS from vertex 0 on this graph: 0–1, 0–2, 1–3, 2–3, 3–4. Write the distance to each vertex and the order in which vertices are dequeued. Then run DFS from 0 and write a valid visit order.

4. Implementation. Write a function that uses BFS to return the actual shortest path (the list of vertices) between two vertices, using the parent-pointer trick from 30.2. What changes if the graph is directed?

5. Topological sort. Given the prerequisites for a small degree program, produce a valid course order and, for one version with a deliberate cycle, show that the algorithm reports failure. Where exactly does the failure show up?

6. Dijkstra. Trace Dijkstra on a small weighted graph of your choosing, showing the priority queue's contents after each pop. Then construct a graph with one negative edge and show that Dijkstra gives a wrong answer, explaining which assumption it violated.

9. Application. A friend group is given as edges between people. Use union-find to determine how many friend circles there are, then use DFS-connected-components and confirm the two answers agree. Which one would you use if people kept becoming friends over time, and why?
