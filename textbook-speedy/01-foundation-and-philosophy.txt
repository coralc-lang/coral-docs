Chapter1

Foundation and Philosophy

The "Why" Before the "How"

Every language exists to solve a problem. Understanding why Coral exists lets you predict its features instead of memorizing them.

A reference manual says what a language looks like; a textbook says why. In Coral the why and the what are the same thing.

1.1 The Origin

Coral began with a love of C: its simplicity, honesty, and directness. C++ added structure and generics, which appealed, but grew painful.

C++ features piled up into slow compiles, exhausting learning, and hard-to-predict code. Each feature was reasonable; together they were not.

Rust and Zig fixed some of this but felt alien to C thinkers. The cost of admission, especially Rust's borrow checker, was steep.

Coral answers one question: can a language keep what makes C great, add modern features and safety, and preserve C-style thinking?

That question became a constraint. A feature earns its place only if it passes three tests:

    Does it preserve the C mental model? If learning Coral means unlearning how you think about memory and the machine, the feature is working against the language, not for it.
    Does it refuse to hide machinery from the programmer? Nothing runs behind your back. If a cost exists, you can point at the source line that pays it.
    Does it make its cost visible in the code? The price of a feature, a copy, an allocation, a dispatch, a check, should be written in the program, not concealed in some library.

These are the constitution of the language. Grasp them and you can predict most of Coral.

The name Coral was chosen at random after the placeholder Wall. There is no acronym or hidden philosophy in it.

1.2 What It Means to Be a Systems Language

Coral is a systems programming language, a phrase with real weight.

Systems languages write the software closest to the hardware: operating systems, drivers, kernels, firmware, game engines, databases, browsers, compilers, and network stacks. They address memory directly, control layout, talk to devices, and demand predictable performance.

First, direct hardware access: a Coral program can allocate memory, read and write addresses, lay out data byte by byte, and touch device registers. Nothing stands between the program and the machine.

Second, no runtime: Coral produces native machine code, with no interpreter, virtual machine, or garbage collector underneath.

Third, manual memory management: you choose stack or heap and when memory is freed. Coral adds smart pointers, explicit error values, and allocator choice to help.

Fourth, predictable performance: allocation happens where written, method calls are function calls, and there are no GC pauses or JIT warm-up.

An application language says the runtime is in charge; a systems language says you are. Coral is firmly in the second camp.

1.3 The Problem Coral Solves

Coral is clearest in what it refuses to do.

It keeps C's type-first syntax, fixed-width integers, explicit pointers, real arrays, and manual memory. Most Coral is readable on sight to a C programmer.

It keeps manual control: no garbage collector, explicit allocation and freeing, or smart pointers that make ownership explicit.

It keeps a real standard library written in Coral: collections, strings, filesystem, networking, concurrency, math, cryptography, and platform abstractions.

Yet it rejects the historical costs of those choices.

It adds methods to C-style structs without classes, inheritance, or virtual dispatch.

It adds generics that fully monomorphize at compile time, giving hand-written performance and compile-time type checking.

It adds traits for shared interfaces without a base class: a trait is a promise a type makes, and any type can implement it.

It adds compile-time evaluation and conditional compilation in the language itself, not in a preprocessor.

It adds a module system with explicit imports the compiler can verify.

It adds Result and Option for errors and absence, instead of exceptions and null.

1.4 Why Not Exceptions

C++ chose exceptions; Coral deliberately rejects them. This shapes every Coral program.

Exceptions are invisible control flow. A throw can abort and unwind arbitrarily far, skipping intermediate functions and making cleanup, performance, and debugging hard to reason about.

Coral uses explicit error values. A fallible function returns a Result carrying either a success value or an error. The caller must handle it, so every failure path is visible.

A Coral file imports the modules and symbols it needs by name:

    import(lib) std::io::ios { parseU64, println };
    import(lib) std::result { Result };

The standard library parses text with functions that take a string view and a success pointer. `str` is the standard string view. Here is a Result-returning helper:

    pub Result<u64, str> parse_count(str text)
    {
        bool ok = false;
        u64 value = parseU64(text, &ok);
        if (!ok)
        {
            return Result<u64, str>::Err { .error = "the text is not a number" };
        }
        return Result<u64, str>::Ok { .value = value };
    }

The call site handles failure where the program can respond:

    var result = parse_count("42");
    if (result.isOk())
    {
        println("parsed the count {}", result.unwrap());
    }
    else
    {
        println("the count was invalid");
    }

Failure is a value in the same type system as everything else, and the if statement chooses what each outcome means. Every path is written.

Explicit failure forces you to confront it where you can act. The standard library returns Result throughout, with the error always in the signature.

1.5 The Target User

Coral is for systems programmers, especially the C programmer who wants safety without a new mental model, and the learner who finds modern systems languages hard to enter.

The C programmer knows pointers and manual memory but lives with buffer overflows, use-after-free, double-free, and data races. Coral keeps the model and adds safety: bounds-checked abstractions, strong typing, Result, smart pointers, and the Drop trait, which releases values automatically at scope end.

Systems programming is traditionally punishing for learners. Coral offers a readable C-like path and grows into the safety machinery as understanding grows.

It also fits game developers moving toward data-oriented design: structs, methods, traits, and an explicit memory model, with no forced vtable, implicit dispatch, or GC pauses.

A team can adopt Coral incrementally, starting with C-style structs, functions, and manual memory, then adding generics, traits, and smart pointers file by file.

1.6 Paradigm Orientation

Coral is primarily imperative and procedural in the C tradition: statements operating on mutable state.

On that core it layers:

Structured data with behavior. Structs can contain methods, with an explicit receiver named self passed like any other parameter. A method call is a function call whose first argument is the receiver, so there is no vtable, hidden dispatch, or hidden copy unless asked for.

The standard library writes methods inside the struct body. Here is a rectangle:

    pub struct Rect
    {
        f64 left;
        f64 right;
        f64 bottom;
        f64 top;

        pub bool contains(f64 x, f64 y)
        {
            return x >= self.left && x <= self.right &&
                   y >= self.bottom && y <= self.top;
        }
    }

self is a parameter like x and y, passed first by the compiler. Calling rect.contains(1.5, 2.0) costs exactly a function call.

Generic programming. Generics let a data structure or algorithm be written once and used with any type. Vec, hash map, set, and sorting are generic, compiled separately per instantiation.

Trait-based polymorphism. Traits provide interface polymorphism through composition, not hierarchy. A type implements a trait by providing its methods; capability, not ancestry, is what matters.

A trait declares the operations it requires:

    trait Shape
    {
        f64 area();
        f64 perimeter();
    }

Any type providing these operations implements the trait, in an implementation block naming the type and trait, Circle::Shape. The type can then be used wherever the trait is expected.

Functional-style data manipulation. The collections library offers map, filter, fold, and iteration over generic containers, and function pointers are first-class. Coral does not impose a functional style.

So Coral is multi-paradigm deliberately: imperative core, structured data, generic and trait polymorphism, and functional collection tools, with each paradigm in a clear role.

1.7 A First Program

The smallest complete program:

    import(lib) std::io::ios { println };

    pub void main()
    {
        println("Hello from Coral.");
    }

Read it the way the language wants:

The first line imports `println` from the standard library's I/O module. Coral has no magical built-in print; printing is an ordinary function. The same module offers `print` (no newline) and `eprint`/`eprintln` for standard error.

void means the program returns nothing. (Coral also allows `i32 main` with `return 0;`.) main is the entry point, and its empty parentheses mean no arguments, though the startup code passes argc and argv and Coral tolerates a main that ignores them. A void main still exits with status zero.

No framework, initialization routine, hidden wrapper, or runtime ceremony sits between source and machine code. What you write is what runs.

Here is a slightly larger program that sums integers from zero to a limit:

    i32 sum_to(i32 limit)
    {
        i32 total = 0;
        i32 i = 0;
        while (i <= limit)
        {
            total = total + i;
            i = i + 1;
        }
        return total;
    }

i32 declares a local variable, type first, exactly like C. total accumulates, i counts upward, and the function returns the result. Every piece is visible.

A main function can call it:

    import(lib) std::io::ios { println };

    i32 sum_to(i32 limit)
    {
        i32 total = 0;
        i32 i = 0;
        while (i <= limit)
        {
            total = total + i;
            i = i + 1;
        }
        return total;
    }

    pub void main()
    {
        i32 result = sum_to(100);
        println("the sum is {}", result);
    }

`println` is variadic and driven by its format string: each `{}` is filled by the next argument, formatted by its type. The integer `result` is converted to text at print time, and the format is checked at build time, so a placeholder with no matching argument is a compile error. The machinery uses `comptime`, covered with generics.

These programs are small to illustrate structure, not because Coral is small. Read the types, then the flow, then the details; that is how Coral presents information.

1.8 Type-First: The Shape of a Coral Program

Coral is type-first: declarations lead with the type. A field is type then name; a function leads with its return type, then name, then type parameters. The first word tells you what a declaration is or produces.

The type is what you most need to know when reading unfamiliar code. Types line up on the left, so a skim gives the program's shape. Name-first languages make you read each declaration through to its type.

A struct field:

    pub struct Circle
    {
        f64 radius;
        f64 center_x;
        f64 center_y;
    }

A function:

    pub u32 clamp(u32 value, u32 low, u32 high)
    {
        if (value < low)
        {
            return low;
        }
        if (value > high)
        {
            return high;
        }
        return value;
    }

Read the signature: produces u32, named clamp, takes three u32 arguments. The type comes first because it is the fact you need first.

There is no fn keyword. A function is a declaration whose body is a block, and the leading return type identifies it once the parentheses follow the name.

Generics follow the same rule:

    pub T identity<T>(T value)
    {
        return value;
    }

The signature reads: produces T, named identity, parameterized over T. The constraint comes before the name because the reader needs it first:

    pub f64 total_area<any Shape>(Vec<any Shape> shapes)
    {
        f64 total = 0.0;
        for (usize i = 0; i < shapes.count(); i = i + 1)
        {
            total = total + shapes.at(i).area();
        }
        return total;
    }

Any type implementing Shape, circle, rectangle, or polygon, can be passed in, and each area call resolves to the right implementation.

Methods are bound to structs in an extend block, keeping operations beside the data:

    pub extend Circle
    {
        f64 diameter()
        {
            return self.radius + self.radius;
        }
    }

Methods may also be written inside the struct body, but the standard library and this book keep fields in the declaration and behavior in an extend block.

The receiver self is available in every method. A static method, which belongs to the type rather than an instance, is called with the type name and a double colon:

    var total = Vec<u64>::withCap(4);

The type is still named first, the operation second.

Type-first syntax makes what the compiler enforces and what the reader sees line up.

1.9 You Get What You Write: The Cost Model

A language is a set of promises about behavior. Coral's answer is extreme: you get what you write. Everything the program does is written in the source or is a behavior-preserving optimization.

In a garbage-collected language, creating an object can trigger a later pause, and a chain of higher-order operations can allocate invisibly. In Coral such hidden machinery does not exist.

A method call is a function call. A struct assignment copies what you ask. An allocation happens where written with the allocator you named. Compile-time bounds and comptime checks happen during the build. There is no GC, hidden runtime, or hidden lock.

The price is visible too. Generic functions are monomorphized: a specialized copy per type combination, with the code-size cost of hand-written code. You can see and control what you instantiate.

The compiler verifies and translates, never reinterprets. It checks types, conversions, instantiations, and comptime assertions, then generates machine code that preserves meaning. The programmer decides behavior; the compiler makes it fast.

This explains the design: errors are values because exceptions are invisible control flow; memory is explicit because a collector is invisible behavior; casts are explicit because implicit conversion is silent reinterpretation. Every decision should be pointable in the source.

1.10 Memory Model and Execution Model

Coral has explicit memory management. The programmer decides where data lives.

The stack holds local variables, arguments, and return addresses. Allocation is fast, scoped, and automatic on scope exit, making it the default for temporary data.

The heap holds data that outlives the current scope. Allocation is explicit through an allocator abstraction: the system allocator, a bounded-latency segregated-fit allocator, a fixed-size pool, or a custom allocator. The interface is a struct of function pointers.

Smart pointer types express ownership. A smart pointer owns and frees its pointee; a shared pointer allows multiple owners and frees when the last is destroyed.

Coral's safety comes from structure and honesty, not an ownership checker. The type system rejects nonsensical conversions and calls at compile time. Ownership is written by the program. What cannot be proven is checked at runtime: container bounds and lock pairing are visible in the code.

When raw pointer arithmetic or an unsafe cast is genuinely needed, code can be marked to suspend the usual expectations. The standard library uses such markings internally, contained and reviewed. Unsafe code is visible and exceptional, not the default.

Coral compiles to native code for x86, x86_64, ARM, ARM64, RISC-V, PowerPC, and others, suitable from desktop to embedded.

Execution is eager and deterministic. Statements run in order, calls happen where written, and there is no lazy evaluation, hidden concurrency, or GC pause.

1.11 Type System Theory

Coral is statically typed. Every expression has a compile-time type, carried through the pipeline; Coral generates C that the platform C compiler then type-checks. Type errors cannot survive to the binary.

Coral is strongly typed. Implicit conversions are limited to well-defined widening; everything else needs an explicit cast, avoiding C's silent conversion traps.

Primitive types are explicit and fixed-width: i8, i16, i32, i64, u8, u16, u32, u64, f32, f64. Write u32 and you get exactly 32 bits, with no platform-dependent width.

The explicit cast is the counterpart of strong typing:

    u32 total = 260u;
    u8 low_byte = (u8)total;

The cast is written where narrowing happens. If total exceeds u8, the truncation is your visible choice on that line.

Composite types build on the primitives: structs with named fields, arrays and vectors, enums, and pointers. Fixed-size arrays carry their size in the type, enabling bounds safety.

Coral infers types where unambiguous. Local declarations can use var:

    var count = 4u;

The initializer shows the type. Inference is local and explicit, not a global engine, and the type is still known at compile time.

The distinct keyword creates a new type with no implicit conversion to or from its underlying type, so a file handle or socket is not interchangeable with an integer. Here are two standard library examples:

    pub distinct File = i32;
    pub distinct TcpSocket = i32;
    pub distinct Dir = void*;

Related but different is typedef, which creates a new name for an existing type:

    typedef u64 nanoseconds;

nanoseconds is exactly a u64, and any u64 code accepts it; the typedef is for readability. A distinct type is genuinely new: File and TcpSocket are not interchangeable, and the compiler rejects mixing them.

Generic types can take type parameters and compile-time value parameters. A generic array can be parameterized by element type and length:

    pub struct Arr<T, N>
    {
        T data[N];

        u64 count() { return N; }
    }

The length is part of the type, so the compiler can specialize code and check bounds at compile time. The std semaphores use exactly this:

    Arr<void*, 8> impl;   // from std/concurrent/semaphore.crl, where the field backs a sem_t

Variadic functions accept an arbitrary number and type of arguments, as in the print family. The value-variadic sibling used by the library's logger is declared in std/io/ios.crl:

    pub void vaprint(... args)
    {
        u8 outBuf[1024];
        _Buf out = _Buf { .fd = 1, .data = outBuf, .len = 0 };
        comptime { for (var arg : args) _fprintOne(&out, arg); }
        _pflush(&out);
    }

And used in the library's logger:

    import(lib) std::io::ios { vaprint };
    vaprint("[", label, "][", self.name.asView(), "] ", msg);

Nullable values are not hidden as in C, where any pointer can be null. Coral's `Option` explicitly represents presence or absence, and the compiler verifies the absence case is handled. With Result for fallible operations, Coral gets modern safety without a GC or radical syntax.

Coral's type system is how it is safe and fast at once: static strong typing, explicit widths, bounds-carrying arrays, distinct types, monomorphizing generics, and Option and Result.

1.12 The Standard Library

A systems language is only as useful as its standard library. Coral ships a comprehensive one, written in Coral.

Collections: `Vec`, `Arr`, `HashMap`, `Map`, sets, linked lists, deques, queues, priority queues, ring buffers, bit sets, tries, trees, caches, sorting, and iteration helpers, all generic and allocator-aware.

Text: `String`, `str`, formatting, string utilities, UTF-8 encoding and decoding, parsers for JSON, XML, CSV, TOML, and INI, plus regular expressions, UUIDs, and URIs.

I/O and system interaction: standard input and output, filesystem operations, buffered and binary I/O, sockets, processes, environment variables, paths, temporary files, terminals, logging, and command execution.

Concurrency: threads, mutexes, read-write locks, semaphores, condition variables, signals, and a thread pool.

Math: common functions, random numbers, vec2/vec3/vec4, matrices, and complex numbers.

Cryptography: SHA-256, HMAC, AES, CRC, base64, hex encoding, and a Bloom filter.

Platform: centralized libc extern declarations, OS and architecture detection, and endianness handling.

The standard library makes Coral practical and demonstrates the language: it is written in Coral, in the style this book teaches.

It is the most demanding test of the philosophy. That it exists, is written in the language, and is safe shows Coral's rules suffice for real systems.

1.13 Compilation and Tooling

Coral compiles to native code with a self-hosted compiler written in Coral, so the language and library are tested by their own development.

Compilation is a pipeline: lex, parse, monomorphize, lower through an intermediate representation, optimize, and generate native code. Coral also emits C and hands it to the platform C compiler, keeping Coral portable while producing real machine code.

Conditional compilation is a language feature expressed with flag blocks:

    flag (platform)
    {
        LINUX   => { println("building for Linux"); },
        WINDOWS => { println("building for Windows"); },
        else    => { println("building for something else"); },
    }

The flag block is parsed and evaluated against the target platform and command-line flags. False branches are compiled out, and the conditions are visible. The platform layer uses nested flag blocks heavily.

Compile-time evaluation lets the compiler reason about types and values during compilation. The printing machinery uses comptime to choose a formatter:

    comptime
    {
        if (T == i8)  { _fprintI8(fd, (i8)val); return; }
        if (T == u8)  { _fprintU8(fd, (u8)val); return; }
        if (T == i32) { _fprintI32(fd, (i32)val); return; }
        if (T == f64) { _fprintF64(fd, (f64)val); return; }
        if (T == str) { _fprintBytes(fd, ((str)val).ptr, ((str)val).len); return; }
        // ... and so on for every type print can handle
    }

This is metaprogramming with the language's own types and control flow. Generics monomorphize first, so by the time the comptime block runs, T is concrete and checkable.

Errors include file, line, column, a source snippet, and related locations. The compiler reports errors in batches and recovers to find more.

1.13.1 The Build Pipeline

Build a Coral program by invoking the compiler on your entry source: coralc myprog.crl -o build/myprog


That lexes, parses, monomorphizes, generates C, and invokes the system C compiler to produce build/myprog. Useful flags:

    -h, --help            show this help

    --emit-h              emit a C header (declarations only)

    --emit-ir             emit WallVM IR (not yet implemented)

    --emit-asm            emit assembly (not yet implemented)

    --debug               include debug information in output

    -O0 -O1 -O2 -O3       optimization level (default -O1)

    --stop-on-error       stop at the first error (default)

    --continue            keep going after errors

    --report-all-errors   emit every error found

    --fcast               force all implicit casts (escape hatch)

    --flags=k=v[,...]     set platform/arch flags (e.g. platform=LINUX,arch=x86_64) .e.g.,
                          --flags=platform=LINUX,ARCH=x86_64,ENDIAN=little
                          set the compile-time flags that flag blocks test against

    --explain <code>      explain an error code in detail (e.g. --explain TC-RETURN)

    --funroll             enable loop unrolling (wallvm)

    --fborrowcheck        enable borrow checker diagnostics

    -o <file>             set output file (default a.out)

    --linker-flags <flags> pass flags to linker (gcc)

The command-line flags, platform, architecture, endianness, are the same flags your source's flag blocks test, and the compiler keeps them consistent. In C and C++ a large build command is a wall of defines that must be reproduced exactly; in Coral the flags that matter are visible in the source.

1.13.2 The Whole Toolchain

The compiler checks and reports precise diagnostics; flags make configuration a first-class language feature; generated C is available when wanted. Because compiler and library share a front end and philosophy, the toolchain has no seams.

The workflow is: write, invoke the compiler on your entry file, read diagnostics, iterate, ship. Targets, features, and configuration are declared in source, chosen on the command line, and kept consistent.

1.14 The Value Proposition

Here is Coral compactly.

Coral is a systems language for people who think in C. It keeps type-first declarations, explicit pointers, manual memory, and plain syntax, and adds methods, monomorphizing generics, traits, smart pointers, explicit Option and Result, a real standard library, and a compiler that shows what it does.

It is small enough to learn in steps, honest enough to keep costs visible, and complete enough to write real systems.
