Error Handling: Option, Result, and the Discipline of Failure

No Exceptions, On Purpose

Coral has no exceptions, no try, no catch, and no hidden stack unwinding. This is deliberate: the standard library's header above Option says "coral has no inbuilt error handling; I will not add try-catch either." Failure is a value the type system sees, the compiler checks, and the reader follows.

An exception leaves a function without returning and unwinds every caller until some distant frame catches it. Intervening cleanup lines never run, and the caller cannot see that open might abandon it.

Coral's fallible functions say so in the return type and return a value meaning "failed"; the caller must inspect it to reach the result.

Every fallible operation declares failure in its return type, and every caller must decide what to do. You cannot forget an error because it is the returned value, not a separate channel. The cost is verbosity; the benefit is that a function returning Result<Fd, IoError> announces its failure mode to every reader.

A normal return is a sealed parcel. An Option is a parcel that may be empty. A Result always contains something, either the item or a note explaining why not. In every case you must open it.

This chapter covers Option and Result, building and propagating them, designing a good error type, and a worked example.

Option<T>: The Absence of a Value

Option<T> answers "a T, or nothing?" without null or a sentinel. It is declared in std::data::option and re-exported as std::option:

coral
pub variant Option<T> {
    None,
    Some { T value; }
}

None is absence; Some carries a value:

coral
Option<i32> maybe   = Option<i32>::Some { .value = 42 };
Option<i32> nothing = Option<i32>::None;

Some { .value = 42 } says yes; None says no. The compiler will not let you treat an Option<i32> as a plain i32, which is the point: a bare i32 cannot say "no."

Other languages smuggle "no value" in as null, -1, or an empty string, with no type warning. Option<T> is a box that is visibly empty or holds a T, and the compiler refuses access until you check.

A magic number such as -1 from findUser breaks when a real id is -1, when someone forgets to check, or when the -1 is passed as an id. A sentinel is an unchecked convention; Option<i32> makes "not found" a case the type knows.

isSome and isNone report the case; unwrap trusts presence; unwrapOr supplies a fallback; take removes the value and leaves None:

coral
if (maybe.isSome()) {
    i32 v = maybe.unwrap();
}

i32 safe = nothing.unwrapOr(-1);      // -1

unwrap is a promise: on None it is an explicit assertion failure, not a garbage value or a later null dereference. unwrapOr handles None; when None is genuinely impossible, an assertion is more honest than a default.

coral
Result<i32, str> r = parseCount(input);
if (r.isOk())
    println("count is {}", r.unwrap());
else
    println("bad count: {}", r.unwrapErr());

The if is the decision: the success path reads the value, the failure path reads the reason, and neither can read the other.

Do not call unwrap everywhere and rebuild the crashes Option prevents. If you cannot prove presence, handle None or use unwrapOr.

take pulls the value out and puts None back:

coral
Option<String> slot = Option<String>::Some { .value = String::from("hello") };
String s = slot.take();     // s is "hello"
// slot is now None
// slot.take() a second time asserts, because there is nothing left

take moves an owned value out of an Option you do not own, leaving a valid empty Option behind, which is exactly what an Option field needs.

ptr returns a pointer to the inner value or null; constPtr returns the read-only version:

coral
i32* p = maybe.ptr();
if (p != null) {
    *p = 99;
}

This is the C nullable-pointer idiom made explicit. The type still knows it is an Option: you cannot call .value on a None or pass Option<i32> where i32 is expected. When crossing into C, ptr is the door and the null check is the price.

map applies a function to a present value in place; andThen chains an operation returning an Option, flattening the nesting; orElse supplies a value on None:

coral
maybe.map(double);                    // Some(v) becomes Some(2v); None stays None
maybe.andThen(parseMore);             // avoids Option<Option<T>>
nothing.orElse(computeDefault);       // runs computeDefault only on None

Those methods return void and mutate self. The standard library's map is:

coral
void map(T(T) fn)
{
    #[[fallthrough]]
    switch (self)
    {
        Some { value } => { self = Option<T>::Some { .value = fn(value) }; }
    }
}

So maybe.map(double); rewrites maybe rather than producing a new Option; copy first if you need the original. This keeps the common in-place transform cheap, at the price of surprising anyone expecting purity. The #[[fallthrough]] lets the None arm do nothing without being flagged as a missing case.

This vocabulary makes "look this up, then that, or give up" chains read as one line. Chapter 16's lookups return Option or pointer-plus-check. Remember that each link rewrites the variable on the left.

Result<T, E>: Failure With a Reason

Option says a value is absent; Result says an operation failed and why. It is declared in std::data::result and re-exported as std::result:

coral
pub variant Result<T, E> {
    Ok  { T value; },
    Err { E error; }
}

Ok carries success, Err the reason. The API author chooses E, usually a variant enumerating the failure modes, which makes failure inspectable rather than a string to parse.

Option fits when the only thing to say is "there was nothing": a failed search or missing key. Result fits when you can say more: the file does not exist, the number was too large, the checksum did not match. Those distinctions live in the error type, so a caller can switch on them.

In short, Option answers "is there anything?" and Result answers "did it work, and if not, why not?"

The choice determines what the caller may know. A map lookup returning Option<V> honestly says "a value or nothing." A file open returning Result<File, IoError> says "a file, or a specific reason," and IoError lets the caller retry, report the path, or use a default.

coral
Result<File, IoError> opened = open("config.txt");
switch (opened) {
    Ok { value }   => { use(value); },
    Err { error }  => { report(error); },
}

The methods mirror Option's: isOk and isErr; unwrap and unwrapOr; unwrapErr for tests; okPtr and errPtr returning pointers to the live case or null:

coral
if (opened.isOk()) {
    File f = opened.unwrap();
}

i32 count = parseCount(input).unwrapOr(0);
IoError e = opened.unwrapErr();

The assertion messages matter: unwrap on an Err reports "Called unwrap() on an 'Err' value." rather than faulting. That names the mistake instead of the symptom, saving an afternoon of debugging.

mapOk transforms success; mapErr transforms the error; andThen chains a fallible operation onto success; orElse recovers with a fallible recovery:

coral
count.mapOk(double);                  // transform the Ok case
count.mapErr(addContext);             // enrich the Err case
count.andThen(validateThenStore);     // chain, flattening Result<Result<...>>
count.orElse(retry);                  // recover on Err

Like Option's, these mutate in place and return void; count.mapOk(double); rewrites count.

mapErr adds context as an error propagates: a parser returns Result<T, ParseError>, a layer maps it to ConfigError naming the file, and the top maps that to a user message. The error's type records which layers have seen it and what they added.

A three-line example. readConfig calls readFile; its job is not to handle I/O but to say which config file was involved:

coral
Result<str, ConfigError> readConfig(str path) {
    var contents = readFile(path);
    contents.mapErr(wrapAsConfigError);
    if (contents.isErr()) return contents.unwrapErr();
    return contents.unwrap();
}

The IoError became a ConfigError carrying the path, and every layer can add context the same way, so the final error is rich with what each layer understood.

Assertions: When Failure Is a Bug

Some failures are contract violations. Coral uses three assertion forms with three audiences.

@assert(cond) aborts with a diagnostic if an invariant fails. Use it for conditions that indicate a bug, not bad input.

coral
@assert(index < count);

@assertOut(cond, "message") adds a message naming the violated precondition:

coral
@assertOut(count > 0, "mean() called on an empty Vec");

@compileError("message") is evaluated at compile time, rejecting an unsupported generic or comptime instantiation at the call site:

coral
@compileError("Vec<T> requires T to be movable");

Keep the division clean. Outside input (a file, socket, command line) uses Result, because it can fail beyond the programmer's control. An internal invariant uses @assert or @assertOut, because a violation is a bug and the only response is to stop loudly. A compile-time constraint uses @compileError, so the mistake never becomes a running program.

Side by side for average(const i32 data[]):

  • If data comes from the user and could legitimately be empty, return Result<f64, StatsError> with an Empty case and let the caller decide.
  • If the contract says "caller must pass a non-empty slice," use @assertOut(data.count() > 0, "average() on empty slice") to stop the bug loudly.
  • If data is a fixed-size array whose length is known to be zero, use @compileError("average() of a zero-length array") so the call never builds.

Same operation, three failure kinds, three tools. Returning a Result for an internal invariant, or asserting on user input, is a common design error.

Ask: "can a caller reasonably do something about this?" If yes, use Result; if the only response is "the program is wrong, stop," use an assertion. A missing file is recoverable; a violated loop invariant is not.

Result is for what the outside world gets wrong; assertions are for what your own code should never get wrong.

A common mistake is asserting on user input: @assertOut(count > 0, "empty list") when count comes from a file turns an expected condition into a crash. That is what Result is for.

Propagating Failure

Coral has no error-propagation operator; there is no question mark that unwraps a Result or returns early. Propagation is explicit, so a reader sees at every call whether failure is handled here or passed up.

The idiom is a switch that returns the error case and continues on success:

coral
Result<Config, ConfigError> loadConfig(str path) {
    Result<File, IoError> opened = open(path);
    switch (opened) {
        Err { error }  => { return ConfigError::Io { .cause = error }; }
        else          => {}
    }
    File f = opened.unwrap();

    Result<str, IoError> contents = readAll(&f);
    switch (contents) {
        Err { error }  => { return ConfigError::Io { .cause = error }; }
        else          => {}
    }

    return parseConfig(contents.unwrap());
}

Before each call nothing can have failed. The call returns a Result; the switch asks "did it fail?" and returns immediately with the underlying error wrapped in the promised ConfigError. On success the else does nothing and the code falls out, where unwrap is safe because failure already returned. The invariant: by the time you reach an unwrap, a switch above has handled the Err.

Do not reach for unwrap first and add the switch later; with no switch above it, unwrap on an Err aborts instead of reporting. Handle the Err with a switch or mapErr first, and let unwrap appear only afterward.

The repeated shape is a small cost. In exchange, every exit on failure is a line you can point to, and the error is enriched at each boundary. "What happens if the file does not exist?" is answered by the first switch, with no call graph to trace.

Walk it through. If open(path) fails, the switch builds ConfigError::Io and returns, so readAll and parseConfig never run. If open succeeds, the else falls through, opened.unwrap() yields the file, and the function continues. Every failure exits by the same visible road: a switch, then a return.

Two refinements reduce repetition. andThen fuses fallible steps when the error types line up:

coral
return open(path)
    .andThen(readAll)
    .andThen(parseConfig);

and the switch appears once, at the end, where the caller decides. mapErr converts an error into the caller's type, so a deep layer can rephrase failure for the layer that reports it. The switch makes each step's failure obvious; the chain makes the successful pipeline obvious. Both are correct.

Caution: because andThen mutates in place and returns void, the expression form above is shorthand for a sequence of statements. When in doubt, write the statements and let each step's type confirm the error types line up.

Designing an Error Type

An error type is an interface. The default good shape is a variant naming the distinct failure modes, each carrying what a caller needs to respond:

coral
pub variant ConfigError {
    NotFound   { str path; }
    Io         { IoError cause; }
    Syntax     { usize line; str message; }
    Validation { str field; str reason; }
}

Four properties make this a good error type.

The compiler distinguishes the cases. A switch over ConfigError is checked for exhaustiveness, so "not found" can be handled differently from "syntax error," unlike a stringly-typed error. Cases needing the same response can share an arm with |:

coral
bool retryable(IoError e) {
    switch (e) {
        IoError::Timeout | IoError::WouldBlock | IoError::Interrupted  => { true; },
        else  => { false; },
    }
}

Read | as "or": one body answers all three cases. It is the same separator Chapter 13 uses for literal patterns. A comma ends an arm and begins the next, so IoError::Timeout, IoError::WouldBlock => true is a different, probably unintended, program.

Each case carries what its handler needs: NotFound the path, Syntax the line, and Io the underlying error rather than a flattened message.

Use the error type directly when there is genuinely one failure mode: Result<str, IoError> is honest when only I/O can fail. A one-case wrapper adds ceremony for nothing.

Wrapping IoError in ConfigError::Io keeps the detail available without forcing every caller to know about file descriptors. The layer that can act on I/O unwraps it; the layer that cannot handles the category.

A variant error also composes with mapping: a caller interested only in "did it parse" ignores the rest, while detail remains available. Adding a new case is a compile-time signal to every switch that needs updating.

Ask whether each case says something a handler could act on differently. If two cases are always handled identically, they are one case; if a case is only logged, a plain str would do. The test is "how many kinds of response are there," not "how many things can go wrong."

Every case is a promise that some caller can respond to it distinctly. A case nobody handles differently enlarges every caller's switch without adding power.

The Error and Panic Catalogue

The compiler's failures follow the same philosophy and carry classifying codes, clustered in two ranges.

The E06xx range is switch and matching. A non-exhaustive switch (E0608) means a Result, Option, or other variant was opened incompletely; an unreachable or duplicate case (E0609) catches a handler that can never run; a fallthrough on the last arm (E0610) catches copy-paste. When you add a fifth case to ConfigError, every switch must decide what to do before the build succeeds.

The E08xx range is lints: unused variable (E0801) and unused import (E0802). --warn-unused keeps a codebase free of refactor debris, including the value left unused after rewriting unwrap into a switch.

Assertion failures are aborts with a location, not error codes, because a violated assertion means the program is wrong. "Returned an Err" is an anticipated failure; "aborted" is a bug. Chapter 23 surveys the full catalogue.

A Worked Example: Reading a Number

A config file has lines like timeout = 30. Parsing the timeout can fail three ways: the key is missing, the value is not a number, or the number is out of range. Each is a distinct case.

coral
pub variant ConfigError {
    MissingKey { str key; }
    NotANumber { str key; str value; }
    OutOfRange { str key; i64 value; i64 min; i64 max; }
}

Result<i64, ConfigError> parseTimeout(Map<str, str>* cfg) {
    if (!cfg.contains("timeout")) {
        return ConfigError::MissingKey { .key = "timeout" };
    }
    str raw = cfg.get("timeout");

    Result<i64, ParseError> parsed = parseInt(raw);
    if (parsed.isErr()) {
        return ConfigError::NotANumber { .key = "timeout", .value = raw };
    }
    i64 value = parsed.unwrap();

    if (value < 1 || value > 86400) {
        return ConfigError::OutOfRange {
            .key = "timeout", .value = value, .min = 1, .max = 86400,
        };
    }
    return value;
}

The signature documents the failure modes: parseTimeout returns a Result, and the Err type enumerates the three ways. The success path returns a bare i64, which the compiler wraps in Ok silently. That sugar keeps the happy path readable; returning failure requires naming the Err case explicitly. It is easy to succeed and necessary to say a word to fail.

This asymmetry shapes the function. The happy path stays quiet while every failure is spelled out, so a reader sees exactly where it can give up. If both needed the same ceremony, neither would stand out.

Each guard produces the specific error the caller needs, carrying the key, the offending value, and the bounds. The caller decides policy:

coral
switch (parseTimeout(&cfg)) {
    Ok { value } => { applyTimeout(value); },
    Err { error } => {
        switch (error) {
            ConfigError::MissingKey { key } => { useDefault(); },
            ConfigError::NotANumber { value } => { warnAndUseDefault(value); },
            ConfigError::OutOfRange { value, min, max } => {
                clampToRange(value, min, max);
            }
        }
    },
}

The outer failure is handled; the inner error is inspected and each category gets its own response. The switch is exhaustive, so a fourth failure mode is a compile error here until the caller handles it. Failure is a value, the value names its cases, and the compiler checks every caller.

The outer switch answers "did it work?"; the inner answers "why not?" useDefault fits a missing key, warnAndUseDefault a non-number, and clampToRange an out-of-bounds value. Each response had the data it needed because the error type carried it.

The real value of Result shows across layers. Suppose loadSettings calls parseTimeout and wants its own errors to mention the config path:

coral
Result<Settings, AppError> loadSettings(str path) {
    Map<str, str>* cfg = readConfigFile(path);
    if (cfg == null) {
        return AppError::NoConfig { .path = path };
    }

    Result<i64, ConfigError> t = parseTimeout(cfg);
    if (t.isErr()) {
        return AppError::BadSetting { .setting = "timeout", .cause = t.unwrapErr() };
    }

    return Settings { .timeout = t.unwrap() };
}

AppError wraps the lower-level errors, and each layer adds context only it possesses. main can switch on AppError and print a helpful message because no layer flattened the failure to a string. "What happens when the config is broken?" has a written, checkable answer.

Exercises

  1. ComprehensionDistinguish Option<T> from Result<T, E> and give a function suited to each.
  2. ComprehensionCoral has no exceptions and no propagation operator. State one advantage and one disadvantage of failure as a return value.
  3. ImplementationWrite firstEven(Vec<i32>) Option<i32> returning the first even number or None, with a range-for and early return, then with the iter adaptors.
  4. ImplementationWrite parseInt(str) Result<i64, ParseError> for base-10 integers with an optional leading minus. Choose and justify ParseError's cases.
  5. DesignList every way reading a database row into a User can fail and design a variant to carry them. Which failures are Result and which assertions?
  6. PropagationRewrite 15.4's loadConfig with andThen and mapErr so the switch appears once. What is gained and lost?
  7. AssertionsChoose @assert, @assertOut, @compileError, or Result for each and explain: a socket connect timeout; a negative array length; a generic instantiated with a non-movable type; a missing required command-line argument.
  8. MethodsOption's map, andThen, and orElse mutate self. What happens when code needs the original, and is the in-place style better or worse?
  9. TransformationGiven Option<i32> maybe, double it if present and otherwise set it to 0, twice: with map/orElse, and with an explicit switch. Which is clearer, and what does each do to maybe?
  10. MetaFind a failure currently handled as a value whose only sensible response is "stop, the program is wrong." Should it be an assertion, or vice versa, and what changes for callers?
