Concurrency and Parallelism

Two Words, Two Problems

One cook switching between orders is concurrent. Eight cooks working stations at once are parallel. Both feed the room; they are not the same kitchen.

The words are often confused, so fix the distinction first.

Concurrency is dealing with many things at once; parallelism is doing many things at once. One cook interleaves orders; eight cooks advance eight orders simultaneously. Concurrency is an organizing problem (sharing one resource without collision). Parallelism is a resource problem (using several resources). A single core can be concurrent but not parallel.

The distinction decides which problem you are solving. A web server handling a thousand waiting connections is concurrency: one thread can serve many if it never blocks. A renderer splitting an image across sixteen cores is parallelism: real arithmetic divided among cores. A parallelism tool on a concurrency problem wastes blocked threads; a concurrency tool on a parallelism problem leaves cores idle.

Coral provides both honestly. A thread is a real OS thread; a thread pool is a fixed set of threads draining a queue; the async runtime is lightweight stacks driven by hand. No hidden scheduler. The machinery is visible and the correctness is yours to write.

Two warnings:

No library makes concurrency easy. Threads, atomics, mutexes, and condition variables are what the hardware and OS offer. Coral adds RAII for locks and some type discipline, but it cannot turn a data race into a compile error. The goal is to keep the difficulty visible.

Everything here is one thing in many hats. A thread pool is a queue with workers, a channel is a queue with a protocol, and an actor's mailbox is a queue. Build one correct producer-consumer queue and you have the engine of the chapter.

Threads

An OS thread is a sequence of instructions the kernel schedules onto a core, with its own stack and registers. Creating one creates a real kernel object and a real stack. Nothing in Coral stands between the call and that object.

The thread module has a deliberately small interface:

coral
import(lib) std::concurrent::thread {
    threadCreate, threadJoin, threadExit, threadCurrent, Thread, ThreadError
};

pub distinct Thread = rawptr;

pub Result<Thread, ThreadError> threadCreate(rawptr(rawptr) fn, rawptr arg);

A thread runs a function taking one rawptr and returning one rawptr, the C signature. It is deliberately raw: the compiler cannot know what your thread needs. Thread is a distinct type over rawptr, so a thread handle cannot be confused with another pointer.

The smallest useful threaded program passes a number to a worker, doubles it, and joins:

coral
import(lib) std::concurrent::thread { threadCreate, threadJoin, Thread, ThreadError };

rawptr worker(rawptr arg) {
    i32* n = (i32*)arg;
    *n = *n * 2;
    return null;
}

void main() {
    i32 value = 21;
    Result<Thread, ThreadError> created = threadCreate(worker, (rawptr)&value);
    if (created.isOk()) {
        Thread t = created.unwrap();
        threadJoin(t, null);
        println("{}", value);        // 42
    }
}

Three points matter:

(i32*)arg tells the compiler what the raw pointer points at; casts are written as the type in parentheses, with no as keyword. (rawptr)&value takes an address and erases its type.

threadCreate returns Result<Thread, ThreadError> because creation can fail: the OS may refuse, the function pointer may be null, or allocation may fail. Branch on created.isOk().

threadJoin orders the threads. Without it, the worker writes at an unknown moment and main reads at another. When threadJoin returns, the worker has finished and all its writes are visible. That guarantee happens exactly once.

threadExit(retval) ends the calling thread; threadCurrent() returns its handle. A joined thread's resources are reclaimed at the join; a detached thread runs to completion and cleans up itself. Join when a later computation needs the result; detach for genuine fire-and-forget.

Threads pass one pointer, so several values usually travel in a struct:

coral
struct Job {
    i32* input;
    i32* output;
    usize count;
}

rawptr runJob(rawptr arg) {
    Job* job = (Job*)arg;
    for (usize i = 0; i < job->count; i += 1)
        job->output[i] = job->input[i] * 2;
    return null;
}

This is how the flat C signature carries structured data. It is also where lifetime discipline begins: pointing a thread at a local that dies before the join is a use-after-free the compiler cannot see.

Atomics

When two threads touch the same value and at least one writes, the result is a data race, which is undefined behaviour. The first defense is the atomic.

Two threads each adding one to a shared counter a hundred thousand times should yield two hundred thousand, but counter = counter + 1 is three actions: load, add, store. If both load 7, both compute 8, and both store 8, one increment is lost. The loss comes from interleaving, not bad luck.

An atomic fixes this for one word. The thread module provides AtomicU64 and AtomicU32:

coral
import(lib) std::concurrent::thread { AtomicU64, AtomicU32 };

AtomicU64 counter;

void main() {
    counter.store(0);
    u64 old = counter.fetchAdd(1);   // read-modify-write as one step
    println("{} {}", old, counter.load());
}

load() reads, store(v) writes, fetchAdd(delta) and fetchSub(delta) update indivisibly, and compareExchange(expected, desired) writes only if the current value matches. These map to hardware instructions (lock xadd and lock cmpxchg on x86, load/store-exclusive on ARM); none is simulated, so no thread observes a half-done operation.

Rule of thumb: use an atomic when the shared state is exactly one integer (a counter, flag, ticket, or index). Use a mutex when it is anything larger. An atomic guards one cell; a mutex guards a region. Do not build a region out of atomics.

An atomic is a turnstile for one tiny operation; a mutex is a door with one key for a whole room.

coral
AtomicU64 ticket;

u64 nextTicket() {
    return ticket.fetchAdd(1);
}

Two threads calling nextTicket get different numbers, and no number is handed out twice.

The Memory Model: Data Races, Happens-Before, and Ordering

The memory model explains why atomics exist and why a forgotten lock is not a small bug.

Processors reorder, buffer, and speculate as long as one thread cannot tell. Trouble starts when threads must observe each other's writes, because a reordering invisible within one thread becomes visible between them. The rules for what one thread sees of another's writes are the memory model.

If operation A happens-before operation B, A's effects are visible to B. Within a thread, program order creates the edge; between threads, you must create it. A data race is two threads accessing the same location, at least one writing, with no happens-before edge. A program with a data race has undefined behaviour: the compiler may assume the race never happens, and the result may change between builds.

Synchronization creates the edge. A mutex unlock happens-before a later lock, threadJoin is an edge, an await is an edge, and atomics carry orderings:

coral
relaxed        only atomicity, no ordering with other memory
acquire        a load that lets later reads observe the writer's earlier writes
release        a store that publishes everything written before it
sequential     a total order all threads agree on (the strongest, the default)

Acquire and release form a pair. A release store synchronizes with an acquire load: everything written before the release is visible after the acquire. One thread fills a buffer then raises a flag with release; another waits on the flag with acquire then reads the buffer:

coral
struct Shard {
    AtomicU64 ready;
    u64 data[1024];
}

rawptr producer(rawptr arg) {
    Shard* s = (Shard*)arg;
    for (u64 i = 0; i < 1024; i += 1)
        s->data[i] = i * i;
    s->ready.store(1);              // release: publish the writes above
    return null;
}

rawptr consumer(rawptr arg) {
    Shard* s = (Shard*)arg;
    while (s->ready.load() == 0) { } // acquire: subscribe
    u64 checksum = 0;
    for (u64 i = 0; i < 1024; i += 1)
        checksum += s->data[i];
    return null;
}

The busy-wait is a teaching scaffold, not good style; a real program uses a join or condition variable. The ordering lesson is real: the release publishes the thousand writes, and any consumer that sees 1 sees all of them. With an ordinary u64, a weakly ordered machine could expose half-written data.

Relaxed gives atomicity and nothing else: other memory may reorder freely. Use it only for a pure counter where nothing else must be visible; it is where the flag-and-buffer bug appears. When unsure, use acquire/release, and when still unsure, use a mutex. Coral's shipped atomics compile to the strong end of the spectrum, safe by default.

Mutex, Read-Write Locks, and Semaphores

An atomic guards one word. For larger shared state, use a mutex: lock before touching the data, unlock after.

Picture a room with one key. To enter, take the key; everyone else waits until you return it. Forgetting to unlock, or returning early from inside the locked region, leaves the key taken forever and every other thread waiting.

coral
import(lib) std::concurrent::mutex { Mutex };

Mutex m;
u64 counter;

rawptr bumper(rawptr arg) {
    for (u64 i = 0; i < 100000; i += 1) {
        m.lock();
        counter = counter + 1;
        m.unlock();
    }
    return null;
}

With both lock lines, two threads print 200000 every time; without them, a smaller number that changes each run. The lock makes the read-add-write indivisible and carries the acquire/release pair that moves memory safely.

Initialize a mutex with m.init() and destroy it with m.destroy(). initRecursive() lets one thread lock twice, useful when locked functions call each other, but prefer designs that avoid it. tryLock() acquires only if free and reports success:

coral
if (m.tryLock()) {
    // we have it
    m.unlock();
} else {
    // someone else holds it; carry on without waiting
}

tryLock refuses to wait, at the cost of handling the not-acquired case. It is one of the standard defenses against deadlock.

A deadlock needs four conditions at once (Coffman): mutual exclusion, hold-and-wait, no preemption, and circular wait. The classic shape is a transfer that locks both accounts:

coral
void transfer(Account* from, Account* to, u64 amount) {
    from->lock.lock();
    to->lock.lock();
    from->balance = from->balance - amount;
    to->balance = to->balance + amount;
    to->lock.unlock();
    from->lock.unlock();
}

If Alice transfers X to Y while Bob transfers Y to X, Alice holds X and waits for Y, Bob holds Y and waits for X, and the bank freezes. The cheapest remedy is lock ordering: give every lock a total order and always acquire in that order. Both transfers then take the smaller-numbered account first and no cycle can form. The library cannot prevent deadlock; the discipline is yours.

An RwLock allows any number of readers or one writer, never both:

coral
import(lib) std::concurrent::rwlock { RwLock };

RwLock rw;
Config config;

void readConfig(Config* out) {
    rw.readLock();
    *out = config;
    rw.unlock();
}

void updateConfig(Config* next) {
    rw.writeLock();
    config = *next;
    rw.unlock();
}

readLock and writeLock acquire; unlock releases either. tryReadLock and tryWriteLock are the non-blocking forms. The configuration cache is canonical: many concurrent reads, rare writes. An rwlock costs more than a plain mutex, so for short critical sections a Mutex is usually faster. Holding a read lock and writing anyway turns the whole apparatus into a placebo.

A semaphore is a gate that lets a fixed number through. It holds a count; wait decrements and blocks at zero, and post increments and wakes a waiter.

coral
import(lib) std::concurrent::semaphore { Semaphore };

Semaphore connections;
connections.init(4);            // at most four at once

void fetchPage(str url) {
    connections.wait();
    openConnection(url);
    readAndClose(url);
    connections.post();
}

The semaphore guarantees at most four open connections. Change the initial value to cap downloads, workers, or printers. tryWait is non-blocking, and value reads the count. A binary semaphore (init(1)) is almost a mutex, but has no owner: any thread may post. Use semaphores to limit and signal; use mutexes to own.

The Condition Variable: Waiting on a Predicate

A thread waiting for work could spin, burning a core, or sleep and check, which is slow or wasteful. A condition variable is a nap with an alarm: block until the predicate might be true.

coral
import(lib) std::concurrent::thread { ConditionVar };
import(lib) std::concurrent::mutex { Mutex };

Mutex mutex;
ConditionVar cond;

void consume() {
    mutex.lock();
    while (!hasWork())
        cond.wait(&mutex);
    // take the work; the mutex is held again here
    mutex.unlock();
}

ConditionVar provides wait, signal, and broadcast. wait releases the mutex and blocks; signal wakes one waiter; broadcast wakes all. Every wait must be paired with a mutex, and the protocol is rigid because a wake-up is only a suggestion.

Three hazards enforce the loop. A lost wakeup: the producer signals between the check and the sleep, so the waiter misses the event; wait releases the mutex atomically with sleeping to prevent this. A spurious wakeup: the platform may wake a waiter without a signal. A stale predicate: another waiter may consume the resource first. The medicine for all three is to recheck in a while, never an if.

coral
// canonical, and the while is not a style choice
while (!predicate())
    cond.wait(&mutex);

That is the whole rule. The next section applies it.

The Producer and the Consumer: A Complete Exchange

The producer-consumer queue is the hello world of condition variables and the engine behind the thread pool, channel, and actor mailbox. Build it once from a ring buffer, a mutex, and two condition variables (item ready, room free).

coral
import(lib) std::concurrent::mutex { Mutex };
import(lib) std::concurrent::thread { ConditionVar };
import(lib) std::mman { alloc, dealloc };

pub struct BoundedQueue {
    Mutex mutex;
    ConditionVar itemReady;
    ConditionVar roomFree;
    u64* items;
    usize cap;
    usize head;
    usize count;
    bool closed;

    bool init(usize capacity) {
        self.items = alloc<u64>(capacity);
        if (self.items == null) return false;
        self.mutex.init();
        self.itemReady.init();
        self.roomFree.init();
        self.cap = capacity;
        self.head = 0;
        self.count = 0;
        self.closed = false;
        return true;
    }

    void destroy() {
        self.mutex.destroy();
        self.itemReady.destroy();
        self.roomFree.destroy();
        dealloc<u64>(self.items);
    }

    void push(u64 v) {
        self.mutex.lock();
        while (self.count == self.cap && !self.closed)
            self.roomFree.wait(&self.mutex);
        if (self.closed) { self.mutex.unlock(); return; }

        self.items[(self.head + self.count) % self.cap] = v;
        self.count = self.count + 1;
        self.itemReady.signal();
        self.mutex.unlock();
    }

    bool pop(u64* out) {
        self.mutex.lock();
        while (self.count == 0 && !self.closed)
            self.itemReady.wait(&self.mutex);
        if (self.count == 0) { self.mutex.unlock(); return false; }

        *out = self.items[self.head];
        self.head = (self.head + 1) % self.cap;
        self.count = self.count - 1;
        self.roomFree.signal();
        self.mutex.unlock();
        return true;
    }

    void close() {
        self.mutex.lock();
        self.closed = true;
        self.itemReady.broadcast();
        self.roomFree.broadcast();
        self.mutex.unlock();
    }
}

Every access to items, count, head, and closed happens under the mutex. Every wait is a while that rechecks its predicate, because wakeups may be spurious and another thread may take the item. push signals itemReady; pop signals roomFree. The ring arithmetic (head + count) % cap keeps the oldest item at head without moving data. close broadcasts to both conditions so every blocked thread wakes, sees closed, and leaves.

The using program has one producer of a hundred values and one consumer:

coral
rawptr producerMain(rawptr arg) {
    BoundedQueue* q = (BoundedQueue*)arg;
    for (u64 i = 1; i <= 100; i += 1)
        q->push(i);
    q->close();
    return null;
}

rawptr consumerMain(rawptr arg) {
    BoundedQueue* q = (BoundedQueue*)arg;
    u64 v;
    u64 total = 0;
    while (q->pop(&v))
        total += v;
    println("sum is {}", total);
    return null;
}

void main() {
    BoundedQueue q;
    q.init(16);

    Result<Thread, ThreadError> p = threadCreate(producerMain, (rawptr)&q);
    Result<Thread, ThreadError> c = threadCreate(consumerMain, (rawptr)&q);
    if (p.isOk()) threadJoin(p.unwrap(), null);
    if (c.isOk()) threadJoin(c.unwrap(), null);
    q.destroy();
}

The buffer holds sixteen, the producer pushes a hundred, and the queue never drops or overflows: the sum is always 5050, because the producer blocks when full and the consumer wakes it. That blocking is backpressure. The consumer's loop ends on false when close wakes it with count zero. The queue, not the join, is the synchronization here.

The producer and consumer share one lunchbox: put food in only when there is room, take it out only when there is some, and never look inside without the lock. The two condition variables are the bells for food ready and room free.

Never write if (empty) wait(): it checks once and can proceed after a spurious wakeup with the item already gone. The while rechecks after every wake. This is a correctness rule, not style.

Thread Pools

Spawning a thread per task does not scale: thread creation, stack reservation, and scheduling are expensive. A thread pool keeps a fixed set of workers and feeds them tasks from a queue.

coral
import(lib) std::concurrent::threadpool { ThreadPool };

ThreadPool pool;
pool.init(8);                 // eight workers
pool.enqueue(work, arg);      // queue a task
// ...
pool.deinit();                // drain, then shut the workers down

init(numThreads) creates workers and reports success. enqueue(func, arg) adds a task and reports acceptance. deinit drains remaining tasks and shuts the workers down. The pool implements @drop, but explicit deinit is needed when shutdown must drain.

The pool is the bounded queue in production form: tasks are items, workers are consumers, and a stop flag handles shutdown. The worker loop generalizes the consumer loop:

coral
void _worker() {
    loop {
        self.mutex.lock();
        while (self.queueHead == null && !self.stop)
            self.cond.wait(&self.mutex);

        if (self.stop && self.queueHead == null) {
            self.mutex.unlock();
            return;
        }

        Task* t = self.queueHead;
        self.queueHead = t->next;
        if (self.queueHead == null) self.queueTail = null;
        self.mutex.unlock();

        t->func(t->arg);
    }
}

The wait is inside a while. deinit sets stop under the lock and broadcasts, so a sleeping worker wakes, rechecks, and exits after draining queued tasks. A task enqueued just before stop is either run or freed, never stranded.

A pool replaces one threadCreate per task with one per worker; per-task cost becomes a queue push and a signal. With eight workers, at most eight tasks run. Size is a tuning decision: one worker per core for CPU-bound work, more for I/O-bound work where workers block, fewer for lock contention. A pool suits many independent short tasks and is wrong for a strictly ordered pipeline.

Async: Overlapping I/O on Fibers

Threads are often wrong for I/O-bound work: a blocked socket holds a stack and scheduler slot doing nothing. Async expresses the same overlap without a thread per operation. A task yields where it would block and resumes when the operation completes; an async sleep frees the thread.

Coral's async is built on fibers, lightweight stacks switched without the OS scheduler. There is no async keyword yet, so the runtime is driven by hand. The scheduler is a stack of contexts, a task is a function on one, and the driver is whoever calls run.

coral
import(lib) std::concurrent::async;
import(lib) std::concurrent::threadpool { ThreadPool };

void fetchAndStore(rawptr arg) {
    // ... do work, and await at the points that would block
}

void coordinator(rawptr arg) {
    Result<async::Future*, async::AsyncError> f = async::spawn(fetchAndStore, arg);
    if (f.isOk())
        async::await(f.unwrap());        // suspend this fiber until done
}

void main() {
    async::init();
    Result<async::Future*, async::AsyncError> c = async::spawn(coordinator, null);
    async::run();                        // drive the scheduler to completion
}

spawn(fn, arg) schedules a function on a fresh fiber and returns a one-shot Future*. await(future) suspends the calling fiber until the result is ready. run() drives the scheduler to completion; runOnce() runs one slice; poolRun(pool, fn, arg) offloads a job to a thread pool and returns a future.

await suspends the calling fiber, but the top level is not a fiber, so awaiting there returns an error. Spawn a coordinator fiber and drive from the top level. Await inside a fiber; drive from outside.

sleep(ms) returns an awaitable future that does not block the thread. AsyncChannel passes raw values between fibers: one task sends, another receives, and the queue handles synchronization.

coral
import(lib) std::concurrent::async;

async::AsyncChannel ch;
ch.init(8);                  // buffered; 0 makes it a rendezvous

if (ch.send((rawptr)value))  // succeed if buffered or a receiver is parked
    // ...
async::Future* got = ch.recv(); // resolve now, or when a later send delivers

A channel implements @drop and is cleaned up at scope exit. send does not block: it hands the value to a parked receiver, buffers it if there is room, or returns false. A receiver gets an already-resolved future or one that resolves on a later send; awaiting it parks the fiber.

Threads are simpler to reason about: code runs straight through, and a blocking call blocks only that thread. Async lets one thread serve thousands of I/O operations on less memory, but requires awaiting at the right points, avoiding blocking calls inside tasks, and remembering suspension. Use async for I/O-bound concurrency at scale, threads for CPU-bound parallelism, and a pool for a bounded number of independent CPU-bound tasks.

Threading Models: OS Threads, Green Threads, and Coroutines

Coral's threads, pool, and fibers are one choice among several threading models.

Threading models differ in where a thread lives and who schedules it.

An OS thread is created and scheduled by the kernel, with a kernel object, a reserved stack, and a context switch crossing the privilege boundary. It is real: exactly what the hardware runs, scheduled by the machine's scheduler. Coral exposes this thread with visible create and join costs.

A green thread is implemented in user space and multiplexed onto fewer OS threads. The runtime scheduler makes switches cheaper, and stacks can start small and grow, which is where millions of goroutines come from. Go's goroutine is a green thread with migration across kernel threads. The cost is hidden runtime machinery.

A coroutine is a function that can suspend and resume, keeping its state. A generator is the familiar shape: yield a value, suspend, resume where it stopped. Coroutines are cooperative, so one that never suspends monopolizes the processor, and they are single-threaded, a control-flow tool rather than a way to use many cores. Coral's async runtime is exactly this: lightweight stacks switched at suspension points, with defaultFiberStackSize tunable. Use it where holding a thread is too heavy and work is mostly waiting. It replaces a hand-written state machine, with the bookkeeping supplied by the runtime.

The models answer different questions: OS threads use all cores, green threads get many threads without many OS threads, and coroutines write stateful loops without hand-written state machines. Serious programs need most of them, which is why Coral provides threads, pools, and fibers.

Two Worlds: Shared Memory and Message Passing

Concurrent activities can share memory or pass messages.

Shared memory is fast and direct: data is where the code is, access is a load or store, and synchronization governs it. Its weakness is the pairing: every shared value needs a guard and every guard needs discipline. Message passing isolates state behind a protocol, so a thread cannot corrupt another's data, but messages must be copied or ownership transferred, and a direct load becomes a round trip.

A game engine shares world state between physics and render threads under a lock because the state is huge and copying it every frame would be wasteful. A chat server gives each connection its own handler and sends messages because the data is small and isolation is worth the copy.

Where data is small and the boundary clean, pass messages. Where data is large and access frequent, share under a mutex and make the guard part of the structure. Between administrative domains, messages are natural, and a mutex guarding shared state is a design smell. Learn to tell which part of a program is which.

Roommates sharing a whiteboard need a lock; roommates passing notes never read a half-written thought. The whiteboard updates faster; the notes are safer.

A channel is message passing's tool, and BoundedQueue is already one: push is a blocking send when full, pop a blocking receive when empty, and capacity is the bound. A bounded channel applies backpressure. An unbounded channel never blocks the sender but lets a slow receiver grow memory. A synchronous channel has capacity zero, so every send is a rendezvous.

The Actor Model

The actor model turns message passing into a discipline. An actor owns its state, has a mailbox, and processes messages one at a time. Actors do not call each other; they send asynchronously, and the mailbox is the only contact. There is no shared state to guard, and an actor can be paused, restarted, or moved because its state is its own.

In Coral, an actor is a pattern: a struct holding state, a bounded queue under a mutex as the mailbox, and a worker thread running the message loop. The smallest actor is a counter that cannot race because only its own thread touches the state:

coral
pub struct CounterActor {
    BoundedQueue mailbox;
    Thread thread;
    u64 value;
}

rawptr counterMain(rawptr arg) {
    CounterActor* a = (CounterActor*)arg;
    u64 msg;
    while (a->mailbox.pop(&msg)) {
        if (msg == 0) break;        // the stop message
        a->value = a->value + msg;
    }
    return null;
}

bool spawnCounter(CounterActor* a) {
    if (!a->mailbox.init(32)) return false;
    Result<Thread, ThreadError> r = threadCreate(counterMain, (rawptr)a);
    if (r.isErr()) return false;
    a->thread = r.unwrap();
    return true;
}

Senders put amounts in the mailbox; only the actor's thread touches a->value. No lock around value, no race to audit, because the mailbox is the only, single-file door. Real actors carry structs or variants through the same door.

A supervision tree is the model's answer to failure. A parent supervises children and restarts a crashed child, containing the crash. In Coral this is ownership plus a join: the supervisor owns the child's resources, the join returns when the child exits, and the supervisor decides whether to restart with fresh state. The actor model's gift is not a primitive but a boundary: the mailbox is the one place ownership crosses.

Lock-Free Programming and the ABA Problem

A mutex is general and an atomic is one-word; some structures can avoid locks entirely using compareExchange. The everyday lock-free shape is a unique-identifier generator:

coral
AtomicU64 ticket;

u64 nextTicket() {
    return ticket.fetchAdd(1);
}

Two threads get different numbers, and each is never handed out again. The fetch-add is one machine instruction with no kernel and no waiting. Lock-free means at least one thread always makes progress because nothing blocks. Its price is discipline: the atomic protects one word, not a structure.

Every lock-free algorithm eventually meets compare-exchange's shadow. The pattern is load, compute a new value, compare-exchange, and retry if the value changed. The shadow is that the value can change and change back.

Thread A loads 1 and plans to store 2. Before its compare-exchange, thread B changes the cell to 5 and back to 1. A's exchange succeeds, believing nothing changed. The cell holds the same bits but a different world. That is the ABA problem.

The canonical setting is the lock-free free-list. A thread loads head = P; another pops P, frees it, and a new allocation reuses the same address for Q, so head is P again bit for bit. The first thread's compare-exchange succeeds, and the stack head becomes Q's next, which was never P's next. The stack is corrupt.

Standard fixes are a tag counter incremented on free, so reuse changes the tag, or delayed reuse via hazard pointers or epoch reclamation. The lesson: compare-exchange promises 'this cell is this value, now,' not 'the world is as you left it.' Pointer-heavy concurrent structures belong behind a mutex, where load, check, and retry form one indivisible region.

Thread-Local Storage

Thread-local storage is the memory model's loophole: each thread sees a private copy, so no thread can race on another's copy. The fastest shared state is state that is not shared.

Coral exposes the platform mechanism with an attribute on a static:

coral
#[[threadlocal]] u64 scratch;

Each thread sees its own scratch, initialized independently. Thread-locals let allocators keep per-thread caches, loggers keep per-thread buffers, and random generators keep per-thread state without contention. A thread-local is a lock that would never be contended, sold as a variable.

errno is the famous example. Old C libraries kept one global, so one thread's failure could be read as another's success. Modern libraries keep one errno per thread. The same pattern serves per-thread allocator caches, replacing a mutex on every use.

Coral treats thread-locals as a design review, not a refusal. A thread-local is implicit state, initialized by machinery the caller never wrote and owned by a thread not visible in the spelling. In a language built on visibility, it is a quiet exception. Prefer passing per-thread state explicitly, as part of the worker's argument or its managed context. Low-level code may need thread-locals, but the explicit form is checkable.

Parallel Patterns: Data, Task, and Pipeline

Given cores, how do you divide the work? A few recurring shapes answer.

Data parallelism applies the same operation to many independent elements and divides them among cores. The canonical example is darkening pixels:

coral
void darken(u8* pixels, usize n) {
    for (usize i = 0; i < n; i += 1) {
        u8 v = pixels[i];
        pixels[i] = v < 30u ? (u8)0 : (u8)(v - 30u);
    }
}

Give each worker a non-overlapping slice of the array. No lock, atomic, or race is needed because sharing is designed out. The correctness lies in dividing the index ranges. The same shape covers audio, matrices, and ray tracing; SIMD and GPUs are this pattern at hardware scale.

Task parallelism divides tasks rather than elements, which is the thread pool's shape: enqueued functions are tasks, pool threads are workers, and concurrency is the pool size. The natural use is a batch of files, URLs, or images:

coral
rawptr parseOne(rawptr arg) {
    str* path = (str*)arg;
    ParseResult r = parseFileAt(*path);
    storeResult(r);
    return null;
}

void parseDirectory(str* paths, usize n, ThreadPool* pool) {
    for (usize i = 0; i < n; i += 1)
        pool->enqueue(parseOne, (rawptr)&paths[i]);
    pool->deinit();     // wait for every parse before returning
}

deinit is the join in pool clothing. The failure mode is imbalance: if one task takes twice as long, cores idle. Choose a grain fine enough to balance but coarse enough to amortize queue operations.

Pipeline parallelism divides work by stage. Each stage's output feeds the next, and each stage can work on a different item simultaneously. A photo pipeline (load, decode, resize, save) uses a thread per stage and a bounded queue per boundary:

coral
BoundedQueue loaded;   // raw bytes -> decoder
BoundedQueue resized;  // decoded pixels -> resizer

rawptr loaderMain(rawptr arg) {
    str* paths = (str*)arg;
    for (usize i = 0; i < 1000; i += 1) {
        u8* raw = readFileBytes(paths[i]);
        loaded.push((u64)raw);
    }
    loaded.close();
    return null;
}

rawptr decoderMain(rawptr arg) {
    u64 raw;
    while (loaded.pop(&raw)) {
        Image img = decodeImage((u8*)raw);
        resized.push((u64)img.pixels);
        dealloc<u8>((u8*)raw);
    }
    resized.close();
    return null;
}

While the resizer works on photo 3, the decoder works on 4 and the loader reads 5, with no locks outside the queues. Bounded queues apply backpressure from slow stages to fast ones. A pipeline wins when stages are balanced and items are many; it is only as fast as its slowest stage.

Fork-Join and Map-Reduce

Fork-join is recursion in parallel: divide a problem, run the halves concurrently, and combine. The join is where the parent waits for the children's results, exactly threadJoin.

coral
struct Slice {
    const u64* data;
    usize n;
    u64 result;
}

rawptr sumSlice(rawptr arg) {
    Slice* s = (Slice*)arg;
    u64 total = 0;
    for (usize i = 0; i < s->n; i += 1)
        total += s->data[i];
    s->result = total;
    return null;
}

u64 parallelSum(u64* data, usize n) {
    if (n <= 1024) {
        u64 total = 0;
        for (usize i = 0; i < n; i += 1)
            total += data[i];
        return total;
    }
    usize half = n / 2;
    if (n >= 65536) {
        // fork: run the lower half on a thread
        Slice s = Slice { .data = data, .n = half, .result = 0 };
        Result<Thread, ThreadError> t = threadCreate(sumSlice, (rawptr)&s);
        u64 upper = parallelSum(data + half, n - half);
        if (t.isOk()) threadJoin(t.unwrap(), null);
        return s.result + upper;
    }
    return parallelSum(data, half) + parallelSum(data + half, n - half);
}

The recursive call is the fork. The if (n >= 65536) threshold is the grain size: below it, forking costs more than it saves. Parallelism's ceiling is the recursion's depth.

Map-reduce restructures fork-join. Map applies an independent operation to every element; reduce combines results with an associative operation; parallelism lives in the map. Summing an array is canonical. The reduction must be associative: integer addition is, but floating-point addition is not, so a parallel float sum may differ from a serial one in the last digits. Map is safe by construction; reduce is safe only when the operation is honestly associative.

Amdahl's Law

Every pattern hits the same ceiling. If a fraction P is parallel and 1 - P is serial, the maximum speedup with N workers is:

coral
speedup(N) = 1 / ((1 − P) + P/N)

As N grows, speedup approaches 1/(1 - P), and the serial part rules. A 90% parallel program is capped at 10x, a 50% one at 2x, and a 99% one at 100x. Serious parallel programmers hunt percentages, not cores.

Ten cars can drive at the same speed, but one toll booth sets the pace for all. The booth is the serial fraction.

The serial part includes critical sections, joins, the shared queue, the straggler stage, and the I/O before and after the parallel work. A report generator that reads a file, transforms in parallel, and writes output still has serial I/O at both ends. Each serial second is a term in (1 - P), invisible on one core and dominant on sixteen.

Shrink the serial part first, then parallelize the rest: hold locks for less, amortize reads, batch the queue, balance tasks, combine incrementally. The law assumes a serial baseline and identical cores; real caches and memory buses bend the curve sooner. It is not a reason to give up on parallelism, but a reason to attack the serial fraction first.

Cancellation, Timeouts, and Backpressure

Concurrency support machinery is where concurrent programs actually die. Cancellation handles work that is no longer wanted. Threads are cancelled cooperatively: a stop flag the loop checks. Nothing can force a thread out of a loop except the loop's own exit. A download manager's cancel button sets a flag; the loop checks it between reads, closes the connection, and exits normally.

coral
AtomicU64 canceled;

rawptr downloadMain(rawptr arg) {
    while (!canceled.load()) {
        // read one chunk; on completion, write it
    }
    return null;
}

A timeout is cancellation by clock, implemented as a deadline. It turns "wait forever" into "wait two seconds, then fail on the ordinary error path." In async, race a sleep future against a real future by awaiting whichever resolves first.

Backpressure is the refusal that keeps a system from being overwhelmed, and you already built it: the bounded queue whose full state blocks the producer. The encoder's frame limit, the pipeline's queued files, and the server's request ceiling all make the fast side slow down instead of growing memory without bound. In a bounded channel, a failed send returns false, and that false is the backpressure signal.

The program that can stop, the program that can wait, and the program that can refuse stay responsive. Each is a boundary decision no language can automate.

The Double Buffer

The double buffer is what games, video players, and audio devices use. A producer draws the next frame while a consumer displays the current one, and the consumer must never see a half-drawn frame. Two buffers and an atomic index solve it: the writer draws into the unpublished buffer, and the reader displays the published one.

coral
struct FrameData { u8 pixels[1920 * 1080 * 4]; }

struct Renderer {
    FrameData buffers[2];
    AtomicU64 front;          // which buffer is published
}

FrameData* beginFrame(Renderer* r) {
    return &r->buffers[1 - r->front.load()];
}

void publishFrame(Renderer* r) {
    r->front.store(1 - r->front.load());
}

The reader loads front and uses the named buffer. Only front is shared, and it is atomic: the store that flips it releases every frame write, and the reader's load acquires the whole frame. The frame data needs no synchronization because at any instant exactly one buffer belongs to the reader and the writer draws only in the other. The reader always gets a complete frame, old or new, never a mixture. Staleness is a feature.

The caveat: the writer must not start drawing into a buffer the reader may still hold. A render loop uses the vertical blank, waiting for the display before starting the next frame. If that assumption fails, add a third buffer or a handshake. The pattern fits producer-consumer exchanges where one frame of staleness is tolerable: render to display, audio callbacks, telemetry to UI.

The Color of Functions

Async has a wart called the color of functions. Synchronous and asynchronous functions are different colors: one can be called anywhere and blocks; the other must be awaited and poisons everything it touches. A synchronous function that wants to call an async one cannot block the loop and cannot await without becoming async, so the color spreads through the call graph.

A red (synchronous) function goes inside and waits at the counter. A blue (async) function leaves its number and comes back. A red function cannot place a blue order without breaking the rules, so it must become blue or wall off the sync core behind a blocking bridge, which defeats the point.

Coral has no colors because it has no async syntax. Threads, pools, and fibers are the same everywhere, with no keyword dividing the world. A function submitting work to a pool is ordinary; a blocking socket call blocks its caller's thread, and the caller decides in ordinary code whether to use a worker. The boundary that colored languages enforce with types is here an architectural boundary drawn in code.

A Worked Example: The Parallel Word Counter

Here are the tools together: count the words in a text file in parallel, using map-reduce with a pool. Chunks are fine enough to balance and coarse enough to amortize.

coral
struct Job {
    const u8* data;     // the chunk
    usize len;          // its length
    u64* count;         // where the map writes its result
}

void countWordsJob(rawptr arg) {
    Job* job = (Job*)arg;
    u64 words = 0;
    bool inWord = false;
    for (usize i = 0; i < job->len; i += 1) {
        u8 c = job->data[i];        // 32 = space, 10 = newline, 9 = tab
        bool ws = c == 32u || c == 10u || c == 9u;
        if (!ws && !inWord) words = words + 1;
        inWord = !ws;
    }
    *job->count = words;
}

u64 countFile(const u8* text, usize size, u32 workers) {
    const usize chunkSize = 65536;

    ThreadPool pool;
    if (!pool.init(workers)) return 0;

    usize nChunks = (size + chunkSize - 1) / chunkSize;
    Job* jobs = alloc<Job>(nChunks);
    u64* counts = alloc<u64>(nChunks);
    if (jobs == null || counts == null) return 0;

    for (usize i = 0; i < nChunks; i += 1) {
        jobs[i] = Job {
            .data = text + i * chunkSize,
            .len = size >= (i + 1) * chunkSize
                 ? chunkSize : size - i * chunkSize,
            .count = &counts[i],
        };
        pool.enqueue(countWordsJob, (rawptr)&jobs[i]);
    }

    pool.deinit();

    u64 total = 0;
    for (usize i = 0; i < nChunks; i += 1)
        total += counts[i];
    dealloc<Job>(jobs);
    dealloc<u64>(counts);
    return total;
}

The pool's deinit is the join, and the joining is the happens-before edge that publishes the counts. Each chunk writes its own result slot, so the map phase shares no words and needs no synchronization. Addition is associative, so the parallel total equals the serial one. The final chunk's len is the boundary the program draws. deinit also makes it safe to free jobs and counts, because no worker can still be reading them after it.
