Data Structures: Layout, Cost, and the Choice of Shape

Where the Cost Comes From

A data structure is a decision about how data sits in memory, and almost every performance property follows from it. Each arrangement makes some operations cheap and others expensive.

Memory is a long street of numbered houses, one byte each. The processor fetches a whole block of neighbouring houses at once, a sixty-four-byte cache line. Reading in order is cheap because the fetched block holds the next houses you want; jumping across town for each value fetches a fresh block and uses few bytes. That difference often decides whether a program runs in a millisecond or a second.

Coral's collections are variations on one theme: arrays lay elements consecutively and compute addresses; vectors add growth; linked lists scatter nodes and link them with pointers; hash maps turn keys into slots; trees keep a shape findable by comparison. Each trades lookup speed, change speed, and cache friendliness differently.

Coral's collections are readable because each is a struct with public fields, and the fields are the layout. You do not guess what a vector costs; you read its declaration and count.

This chapter covers ideas and trade-offs, with code for each. It is not a method catalogue (Chapter 16) or a text layer (Chapter 17). It builds the mental model behind arrays, linked nodes, hashing, heaps, and choosing a shape from an access pattern.

What a Data Structure Is

A data structure is three things at once.

First, a layout: which bytes go where. A vector is one heap block with packed elements. A linked list is many small blocks, each holding a value and pointers. A hash map is a table of occupied and empty slots.

Second, an interface: the operations the layout supports. A vector has push and at; a list has pushFront and each but no at; a map has get and insert.

Third, a cost: how much work each operation does and how many memory blocks it touches. push on a vector is constant on average; at is constant; removeAt in the middle is proportional to the elements after it. Cost follows from layout.

The three are inseparable: layout enables operations, operations give layout its purpose, and cost is the price of both. Do not pick an interface while ignoring the layout that must pay for it.

A data structure is a choice about how to arrange data in memory, and each arrangement makes some jobs fast and others slow.

In Coral the layout is not hidden. Here is the vector exactly as std::collections.vec declares it:

pub struct Vec<T>
{
    T* data;
    usize len;
    usize cap;
}

data points at a block of cap slots, len is how many hold live elements, and cap is the block's capacity. Every operation is bookkeeping on those three numbers.

When you can see the fields, you can see the cost, and choosing a structure becomes arithmetic.

Two Kinds of Work: Arithmetic and Movement

Almost every collection operation does one or both of two kinds of work.

Address arithmetic computes where an element is. With consecutive same-sized elements, element i is at base plus i times the element size, one multiply and one add. Indexing an array is that formula, so it is constant time regardless of size.

Movement copies elements. Inserting into an array's middle slides every later element right. Growing a vector copies every live element. Rehashing a map recomputes every key's position. Movement is the expensive work, and its amount is what you count.

The two kinds of work differ by structure:

  • An array's read is arithmetic only: base + i * size.
  • A vector's append is arithmetic plus, occasionally, a movement of the whole buffer when it grows.
  • An array's middle insert is mostly movement: it shifts the tail.
  • A linked list's insert is arithmetic only: it rewrites two pointers, moving nothing.
  • A linked list's lookup is a series of pointer chases: one small arithmetic step per node, across scattered memory.
  • A hash map's lookup is a hash (some arithmetic), then a short walk over consecutive slots: arithmetic, not movement.

Contiguous storage makes location cheap and movement expensive. Scattered storage reverses that. That one sentence explains why arrays and linked lists coexist and why neither is simply better.

If you want to find things quickly, pack them together; if you want to rearrange them quickly, let them live apart. No single layout does both.

Contiguity, Locality, and the Cost of Indirection

Arithmetic versus movement is the algorithmic half. The memory-system half is locality, which dominates for large collections.

With contiguous elements, iteration reads consecutive addresses, and the cache fetches a block at once. You fetch one cache line, use all of it, and the next is likely on its way. Coral calls this locality; the array is its purest example.

With scattered elements, iteration follows pointers to random addresses. Each hop is a fresh cache line, and you use perhaps eight of its sixty-four bytes. A program that misses on every element can be an order of magnitude slower than one that never misses, with the same algorithmic step count.

This is pointer chasing, or indirection. A pointer holds an address instead of the thing; it buys flexibility and costs a cache miss each time you follow it.

A pointer is a slip of paper with an address: cheap to pass around, but you must travel to the address to get the thing. Contiguous memory is a book read page by page; pointers are a trail of notes left in different buildings.

i32 value = 42;
i32* address = &value;    // a pointer: the address of value
println("{}", *address);  // 42, follow the address to reach the value

This is why the vector is the default in Coral and almost everywhere else, and why the linked list is the special case. Both iterate in linear time, but the vector reads forward and the list jumps around, and on modern hardware that difference is enormous.

Suppose each element is eight bytes and a cache line is sixty-four. A million-element vector touches about a hundred and twenty-five thousand cache lines, using every byte, all sequential and easy to prefetch. A million-element linked list touches one cache line per node, a million fetches the prefetcher cannot guess.

The Fixed Array: When the Size Is Part of the Type

The array is the simplest collection: a fixed number of consecutive elements, nothing else. In Coral the array is generic over element type and count:

pub struct Arr<T, N>
{
    T data[N];
}

N is part of the type. Arr<i32, 3> and Arr<i32, 4> are different types, and the compiler knows each size before the program runs. An Arr<u8, 16> is exactly sixteen bytes, inline in a stack frame or containing object, with no heap allocation and no pointer.

at reads and set writes an element, both checking the index. count returns N, isEmpty asks whether N is zero, front and back read the ends, fill writes every element, copyTo/copyFrom copy the whole array, and ptr/constPtr expose the storage:

import(lib) std::arr { Arr };

Arr<str, 3> months = Arr<str, 3> { "jan", "feb", "mar" };
for (usize i = 0; i < months.count(); i++)
    println("{}", months.at(i));
println("first is {}, last is {}", months.front(), months.back());

Because N is a compile-time constant, storage is exact and bounds are knowable. A lookup table, conversion table, or small constant-size buffer is an array, needing no allocation, growth, or bookkeeping.

A small example of the no-allocation promise:

Arr<i32, 4> dice = Arr<i32, 4> { 1, 2, 3, 4 };
i32 total = 0;
for (var face : dice)
    total += face;
println("four dice total {}", total);

When a count is truly fixed and known, an Arr states that fact in the type, so no caller can make it larger or forget to grow it.

The array is the base case. Every other collection is "an array plus a strategy" or "arrays connected by pointers." The vector is an array that can move. The hash map is an array indexed by a computed key. The heap is an array encoding a tree. The bitset is an array of words used as bits.

The Vector: A Contiguous Buffer That Grows

The array's fixed size is its limitation: programs often do not know the count until runtime. The vector is the array with growth, a contiguous buffer that starts small and expands when full.

The layout is the array's storage plus two numbers:

pub struct Vec<T>
{
    T* data;
    usize len;
    usize cap;
}

data points at the buffer, len is the live count, and cap is the capacity. len never exceeds cap, and live elements occupy data[0] through data[len - 1].

Create one empty or with room set aside:

import(lib) std::vec { Vec };

Vec<i32> empty = Vec<i32>::new();
Vec<i32> roomy = Vec<i32>::withCap(1024);

new allocates nothing until the first push. withCap allocates immediately, useful when the count is roughly known: allocate once, then push without growth. The operations are the array's plus growth. at and set index (checked); atPtr and atConst return element pointers; ptr/constPtr return the buffer; push appends; pop removes the last; insert/removeAt modify the middle; front/back read the ends; count/isEmpty report state.

The push method is the vector in miniature:

void push(T val)
{
    if (self.len >= self.cap)
    {
        usize newCap = self.cap > 0 ? self.cap * 2 : 4;
        self.reserve(newCap);
    }
    self.data[self.len] = val;
    self.len++;
}

Check the room, grow if needed, store, advance the length. Every growth-triggering operation has that shape.

The middle operations have their costs in their shapes. insert and removeAt move every element after the index, so they are linear in the tail. Appending is the fast path; the middle is where a vector pays for contiguity.

Vec<u64> squares = Vec<u64>::withCap(10);
for (usize i = 0; i < 10; i++)
    squares.push(i * i);

u64 total = 0;
for (usize i = 0; i < squares.count(); i++)
    total += squares.at(i);

Capacity management makes a vector fast. reserve grows to a requested capacity, reserveExact allocates exactly, shrinkToFit releases spare capacity, and clear resets the length without freeing the buffer. The vector is the default for "many elements of one type": array-like reads, list-like growth, contiguous and cache-friendly.

Do not confuse count() with capacity. count() reports live elements; capacity is the room behind them, changed only by withCap, reserve, or growth. clear does not return memory; it sets length to zero and keeps the buffer.

Growth, Doubling, and What "Amortized" Means

A push that triggers growth copies every live element, which is expensive for a large vector, yet appending is called constant time. Both are true, and that is amortized cost.

"Amortized constant time" means the rare expensive step is paid for by a long run of cheap ones.

When full, the vector does not grow by one slot; it doubles, with a floor of four on the first growth:

void reserve(usize newCap)
{
    if (newCap <= self.cap) return;
    self.data = realloc<T>(self.data, newCap);
    self.cap = newCap;
}

Doubling is the trick. After a growth, the vector has at least as much free room as it had live elements, so one expensive copy buys a long run of cheap appends. Total cost of n pushes divided by n stays constant.

Push a million elements from empty. Capacities are 4, 8, 16, and so on, and the copies total roughly the final capacity, about a million moves. So a million pushes cost about two million operations, about two per push, a constant. Growing by one slot per push would copy the whole vector every time and be quadratic.

A small trace from an empty vector whose first growth reaches capacity four:

// push 1..4   -> room already there, no copy
// push 5      -> buffer full: copy 4 elements, grow capacity to 8
// push 6..8   -> room already there, no copy
// push 9      -> buffer full: copy 8 elements, grow capacity to 16

Four pushes triggered a copy and seven did not, and the triggering fraction keeps shrinking.

Every growable collection follows the same analysis. The vector's reserve, the string's _ensure, the deque's _grow, and the hash map's rehash all double, and all are amortized constant.

When the count is known, withCap allocates exactly and the vector never copies. When bounded, reserve allocates up front. The library names the methods that control growth, so a caller who knows the future can avoid the surprise.

A Stack Is a Usage, Not a Type

Some structures are usages of a type, not types. A stack is last-in-first-out: remember a value, get it back in reverse order. Every program has one underneath it, the call stack.

A stack is a pile of plates: add and take from the top, so the last plate set down is the first picked up.

Coral has no separate Stack type, by design. A stack is a Vec used with push and pop at the same end:

Vec<u64> stack = Vec<u64>::new();
stack.push(1);
stack.push(2);
stack.push(3);
u64 top = stack.pop();      // 3, the last one in
u64 next = stack.pop();     // 2

These are the vector's back-end operations at the same amortized constant cost. A data structure is a layout plus its operations, and when an existing type provides them, the type is the structure.

A stack's canonical use is matching delimiters, because nesting is LIFO: the most recently opened delimiter must close first. Push each opener; on a closer, the matching opener must be the last pushed:

pub bool balanced(str text)
{
    Vec<u8> stack = Vec<u8>::new();
    str open = "([{";
    str close = ")]}";
    for (usize i = 0; i < text.len; i++)
    {
        u8 c = text.at(i);
        usize o = open.findByte(c);
        if (o < open.len) { stack.push(c); continue; }
        usize k = close.findByte(c);
        if (k < close.len)
        {
            if (stack.isEmpty()) return false;
            if (stack.pop() != open.at(k)) return false;
        }
    }
    return stack.isEmpty();
}

The function is linear: each character is examined once, and each push and pop is amortized constant. The same LIFO order is an undo history and the shape of any backtracking search.

When a problem says "use a stack" or "use a queue," look at the access pattern, not for a magic type. The pattern is the data structure; the container is just storage.

Linked Nodes: The Other Way to Connect

If the array is everything packed, the linked list is the opposite. Each element gets its own block, a node, connected by pointers. To reach the tenth element you follow nine pointers. Nothing moves; insertion rewrites a couple of pointers.

A linked list is a treasure hunt: each clue tells you where the next is hidden. A vector is a row of numbered boxes you can walk straight to.

In Coral a node is an ordinary struct with a value and pointers, and the list is a struct with a pointer to the first node. The standard library declares a doubly linked version:

pub struct ListNode<T>
{
    T value;
    ListNode<T>* prev;
    ListNode<T>* next;
}

pub struct LinkedList<T>
{
    ListNode<T>* head;
    ListNode<T>* tail;
    usize len;
}

The node and list declarations show the cost before use: each element carries two pointers, and the list holds both ends plus a count.

You can build a singly linked list by hand to control allocation. Allocation is explicit through std::mman:

import(lib) std::mman { alloc, dealloc };

pub struct Node<T>
{
    T value;
    Node<T>* next;
}

Node<i32>* pushFront(Node<i32>* head, i32 value)
{
    Node<i32>* node = alloc<Node<i32>>(1);
    node->value = value;
    node->next = head;
    return node;
}

void freeList(Node<i32>* head)
{
    while (head != null)
    {
        Node<i32>* next = head->next;
        dealloc<Node<i32>>(head);
        head = next;
    }
}

alloc<T>(count) reserves count elements on the heap; * and -> reach through a pointer; dealloc<T> returns the block. pushFront allocates one node, writes the value, points it at the old head, and returns the new head: constant time, no movement. Freeing walks the chain, saving each next before releasing the node.

pushFront and pushBack add at the ends, popFront and popBack remove, insertAfter and remove work on individual nodes, and each walks from head to tail. End operations are constant time because the list holds both ends. Reaching the middle walks from the head, linear time, and there is no index operation.

End insertion and removal are constant time with no copying, since pointers are rearranged. Reaching the middle is linear, and iteration touches a different cache line per element. Use a list when work is at the ends and churn is high, not for indexing.

Do not assume the linked list is the "advanced" collection and reach for it by default. On modern hardware the vector wins for almost every read-and-store workload; the list earns its place only when addresses must stay put or churn is at the ends.

Pointer Stability, and When Indirection Wins

The linked list buys one thing the vector cannot: stable addresses.

When a vector grows, it allocates a new buffer and copies elements, so a pointer into it is invalidated the instant it grows. A linked list makes no such bet: each element lives in its own node, and a pointer stays valid however many other nodes are added or removed, as long as that node is not removed.

Pointer stability makes intrusive structures possible. An intrusive structure stores links inside the data itself: a cache entry that is both a recency-list node and a map value, or a task on a scheduler's list. Links move without moving the data. The library's Cache in std::collections.cache is exactly this: a hash map for lookup and a doubly linked list for recency, with each entry doing both jobs.

For iterating and indexing, the vector's locality wins overwhelmingly and it is the default. For rearranging links and holding pointers to elements that must not move, the list's stable addresses win. The structures are not ranked; they are different points on a trade.

The Deque and the Ring Buffer: Both Ends

A vector is fast at the back and slow at the front: push appends in constant time, but insert(0, x) shifts the entire buffer. A work queue that takes from the front and adds to the back needs a deque.

A deque (double-ended queue) supports constant-time insertion and removal at both ends. It is a ring buffer: one contiguous block with head and tail indices that wrap around.

pub struct Deque<T>
{
    T* data;
    usize head;
    usize tail;
    usize cap;
    usize mask;
}

The mask field is the ring trick. Capacity is a power of two, mask is capacity minus one, and advancing an index means adding one and masking. count subtracts and masks; _grow allocates a new buffer and copies head to tail. Both ends are positions on a circle, so both are constant time, and storage stays contiguous.

The operations are pushFront/pushBack, popFront/popBack, front/back, and index access through at/set, which index from the head. Queue is a thin wrapper over the deque:

import(lib) std::collections.deque { Deque };

Deque<u64> work = Deque<u64>::new();
work.pushBack(1);
work.pushBack(2);
work.pushFront(0);
while (!work.isEmpty())
{
    u64 job = work.popFront();
    if (job > 0) work.pushBack(job - 1);
}

The ring idea also appears with fixed capacity in RingBuf, in std::collections.ringbuf. It never allocates after construction; when full, a push overwrites the oldest element. Its declaration adds a full flag because with wrapping indices, empty and full look the same:

import(lib) std::collections.ringbuf { RingBuf };

RingBuf<f64> recent = RingBuf<f64>::new(16);
recent.push(1.5);
recent.push(2.5);
if (recent.isFull())
    println("window full, oldest dropped");   // the overwrite is the policy
println("oldest is {}", recent.front());

Fixed capacity makes the ring buffer predictable, which is why it appears wherever a buffer must never grow: streaming data, bounded producer-consumer buffers, and recent-event rings. It tells you when it is full, and you decide what full means.

The Queue and the Order of Arrival

A queue is first-in-first-out: the first added is the first removed. It is the shape of fairness and of any process that preserves arrival order. Queue wraps the deque, exposing one-ended vocabulary:

pub struct Queue<T>
{
    deque::Deque<T> inner;
}

enqueue adds at the back, dequeue removes from the front, peek reads the front, and count, isEmpty, and clear delegate to the deque. Each enqueue and dequeue is constant time.

import(lib) std::collections::queue { Queue };

Queue<u64> jobs = Queue<u64>::new();
jobs.enqueue(1);
jobs.enqueue(2);
u64 first = jobs.dequeue();   // 1

The queue's deepest use is breadth-first search, where queue order is discovery order. Mark and enqueue the start. Each iteration dequeues a node, visits it, and enqueues its unmarked neighbours. Every node at distance one is visited before any at distance two, so the walk spreads outward one layer at a time. A Bitset can serve as the mark set for small integer nodes:

import(lib) std::collections.bitset { Bitset };

pub void bfs(u64 start, const Vec<Vec<u64>>* adj, void(u64) visit)
{
    Bitset seen = Bitset::new(64);
    Queue<u64> frontier = Queue<u64>::new();
    frontier.enqueue(start);
    seen.set(start);
    while (!frontier.isEmpty())
    {
        u64 node = frontier.dequeue();
        visit(node);
        Vec<u64> neighbors = adj->at(node);
        for (usize i = 0; i < neighbors.count(); i++)
        {
            u64 next = neighbors.at(i);
            if (!seen.test(next))
            {
                seen.set(next);
                frontier.enqueue(next);
            }
        }
    }
}

A node is marked when enqueued, never when visited, so the mark means "discovered" and no node is enqueued twice. The queue delivers layers in order, and the walk ends when the frontier drains. Every edge is examined once, so the walk is linear.

Hashing: Turning a Key Into an Address

Earlier collections index by position or walking. The hash map indexes by value: it hashes the key, reduces the number to a slot, and looks there, turning "search for the key" into "compute where it must be."

Think of a coat check: hand over a coat, get a numbered ticket, and the number takes you straight to the shelf. The hash function turns a key into a ticket number. Shelves are ordered by ticket, not by the coats, so the map promises no key order.

The standard hash map uses open addressing: entries live in one array, and each records whether it is occupied. Its fields include the two functions defining what a key means:

pub struct HashMapEntry<K, V>
{
    K key;
    V value;
    bool occupied;
}

pub struct HashMap<K, V>
{
    HashMapEntry<K, V>* entries;
    usize cap;
    usize len;
    usize(K) hashFn;
    bool(K, K) eqFn;
}

A hash map cannot hash an arbitrary T or know equality, so it asks the caller for both: hashFn turns a key into a number, and eqFn decides whether two keys are equal. The constructor takes them:

import(lib) std::collections.hashmap { HashMap };

pub usize hashU64(u64 k) { return (usize)k; }
pub bool eqU64(u64 a, u64 b) { return a == b; }

HashMap<u64, str> names = HashMap<u64, str>::new(hashU64, eqU64);
names.insert(7, "seven");
names.insert(11, "eleven");

A hash function is a deterministic scramble. The same key must always produce the same number, and a good hash spreads different keys across the integer range. Hash order is not key order: two keys that hash near each other have no relationship. That is why the map promises no entry order.

Do not expect a hash map to remember insertion order. It stores each key wherever its hash lands. For insertion order use a vector; for sorted keys use the tree map of Section8.15.

Lookup hashes the key and probes from the resulting slot:

Option<V> get(K key)
{
    usize h = self.hashFn(key) % self.cap;
    usize start = h;
    while (self.entries[h].occupied)
    {
        if (self.eqFn(self.entries[h].key, key))
            return Option<V>::Some { .value = self.entries[h].value };
        h = (h + 1) % self.cap;
        if (h == start) break;
    }
    return Option<V>::None;
}

The method hashes, probes, and compares with the equality function. It returns an Option: Some when present, None when not. That is the map's honesty about absence, the same Option as Chapter 15. getPtr returns an Option wrapping a pointer for in-place modification. The module provides insert, get, getPtr, contains, remove, clear, keys, values, and each.

Collisions, the Load Factor, and the Rehash

Two keys can hash to the same slot, so the map needs collision resolution. Coral uses linear probing: when the hashed slot is occupied, the probe moves to the next slot until it finds a free slot or the matching key. That is the h = (h + 1) % self.cap; in get.

Linear probing keeps entries in one array, which is cache-friendly and simple. Its weakness is clustering: as the table fills, occupied slots form runs, new insertions extend them, and lookups walk long runs. Keeping clusters short means keeping the table sparse.

The load factor is how full the table may get. Coral's map checks before inserting and grows when length reaches half capacity:

if (self.len * 2 >= self.cap)
{
    usize newCap = self.cap * 2;
    // allocate newCap, re-home every occupied entry by its hash
}

At or below a load factor of one half, probes stay short. Growth doubles and rehashes every occupied entry, because the slot is the hash modulo the capacity and capacity changed. The rehash is why the map remembers its hash function, and it is amortized like the vector's growth.

The load factor is a trade: a denser table uses less memory and probes more; a sparser table uses more memory and probes less. The standard map's threshold is its chosen point:

Option<V> get(K key)        // returns a value, or None
Option<V*> getPtr(K key)    // returns a pointer, or None
bool contains(K key)        // membership
Result<V, CollectionError> insert(K key, V value)  // may allocate

The map is the choice for key lookup when order does not matter. Finding a key is constant time on average, provided the hash spreads its keys. A poor hash piles keys into one cluster and turns the map into a linear scan. Section8.14 shows the rules both functions must obey.

A load factor is a car park deliberately kept half empty: if every space were filled, finding a free one would mean circling a long row. Keeping spaces open costs memory and keeps lookups fast.

The Frequency Counter: A Map Put to Work

The hash map's natural job is counting. For each word in a stream, find its running count and add one. The word is the key, and lookup is constant time on average no matter how many distinct words there are.

getPtr combines lookup and update: find the value's pointer and increment through it. A get followed by insert would look up twice. For str keys, both functions are written by the caller:

pub usize hashView(str s)
{
    usize h = 5381;
    for (usize i = 0; i < s.len; i++)
        h = h * 33 + (usize)s.at(i);
    return h;
}

pub bool eqView(str a, str b)
{
    return a.equals(b);
}

pub void countWords(const Vec<str>* words)
{
    HashMap<str, u64> counts = HashMap<str, u64>::new(hashView, eqView);
    for (usize i = 0; i < words->count(); i++)
    {
        str w = words->at(i);
        Option<u64*> slot = counts.getPtr(w);
        if (slot.isSome())
        {
            u64* p = slot.unwrap();
            *p = *p + 1;
        }
        else
            counts.insert(w, 1);
    }
    Vec<str> keys = counts.keys();
    for (usize i = 0; i < keys.count(); i++)
    {
        str w = keys.at(i);
        println("{} : {}", w, counts.get(w).unwrap());
    }
}

The first time a word appears, the slot is None and the word is inserted with count one; later, the Some pointer increments the count. Keys come out in hash order, not insertion order, because the map promises lookup, not order.

A good hash uses the whole key, varies with every part, and spreads across the full range. A hash ignoring part of a key piles together records sharing that part. A constant hash turns the map into a linear search. An expensive hash is also bad, because the map pays it on every operation. The classic string hash, multiply an accumulator by a small prime and add each byte, is the model.

Equal keys must hash to the same value, or the map searches one place for a key stored in another and quietly fails. For a composite key, use every field in both functions:

pub struct Point { i64 x; i64 y; }

pub usize hashPoint(Point p)
{
    usize h = 17;
    h = h * 31 + (usize)p.x;
    h = h * 31 + (usize)p.y;
    return h;
}

pub bool eqPoint(Point a, Point b)
{
    return a.x == b.x && a.y == b.y;
}

HashMap<Point, str> labels = HashMap<Point, str>::new(hashPoint, eqPoint);

The hash combines both coordinates so a change in either changes the hash, and equality compares the same two coordinates. If the hash and equality disagree, the map quietly fails.

Order as a Feature: The Tree Map

Hashing deliberately destroys order. Sometimes order is the point: iterate keys smallest to largest, or find all keys in a range. The ordered map keeps entries in a balanced binary search tree. Coral's Map in std::collections.map is an AVL tree, tracking each node's height:

pub struct MapEntry<K, V>
{
    K key;
    V value;
    i32 height;
    MapEntry<K, V>* left;
    MapEntry<K, V>* right;
}

pub struct Map<K, V>
{
    MapEntry<K, V>* root;
    usize len;
    i32(K, K) cmpFn;
    bool failed;
}

Ordering comes from cmpFn, which compares two keys and returns negative, zero, or positive, the same three-way protocol as str::compare and binary search. A rotation rebalances: when a subtree is too tall on one side, a few pointer changes move a node up and reattach the middle subtree, preserving search order. After insertion or removal the tree rebalances along the changed path, so depth stays a small constant times the logarithm of size.

import(lib) std::collections.map { Map };

pub i32 cmpView(str a, str b) { return a.compare(b); }
pub void printPair(str k, u64 v) { println("{} : {}", k, v); }

Map<str, u64> scores = Map<str, u64>::new(cmpView);
scores.insert("ada", 42);
scores.insert("bob", 7);
scores.insert("cecile", 19);
scores.each(printPair);       // delivered in key order: ada, bob, cecile

The operations match the hash map's, but entries are kept in order. each walks in order (left subtree, node, right subtree), delivering keys smallest to largest. The tree is the keys' order made visible.

The price is logarithmic lookup, insert, and remove, where the hash map is constant on average. The library provides both. Chapter 16 calls the hash-based wrapper UnorderedMap, the same table behind a name stating "no order."

Sets: Membership on Its Own

A set drops the values and keeps the keys. It holds distinct elements, answers "is this present?", and enforces no duplicates. Coral's Set is a HashMap<T, bool> underneath, storing each element as a key with a throwaway value:

pub struct Set<T>
{
    HashMap<T, bool> inner;
    usize(T) hashFn;
    bool(T, T) eqFn;
}

Membership is constant time on average, inherited from the map. insert records a value, contains asks whether it is present, and remove forgets one. This is the collection for "have I seen this before":

import(lib) std::collections.set { Set };

Set<u64> seen = Set<u64>::new(hashU64, eqU64);
Vec<u64> unique = Vec<u64>::new();
for (usize i = 0; i < values.count(); i++)
{
    u64 v = values.at(i);
    if (!seen.contains(v))
    {
        seen.insert(v);
        unique.push(v);
    }
}

The first encounter keeps a value and later ones are skipped; since membership is constant on average, the pass is linear. The set's extra operations are union, intersection, difference, and isSubset/isSuperset:

Set<u64> common = seen.intersection(&other);   // elements in both
Set<u64> onlyA  = seen.difference(&other);     // in seen but not other
Set<u64> both   = seen.union(&other);          // in either

The set's design is that the seen-list grows without a slowdown, and the same structure answers deduplication, overlap, and combining distinct collections.

The Bitset: Membership in a Single Bit

A set of small integers in a dense range has a denser representation: one bit per integer. A bitset packs bits into machine words and answers membership by testing a bit:

pub struct Bitset
{
    u64* words;
    u64 numBits;
    u64 numWords;
}

The word count is the bit count divided by sixty-four, rounded up. Each bit operation finds its word and offset with division and modulus, then applies a bit operation:

void set(u64 bit)
{
    @assert(bit < self.numBits);
    u64 word = bit / 64;
    u64 off = bit % 64;
    self.words[word] |= (1u << off);
}

set turns a bit on, clear off, toggle flips, and test reads. countOnes and countZeros count by clearing the lowest set bit, and and, or, xor, and not apply word operations. One bit per element means a million elements occupy about a hundred and twenty-five kilobytes. Membership is constant time, and set algebra is a few word operations per word.

The classic demonstration is the sieve of Eratosthenes, whose universe is exactly a dense integer range:

import(lib) std::collections.bitset { Bitset };

pub Vec<u64> primesBelow(u64 n)
{
    Bitset composite = Bitset::new(n);
    for (u64 i = 2; i * i < n; i++)
    {
        if (composite.test(i)) continue;
        for (u64 j = i * i; j < n; j += i)
            composite.set(j);
    }
    Vec<u64> primes = Vec<u64>::new();
    for (u64 i = 2; i < n; i++)
        if (!composite.test(i))
            primes.push(i);
    return primes;
}

The set handles arbitrary values and pays for a hash table. The bitset handles a fixed, dense range and pays one bit each, asserting the bound on every operation. Arbitrary values: set; dense range: bitset.

The Heap: Priority Without a Sort

A priority queue always yields the most important element available. It is a heap: a complete binary tree in an array, arranged so every parent outranks its children. No pointers are needed because the tree is the indices: a node at i has children at 2i+1 and 2i+2 and parent at (i-1)/2.

pub struct PriorityQueue<T>
{
    T* data;
    usize len;
    usize cap;
    bool(T, T) less;
}

Priorities come from the less function the constructor takes. The queue does not know what "more important" means; the comparator decides, so the same collection serves a min-heap or max-heap. push places the new element at the end and sifts it up, swapping with its parent until the parent outranks it:

void _siftUp(usize idx)
{
    while (idx > 0)
    {
        usize parent = (idx - 1) / 2;
        if (!self.less(self.data[idx], self.data[parent])) break;
        T tmp = self.data[idx];
        self.data[idx] = self.data[parent];
        self.data[parent] = tmp;
        idx = parent;
    }
}

pop takes the root, moves the last element into its place, and sifts down. Each sift moves one level down a tree of logarithmic height, so each operation is logarithmic.

The heap's beauty is that the tree lives in the array with no pointers: children and parent are computed from the index, so the heap never allocates a node. The cost is that the array is not sorted; only the heap property holds. That is enough, because the queue only needs the root, and sifting restores the property after each push and pop.

import(lib) std::collections.priorityqueue { PriorityQueue };

pub bool lessU64(u64 a, u64 b) { return a < b; }

PriorityQueue<u64> deadlines = PriorityQueue<u64>::new(lessU64);
deadlines.push(30);
deadlines.push(10);
deadlines.push(20);
u64 next = deadlines.pop();     // 10, the smallest

With less meaning "a is less than b," the queue is a min-heap; flip the comparator for a max-heap. Use it for "always take the most important next": earliest-deadline scheduling, event loops, and nearest-frontier algorithms. Push and pop are logarithmic, peek is constant.

The Cache: Two Structures, One Job

A cache remembers a limited number of entries and forgets the rest. Coral's Cache is least-recently-used: when full and a new entry arrives, the coldest entry is evicted. It uses two structures, each doing what it does best.

pub struct CacheEntry<K, V>
{
    K key;
    V value;
    CacheEntry<K, V>* prev;
    CacheEntry<K, V>* next;
}

pub struct Cache<K, V>
{
    HashMap<K, CacheEntry<K, V>*> map;
    CacheEntry<K, V>* head;
    CacheEntry<K, V>* tail;
    usize maxSize;
    usize(K) hashFn;
    bool(K, K) eqFn;
}

The map finds an entry by key in constant time. The linked list keeps entries in recency order, most recent at the head, least recent at the tail. Every access moves the entry to the head in constant time; every insertion beyond the limit evicts the tail. The entry is both a list node and a map value, so the map stores a pointer to it. This is the pointer stability of section8.9 made useful.

import(lib) std::collections.cache { Cache };

Cache<u64, u64> table = Cache<u64, u64>::new(128, hashU64, eqU64);
table.insert(7, 49);
table.insert(11, 121);
Option<u64> hit = table.get(7);    // a hit also moves 7 to the hot end
if (hit.isSome())
    println("{}", hit.unwrap());

Every get is a map lookup plus a list move; every insert is a map insert, a list push, and at most one eviction, all constant time. The constructor's size is the maximum entries, defaulting to sixty-four when zero is passed.

The cache's characteristic use is memoization: turning a repeating computation into one that remembers. Naive recursive Fibonacci recomputes values exponentially; the memoized version computes each distinct argument once:

pub u64 fib(u64 n, Cache<u64, u64>* memo)
{
    Option<u64> hit = memo->get(n);
    if (hit.isSome())
        return hit.unwrap();
    u64 result = (n < 2) ? n : fib(n - 1, memo) + fib(n - 2, memo);
    memo->insert(n, result);
    return result;
}

Each call begins with a get; a hit returns the remembered answer, and a miss computes, stores, and returns. The cache turns exponential fib into linear. An unbounded table would grow forever; the cache stops at its maximum and evicts the least recently used answer, trading occasional recomputation for bounded memory.

Hierarchies: The Generic Tree

Some data is naturally a hierarchy: directories contain files and directories, companies have departments, sentences parse into phrases and words. Each is a node with children, and the generic tree is the library's container for that shape. It is a shape, not a search structure like the tree map.

pub struct TreeNode<T>
{
    T value;
    Vec<TreeNode<T>*> children;
}

pub struct Tree<T>
{
    TreeNode<T>* root;
}

A tree node is a value and a vector of pointers to child nodes. "Generic" means the value can be anything; vector children mean the number of children is not fixed, making this an n-ary tree. The tree itself is a pointer to the root.

The key property is that node pointers returned by setRoot and addChild are stable. A child is created, and the caller keeps its pointer to add grandchildren:

import(lib) std::collections.tree { Tree, TreeNode };

Tree<str> org = Tree<str>::new();
TreeNode<str>* ceo = org.setRoot("ceo");
TreeNode<str>* eng = org.addChild(ceo, "engineering");
TreeNode<str>* ops = org.addChild(ceo, "operations");
org.addChild(eng, "backend");
org.addChild(eng, "frontend");
org.addChild(ops, "platform");

pub void showOrg(str name) { println("{}", name); }
org.preOrder(showOrg);

eng points to the engineering node, and every later addChild naming eng hangs a child under it. preOrder visits the value before children; postOrder visits children first. depth measures the deepest chain, size counts nodes, and toVec collects every value.

The tree's costs are its pieces' costs: vector children give each node a growable child list, and nodes are individual allocations linked by pointers, so traversal walks scattered memory like a linked list. Use it when the hierarchy is the point.

Prefixes: The Trie

A trie is for "do many strings share prefixes?" Words are stored as a tree where each level holds one byte, so car, card, and cart share the path c-a-r and fork only at the end. The trie arranges words by character; the tree map arranges keys by comparison.

const u32 TRIE_FANOUT = 256;

pub struct TrieNode
{
    TrieNode* children[TRIE_FANOUT];
    bool isEnd;
}

pub struct Trie
{
    TrieNode* root;
    usize count;
}

Every node carries an array of 256 child pointers, one per byte value, and a flag marking whether a word ends there. Insert walks the bytes, creating missing nodes and setting isEnd at the final node. contains returns false when a child is missing and true only if the final node's isEnd is set, so cat is found but ca is not. startsWith is the same walk without the word-end check:

import(lib) std::collections.trie { Trie };

Trie dict = Trie::new();
dict.insert("cat");
dict.insert("cattle");
dict.insert("car");
dict.insert("dog");

if (dict.startsWith("ca"))
    println("there are words beginning with ca");
if (dict.contains("cat"))
    println("'cat' is a word");

Lookup costs the key's length and zero comparisons against other words: prefix membership is as cheap as the prefix is short, regardless of dictionary size. A trie stores a set of keys, not an associative map; for a payload per word, use a companion map.

Each node is 256 pointers, so a long word with no shared prefixes builds a chain of wide nodes, and memory is far heavier than a set of the same words. Use a trie when the question is "what begins with this" (autocomplete, spell-check, routing); use a set or map when it is "is this whole thing present."

Choosing Among the Collections

The collections are distinguished by the questions they answer. The access pattern usually decides.

When the count is known and fixed, use the array: the count is in the type, storage is the struct's, and there is nothing to grow or free. When the count is runtime-known and the work is appending, indexing, and iterating, use the vector. When both ends matter, the deque; when only arrival order matters, the queue; when the buffer must never grow, the ring buffer.

For finding a value by key with no order requirement, the hash map. When key order matters, the tree map. For membership, the set for arbitrary values and the bitset for a dense range. For always taking the most important next, the priority queue. For recent results under a bound, the cache.

For rearranging links and holding pointers to elements that must not move, the linked list. For a hierarchy, the generic tree. For prefixes, the trie. For "remember and return in reverse order," a vector used at one end: the stack.

Two axes organize the table. Order: the hash map and set promise none, the tree map promises key order, the array and vector promise insertion order, and the heap promises priority order. Storage: contiguous (array, vector, deque, ring buffer, bitset, heap) or scattered and linked (list, tree nodes, trie nodes, cache entries).

The same operation costs differently in different structures. Membership is constant in a hash set and logarithmic in a sorted search; finding the smallest is constant in a min-heap and linear in an unordered vector; getting the i-th element is constant in a vector and linear in a list. No structure is fast at everything.

Generic Containers, Requirements, and any Trait

Every collection here is a generic type. The compiler generates a concrete version per element or key type. Vec<i32> is a real array of i32, not a boxed void* array. There is no per-element indirection and no runtime type tag.

There are no bounds on a type parameter: you cannot write <T : Comparable>. The requirement on T is exactly the operations the body names, checked at each instantiation. That is why containers take key functions as parameters: a generic K has no built-in equality or hash, so the caller supplies them.

When the concrete type is not known until runtime, as in a heterogeneous collection, plugin registry, or dispatch table, use any Trait, a trait object. A trait names methods; a type conforms with an extend block; any Trait is the dynamic view:

trait Shape
{
    f64 area();
}

struct Circle { f64 radius; }
pub extend Circle : Shape
{
    f64 area() { return 3.14159 * self.radius * self.radius; }
}

struct Square { f64 side; }
pub extend Square : Shape
{
    f64 area() { return self.side * self.side; }
}

Vec<any Shape> shapes = Vec<any Shape>::new();
shapes.push(Circle { .radius = 1.0 });
shapes.push(Square { .side = 2.0 });
for (any Shape s : shapes)
    println("area = {}", s.area());

An any Shape value carries a reference to the value and a reference to its Shape implementation, so s.area() dispatches at runtime. That lets one collection hold different concrete types. The trade is an extra indirection per call, no inlining across the boundary, and only the trait's methods visible. Keep dynamic dispatch at boundaries and internals static, because a generic T is monomorphised and free.

A homogeneous collection with a compile-time element type wants a generic; a heterogeneous one, or one decided at runtime, wants any Trait. Neither is worse; they answer different questions.

Text as a Data Structure

Text is the data structure most programs touch most, and it obeys the same layout-and-cost reasoning. Coral's text layer has two types: str, the borrowed view, and String, the owned, growable buffer. Chapter 17 is the full treatment.

The view is a pointer and a length, owning nothing:

pub struct str
{
    const u8* ptr;
    usize len;
}

str is built in, and the standard library extends it with operations. A slice of a larger view is a new pointer and length into the same bytes, so slicing costs nothing:

str full = "coral";
str front = full.slice(0, 3);    // "cor"
str back = full.slice(3, 5);     // "al"

at reads a byte, findByte and findView search, startsWith and endsWith test the edges, and equals and compare compare text. Because the view borrows, reading functions take a str with no copying; it must not outlive the bytes it points at.

The string is the owning, growable buffer, a vector of bytes with capacity:

pub struct String
{
    u8* ptr;
    usize len;
    usize cap;
}

String grows by the same doubling strategy, so building by appending is linear with amortized copies. pushChar and pushView append, insertView and removeRange modify the middle, truncate cuts the end, and asView hands out a borrowed view:

String name = String::from("coral");
name.pushChar('!');
println("{}", name.asView());

The view borrows, the string owns. Reading code takes views; building code returns strings. The string's buffer must be contiguous and its views cheap; the text layer is the vector idea applied to bytes.

The Honest Boundaries

Two boundaries are worth stating plainly.

First, the standard library has no time or date types. There is no Duration, clock, calendar, or time zone under std. A program needing elapsed time or the wall clock must use the platform layer or a library; civil dates must be built from a raw second count.

Second, formatting. The fmt module provides typed functions: formatInt, formatUint, formatFloat, formatHex, formatBin, formatChar, padLeft, padRight, repeat, join, and joinVec, each returning a String. The general format(str f, ...) is a stub that does no placeholder substitution. For formatted output, use print and println, which take a comptime format string checked before the program runs:

import(lib) std::fmt { formatUint, padLeft };

String hex = formatUint(255, 16, false);    // "ff"
String pad = padLeft("7", 3, '0');          // "007"
println("{} and {} and {:x}", hex.asView(), pad.asView(), 255);

The println format supports {} for a value, {:x} and {:b} for bases, {:.3} for precision, {..} to spread an iterable, and {{/}} for literal braces. A mismatch is a build failure because the compiler sees both at the call site.

Everything named here exists under std::collections, with Vec, Arr, Option, and Result also reachable through root shortcuts. The method catalogue is Chapter 16.

Chapter 8 Summary

A data structure is a layout, a set of operations, and a cost; in Coral the layout is visible in the type's public fields.

Operations do address arithmetic to locate elements and sometimes movement to copy them; contiguous storage makes location cheap and movement expensive, and scattered storage reverses that.

Locality is the memory-system half of cost: contiguous elements share cache lines and iterate fast; linked elements miss per node.

Arr<T, N> is a fixed-size contiguous array with the count in the type and no heap allocation.

Vec<T> is a contiguous buffer that grows; push is amortized constant because growth doubles capacity.

withCap, reserve, and reserveExact let a caller who knows the count avoid growth; insert and removeAt are linear because they shift the tail.

A stack is a Vec used at one end, not a separate type; the delimiter matcher is its canonical use.

A linked list is a chain of individually allocated nodes connected by pointers; end operations are constant time and nothing moves, but access is linear and iteration misses the cache.

Linked-list nodes have stable addresses, so pointers survive insertions elsewhere, which is why intrusive structures such as the cache use one.

Deque<T> is a ring buffer with constant-time operations at both ends; Queue<T> wraps it as FIFO, and RingBuf<T> is the fixed-capacity ring that overwrites the oldest element.

Breadth-first search is the queue's canonical use, marking each node when discovered.

A hash map turns a key into a slot with a hash function and probes linearly; it needs caller-supplied hash and equality, and lookups are constant time on average.

The load factor keeps the table at most half full so probe clusters stay short; growth doubles capacity and rehashes every entry, amortized like the vector's growth.

The frequency counter is the map's canonical job: find each key's slot with getPtr and update in place in a linear pass.

Map<K, V> is an AVL tree that keeps keys in order, giving logarithmic operations and ordered iteration.

A Set<T> is a hash map of keys with a throwaway value, providing membership and set algebra; a Bitset answers the same question at one bit per element for a dense range.

PriorityQueue<T> is a heap encoded in an array, giving logarithmic push and pop and constant peek, with the caller's comparator deciding min versus max.

Cache<K, V> pairs a hash map for lookup with a doubly linked list for recency, so both operations are constant time.

Tree<T> is an n-ary hierarchy with vector children and stable node pointers; Trie stores strings by shared prefix.

Choosing a collection is choosing the question the program asks and the cost its access pattern can afford; no structure is fast at everything.

Every collection is a generic type; a generic's requirements are the operations its body names, checked at each instantiation. any Trait is the dynamic view for a heterogeneous collection.

str is a borrowed pointer-and-length view that slices for free; String is an owned, growable byte buffer following the vector's growth strategy.

The standard library has no time or date types, and fmt::format is a stub; formatted output goes through print and println and the typed fmt functions, all checked before the program runs.
