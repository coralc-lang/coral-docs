Collections and the Standard Library

A Language Without a Library Is a Set of Keywords

Remove every library from your language and only keywords and byte-moving remain. The container that holds an unknown-length list, the text buffer, and the lookup table all live in the standard library. The language is the grammar; the library is the vocabulary.

Coral's library is a tree of capabilities. Under std sit collections, text, io, fmt, math, memory, crypto, concurrent, parser, data, and testing; under collections, arr, vec, map, hashmap, unordered_map, set, queue, deque, ringbuf, priorityqueue, linkedlist, tree, trie, bitset, cache, iter, sort, and range.

std is the portable surface. core is what the language is built from: str (methods in core::str), cchar, char_util, and core::limits. Normal programs import from std; platform wraps the OS and is reached only close to the metal.

Two import spellings. The platform aggregator lib/std/x86_64/<platform>/lib.crl re-exports only option, result, vec, mman, allocator, and intrinsics, so std::vec, std::option, and std::result resolve. std::arr does not; use std::collections::arr or the prelude. Older notes may show std::arr; do not depend on it.

More plainly: the library is a tree, but a few leaves hang near the root so you need not climb. Writing:

coral
import(lib) std::vec { Vec };
import(lib) std::option { Option };
import(lib) std::result { Result };

uses three shortcuts equivalent to std::collections::vec, std::data::option, and std::data::result. This chapter uses full paths where they clarify which branch a type comes from.

The Whole Collections Surface at a Glance

Every module below lives under std::collections; the import column is the exact resolving path. Vec, Arr, Option, and Result also come from the compiler prelude, which loads core::str, std::io::ios, std::text::string, std::option, std::result, std::vec, and std::collections::arr into every unit, so those names need no import. The other container names do.

Three facts hold. Every container is generic and monomorphised (Vec<i32> and Vec<String> share one source, as in Chapter 7). No container takes an allocator: all use the process-wide allocator in std::memory::mman (alloc<T>, dealloc<T>, realloc<T>, routing to defaultAllocator), so arenas are separate (16.12). Struct fields have no visibility keyword, so Vec.data, Vec.len, Vec.cap, and MapEntry's fields are interface.

Vec<T>: The Dynamic Array

Vec<T> is the library's workhorse, and much else is built on or modelled after it.

You are reading records whose count you do not know. A fixed array cannot hold them; a linked list would hop across the heap and thrash the cache. You want an array that grows itself. That is a Vec.

Its declaration, quoted from std::collections::vec:

coral
pub struct Vec<T> {
    T*    data;
    usize len;
    usize cap;
}

data points at cap heap slots, len counts live elements, and cap is the allocation's room. Elements occupy data[0] through data[len - 1]; slots from len to cap exist but are not part of the value. Every operation is bookkeeping on these public numbers, which make a Vec a documented data structure.

A Vec is a stretchy shelf with cap slots and len books. Adding to a full shelf buys a bigger one, copies every book, and discards the old, so push is usually instant but occasionally does real work.

Create one with new, which allocates nothing, or withCap, which allocates room up front:

coral
import(lib) std::vec { Vec };

Vec<i32> a = Vec<i32>::new();
Vec<i32> b = Vec<i32>::withCap(1024);

new costs nothing until the first push, which allocates a small default capacity. withCap allocates immediately; when you know the count, allocate once and push a thousand times instead of reallocating and copying seven times.

The core operations:

coral
Vec<i32> v = Vec<i32>::new();
v.push(10);                 // append to the end
v.push(20);
v.push(30);

i32 last = v.pop();         // 30; removes and returns the last
usize n  = v.count();       // 3 before the pop, 2 after
bool e   = v.isEmpty();     // count() == 0

push appends; when len reaches cap it calls reserve, doubling capacity (or using 4 on first growth) and copying the elements. pop removes and returns the last element, trapping if empty, so guard with isEmpty. count reports len; isEmpty is count() == 0.

Access comes in several forms. at returns an element by value with a bounds check; set writes one; atPtr and atConst return mutable and const element pointers; ptr and constPtr return a pointer to the whole backing array:

coral
v.set(0, 99);                     // v[0] = 99
i32 x = v.at(0);                  // bounds-checked read, by value
i32* p = v.atPtr(1);              // pointer to element 1
const i32* cp = v.atConst(1);     // const pointer to element 1
i32* base = v.ptr();              // the whole array
const i32* cbase = v.constPtr();  // the whole array, read-only

at copies; atPtr and atConst point at the element in place, so writing through a T* mutates the vector. atPtr carries the same @assertOut(i < len) guard as at. Only ptr()/constPtr() are unchecked.

Moving elements:

coral
v.insert(0, 5);            // shift right, put 5 at the front
v.removeAt(0);             // shift left, drop the front
v.removeRange(1, 3);       // remove elements [1, 3)
v.fill(7);                 // every element becomes 7
v.reverse();               // in place
v.clear();                 // len = 0; the allocation is kept

insert and removeAt are O(n) because they shift the tail, the honest cost of contiguity. clear frees nothing; it sets len to zero so the allocation can be reused, ideal for a refill loop.

Ordered-sequence methods:

coral
bool sorted = v.isSortedBy(less);          // bool(T, T) less
v.sortBy(less);                            // in-place quicksort
i64 where = v.binarySearchBy(key, cmp);    // index, or -1

sortBy takes a bool(T, T) "a before b" predicate; binarySearchBy takes an i32(T, T) comparator returning negative, zero, or positive. The generic sort in std::collections::sort and the typed sortI32, sortF64, and sortusize share the idea; see 16.11.

Capacity management:

coral
v.reserve(4096);           // grow capacity to 4096 if it is smaller
v.reserveExact(4096);      // same effect: no-op if cap is already >= 4096
v.shrinkToFit();           // shrink the allocation to len
v.dispose();               // free the backing array now

Call shrinkToFit when a Vec has finished growing and may live long; it releases the slack doubling left behind. dispose frees the array immediately, and drop (via @drop) calls it when the value leaves scope. You rarely call dispose by hand; that is Chapter 11's RAII specialised to the container.

The two reserve methods are the same function in the shipped source: both return if capacity suffices, otherwise realloc once to the requested size. Doubling belongs to push alone (reserve(cap * 2) when full, reserve(4) on the first push). The names differ by intent, not implementation.

Membership and end methods:

coral
bool here = v.contains(30);    // linear scan, equality on T
i32 f = v.front();             // v.at(0), asserts if empty
i32 b = v.back();              // v.at(len - 1), asserts if empty

contains is an O(n) scan using ==; it is not hashed membership and needs no equality function passed in, because == on the element type must already exist. front and back are at(0) and at(count() - 1) with the same bounds assertion.

The complete method set, source order: new, withCap, reserve, push, pop, count, atPtr, atConst, at, ptr, isEmpty, constPtr, set, front, back, insert, removeAt, removeRange, contains, fill, reserveExact, shrinkToFit, clear, reverse, isSortedBy, sortBy, binarySearchBy, dispose. (Private _sortByRange and _partitionBy drive sortBy.) A Vec is an array with a length; algorithms belong in iter and sort.

Iterate by index or range-for:

coral
for (usize i = 0; i < v.count(); i += 1) {
    println("{}", v.at(i));
}

for (i32 value : v) {
    println("{}", value);
}

Range-for is the idiomatic read: each element once, in order, with the index hidden. Use the indexed form only when you need the index.

A complete program that builds a Vec and sums it:

coral
import(lib) std::io::ios { println };
import(lib) std::vec { Vec };

void main() {
    Vec<i32> scores = Vec<i32>::new();
    scores.push(90);
    scores.push(85);
    i32 total = 0;
    for (i32 s : scores) {
        total += s;
    }
    println("total = {}", total);
}

Almost every real program keeps an unknown-length list: file lines, players, query results. Vec grows to hold them.

Arr<T, N>: Fixed Size, Inline Storage

Arr<T, N> is Vec's fixed-size sibling: the length is part of the type, known at compile time, and storage is inline rather than behind a pointer.

coral
import(lib) std::collections::arr { Arr };   // note: "std::arr" does not resolve; the prelude also provides Arr
Arr<i32, 4> location = Arr<i32, 4> { 1, 2, 3, 4 };

The declaration, the smallest container in the library:

coral
pub struct Arr<T, N> {
    T data[N];
}

No pointer, length field, or capacity: N is the length, and data is the storage. A value is exactly N * @sizeof(T) bytes; copying copies every element, so pass a pointer unless it is small. N is a comptime parameter, so generic code over unknown lengths must be generic over N.

Because N is a compile-time constant, constant indices are checked at compile time, so an out-of-range constant is a build error. The API mirrors Vec: ptr, constPtr, count, isEmpty, at, set, atPtr, front, back, fill, copyTo, and copyFrom:

coral
location.set(0, 9);
i32 first = location.front();
i32 last  = location.back();
i32 buf[4];
location.copyTo(buf);          // copy every element out
location.copyFrom(buf);        // copy every element in

count() returns N, and isEmpty() is N == 0, so Arr<T, 0> is legal and always empty. at, set, and atPtr assert i < N at runtime even though N is known; the assertion is the contract. There is no dispose, drop, or free (an Arr owns no heap), and no insert or push.

Arr is for genuinely fixed sizes: a 3-component vector, 2x2 matrix, fixed header, or comptime-sized lookup table. It needs no heap and its size is a compiler fact. A plain T name[N] is the same storage without the methods.

Map<K, V>: The Ordered Associative Container

Coral's ordered map is an AVL tree, so iteration is deterministic in key order and range-shaped queries are possible. The price is O(log n) per operation instead of O(1).

The declaration explains the API:

coral
pub struct Map<K, V> {
    MapEntry<K, V>* root;
    usize len;
    i32(K, K) cmpFn;
    bool failed;
}

The map cannot compare arbitrary keys, so it is handed an i32(K, K) comparator at construction, returning negative, zero, or positive as qsort and strcmp do:

coral
import(lib) std::collections::map { Map };

i32 cmpStr(str a, str b) { return a.compare(b); }

Map<str, i32> ages = Map<str, i32>::new(cmpStr);
ages.insert("ada", 36);
ages.insert("grace", 45);

if (ages.contains("ada")) {
    Option<i32> a = ages.get("ada");
    println("ada = {}", a.unwrap());
}
ages.remove("grace");

Two things matter. insert returns Result<V, CollectionError>, because the AVL tree allocates and allocation can fail (CollectionError has an AllocFailed case). get returns Option<V>, the honest "a value, or nothing" from Chapter 15:

coral
Option<i32> maybe = ages.get("ada");
if (maybe.isSome()) {
    i32 a = maybe.unwrap();
}
i32 definitelyThere = ages.get("ada").unwrapOr(-1);

To modify in place rather than copy out, getPtr returns Option<V*>:

coral
Option<i32*> slot = ages.getPtr("ada");
if (slot.isSome()) {
    *slot.unwrap() = *slot.unwrap() + 1;   // increment in place
}

Because a Map is ordered, iteration is in key order via each, since the map implements no @iter:

coral
void printAge(str key, i32 value) {
    println("{} = {}", key, value);
}
ages.each(printAge);

The callback receives key and value and returns nothing. This is how Coral walks containers other than Vec or Arr: hand it a function, not a cursor. _eachInOrder recurses left, calls fn, then recurses right, so keys arrive in ascending comparator order.

The method set: new, dispose, count, isEmpty, insert, get, getPtr, contains, remove, clear, each. remove and clear return nothing; ask contains if needed. insert overwrites an existing key or allocates one MapEntry, the only fallible operation. _insert balances the AVL tree with at most one single or double rotation; _remove rebalances on the way out. Lookup is O(log n); contains, get, and getPtr share _find.

insert returns Result<V, CollectionError>::Ok { .value = value }, handing your value back, so it is not "insert-or-update returning the old value." AVL deletion copies the in-order successor's key and value up, then deletes the successor; for owning types this moves the same object between nodes, which is fine because the map never frees keys or values (16.12).

There is no @iter implementation, no reverse iteration, firstKey/lastKey, or range scan. For descending order, collect keys with each into a Vec<K> and reverse, or pass a negated comparator (i32 reverseCmp(K a, K b) { return -cmpAsc(a, b); }), which keeps the AVL invariants. For "all keys in [lo, hi)", collect and filter, or use a structure with a range operation.

The Hashed Maps: HashMap and UnorderedMap

When you do not need order but want speed, use a hash table. HashMap<K, V> is linear-probing with O(1) average operations:

coral
pub struct HashMap<K, V> {
    HashMapEntry<K, V>* entries;
    usize cap;
    usize len;
    usize(K) hashFn;
    bool(K, K) eqFn;
}

Hashing needs two functions a generic container cannot invent: a hash and an equality test. You supply both, deciding what "the same key" means:

coral
import(lib) std::collections::hashmap { HashMap };

usize hashStr(str k) {
    usize h = 5381;
    for (usize i = 0; i < k.len; i += 1) h = h * 33 + (usize)k.ptr[i];
    return h;
}
bool eqStr(str a, str b) { return a.equals(b); }

HashMap<str, i32> counts = HashMap<str, i32>::new(hashStr, eqStr);
counts.insert("apple", 3);
counts.insert("pear", 1);

The API is close to Map's: insert (Result), get and getPtr (Option), contains, remove, removeEntry, clear, count, keys, values, each, eachEntry. HashMap has no isEmpty; use count() == 0. Map and Set both have one, so the omission trips people up.

The table starts at capacity 16 and doubles when len * 2 >= cap, re-homing occupied entries. Collisions use linear probing with step one; lookups stop at the first unoccupied slot (with a wrap guard). Order is not promised: each, keys, and values return slot order, a function of hash values, not insertion.

A coat check computes a hook from your ticket; two guests can collide, so the rule adds "if taken, try the next one." Lookup runs the same rule and walks the same short chain. A hash returning the same value for many keys still works, but every lookup becomes a linear scan and O(1) becomes O(n).

each walks occupied entries in slot order; eachEntry hands you a pointer to the live HashMapEntry instead of copies:

coral
void report(str key, i32 value) { println("{}: {}", key, value); }
counts.each(report);

eachEntry's pointer is the hook for keys or values that own memory. remove discards the entry; removeEntry returns it by value (Option<HashMapEntry<K, V>>) so the caller can dispose of owned data first. Backward-shift deletion keeps probing chains intact, so insertion need not distinguish "empty" from "deleted."

UnorderedMap<K, V> states in the type that iteration order is not promised. It forwards every HashMap operation, so nobody can depend on an unguaranteed order. It adds isEmpty (inner.count() == 0) and its own @drop. Methods: new, dispose, count, isEmpty, insert, get, getPtr, contains, remove, clear, keys, values, each. eachEntry and removeEntry exist only on HashMap.

coral
import(lib) std::collections::unordered_map { UnorderedMap };
UnorderedMap<str, i32> cache = UnorderedMap<str, i32>::new(hashStr, eqStr);

The three-map split reflects a principle: when behaviours differ, they are two types with two names, not one type with a flag. A flag would let a caller depend on an order HashMap never promised; two types make the promise explicit in every signature.

Set<T>

A set is a map without values: it answers "is this present?" and enforces uniqueness. Coral's Set is a HashMap<T, bool> underneath with the same two functions:

coral
pub struct Set<T> {
    HashMap<T, bool> inner;
    usize(T) hashFn;
    bool(T, T) eqFn;
}

import(lib) std::collections::set { Set };

Set<str> seen = Set<str>::new(hashStr, eqStr);
seen.insert("apple");
seen.insert("banana");
seen.insert("apple");          // no effect; already present

if (seen.contains("apple")) { ... }
seen.remove("banana");
seen.each(printStr);

Sets are the natural tool for deduplication, membership, and set algebra, which the library provides directly:

coral
Set<str> a = Set<str>::new(hashStr, eqStr);
Set<str> b = Set<str>::new(hashStr, eqStr);
// ... fill both ...

Set<str> both  = a.union(&b);
Set<str> share = a.intersection(&b);
Set<str> onlyA = a.difference(&b);
bool aInB      = a.isSubset(&b);       // every element of a is in b
bool aCoversB  = a.isSuperset(&b);     // every element of b is in a
Vec<str> asList = a.toVec();

Methods: new, dispose, count, isEmpty, insert, contains, remove, clear, toVec, each, union, intersection, difference, isSubset, isSuperset. insert returns nothing, not a Result: duplicates are not counted. The algebra methods take const Set<T>* and return a new Set<T> using the receiver's hash and equality functions, disposed independently; inputs are unchanged. isSubset and isSuperset allocate a temporary Vec<T>.

Set is unordered; there is no HashSet alias and no ordered set in std::collections. For ordered traversal, use Map<K, V> with V = bool and walk it with each, which visits keys in comparator order.

Printing each distinct word is a Set in a few lines:

coral
Set<str> words = Set<str>::new(hashStr, eqStr);
for (str w : splitVec(text, ' ')) {
    words.insert(w);
}
words.each(printStr);

For a handful of items a scan is faster and simpler; for thousands, the set's O(1) membership wins.

Queue, Deque, and RingBuf

Order matters as much as membership. Queue<T> is first-in-first-out, a thin wrapper over Deque exposing only one end:

coral
pub struct Queue<T> {
    deque::Deque<T> inner;
}

import(lib) std::collections::queue { Queue };

Queue<i32> q = Queue<i32>::new();
q.enqueue(1);
q.enqueue(2);
q.enqueue(3);
i32 first = q.dequeue();       // 1, FIFO
i32 front = q.peek();          // 2, without removing

usize n = q.count();
bool empty = q.isEmpty();
q.clear();

A Queue is a checkout line: first in, first served, add at the back, take from the front. Deque<T> has a second door, so you can join or leave at either end. RingBuf<T> is a fixed-size circular conveyor that knocks off the oldest item when full, the shape for "the last N readings."

Do not use a Vec as a queue by calling removeAt(0): each removal slides every remaining element down, O(n) where a Queue is O(1). Use the container whose name says "queue."

Deque<T> is a growable ring supporting both ends, the structure for a work list that grows at both ends and for a sliding window:

coral
import(lib) std::collections::deque { Deque };

Deque<i32> d = Deque<i32>::new();
d.pushBack(2);
d.pushFront(1);
i32 left  = d.popFront();      // 1
i32 right = d.popBack();       // 2
i32 at    = d.at(0);           // random access by logical index
d.set(0, 9);

RingBuf<T> is a fixed-capacity ring with wrapping head and tail indices. It never allocates after construction, and when full, pushing overwrites the oldest element, ideal for a logging buffer or recent-history window:

coral
import(lib) std::collections::ringbuf { RingBuf };

RingBuf<f64> samples = RingBuf<f64>::new(1024);
samples.push(sample);          // overwrites the oldest once full

usize held = samples.count();
bool full  = samples.isFull();
f64 oldest = samples.front();
f64 newest = samples.back();

The method sets are small. Queue<T>: new, dispose, count, isEmpty, enqueue, dequeue, peek, clear, plus @drop. Deque<T>: new, dispose, count, isEmpty, capacity, pushFront, pushBack, popFront, popBack, front, back, at, set, clear, plus @drop. RingBuf<T>: new, dispose, count, isEmpty, isFull, capacity, push, pop, front, back, at, clear, plus @drop.

Deque reserves one slot to distinguish full from empty: Deque::new() allocates 8 but capacity() reports 7, and _grow runs when count() >= cap - 1. Deque mask-indexes a power-of-two array; RingBuf uses % cap, so new(1024) and new(1000) are legal, and new(0) asserts. clear resets head/tail but abandons element slots, which matters for owning types (16.12). popFront, popBack, dequeue, pop, front, back, at, and set carry @assert guards.

The overlap is intentional: Queue is the simplest one-ended interface, Deque adds the other end, RingBuf adds a size bound and no-allocation guarantee. Pick the one whose constraints you need, so the type documents the constraint.

PriorityQueue<T>

A priority queue always hands you the smallest element, or the largest with a reversing comparator. It is a binary heap over Vec-like storage:

coral
pub struct PriorityQueue<T> {
    T* data;
    usize len;
    usize cap;
    bool(T, T) less;
}

import(lib) std::collections::priorityqueue { PriorityQueue };

bool lessI32(i32 a, i32 b) { return a < b; }

PriorityQueue<i32> pq = PriorityQueue<i32>::new(lessI32);
pq.push(5);
pq.push(1);
pq.push(3);
i32 min = pq.pop();            // 1
i32 peeked = pq.peek();        // the next one out, without removing

The comparator is bool(T, T) less, "is a strictly before b?", the same shape Vec's sortBy uses. For a max-heap, pass bool greaterI32(i32 a, i32 b) { return a > b; }. Priority queues drive Dijkstra's algorithm, event simulation, and scheduling; we use one for ranking below.

A flat binary heap: children of i are 2*i + 1 and 2*i + 2, the parent (i - 1) / 2. push appends and sifts up; pop moves the last element to the root and sifts down. The array starts at 16 and doubles in _grow. Methods: new, dispose, count, isEmpty, push, pop, peek, clear, plus @drop. peek and pop assert on emptiness. No decreaseKey or arbitrary remove: decrease-key uses lazy deletion (push a duplicate, discard stale pops). clear resets len and keeps the array.

LinkedList<T>

A linked list is a chain of nodes. Use it sparingly: arrays usually win on cache locality, but a list wins for O(1) insertion/removal given a cursor and expresses intrusive pointer-linked structures.

coral
import(lib) std::collections::linkedlist { LinkedList };

LinkedList<i32> l = LinkedList<i32>::new();
l.pushBack(1);
l.pushBack(2);
l.pushFront(0);

i32 head = l.front();
i32 tail = l.back();
i32 popF = l.popFront();
i32 popB = l.popBack();
l.each(printI32);

The node type is part of the interface, because insertAfter and remove take a cursor:

coral
pub struct ListNode<T> {
    T value;
    ListNode<T>* prev;
    ListNode<T>* next;
}

The method set: new, dispose, count, isEmpty, pushFront, pushBack, popFront, popBack, front, back, insertAfter, remove, each, plus @drop. insertAfter(null, val) appends at the front, and remove(null) does nothing. Every push allocates one node, so memory tracks len exactly, and there is no at: random access means walking each and counting. End operations assert on emptiness.

The library provides it because some interfaces and designs genuinely want it; it is not the default list. The default is Vec.

Tree and Trie

Two specialised structures round out the collection family.

Tree<T> is a general tree, a node with children: a file system, scene graph, syntax tree, or org chart. Nodes hold a value and a vector of child pointers:

coral
pub struct TreeNode<T> {
    T value;
    Vec<TreeNode<T>*> children;
}

pub struct Tree<T> {
    TreeNode<T>* root;
}

import(lib) std::collections::tree { Tree };

Tree<str> root = Tree<str>::new();
TreeNode<str>* r = root.setRoot("root");
TreeNode<str>* docs = root.addChild(r, "docs");
TreeNode<str>* src  = root.addChild(r, "src");

usize kids = root.childCount(r);
Option<TreeNode<str>*> first = root.childAt(r, 0);
root.preOrder(printNodeValue);     // depth-first, parent first
root.postOrder(printNodeValue);    // depth-first, children first
usize d = root.depth(r);
usize total = root.size();
Vec<str> flat = root.toVec();

Because a Tree is not a Vec, iteration uses preOrder and postOrder, taking a void(T) function. Methods: new, dispose, isEmpty, setRoot, addChild, childCount, childAt, removeChild, preOrder, postOrder, depth, size, toVec, plus @drop. setRoot on an existing tree disposes the old tree; addChild(null, val) returns null; removeChild(parent, i) disposes the child's subtree; childAt returns an Option. depth(node) is subtree height (leaf 1, null 0), size() counts every node, and toVec is pre-order. Tree never drops T: dispose frees nodes and child arrays; the caller frees values.

Trie is a prefix tree keyed on string bytes, ideal for autocomplete, dictionaries, and routing, where the query is "all keys with this prefix":

coral
import(lib) std::collections::trie { Trie };

Trie dict = Trie::new();
dict.insert("car");
dict.insert("cart");
dict.insert("cat");

if (dict.contains("car")) { ... }
if (dict.startsWith("ca")) { ... }
bool removed = dict.remove("cart");
dict.each(printWord);

A trie stores keys, not payloads, so insert takes only the key; use a companion Map for values. Methods: new, dispose, size, isEmpty, insert, contains, startsWith, remove, each, plus @drop. Each TrieNode holds TrieNode* children[256] and bool isEnd; keys are walked byte by byte, so a multi-byte UTF-8 character is several edges. contains requires the walk to end on an isEnd node, unlike startsWith. remove clears the end marker and prunes empty branches. size() is the key count.

One subtlety: each uses a scratch byte buffer sized to the deepest key and builds callback arguments with str::fromParts(buf, depth). Each string views that buffer, so it is valid only during the callback; copy it (for example with String::from) to keep it. Children are visited 0..255, so each yields ascending byte order, lexicographic for ASCII.

Bitset and Cache

Bitset is a fixed-width set of bits packed into 64-bit words, right for a dense set of small non-negative integers, visited graph nodes, or feature flags, where a Set<usize> would spend 64 bits per bit.

coral
import(lib) std::collections::bitset { Bitset };

Bitset visited = Bitset::new(256);
visited.set(42);
visited.toggle(7);
if (visited.test(42)) { ... }
visited.clear(42);

u64 setBits   = visited.countOnes();
u64 clearBits = visited.countZeros();
bool any      = visited.hasAny();
bool allSet   = visited.all();

Bitsets also do in-place bitwise algebra, which is how they earn their keep on sets of nodes:

coral
visited.and(&other);
visited.or(&other);
visited.xor(&other);
visited.not();
visited.setAll();
visited.clearAll();

Methods: new, dispose, count, wordCount, set, clear, toggle, test, setAll, clearAll, countOnes, countZeros, hasAny, none, all, and, or, xor, not, plus @drop. count() returns numBits, the construction width, not countOnes(). wordCount() is ceil(numBits / 64). set, clear, toggle, and test assert bit < numBits. and, or, xor, and not mutate in place; the first three assert equal widths. Unused high bits are masked, so all() requires every numBits bit. There is no get alias, and a Bitset cannot grow.

Cache<K, V> is a bounded, eviction-aware map for when a map must not grow without limit. The policy is true LRU: a hit moves the entry to the most-recently-used end; a full cache drops the coldest. It takes a maximum, hash, and equality:

coral
import(lib) std::collections::cache { Cache };

Cache<str, Page> pages = Cache<str, Page>::new(128, hashStr, eqStr);

pages.insert(url, fetch(url));      // may evict the coldest
Option<Page> hot = pages.get(url);  // a hit moves it to the hot end
Option<Page*> p  = pages.getPtr(url);
bool here = pages.contains(url);
pages.remove(url);
pages.each(visitPage);
pages.resize(256);

The structure is a HashMap<K, CacheEntry<K, V>*> plus a doubly-linked recency list (head most recent, tail least recent). Methods: new, dispose, count, maxSizeValue, insert, get, getPtr, contains, remove, clear, each, resize, plus @drop. There is no isEmpty; use count() == 0. new clamps a non-positive maximum to 64 and resize to at least 1. insert adds at the head and evicts from the tail while count() > maxSize. get and getPtr move a hit to the head; contains does not. each walks most recent first. dispose and _evict free entries, not keys or values.

We use the standard-library LRU cache in the second worked example.

Iteration, iter, and sort

Three utilities cut across every container, the first being the @iter protocol that drives the ranged for of Chapter 4.

Iteration is index based. A container opts in by providing count(), at(usize i), and, for bounded loops, IterRange range(usize start, usize end) in an @iter extend block. The ranged for asks count() once, then at(i) per index. The types that opt in are Vec, Arr, Deque, RingBuf, Queue, LinkedList, PriorityQueue, and Bitset; the associative containers (Map, HashMap, Set, Tree, Trie, Cache, UnorderedMap) do not, having no single canonical indexed order, and are walked with each(). IterRange, with fields start and end, lives in std::collections::range:

coral
import(lib) std::collections::range { IterRange };

for (var x : v)             { ... }   // whole vector
for (var x : v(1, 3))       { ... }   // indexes 1 and 2, half-open
for (var x : v.range(1, 3)) { ... }   // the same, method spelling

The bounded form clamps its bounds to count() and treats end < start as an empty loop, so a runtime range never indexes out of bounds. The loop variable is a copy; use an index loop with atPtr() to write through it.

std::collections::sort implements ordering on Vecs, with typed entry points and a generic one:

coral
import(lib) std::collections::sort {
    sortI32, sortF64, sortusize,
    sortBy, isSortedI32, binarySearchI32,
    binarySearchBy, reverse
};

Vec<i32> v = Vec<i32>::new();
v.push(3); v.push(1); v.push(2);
sortI32(&v);                            // ascending

bool ordered = isSortedI32(&v);
isize idx = binarySearchI32(&v, 2);     // index, or -1

For other element types, sortBy takes a "less than" predicate and binarySearchBy takes a three-way comparator:

coral
sortBy(&v, lessSomeType);
isize where = binarySearchBy(&v, key, cmpSomeType);

std::collections::iter provides adaptors that make bulk operations read as transformations rather than loops. Each takes a Vec pointer and a function, returning a new Vec or a folded value:

coral
import(lib) std::collections::iter {
    map, filter, reduce, forEach, find, findIndex,
    hasAny, all, take, skip, slice, zip,
    countIf, minBy, maxBy, unique, flatten,
    enumerate, sum, average
};

Vec<i32> doubled = map(&v, double);
Vec<i32> evens   = filter(&v, isEven);
i32 total        = reduce(&v, 0, add);
i32 biggest      = maxBy(&v, lessI32);
usize howMany    = countIf(&v, isEven);
Vec<i32> firstTwo = take(&v, 2);
Vec<i32> rest     = skip(&v, 2);
Vec<usize> indices = enumerate(&v);
i32 s            = sum(&v);
f64 avg          = average(&f64v);

The pipeline reads in operation order, which a loop with a temporary loses. The folder is reduce, not fold; typed sorts are sortI32 and friends; every adaptor takes a pointer, so map(&v, f).

These adaptors turn a loop into a sentence: map does this to every element and collects the results, filter keeps only approved elements, and reduce boils the list to one value.

Allocators: map, filter, take, skip, slice, zip, unique, flatten, enumerate return new Vecs. Scalars: reduce, forEach, find, findIndex, hasAny, all, countIf, minBy, maxBy, sum, average. find returns T() on no match, so 0 is ambiguous; use findIndex (isize or -1). minBy, maxBy, and sum assert non-empty; average returns 0.0 for empty. slice is half-open and clamps; invalid bounds return empty. zip stops at the shorter input and yields Pair with first and second. enumerate returns indices. unique is O(n^2). flatten takes Vec<Vec<T>>*.

sort is median-of-three quicksort, as Vec::sortBy uses. sortI32, sortusize, sortF64, sortBy, and reverse mutate in place and take a non-const Vec<T>*; isSortedI32, isSortedusize, isSortedBy, binarySearchI32, binarySearchusize, and binarySearchBy take const Vec<T>*. Typed sorts use <, so sortF64 inherits NaN behaviour. binarySearchBy takes a three-way comparator; searches return isize or -1, not an insertion point. Neither iter nor sort is an @iter adapter: the helpers in iter take a Vec<T> pointer, so use the ranged for when iterating another collection.

Ownership, Allocation, and Who Frees What

Two questions hide under "ownership." First, who frees the container's own storage. Second, who frees what the elements point at. Getting the first right and the second wrong is the most common leak with these types.

Every allocating container uses the process-wide allocator in std::memory::mman: alloc<T>, dealloc<T>, realloc<T>, forwarding to defaultAllocator. There is no allocator parameter, per-container policy, or arena field. dispose() frees exactly the container's backing storage and nothing else:

  • Vec<T> deallocates its element array (never touching the elements).
  • Arr<T, N> owns inline storage; it has no dispose and nothing to free.
  • Map<K, V> walks the tree and frees each MapEntry node.
  • HashMap<K, V> deallocates its entries array.
  • UnorderedMap forwards to its inner HashMap; Set<T> to its HashMap<T, bool>.
  • Deque, Queue, RingBuf, and PriorityQueue deallocate their backing arrays.
  • LinkedList frees each ListNode.
  • Tree frees each TreeNode and each node's child Vec (the arrays only), walking children before parents.
  • Trie frees each TrieNode; Bitset deallocates its word array.
  • Cache frees each CacheEntry and disposes its inner HashMap.

None of those disposals calls an element destructor. Vec<String>::dispose frees the String headers but not their character buffers; Map<str, String>::dispose leaks every value; Cache<str, Page>::dispose leaks every Page. There is no cascade because the element type is arbitrary. Every collection file opens with #[[no_drop_all]], turning off drop-trait auto-RAII (Chapters6, 10, and 11), and the @drop conformances only call dispose.

For a container of owning values, clean up before disposing, as std::parser::ini does: IniSection holds a HashMap<String, String>, and its dispose frees every key and value before the table.

coral
void freeEntry(HashMapEntry<String, String>* e) {
    e->key.free();
    e->value.free();
}
void dispose() {
    self.entries.eachEntry(freeEntry);   // free every owned key and value
    self.entries.dispose();              // then free the table's storage
}

eachEntry hands you a pointer to the live entry so you can free what it owns while reachable. HashMap::removeEntry returns an entry by value for the same reason. On a Vec<String>, use for (usize i = 0; i < v.count(); i += 1) v.atPtr(i)->free(); before v.dispose().

A Vec<T*> owns the pointer array, not the pointees; disposing it frees no T. std::memory offers SmartPtr<T> (init, dispose, get, data, constData, set, isValid, take) and reference-counted SharedPtr<T> (init, dispose, get, data, constData, refCount, isValid), both @drop. The container will not drop elements, so walk it and dispose each smart pointer, or scope the elements. SharedPtr<T> has no retain/clone; copying raises its count, and the last copy frees the object.

Allocation strategy is a separate facility. For an arena reset at once, a pool of same-sized nodes, or a fixed buffer, std::memory provides Allocator (a context pointer plus alloc, free, realloc pointers) and concrete allocators that fill it in:

coral
import(lib) std::memory::mman {
    AllocError, alloc, dealloc, realloc,
    FixedBufferAllocator, StackFallbackAllocator, ArenaAllocator,
    PoolAllocator, ScopeAlloc, LoggingAllocator,
    libcAllocator, miAllocator, cAllocator, pageAllocator, defaultAllocator,
    initDefaultAllocator, ensureDefaultAllocator, deinitDefaultAllocator
};
import(lib) std::memory::allocators::allocator { Allocator };  // ctx + alloc/free/realloc fn ptrs
import(lib) std::memory::pool { Pool };

Pool<T> is a fixed-size pool for one T. initDefaultAllocator() and deinitDefaultAllocator() set up and tear down the global allocator; ensureDefaultAllocator() is idempotent. Containers use that global allocator, so another strategy means using these types directly; supplying an allocator to a Vec is impossible. See Chapter 11 and Appendix A for AllocError.

A Worked Example: Word Frequency

Count each word and print the ten most frequent. A hashed map counts, its key list fans out, and a priority queue ranks. The word read from a line is a borrowed str that dies with the next line, so the map must own and free its keys (16.12).

coral
import(lib) std::io::ios { println, readLine };
import(lib) std::text::strutil { splitVec, trim };
import(lib) std::collections::hashmap { HashMap, HashMapEntry };
import(lib) std::collections::priorityqueue { PriorityQueue };
import(lib) std::text::string { String };

// The keys are owned Strings, so hash and compare their bytes (FNV-1a).
usize hashString(String s) {
    str v = s.asView();
    u64 h = 14695981039346656037u;
    for (usize i = 0; i < v.len; i += 1) {
        h ^= (u64)(u8)v.ptr[i];
        h *= 1099511628211u;
    }
    return h;
}
bool eqString(String a, String b) { return a.asView().equals(b.asView()); }

struct WordCount {
    str word;            // a view; valid while the map that owns it lives
    i32 count;
}

bool moreFrequent(WordCount a, WordCount b) {
    return a.count > b.count;          // under `less`, larger counts pop first
}

void freeEntry(HashMapEntry<String, i32>* e) { e->key.free(); }

void main() {
    HashMap<String, i32> counts = HashMap<String, i32>::new(hashString, eqString);

    String line = String::new();
    while (readLine(&line)) {
        if (line.isEmpty()) break;
        for (str raw : splitVec(line.asView(), ' ')) {
            str trimmed = trim(raw);
            if (trimmed.len == 0) continue;

            String key = String::from(trimmed);   // take a copy we can own
            key.toLower();
            Option<i32*> slot = counts.getPtr(key);
            if (slot.isSome()) {
                i32* p = slot.unwrap();
                *p = *p + 1;
                key.free();                       // already present; drop the probe
            } else {
                (void)counts.insert(key, 1).unwrap();   // the map keeps this buffer
            }
        }
    }

    PriorityQueue<WordCount> top = PriorityQueue<WordCount>::new(moreFrequent);
    Vec<String> words = counts.keys();            // shallow copies sharing the map's buffers
    for (usize i = 0; i < words.count(); i += 1) {
        String w = words.at(i);
        top.push(WordCount { .word = w.asView(), .count = counts.get(w).unwrap() });
    }

    for (i32 i = 0; i < 10 && !top.isEmpty(); i += 1) {
        WordCount wc = top.pop();
        println("{}: {}", wc.word, wc.count);
    }

    counts.eachEntry(freeEntry);   // free every key buffer the map owns ...
    counts.dispose();              // ... then the hash table's storage
    words.dispose();
    top.dispose();
}

The HashMap accumulates counts and owns each key because each borrowed word was copied into a String. keys gives the distinct words, and the WordCount views are safe because the key buffers outlive the ranking loop. The PriorityQueue orders by comparator, so the top ten are the first ten pops. Since the map does not free keys, eachEntry(freeEntry) releases every buffer before dispose frees the table.

A Worked Example: An LRU Page Cache

The second example uses the Cache container for its intended task, then shows what building it by hand would cost.

coral
import(lib) std::collections::cache { Cache };
import(lib) std::text::string { String };

usize hashStr(str k) { ... }        // as above
bool eqStr(str a, str b) { return a.equals(b); }

struct Page { String contents; }

Cache<str, Page> pages = Cache<str, Page>::new(256, hashStr, eqStr);

Page* fetchPage(str url) {
    Option<Page*> hot = pages.getPtr(url);
    if (hot.isSome()) {
        return hot.unwrap();        // touched; stays hot
    }
    Page fresh = loadFromNetwork(url);
    pages.insert(url, fresh);       // may evict the coldest
    return pages.getPtr(url).unwrap();
}

Eviction is the container's business: insert removes the least-recently-used entry if full; get and getPtr move a hit to the hot end. A hand-rolled version is thirty lines with the classic bug of not moving an element on a get, visible only under load. The library fixes it once.

Two caveats from 16.12. The keys are str views stored as-is; if url points into a caller's buffer, that buffer must outlive the cache. A production version would key on an owned String and free keys with an eachEntry pass. Second, Cache has no eviction callback: _evict frees the CacheEntry, and neither it nor dispose touches key or value, so a Page owning a String leaks on every eviction and at shutdown. Use it with handles or plain data managed elsewhere; with owning values, sweep before dispose.

  2. ComprehensionWhy are data, len, and cap public rather than hidden? Give one advantage and one risk.
  3. ImplementationGiven Vec<i32>, return doubled elements with zeros removed using map and filter, then rewrite with an explicit loop and compare.
  4. ContainersBuild an LRU cache by hand with HashMap and LinkedList, then replace it with Cache. Compare line counts and easy-to-miss operations.
  5. SignaturesWrite from memory the parameter lists of Map::new, HashMap::new, Set::new, and Cache::new, then check Appendix A. Why one i32(K, K) versus usize(K) and bool(K, K)?
  6. OwnershipDeclare a Vec<T*> of allocated pointers. Free the Vec, then each pointee: what order is correct, and what breaks otherwise? Rewrite with SmartPtr<T> and explain why the container still does not release them.
  7. SetsGiven two Vec<str> of names, compute their intersection as Set<str>. Give the running time, why it beats nested loops, then repeat with Set::difference.
  8. PriorityChange the word-frequency program to print the ten least frequent words. What changes, what does not, and what must you watch in the comparator?
  9. BetweenA circular audio-sample buffer is written fast, read slower, and must never allocate. Which container, why not Deque, and what happens when it fills?
  10. BitsetRepresent a 512-node graph's adjacency as Bitset. How much storage does this save over Set<usize> or Vec<bool>? Use and, or, and countOnes to count common neighbours.
  11. TrieBuild a Trie of a few hundred words and count stored words with a given prefix. (Hint: startsWith gives presence; counting needs an each pass into a Vec<str>.)
  12. MetaThe library has Map, HashMap, and UnorderedMap, plus Queue, Deque, and RingBuf. Argue for and against this proliferation. Where is the line between a useful distinction and a one-time choice?
  13. OwnershipA HashMap<String, String> goes out of scope and dispose runs. What is freed, what leaks, and what eachEntry pass fixes it? Why cannot dispose do it? (Compare std::parser::ini.)
