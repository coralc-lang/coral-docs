Modules, Imports, and Visibility

Why Programs Need Seams

A program of two hundred lines fits in your head. A program of two hundred thousand does not, and the only way to keep working on it is to cut it into pieces small enough to hold, then agree on how the pieces may talk to each other. A module system is that agreement. It is not a folder organising convention; it is a contract about names, about reach, and about what a caller is allowed to depend on. Get the module system right and a codebase can be understood one file at a time. Get it wrong and every file knows about every other file, and the only way to change anything is to hold the whole thing in your head at once.

Here is a picture that will carry us through the chapter. Think of a public library. The building has many rooms, and each room has shelves, and each shelf is full of books. But you do not wander the back offices and the storage basements looking for a title. You go to the front desk, and the front desk has a catalogue: a short list of exactly what this library lends and exactly what each item is called. The catalogue is the contract. Behind it, the library may have a thousand books nobody outside ever sees, and the library is free to move them, rebind them, or throw them out, so long as the catalogue still describes what is available.

A Coral module is that library. A module is a folder. The books are the source files. The catalogue is a file called lib.crl, and it lists, in a handful of lines, exactly what the module makes public. Everything not in the catalogue is the back office: real, useful, and invisible to the outside. Once you hold that picture, the rest of this chapter is detail.

Coral's module system is deliberately small. There is a source file, a module surface, four import forms, and one visibility keyword. That is the entire vocabulary. The complexity that most languages carry, namespace hierarchies, header files, forward declarations, circular-dependency workarounds, is absent, and its absence is a design decision rather than an omission. This chapter explains the pieces and, just as importantly, the rules that keep them predictable.

Files, Folders, and the Module Surface

A Coral source file ends in .crl. A folder that participates in a build is a module. A module's public face is a file named lib.crl in that folder. Everything the module exports to the rest of the program is listed in lib.crl, and everything lib.crl re-exports becomes the module's namespace.

Let us be careful about the word "namespace," because it is doing real work here. The namespace is the set of names an outsider can write after the module's name. If lib.crl contains one line exporting a submodule called string, then text::string is a name outsiders can reach; if it does not, text::string is not a name at all outside the module, no matter how many string files sit in the folder. The namespace is not the folder's contents. The namespace is the catalogue's contents.

Consider a folder src/text/:

src/text/
├── lib.crl          # the module surface
├── string.crl       # String
├── strutil.crl      # free functions on str
└── ascii.crl        # ASCII helpers

The surface declares what the module offers:

// src/text/lib.crl
pub mod string  = import string;
pub mod strutil = import strutil;
pub mod ascii   = import ascii;

Each pub mod NAME = import TARGET; line takes a sibling, gives it a public name, and makes it reachable as text::NAME from outside. Read the line left to right as a sentence: "publicly, this module has a submodule called string, and it is the sibling file string." The NAME on the left is the name the outside world uses; the TARGET on the right is the sibling the name refers to. They are usually the same, but they do not have to be, and Section14.5 shows why you would want them to differ.

Code that does not appear in lib.crl is not part of the module's surface; it is visible only within the module's own files. That single rule, the surface file is the contract, is what lets a module have a large private implementation and a small public face. A text module might have ten helper files inside it, full of internal machinery, and expose four submodules. A reader of the outside code never has to know the ten exist.

Hold on, how is it that string.crl can be reached by an outsider at all, if it is just a file? Through the pub mod line, and only through it. The mechanism is worth stating plainly because it explains the whole chapter: a sibling file is not automatically part of the module. It becomes part of the module when the surface exports it. Until then it is a book in the back office. This is the opposite of how many languages work, where putting a file in a folder is itself a kind of export, and it is deliberate. In Coral, being reachable is a decision someone wrote down, not a side effect of where a file was saved.

If you are new to modules, the plain version is this: creating a file does not show it to the world. Only the catalogue, lib.crl, shows anything. It is like a shop's window display: the shop may hold hundreds of items in the back, but only the ones placed in the window are visible from the street.

The Four Import Forms

A file brings names into scope with import. Four forms exist, and each answers a different question. Learn the question each one answers and you will never have to memorise the syntax.

The first form imports a sibling file by bare name. No quotes, no extension; the name is the file name without .crl, resolved in the importing file's own directory:

import lexer { Lexer, Token };

This is the form you use inside a module, where files sit next to each other. Because the name is a bare identifier, it is greppable: searching for import lexer finds every file that depends on lexer.crl, and a bare name cannot accidentally contain a path that escapes upward. The braces name the symbols you want from that file. If a dependency is not a sibling, it is not a sibling import; it is one of the following forms.

Read the braces carefully, because they are the "allow-list." import lexer { Lexer, Token }; does not bring in the whole of lexer.crl; it brings in exactly two names. If someone later adds a Parser to lexer.crl, your file does not silently gain a Parser in scope. The list is the contract at the file level in the same way that lib.crl is the contract at the module level. This is the same philosophy applied twice: depend on names you chose, not on names that happened to appear.

A common mistake is to import a file and assume every name inside it arrived. It did not: only the names in the braces came. If you then use a name that was never imported, the compiler reports it as unknown, and the fix is to add it to the list, which is the list quietly doing its job as the file-level contract.

In plain words, an import is like ordering from a menu rather than raiding the kitchen. You name exactly the dishes you want, and if the kitchen adds a new one tomorrow, your order does not change. The braces are your order; what you leave out simply never reaches your table.

The second form imports a name from another module through the module table. A double-colon path names the module and the exported item:

import lexer::table { TokenTable };
import common::slice { Slice };

The builder resolves lexer::table against the module map it generated from every module's lib.crl (Section14.6). The importing file never states a path; it states an identity, and the build system owns the mapping from identity to file. This is the shape you use to reach a module that is not sitting in your own folder, a module from elsewhere in the project. The double colon reads as "inside": lexer::table is the table inside the lexer module.

The third form imports from a library surface, marked with the (lib) qualifier:

import(lib) std::text::string { String };
import(lib) std::collections::vec { Vec };
import(lib) std::io::ios { print, println, eprintln };
import(lib) std::option { Option };
import(lib) std::result { Result };

This is the everyday form for reaching the standard library. std is the library root; the path after it names the module; the braces name the symbols. The (lib) qualifier is the signal that the name after it is a root provided by the environment, the standard library, the core library, a platform library, rather than a module of your own project. When you see (lib), read it as "this name lives in the installed library, not in our source tree."

When you want a module's whole surface rather than specific symbols, drop the braces:

import(lib) std;

That line brings std itself into scope. It is the blunt instrument: use it when you genuinely want everything, and prefer the brace forms when you want a few names, because a brace list is a record of what this file actually uses.

The fourth form imports with an alias:

import renderer::framebuffer { FrameBuffer as FB };

An alias binds a different local name to the imported symbol. Use it when a name is long, or when two imported names collide and you want to keep both. A bare alias is also allowed when you are importing a single name and just want to rename it:

import sym as alias;

The as in an import changes the name in your file only. It does not change the name the symbol has anywhere else, and it does not change what the module exports. Think of it as a nickname you use privately: FB is what you write, FrameBuffer is what the world calls the type, and the compiler knows they are the same.

Every form accepts a grouped, nested right-hand side, so a file can state several imports in one place without repeating the prefix:

import(lib) std {
    io::{ print, println, eprintln },
    text::string::{ String },
    collections::vec::{ Vec },
};

import lexer {
    table::{ TokenTable, TokenKind },
    ident::{ scanIdent, isIdentStart },
};

import(lib) std::text {
    string::{ String },
    strutil::{ split },
};

The nesting is purely textual grouping. The final binding is always the last segment: io::{print} binds the name print. A trailing comma after the last group is allowed, which keeps diffs small when you add an item. The advantage is not brevity for its own sake; it is that a related set of imports sits together as one block, so a reader can see at a glance that this file talks to std's IO, text, and collections, and to nothing else.

What is deliberately not allowed matters as much as what is. No string-literal import path, no "…/foo.crl", no ../ to climb directories. A path string is nameless, it introduces no binding a reader can grep for and no constraint a compiler can check, so Coral removed it. Consider what a path gives you and what it costs. A path like "../../common/util/lexer.crl" tells you where a file sits relative to the importer, which depends on the importer's location, which means the same dependency is written differently from every file that uses it, and moving a file rewrites every path that named it. A module identity like lexer::table names the thing, not the route to it. If a file is not a sibling, it is reached through a module name, and module names are the builder's business, not the source's.

Visibility and Enforced Privacy

An item is private to its file and module unless it is marked pub.

pub struct Point { f64 x; f64 y; }
struct Internal { i32 scratch; }        // private to this file

pub f64 magnitude(Point p) { return ...; }
f64 helper(i32 n) { ... }                // not callable from outside

A private item is not merely undocumented; it is invisible. The compiler enforces module privacy: a name that is not pub cannot be called or referenced from outside the module that declares it, and the attempt is an error rather than a warning. Reaching across a module boundary to a private symbol is the kind of coupling that makes refactoring expensive, so the language refuses to allow it by accident. If you need something to be reachable, you mark it pub and it becomes part of the contract you are agreeing to maintain.

Let me be precise about "error rather than warning," because this is the sentence people skim. In many languages, using a private member from outside produces a warning, or nothing at all, and the program still builds. Coral makes it a hard error. That means the privacy boundary is not advisory; it is structural. You cannot ship code that leans on another module's internals, because the build will not produce that code. The practical effect is that when a library author wants to change an internal representation, they can do it with confidence that nobody outside could have been relying on it, because the compiler would have refused to compile such a reliance in the first place.

Privacy applies at the item level, not only the module level. In the surface file, only pub mod lines export anything. Inside a module, only pub functions, types, constants, and fields are visible to importers. And note that fields are items too: a pub struct may have private fields, in which case outside code can name the type but cannot read or write the fields directly. This is how you make an opaque handle, a type whose representation is the module's business:

// in module net, file socket.crl
pub struct TcpSocket {
    i32 fd;                    // private field
}

pub Result<TcpSocket, IoError> tcpConnect(str host, u16 port) { ... }
pub void tcpSend(TcpSocket* s, const u8[] data) { ... }

Outside code can hold a TcpSocket, pass it to tcpSend, and never touch the descriptor. If the representation changes from an fd to a pointer, no caller notices. That is the whole point of a private field: it makes the type's representation free to change.

In plain words, a private field is a locked drawer inside a machine the user is allowed to operate. The user can press the buttons you expose, but they cannot reach into the drawer and rearrange its contents. That is the freedom that lets you change what is in the drawer later without breaking anyone who only ever pressed the buttons.

Simply put, privacy is a promise about what will not change. A pub name is a promise that you will keep it working; a private name is one you are free to rewrite tomorrow. That is why starting a new public type with private fields is the safer habit: every field you expose is a small contract you now have to honour.

Think about what an opaque handle buys you with a concrete story. Suppose you are writing an audio library, and a Decoder is exposed to users. If the users can see the fields, then every field is a promise: you cannot remove one, rename one, or change its type without breaking them. If the fields are private and the users only ever call decode, reset, and close, then your internal buffer, your sample cursor, and your platform handle are all yours to rearrange. The users hold a Decoder; they do not know or care what is inside it. That is the difference between a type you can evolve for ten years and a type that is frozen the week you ship it.

There is a useful habit that goes with this: when you design a public struct, start with every field private and add accessors only for the ones a caller genuinely needs. It is much easier to make a private field public later than to make a public field private later, because the latter breaks every caller who was reading it. Starting closed and opening deliberately keeps the contract small, and a small contract is one you can keep.

For a nominal type that must not be confused with its representation under any circumstance, distinct is the stronger tool (Chapter 4): pub distinct TcpSocket = i32; gives a type that is the fd's bytes but not the fd's type, so no caller can treat a socket as an integer even by accident. A private field and a distinct type solve related problems from different directions: the private field hides the representation, and the distinct type makes the value's identity unambiguous. Often you want both.

Qualifying Names

Imported symbols are used by their bare names. When you want to be explicit, or when a name would be ambiguous, you qualify with the module:

import(lib) std::text::string { String };
import(lib) std::collections::vec { Vec };
import(lib) std::option { Option };

String greeting = String::from("hello");
Vec<i32> nums = Vec<i32>::new();
Option<i32> maybe = Option<i32>::Some { .value = 42 };

The type name is bound by the import; :: is how you reach an associated item (a static method such as new, a variant case such as Some, a constant). This is the same :: that qualifies enum cases and variant cases in Chapter 13, generalised to module members. A module's exported name is the last segment, so std::text::string exports String, std::collections::vec exports Vec, and so on. The standard library is organised in nested folders precisely so that a module name is short and a symbol name is unique within it; you write vec::Vec or just Vec after importing it, never the full folder path.

Notice what is happening on each ::. In String::from("hello"), the String is a type and from is a static method on it, a function that belongs to the type but does not need an instance. In Option<i32>::Some { .value = 42 }, the Some is a variant case of Option, and :: is how you say "this case, of this type." In both cases :: means "a member of what is on the left." The same operator reaches into modules, types, and variants, which is why the language has one :: instead of three special syntaxes. Once you internalise "left side is the container, right side is the thing inside it," every use of :: in Coral reads the same way.

Here is a small example that puts qualification to work in a realistic function:

import(lib) std::collections::vec { Vec };
import(lib) std::text::string { String };
import(lib) std::option { Option };

Option<String> firstWord(const String[] words) {
    if (words.count() == 0) return Option<String>::None;
    return Option<String>::Some { .value = words[0] };
}

Every type in the signature is a bare name, because the imports brought them into scope. Every use of an associated item is qualified, because None and Some belong to Option and could not be reached without saying which type they belong to. That is the whole rule: import the type's name, qualify its members.

A tiny example shows the pattern in the smallest possible form:

import(lib) std::collections.vec { Vec };
import(lib) std::io::ios { println };

Vec<u64> counts = Vec<u64>::new();
counts.push(3);
println("{} item", counts.count());

Vec is a bare name because the import brought it in; Vec<u64>::new() stays qualified because new is a member of the type. Read every colon as "belongs to": std::collections::vec is the vec module inside collections inside std, and Vec::new is new inside Vec.

When two imports bring in the same name, the compiler rejects the collision rather than silently picking one. That is another small stand against surprise. If you genuinely need both, say two different Config types from two modules, you use an alias:

import app::server { Config as ServerConfig };
import app::client { Config as ClientConfig };

Now your file has ServerConfig and ClientConfig, and a reader can tell at every use site which one is meant. Silent shadowing is the enemy here: if the language quietly let the second import win, a reader could not tell which Config a line referred to without chasing the import list, and a later reordering of imports could change the program's meaning. Coral makes you name the two things differently, which costs one word and saves an afternoon.

Re-exports and Module Aliases

A module may re-export another module under a new name. pub mod NAME = import TARGET; is not a submodule declaration; it is a re-export, a one-line forwarding statement:

// src/lib.crl, the program's own surface
pub mod text   = import(lib) std::text;
pub mod bits   = import(lib) std::collections::bitset;
pub mod shapes = import shapes;

The first two lines re-expose standard-library modules under the program's own surface; the third exposes a local module. Re-exports are how a library presents a curated view: a program can decline to re-export a std module it does not want to be part of its own API, and it can rename a module whose name is too generic for its domain. Because a re-export is a single line, the module table stays small and a reader can see the whole public surface at a glance.

Why would a program have its own lib.crl at all? Because a program is, from its own perspective, also a library. The top-level lib.crl is where the program decides what its own modules are called and what it exposes to its own files. It is the same mechanism as a module's surface, one level up. If you are building an executable, the surface mostly exists to give friendly names to the pieces; if you are building a library that others will import, the surface is the product, it is the catalogue the whole world reads.

The difference between a re-export and a definition is worth being explicit about. pub mod shapes = import shapes; does not copy shapes.crl into your module. It does not compile anything. It creates a name, shapes, that points at the same module. If the underlying module changes, the re-export changes with it, because it is a pointer, not a copy. This is the mechanism by which a library can present text as the standard library's text module without duplicating a line of it. One line, one pointer, no maintenance.

One special case is worth remembering: a module whose surface is a single file can be reached as that file. If a folder contains only lib.crl, the module is the file. And conversely, a sibling file that is imported by bare name does not need an entry in lib.crl; only items you want visible outside the module do. Inside the module, siblings talk to each other directly, by bare name, with no surface in the way.

Let me tie the two halves together with a small story. Suppose you are building a game and you have a math module full of vector and matrix helpers. Internally, math has files for vectors, matrices, and the scalar utilities they share. To the rest of the game, math is a catalogue with two submodules, vec and mat. The game never sees the scalar file, never learns its name, and never has a reason to. If you later split the scalar file in two, or merge it into the vector file, the game is untouched, because the game only ever depended on the catalogue. That is the payoff, in one scenario: the freedom to change your mind about the internals without changing the world outside.

Simply put, a re-export is a pointer, not a copy. pub mod shapes = import shapes; makes the name shapes point at the same module the rest of the world uses; it does not duplicate the code or outlive a change. If the underlying module changes, the re-export follows, because there is only one module and the re-export is one of its names.

Cycles, Resolution, and the Module Map

Two files that import each other would, naively, require each to be compiled before the other. Coral resolves this by separating declaration from definition. The compiler reads every file's top-level declarations before it reads any function body, so a function may call a function declared later in the same module, and two modules may refer to each other's types as long as neither needs the other to be fully defined to compute a type's size. This is the same "declare all, then define" prescan that lets array sizes be order-independent within a file, lifted to the module level.

Let me unpack that, because "declaration versus definition" is the kind of phrase that slides off the eye. A declaration is the shape of a thing: a function's name, parameter types, and return type; a type's name and fields. A definition is the thing itself: the body of the function, the actual storage of the struct. To compile a call, the compiler needs the declaration, it needs to know what the function takes and returns. It does not need the body. So it makes a first pass over every file collecting declarations, and only then, with the whole map in hand, does it read bodies. That is why a function can call one written below it, and why two modules can name each other's types: by the time either body is read, both declarations are known.

In plain words, the compiler first walks the whole neighbourhood writing down who lives where, and only later delivers the mail. Because the address book is finished before any letter is sent, a house can send a letter to a house that is not built yet, as long as its address is already in the book.

The one case that does not compose is a cyclic layout, which is Chapter 13's territory: a struct cannot contain itself by value, because the compiler needs the size of the inner value to compute the size of the outer one, and the cycle never bottoms out. You break it with a pointer. But naming each other's types, and calling each other's functions, is fine, because neither requires the other's body or its finished size.

For cross-module imports, the builder does the resolution in a pass of its own, before the compiler runs. It walks every module listed in the build file, reads each lib.crl's pub mod lines, and writes a module map: a plain-text table from a module identity such as lexer::table to the file that implements it. The builder places this map at .coral/modules.map in the build directory.

# .coral/modules.map, generated by the build, do not edit
lexer::base     ->  compiler/coral-lexer/base.crl
lexer::table    ->  compiler/coral-lexer/table.crl
parser::expr    ->  compiler/coral-parser/expr.crl

The map is text, not JSON, for three reasons the build documentation states plainly: it diffs cleanly in git, it is greppable, and reading it needs no parser. When the compiler sees import lexer::table, it asks the map for a path and the map answers. The compiler never walks the filesystem guessing; the map is the single source of truth for where a module lives. That is worth emphasising: there is exactly one place that knows where each module's file sits, and it is a file you can open and read. If a build ever resolves a module somewhere surprising, you look at the map, and the mystery is over.

Cycles in the module graph are detected by the builder, so a genuine build-order cycle is reported as a build error with a trace rather than hanging. When a module cannot be resolved, the builder reports it as its own class of error: an unresolved re-export path (E1004), a missing module (E1001), a duplicate module identity (E1002), an alias pointing at a nonexistent module (E1003), or an unresolved module import (E1005). These are build errors, distinct from the compiler's E-codes for source-level problems, and Chapter 21 describes the build pipeline that produces them.

The split between build errors and compiler errors is a useful thing to have in your head when something goes wrong. If the complaint is "I cannot find this module," it is the builder, and the answer is in lib.crl or the map. If the complaint is "this name does not exist" or "this field is private," it is the compiler, and the answer is in the source. Knowing which tool is unhappy cuts the search space in half before you read a single line of the error.

Standard Library Roots and Resolution Order

The standard library is reached through two roots. std is the portable surface, the modules that every platform provides with the same names, parameters, and return types. core holds the pieces the language itself depends on: str, cchar, char utilities, and the numeric limits. A third root, platform, holds the parts that are genuinely platform-specific, such as libc bindings.

Platform parity is a first-class rule of the standard library: every public API that exists for one platform has a direct equivalent on the other, with the same name, the same parameters, and the same return type including its error type. Internals differ, a Linux build issues one syscall and a Windows build issues another, but a program written against std compiles on both. A user's import does not change when the target changes:

import(lib) std::io::fs { File, open, read, write };
import(lib) std::concurrent::thread { threadCreate, threadJoin };

The same source builds on x86_64 Linux and x86_64 Windows because the module names are the contract. This is why the standard library organises by capability (io, collections, text, concurrent, crypto) rather than by platform: the platform lives behind the surface. The whole point of the parity rule is that you write your program once, against capability names, and the platform is somebody else's problem.

When the compiler resolves an import, it searches, in order, the project's own lib, the current directory's lib, and finally the global library root (the CORAL_HOME/lib or ~/.coral/lib installation), checking the platform subtree before the base subtree. That order means a project can shadow a standard module with its own implementation by placing a lib of the same name next to itself, a deliberate escape hatch, and one to use sparingly, because a shadowed std module is a surprise for the next reader.

The order is "most specific wins," which is the same principle as local variables shadowing globals. Your project's own definition is the most specific, so it wins; the current directory is next; the installed library is the fallback. The escape hatch exists because sometimes you genuinely must replace a standard module, to patch a bug, to target an unusual platform, to instrument calls for debugging. But a shadowed module is invisible at every import site that uses it, so leave a comment in the shadowing file explaining why it exists, or the next person will spend an hour assuming std is doing the standard thing.

A common beginner mistake is to give a project module the same name as a library module the project also uses. Because the most specific definition wins, the local one may be chosen where you expected the library's, and the compiler's complaint will point at a name that looks correct. When a name resolves somewhere surprising, first check whether two modules are sharing it.

Here is a small illustration of how the roots divide. If you need println, you reach it through std::io::ios. If you need the integer limits, you reach them through core::limits. If you need to call mmap, you reach it through a platform binding, because mmap is not portable and pretending otherwise would be a lie. The three roots are the three honest answers to "is this portable, language-fundamental, or tied to my machine?"

Why this matters: knowing which root a name lives under tells you how far it will travel. A std import works on every platform the library supports; a core import is part of the language's own floor; a platform import is a conscious bet on one machine. When you review a dependency, the root is the first clue about whether the code is portable.

A Worked Example: A log Module

Assemble the pieces. Suppose you are building a module that formats and emits log lines. Create a folder and give it a surface:

src/log/
├── lib.crl
├── level.crl
└── logger.crl

The level file declares the level as an enum and a rendering function, private to the module except for what level.crl marks pub:

// src/log/level.crl
pub enum Level { Debug, Info, Warn, Error, Fatal }

pub str levelName(Level l) {
    return switch (l) {
        Level::Debug => "DEBUG",
        Level::Info  => "INFO",
        Level::Warn  => "WARN",
        Level::Error => "ERROR",
        Level::Fatal => "FATAL",
    };
}

str levelTag(Level l) { return levelName(l); }   // private helper

Notice levelTag. It is a real function, and levelName is free to call it, but it is not pub, so nobody outside the module can. It is a book in the back office. The author of this file can rename it, delete it, or change its signature tomorrow, and no code outside the module has a thing to say about it.

The logger file imports the sibling and uses it:

// src/log/logger.crl
import level { Level, levelName };
import(lib) std::io::ios { println };

pub struct Logger {
    Level minLevel;
    str   name;
}

pub void log(Logger* self, Level l, str message) {
    if (l < self.minLevel) return;
    println("[{}] {}: {}", self.name, levelName(l), message);
}

The sibling import import level { Level, levelName }; brings in exactly two names, both of which logger.crl actually uses. It does not bring in levelTag, which is convenient because levelTag is private and would be rejected anyway. The (lib) import names exactly the one standard symbol this file prints through. Two imports, four names, and the dependency graph of this file is fully written down in two lines.

Now the module's public surface exports exactly what it intends:

// src/log/lib.crl
pub mod level  = import level;
pub mod logger = import logger;

Outside the module, code writes:

import myapp::log::logger { Logger, log };
import myapp::log::level { Level };

var logger = Logger { .minLevel = Level::Info, .name = "server" };
log(&logger, Level::Warn, "disk almost full");

Notice what a caller can and cannot see. It can see Logger and log because logger.crl marked them pub and lib.crl re-exported them. It can see Level because level.crl marked it pub. It cannot see levelTag, because that function is not pub. It cannot reach into Logger's representation, only the fields the type exposes, and here both fields happen to be public, but a private field would be equally invisible. Each file's imports name exactly what it uses, so the dependency graph is readable line by line: logger depends on level and on std::io::ios, and nothing else.

Let us push the example one step further, because the interesting part of a module system is what happens when it grows. Suppose a second caller wants to write log lines to a queue instead of to the console. Add a sibling:

// src/log/sink.crl
pub enum Sink { Console, File, Memory }

pub void emit(Sink s, str line) {
    switch (s) {
        Sink::Console => println("{}", line),
        Sink::File    => appendToLogFile(line),
        Sink::Memory  => pushToRing(line),
    }
}

void appendToLogFile(str line) { ... }   // private
void pushToRing(str line)     { ... }    // private

Then export it from the surface:

// src/log/lib.crl
pub mod level  = import level;
pub mod logger = import logger;
pub mod sink   = import sink;

The outside world gains Sink and emit, and gains nothing else: appendToLogFile and pushToRing stay in the back office. The callers who only wanted Logger see no change at all, because a module's surface growing is backward-compatible; the callers who want the new capability import sink. This is the shape of a module growing in the open, one catalogue line at a time, without leaking internals.

What makes this example worth re-reading is that every rule in the chapter is visible in it, and none of them felt like ceremony. The surface listed the exports. The sibling imports named their symbols. The (lib) imports pulled in the standard library. The private helpers stayed private. No path string appeared anywhere. No file needed to know where another file lived. And when we added a submodule, we added one line to the catalogue. That is the whole system.

Exercises

  1. ComprehensionWhat is the difference between a module's private items and its lib.crl surface? Which one is the contract, and what does the other one let the module author change freely?
  2. ComprehensionWhy does Coral reject import "path/to/file.crl" in favour of import mod::item? Give two concrete costs of the string form.
  3. ImplementationTake the log module of 14.8 and add a Sink variant so a Logger can write to stdout, a file, or memory. Keep the union of behaviour behind one public API and make every helper private.
  4. ModulesFour files in a folder each import a sibling named token. Which file is token.crl resolved against, the importing file's directory, the module root, or the current working directory? Explain why the answer matters when two modules both have a token.crl.
  5. VisibilityA pub struct is declared with a private field. Write an accessor pair (a getter and a setter) and explain what a caller gains over reading the field directly. When would you expose the field instead?
  6. BuildSketch the lib.crl for a module that re-exports two std modules under shorter local names, without copying their implementations. Which import form do you use?
  7. CyclesTwo modules refer to each other's types. Explain why this compiles, and give one case where it would not.
  8. ImportsWrite, in one grouped import statement, the imports for a file that needs String from std::text::string, split from std::text::strutil, Vec from std::collections::vec, and println from std::io::ios. Then rewrite the same imports as four separate lines and say which you would rather review.
