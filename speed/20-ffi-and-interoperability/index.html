Foreign Function Interface and Interoperability

Living With C

Coral runs on systems written in C, links against C libraries, and sometimes exposes itself to C callers. The foreign function interface (FFI) is that seam. Every systems language needs one, because no language reimplements the world.

Inside Coral, a pointer has a type, a string has a length, and struct layout is private. Inside C, a pointer is an address, a string is nul-terminated bytes, and struct layout is a byte contract. Coral's FFI is thin: declare a C signature, call it, and the linker resolves it. There is no binding generator or runtime marshalling layer.

Thin is not trivial. Learn to declare foreign functions, pass and receive data, represent C types, and build wrappers so the rest of the program never touches the raw interface. A good FFI is invisible from outside.

The FFI is a border crossing. A pointer is a passport without a photo, a C string is a name without a promised length, and a struct is a parcel both sides must pack identically. The wrapper is the customs officer who translates once.

What the FFI Is For

The FFI serves four jobs.

The operating system: there is no Coral way to ask the kernel to open a file. read, write, open, close, mmap, and socket are C functions, and the FFI is how Coral pronounces them.

Third-party libraries: compression, cryptography, databases, graphics, and parsing are overwhelmingly C. Calling zlib means calling a C function.

Performance: an existing hand-tuned C library may beat a rewrite. This is real but dangerous, because crossing the boundary mid-computation is awkward and costly.

Exposure: sometimes Coral is the library, a plugin, shared object, or entry point that C loads and calls (20.9).

In every case, two sets of rules meet and someone must translate. That someone is you.

Declaring an Extern Function

An extern function is a declaration with no body. The compiler records the signature, and the linker connects the name to a symbol.

pub extern i64 read(i32 fd, cchar* buf, u64 count);
pub extern i32 open(const cchar* path, i32 flags, i32 mode);
pub extern void free(rawptr ptr);

Three things matter:

There is no body. extern with no {} promises the linker that a symbol with this name and signature exists. A missing symbol fails the link, early and correctly.

Parameter names are optional. i32 open(const cchar*, i32, i32); is equally valid; names are documentation.

The C standard library links by default. Other libraries need a link flag, supplied by the build:

// links against -lm
pub extern f64 sqrt(f64 x);
pub extern f64 pow(f64 x, f64 y);

The standard library's platform bindings are the model: libc for POSIX and win32 for Windows, each a list of bodyless extern declarations:

// a fragment of platform/libc.crl
pub extern u64 strlen(const cchar* s);
pub extern rawptr malloc(u64 size);
pub extern i32 open(const cchar* path, i32 flags, i32 mode);
pub extern i64 read(i32 fd, cchar* buf, u64 count);

// a fragment of platform/win32.crl
pub extern rawptr CreateFileA(const cchar* lpFileName, u32 dwDesiredAccess, u32 dwShareMode, rawptr lpSecurityAttributes, u32 dwCreationDisposition, u32 dwFlagsAndAttributes, rawptr hTemplateFile);
pub extern bool ReadFile(rawptr hFile, cchar* lpBuffer, u32 nNumberOfBytesToRead, u32* lpNumberOfBytesRead, rawptr lpOverlapped);

The Windows fragment shows longer names and types such as u32 and bool where C has unsigned and its own boolean (see 20.4). Adding a missing binding is a one-line declaration.

A complete binding can be tiny. This program opens and closes a file with no wrapper:

import(lib) platform::libc { open, close };

void main() {
    i32 fd = open(C"/etc/hosts", 0, 0);
    if (fd >= 0) {
        close(fd);
    }
}

It works, and it shows why a wrapper is worth writing: the raw i32 descriptor and magic 0, 0 flags are details a wrapper should hide.

Calling Conventions and Function Pointers

A calling convention is the agreement about argument passing and cleanup: registers or stack, order, who pops. extern uses the platform's C convention by default. Name a non-default convention explicitly:

pub extern("C") void callback_handler(i32 code);

extern("C") makes the C convention explicit. On mainstream targets the call is identical, so it is mostly clarity. It matters when names could be mangled or the platform has multiple conventions.

C passes callbacks as function pointers, and Coral passes functions as pointers too. A callback parameter is written as a Coral function-pointer type, RetType(params):

pub extern void qsort(rawptr base, usize count, usize size, i32(const rawptr, const rawptr) cmp);
pub extern rawptr signal(i32 signum, void(i32) handler);

i32(const rawptr, const rawptr) is a pointer to a function taking two const rawptr and returning i32. void(i32) takes an i32 and returns nothing. A Coral function with a matching signature is usable as that type:

i32 compareInts(const rawptr a, const rawptr b) {
    i32 x = *(i32*)a;
    i32 y = *(i32*)b;
    return x - y;
}

void main() {
    i32 data[5];
    data[0] = 5; data[1] = 3; data[2] = 4; data[3] = 1; data[4] = 2;
    qsort((rawptr)data, 5u, 4u, compareInts);
}

A callback invoked by C must use the C convention and take and return only FFI-compatible types. It must not throw or unwind. Owned Coral types with drop behaviour cannot be passed by value; keep callbacks simple, and pass context through a raw pointer as C does.

C Types and Coral Types

This translation table prevents the most common FFI bug: a type that is the right size on one platform and wrong on another.

C type        Coral type       note
int           i32              on the platforms Coral targets
long          i64 (LP64)       i32 on Windows (LLP64), check the platform
unsigned      u32
size_t        usize            pointer-sized
char          cchar            a byte, signedness platform-dependent
char*         cchar*           a C string or byte buffer
const char*   const cchar*     a read-only C string
void*         rawptr           an untyped pointer
bool          bool             C's boolean, in the bindings
struct foo    struct foo       by value, with a matching layout
function ptr  void(rawptr)     the same, spelled Coral's way

Four deserve attention:

cchar is C's char: one byte whose signedness is platform-dependent, and the element of a C string. It is distinct from Coral's char (a Unicode codepoint) and from u8 (unambiguously unsigned). Using cchar signals C's notion of a character and prevents passing a codepoint where a byte is wanted.

rawptr is void*: an address with no type. Convert explicitly with (rawptr)x and (T*)ptr, marking where type erasure and restoration happen.

usize is size_t, the pointer-sized unsigned integer used for every C length and count.

Sizes are not universal. long is 64 bits on LP64 (Linux, macOS) and 32 bits on LLP64 (Windows). Declaring i64 for a C long is wrong on Windows. This is the first thing to check when a binding misbehaves on one platform, and why platform bindings are separate files.

C Strings and Coral Strings

String handling is the largest source of FFI bugs. A Coral str is a pointer and a length; a C string is nul-terminated bytes with no length. They are not interchangeable.

A str is a page with the word count at the top; a C string is a page that stops at the first blank line. Hand the first to C and it keeps reading until it finds a blank or walks off the page.

To call a C function expecting a C string, you need a C string. A C literal is one:

open(C"/etc/hosts", 0, 0);

C"..." is nul-terminated and has type const cchar*, so it passes directly with no allocation. Use it whenever the string is known at compile time.

For a runtime string, convert explicitly. A String keeps a trailing nul and can produce a C-string view; a str view must be copied into an owned buffer first:

String s = String::from("config.txt");
cchar* cstr = s.asCstr();          // valid while s is alive

// a borrowed view that must be owned before it can be a C string
String tmp = String::from(view);
open(tmp.asCstr(), 0, 0);

Conversion is neither free nor implicit, by design. asCstr() does not allocate; it lends the String's bytes, so the String must outlive the pointer.

A common mistake is open(tmp.asCstr(), ...) where tmp is already gone when C reads it. If the pointer must outlive the string, copy the bytes first.

The reverse direction is explicit too. String::fromCstr measures and copies into an owned String; str::fromCstr measures and returns a borrowed view:

String owned = String::fromCstr(cstr);   // copies; owns its bytes
str view = str::fromCstr(cstr);          // borrows; measures with strlen

Two bugs everyone writes once: a borrowed str from C does not own the bytes, so freeing them in C leaves a dangling view; and a non-nul-terminated str must never be passed to C, which will read past the end looking for a nul.

A C function returning cchar* may return null, as getenv does. Passing null to String::fromCstr sends it into strlen and faults. Check first:

pub extern cchar* getenv(const cchar* name);

String home(str name) {
    const cchar* val = getenv(name.asCstr());
    if (val == null) return String::from("(unset)");
    return String::fromCstr(val);
}

Passing Structures and Buffers

A struct can cross by pointer, or by value if its layout matches. By default the compiler may insert padding and reorder fields, so a plain Coral struct may not match C. Pin the layout for boundary structs:

#[[packed]]
struct Header {
    u8  version;
    u8  flags;
    u16 length;
    u32 checksum;
}

pub extern i32 readHeader(i32 fd, Header* out);

#[[packed]] removes padding and keeps declaration order, so size is the sum of fields and bytes lie as written. It is required for wire formats, protocol headers, and any external ABI. The trade-off is access speed: unaligned fields cost more on some platforms, so pack only boundary structs.

#[[reorder]] lets the compiler permute fields for density. That is fine for private in-memory types and wrong across a boundary, because C reads bytes where it expects them. A struct with neither attribute has a private compiler-chosen layout. If a struct crosses the FFI, mark it packed; otherwise treat its layout as private.

Buffers cross as a pointer plus an explicit length, because C cannot infer one. A function filling a buffer takes a rawptr or cchar* and a usize:

u8 buffer[4096];
i64 n = read(fd, (cchar*)buffer, 4096u);

The cast matches the parameter type, and the length is separate. The caller owns the buffer and its lifetime; C writes into it and returns the byte count, with a negative value meaning error. Wrapping this so callers get a String or typed result is the wrapper's job.

Wrapping the Boundary

A C interface is designed for C: raw pointers, integer return codes, out-parameters, and global error codes. Do not let it leak into your program. Write a wrapper that converts, checks codes, returns Results, and exposes a Coral-shaped API.

A wrapper for a C file API shows the shape. The C side offers the standard trio:

pub extern rawptr fopen(const cchar* path, const cchar* mode);
pub extern u64 fread(rawptr ptr, u64 size, u64 count, rawptr stream);
pub extern i32 fclose(rawptr stream);

Wrap it in an owned type with a drop and a Result-returning open:

import(lib) platform::libc { fopen, fread, fclose };
import(lib) std::text::string { String };

pub struct File {
    rawptr handle;
}

pub variant FileError {
    NotFound { String path; },
    PermissionDenied { String path; },
    Unknown { i32 code; },
}

pub extend File : @drop {
    void drop() { fclose(self.handle); }
}

pub Result<File, FileError> fileOpen(str path) {
    String tmp = String::from(path);
    rawptr h = fopen(tmp.asCstr(), C"r");
    if (h == null)
        return Result<File, FileError>::Err {
            .error = FileError::NotFound { .path = path.asString() }
        };
    return Result<File, FileError>::Ok { .value = File { .handle = h } };
}

pub Result<usize, FileError> fileRead(File* f, u8* buf, usize len) {
    u64 n = fread((rawptr)buf, 1u, len, f->handle);
    return (usize)n;
}

The wrapper hides every awkward detail. fopen's null becomes a typed Result error. The handle is owned and closed by @drop, so RAII works at the boundary. C-string conversion happens once inside. Callers write fileOpen("config.txt") and never hold a rawptr or remember to close.

A wrapper turns a C library from a pile of footguns into a tool teammates can use without the C manual. Do the boundary work once, in one file.

The wrapper also decides ownership. File owns the handle, so copying it would double-close; the wrapper must forbid copying or use reference counting. C did not decide this for you, so the wrapper must decide once and express it in the type.

Two finishing details: map error codes to a small closed set, and group shared handling paths with |:

switch (err) {
    FileError::NotFound | FileError::PermissionDenied => { recover(); },
    FileError::Unknown { code } => { panic(code); }
}

This is the variants chapter's pattern matching applied at the boundary: a C integer becomes a compiler-checked Coral variant.

When C reports failure with a sentinel and sets errno, the wrapper reads errno through its accessor. On POSIX, errno is reached through __errno_location, which returns a pointer to the current thread's error cell:

import(lib) platform::libc { __errno_location };

i32 currentErrno() {
    return *__errno_location();
}

The function indirection is how errno is made thread-local, so one thread's error cannot be read by another.

Inline Assembly and Clobbering

Inline assembly skips C entirely. When no C function exists for a raw syscall, fence, or unexposed instruction, write the instruction in a Coral statement. It trades safety for reach and underlies the standard library's platform layer: the mmap in std/x86_64/linux/memory/intrinsics/memory.crl is an inline syscall, and the atomics in std/x86_64/linux/concurrent/thread.crl are inline lock-prefixed instructions.

The grammar is small: an asm keyword, optional volatile, and a brace block:

asm [volatile] { "template" [ : outputs ] [ : inputs ] [ : clobbers ] }

volatile asm { ... } is also accepted; the qualifier sets the isVolatile bit on StmtKind::Asm. The template is one or more string literals; adjacent literals join, as in C. Three optional colon-delimited sections follow: outputs, inputs, then clobbers. Sections may be omitted from the right, and :: (one ColonColon token) closes a section and leaves the next empty, which is how the barrier asm volatile { "" ::: "memory" } reaches the clobber list. Operands are "constraint"(expression) pairs; clobbers are bare strings. The parser stores StmtKind::Asm { template, outputs, inputs, clobbers, flags } (coral-ast/stmt.crl:127).

An asm block writes machine instructions and hands them to the C compiler to place around your Coral variables. The template is the instruction text; outputs, inputs, and clobbers tell the compiler what the block reads, writes, and tramples.

The template is emitted verbatim inside the host C compiler's __asm__ (or __asm__ volatile), because the backend lowers straight to GNU inline assembly (coral-backend/codegen.crl:4908). Operand placeholders are C's: %0, %1, and so on, outputs first then inputs; a literal percent is %%, so registers are %%rax and instruction streams use \n\t. Constraint letters are also C's, copied without interpretation (codegen.crl:4955): "r" general register, "m" memory, "i" immediate; on x86 "a", "D", "S", "d" name AX, DI, SI, DX, and "q" a byte-addressable register. = marks an output, + a read-write operand, and a digit ties an input to an output. Operands bind by being lvalues: "=r"(v) names local v; the compiler loads inputs before and stores outputs after. Semantics checks template, output, and input expressions (coral-semantics/stmt.crl:203) but not constraints or clobbers.

A syscall shows every piece. This is the shape of the standard library's mmap:

pub rawptr sysMmap(rawptr addr, usize length, i32 prot, i32 flags, i32 fd, i64 offset) {
    usize ret;
    asm volatile {
        "movq %2, %%rdi\n\t"
        "movq %3, %%rsi\n\t"
        "movq %4, %%rdx\n\t"
        "movq %5, %%r10\n\t"
        "movq %6, %%r8\n\t"
        "movq %7, %%r9\n\t"
        "syscall\n\t"
        "movq %%rax, %0"
        : "=a"(ret)
        : "0"(9u), "D"((usize)addr), "S"(length), "d"((usize)prot),
          "r"((usize)flags), "r"((usize)fd), "r"((usize)offset)
        : "rcx", "r8", "r9", "r10", "r11", "memory"
    }
    if ((i64)ret < 0 && (i64)ret >= -4095) return null;
    return (rawptr)ret;
}

The template moves the syscall number and arguments into kernel registers, issues syscall, and reads the result from %%rax. %% keeps register names literal; %0...%7 are operands. "=a"(ret) puts the result in AX and stores it into ret. "0"(9u) shares output 0, and the rest use "D", "S", "d", or generic "r". Clobbers name destroyed registers ("rcx", "r8", "r9", "r10", "r11") and "memory", telling the compiler the call may touch arbitrary memory.

A memory barrier is the shortest useful form, nothing but a clobber:

void memoryBarrier() {
    asm volatile { "" ::: "memory" }
}

The template is empty, both operand sections are skipped with ::, and "memory" is the whole point: it forbids keeping memory values in registers across the statement. "cc" is the sibling clobber for condition codes; naming a register says it does not survive the block.

Reading a register is an output with no input. The stack pointer is always in %%rsp:

usize readStackPointer() {
    usize sp;
    asm volatile { "movq %%rsp, %0" : "=r"(sp) }
    return sp;
}

The timestamp counter has the same shape but splits its result across two registers: asm volatile { "rdtsc" : "=a"(lo), "=d"(hi) }.

Inline assembly is the least safe surface in the language. It is architecture- and target-specific, and the target C compiler assembles it, not Coral. The standard library keeps separate files per platform (std/x86_64/linux/... versus std/x86_64/windows/...); quarantine asm the same way behind a wrapper. An asm without volatile or outputs is dead code and may be deleted; use volatile for side effects. Coral does not validate constraints or clobbers today: it copies constraint strings through and never inspects them, so a wrong constraint, unlisted clobber, or missing "memory" can miscompile differently at each optimization level. The catalogue reserves E0401 (invalid register-constraint allocation), E0402 (clobbered register also a live operand), and E0403 (volatile write flushed by a non-volatile read), but those are documented intentions in errors.txt, not current checks. Do not rely on being warned.

Function attributes do not make assembly safer. #[[noreturn]] records that a function does not return, but is parsed, stored, and not yet honoured. #[[noalias]] is parsed but not emitted and is the wrong tool here: aliasing across asm is controlled by the "memory" clobber. #[[inline]] and #[[inline_always]] are codegen hints the current C backend ignores; inlining can change register allocation, never the asm. The asm's volatile differs from #[[const]]: volatile prevents movement or deletion, while #[[const]] promises no mutation of self or parameters. The const checker does not inspect asm operands, so const-correctness over asm is your responsibility.

Reach for an ordinary extern binding first: it is checkable and portable. Use inline assembly only when no binding exists (a raw syscall, an unemitted instruction, a fence), then put it in one small, target-guarded function with an accurate clobber list, and let the rest of the program call it normally.

Calling Into Coral From C

Sometimes a Coral function must be callable from C: an entry point, a callback, or a symbol in a shared object. It must have an FFI-compatible signature and an exported name. #[[no_mangle]] keeps the symbol unmangled so the linker matches what C expects:

#[[no_mangle]]
pub extern("C") i32 coral_entry(i32 argc, cchar** argv) {
    return run(argc, argv);
}

extern("C") asserts the C convention; #[[no_mangle]] keeps the symbol name. Together they make coral_entry visible and callable by that name. A callback needs no extra attributes beyond the C-compatible signature.

Three rules keep the reverse direction safe. A Coral function passed to C must not throw, panic, or unwind across the boundary; communicate errors through return values. A @drop type must never be passed by value to C, because C cannot run the destructor; it may cross by pointer under the wrapper's ownership contract. Keep the exported surface small: every exported symbol is a contract with code you cannot see.

A Worked Example: Reading a File Through a Wrapper

This program reads a text file through the wrapper, keeping the mess in one module. First the wrapper:

// file.crl, the only module that mentions a rawptr
import(lib) platform::libc { fopen, fread, fclose };
import(lib) std::text::string { String };

pub struct File { rawptr handle; }
pub variant FileError {
    OpenFailed { String path; },
    Unknown { i32 code; },
}

pub extend File : @drop {
    void drop() { fclose(self.handle); }
}

pub Result<File, FileError> fileOpen(str path) {
    String tmp = String::from(path);
    rawptr h = fopen(tmp.asCstr(), C"r");
    if (h == null)
        return Result<File, FileError>::Err {
            .error = FileError::OpenFailed { .path = path.asString() }
        };
    return Result<File, FileError>::Ok { .value = File { .handle = h } };
}

pub Result<usize, FileError> fileRead(File* f, u8* buf, usize len) {
    return Result<usize, FileError>::Ok { .value = (usize)fread((rawptr)buf, 1u, len, f->handle) };
}

Then the program that uses it, which never sees C:

import(lib) std::io::ios { println, eprintln };
import(lib) std::text::string { String };
import file;

Result<String, FileError> readWholeFile(str path) {
    Result<File, FileError> opened = fileOpen(path);
    switch (opened) {
        Err { error } => { return Result<String, FileError>::Err { .error = error }; },
        else          => {}
    }
    File f = opened.unwrap();

    String out = String::new();
    u8 buf[4096];
    Result<usize, FileError> r = fileRead(&f, buf, 4096u);
    while (r.isOk()) {
        usize n = r.unwrap();
        if (n == 0) break;
        out.pushView(str::fromParts(buf, n));
        r = fileRead(&f, buf, 4096u);
    }
    return Result<String, FileError>::Ok { .value = out };
}

void main() {
    switch (readWholeFile("config.txt")) {
        Ok { value } => { println("read {} bytes", value.len); },
        Err { error } => { eprintln("could not open the file"); }
    }
}

main never sees a rawptr, cchar, or return code, only a Result and a String. The File is owned, so it closes automatically on success or failure. The buffer is a fixed array passed as pointer and length and converted by the wrapper. The boundary is invisible, and its discipline lives in one file.

The wrapper does not hide failure, and should not: reading can fail, and failure is ordinary flow. C reported it with zero or null, the wrapper carried it as a Result, and the caller switched on it. The error never disappeared or surprised anyone. Speak both languages, decide once where translation happens, and let the rest of the code act as if C were never there.

Exercises

  1. ComprehensionWrite Coral signatures for C's double clamp(double x, double lo, double hi); and for one returning char*. Explain each type choice.
  2. ComprehensionDistinguish Coral's char, cchar, and u8. Which crosses as C char, and what breaks if you choose wrong?
  3. ImplementationDeclare externs for getpid, time, and getenv, then print the process id and an environment variable. Handle getenv returning null.
  4. StringsWrite a function taking a str and calling strlen on its C equivalent. Why convert first, what happens with a non-nul-terminated view, and how does a C"..." literal differ?
  5. LayoutDefine a packed struct for struct { char tag; int value; } and explain why #[[packed]] is required. What could the compiler do without it?
  6. DropWrite a wrapper for a C resource whose destructor frees it, show a use, and explain exactly when the destructor runs, including on error paths.
  7. ErrorsA C function returns -1 and sets errno. Wrap it in a Result-returning Coral function, and explain how to reach errno and why it is thread-local.
  8. CallbacksDeclare a C function taking a per-element callback, write and pass the Coral callback, and explain why the callback must avoid owned Coral types.
  9. ExportWrite a Coral function with C calling convention and unmangled name that C could call. Why does a @drop type not belong in its signature, even by pointer-as-value?
  10. Design and meta. Design a wrapper for a C library you know (zlib, sqlite, a graphics library): which types become structs, which functions return Results, and where destructors go. Then describe when calling C directly, with no wrapper, is right and why the wrapper is not worth its cost.
