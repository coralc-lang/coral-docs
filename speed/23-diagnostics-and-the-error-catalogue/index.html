Diagnostics and the Error Catalogue

A Compiler's Second Job

Everyone has met a compiler error that says nothing useful: a caret in the wrong place and a twenty-minute hunt for a mistake the compiler could see. Hence the compiler's second job.

A compiler first translates correct programs. Its second job, which decides whether the first is usable, is explaining incorrect ones. A diagnostic is writing for someone who just made a mistake; a vague error sends them searching, a good one ends the search in seconds. Every Coral diagnostic carries a stable code with a defined audience.

A bad error is a car alarm in a full lot. A good diagnostic is a note under the wiper saying which tire is flat and where the spare is. Coral aims for the note.

This chapter tours the catalogue by mistake kind, with a worked example of each shape, plus invocation and what makes a diagnostic good.

How Diagnostics Are Invoked

Diagnostics surface through three flags and the build subcommands that pass them along.

The default build reports errors and core warnings. --strict promotes warnings to errors for release builds. Unused-variable warnings are always on (the old --warn-unused was removed as redundant). --explain CODE prints a longer explanation:

coral
$ coralc --explain E0608

Set strict flags in the build file so every build and developer gets the same standard. A lint on for one developer and off for another is worse than off everywhere, because code drifts toward the least-strict configuration invisibly.

What Makes a Diagnostic Good

Coral diagnostic conventions are checkable.

A diagnostic names the problem in a sentence a person would say, not "invalid token" but "identifier contains a non-ASCII lookalike (U+0430) that mimics ASCII 'a' (U+0061)." The test: could you read it aloud and have a colleague understand the bug without seeing the code?

A diagnostic points at the location and, when possible, the related location. A non-exhaustive switch names the missing case; a signature mismatch points at trait and implementation. That distinguishes "there is an error somewhere" from "these two things disagree."

A diagnostic carries a stable code, so it can be searched, discussed in review, suppressed, and reused to find the same mistake. A code without a sentence is not a diagnostic, but the code makes it shared vocabulary.

A diagnostic suggests a mechanical fix: the nearest attribute, nearest specifier, or probably-intended function. A suggestion turns a puzzle into an edit.

User-generated diagnostics (@compileError or a format mismatch raised in comptime) must be structured like any other. It must not be a debug string:

coral
src[mono] evalComptimeBody FAILED decl=4106 name=println
  msg="print: placeholder/argument count mismatch
  (more placeholders than arguments)"
coral: compile failed, errors=1

That is not a diagnostic; it is the compiler leaking internals. [mono], decl=4106, and phase names do not belong in front of a person. A library-raised compile-time error is still read by a person and should carry a code, location, and sentence:

coral
src/main.crl:12:5: error E0901: format string has 2 placeholders
  but 1 argument was provided
  |
12|     println("{} {}", a)
  |     ^^^^^^^^^^^^^^^^^^^ expected 2 arguments, found 1

The compiler may not have two diagnostic classes, one for itself and an uglier one for libraries. A format mismatch is a formatted diagnostic with a location, not a debug line. One format makes the catalogue learnable.

Two error formats force a reader to identify the format before understanding the error. One format, one vocabulary, one place to look.

Build output follows the same rule. modules.map written (1 modules, 0 aliases) on every compile is noise; if the map has no reader, it should not print.

E01xx, Lexical and Parse-Time

E01xx catches surface problems: characters that are not what they look like, misplaced annotations, and misplaced comments.

E0103, Unicode homoglyph confusable reference, is the flagship. A pasted identifier contains a Cyrillic а (U+0430) where ASCII a (U+0061) was meant. They render identically but differ in bytes. A naive compiler says "undeclared identifier," sending the reader hunting for a nonexistent scope bug. Coral names the real problem:

coral
// error E0103: identifier `cаche` contains a non-ASCII lookalike
//   character (U+0430 CYRILLIC SMALL LETTER A) that mimics ASCII 'a' (U+0061)

The message names the character, codepoint, and ASCII lookalike, exactly what a one-edit fix needs. Say what is wrong, not the first downstream symptom.

E0104, misplaced attribute target, fires when #[[inline]] attaches to a statement or expression instead of a function or struct:

coral
void setup() {
    #[[inline]]             // error E0104: #[[inline]] does not apply to
    x = compute();          //   a statement
}

The compiler knows which attributes are valid at which positions and reports the mismatch rather than ignoring it. An instruction that cannot mean what it says is a bug, not a no-op.

E0105, doc-comment on an expression statement, fires when /// or /** attaches to executable code rather than a declaration:

coral
void process() {
    /// This comment documents what?
    x = x + 1;              // error E0105: doc-comment on an
}                           //   expression statement

Doc comments travel with declarations into generated documentation. Attached to executable code, the comment has nowhere to go, usually because it drifted from a declaration above or below.

E02xx, Type Layout

E02xx concerns memory layout; its most important member stops a program from being impossible.

E0201, cyclic type layout of infinite size, catches a struct or variant containing itself with no indirection:

coral
struct Node {
    i32 data;
    Node next;      // error E0201: Node contains itself
}

Node's size depends on Node's size, so the recursion never bottoms out. The fix is indirection, Node* next, whose size is known regardless of what it points at:

coral
struct Node {
    i32 data;
    Node* next;     // fine: a pointer is one machine word
}

The message explains the cycle and names the closing field. The compiler refuses to emit a type with no bytes. Recursive variants trigger the same error, which is why Chapter 13's interpreter stores sub-expressions behind pointers.

The compiler is asked to size a box containing itself and can never finish. A pointer says where the other box is instead of containing it, and an address on paper has a size regardless of the building.

E0202 catches a zero-sized field forced to overlap adjacent data or a zero-sized type needing a distinct address. E0203 catches layout conflicting with target alignment, such as #[[align(N)]] or an impossible C layout. E0204 catches bitfields exceeding backing storage. E0205 catches casting a composite directly to a primitive with no serialization:

coral
struct Color { u8 r; u8 g; u8 b; u8 a; }
Color c = ...;
u32 packed = (u32)c;    // error E0205: cast truncates composite layout

Each is a layout question answered at compile time. The compiler will not guess at bytes; ambiguous or impossible layouts are reported.

E03xx, Constant Evaluation

E03xx catches errors visible during constant evaluation, in a comptime block or const initializer. These would be runtime crashes in a less careful language.

E0304, dereferencing a raw pointer inside compile-time const evaluation, catches a comptime block reading a hardware address:

coral
const val = @comptime {
    rawptr p = (rawptr)0xDEADBEEF;
    return *p;          // error E0304: cannot read an address at comptime
};

The value is unknown until the program runs on a particular machine, so it cannot be constant. Only deterministic memory values are permitted at compile time.

E0305, division by zero in constant evaluation, catches a compile-time divide by literal zero:

coral
const ratio = 10 / 0;   // error E0305: division by zero in const evaluation

E0306, integer literal overflows declared type, fires when a literal fits no value of its declared type:

coral
u8 x = 300;             // error E0306: 300 does not fit in u8

The type is eight bits and the value needs nine; no truncation or wraparound is chosen. The literal is simply not a legal u8.

E0307, constant array index out of bounds, fires when a fixed-size array is indexed by a constant outside its bounds:

coral
i32 a[4];
a[7] = 1;               // error E0307: index 7 out of bounds for [4]

This is compile-time bounds safety. A constant index is checked at build time, so the runtime check can disappear for the common known-index case. The compiler has the length and index and reports rather than reading past the end.

E04xx, Inline Assembly

E04xx guards hand-written assembly, where the compiler's machine model must match the programmer's. Assembly mistakes are silent and catastrophic: the program links, runs, and returns wrong answers.

E0401, invalid inline assembly register constraint allocation, catches an output bound to a register class of the wrong size, such as a 64-bit value in a 32-bit register or a float in a general-purpose register. Constraint and operand size must agree.

E0402, clobbered register listed as a live input or output operand, catches a contradiction: the programmer says the block modifies a register and also passes an input placed in that same register. The input would be destroyed before use, so the compiler reports rather than guessing.

E0403, volatile memory write flushed by non-volatile read optim, catches a volatile write immediately overridden by a non-volatile read the optimizer may remove or reorder, defeating the intended signal. It is a warning that the code's memory model does not say what the author thinks.

These checks are the compiler holding up its side: raw instructions still require coherent register discipline.

E05xx and the Build Diagnostics, Linking and Modules

E05xx catches boundary problems between Coral, the linker, and modules.

E0501, duplicate symbol conflicting with the target export map, catches a symbol colliding with a reserved ABI name, such as a #[[no_mangle]] name already used by an OS hook or ABI reservation. It names the symbol and the reservation.

E0502, cyclic external module initialization chain, catches a startup cycle where module A's setup needs B's and B's needs A's. Neither can finish first. The trace shows the loop, turning a runtime hang into a build error.

E0503, mismatched linkage convention for function pointer, catches passing a standard native function pointer to an API requiring a different convention (extern "stdcall" or extern "C"). Calling convention is part of the type.

Module resolution has its own build-time diagnostics. An unresolved re-export, missing module, duplicate identity, bad alias, unresolved import, or module-graph cycle gets a code, with a trace for cycles. These are the builder's findings from Chapter 21, kept distinct so "imports do not resolve" and "code has a type error" remain different problems. Cyclic imports themselves are resolved; the initialization cycle, E0502, is the genuine error.

E06xx, Control Flow, Switch, and Data Flow

E06xx is the largest and most frequent range: mistakes about control flow and data flow.

E0608, switch not exhaustive and missing else, is the promised one. A switch over an enum or variant with no else that misses a case is an error:

coral
switch (shape) {
    Shape::Circle { r }  => { area = pi * r * r; },
    // error E0608: non-exhaustive switch; missing Shape::Square, Shape::Point
}

The message names the missing cases, so the fix is immediate. This makes Chapter 13's variant-and-switch style safe: forgetting a case is a build failure with a list, and adding an enum case breaks every switch that did not anticipate it.

E0609, unreachable switch case, catches a duplicate case or a variant already covered by an earlier arm:

coral
switch (c) {
    Color::Red  => { ... },
    Color::Red  => { ... },      // error E0609: unreachable case
}

This arm can never run. It catches copy-paste mistakes where a case was meant to change but did not.

E0610, fallthrough attribute on last arm, catches a leftover #[[fallthrough]] where there is nothing to fall into, usually a copy-paste vestige.

The rest concerns data flow across branches. E0601, branch reaches end of non-void block without value yield, catches a path that skips returning while others yield:

coral
i32 pick(bool c) {
    if (c) {
        return 1;
    }
    // error E0601: this path reaches the end without returning a value
}

E0602, use of partially moved or deallocated stack memory, catches passing a struct to a consuming function then reading a remaining field:

coral
File f = File::open("x");
consume(f);             // f is moved here
log(f.name);            // error E0602: use of partially moved value

E0603, unreachable code after diverging statement, catches statements after return, break, or continue in the same block. E0604, non-void function reaches end without return, catches a non-void function that can fall off its end. E0606 catches self-assignment such as x = x; or x += 0. E0607, use of local before all paths initialize it, is definite-assignment analysis:

coral
i32 x;
if (c) {
    x = 1;
}
return x;               // error E0607: x may be uninitialized here

Each is a bug class that has shipped in languages lacking the check. Coral's compiler can see them, so it should; none requires running the program.

Definite-assignment analysis walks every path and asks whether the variable is certainly set. One skipped path stops you. Assigning inside if (c) { ... } does not count afterward, because the branch might not run.

E07xx, Parse Ambiguities

E07xx is about grammar, not semantics: places where C-like syntax has two readings and the compiler must choose.

E0701 is the classic most-vexing-parse. Time Keeper(Timer()); can read as a function call or a variable declaration. Coral picks one and explains how:

coral
Time Keeper(Timer());
// warning E0701: parsed as a variable declaration `Keeper` of type
//   `Time`, initialized with a temporary `Timer`; if you meant to call
//   `Keeper`, wrap the argument: `Time Keeper((Timer()));`

The diagnostic states the choice and shows the fix rather than leaving the reader to discover the unexpected reading.

E0702, missing typename or template keyword in dependent scope, catches T::InternalType* ptr;, where the parser cannot tell whether InternalType is a static variable multiplied or a type pointed to. It states its assumption so the ambiguity surfaces at parse time.

E0703, tentative parse rollback limit exceeded, is a safety valve. If a malformed expression forces too many speculative branches without a synchronizing token, the parser kills the branch rather than overflowing its stack. A reported parse failure beats a crash.

E0704 is the dangling else: a nested unbraced if binds the else to the innermost condition, and the compiler reports the binding so braces can be added if needed:

coral
if (a)
    if (b)
        doX();
else                    // warning E0704: this `else` binds to `if (b)`
    doY();

This range is the compiler being honest about its choices. Silent disambiguation creates surprising behavior; stating the resolution avoids it.

E08xx, Lints

E08xx is advisory: legal but almost certainly not intended. Warnings by default, errors under --strict.

E0801, unused variable, catches a computed value never used, usually a deleted line or mistyped name. E0802, unused import, keeps dependencies honest. E0803, unused parameter, catches a parameter never read; a leading underscore opts out for callbacks that require an unused argument:

coral
void onEvent(Event e, _context ctx) { ... }   // _context opts out

E0804, binding never mutated but declared mutable, catches a mutable variable never reassigned, which could be const. E0805, use of deprecated item, is generated by #[[deprecated]] and names the replacement:

coral
connect("example.com");
// warning E0805: `connect` is deprecated: use connect_v2(host, port) instead

E0806 and E0807 are the attribute lints from Chapter 22. An unknown attribute gets a nearest-match suggestion, so a typo becomes a fix:

coral
#[[inlne]]
// warning E0806: unknown attribute `inlne`; did you mean `#[[inline]]`?

A duplicate attribute is reported so a repeated or contradictory instruction is never dropped. Attributes carry intent, and dropping one diverges intent from result.

E09xx, Format Strings

E09xx checks format strings from Chapter 17, because the compiler can see both format and arguments.

E0901, format string argument count mismatch, fires when placeholder count differs from argument count:

coral
println("{} {}", a);    // error E0901: 2 placeholders, 1 argument

E0902, format placeholder type mismatch, fires when a specifier demands an integer and receives a type with no such rendering, such as a pointer or unformattable struct. E0903, unknown format specifier, fires on a specifier outside the set, with the closest suggested:

coral
println("{q}", value);  // error E0903: unknown specifier `q`; did you mean `{}`?

This is comptime's payoff: format and arguments are visible at compile time, so a runtime crash in C becomes a build failure. A library comptime failure is still a normal E09xx diagnostic with a location, not an internal string. Runtime-built format strings cannot be checked, but most are literals, where the check is free.

Because Coral sees format string and values together before running, a wrong count is treated like a typo: a build error, not a three-in-the-morning surprise.

E10xx, Const and Mutation

E10xx catches mutation of things that must not change. E1001, mutation through a const-qualified pointer, fires when a function takes const T* and writes through it:

coral
void overwrite(const i32* p) {
    *p = 0;             // error E1001: cannot mutate through const i32*
}

This is const's teeth. A const parameter promises the pointee will not change; violating it is a callee bug, caught at the store rather than at the caller. With the const method check, it makes const worth writing.

E11xx, Compile-Time Execution

E11xx guards the comptime machinery of Chapter 7, where code runs during the build.

E1101, comptime leak of runtime-dependent address, catches a comptime block reading or storing an address known only at load time, such as a heap allocation or thread-local:

coral
const addr = @comptime { return (usize)&globalHeap; };
// error E1101: address is only known at load time

E1102, comptime mutation of immutable static memory, catches a comptime write to a global constant or frozen read-only segment. E1103, comptime evaluation loop limit exceeded, cuts off unbounded comptime loops or recursion, showing macro call-stack depth, so an accidental infinite loop is a diagnostic rather than a hang:

coral
@comptime {
    while (true) { }
    // error E1103: comptime evaluation exceeded its budget
    //   (loop/recursion depth limit); call stack: genVector -> genVector ...
}

E1104, non-comptime type emitted by generic factory, catches a function intended to generate types that returns a runtime instance or evaluated variable rather than a concrete type token. Comptime has a budget, and exceeding it is reported.

E12xx, Methods and Traits

E12xx checks the trait machinery of Chapter 6.

E1201, overlapping method definitions across blocks, catches a method defined twice for one type across extend blocks. The blocks may be separate, but a signature may exist only once, and the compiler points at both:

coral
extend Shape { f64 area() { ... } }
extend Shape { f64 area() { ... } }
// error E1201: `area` defined twice for `Shape` across extend blocks

E1202, trait method signature mismatch, catches an implementation whose parameters or return type differ from the trait's declaration, reporting both. E1203, missing required trait method, catches a claimed conformance that omits a required method:

coral
extend Circle : @shape { }
// error E1203: `Circle` implements `@shape` but is missing `area()`

These three make trait conformance trustworthy: a type claiming Shape either implements it or does not compile. This is the abstract-class check moved to the conformance site.

E13xx, Drop and Bounds

The final range guards ownership interacting with traits and generics; it is the most subtle family.

E1301, explicit call to a drop method disallowed, catches x.drop():

coral
String s = String::from("hi");
s.drop();               // error E1301: cannot call drop() explicitly
//   note: `drop` runs automatically when `s` goes out of scope;
//   for manual cleanup use #[[no_drop]] and clear()/free()

Because drop is driven by scope termination, an explicit call invites a double free when the scope also ends. The compiler blocks it and suggests the built-in cleanup function. Use #[[no_drop]] plus a normal cleanup function for manual cleanup; let scope end for automatic cleanup. Never both.

E1302, drop trait implemented on type with comptime bounds, catches a drop implementation whose type varies entirely with comptime conditions, where a fixed-layout destructor cannot be sound. E1303, linear field capture outlives drop execution, catches a field moved out before drop runs, which would run drop on partially uninitialized memory:

coral
struct Holder : @drop { Payload p; ... }
Holder h = ...;
Payload taken = h.p;    // moves p out
// ... later, h goes out of scope and drop() runs on the moved-out field
// error E1303: field `p` was moved out; drop cannot run on a partial value

E1304, a capability missing at a generic's instantiation, catches a generic using an operation its type parameter lacks, such as printing a T that has no @toStr. These four are lifetime or capability mistakes that must be caught for soundness, each at compile time with a location and sentence.

A Worked Example: Reading a Diagnostic Trail

One mistake often produces several diagnostics. Consider a non-exhaustive switch in a non-void function, with an unused variable above:

coral
str label(Shape s) {
    i32 unused = 0;
    switch (s) {
        Shape::Circle { r }  => { return "circle"; },
    }
}

The compiler reports in order: E0801 unused variable unused; E0608 non-exhaustive switch over Shape, missing Shape::Square and Shape::Point; then E0604 non-void function label can reach its end without returning. Three diagnostics, one root cause in two places.

Read the order as a dependency graph, not a to-do list. E0604 is a consequence of E0608: once the switch is exhaustive, every path returns and E0604 vanishes. Fixing the cases clears both; removing the unused variable clears E0801 independently. Ask of each diagnostic: is this the problem, or its shadow?

Stable codes pay off here. "Control reaches end of non-void function" and E0604 are the same finding; the code lets a reader search, suppress consistently, or find the reference. The catalogue is the compiler's vocabulary.

Exercises

  1. ComprehensionWhy does every diagnostic carry a code? Give two things a code makes possible that a bare message does not.
  2. ComprehensionE0201 prevents an infinite-size type. Why does a pointer break the cycle? Give a legal self-referential type.
  3. ComprehensionA user-raised @compileError and a library-detected format mismatch are both diagnostics. Why may neither be a debug string? Use the evalComptimeBody FAILED decl=4106 line as what to avoid.
  4. ImplementationTrigger E0608, then fix it three ways: add missing arms, add an else, and add a fallthrough. Which fix is right, and when?
  5. ImplementationTrigger E0307 with a constant index and with a runtime index. Which fires at compile time, and why?
  6. LintsCount unused-variable warnings in one of your programs, fix them, and classify which caught real bugs and which were noise.
  7. FormatWrite calls triggering E0901, E0902, and E0903, then the corrected calls.
  8. TraitsTrigger E1203 by claiming a trait conformance and omitting a method. What does the diagnostic name, and what is the fix?
  9. DropTrigger E1301 by calling drop directly. What does the compiler suggest, and why is the manual call unsafe?
  10. OrderingWrite a program with a missing switch case inside a non-void function. List diagnostics in order and identify causes versus consequences.
  11. MetaThe catalogue is organized by mistake kind rather than compiler pass. Argue for and against. Would you group E06xx differently, and why?
  12. WritingFor E0701 and Time Keeper(Timer());, write the message you think it should produce. Aim for E0103's standard: what happened, where, and why.
