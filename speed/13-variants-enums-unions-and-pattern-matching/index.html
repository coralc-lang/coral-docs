Variants, Enums, Unions, and Pattern Matching

The Shape of "One of Several Things"

A payment is a card payment, a bank transfer, a gift card, or a refund, each carrying different data: card number and expiry, account and routing code, code and balance, or a pointer to the original payment.

Giving them all the same struct leaves half the fields meaningless for any value, and nothing stops code reading an empty one. This is the most common modelling problem: a value that is one of several things, each with its own data.

Coral has three non-interchangeable tools, differing in how much the compiler may know:

enum     a closed, named set of integers, with no extra data attached
variant  a "tagged union", one of several cases, each carrying its own data
union    a raw, unsafe overlapping of storage, with no tag at all

An enum is a label. A variant is a label plus cargo. A union is no label at all, just a spot where different things take turns standing.

Plain Enums: Giving Integers Names

A traffic light can be red, yellow, or green, nothing else. In C you would use raw integers with a comment, or constants. Both are quietly dangerous.

The first is raw integers pretending to be names:

i32 light = 0;      // 0 = red, 1 = yellow, 2 = green
...
if (light == 3)     // oops, there is no 3, but this compiles

The comment is not a type: nothing stops the 3 or a function returning 17. The compiler does not read wishes.

The second is constants:

const i32 RED = 0;
const i32 YELLOW = 1;
const i32 GREEN = 2;

Better, but constants add no type checking. A constant is a name for a number, not a distinct type: you can still assign 3 to a light, or pass a light where an age is expected.

An enum creates a genuinely new type and lists the only values it can hold:

enum TrafficLight {
    Red,
    Green,
    Yellow,
}

Three consequences. TrafficLight is a real type, so a TrafficLight is not an i32 and vice versa. There are exactly three legal values. And the compiler knows the complete list, so it can check whether a switch covers every case.

Write an enum value with two colons:

TrafficLight light = TrafficLight::Red;

if (light == TrafficLight::Red) {
    stop();
} else if (light == TrafficLight::Green) {
    go();
} else {
    slowDown();
}

The double colon :: means "the case Red of the type TrafficLight." The left side is the container, the right side the item inside it, as with a module (std::io) or a static method (Vec::new).

Enums let the compiler enforce a value's legal choices: a function taking a TrafficLight can never receive a stray 3, and a switch over it can be checked for completeness. A fact that used to live in a comment becomes something the compiler enforces.

switch (light) {
    TrafficLight::Red    => stop(),
    TrafficLight::Green  => go(),
    TrafficLight::Yellow => slowDown(),
}

Three arms, no else, and the compiler is satisfied because all three lights are covered. Add a fourth light and this switch stops building until the new case is handled.

A Layer Behind: the actual integers

Underneath, an enum is an integer: Red is 0, Green is 1, Yellow is 2. The compiler numbers cases from zero in declaration order. Normally do not rely on the numbers; the point is to refer to cases by name.

When the number matters, say so. File types from an operating system have fixed, non-sequential numbers:

enum FileType : u8 {
    Unknown   = 0,
    Regular   = 1,
    Directory = 2,
    Symlink   = 7,
    Socket    = 12,
}

Two pieces of syntax: : u8 sets the underlying storage to one byte instead of the default four, which matters when the enum is a field and struct size is at stake. = N pins a case's numeric value when the numbers are dictated by an external format or system call.

The pinning rule: a case with an explicit value takes it; a case without one takes the previous value plus one. Here, a case after Socket with no =, would be 13.

Reach for an enum for a small, closed, unchangeable set of options with no extra data: traffic lights, days of a week, connection states (Connecting, Open, Closing, Closed), card suits, log levels (Debug, Info, Warn, Error, Fatal), token kinds in a lexer.

Never let a raw integer from outside sneak into an enum-typed variable unchecked. A byte of 5 cast to FileType manufactures an illegal case absent from your list, and every switch behaves as though it were impossible. Coral treats integer-to-enum as a checked conversion: convert deliberately and handle "not one of mine." Chapter 23 lists the diagnostic for a switch that forgot a case.

Variants: When Each Case Carries Its Own Data

Enums are for options with nothing attached. Now each option carries different things.

Picture a drawing program. A shape is a circle with a radius, a rectangle with a width and height, or a point with nothing. You want one variable, shape, that can be any of these, and you want its area without accidentally reading a rectangle's width off a circle.

An enum cannot carry the radius. You could bolt the data on with a kind field and all possible fields in one struct:

enum ShapeKind { Circle, Rectangle, Point }

struct Shape {
    ShapeKind kind;
    f64 radius;     // only valid if kind == Circle
    f64 width;      // only valid if kind == Rectangle
    f64 height;     // only valid if kind == Rectangle
}

This is the C way, and it is a trap. "Only valid if kind == Circle" is a wish: nothing prevents reading shape.radius on a rectangle, which silently yields zero and draws the wrong thing. The four pieces must always agree, nothing enforces it, and every new field must be threaded through every function touching Shape.

A variant removes the trap. One declaration says a Shape is one of these cases, and each case brings its own fields into existence:

variant Shape {
    Circle { f64 radius; }
    Rectangle { f64 width; f64 height; }
    Point,
}

A variant value is exactly one of its cases, and each case brings its own fields into existence.

Think of a job application form that can be for one of several roles. The paper is the same, but a driver application has a licence number, a chef application has a food-safety certificate, and a cashier application has neither. You cannot ask a driver application for a food-safety certificate because that field does not exist on that form.

A Circle contains a radius and no width or height; a Rectangle contains width and height and no radius. The other fields are absent, not merely empty. Underneath, the compiler stores a hidden tag recording which case this is, plus room for the largest case's fields. It will not let you read the radius of something tagged Rectangle, because that radius is not part of this value. The box has a label outside and exactly the cargo for that label inside.

Build a variant value by naming the case and giving its fields:

Shape a = Shape::Circle { .radius = 1.0 };
Shape b = Shape::Rectangle { .width = 3.0, .height = 4.0 };
Shape c = Shape::Point;

The { .radius = 1.0 } is the same designated-field syntax used to initialise a struct. A case with no fields is written as just Shape::Point, optionally with empty braces.

A common mistake is leaving off the case name: { .radius = 1.0 } reads as a bare struct literal with no tag, so the compiler cannot tell which case it is and refuses it where a Shape is expected. Shape::Circle places the value in the right family.

The same model for network messages, where each case carries different things:

variant Message {
    Login  { str username; str password; }
    Logout { str reason; }
    Data   { u32 sequence; u8[] payload; }
    Ping,
}

Every message is exactly one of those four. Ping carries nothing; Login carries a username and password. You cannot send a message that is half Login and half Data. Adding a fifth kind makes every switch that handles messages refuse to compile until it handles the new case.

A variant is a labelled box: the label says which case this is, and inside is exactly the cargo for that label. A Login box has no room for a payload; a Data box has no password. Because the label is part of the value, the compiler always knows which cargo is truly there, which is the difference between a variant and a bare union of the same bytes.

The recursive example: JSON, and why it matters

Recursive variants matter because they model entire domains. A JSON document is null, a boolean, a number, a string, an array of JSON, or an object mapping strings to JSON. Two cases refer back to JSON itself:

variant Json {
    Null,
    Bool   { bool value; }
    Number { f64 value; }
    Str    { str value; }
    Array  { Vec<Json> items; }
    Object { Map<str, Json> fields; }
}

This is a tree whose shape is defined by the variant. An array holds more JSON, which may themselves be arrays, as deep as the document goes. The type is self-referential, and the variant makes that expressible cleanly. In C you would use a struct with a type field, a void* payload, and casts at every use site. The variant turns the casts into a language feature and the compiler tracks the payload's type. std::parser::json is built on precisely this declaration.

Variants can have methods, inline or in an extend block. The shape example with an area method:

pub extend Shape {
    f64 area() {
        switch (self) {
            Shape::Circle { radius }         => 3.14159 * radius * radius,
            Shape::Rectangle { width, height } => width * height,
            Shape::Point                     => 0.0,
        }
    }
}

Inside area, self is the whole Shape. The switch asks which case it is, and Shape::Circle { radius } checks that it is a circle and binds its radius to a local. This is pattern matching, the second half of the chapter, and it is why variants are pleasant rather than merely possible.

Unions: Overlapping Storage, and Why You Rarely Want It

The raw union is worth understanding even though you will rarely use it, because it explains what a variant is not.

Picture one parking spot. Monday a car, Tuesday a motorcycle, Wednesday a bicycle. The spot is one piece of pavement, but the occupant changes, and only the current occupant is valid to inspect. On Wednesday the pavement does not stop you from measuring the bicycle as though it were a car.

A union is that parking spot. It overlaps its fields in the same bytes:

union Bits {
    u32 whole;
    struct {
        u8 b0; u8 b1; u8 b2; u8 b3;
    } bytes;
}

Bits b;
b.whole = 0x01020304;
u8 low = b.bytes.b0;      // which byte is this? depends on your machine

Writing b.whole fills all four bytes; reading b.bytes.b0 views them as four separate bytes. That is a type pun, and it is occasionally right and mostly wrong. The critical difference from a variant is in the declaration: a union has no tag, so nothing records which field you wrote. Reading b.bytes.b0 after writing whole reinterprets whatever bytes are there. Get it wrong and you get no error, just a plausible, meaningless number.

A union is right in three honest jobs, and almost nothing else:

  • Implementing a tagged union by hand at an ABI boundary where you genuinely cannot use Coral's variant (for instance, a C library's struct layout that you must match byte for byte).
  • Deliberate, endian-aware type punning, reading an integer as bytes or the reverse, in code that is explicitly about representation.
  • Laying out hardware registers or wire-protocol headers where fields are specified to share storage.

Each of those deals with bytes as bytes, with known system rules. Everything else, ninety-nine cases out of a hundred, wants a variant. If you find yourself writing a union and an enum side by side, a struct holding both, and code checking the enum before touching the union, stop: you have reimplemented a variant, worse.

If you do use a union, two habits keep it safe. Hide it behind a function or method that documents the invariant and endianness assumptions; never let raw union access spread. Keep it private: a bare union field crossing a module boundary is a promise no reader can verify, so expose a typed accessor.

Unions are the tool of last resort, for matching a layout the outside world dictated: a C struct, a network header, a hardware register. Otherwise a variant gives the same compact storage with a compiler-checked label. A union where a variant would do is a parcel with no address, hoping the courier guesses.

By default the compiler may insert padding, leave alignment gaps, and reorder fields for efficiency. For a union that must match an external layout, pin the layout with attributes. #[[packed]] removes padding so bytes lie exactly where you put them; #[[reorder]] explicitly permits permutation for a tighter fit. Chapter 22 covers these; you will need them whenever the bytes matter, as in FFI, files, and networks.

Pattern Matching: switch as a Decision Procedure

We have built values that are one of several things. Now we take them apart with switch, which in Coral is both a statement and an expression: it can decide what to do and compute a value.

Suppose a user types a command character and you want different behaviour for each:

switch (command) {
    'q' | 'Q' => quit(),
    'h'      => help(),
    else     => unknown(),
}

Read left to right: if the command is 'q' or 'Q', quit; if 'h', help; otherwise unknown. Each line is an arm. The thing left of => is a pattern, a shape to match, and the right is what to do. The first matching arm wins.

For command equal to 'h', the first arm fails because the value is neither 'q' nor 'Q'. The second matches, so help() runs and the switch is done; else is never reached. For 'z', neither of the first two matches, so else runs unknown().

There is no break between arms: a Coral switch does not fall through. Each arm is self-contained, the opposite of C, and deliberately so, because accidental fallthrough is a classic C bug. To share a body, list both patterns on one arm joined by |, as 'q' | 'Q' does; | reads as "or." The standard library and the compiler's own back end (wallvm) use this throughout, e.g. IrOpcode::Load | IrOpcode::Gep | IrOpcode::AtomicLoad => ....

The forms a pattern can take

Patterns match against the shape of a value. The main kinds:

Literal patterns match a specific constant. Several literals joined with | mean "any of these":

switch (httpStatus) {
    200            => println("OK"),
    301 | 302 | 307 => println("redirect"),
    404             => println("not found"),
    500 | 502 | 503 => println("server error"),
    else           => println("other"),
}

Variant patterns match a case and pull its fields into local names. This is the workhorse:

switch (message) {
    Message::Login { username, password } => authenticate(username, password),
    Message::Logout { reason }            => logOut(reason),
    Message::Data { sequence, payload }   => store(sequence, payload),
    Message::Ping                         => sendPong(),
}

The names in braces are fresh locals scoped to that arm. Name only the fields you need: Message::Login { username } => ... binds just the username and ignores the password. Some { value } and Option::Some { value } mean the same thing.

Tuple patterns match position by position, covered in Chapter 12. A small useful one, deciding what a pair of signs means:

switch ((x >= 0.0, y >= 0.0)) {
    (true, true)   => println("first quadrant"),
    (false, true)  => println("second quadrant"),
    (false, false) => println("third quadrant"),
    (true, false)  => println("fourth quadrant"),
}

Four possible combinations, all listed, so the switch is exhaustive and the compiler confirms it. Encoding a decision as a tuple of small closed values and matching turns a chain of ifs into a table the compiler can check.

Binding patterns give a name to the whole value. A bare identifier in pattern position is a binding, not a constant to compare against:

switch (point) {
    (x, 0) => println("on the x-axis at {}", x),
    (0, y) => println("on the y-axis at {}", y),
    (x, y) => println("at ({}, {})", x, y),
}

The wildcard is written else, not an underscore. Coral uses else for "anything not matched above."

Guards: patterns with a condition

Sometimes shape is not enough and you want "a key event, but only the escape key." A guard is an if clause between pattern and arrow. It is checked only after the pattern matches and may read the names the pattern bound:

switch (event) {
    Event::Key { code } if code == ESC => quit(),
    Event::Key { code }                => handleKey(code),
    Event::Resize { width, height }    => onResize(width, height),
    else                               => ignore(),
}

The first arm matches any key event, binds its code, and asks whether it is ESC. If not, the arm fails and the next is tried. Without guards you would need one arm per key or a nested if; with them, the condition lives with the pattern.

The Three Rules of a Coral switch

A switch over an enum or variant is governed by three rules, which together make forgetting a case a compiler error rather than a runtime surprise.

First, be exhaustive. A switch over an enum or variant must cover every case or include an else. If a case is missing and there is no else, the compiler reports it and names the missing cases:

enum Color { Red, Green, Blue }

str name(Color c) {
    switch (c) {
        Color::Red   => return "red",
        Color::Green => return "green",
        // Color::Blue is missing!
    }
}

// error E0608: non-exhaustive switch over Color;
//   missing cases: Color::Blue

The error names exactly what is missing. When someone later adds a Color::Purple case, every switch that did not anticipate it stops compiling, and the compiler lists every place needing an update. "I forgot a place" becomes a build failure rather than a shipped bug.

Exhaustiveness means the compiler will not let you leave a case unhandled. Adding a case to a variant is therefore safe: the compiler visits every switch and makes each decide what to do.

Second, be reachable. An arm that can never run is an error. A duplicate case, or a case an earlier arm already covered, is reported:

switch (c) {
    Color::Red   => ...,
    Color::Red   => ...,      // error E0609: unreachable case
}

This catches a copy-paste mistake and overlapping ranges.

Third, fallthrough must be deliberate. Arms do not fall through by default, but sometimes you want the C behaviour. Say so with #[[fallthrough]]:

switch (mode) {
    Mode::Initialize => {
        setup();
        #[[fallthrough]]
    }
    Mode::Run => {
        run();
    }
    else => {},
}

#[[fallthrough]] on the last statement of Initialize tells the compiler "yes, I meant to fall into Run." Without it, the compiler warns, because accidental fallthrough is almost always a bug. Putting it on the last arm, where there is nothing to fall into, is an error (E0610), always a leftover from copying an arm.

Together the three rules say every case is handled, caught by else, or deliberately fallen through, and someone said so on purpose.

A missing case is not just a warning: a non-exhaustive switch over an enum or variant is an error (E0608) and the program will not build. Some value could reach the switch with nothing to do, and the compiler stops you now rather than letting it surprise you at runtime.

switch That Computes a Value

Because arms produce values, a switch can be the right-hand side of an assignment, an argument, or a function body. When every arm yields the same type and the switch is exhaustive, the switch has that type.

str severityLabel(LogLevel level) {
    return switch (level) {
        LogLevel::Debug => "DEBUG",
        LogLevel::Info  => "INFO",
        LogLevel::Warn  => "WARN",
        LogLevel::Error => "ERROR",
        LogLevel::Fatal => "FATAL",
    };
}

Each arm is an expression; all arms are strings and every LogLevel is covered, so the switch is a string. When an arm's body is a block, the block's final expression is the arm's value:

f64 area(Shape s) {
    return switch (s) {
        Shape::Circle { radius } => 3.14159 * radius * radius,
        Shape::Rectangle { width, height } => {
            f64 a = width * height;
            return a;
        }
        Shape::Point => 0.0,
    };
}

A switch used for side effects is a statement and takes a semicolon. A switch used for a value is written where a value is expected.

A value-computing switch turns a label into a result without temporary variables, and the compiler still checks exhaustiveness, so the promised value exists for every case in the type.

Matching on Ranges and the Exhaustiveness Check Applied

Literal patterns cover exact values. For the common "between these bounds" case, Coral has range patterns, checked for overlap as literals are for duplicates.

char grade;
switch (score) {
    90..=100 => grade = 'A',
    80..=89  => grade = 'B',
    70..=79  => grade = 'C',
    60..=69  => grade = 'D',
    0..=59   => grade = 'F',
    else     => grade = '?',
}

..= is an inclusive range, "from 90 up to and including 100." .. is exclusive. Overlapping ranges make the second unreachable (E0609), a bug class that slips past if chains.

Reach for ranges, enums, and tuples rather than long if chains because the compiler can check a closed, structured decision for completeness and overlap, and it cannot check a chain of ifs at all. Every decision expressed as a match over a closed set is work handed to the compiler.

A Worked Example: An Arithmetic Interpreter

The classic use of variants and matching is a little language, which shows how the shape of the data and the shape of the code mirror each other. Represent and evaluate expressions like (3 + 4) * -(2).

An expression is a number, the sum of two expressions, the product of two expressions, or the negation of one. That sentence is already a variant:

variant Expr {
    Num { f64 value; }
    Add { Expr left; Expr right; }
    Mul { Expr left; Expr right; }
    Neg { Expr operand; }
}

Evaluate a number by returning it; a sum by evaluating both sides and adding; a product by evaluating both sides and multiplying; a negation by evaluating the operand and negating. Each sentence is one arm:

f64 eval(Expr e) {
    return switch (e) {
        Expr::Num { value }       => value,
        Expr::Add { left, right } => eval(left) + eval(right),
        Expr::Mul { left, right } => eval(left) * eval(right),
        Expr::Neg { operand }     => -eval(operand),
    };
}

Two things stand out. eval is total: it covers all four cases, so the compiler guarantees no shape is forgotten. Add Expr::Div and eval stops compiling until it handles division. And the code mirrors the data: eval recurses on children, while Num, which has none, stops the recursion. One function per operation, one case per shape, is the functional style, and the variant makes it natural.

For (3 + 4), eval sees Expr::Add, binds left to Num { .value = 3.0 } and right to Num { .value = 4.0 }, then computes eval(left) + eval(right): 3.0 and 4.0, giving 7.0. Recursion bottoms out at the Num cases.

Printing shows the same mirroring from another operation:

str show(Expr e) {
    return switch (e) {
        Expr::Num { value }       => formatFloat(value),
        Expr::Add { left, right } => "(" + show(left) + " + " + show(right) + ")",
        Expr::Mul { left, right } => "(" + show(left) + " * " + show(right) + ")",
        Expr::Neg { operand }     => "-" + show(operand),
    };
}

Two functions, two switches over the same variant. Add an operation and write a new switch; add a case and you must update both switches because the compiler insists. That trade, new operations are cheap while new cases touch every operation, is the expression problem. Whether it is good depends on which direction you expect to change more, and the variant makes the trade explicit.

One rule from this example: Expr::Add stores two Expr values by value, and Expr is recursive, so a naive layout would be infinite: the size of an Expr needs the size of its children, forever. The compiler refuses such a type with a cyclic type layout of infinite size (E0201). Put the recursion behind a pointer:

variant Expr {
    Num { f64 value; }
    Add { Expr* left; Expr* right; }
    Mul { Expr* left; Expr* right; }
    Neg { Expr* operand; }
}

Now an Expr is a pointer plus the largest non-recursive case, and the tree links through the heap. Chapter 11 covers ownership and freeing of exactly this kind of data, and smart pointers and arenas make such trees manageable.

A Second Worked Example: A State Machine

Variants are not only for trees. A value that changes what it is over time is a state machine, which is a variant with methods that move between cases. A network connection starts disconnected, connects, becomes connected, and may fail.

variant Connection {
    Closed,
    Connecting { str host; u16 port; },
    Open       { i32 fd; },
    Closed
}

That is not quite right, and the mistake is instructive: two cases cannot be named Closed. Model the real states:

variant Connection {
    Disconnected,
    Connecting { str host; u16 port; },
    Connected   { i32 fd; },
    Error       { str reason; }
}

Now the operations are methods that match the current state and produce the next:

pub extend Connection {
    Result<Connection, str> open(str host, u16 port) {
        return switch (self) {
            Connection::Disconnected => connectTo(host, port),
            else => return Error::Err { .error = "already connecting or connected" },
        }
    }

    void disconnect() {
        switch (self) {
            Connection::Connected { fd } => { closeFd(fd); self = Connection::Disconnected; },
            else => { self = Connection::Disconnected; },
        }
    }
}

The value's identity, Disconnected, Connecting, Connected, Error, is its case, and that case's data is attached to it. When Connected you have a file descriptor and nothing else; when Connecting you have a host and port and no descriptor yet. The type stops you reading the descriptor of a connection that is not yet connected, exactly the bug that plagues hand-rolled state machines with a state field and nullable fields.

  3. ComprehensionExplain the three rules of a Coral switch (exhaustive, reachable, deliberate fallthrough) to someone who has only used C's switch. What does each rule protect against?
  4. ImplementationDefine variant Temperature { Celsius { f64 deg; }, Fahrenheit { f64 deg; }, Kelvin { f64 deg; } } and write toCelsius(Temperature) f64 with an exhaustive switch. Then add a Rankine case and list every place the compiler complains.
  5. ImplementationAdd a Div case to the interpreter in 13.8. Decide what division by zero should do, return a Result<f64, str>, or abort with @assertOut, and justify your choice in two sentences.
  6. PatternsWrite classify(Vec<i32>) str returning "empty", "single", "sorted-ascending", "sorted-descending", or "unsorted", using at least one guard and as few ifs as you can manage.
  7. FallthroughWrite a switch where two cases genuinely need to share a tail of code, first with an else, then with #[[fallthrough]]. Which reads better, and when is each appropriate? What does the compiler say if you forget the attribute?
