Live Examples: Arrays, Strings, and Two Pointers

Two Fingers on the Same List

This chapter is about two pointers: keep two positions in the data and move them by a rule. Most problems beginners solve with a double loop do not need one; the nested loop rediscovers information the other loop already has. The brute force costs n²; the two-pointer version costs n.

The art is choosing which pointer moves. That rule is always justified by a property of the data: sortedness, a target, or symmetry. Each problem below names the property that licenses the move, because that is the part that transfers.

The other theme is str versus String, and read-only versus overwritable. Reversing in place needs a mutable buffer, a String; a str is a borrowed, read-only view (Chapter 17). Several problems also use a write pointer and a read pointer in one array: one index writes the survivors, the other scans. Filtering, deduplicating, and compacting are all the same three lines.

Reverse a String In Place

The problem

Reverse a mutable string's characters without allocating a second string.

Picture this

Two people at opposite ends of a row walk toward the center, swapping as they meet. When they pass, every box has changed places exactly once.

Brute force

Walk the original backwards and append each character. Correct and linear, but it needs a second buffer; "in place" forbids that.

The better approach

Pointers at both ends swap the characters they point at, then step inward, stopping when they meet or cross. Every position is touched once; the only extra storage is one character.

The implementation

coral
import(lib) std::text::string { String };
import(lib) std::io::ios { println };

void reverseString(String* s) {
    isize i = 0;
    isize j = (isize)s->len - 1;
    while (i < j) {
        u8 t = s->at((usize)i);
        s->atApply((usize)i, s->at((usize)j));
        s->atApply((usize)j, t);
        i++;
        j--;
    }
}

void main() {
    String text = String::from("hello");
    reverseString(&text);
    println("{}", text.asView());
}

Two details: types and mutability. The counters are isize because j-- must reach zero and stop; unsigned would wrap and crash. The operations go through String, whose at and atApply give read and overwrite access. A str would not compile, the type system telling you reversing needs ownership of the bytes, not a view.

The cost

Time is linear: about half the length, constant work per iteration. Space is constant. The build-a-new-string approach is also linear in time but linear in extra space; here two pointers buy a space improvement, not a time one.

Edge cases and a variation

Empty and single-character strings exit immediately. Even lengths end with j < i; odd lengths end with i == j on the middle character, which has nothing to swap. Variation: reverse the words in a sentence ("the sky is blue" becomes "blue is sky the") by reversing the whole string, then each word back, with no second buffer.

Valid Palindrome

The problem

Decide whether a string reads the same forwards and backwards, considering only letters and digits and ignoring case. "A man, a plan, a canal: Panama" is a palindrome.

Picture this

Two readers at each end ignore punctuation and case. If their characters differ, the answer is no; if they meet having agreed on everything, yes.

Brute force

Strip everything but letters and digits, lowercase, then compare the copy to its reverse. Two passes and an allocation, and the cleaning step is error-prone.

The better approach

Pointers from each end advance past non-alphanumeric characters and compare survivors with case folded. No copy. This is 24.1's skeleton with two changes: skip non-alphanumeric before comparing, and compare lowercase instead of swapping.

The implementation

coral
import(lib) std::text::ascii { isAsciiAlnum, toAsciiLower };
import(lib) std::io::ios { println };

bool isPalindrome(str s) {
    isize i = 0;
    isize j = (isize)s.len - 1;
    while (i < j) {
        while (i < j && !isAsciiAlnum(s.at((usize)i))) i++;
        while (i < j && !isAsciiAlnum(s.at((usize)j))) j--;
        if (toAsciiLower(s.at((usize)i)) != toAsciiLower(s.at((usize)j))) {
            return false;
        }
        i++;
        j--;
    }
    return true;
}

The inner while loops advance past characters that should not be compared. Their i < j condition stops an all-punctuation string from running the pointers past each other and off the end, a detail first attempts miss on inputs like "...".

The cost

Time is linear: each pointer moves inward and never retreats, so total movement is bounded by the length despite nested loops. Space is constant. Loops nested in the source need not mean nested cost if the inner loop draws from a shared budget.

Edge cases and a variation

Empty and single-character strings are palindromes. "0P" is not, since 0 and P differ after folding. This code compares bytes, so it is correct for ASCII and wrong for accented letters or emoji, whose UTF-8 encodings are multiple bytes; Chapter 17 explains the nextCodepoint fix. Variation: allow deleting at most one character, solved by trying both skips when the pointers disagree.

Two Sum in a Sorted Array

The problem

Given a sorted array and a target, find the two positions whose values add to the target. Assume exactly one pair exists.

Picture this

Two people at the ends of a sorted number line want their numbers to sum to a target. Too small: move the left person rightward to a bigger number. Too big: move the right person leftward. Each move is the unique sensible one.

Brute force

For each i, scan every j after it: about n² / 2 additions. It ignores that the array is sorted, the tell that the intended solution uses ordering.

The better approach

Two pointers, left and right. If the sum equals the target, return the positions. If too small, advance i; no pair with the smallest value can reach the target otherwise. If too big, move j leftward. Each step eliminates one candidate, so the pointers cross after at most n steps.

The implementation

coral
import(lib) std::vec { Vec };
import(lib) std::io::ios { println };

Vec<i32> twoSumSorted(const Vec<i32>* v, i32 target) {
    Vec<i32> out = Vec<i32>::new();
    isize i = 0;
    isize j = (isize)v->count() - 1;
    while (i < j) {
        i64 sum = (i64)v->at((usize)i) + (i64)v->at((usize)j);
        if (sum == (i64)target) {
            out.push((i32)i);
            out.push((i32)j);
            return out;
        }
        if (sum < (i64)target) {
            i++;
        } else {
            j--;
        }
    }
    return out;
}

The sum is widened to i64: two large i32s can overflow and wrap, making the "too small" branch fire when the true sum was "too big." The cheapest guard against a silent bug.

The cost

Time is linear: each iteration moves one pointer inward, at most n iterations. Space is constant. Sortedness decides which pointer must move, so each comparison rules out a whole row or column of the pair table.

Edge cases and a variation

Fewer than two elements returns an empty vector. Equal values are fine: [3, 3] with target 6 returns 0 and 1, since i < j. Variation: on an unsorted array, two pointers fail because no ordering justifies a move. Use a hash map from value to position and ask whether each number's complement was already seen, Chapter 26's opening problem. Sorted permits two pointers; unsorted demands hashing.

Remove Duplicates from a Sorted Array

The problem

Given a sorted array, remove duplicates in place so each value appears once, and return the new length. Elements beyond it do not matter.

Picture this

Items arrive sorted, so copies sit adjacent. A write hand points at the next slot; a read eye scans. When the eye finds an item different from the last kept, place it and advance the hand.

The better approach

Two indices, read and write, both starting after the first element. The write index advances only when the current element differs from the last written. Sortedness means the last written value is the right comparison: no set, no memory. At the end, the write index is the distinct count.

The implementation

coral
import(lib) std::vec { Vec };
import(lib) std::io::ios { println };

usize removeDuplicates(Vec<i32>* v) {
    if (v->count() == 0) return 0;
    usize k = 1;
    for (usize i = 1; i < v->count(); i++) {
        if (v->at(i) != v->at(k - 1)) {
            v->set(k, v->at(i));
            k++;
        }
    }
    while (v->count() > k) {
        v->pop();
    }
    return k;
}

Compare against v->at(k - 1), the last value kept, not v->at(i - 1). They usually match, but after a write they diverge; the last kept value is the correct invariant. The final pop loop trims the vector, since a Vec has no truncate.

The cost

Time is linear: one pass, one comparison and occasionally one write per element. Space is constant, no allocation, the point of an in-place problem. The pop loop is linear in duplicates removed, so the total stays linear.

Edge cases and a variation

Empty returns zero; one element returns one; all-equal leaves one and returns one. Variation: allow each value at most twice, keeping the second but not the third. The write-pointer pattern is unchanged; only the predicate changes, comparing against the value two positions back in the kept prefix. These are all the same skeleton with a different predicate.

Move Zeroes

The problem

Move every zero to the end in place, keeping the relative order of nonzero elements.

Picture this

A worker slides empty boxes to the far end without disturbing the full ones. A hand marks the next open slot on the left; each full box goes under it and the hand moves on. The tail is then filled with zeroes.

Brute force

Collect the nonzero elements in order into a second list, then write them back followed by zeroes. Linear, but allocates a second array.

The better approach

The write-pointer pattern with the predicate "is nonzero." Whenever a value is nonzero, write it at the write index and advance. At the end, the first k positions hold the nonzero values in order, and the rest get zero.

The implementation

coral
import(lib) std::vec { Vec };
import(lib) std::io::ios { println };

void moveZeroes(Vec<i32>* v) {
    usize k = 0;
    for (usize i = 0; i < v->count(); i++) {
        if (v->at(i) != 0) {
            v->set(k, v->at(i));
            k++;
        }
    }
    for (usize i = k; i < v->count(); i++) {
        v->set(i, 0);
    }
}

Order is preserved because the read pointer visits nonzero elements in order and the write pointer accepts them in that order. If order did not matter, a swap-based version would touch each element once.

The cost

Time is linear: one full scan plus a tail scan, at most twice the length. Space is constant. The second pass is the price of overwrite-and-fill rather than swap; the swap-based alternative avoids it when order does not matter.

Edge cases and a variation

No zeroes: one pass and an empty tail. All zeroes: k stays zero and the whole array is zeroed. Variation: move a given value to the end, or evens to the front, same skeleton with a different if. Sorting by parity while preserving within-group order needs two passes, since the write pointer must first count the odds.

Merge Two Sorted Arrays

The problem

Merge two sorted arrays into the first, which has room at its end for both. Do not allocate.

Picture this

Two sorted stacks and empty space at the right. Work backwards: place the larger of the two largest remaining cards in the rightmost empty slot. The biggest card must end up at the far right, so this is safe.

Brute force

Copy both into a fresh buffer and sort: O((m+n) log(m+n)), allocates, and squanders the sortedness.

The better approach

Three pointers walking backwards: i at the last real element of the first array, j at the last of the second, k at the last combined slot. Write the larger of a[i] and b[j] at k and step that source back. When the second array is exhausted, the first array's leftovers are already in place.

The implementation

coral
import(lib) std::vec { Vec };
import(lib) std::io::ios { println };

void merge(Vec<i32>* a, i32 m, const Vec<i32>* b, i32 n) {
    isize i = (isize)m - 1;
    isize j = (isize)n - 1;
    isize k = (isize)(m + n) - 1;
    while (j >= 0) {
        if (i >= 0 && a->at((usize)i) > b->at((usize)j)) {
            a->set((usize)k, a->at((usize)i));
            i--;
        } else {
            a->set((usize)k, b->at((usize)j));
            j--;
        }
        k--;
    }
}

The loop condition is j >= 0, not both, deliberately: once the second array is exhausted, the first array's leftovers already sit in order at the front. The i >= 0 guard protects the a[i] read when the first array runs out first.

The cost

Time is linear: each iteration places one element, and there are m + n. Space is constant. Working backwards avoids allocation because the destination is larger and consumes the source from the same end it fills from.

Edge cases and a variation

An empty second array leaves the first untouched; an empty first copies the second into place. Variation: merge k sorted arrays. Pairwise merging is O(k · N · log k), but a min-heap yielding the smallest front does it in O(N log k), which is Chapter 16's PriorityQueue.

Sort Colors (the Dutch National Flag)

The problem

Given an array of only 0s, 1s, and 2s, sort it in place in one pass.

Picture this

Three regions, like the flag's bands. A left hand owns the 0s, a right hand owns the 2s, and a middle eye scans. A 0 goes left and grows that region; a 2 goes right; a 1 is already home. The regions grow toward each other until they meet.

Brute force

Count the 0s, 1s, and 2s in one pass, then overwrite. Two passes, linear, fine, but not the required single pass and it does not generalize to many distinct values.

The better approach

Three pointers: low is the boundary after the region of 0s, high is the boundary before the region of 2s, and mid is the scanning eye moving between them. At each step, look at v[mid]:

  • if it is 0, swap it with the element at low, advance both low and mid;
  • if it is 1, it is in its final region, advance only mid;
  • if it is 2, swap it with the element at high, retreat high, and do not advance mid.

After swapping with high, the element now at mid came from the unprocessed right end and has never been examined, so we must look at it again rather than step over it.

The implementation

coral
import(lib) std::vec { Vec };
import(lib) std::io::ios { println };

void swapAt(Vec<i32>* v, usize a, usize b) {
    i32 t = v->at(a);
    v->set(a, v->at(b));
    v->set(b, t);
}

void sortColors(Vec<i32>* v) {
    isize low = 0;
    isize mid = 0;
    isize high = (isize)v->count() - 1;
    while (mid <= high) {
        i32 x = v->at((usize)mid);
        if (x == 0) {
            swapAt(v, (usize)low, (usize)mid);
            low++;
            mid++;
        } else if (x == 1) {
            mid++;
        } else {
            swapAt(v, (usize)mid, (usize)high);
            high--;
        }
    }
}

mid <= high, with high inclusive, marks the unprocessed region. When mid passes high, nothing is left; every iteration shrinks that region or advances mid into known territory, so one pass suffices.

The cost

Time is linear, and a true single pass: each element is examined a constant number of times and swapped at most once. Space is constant, three indices. Counting sort takes two passes; the single-pass property is what makes the pattern reusable.

Edge cases and a variation

One distinct value leaves the pointers in place. All 0s advance low and mid together. Avoid advancing mid after a 2-swap; test [2, 0, 1]. Variation: four or five values does not extend trivially, since boundary pointers grow awkwardly; beyond a handful, use counting sort.

Container With Most Water

The problem

Given wall heights along a line, choose two walls forming the container that holds the most water: distance times the shorter wall's height.

Picture this

On a skyline, water is limited by the shorter building and width by the distance. Moving inward always reduces width, so the shorter wall is the one worth abandoning.

Brute force

Check every pair, compute the area, keep the maximum: n² / 2 constant-work computations.

The better approach

Start with pointers at the ends, the widest container. Compute its area, then move the pointer at the shorter wall inward. Moving the taller one only shrinks the width with the same cap, so it cannot improve. Repeat until the pointers meet.

The implementation

coral
import(lib) std::vec { Vec };
import(lib) std::io::ios { println };

i64 maxArea(const Vec<i32>* h) {
    isize i = 0;
    isize j = (isize)h->count() - 1;
    i64 best = 0;
    while (i < j) {
        i64 width = (i64)(j - i);
        i64 hi = (i64)h->at((usize)i);
        i64 hj = (i64)h->at((usize)j);
        i64 shorter = hi < hj ? hi : hj;
        i64 area = width * shorter;
        if (area > best) best = area;
        if (hi < hj) {
            i++;
        } else {
            j--;
        }
    }
    return best;
}

All arithmetic is i64, so the largest possible area cannot overflow. The move rule is the proof: discarding the shorter wall discards every container that could have used it, and none could beat the best already recorded. That is why greed is safe.

The cost

Time is linear: each iteration moves one pointer inward, so n - 1 iterations. Space is constant. The move rule discards a whole family of candidate pairs without checking them.

Edge cases and a variation

Fewer than two walls yields zero, which the loop returns. Equal heights allow moving either pointer. Variation: return the indices of the best walls, updating them whenever the best improves. The next problem, "trapping rain water," looks similar but asks for total water across all gaps, with a subtly different rule.

Trapping Rain Water

The problem

Given wall heights, compute how much rainwater is trapped after a storm.

Picture this

Water collects in every dip up to the lower of its two bounding walls. At each point, the water level is the smaller of the tallest wall to its left and the tallest to its right; the water above is that level minus the point's height.

Brute force

For each position, scan left and right for the maxima; the water is the smaller maximum minus the height, when positive. O(n²), the most direct translation of the definition.

The better approach

Two pointers with running left and right maxima. If the left maximum is shorter than the right, the water level at the left pointer is governed entirely by the left maximum, since the right side has a wall at least as tall. Add leftMax - height[i] and move inward; mirror on the right. One pass.

The implementation

coral
import(lib) std::vec { Vec };
import(lib) std::io::ios { println };

i64 trap(const Vec<i32>* h) {
    if (h->count() == 0) return 0;
    isize i = 0;
    isize j = (isize)h->count() - 1;
    i64 leftMax = 0;
    i64 rightMax = 0;
    i64 water = 0;
    while (i < j) {
        i64 hi = (i64)h->at((usize)i);
        i64 hj = (i64)h->at((usize)j);
        if (hi < hj) {
            if (hi >= leftMax) {
                leftMax = hi;
            } else {
                water += leftMax - hi;
            }
            i++;
        } else {
            if (hj >= rightMax) {
                rightMax = hj;
            } else {
                water += rightMax - hj;
            }
            j--;
        }
    }
    return water;
}

hi < hj processes the side with the smaller wall, whose water level is settled because the other side offers a taller wall. The hi >= leftMax branch distinguishes a new high wall (traps nothing) from a valley (traps the difference).

The cost

Time is linear: pointers move inward and each position is processed once. Space is constant, two maxima and an accumulator. Computing the maxima on the fly replaces rescanning, the same "carry it forward" idea as Chapter 24's running sum.

Edge cases and a variation

Empty or single-position input traps nothing. A monotonic skyline traps nothing, since every position either sets a new maximum or contributes zero. The move rule here differs from 24.8: there we move the shorter wall to optimize one container; here we move the side with the smaller maximum to accumulate everywhere. Compare them side by side.

Longest Common Prefix

The problem

Find the longest prefix shared by a list of strings. For ["flower", "flow", "flight"] it is "fl"; for ["dog", "racecar", "car"], the empty string.

Picture this

Lay the words in a column and read down each character position. As long as every word agrees on a column, it belongs to the prefix; the first disagreement ends it. Compare one column at a time, not whole words.

Brute force

Take every pair, find their shared prefix, and shorten a running answer. O(n · L) in the worst case, but it rebuilds strings and compares words unnecessarily; two words agreeing with the first already agree with each other.

The better approach

Use the first word as the candidate prefix and shrink it. For each later word, compare character by character and cut the candidate to the matching length. Stop once it is empty. This vertical scan makes at most one pass over each word up to the current prefix.

The implementation

coral
import(lib) std::vec { Vec };
import(lib) std::io::ios { println };

str longestCommonPrefix(const Vec<str>* words) {
    if (words->count() == 0) return str::empty();
    str first = words->at(0);
    usize limit = first.len;
    for (usize i = 1; i < words->count(); i++) {
        str w = words->at(i);
        usize j = 0;
        while (j < limit && j < w.len && w.at(j) == first.at(j)) {
            j++;
        }
        limit = j;
        if (limit == 0) break;
    }
    return first.slice(0, limit);
}

limit is the only state and only shrinks, so the worst-case work is the shortest word's length times the word count, usually far less. The returned str is a view into the first word's bytes, so nothing is allocated; the caller's list must outlive it, which the borrowed type makes explicit.

The cost

Time is O(n · L) in the worst case, where L is the answer length: each word is scanned only to the current prefix, which shrinks. Space is constant, one index and one length, since the answer is a view. Binary search halves comparisons but pays off only for enormous strings.

Edge cases and a variation

An empty list returns the empty string; a single-word list returns that word. If any word is empty, the shared prefix is empty and the loop stops. This compares bytes, correct for prefix purposes but splitting multibyte characters; Chapter 17's codepoint decoding is the fix. Variation: longest common suffix, scanning from the back with limit counting from the end. Same skeleton, reversed direction.

Rotate an Array by k

The problem

Rotate an array right by k places, in place: [1, 2, 3, 4, 5, 6, 7] becomes [5, 6, 7, 1, 2, 3, 4].

Picture this

Move the bottom k cards to the top. Instead of rotating one card at a time, flip the whole deck, then flip each of the two piles back. Reversal plus reversal gives rotation and touches every card twice.

Brute force

Rotate one position at a time, k times. Each rotation moves every element, so the cost is O(n · k), and for k near n that is quadratic. It is simple and it is in place, and it is the baseline.

The better approach

Three reversals. Reverse the whole array, reverse the first k elements, then reverse the remaining n - k. After the first reversal the two groups are in the wrong internal order but on the correct sides; the second and third reversals restore the order inside each group. Every element is moved a constant number of times, so the work is linear. Reduce k modulo n first so that k = n (or 0) is handled without special cases.

The implementation

coral
import(lib) std::vec { Vec };
import(lib) std::io::ios { println };

void reverseRange(Vec<i32>* v, usize lo, usize hi) {
    while (lo < hi) {
        i32 t = v->at(lo);
        v->set(lo, v->at(hi));
        v->set(hi, t);
        lo++;
        hi--;
    }
}

void rotateRight(Vec<i32>* v, usize k) {
    usize n = v->count();
    if (n == 0) return;
    k = k % n;
    if (k == 0) return;
    reverseRange(v, 0, n - 1);
    reverseRange(v, 0, k - 1);
    reverseRange(v, k, n - 1);
}

The two guards at the top are not decoration. An empty array would make n - 1 wrap around when it is unsigned, and k % n would divide by zero; returning early avoids both. The k % n line also means a rotation by more than the length behaves correctly instead of reading out of bounds. reverseRange is the same two-pointer swap as 24.1, generalized to an arbitrary interval.

The cost

Time is linear: three passes, each moving each element at most once, so at most six writes per element. Space is constant, two indices and one temporary value. Compare the one-step-at-a-time version, which is also in place but k times slower.

Edge cases and a variation

An empty array and a k that is a multiple of n both do nothing. A single-element array is left alone even for large k. The variation: rotate to the left by k is the same routine applied to n - k, or equivalently the three reversals done with the two parts swapped. A second, genuinely different method is the "juggling" algorithm, which moves elements in cycles and does exactly n writes for the whole rotation rather than touching some elements twice. It is trickier to get right and worth reading once, if only to see the constant-factor trade.

String Compression (Run-Length Encoding)

The problem

Compress a string by replacing each run of repeated characters with the character followed by the run length, omitting the length when it is one. So "aabccc" becomes "a2bc3" and "abc" stays "abc".

Picture this

Walk the string and keep one finger at the start of the current run and another moving forward while the characters match. When the second finger finds a different character, the run is over: write the character, write the count if there was more than one, and move the start finger up to where the second one stopped. Every character is visited once by the moving finger and the runs are written in order.

Brute force

There is no meaningfully different slow version; a run-length compressor is naturally linear. The naive implementation instead rebuilds substrings and counts duplicates with an inner search for each position, which is quadratic and obscures the two-pointer skeleton that is the whole idea.

The better approach

One pass with a start index and a scan index. For each run, push the character into the output String and append the count when the run is longer than one. The only piece of machinery that is not obvious is turning a multi-digit count into its decimal characters, because Coral's formatting helpers are not the right tool for building a string one byte at a time.

The implementation

coral
import(lib) std::vec { Vec };
import(lib) std::text::string { String };
import(lib) std::io::ios { println };

void pushUint(String* out, usize n) {
    if (n == 0) {
        out->pushChar(48);
        return;
    }
    Vec<u8> digits = Vec<u8>::new();
    while (n > 0) {
        digits.push((u8)(48 + (n % 10)));
        n = n / 10;
    }
    isize i = (isize)digits.count() - 1;
    while (i >= 0) {
        out->pushChar(digits.at((usize)i));
        i--;
    }
}

String compress(str s) {
    String out = String::new();
    usize i = 0;
    while (i < s.len) {
        u8 c = s.at(i);
        usize j = i;
        while (j < s.len && s.at(j) == c) {
            j++;
        }
        out.pushChar(c);
        usize run = j - i;
        if (run > 1) pushUint(&out, run);
        i = j;
    }
    return out;
}

pushUint peels the decimal digits into a vector in reverse, then emits them in order; it is the integer-reversal idea of 23.3, used here to write a number rather than read one. The byte constant 48 is '0', and adding a digit value to it produces the character. The compression loop itself is only six lines, which is the payoff for extracting the number-writing helper.

The cost

Time is linear in the input length: the scan index advances across each character once, and the digit work for the counts adds only a logarithm per run. Space is proportional to the length of the output, which for a highly repetitive string is far smaller than the input but in the worst case (no repeats) is the same size.

Edge cases and a variation

The empty string produces an empty string; the loop never runs. A string with no repeats returns a copy of itself with every count omitted. A run longer than nine exercises pushUint's multi-digit path, which a '0' + run shortcut would get wrong. The variation from the interview version: if the compressed result is not shorter than the original, return the original. Keep the original str and the built String, then compare their lengths before returning. A second variation: decode, or decompress, a run-length string, which is the same two-pointer walk in reverse and is a good check that you understand the format you invented.

Product of Array Except Self

The problem

Given an array, produce a second array where position i holds the product of every element except v[i]. Do it without using division, so zeros and negative numbers cause no trouble, and in linear time.

Picture this

The product of everything except position i is (the product of everything to its left) times (the product of everything to its right). So make two sweeps. On the way right, record at each position the product of everything before it. On the way back, multiply that by the product of everything after it, accumulated as you go. Neither sweep needs to know the whole array's product, so division never enters.

Brute force

For each position, loop over every other position and multiply. That is O(n²) and it recomputes the same partial products from every starting point.

The better approach

Two passes and one output array. The first pass fills out[i] with the running prefix product before i. The second pass walks backward maintaining a running suffix product and multiplies it into out[i]. The output array itself is the only extra storage, so beyond the answer the space is constant. Widen the accumulator to i64: a product of many i32 values overflows a 32-bit integer almost immediately.

The implementation

coral
import(lib) std::vec { Vec };
import(lib) std::io::ios { println };

Vec<i64> productExceptSelf(const Vec<i32>* v) {
    usize n = v->count();
    Vec<i64> out = Vec<i64>::withCap(n);
    for (usize i = 0; i < n; i++) out.push(1);

    i64 prefix = 1;
    for (usize i = 0; i < n; i++) {
        out.set(i, prefix);
        prefix = prefix * (i64)v->at(i);
    }

    i64 suffix = 1;
    isize i = (isize)n - 1;
    while (i >= 0) {
        out.set((usize)i, out.at((usize)i) * suffix);
        suffix = suffix * (i64)v->at((usize)i);
        i--;
    }
    return out;
}

The forward pass stores the product of the elements strictly before i; the backward pass multiplies in the product strictly after i. They never overlap, which is why no division is needed and zeros are harmless: a zero simply makes every prefix after it zero and every suffix before it zero, and each answer ends up correct. The signed isize backward index is the same choice as 24.1, so the i-- can reach zero and stop without wrapping.

The cost

Time is linear: two passes, constant work per element. Space is linear only because the answer is the same length as the input; the working state is a single running product. This is the discipline that distinguishes "extra space" from "output space," and the problem is usually asked precisely to test that distinction.

Edge cases and a variation

An empty array returns an empty result. A single element returns a single one, since the product of nothing is one. A zero in the input is handled by the two-pass structure, unlike a divide-by-total approach which would break. The variation: allow division and solve it in one pass by taking the total product and dividing each element out, then handle zeros as a special case. It is shorter and it fails on the cases that matter, which is exactly the lesson of the problem.

3Sum

The problem

Given an array of integers, return every unique triple of values (not positions) that sums to zero. So from [-1, 0, 1, 2, -1, -4] the answer is [-1, -1, 2] and [-1, 0, 1].

Picture this

Sort the array first, so equal values sit together and we can skip repeats by hand. Fix the smallest value of the triple with an outer loop, then find the other two with the converging two-pointer walk of 24.3. Because the array is sorted, when the sum is too small we can move the left pointer right and know we have not missed a candidate, exactly as in the sorted two-sum.

Brute force

Three nested loops over all triples, checking each sum and then deduplicating the results. That is O(n³) and the deduplication is a fiddly second problem on top. It ignores the sortedness that a single sort would provide.

The better approach

Sort once, then fix the first element with an outer index i. For the remaining window (i, end], run the two-pointer two-sum against the target -v[i]. The sortedness licenses the pointer movement, and it also makes duplicate-skipping trivial: skip an i equal to the previous one, and after recording a triple, skip equal values on both ends of the window.

The implementation

coral
import(lib) std::vec { Vec };
import(lib) std::collections::sort { sortI32 };
import(lib) std::io::ios { println };

Vec<Vec<i32>> threeSum(Vec<i32>* nums) {
    sortI32(nums);
    Vec<Vec<i32>> out = Vec<Vec<i32>>::new();
    usize n = nums->count();
    if (n < 3) return out;

    for (usize i = 0; i + 2 < n; i++) {
        if (i > 0 && nums->at(i) == nums->at(i - 1)) continue;
        isize lo = (isize)i + 1;
        isize hi = (isize)n - 1;
        while (lo < hi) {
            i64 sum = (i64)nums->at((usize)lo)
                    + (i64)nums->at((usize)hi)
                    + (i64)nums->at(i);
            if (sum == 0) {
                Vec<i32> triple = Vec<i32>::new();
                triple.push(nums->at(i));
                triple.push(nums->at((usize)lo));
                triple.push(nums->at((usize)hi));
                out.push(triple);
                lo++;
                hi--;
                while (lo < hi && nums->at((usize)lo) == nums->at((usize)lo - 1)) lo++;
                while (lo < hi && nums->at((usize)hi) == nums->at((usize)hi + 1)) hi--;
            } else if (sum < 0) {
                lo++;
            } else {
                hi--;
            }
        }
    }
    return out;
}

There are three places duplicates could sneak in, and each is guarded once. The outer skip handles repeated first elements; the two inner skips handle repeated second and third values after a hit. The sum is widened to i64 so three large i32s cannot overflow and flip the sign of the comparison. The returned triples come out in the order the sorted array produces, one per distinct value combination.

The cost

Sorting is O(n log n), and the outer loop with its inner two-pointer walk adds O(n²), so the total is O(n²), which beats the cubic brute force by a full factor of n. Space is constant beyond the sort and the output. The sorting cost is negligible next to the quadratic scan for any interesting input.

Edge cases and a variation

Fewer than three elements returns nothing. All-zero input yields exactly one triple [0, 0, 0], because the two inner skips collapse the repeats. The variation: k-sum generalizes this by fixing the first k - 2 elements with nested loops and running the two-pointer walk for the last two; for fixed k that is O(n^{k-1}), and the pattern of "sort, fix, then converge" is identical all the way down. The 3Sum closest variant replaces the equality test with a running best distance, and is often the easier interview version because it does not need the duplicate guards.

Find All Anagrams in a String

The problem

Given a string s and a shorter pattern p, return the starting indices of every substring of s that is an anagram of p. So for s = "cbaebabacd" and p = "abc", the answer is 0 and 6 ("cba" and "bac").

Picture this

An anagram is fully described by how many of each letter it contains, not by their order. So slide a window exactly as wide as p across s, and at each position ask whether the window's letter counts match p's. When the window moves one step, only two letters change: one enters on the right and one leaves on the left. Update two counts instead of recounting the whole window.

Brute force

At every start position, copy the next m characters, sort them, and compare to the sorted pattern. There are n - m + 1 windows, and each costs O(m log m), for O(n · m log m) overall. It re-sorts windows that differ from their neighbours by a single letter.

The better approach

A fixed-size sliding window with two frequency arrays, one for the pattern and one for the current window, each of 26 counters. Seed both from the first window, then compare. On each step, add the entering character to the window count and subtract the leaving one. Since the alphabet is tiny and fixed, comparing the two arrays is a constant 26 operations, and the total is linear in n.

The implementation

coral
import(lib) std::vec { Vec };
import(lib) std::io::ios { println };

Vec<i32> findAnagrams(str s, str p) {
    Vec<i32> out = Vec<i32>::new();
    usize n = s.len;
    usize m = p.len;
    if (m == 0 || n < m) return out;

    Vec<i32> need = Vec<i32>::withCap(26);
    Vec<i32> win = Vec<i32>::withCap(26);
    for (usize i = 0; i < 26; i++) {
        need.push(0);
        win.push(0);
    }

    for (usize i = 0; i < m; i++) {
        usize k = (usize)((i32)p.at(i) - 97);
        need.set(k, need.at(k) + 1);
    }

    for (usize i = 0; i < n; i++) {
        usize enter = (usize)((i32)s.at(i) - 97);
        win.set(enter, win.at(enter) + 1);
        if (i >= m) {
            usize gone = (usize)((i32)s.at(i - m) - 97);
            win.set(gone, win.at(gone) - 1);
        }
        if (i >= m - 1) {
            bool same = true;
            for (usize c = 0; c < 26; c++) {
                if (win.at(c) != need.at(c)) {
                    same = false;
                    break;
                }
            }
            if (same) out.push((i32)(i - m + 1));
        }
    }
    return out;
}

The subtraction (i32)s.at(i) - 97 maps 'a' to index 0 and 'z' to 25; the constant 97 is 'a'. The two conditions delimit the window: remove the leaving character only once i >= m, and test only once the window is full at i >= m - 1. The comparison loop breaks on the first mismatch, which makes the common (non-matching) case cheap.

The cost

Time is O(26 · n), which is O(n) because the alphabet size is a constant. Space is constant: two arrays of 26 integers, regardless of how long s and p are. This is the fixed-alphabet cousin of 25.6's sliding window, where the map grows with the number of distinct characters instead.

Edge cases and a variation

An empty pattern is not a valid anagram and returns no indices; a pattern longer than s cannot fit and also returns none. This assumes lowercase a to z; an uppercase letter or a space would compute an out-of-range index and must be rejected first, or the counters must be widened to cover the full byte range. The variation: at most k distinct characters, or "find all anagrams of any permutation of a list of patterns," both loosen the fixed-size comparison into a count of how many letters are satisfied and how many distinct letters are present. Fixed size becomes sliding maximum, but the two-array diffing idea stays.
