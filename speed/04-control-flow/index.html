Control Flow

More Than Just if and for

Control flow decides what runs, how many times, and in what order. It is where a program's shape is decided, and where a language that fights you is most visible.

Coral's control flow is C's, plus structure: a ranged for over containers, defer for guaranteed cleanup, and a pattern-matching switch with guards and exhaustiveness checking. Every condition is a real bool, and control flow is explicit.

This chapter covers conditionals, loops, the @iter protocol, break and continue, and defer. Error handling with Result and Option has its own chapter, because it is control flow built on types rather than keywords.

The if Statement

The if statement evaluates a bool condition and runs a block when it is true.

if (condition)
{
    // runs when condition is true
}

An if is a fork: the program asks a yes/no question and takes one path. The question is the bool expression in parentheses.

The condition must be a bool, enforced by the type checker. There is no truthiness: test an integer with a comparison and a pointer against null.

The else clause runs when the condition is false.

if (condition)
{
    // runs when condition is true
}
else
{
    // runs when condition is false
}

An else if chain tests conditions in order and runs the first true block. Each condition is evaluated only if the earlier ones were false.

if (a)
{
    // a
}
else if (b)
{
    // b
}
else if (c)
{
    // c
}
else
{
    // none
}

The library is built from such chains: character classification, the UTF-8 encoder deciding byte counts, and parsers deciding how to interpret each character.

Clamping a value into a range is a three-way decision:

u64 clamp(u64 v, u64 lo, u64 hi)
{
    if (v < lo) return lo;
    if (v > hi) return hi;
    return v;
}

Each test is one condition and one outcome, all visible. If chains suit independent ranges; a switch suits a fixed set of exact values.

Mapping a score to a letter grade is the same shape, because the boundaries are ranges:

char gradeFor(u64 score)
{
    if (score >= 90) return 'A';
    if (score >= 80) return 'B';
    if (score >= 70) return 'C';
    if (score >= 60) return 'D';
    return 'F';
}

Each test clips a range off the top, and the thresholds are naturally ordered. A switch over every possible score would be absurd.

The Shape of Conditions

A condition can be any bool expression, and short-circuit operators make compound conditions safe:

if (self.ptr != null && self.ptr[0] == 'x') ...

if (i < self.len && self.ptr[i] == c) ...

The first example checks the pointer before reading through it; the second checks the bound before subscripting. Both rely on short-circuiting.

Guard clauses dispose of special cases early, leaving the main path:

u64 lengthOf(str s)
{
    if (s.ptr == null) return 0;   // the empty case, disposed immediately
    return s.len;
}

A validator built from guard clauses reads as its own list of requirements:

bool validConfig(Config* c)
{
    if (c->port == 0) return false;              // no port: nothing to serve
    if (c->backlog > MAX_BACKLOG) return false;  // an unreasonable backlog
    return c->workers > 0 && c->workers <= MAX_WORKERS;
}

The last line combines two bounds, and the function reads as the config's rules, each stated where it fails.

For independent or complex tests, use if chains; for choosing among a fixed set of values of one expression, use a switch.

The switch Statement

The switch dispatches on one expression. Each arm pairs a pattern with the code to run when it matches:

switch (value)
{
    0    => { /* value is 0 */ },
    1    => { /* value is 1 */ },
    else => { /* value is something else */ }
}

Think of a vending machine: the expression's value is the code, each arm is a shelf, and else catches anything unmatched.

The expression is evaluated once and matched against patterns in order; the first match runs. Arms are comma-separated, and an arm's body is an expression or a brace block. There is no break and no accidental fallthrough. The else arm is the catch-all and must come last. To fall through, say so with the #[[fallthrough]] attribute; silence is never fallthrough.

Patterns are constants compared against the switch value: integer constants, character constants, or enum variants, checked for type compatibility. Enum variants are especially useful: a switch over an enum names each meaning instead of a raw number.

enum LogLevel { Debug, Info, Warn, Error, Fatal }

char levelChar(LogLevel level)
{
    switch (level)
    {
        LogLevel::Debug => { return 'D'; },
        LogLevel::Info  => { return 'I'; },
        LogLevel::Warn  => { return 'W'; },
        LogLevel::Error => { return 'E'; },
        LogLevel::Fatal => { return 'F'; }
    }
    return '?';
}

A variant is named by type and variant with a double colon, as in LogLevel::Debug. Every variant has an arm, so the switch is total and the compiler can confirm it.

No forgotten break: an arm never runs the next arm's body unless asked. This removes a persistent C bug source and makes a switch a clean table of decisions.

Block arms allow several actions per arm, run in order:

void handle(LogLevel level, str msg)
{
    switch (level)
    {
        LogLevel::Error => {
            logToStderr(msg);
            raiseAlert();          // both lines run, then the arm ends
        },
        LogLevel::Fatal => {
            logToStderr(msg);
            halt(1);
        },
        else => {
            logToStdout(msg);
        }
    }
}

Each arm is a small statement sequence that ends with its block, so neither branch runs for another arm and no break is missing.

Switches as Expressions

A switch is also an expression: it produces the matched arm's value, so it can be assigned, returned, or passed.

u64 size = switch (kind)
{
    Size::Small  => { 16; },
    Size::Large  => { 1024; },
    else         => { 0; }
};

Expression and statement forms are the same construct. An expression body contributes a value; a brace block runs statements and contributes nothing. A switch used as a value must give every arm an expression body. Choose the expression form for values and the statement form for actions.

The level-character decision as an expression:

char levelChar(LogLevel level)
{
    return switch (level)
    {
        LogLevel::Debug  => { 'D'; },
        LogLevel::Info   => { 'I'; },
        LogLevel::Warn   => { 'W'; },
        LogLevel::Error  => { 'E'; },
        LogLevel::Fatal  => { 'F'; }
    };
}

The expression switch supports pattern matching over the language's types: enum variants, literal constants, and an else for the rest. Because the compiler knows the types, it can check coverage: over an enum, every variant must be handled or an else must cover the remainder. This is exhaustiveness checking.

The switch is where Coral's type system meets its C-shaped syntax: patterns come from types, else names the catch-all, and the result composes as an expression.

Pattern Matching

Patterns go beyond single constants and are built from the type system.

A literal pattern matches one value. An enum pattern matches one variant, as in LogLevel::Warn. else matches anything. A barred list matches any of several patterns: 1 | 2. A variant pattern destructures and binds fields, as in Some { value } => ... A guard refines a pattern: pat if cond => runs only when both hold.

Two beginner habits to correct: the catch-all is else, not _, which is not a wildcard, so write else => for "anything left." Alternatives use bars: the bars in 1 | 2 are the "or" that lists them, so 1 | 2 => ... is correct and 1, 2 => ... is not.

Patterns say in one line what an if chain takes several. A switch over specific values plus a general case reads as a table:

u64 byteCount(u64 x)
{
    return switch (x)
    {
        0      => { 0; },          // 0 bytes: representable in zero
        1 | 2  => { 1; },          // one byte can hold 0..255
        3 | 4  => { 2; },          // two bytes hold up to 65535
        else   => { 8; }           // anything larger: use the full width
    };
}

The barred list matches either value and else catches the rest, turning a long if chain into a handful of lines.

Patterns are most powerful with variants. A switch over a variant with an arm per case plus else turns the value into a decision, reaching fields directly:

u64 unwrapOrZero(Option<u64> o)
{
    return switch (o)
    {
        Some { value }  => { value; },
        else            => { 0; }
    };
}

Coverage checking makes this safe: handle every variant and the switch is total; use else and you state that the rest is handled together.

A guard combines a pattern with a condition, letting one arm cover many values and still discriminate:

char classify(i32 temp)
{
    return switch (temp)
    {
        t if t < 0   => { 'C'; },
        t if t == 0  => { 'Z'; },
        else         => { 'H'; }
    };
}

Coral's patterns are the type system made executable: the patterns are the types, and the switch selects behavior by type.

Expression-Oriented Conditionals

Coral's conditionals come in statement and expression forms.

Statement forms, if and switch-as-statement, run blocks of actions. Use them when the decision controls what the program does.

Expression forms, the ternary and switch-as-expression, produce values. Use them when the decision controls which value is assigned, returned, or passed.

u64 size = switch (kind)
{
    Size::Small  => { 16; },
    Size::Large  => { 1024; },
    else         => { 0; }
};

There is a third expression form: the if expression.

u64 size = if (kind == Size::Small) { 16 } else { 1024 };

The if expression spells the ternary with keywords. Its condition must be a real bool, both branches must have compatible types, and it produces the chosen branch's value. A null-literal branch adopts the other branch's type. It is exactly as safe and type-checked as the operator, just a longer spelling. The library favors ?: inline but supports both.

A decision that produces a value can be written inline without a separate statement. Switch statement and switch expression are one construct; choose by whether you are choosing actions or values.

The while Loop

The while loop evaluates a bool condition, runs a block when true, and repeats until false.

while (condition)
{
    // body
}

A while loop means "keep doing this while the condition stays true." The condition is checked before every trip, so the body may run zero times. It is the loop of "until something happens."

Because the condition is checked first, a false condition means the body never runs. The body may execute zero times.

The library uses while for search and traversal: scanning until found or exhausted, walking linked nodes, cache eviction, and bit counting.

A compound condition is the standard bounded scan. String trimming runs while input remains and the current character is a space:

while (i < self.len && (self.ptr[i] == ' ' || self.ptr[i] == '\t')) i++;

Short-circuiting makes this safe: the character test runs only while the index is in bounds. The loop stops when input is exhausted or a non-space is found.

Repeated division extracts digits:

u64 digits = 0;
u64 n = value;
while (n > 0)
{
    n /= 10;
    digits++;
}

The loop runs once per decimal digit and terminates because each division moves n toward zero. The condition moves a value toward a bound.

The pointer walk traverses a chain, and the linked list is its home:

Node* cur = head;
while (cur != null)
{
    process(cur->value);
    cur = cur->next;
}

The condition is the chain's termination: cur is null exactly at the end, and each step moves one node deeper. Nothing counts or indexes; the loop's shape is the list's shape.

The for Loop

The for loop is the counted loop, folding initialization, condition, and step into one statement:

for (u64 i = 0; i < n; i++)
{
    // body
}

The initialization runs once; the condition is checked before each iteration; the step runs after each iteration. It is equivalent to the while form with the pieces in order.

u64 i = 0;
while (i < n)
{
    // body
    i++;
}

The for loop makes counted iteration one readable statement. The library uses it constantly for walking collection lengths: copy, zero, search, count bits, initialize tables.

Summing a fixed array shows the canonical shape:

u64 total = 0;
for (u64 i = 0; i < n; i++)
    total += values[i];

The header is flexible: the initialization can be omitted, the condition can be any bool expression, and the step can be any expression. An unbounded loop is written with the loop keyword, not with an empty for header.

Reversing a buffer in place walks two indices toward the middle:

void reverse(u64* data, u64 n)
{
    for (u64 i = 0, j = n - 1; i < j; i++, j--)
    {
        u64 tmp = data[i];
        data[i] = data[j];
        data[j] = tmp;
    }
}

The counters move in opposite directions, i < j is the meeting test, and the step moves both. The whole walk is visible in the header.

Nested for loops compose ranges into grids, such as a multiplication table:

for (u64 r = 1; r <= 10; r++)
{
    for (u64 c = 1; c <= 10; c++)
        print("{}\t", r * c);
    print("\n");     // one row per outer iteration
}

The inner loop completes a row before the outer advances, so the printed shape is the grid. Nested for is the shape of two-dimensional work.

The loop Keyword

Coral also provides loop for an infinite loop, making the intent explicit without an empty header.

loop
{
    // runs until a break or return exits
}

loop says "repeat until something inside stops me." With no condition, only a break or a return exits, which suits servers and menus.

The loop construct states intent: this loop is unbounded and exits inside the body. The loop keyword says this is an infinite loop, and it is the only spelling Coral provides for one.

Infinite loops are for servers, event loops, interactive sessions, and parsers scanning to a terminator. The body always contains the exit. A minimal REPL:

loop
{
    str line = readLine();
    if (line.len == 0) break;   // end of input: exit
    run(line);
}

The Ranged for Loop

The ranged for iterates directly over a container, with no index variable:

for (var x : container)
{
    // body, with x bound to each element
}

Read it as "for each x in the container." You manage no counter, start index, or stopping bound; the loop hands you one element at a time.

An explicit element type may replace var:

for (i32 value : ints) { ... }

A var loop can also bind several names at once, when at() returns a tuple:

for (var index, value : pairs) { ... }

Each name takes one tuple element, in order, so the tuple must have exactly one element per binding. This works only with var; the explicit element type takes a tuple type instead, as in for (struct(i32, i32) pair : pairs).

Iteration is index based: the compiler reads the container's count once, then asks for each element by index in increasing order. The loop variable is a copy, so assigning to it does not change the collection; use an index loop with atPtr() to mutate in place.

A ranged for can walk a slice by giving a half-open index range, in two equivalent spellings:

for (var x : values(start, end))       { ... }
for (var x : values.range(start, end)) { ... }

Both call range(start, end). end is exclusive, the bounds are clamped to the element count, and end < start runs the body zero times, so an overshooting range is safe. A single-bound form such as values(end) is not supported.

The ranged for is defined over the @iter protocol, so any type that opts in can be iterated.

The @iter Protocol

The ranged for works through the @iter protocol, a small set of methods a type provides. Arrays and slices are iterable already; a type opts in with an @iter extend block.

The protocol is index based and has three methods:

method                                     required            contract
usize count()                              always              number of elements
T     at(usize i)                          always              element at 0 <= i < count()
IterRange range(usize start, usize end)    bounded form only   the clamped interval [start, end)

A plain loop calls count() once, then at(i) for each index. A bounded loop also calls range(start, end), which clamps the interval and returns it as an IterRange. range() is O(1) for the built-in collections. When a var loop binds several names, at() returns the tuple those names destructure, one element per name.

@iter is structural: no runtime object, vtable, or methods of its own, so the methods live in the extend block. A type you write joins the same way:

import(lib) std::collections::range { IterRange };

pub extend CountTo : @iter
{
    usize count() { return self.n; }
    i32   at(usize i) { return (i32)i; }
    IterRange range(usize start, usize end) { ... }
}

IterRange, with fields start and end, is declared in std::collections::range. It is deliberately non-generic, so importing a collection does not instantiate a container such as Vec<T> merely because range() is declared.

The collections that opt in:

type              order               at() cost   notes
Vec<T>            insertion           O(1)
Arr<T, N>         index               O(1)
Deque<T>          front to back       O(1)
RingBuf<T>        oldest to newest    O(1)
Queue<T>          front to back       O(1)        does not consume
LinkedList<T>     head to tail        O(i)        prefer each() for large lists
PriorityQueue<T>  heap-array order    O(1)        not sorted; pop() consumes by priority
Bitset            bit index           O(1)        yields bool

Map, HashMap, Set, Tree, Trie, Cache, and UnorderedMap do not implement @iter, having no single canonical indexed order; walk them with each().

A type marked @iter must provide count() and at(); the compiler names the missing method and the protocol if one is absent. A bounded loop also needs range(). Using the ranged for on a type that is neither an array, a slice, nor @iter is an error. Multi-binding is var-only and needs at() to return a tuple with one element per binding; iteration yields copies.

Iteration and Invalidation

One discipline follows from the index-based protocol: do not change a container's element count while a ranged for is walking it.

The loop samples count() once, then indexes up to that count. If the body shrinks the container, a later at(i) reaches past the new end and trips the bounds assertion. If the body grows it, the extra elements are never visited, because the loop still runs against the old count; growth can also move the storage and dangle a pointer from atPtr().

// Wrong: the loop sampled the count before the body ran, and
// pushing may reallocate the storage underneath it.
for (var x : v)
{
    if (x == FLAG) v.push(x * 2);   // do not mutate while iterating
}

Read while iterating, write after. Collect what you need into a separate container, then change the original once the loop finishes:

// Correct: collect the interesting indices, then act after iteration.
Vec<u64> found;
for (var x : v)
    if (x == FLAG) found.push(indexOf(x));
for (var idx : found)
    v.removeAt(idx);

break and continue

Two statements control loop bodies: break and continue.

break exits the innermost loop immediately, continuing after it. It ends infinite loops and stops searches early.

continue skips the rest of the current iteration. In a for loop it jumps to the step, so the counter advances; in a while loop it jumps to the condition.

Adding only even numbers and stopping at a sentinel:

u64 total = 0;
for (var n : values)
{
    if (n == SENTINEL) break; // stop the whole loop
    if (n % 2 != 0) continue; // skip just this one
    total += n;
}

break does not escape nested loops at once; it exits only the loop it is written in. To stop both, carry a flag into the outer condition or return from the function.

The library uses both pervasively: parsers break at terminators, searches break on a match, and loops continue past unprocessed input such as blank lines or separators.

Summing only nonblank lines shows continue:

u64 totalChars = 0;
while (read next line into line)
{
    if (line.len == 0) continue;   // skip nothing lines entirely
    totalChars += line.len;
}

break and continue affect only the innermost loop. A break in a nested loop exits the inner loop; a continue advances it. To affect the outer loop, use a flag checked by its condition or a return.

A two-dimensional search shows the nesting:

bool found = false;
u64 foundRow = 0;
u64 foundCol = 0;
for (u64 r = 0; r < rows && !found; r++)
{
    for (u64 c = 0; c < cols; c++)
    {
        if (grid[r][c] == target)
        {
            foundRow = r;
            foundCol = c;
            found = true;
            break;
        }
    }
}

The inner break exits the column loop, and the outer condition tests found, so the whole search stops. A flag in the outer condition is the standard way to stop nested loops together.

Early Return

return exits the current function immediately. Early return handles a special case as soon as it is known.

u64 find(char c)
{
    for (u64 i = 0; i < self.len; i++)
        if (self.ptr[i] == c) return i;
    return self.len;
}

This returns the first match's index or a sentinel. The return exits the whole function at the match. Without it, the function would need a flag, a break, and a post-loop check.

Early return is the dominant style in the library: searches return on finding, validators return false on a violation, and parsers return on a decision. What remains after the checks is the main path.

A validator shows each check disposing of one failure:

bool isValidName(str s)
{
    if (s.len == 0) return false;
    if (!isAlpha(s.ptr[0])) return false;
    for (u64 i = 1; i < s.len; i++)
        if (!isAlnum(s.ptr[i]) && s.ptr[i] != '_') return false;
    return true;
}

Keep exit points legible. Several returns are fine when each is where the decision is made and its reason is visible.

defer

defer registers code to run when the current scope exits, however it is left: by reaching the end, a return, or a break.

void processFile()
{
    File* f = openFile("data.txt");
    defer closeFile(f);
    // body; closeFile(f) runs when this function exits
}

defer means "when this block is done, however it ends, run this line last." Cleanup sits next to acquisition instead of at a distant exit.

closeFile(f) runs at the end of the function whether the body completes, returns early, or breaks. This is Coral's guaranteed cleanup without a finally clause or exceptions.

Cleanup written next to acquisition lets a reader see the resource's whole lifetime. New early returns and branches also run the deferred call, so the guarantee scales with complexity.

Multiple defers run in reverse order of registration: A, then B, then C, executes C, B, A. The most recently acquired resource, the innermost, is released first.

Reverse order tears down layered resources correctly. A connection holds a socket, and the socket's buffer must be freed before the socket closes, which must happen before the connection is released:

Connection* conn = connect(host, port);
defer releaseConnection(conn);
Socket* sock = conn.socket;
defer closeSocket(sock);
u8* buf = socketBuffer(sock);
defer freeBuffer(buf);

The innermost acquisition is deferred last and released first; the outermost is deferred first and released last. Each resource is released before the resource it depends on.

In an exception language, cleanup relies on unwinding. Coral has no exceptions, so defer provides the same guarantee through the language: deterministic, ordered, on every scope exit, with no hidden runtime.

@assert

@assert is Coral's built-in runtime check. It takes a bool; if false, the program fails with a diagnostic pointing at the assertion.

@assert(i < self.len);
@assert(self.ptr != null);
@assert(factor != 0);

The library uses @assert at method tops and inside algorithms to state what must be true: vector indices are in range, a priority queue is not popped empty, a divisor is nonzero. A violation is caught with a precise location.

@assert catches programmer error, not expected conditions. A failed assertion is a bug, caught at the violation with line and condition. Expected conditions from user input or external events use Result. Assert what must be true; handle what might not be.

An @assert is a statement about the code, not the world:

u64 divide(u64 a, u64 b)
{
    @assert(b != 0);       // "this is a bug if b is zero", the caller broke the rules
    return a / b;
}

Result<u64, i32> parseRatio(str s)
{
    if (s.len == 0) return Result<u64, i32>::Err { .error = -1 };   // "this might happen", handle it, don't assert
    // ...
}

Choosing the Right Loop

The four loop forms match different shapes of work.

Use while when the number of iterations is unknown and the loop runs until a condition becomes false: searching, scanning, traversing.

Use for over a counted range of indices: fixed iteration counts, buffer walks, table building.

Use the ranged for over container elements when the elements matter more than the indices.

Use loop when the loop is unbounded and its exit is decided inside the body: servers, event loops, parsers scanning to a terminator.

The library demonstrates the range: indexed scans use for, boundary scans and node chains use while, parsers use loop, and argument packs use the ranged for.

Loop Fusion and Unrolling

Two compiler concepts explain what happens to your loops.

Loop unrolling duplicates the body so several iterations run per pass, cutting branch and counter overhead and exposing more independent work. The compiler decides from loop size and trip count. Write simple, regular loops it can unroll safely.

Loop fusion merges two adjacent loops over the same range into one, cutting iterations and improving locality. The compiler fuses loops with provably equal ranges and independent bodies. Regularity helps.

Neither is written by the programmer. They are compiler transformations, mentioned so optimization does not confuse. Write the loop that says what you mean, and let the compiler make it fast.

Error Handling as Control Flow

Error handling is control flow, and Coral treats it as such. Coral has no exceptions; this section describes the machinery it uses instead: Result, Option, assertion, termination, and deferred cleanup.

Exceptions are hidden control flow: a failure can unwind arbitrarily far, bypassing functions and reporting far from its cause. Coral has no exceptions, no stack unwinding, and no try, catch, throw, or finally.

In place of exceptions, Coral has values. A fallible function returns a value that says so, visible in its signature, checked by the type system, and handled where the caller can act.

The Result Type

Result is Coral's primary error-handling type: a generic variant holding either a success value or an error value.

A success returns Ok carrying the value; a failure returns Err carrying the error. Result<T, E> names both types.

Result<File, i32> openFile(str path);

This signature says the function may succeed with a File or fail with an i32. The failure mode is visible before the implementation, which is why Result replaces exceptions.

Think of a Result as a sealed envelope containing either your answer or a note explaining what went wrong. You must open it and check before using the answer, which forces you to confront failure.

Result has cases built with Result<T, E>::Ok { .value = v } and Result<T, E>::Err { .error = e }, plus inspection, extraction, and chaining methods. It is deliberately small.

The error type is a type parameter, so you choose the representation: an integer code, a string, or an enum. The library uses Result where a fallible operation must distinguish success and carry a value.

The caller must handle both states before touching the value:

Result<Config, ParseError> result = loadConfig(path);
if (result.isOk())
{
    Config cfg = result.unwrap();
    applyConfig(cfg);
}
else
{
    reportError(result.unwrapErr());
}

The branch is the error handling, visible in the text. There is no hidden path; the caller sees both branches and decides what each does.

The Option Type

Option is Coral's type for a value that may be absent: the safe replacement for null pointers and sentinels.

Some carries a value; None carries nothing. Option<T> holds either a T or nothing.

An Option is a box that might be empty. You must check before using it, which prevents the classic "nothing was in the box" crash.

Option<u64> findByte(char c);

This says the function may return a byte's index or nothing. The absence is typed: no sentinel, no -1, no null pointer. The caller must handle both states.

Result and Option differ: Result says the operation had an error and did not complete; Option says it completed and there is no value. A file lookup fails with Result; a search finding nothing returns Option.

Option has cases Some and None, inspection methods isSome and isNone, extraction methods, and chaining methods. A hash map's lookup returns an Option because the key may not exist.

Inspection and Extraction

The first thing a caller does is ask the state.

Result provides isOk and isErr; Option provides isSome and isNone. These are the primary branching points.

Extraction gets the value out. unwrap returns the value when present and asserts the precondition otherwise: unwrapping an err or none is a programming error. unwrapOr is safe extraction, returning the value or a default. unwrapErr extracts the error, asserting the result is an error.

File f = r.unwrapOr(defaultFile);

Choose unwrap when presence is guaranteed by surrounding logic, making the guarantee checked; choose unwrapOr when absence has a reasonable default, making the default explicit.

The okPtr and ptr Accessors

For performance, Result and Option provide pointer accessors that avoid copying.

Result's okPtr returns a pointer to the success value or null; errPtr returns the error or null. Option provides ptr and constPtr: a pointer to the value or null.

These let callers work through a pointer when the value is large or must be modified in place. Check the state; a non-null accessor means present. They bridge typed absence and C's pointer world.

Chaining: map, andThen, orElse

Chaining methods transform a Result or Option without manual branching, composing operations on one value.

andThen chains a fallible operation: it takes a function from the value to a new Result. On Ok the function is applied; on Err it is skipped and the error carries through.

r.andThen(nextStep);

orElse handles the error path: it takes a function from the error to a new Result. On Err it is applied; on Ok the value carries through.

map methods transform the contained value. Result has mapOk and mapErr; Option has map. They change the value while leaving the state alone.

Chains compose. A sequence of fallible steps is a chain of andThen calls, read top to bottom. An error short-circuits the remaining steps, so the happy path is linear and failure is handled where recovery makes sense.

Each step takes the previous outcome and replaces it with its own.

A full pipeline: loading a user record opens a file, reads a line, and parses an id, each fallible, chained into one Result:

Result<User, Err> loadUser(str path)
{
    Result<File, Err> f = openFile(path);
    Result<str, Err> line = f.mapOk(readLine);
    Result<u64, Err> id = line.mapOk(parseId);
    Result<User, Err> user = id.mapOk(makeUser);
    return user;
}

Each step transforms the value while the error state carries through untouched. If openFile fails, the remaining mapOk calls skip their functions and the error survives. The happy path is linear; failure is the same chain short-circuited.

Abort and Termination

So far failure has been recoverable. Coral also has an explicit model for unrecoverable failure.

@assert is the primary abort mechanism: a failure terminates with a diagnostic at the site. unwrap uses it internally. This path is for programming errors, violated invariants, and conditions that must never occur.

exit terminates the program with an exit code immediately, without returning. The process module provides it, and startup uses the same path. There is no unwinding; the program stops where exit is called.

The types draw the boundary. Result and Option are recoverable: the function returned and the caller can handle both states. Assertion failure and exit are unrecoverable: the program stops. A fallible function returns Result; an impossible condition is asserted.

Resource Cleanup with Errors

Result plus defer handles the hardest part of error handling: releasing resources when an error path exits.

defer registers cleanup that runs on every scope exit, including error exits. Acquire, defer release, then operate, with every error path returning through the cleanup:

Result<Buffer, i32> readFile()
{
    File f = fileOpen("data.txt", "r");
    defer fileClose(f);
    Buffer b = Buffer::new();
    defer b.dispose();
    // ... read into b, returning Result<Buffer, i32>::Ok { .value = b } or an error
    // on every path, f is closed and b is disposed
}

The defers guarantee the file closes and the buffer is disposed however the function exits, success or error. Cleanup is written at acquisition, replacing finally and exception unwinding.

Smart pointers extend this to ownership: they release the object when destroyed, and shared pointers release when the last owner is gone. An error path that exits a scope releases owned objects without an explicit defer.

Coral has no destructors forced on every type. It has defer for explicit cleanup, @drop for types opting into automatic release (Chapter 11), and smart pointers for ownership-based release. All are explicit and visible, with no hidden unwinding.

Reasoning About Loops: Invariants

A loop is trustworthy when its invariant holds: a property true when the loop begins, after every iteration, and therefore when it ends. The invariant is the loop's promise.

Sorting cards in your hand, the left part is always sorted as you go. That maintained property is the invariant.

A running sum:

u64 total = 0;
for (u64 i = 0; i < n; i++)
    total += data[i];

The invariant is that total holds the sum of elements before i. It holds initially (zero is the empty sum), each iteration adds the next element and re-establishes it with i advanced, and at the end it says total is the sum of all n elements.

The invariant guides shape. A loop maintaining two facts is written to keep both true. Write the invariant first, then the loop; the body preserves it and the condition terminates.

Binary search is easy to get wrong and needs its invariant stated:

// invariant: target, if present, lies in [lo, hi)
while (lo < hi)
{
    u64 mid = lo + (hi - lo) / 2;
    if (arr[mid] < target) lo = mid + 1;
    else hi = mid;
}

The invariant, "the answer is in [lo, hi)," is preserved by every branch: raising lo past a smaller element keeps hi above it, and lowering hi keeps lo below. At the end lo equals hi, pinning the answer. The interval shrinks, so it terminates.

The running maximum is trivial to trust with its invariant:

u64 best = data[0];
for (u64 i = 1; i < n; i++)
    if (data[i] > best) best = data[i];
// invariant: best is the largest of data[0..i)

Initially best is data[0], the largest of a one-element range. Each step keeps the larger, so the invariant holds with i advanced, and at the end best is the largest of the array.

An invariant distinguishes a loop from a guessing game: trust comes from a stated, preserved property, not from seeming to work. Read every loop against its invariant.

A Worked Example: The Command Dispatcher

The pattern-matching switch is at its best where types dispatch. A command dispatcher takes an enum and selects an action, and the compiler checks coverage.

pub enum Command
{
    Move,
    Attack,
    Heal,
    Quit
}

void runCommand(Command cmd)
{
    switch (cmd)
    {
        Command::Move =>
        {
            moveUnit(currentUnit);
        },
        Command::Attack =>
        {
            attackTarget(currentTarget);
        },
        Command::Heal =>
        {
            healUnit(currentUnit);
        },
        Command::Quit =>
        {
            gameOver = true;
        }
    }
}

The switch matches the variants directly, and the compiler verifies every variant is handled with no missing arm and no accidental fallthrough. Adding a command makes the compiler demand its arm, so the dispatcher is total by construction.

An if chain would compare against each variant and lose the totality guarantee. The switch matches the type's structure, and exhaustiveness is its reward.

A Worked Example: The Tokenizer

The tokenizer shows the features together: it scans a buffer, classifies each token by its first character, skips separators, and stops at end of input. The outer loop is infinite with an internal exit, classification is an if chain, and cleanup is defer.

pub enum TokKind
{
    Ident,
    Number,
    Symbol
}

pub struct Token
{
    TokKind kind;
    u64 start;
    u64 len;
}

void tokenize(str src, void(Token) emit)
{
    u64 i = 0;
    loop
    {
        while (i < src.len && isSpace(src[i])) i++;
        if (i >= src.len) break;
        u64 start = i;
        u8 c = src[i];
        if (isDigit(c))
        {
            while (i < src.len && isDigit(src[i])) i++;
            emit(Token { .kind = TokKind::Number, .start = start, .len = i - start });
        }
        else if (isAlpha(c))
        {
            while (i < src.len && isAlpha(src[i])) i++;
            emit(Token { .kind = TokKind::Ident, .start = start, .len = i - start });
        }
        else
        {
            i++;
            emit(Token { .kind = TokKind::Symbol, .start = start, .len = 1 });
        }
    }
}

The outer loop is unbounded and breaks at end of input. The inner while loops consume whole tokens, and the if chain classifies by first character. The invariant is that everything before i is tokenized, preserved by advancing i past each emitted token.

A Worked Example: Parsing with Defer and Result

The cleanest error-model demonstration acquires a resource, does fallible work, and must release on every path. Pairing defer with Result makes the function straight-line with all exits covered.

Result<u64, ParseErr> sumFile(str path)
{
    File f = fileOpen(path, "r");
    defer fileClose(f);
    u64 total = 0;
    u8 buf[256];
    i64 n = 0;
    while ((n = fileRead(f, buf, 256)) > 0)
    {
        for (i64 i = 0; i < n; i++)
        {
            if (!isDigit(buf[i]))
            {
                if (buf[i] == ',') continue;
                return Result<u64, ParseErr>::Err { .error = ParseErr::InvalidChar };
            }
            total = total * 10 + (u64)(buf[i] - '0');
        }
    }
    return Result<u64, ParseErr>::Ok { .value = total };
}

The file is opened and protected by defer, so every return, error or success, runs fileClose. Digits accumulate, commas are skipped, and any other character returns an error immediately. The Result type states the function's purpose, and cleanup is written at acquisition.

Control Flow and the Machine

Control flow maps directly to hardware, which explains its shape. A processor understands only sequential instructions and branch instructions.

An if compiles to a comparison and a conditional branch. A while compiles to a comparison, a body, and a branch back. A for is a while with initialization, condition, and step arranged. A switch compiles to comparisons or a jump table. Every construct is comparisons and branches.

This is why the C model is right for Coral: conditions are comparisons, loops are branches, and the cost of a decision is a comparison and a jump, visible in the source.

The additions follow the same rule. The ranged for compiles to an index loop over the container; the pattern switch to comparisons or a jump table; defer to cleanup at each exit point. Each is convenience in the source and plain branches in the machine.

Control Flow and the Type-First Principle

Coral's control flow is C's, so a C programmer reads it correctly on sight. The additions, ranged for, defer, and the pattern switch, modernize without breaking the model.

The additions are type-driven. The ranged for is defined by the @iter protocol, the switch by patterns built from types with exhaustiveness checking, and conditions by bool. Control flow is the type system directing execution.

Chapter 4 Summary

Coral's control flow is C's, with conditions that must be real bools and no truthiness.

if, else if, and else form ordered decision chains, and short-circuit conditions make bound and pointer tests safe inline.

The switch dispatches on one value with arms pairing a pattern and a body, using else as the catch-all and having no accidental fallthrough.

The switch is also an expression: it pairs patterns with results using a fat arrow, uses else as the wildcard, produces a value, and checks exhaustiveness over enums.

Pattern matching is built from types: literals, constants, enum variants, barred lists, ranges, variant destructuring, guards, and else. A value's type selects its behavior.

while tests before each iteration and may run zero times. for combines initialization, condition, and step. loop is the explicit infinite loop.

The ranged for iterates over container elements directly, defined by the @iter protocol each container implements.

The loop samples the element count once, so modifying a container's structure during iteration reads past the end or skips elements. Collect results while iterating; modify after.

break exits the innermost loop; continue skips to the next iteration. Both act only on the nearest loop.

Early return exits a function when a decision is made, keeping the happy path straight-line.

defer registers cleanup to run when a scope exits, regardless of how, in reverse order. It is Coral's resource-cleanup guarantee without exceptions.

@assert is the runtime tripwire for what must be true, distinct from Result for what might not be.

Choose the loop by the work's shape: while for scans, for for counted ranges, ranged for for elements, and loop for unbounded servers and parsers.

Loop unrolling and fusion are compiler transformations on regular loops: write clear loops and the compiler makes them fast.

A loop invariant is true before the loop, after every iteration, and at the end. Reading a loop against its invariant is how it is known correct.

The switch dispatches for enums: the compiler checks that every variant is handled, so adding a variant forces its arm.

The tokenizer and parser show the constructs together: loop with an internal break, while loops for tokens, the if chain for classification, and defer paired with Result so every error path releases resources.

Control flow maps to the machine as comparisons and branches, which is why Coral uses the C model: source constructs compile to straight-line code and jumps with nothing hidden.

Control flow in Coral is the type system directing execution, and the modern additions are type-driven without breaking the C model.
