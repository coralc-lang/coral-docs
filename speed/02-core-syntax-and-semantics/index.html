Speed Edition · Chapter 2

Core Syntax and Semantics

The "Hello World" Trap

Most books open with Hello World, teaching a ritual rather than a mental model. This chapter starts beneath the surface: source characters, comments, identifiers, primitive types, and declaration and assignment rules. Hello World waits until it can be understood in full.

The Source File

A Coral source file is UTF-8 text. UTF-8 is ASCII-compatible and represents every Unicode character in one to four bytes, so code, comments, and string literals can use any writing system with no configuration, magic comment, or BOM. Pinning the encoding removes a category of cross-machine bugs.

Source files use .crl. A build file, itself Coral source, is build.coral at the project root. Those are the only filename conventions.

Comments

Coral has three comment forms. Two are inherited from C; the third is for documentation.

A line comment begins with two slashes and runs to the end of the line:

coral
// This entire line is a comment.
u64 x = 42; // Everything after the slashes is a comment too.

A comment is a note for people that the compiler ignores completely.

A block comment begins with slash-asterisk and ends with asterisk-slash, and can span lines:

coral
/* This comment
   spans multiple
   lines. */

Block comments do not nest; the first closing sequence ends the comment. So commenting out code that already contains a block comment can resurrect part of it. Use line comments for single lines and block comments for explanations; if you must disable a chunk, delete it.

A documentation comment begins with three slashes and attaches to the declaration that follows:

coral
/// Adds two numbers and returns their sum.
pub i32 add(i32 a, i32 b) { return a + b; }

The editor and language server show /// comments on hover and in completion, the way clangd and rust-analyzer do. The compiler still ignores them; four or more slashes are an ordinary comment.

coral
// pub i32 add(i32 a, i32 b) { // Error, the code on this line is invalid
    return a + b;
}

Comments carry no meaning to the compiler. Use them to explain why, not what. The standard library comments sparingly, to explain intent.

coral
// No alignment here: the allocator returns max-aligned blocks already.
// Reusing this buffer would over-align and waste bytes on every call.

Identifiers

An identifier names a variable, function, struct, variant, module, type parameter, or field. It begins with a letter or underscore, followed by letters, underscores, or digits. Names are case sensitive, so value, Value, and VALUE are distinct. Unicode letters are allowed. A name cannot start with a digit.

The compiler cares only about the character rules; naming conventions are for humans.

Coral's naming conventions are C-style.

Types, including structs and enums, use PascalCase: String, Duration, Timespec, LogLevel. A type name is a noun or noun phrase.

Functions and variables use camelCase: push, reserve, countCodepoints, formatInt. Functions are verbs; variables are short, meaningful nouns such as len, cap, count.

Constants use UPPER_CASE with underscores: INT64_MIN, U64_MAX, CLOCK_MONOTONIC. This makes them visually distinct from variables.

Type parameters use a single uppercase letter: T for the primary type, U for a secondary, N for a compile-time value. This is convention, not enforcement, but the standard library follows it.

An instance method's receiver is named self and is implicit: it is available in the body but never written in the parameter list. A static method has no self.

Reserved Words

A reserved word is an identifier the language has claimed. You cannot use it for your own names. Grouped by role:

Declarations: struct, variant, union, enum, trait, extend, const, var, import, mod, typedef, distinct, pub, extern, static, flag.

Control flow: if, else, while, for, loop, switch, break, continue, return, defer, assert.

Types and values: self, null, true, false, i8, i16, i32, i64, u8, u16, u32, u64, f32, f64, bool, char (for C compatibility).

Compile-time: comptime, asm.

The list is small and each word names a fundamental concept. Meanings are fixed, with no context-sensitive keywords.

Built-ins the compiler knows by name, the @-prefixed calls such as @sizeof, @typeof, and @assert, and the built-in traits @drop and @toStr, are in Appendix B.

Whitespace and Semicolons

Whitespace is insignificant. Spaces, tabs, and newlines separate tokens, and indentation is style. Structure comes from braces, parentheses, and semicolons.

This avoids the fragility of indentation-sensitive languages, where a reformatted file can silently change meaning. Coral's structure is explicit, so reformatting cannot change behavior.

The semicolon terminates statements. Omitting it is a syntax error, and the compiler points at the missing spot.

Forgetting the semicolon is the most common beginner mistake. Think of it as the period ending a sentence.

The cost is writing semicolons; the benefit is that a statement is a statement however it wraps across lines.

Line Continuation

Because whitespace is insignificant and statements end at semicolons, no line-continuation character is needed. Lines are formatting; the semicolon is grammar.

The standard library splits long expressions and calls across lines for readability, with the semicolon only at the true end:

coral
_fprintFloat(fd, value, 10u, true, "%.15g", 4u, 0);

_fprintFloat(fd,
             value,
             10u,
             true,
             buf,
             64u);

You may break a line anywhere between two tokens, and the statement continues to its semicolon. Indent continuations honestly for your readers.

The Primitive Types

The primitive types are the atoms of every Coral program. Each has a fixed, explicit width, and its name is its width.

Integers, signed: i8, i16, i32, i64.

Integers, unsigned: u8, u16, u32, u64.

Floating point: f32, f64.

Booleans: bool.

Characters: char.

And the special type that is not a value: void.

The number in an integer type's name is its bit width. Signed types hold negatives; unsigned types hold zero and positives. More bits give a wider range and use more memory.

There is no arbitrary-precision integer. Fixed widths are a promise to the machine, and exact widths matter when serializing, calling the OS, or loading registers. Need more than 64 bits? Compose it from 64-bit pieces.

The signed range is -2^(width-1) through 2^(width-1)-1; the unsigned range is 0 through 2^width-1. The standard library names these limits:

coral
INT8_MIN = -128
INT8_MAX = 127
INT16_MIN = -32768
INT16_MAX = 32767
INT32_MIN = -2147483648
INT32_MAX = 2147483647
INT64_MIN = -9223372036854775808
INT64_MAX = 9223372036854775807
U8_MAX = 255
U16_MAX = 65535
U32_MAX = 4294967295
U64_MAX = 18446744073709551615

These live in the core module and are the canonical way to refer to limits. Using U32_MAX instead of a literal makes intent visible and avoids typo bugs.

Integer Semantics

Integer arithmetic is modular. Fixed-width operations wrap in two's complement, as the hardware does, with no bignum and no overflow exception. Adding one to the maximum yields zero; subtracting one from zero yields the maximum.

This is not a weakness. It is what the hardware does, and systems code relies on wrapping for counters, hashes, addresses, and bit patterns. Arbitrary precision or overflow errors would change systems code and destroy performance.

coral
u8 v = 255;
v = v + 1;   // v is now 0; the byte wrapped around
u8 w = 0;
w = w - 1;   // w is now 255

A common trap is expecting a warning when a value is too big. Arithmetic on values wraps quietly at run time, with no warning. Only a literal that does not fit its type is caught, and it is a compile-time error, T0010 literal out of range. Choose a wider type up front; u64 is a safe default when unsure.

You must think about range when writing arithmetic. If a value can exceed its type, use a wider type or handle the wrap explicitly. The standard library does this constantly, for example using two 64-bit fields in a duration, or checking before doubling a vector's capacity.

Signedness is part of a type's meaning. Signed types suit values that can go negative: differences and offsets. Unsigned types suit lengths, capacities, sizes, indices, and bytes. Mixing is legal but conversions are explicit, which prevents the C bug where a negative becomes a huge unsigned value.

Bitwise operations treat integers as bit patterns: AND, OR, XOR, complement, left shift, arithmetic right shift, and logical right shift. A signed right shift preserves the sign bit; an unsigned one fills with zeros. The endian and byte-order helpers use shifts and masks, which is integers as bit patterns in its purest form.

Endianness

Endianness is the order of a multi-byte value's bytes in memory. Little endian stores the least significant byte at the lowest address; big endian stores the most significant first. x86 and ARM are little endian; PowerPC and some embedded and networking hardware are big endian.

Data written on one machine may be read on another, and network protocols define byte order. A little-endian machine writing 0x01020304 stores 04 03 02 01; a big-endian reader naively reconstructs 0x04030201, a subtle corruption if that value is a length, checksum, or address.

The core platform module declares the machine's endianness, provides byte-swap functions for 16, 32, and 64 bits, and provides htons, ntohs, htonl, ntohl, htonll, and ntohll for host-to-network conversion.

coral
// Reading a 16-bit port number the network sent us, big-endian:
u16 wirePort = readBE16(stream);
u16 hostPort = htons(wirePort); // htons: host order from network order

The byte-swap functions use only shifts and masks, no conditionals or memory.

Floating-Point Semantics

Coral's f32 and f64 follow IEEE 754. f32 is 32-bit single precision with about 7 significant decimal digits; f64 is 64-bit double precision with about 15 to 17. Floating point offers range and speed, not exactness.

IEEE 754 cannot represent most decimal fractions exactly. One tenth cannot be written exactly in binary, just as one third cannot in decimal. So 0.1 + 0.2 is not exactly 0.3, and comparing it directly fails.

coral
f64 sum = 0.1 + 0.2;
if (sum == 0.3) { /* does not run */ }
if ((sum - 0.3) < 1e-9) { /* runs: they are close enough */ }

Respect the rules: never compare floats for exact equality unless they are provably exact, compare with a tolerance, and never accumulate money in floating point. Repeated operations accumulate rounding error, and mathematically identical formulas can diverge in finite precision. The library's math functions are accurate, but no finite representation is exact.

IEEE 754 defines infinities for overflow and NaN for undefined results such as zero divided by zero. NaN is not equal to anything, including itself. The library names the floating-point limits for the same reason it names integer limits.

Float literals use conventional forms: a fractional part, or an exponent with e and a power of ten.

coral
3.14     // a float literal
1.0e6    // one million, in exponent form
1.0e-9   // one billionth, convenient for tolerances like the one above

Characters

The char type is one Unicode scalar value, stored in 32 bits. That differs from C, where a char is a byte.

In Coral the byte is u8 and the character is char. Unicode assigns each character a code point from U+0000 to U+10FFFF. ASCII characters are code points 0 to 127 and store with the same bit value; other characters use higher code points, held directly in 32 bits.

A char is a code point, with no decode step to read one. To get its bytes for a file or buffer, encode it to UTF-8, producing one to four u8 values. A string is a sequence of bytes; decoding turns bytes into characters, and encoding does the reverse.

Keep three levels distinct: a byte is one u8; a code point is one char and uses one to four UTF-8 bytes; a grapheme cluster is what a human sees as one character and may span several code points. Correct text programs keep these levels straight.

Character Literals

A character literal is one character or escape sequence in single quotes, with type char. It is the Unicode code point directly.

coral
'A'    // the code point for the uppercase letter A
'0'    // the code point for the digit zero
'\n'   // newline
'\t'   // tab
'\0'   // the null code point
' '    // space

One rule trips up everyone: single quotes make a char ('A'), double quotes make a string ("A"). They are different types, and the compiler rejects one where the other belongs.

Escapes are conventional: \n newline, \t tab, \r carriage return, \0 null, plus backslash escapes for the backslash and single quote. \x41 writes a code point in hex. A char literal up to 255 can initialize a u8, as in u8 const newline = '\n';.

The library's classification functions split along the byte/character line. The char family, charIsDigit, charIsAlpha, charIsAlnum, charIsUpper, charIsLower, charIsSpace, charIsControl, charIsPrint, plus charToUpper and charToLower, works on code points. The u8 family, isDigit, isAlpha, isAlnum, isUpper, isLower, isSpace, isPrint, isControl, isHexDigit, toLower, toUpper, works on bytes. Both are ASCII-only range checks, not table walks.

Booleans

bool has exactly two values, true and false. There is no null, undefined, or truthiness. A comparison or logical combination produces a bool.

Some languages treat 1, a non-empty string, or a non-null pointer as true. Coral refuses: only a real bool is a condition, so if (count) is an error and if (count > 0) is correct.

There is no truthiness coercion. A condition must be a bool; test an integer with a comparison and a pointer against null. This eliminates the C bug where a value is mistaken for a condition, especially a slipped assignment.

coral
u8* p = lookup(key);
if (p) { /* error in C, correct-intending but wrong-shaped here */ }
if (p != null) { /* the Coral way: a comparison that is a bool */ }

The logical operators are && for AND, || for OR, and ! for NOT. The binary operators short-circuit, and this is guaranteed by the language: in a && b, b runs only if a is true; in a || b, b runs only if a is false.

coral
if (node != null && node->value == target) { proceed(); }

The pointer is checked first, and only a non-null pointer is touched.

Void

void is the type of nothing, used as the return type of a function that returns no value. A return in a void function carries no expression.

coral
void greet()
{
    println("Hello.");
}

void is not null and not undefined. Null is a value a pointer can hold, meaning no object; there is no object or variable of type void. A void function returns nothing; a pointer may return null.

Coral makes absence first-class: Option represents presence or absence, Result represents success or failure. Null exists only for pointers, and safety machinery prevents dereferencing a null pointer.

Literals

Literals write constant values directly. Coral's forms are C-style and explicit.

Integer literals. Digits alone are decimal. Prefix 0x for hexadecimal, 0b for binary, 0o for octal. A trailing u marks unsigned. The type is inferred from context, magnitude, and suffix.

coral
42        // decimal
0x2A      // hexadecimal: also forty-two
0b101010  // binary: also forty-two
0o52      // octal: also forty-two
0xFF      // a byte with every bit set
10u       // unsigned ten

Float literals. A fractional part or exponent makes a float literal; the type is inferred from context.

Character literals are single characters or escapes in single quotes.

String literals are characters in double quotes. They are UTF-8 byte sequences; the library provides the owning String and borrowing str view. Adjacent literals concatenate.

coral
"hello"
"a long message that continues "
"across two adjacent literals"

Boolean literals are true and false.

The null literal means "no object" for pointer types.

Declarations and Definitions

A declaration introduces a name and gives it a type; a definition also provides storage or a body. In Coral, as in C, the same text usually does both.

A declaration is where you create a named thing: a type, a name, and a starting value.

For a variable, the type comes first, then the name, then an optional initializer:

coral
u64 length = 0;
i32 error = -1;
bool ready = false;
f64 ratio = 0.5;

The type is on the left, so the range and behavior are known before the name. Coral is type-first because the type is the primary fact.

A variable may be declared without an initializer. It is uninitialized, and you must assign it before reading. The standard library does this when filling a struct field by field:

coral
Duration d;
d.sec = seconds;
d.nsec = 0;
return d;

This is the normal pattern for building a struct value. The fields get values in a visible order, and the compiler can check that every field is assigned before the value escapes.

var and Type Inference

The var keyword lets the compiler infer a local variable's type from its initializer.

coral
var x = 42;      // x has the integer type that fits 42
var ratio = 0.5; // ratio is a float
var ok = true;   // ok is a bool

var means "work out the type from the value." The type is fixed: after var x = 42;, x is an integer, and x = "hello"; is an error. var is not "any type."

Inference is a convenience, not a loss of information. The type is still determined at compile time; var only removes the repetition of writing an obvious type twice.

Inference is local and modest: it works for variables, not parameter or return types, and there is no global inference engine. Types stay explicit at every boundary.

The ranged for uses var to infer the element type from the container:

coral
for (var arg : args) print(arg);

The element type follows the container, and nothing redundant is written. (print here comes from import(lib) std::io::ios { print };.)

Mutability

Mutability is explicit. A value that can change is a variable; one that cannot is a constant. The compiler enforces the distinction at the declaration.

A const declaration binds a name to a value that cannot be reassigned for the program or scope. The library's integer limits, clock constants, and endianness flags are const.

coral
const i32 CLOCK_MONOTONIC = 1;
pub const INT32_MAX = 2147483647;

A variable, declared with a type or var, can be reassigned with the single equals sign, as in C.

coral
u64 pos = 0;
pos = pos + 1;

const and var state mutability directly; there is no separate let syntax. A reader knows at once whether a name is fixed, and the compiler enforces it.

In pointer and parameter types, const means the referred-to data is read-only through that reference. A parameter declared const u8* can read bytes but not modify them. The library marks non-modifying inputs const so the signature shows what is read and what is modified.

Scope

Scope is the region where a name is visible. Coral uses C-like block scoping.

Scope is the stretch of code where a name means something. The braces { } are the walls: a name created inside is usable only inside.

Names declared in a block are visible from declaration to the end of that block, and not outside. Inner blocks see outer names; outer blocks do not see inner names. A function body is a block.

coral
{
    u64 inner = 1;     // visible only inside this block
    {
        u64 x = inner; // an inner block can see outer names
    }
}
// inner is not visible here

Loop bodies, if branches, and nested structures each create blocks, and what is declared inside stays inside.

Scope makes locals safe: a variable that cannot be seen cannot be modified, and block boundaries define lifetime. When a block ends, its locals cease to exist and their stack storage is reclaimed.

Shadowing

Shadowing is when an inner declaration has the same name as an outer one. The inner name takes precedence and hides the outer name within its block.

Shadowing is legal and behaves as C programmers expect. The inner variable is a separate entity with its own storage. Assignments inside the block refer to it, and when the block ends the outer variable is visible again, unchanged.

coral
u64 count = 0;
{
    u64 count = total; // a fresh variable, unrelated to the outer one
    process(count);    // uses the inner one
}
// the outer count is still 0 here

If shadowing looks like a bug, remember that the inner name is a completely separate variable. The outer one is hidden until the block ends and is left untouched.

The classic use is a loop counter or intermediate value inside a loop, declared fresh each iteration.

Shadow to create a fresh, specific meaning in a small scope. Shadowing merely to reuse a convenient name over a large region confuses readers: a shadow that lives three lines is a convenience; one that lives three hundred is a lie.

Assignment

Assignment gives a variable a new value. The target is on the left and the new value on the right.

coral
x = 42;
name = "coral";

Do not confuse x = 5, which stores 5, with x == 5, which asks whether x holds 5. Assignment produces no bool, so slipping one into an if is a compile error.

The target must be assignable: a variable, struct field, array element, or location through a pointer. The value's type must match the target's; a mismatch is a compile error. If a conversion is wanted, write an explicit cast.

Compound assignment operators combine an operation with assignment back to the left operand: +=, -=, *=, /=, %=, &=, |=, ^=, <<=, >>=. The statement x += 1 is exactly x = x + 1.

coral
len += 1;   // same as len = len + 1
mask |= 0x80;   // same as mask = mask | 0x80
pos <<= 3;  // same as pos = pos << 3

Increment and decrement have prefix and postfix forms. ++x increments and yields the new value; x++ increments and yields the old value. The distinction matters only when the value is used.

coral
u64 i = 0;
u64 a = ++i; // a is 1, i is 1
u64 b = i++; // b is 1, i is 2

Initialization Requirements

The one initialization rule: a variable must not be read before it has a defined value. Reading an uninitialized variable is undefined behavior. The var declaration and the fill-every-field pattern both define a value before any read.

Two idioms are safe. Declare with an initializer, or declare a struct and fill every field before use (the constructor pattern, section5.22). No field may be read before it is assigned.

coral
Duration d;
d.sec = s;
d.nsec = 0;
return d;

This is safe because the assignments complete before the value is consumed. A struct that escapes with unassigned fields, or a variable read on a path where it was never assigned, is a bug.

Swapping and Multiple Assignment

Coral has no multiple simultaneous assignment and no swapping assignment. Swap with a temporary:

coral
u64 tmp = a;
a = b;
b = tmp;

Coral also has no multi-name binding declaration such as var (x, y) = pair;. Tuples are taken apart by position (.0, .1) or by matching in a switch (Chapter 12). Reassigning two variables at once and swapping without a temporary are likewise not in the grammar. The library provides swap and exchange operations where needed.

The concurrency module provides an atomic exchange, and the library supplies the moves for swapping owned data. A library swap can be written with the exact semantics each type needs; a grammar-stamped version would have to guess about ownership and aliasing.

Where Variables Live

A variable's type and scope determine where its storage lives, making performance and lifetime predictable.

"Where a value lives" is about how long it lasts and who cleans it up.

Stack storage. Local variables live on the stack, which grows and shrinks with calls. A call gets a frame; on return it is reclaimed. Allocation is nearly free, and temporaries and arguments also live there. The stack has a hard limit, and deep recursion can overflow it.

Static storage. Constants and file-scope values live in static storage for the whole program, initialized before it runs. Nothing there needs freeing.

Heap storage. Values that outlive a call, or whose size is unknown until runtime, live on the heap, allocated explicitly through the allocator interface. Vec, String, and Map allocate and free there. Heap allocation is slower, requiring a block search, and is reclaimed only on explicit free or owner destruction.

Register storage. Short-lived values may be kept in registers at the compiler's choice. A register value has no address, so taking its address forces it into memory. Write clearly scoped code and the compiler can keep values in registers.

The Type-First Principle

The type-first principle runs through the chapter: the type is stated on the left, before the name, and the compiler enforces it.

Type-first makes Coral readable to C programmers and makes its safety machinery possible: every use, assignment, conversion, and access is checked; widths are explicit; mutability is declared; inference stays modest and local.

Operators and expressions are defined in terms of these types; control flow consumes this bool; functions compose these values; the safety machinery enforces these types. Master type-first and the rest follows.

Chapter 2 Summary

Coral source is UTF-8 text in .crl files, with no encoding ceremony.

Comments come in three forms: line comments with two slashes, block comments between slash-asterisk and asterisk-slash, and /// documentation comments that editors surface for the declaration below. Comments explain why, not what.

Identifiers begin with a letter or underscore, are case sensitive, and follow C-style conventions: PascalCase for types, camelCase for functions and variables, UPPER_CASE for constants. The receiver is the implicit self of an instance method.

Whitespace is insignificant, statements end at semicolons, and no line-continuation characters are needed. Indentation is style, not syntax.

Primitive types are fixed-width and explicit: i8 through i64, u8 through u64, f32 and f64, bool, char, and void.

Integer arithmetic on values is modular and wraps at the type width; a literal that does not fit its type is a compile-time error. Signed and unsigned are distinct, bitwise operations are first-class, and endianness uses explicit byte-swap and host-to-network functions.

Floating point follows IEEE 754, cannot represent most decimal fractions exactly, requires tolerance-based comparison, and makes NaN unequal to everything, including itself.

A char is one Unicode code point in 32 bits; a u8 is a byte. A code point occupies one to four UTF-8 bytes, and a grapheme cluster may span several code points.

Booleans have exactly two values, no truthiness, and short-circuiting AND and OR.

Void is the absence of a value; null is a pointer value meaning no object. They are different concepts.

Variables are declared type-first, or with var for local inference. Constants are immutable, variables mutable, and const pointers express read-only access.

Scope is block-scoped, shadowing is legal and local, and assignment uses the single equals sign with compound and increment operators available.

Locals live on the stack, constants in static storage, dynamic collections on the heap through the allocator, and short-lived values may live in registers.

The type-first principle, types before names and enforced by the compiler, is the foundation of Coral's readability and safety.
