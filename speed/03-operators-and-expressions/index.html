Speed Edition · Chapter 3

Operators and Expressions

The Hidden Complexity

Operators look simple, but they carry a language's deepest semantics: behavior per type combination, evaluation order, and edge cases. Get modulo with negatives, shift signedness, or struct equality wrong and the code is quietly wrong, passing tests and failing at two in the morning.

Coral's operators are C's operators, with the same hardware behavior and no hidden work. Coral adds structure through its type system, which changes how operators interact with composite types.

The Program Is a Bundle of Operations

A program is a bundle of operations: small, well-defined actions arranged in a chosen order.

Each operator has a fixed, knowable behavior. This chapter states each one's guarantees, limits, and edge cases.

The rest of this section is practice: small problems, each solved with a few operations.

The average of three scores, 6, 7, and 4:

u64 a = 6;
u64 b = 7;
u64 c = 4;
u64 total = a + b + c;     // 17: one addition, then another
u64 avg = total / 3;       // 5: the total divided by the count

The recipe is visible. The additions run, then the division, in the order written. The true average is five and two thirds, but the result is 5 because integer division drops the fraction, previewing section3.3.

The Fahrenheit temperature of a Celsius reading:

f64 c = 21.0;
f64 f = c * 9.0 / 5.0 + 32.0;    // 69.8

u64 cInt = 21;
u64 fInt = cInt * 9 / 5 + 32;     // 69

The same formula gives 69.8 and 69. The types decide which division you get, not the symbol. Knowing what operations do with each kind of number is this chapter's subject.

The monthly budget: after rent, food, and transit, is there enough for savings?

u64 income  = 3200;
u64 rent    = 1400;
u64 food    = 520;
u64 transit = 210;

u64 left = income - rent - food - transit;      // 1070
if (left >= 500)
    println("goal met: {} left", left);
else
    println("short this month: {} left", left);

The subtractions run left to right, as written. A different grouping gives a different number, so placement is meaning. The comparison produces a bool, and the program takes one of two paths.

A stopwatch has measured 8451 seconds since midnight. Report hours, minutes, and seconds:

u64 s = 8451;
u64 h = s / 3600;          // 2: whole hours
u64 m = (s % 3600) / 60;   // 20: whole minutes after the hours
u64 sec = s % 60;          // 51: seconds after the minutes

Each line peels one unit off. Hours come from division by 3600; minutes from the remainder divided by 60; seconds are the final remainder. Divide and take the remainder is one of the most repeated patterns in programming.

A smaller decision: does this order fit the cart's budget?

u64 price = 39;
u64 count = 12;
u64 cart = 350;
if (price * count <= cart)
    proceed_to_checkout();
else
    warn("over budget");

One multiplication, one comparison, one choice, all visible and chosen by you.

In every example you decided the operations, their order, and the arrangement. The compiler only checks that each operation's operands are valid and translates the bundle faithfully.

The rest of the chapter covers what each operation does, on which types, at the edges. Truncation, overflow (section3.5), and division by zero (3.4) are where surprises live.

What Is an Operator?

An operator is an operation on values, written with a symbol. Underneath it is a function of fixed signature, and the symbol is a promise that the mapping is fundamental enough to deserve the shortest spelling.

Think of an operator as a tiny machine with fixed input slots. You drop values in, it does its one job, and out comes a new value. The less-than machine hands back true or false.

Every operator compiles to machine instructions. That is why Coral chooses the C operators: plus is the processor's add instruction, equality a compare and branch, bitwise AND a single instruction. Nothing sits between the expression and the hardware.

Operators come in three arities. Unary takes one operand: unary minus, logical NOT, bitwise NOT, address-of, dereference, and prefix and postfix increments. Binary takes two: arithmetic, comparison, logical, and bitwise. Ternary takes three: Coral's only ternary is the conditional expression.

Every operator states its operand and result types, checked at compile time. Coral has no implicit conversions between distinct types, so operands must match or be converted explicitly. Literals adapt to context, but two differently typed variables never combine silently.

The unit-price question makes this concrete. One jar is 300 grams for 460 cents, another 500 grams for 690 cents:

u64 small = 460 * 100 / 300;   // 153 cents per 100 grams
u64 large = 690 * 100 / 500;   // 138 cents per 100 grams

Each line multiplies by 100 to get cents per 100 grams, then divides by size. The large jar wins at 138 against 153. Four ordinary operations, nothing hidden.

The three arities in one place:

u64 neg = -v;                // unary: one operand, the value v
bool inverse = !yes;         // unary: flips one bool
u64 sum = p + q;             // binary: two operands
bool ordered = p < q;        // binary: compares two
i32 sign = v < 0 ? -1 : 1;   // ternary: a condition and two values

The first two lines are one-input machines, the middle two two-input, the last three-input. A unary operator reshapes, a binary joins, and a ternary is a small decision inside an expression.

The Arithmetic Operators

The arithmetic operators are the four elementary operations plus remainder:

+   addition
-   subtraction
*   multiplication
/   division
%   remainder (modulo)

If % is new: remainder is what is left after whole-number division, so 10 % 3 is 1.

These operators have two flavors, integer and floating-point. Integer division and floating-point division behave differently, and nothing in the symbol says which you get.

The compiler selects the instruction from the operand types. Integer and float instruction families do not mix. Coral's strict typing requires an explicit conversion before mixing, so the same symbols express two families of operations.

i32 a = 7;
i32 b = 2;
i32 q = a / b;      // integer division: q is 3
i32 r = a % b;      // remainder: r is 1

f64 x = 7.0;
f64 y = 2.0;
f64 d = x / y;      // floating-point division: d is 3.5

The same slash compiles to different instructions and gives different values. The operator is what the operand types make it.

A common beginner surprise: 7 / 2 is 3, with no warning. For a fractional answer, make a side a float, as in 7.0 / 2.0 or (f64)x / (f64)y.

Integer division truncates toward zero. 7 / 2 is 3, not 3.5; the fraction is discarded, not rounded. This matches the hardware and is used when dividing counts into whole pieces.

Truncation toward zero matters for negatives: -7 / 2 is -3, not the floor -4. If you need floor division, compute it yourself. 7 / -2 is also -3. Decide explicitly whether truncation or flooring is wanted when signs may differ.

Floating-point division is IEEE 754: the nearest representable quotient, and division by zero produces a special value rather than a crash. The compiler picks the operation from the operand types.

Remainder is defined for integers and floats. Integer remainder follows integer division: 7 % 3 is 1. The sign of the result follows the dividend, so -7 % 3 is -1 and 7 % -3 is 1. The invariant is that (a / b) * b + (a % b) equals a.

i32 r1 = 7 % 3;     // 1
i32 r2 = -7 % 3;    // -1, follows the sign of the dividend
i32 r3 = 7 % -3;    // 1, the divisor's sign does not affect the result

The library uses remainder constantly: the bitset finds the word with division and the bit with remainder, duration splits nanoseconds, and the hash map maps keys to buckets with remainder.

Because division truncates, rounding rules are built explicitly. Ceiling division adds one fewer than the divisor before dividing:

pub u64 divCeil(u64 n, u64 d)
{
    return (n + d - 1) / d;
}

u64 pages = divCeil(byteCount, 4096);   // how many 4K pages hold the bytes

Rounding to nearest adds half the divisor first:

pub u64 divRound(u64 n, u64 d)
{
    return (n + d / 2) / d;
}

u64 avg = divRound(total, count);       // the count divided, rounded to nearest

Both depend on the addition not overflowing, which the caller ensures. Any rounding rule other than truncation is written down.

Division and remainder also map a flat position into row and column:

u64 k = 175;
u64 cols = 16;
u64 row = k / cols;        // 10: which row, quotient by the row width
u64 colIndex = k % cols;   // 15: which column within it, the last one

This is the inverse of cell = row * cols + col, and it appears in image buffers, tile maps, and spreadsheet storage.

Division by Zero

Division and remainder by zero are undefined behavior, as in C, because the hardware has no defined result. On most hardware integer division by zero raises a fault and terminates, which is honest: dividing by zero is a bug.

The machine has no answer for "how many times does zero fit into five," so Coral does not invent one. Ask before every division whether the divisor can be zero.

Code must ensure the divisor is not zero when it is not known safe. Guard with a comparison:

if (divisor == 0) return 0;
u64 avg = total / divisor;      // safe: the zero case was handled above

The standard library guards every division whose divisor could reach zero, where a reader can see it. One comparison prevents a crash or a wrong result.

Floating-point division by zero is defined by IEEE 754: a nonzero value divided by zero gives infinity, and zero divided by zero gives NaN.

An average of a possibly empty list shows the guard:

u64 average(u64 sum, u64 count)
{
    if (count == 0) return 0;   // no measurements: no division, no crash
    return sum / count;
}

The guard sits one line above the division, so the zero case and the defined case are both visible.

The divisor may be a computation, not a variable. A throughput measurement divides by elapsed time, which can be zero:

u64 rateOf(u64 work, u64 seconds)
{
    if (seconds == 0) return 0;   // no elapsed time: no defined rate
    return work / seconds;
}

Guard the expression, not just a named variable. Look at every division and ask what could make the right operand zero.

Overflow and Underflow

Overflow is when a result exceeds its type's range. Integer arithmetic wraps at the type width in two's complement, and expressions show the consequences.

Adding one to the maximum wraps to the minimum: 255 becomes 0 for u8, 127 becomes -128 for i8. Every integer operation is performed at the operand width and truncated to it, deterministically, matching the hardware.

u8 m = 255;
m += 1;     // m is now 0, wrapped
i8 s = 127;
s += 1;     // s is now -128, wrapped
u8 n = 0;
n -= 1;     // n is now 255, wrapped

Overflow is an odometer rolling from 99999 to 00000: no alarm, no error, just a restart. Pick a type big enough for the values you expect.

Wrapping is the machine's natural arithmetic, not a compiler special case. The processor reports overflow in a status flag, but Coral does not read it implicitly; code that needs to know checks the operands.

There is no saturation. Coral wraps, and if you need clamping you implement it explicitly.

There is no panic on integer overflow. Checked arithmetic on every operation would slow every program, so the wrapped result stands. When range is a risk, check operands before the operation.

For unsigned addition, a wrapped sum is smaller than either operand, which makes overflow detectable from the result:

pub u64 checkedAdd(u64 a, u64 b)
{
    u64 sum = a + b;
    @assert(sum >= a);   // false exactly when the addition wrapped
    return sum;
}

The @assert fires exactly when the addition wrapped. The check is arithmetic itself, not a hardware flag guess.

A wrapped multiplication is detected by dividing the product by a factor:

pub u64 checkedMul(u64 a, u64 b)
{
    u64 p = a * b;
    @assert(a == 0 || p / a == b);   // false exactly when the multiply wrapped
    return p;
}

If the product is true, p / a is b. If it wrapped, the division gives a different quotient and the @assert fires. The first clause excludes zero, the one divisor that would make the check undefined.

A small counter in a long loop can wrap silently:

u8 counter = 250;
u64 rounds = 0;
while (counter != 16)      // intended: "until it reaches 16"
{
    counter += 1;
    rounds++;
}
// rounds is 22, not 10: the counter detoured through 254, 255, 0, and 1..15

The loop terminates, which makes the bug expensive: nothing warns, it just takes the long way. Choose the counter's type from its range.

Underflow has two senses. Integer underflow is overflow in the negative direction and wraps identically. Floating-point underflow is a result too small to represent, handled by a subnormal value or zero.

The Compound Arithmetic Operators

Every arithmetic and bitwise operator has a compound assignment form: the operator followed by an equals sign. It computes the operation and assigns back to the left operand.

+=    -=    *=    /=    %=
&=    |=    ^=    <<=   >>=

x += 1 is exactly x = x + 1. The form shortens in-place modification and avoids repeating the variable name.

u64 total = 0;
total += first;
total += second;
total += third;      // the three values accumulate into total

u32 flags = 0;
flags |= FLAG_READ;     // sets the read bit
flags |= FLAG_WRITE;    // sets the write bit without clearing the read bit

The accumulation pattern is the heart of counting and summing; the flag pattern is the heart of representing sets of options in one word. OR only turns bits on, which is what makes the flag word safe.

Three more idioms: accumulating a product, cycling an index, and toggling a mode:

u64 product = 1;
for (u64 i = 2; i <= 5; i++)
    product *= i;           // 2, then 6, then 24, then 120

u64 slot = 0;
for (u64 i = 0; i < 20; i++)
{
    slot++;
    slot %= 8;              // the index cycles 0..7 forever, without an if
}

bool dark = false;
dark ^= true;               // flips: on, off, on...
dark ^= true;               // the toggle, two lines long, needs no if

The %= is a ring-buffer step in one line. The ^= is a mode flip. Each compound form names its operation at the front.

Increment and decrement have prefix and postfix forms. Prefix yields the new value; postfix yields the old. When the value is unused, the forms are identical; when used, the choice is semantic.

u32 i = 0;
u32 a = ++i;    // i becomes 1, a is 1: prefix yields the new value
u32 b = i++;    // b is 1, i becomes 2: postfix yields the old value

The forms differ only in the value produced. The library's loops use bare i++ when the value is discarded, the conventional spelling of "advance by one."

Expressions and Statements

An expression combines operators, operands, literals, and calls to produce a value. A statement is a unit of action. Coral keeps the distinction sharp.

Every expression has a type and a value. 3 + 4 has an integer type and value 7; a == b has type bool; a call is an expression whose value is the return value. Operators assemble values into larger values, without limit.

A statement acts: assignment, if, return, loop. Some contain expressions: in x = y + 1, the right side is an expression; in if (a < b), the condition is. Expressions answer "what is the value"; statements answer "what does the program do."

An expression statement is an expression followed by a semicolon, with its value discarded. Most void calls are expression statements:

v.push(3);    // the call runs, the void value is discarded

Assignment is also an expression whose value is the assigned value, and the semicolon discards it. So assignment can appear inside a larger expression:

i32 y = (x += 2);   // the assignment to x runs, then y receives the value

Nesting assignments is occasionally useful, but the library prefers explicit statements. Expressions produce; statements act.

Side Effects and Evaluation Order

A side effect is a change to program state that outlasts the expression that caused it. x + 1 has none; assignment, increment, and state-modifying calls do. Make each side effect visible and intentional.

Evaluation order matters. Coral follows C: the operands of a binary operator may be evaluated in any order. Each operand is fully evaluated before the operator applies, and operands do not interleave.

The consequence is a rule that prevents whole classes of bugs: never read and write the same variable in one expression, unless they are the two sides of one assignment. The classic mistake:

v = v + (v = v + 1);   // wrong: the result depends on an unspecified order

The language does not say whether the right-hand v is read before or after the inner assignment, so the result is undefined. Split such code into two statements.

Between statements, each runs to completion before the next begins. The written order is the order of effects; only inside one expression does order need care.

v = v + 1;      // one effect, clearly ordered
x = v;          // the next statement sees the updated v

Increment and decrement are side effects inside expressions, which is why prefix and postfix exist. In i++, the effect is the point; in y = ++i, the expression both changes i and yields the new value.

The same rule covers function arguments. Their evaluation order is unspecified, so two side effects on the same variable in one call are the same trap:

f(n, ++n);      // not specified: does the first argument see the increment?

The reader cannot know whether the first n is read before or after the increment. Give each effect its own statement:

u64 before = n;     // one effect per statement, written in order
n += 1;
f(before, n);       // the two values the call needs, taken when they exist

The three lines say what the one line meant, with the order written down.

The Comparison Operators

Comparison operators compare two values and produce a bool:

==    equal to
!=    not equal to
<     less than
<=    less than or equal to
>     greater than
>=    greater than or equal to

Comparisons answer questions and hand back a bool, exactly what if and while expect. 3 == 3.0 mixes an integer and a float, which Coral refuses; convert explicitly.

For integers, comparisons compare numeric values. Mixed signed and unsigned comparisons are handled carefully, with the conversion explicit, to avoid classic mixed-sign bugs.

i32 a = 3;
i32 b = 4;
bool less = a < b;       // true
bool equal = a == b;     // false
bool different = a != b; // true

Mixed signs need their own example, because the same bits mean different numbers. An i32 holding -1 and a u32 holding 0 are different values, so Coral requires a cast to choose the interpretation:

i32 s = -1;
u32 u = 0u;
bool same = ((u32)s == u);   // false: -1 as u32 is a huge unsigned value

The cast states which type is compared, giving one defined meaning. In C this line would be a coin flip; in Coral it is a documented decision.

The most common victim is a loop condition comparing a signed counter with an unsigned length. The cast writes the decision down:

for (i32 i = 0; (u64)i < len; i++)
    processRecord(&records[i]);   // (u64)i: the comparison is explicitly unsigned

The cast states that the count is compared as unsigned, and the loop runs exactly len times. Omitting it is a compile error, not a silent behavior change; the error forces the author to choose.

Float comparisons follow IEEE 754, so NaN must be understood. Every relational comparison with NaN is false, including NaN == NaN. Only NaN != NaN is true. A range check therefore rejects NaN, and the not-equal form detects it.

f64 r = total / count;                // may be NaN when count is zero
bool inRange = r > 0.0 && r <= 1.0;   // false when r is NaN
bool isNan = r != r;                  // true exactly when r is NaN

The range check rejects NaN automatically because each comparison is false. The not-equal comparison is the standard NaN detector.

The comparison operators apply directly to primitives. Composite types, structs and strings, do not compare contents automatically. Coral defines no implicit struct equality because the correct meaning is a property of the type. The library provides explicit methods.

Value Equality and Reference Equality

Value equality and reference equality are among the most important distinctions in programming, and Coral draws them clearly.

Value equality asks whether two things hold the same content; reference equality asks whether two names point at the same object. Two identical houses on different lots are equal in contents but not the same house.

Value equality asks whether two values are the same value. Primitives have it: a == b for integers is true exactly when they hold the same number.

Reference equality asks whether two references name the same object. Two pointers to the same location are reference-equal; two pointers to different locations are not, even if their contents are identical.

In Coral, == on pointers compares addresses. To compare pointed-to contents, use the type's comparison method, because only the type knows what "same contents" means. == is identity for pointers, value equality for primitives, and nothing is guessed for composites.

i32 x = 5;
i32 y = 5;
i32* px = &x;
i32* py = &y;
i32* qx = &x;

bool valueEq = (x == y);     // true: the numbers 5 and 5 are equal
bool refEq = (px == py);     // false: two different objects, same contents
bool sameObj = (px == qx);   // true: both pointers name the same object

The integers compare by value, the pointers by address, and the pointer comparison neither claims nor denies content equality. Identity and content equality are different questions.

The collections depend on this. A hash map cannot compare keys by pointer identity, so it requires the caller to provide an equality function for the key type.

Equality for Composite Types

Composite types, structs and library types built on them, have no built-in ==. Automatic member-by-member equality is usually wrong: a pointer field would compare addresses, not contents. Coral refuses to guess and provides the tools to define equality correctly.

Library types implement equality as methods. The string view provides equals, comparing lengths and bytes, and compare, returning a negative, zero, or positive ordering. The duration type has eq and compare for the same reason.

str a = "coral";
str b = "coral";
bool sameText = a.equals(b);      // true: same length, same bytes
bool sameObject = (a.ptr == b.ptr);   // false unless both views share storage

The two views are equal as text even if they point at different buffers; only equals, which compares lengths and bytes, can say so. Insisting that types define equality makes "equal" mean what you mean.

The pattern is everywhere. The string's find uses memcmp and tests against zero; contains calls find and tests against a sentinel. Composite equality is always a method named for what it does.

The Comparison Protocol

For ordering, Coral uses a compare protocol: negative when the first is less, zero when equal, positive when greater. One method answers all six comparison questions, and sorting and ordered collections build on it.

The string view's compare uses memcmp and treats a shorter equal prefix as less. The duration's compare compares seconds then nanoseconds, giving a total order. Sort algorithms, trees, and priority queues consume this protocol. Implement it and your type plugs into every ordered algorithm.

Consume the protocol by testing the sign:

i32 order = a.compare(b);
bool aFirst = order < 0;     // a sorts before b
bool equal = order == 0;     // a and b are equivalent
bool aLast = order > 0;      // a sorts after b

str smaller = a.compare(b) <= 0 ? a : b;   // the minimum by the protocol

The sign test replaces six relational operators: one call, three possible results, any comparison answered against zero. A sort needs "which comes first," and compare answers directly.

Primitive operators provide individual comparisons; compare aggregates them into a total order; algorithms consume it. Nothing hidden can surprise you.

The Logical Operators and Short-Circuit Evaluation

The logical operators combine bools and produce bools.

&& means both must be true, || means at least one, and ! flips a bool. They stop early: a false left side of && means the right side is never evaluated, which makes safety checks inline.

&&    logical AND
||    logical OR
!     logical NOT

The binary operators short-circuit, guaranteed by the language. If a is false in a AND b, b is not evaluated; if a is true in a OR b, b is not evaluated. This is defined behavior, not an optimization.

The compiler emits the first operand, then a conditional branch that skips the second. The second operand's code may not run at all, and the compiler may not hoist it.

Short-circuiting makes chained conditions safe:

if (p != null && p[0] == 'x') ...

The pointer is tested first, and only a non-null pointer is dereferenced. This is a null-safety guard folded into an ordinary condition.

The same shape guards an indexed read:

u64 i = 0;
while (i < n && data[i] != target)   // the bound test guards the read
    i++;
bool found = i < n;                  // false means the loop ran off the end

The bound test runs first, so data[i] is read only when i < n. This is the shape of every hand-written bounds-checked search.

Short-circuiting also guards invalid or wasteful computations:

u32 count = 0;
bool safe = count != 0 && (10 / count) > 2;   // the division never runs at 0

bool ready = checkFastPath() || checkSlowPath();   // slow path runs only when needed

The right operand runs only when the left leaves the outcome undecided. The guarantee turns expression structure into control flow.

The logical operators accept only bools, not integers. Use them for conditions and the bitwise operators for bit patterns.

The Ternary Operator

The conditional expression, written with ? and :, is the expression-level if. It chooses one of two expressions based on a bool and produces a value:

condition ? valueIfTrue : valueIfFalse

Read it as "if the condition, the first value, otherwise the second." Its result can be stored directly, as in u64 bonus = overtime ? 100 : 0;, which gives 100 when overtime is true and 0 otherwise.

The condition is evaluated first, and only one branch is evaluated, so the ternary shares short-circuiting. A branch invalid in the other case is safe.

The ternary is an expression, so it can appear in assignments, arguments, and larger expressions:

u64 newCap = self.cap > 0 ? self.cap * 2 : 4;

If capacity is positive it doubles; otherwise it is four. Both branches must have the same type, which is the whole expression's type.

Because branches are expressions, ternaries nest:

i32 sign = value < 0 ? -1 : (value > 0 ? 1 : 0);

The outer condition chooses -1 or a second ternary, which chooses 1 or 0. Parentheses make the grouping visible because the operator associates to the right. Both branches must have the same type.

The two helpers every systems program writes by hand, minimum and clamp:

u64 smaller = a < b ? a : b;                  // the minimum of two
i32 clamped = v < lo ? lo : (v > hi ? hi : v);   // v, kept inside [lo, hi]

The clamp is two ternaries read outside in: lo when v is too small, hi when too big, and v otherwise. Because both branches are values, the whole expression is a value.

Only the chosen branch is evaluated, so a branch with a side effect is safe. In flag ? enable() : disable(), only one call runs.

The ternary chooses a value; an if statement chooses a sequence of actions. Expressions produce, statements act.

Null Coalescing

Coral represents a missing value with Option, and providing a default has a corresponding idiom.

Option holds either a value or nothing. The library provides methods to test, extract, and provide a default. The default-value method is coalescing: return the value if present, otherwise the default.

u64 count = maybeCount.unwrapOr(0);

unwrapOr makes the fallback explicit and visible, and is the standard way to consume an optional with a sensible default.

A subtlety: unwrapOr's argument is an ordinary argument, evaluated before the call. An expensive default runs whether or not the Option holds a value.

u64 a = cached.unwrapOr(0);                  // a constant default: free either way
u64 b = cached.unwrapOr(computeDefault());   // computeDefault always runs

When the default is cheap, the method is perfect. When it is expensive, guard it with a presence test. A method call has method-call semantics, and its arguments are evaluated predictably.

Reading settings from a config file meets the pattern constantly:

u64 port = config.lookup("port").unwrapOr(8080);   // the file's value, or the default

lookup returns an Option because the key may be missing, and unwrapOr supplies the fallback in the same line. A missing setting is not a crash or a special case.

The Bitwise Operators

The bitwise operators treat integers as bit patterns, the machine's raw operations on individual bits:

&     bitwise AND
|     bitwise OR
^     bitwise XOR (exclusive OR)
~     bitwise NOT (complement)
<<    left shift
>>    right shift

A value is a row of on/off switches, and a bitwise operator works position by position. & keeps a bit only where both inputs have it; | turns a bit on if either has it; ^ turns it on if exactly one does. This stores many yes/no facts in one number.

AND produces a 1 where both operands have a 1; it is the masking operator, used to clear bits, test bits, and extract fields. OR produces a 1 where either has a 1; it sets bits without disturbing others. XOR produces a 1 where exactly one has a 1; it toggles masked bits. NOT flips every bit.

A worked example, with each hex digit representing four bits:

u8 a = 0x3C;    // binary 0011 1100
u8 b = 0x0F;    // binary 0000 1111

u8 and_ = a & b;     // 0x0C, binary 0000 1100: bits set in both
u8 or_ = a | b;      // 0x3F, binary 0011 1111: bits set in either
u8 xor_ = a ^ b;     // 0x33, binary 0011 0011: bits set in exactly one
u8 not_ = ~a;        // 0xC3, binary 1100 0011: every bit flipped

AND keeps bits set in both, OR keeps every bit either has, XOR keeps bits where they disagree, and NOT inverts. The four operators can produce any combination of input bits.

Do not confuse the single-character bitwise operators with the double-character logical operators. Bitwise combines bits into an integer; logical combines bools into a bool. Writing one for the other is a different operation, and the type checker rejects it, catching a class of legendary C bugs at compile time.

The library uses bitwise operators everywhere. The bitset sets with OR and a mask, clears with AND and a complemented mask, toggles with XOR, and tests with AND against zero. The endian module swaps bytes with shifts and masks. countOnes clears the lowest set bit repeatedly with value AND (value minus one).

Shift Operators

The shift operators move bits left or right:

<<    left shift
>>    right shift

A left shift moves bits left by the right operand, filling with zeros. It is multiplication by 2 to the power n while no bits shift out. The bitset builds masks by shifting a 1 into position.

A right shift depends on signedness. For unsigned values it is logical: bits move right, zeros fill in, and it is division by 2 to the power n. For signed values it is arithmetic: copies of the sign bit fill in, preserving the sign. The library's byte-swap functions use only unsigned shifts and masks.

The two right shifts on the same eight bits, 11111000, which is -8 signed and 248 unsigned:

i8 neg = -8;              // binary 1111 1000
i8 ar = neg >> 2;         // -2: arithmetic shift, sign bits fill in

u8 pos = 0xF8;            // the same eight bits, but unsigned
u8 lg = pos >> 2;         // 0x3E, binary 0011 1110: logical shift, zeros fill in

The signed result stays negative near -2, division by four with the sign preserved. The unsigned result becomes 62, division by four with zeros filled. Coral selects the form from the left operand's type.

Shifts build masks and extract fields. To isolate the third byte, shift right by sixteen and mask the low eight bits; to build a single-bit mask, shift a 1 left by n:

u32 thirdByte = (x >> 16) & 0xFF;    // the byte in bits 16..23
u32 mask = 1u << 12;                 // a 1 at bit 12

The shift moves the field low and the mask discards the rest. Shift and mask is the universal mechanism for packing and unpacking fields.

The shift count must be less than the width of the left operand; shifting by the width or more is undefined behavior. Shift only by zero through width minus one, and guard computed counts:

u32 shifted = (n < 32) ? (x << n) : 0;   // never shifts by 32 or more

Bit Manipulation Patterns

A handful of bit-manipulation patterns recur throughout systems code and the Coral library. These four are the root patterns.

Set a bit. OR the value with a mask that has a 1 at position n:

flags = flags | (1 << n);
flags |= (1 << n);

Clear a bit. AND the value with the complement of the mask:

flags = flags & ~(1 << n);
flags &= ~(1 << n);

Toggle a bit. XOR the value with the mask:

flags ^= (1 << n);

Test a bit. AND the value with the mask and compare against zero; the result is nonzero exactly when the bit is set.

(flags & (1 << n)) != 0

These four patterns are the bitset module in miniature: set, clear, toggle, and test, each on a machine word.

Clear the lowest set bit. value AND (value minus one) clears the lowest set bit and leaves the rest unchanged. countOnes loops on this until the value is zero.

Check whether a value is a power of two. A value is a power of two exactly when it is nonzero and value AND (value minus one) is zero.

Build a mask of the low n bits. Shifting 1 left by n and subtracting 1 sets the low n bits. The bitset's all method uses this on the remainder word.

The mask-and-shift pattern extracts and replaces a field in a packed value. Extract by shifting low and masking; replace by clearing the field and ORing in a shifted, masked value.

u32 packed = 0xAABBCCDD;
u32 red = (packed >> 24) & 0xFF;      // 0xAA: shift the field low, mask it
u32 green = (packed >> 16) & 0xFF;    // 0xBB
u32 blue = (packed >> 8) & 0xFF;      // 0xCC

packed = (packed & ~(0xFFu << 8)) | ((newBlue & 0xFF) << 8);   // replace the blue byte

Reads are shift then mask; the write clears the old field with a complemented mask, then ORs in the new field. This read-modify-write is the same order used by image decoders, protocol parsers, and compact records.

The alignment helper rounds a value up to a multiple of a power of two by adding one less than the alignment and clearing the low bits:

pub u64 alignUp(u64 x, u64 align)
{
    return (x + align - 1) & ~(align - 1);
}

u64 buf = 1000;
u64 aligned = alignUp(buf, 64);   // 1024, the next multiple of 64

This requires align to be a power of two, the common case for buffers and segments. Allocators use it to round sizes to alignment classes.

Toggling every even bit shows test and toggle together:

u64 bits = 0;
for (u64 i = 0; i < 64; i += 2)
    bits ^= (1u << i);   // toggle the even-numbered bits on

bool evenSet = (bits & (1u << 4)) != 0;   // true: bit 4 was toggled on

The loop builds each mask with a shift and applies it with XOR; the test confirms a bit with AND and a comparison.

The Address and Dereference Operators

Pointers are fundamental to Coral, and their operators are C's, with the same meanings:

&     address of
*     dereference
->    member access through pointer
.     member access

Think of a variable as a labelled box and a pointer as a slip of paper with its location. &x writes the location; *p goes there and uses what is stored. Passing the slip lets two pieces of code work on the same box.

The address-of operator produces a pointer to its operand. Such a pointer can be passed to functions that modify the caller's value. Methods name their receiver self, and the compiler takes its address when needed.

The two operators are machine-level inverses. Address-of loads an address; dereference loads or stores through it. Passing an address gives the function a name for the caller's memory:

pub void increment(u64* p)
{
    (*p) += 1;   // modify the caller's variable through the pointer
}

u64 n = 0;
increment(&n);   // n is now 1

The call passes the address, the function dereferences to reach the variable, and the compound operator stores back through the pointer. The whole transaction is visible.

The swap is the classic first pointer lesson, using both operators in their purest form:

pub void swap(u64* a, u64* b)
{
    u64 t = *a;     // dereference: read what a names
    *a = *b;        // dereference on both sides: copy and store
    *b = t;
}

Each line is one dereference: read the first value, copy the second into the first, copy the temporary into the second. The function sees addresses, and that is enough.

Dereferencing a null pointer is a bug, and Coral's safety machinery prevents it. The arrow combines dereference and member access: p->field is (*p).field. Methods use the dot on self; the arrow appears when following an explicit pointer, as in node->next.

The arrow and star-plus-dot are exactly equivalent:

Buffer b;
Buffer* pb = &b;
b.len = 4;          // dot: direct field access on the value
pb->len = 8;        // arrow: field access through the pointer
(*pb).len = 12;     // dereference, then dot: exactly the arrow above

All three assignments reach the same field; the arrow is the shorter spelling of the third. The dot is for values, the arrow for pointers, and the compiler rejects each on the wrong kind.

The dot accesses a field of a struct value or reference. Coral methods reach their receiver's fields with the dot; the arrow is for explicit pointers the code follows by hand.

Subscript and Casting

The subscript operator accesses an element of an array or pointer to contiguous storage:

array[index]

array[index] is *(array + index). This is the C model, fast and simple. The library's collections expose contiguous storage and use subscripting internally, while their access methods assert bounds. The primitive subscript is raw; checked access is built on top.

u8* bytes = raw;        // a pointer into some contiguous storage
u8 third = bytes[2];    // the same as *(bytes + 2), the third byte

The subscript adds the index scaled by element size and dereferences. The scale comes from the pointer's type, so a u8* advances one byte per index. This automatic multiplication is why a wrong index can overrun a buffer, and why checked methods exist.

Two-dimensional storage composes the subscript. A flat array indexed by row and column uses the row-major formula:

u64 idx = row * width + col;     // the flat position of the cell
u8 pixel = pixels[idx];          // the same access the GPU makes

A pointer walks the same storage, one dereference per stop:

u64 total = 0;
for (const u64* p = data; p < data + n; p++)
    total += *p;

The pointer advances one element per step and dereferences at each stop. Subscript, pointer arithmetic, and dereference are one mechanism with three spellings.

Casting converts a value from one type to another. Coral uses the C-style cast, with the target type in parentheses before the expression:

(u64)value
(i32)value
(T*)pointer

A cast tells the compiler to treat a value as another type. Coral never converts behind your back, so a cast is how a conversion is written down. The type goes in parentheses before the value, as in (u32)x; there is no as keyword. Because a cast can change a value or reinterpret bits, pause on every one.

A cast is an explicit, deliberate conversion where implicit conversions do not apply. Casting between integer types converts the numeric value to the target width. Casting between pointers and integers, or between unrelated pointer types, is unsafe and permitted only where safety rules allow.

u32 x = 300;
u8 b = (u8)x;     // 44: the value is truncated to eight bits
u32 back = (u32)b;   // 44: the byte widens back to the same value

The narrowing cast keeps the low eight bits of 300, which is 44, and widening restores 44. Widening is zero or sign extension, described next.

Sign Extension and Zero Extension

Widening to a larger integer type must decide the new high bits. Coral decides from the source type, and the two cases are different instructions.

Zero extension fills the new high bits with zeros and applies to unsigned values. 250 as u8, 11111010, widens to 0000000011111010, still 250.

Sign extension fills the new high bits with copies of the sign bit and applies to signed values. -2 as i8, 11111110, widens to 1111111111111110, still -2. Without it, -2 would become 254.

i8 s = -2;
i16 widened = (i16)s;       // sign-extended: still -2

u8 u = 250;
u16 widenedU = (u16)u;      // zero-extended: still 250

The signed value keeps its ones and its meaning; the unsigned value gains zeros. The compiler chooses the instruction from the source's signedness.

The two sources can hold the same bits. 11111110 is -2 as i8 and 254 as u8, and widening produces different results. Only the type says which is intended, and Coral always supplies it.

A sensor read makes the difference real. It reports tenths of a degree in one signed byte, arriving as unsigned; 0xFE means minus two and must not become 254:

u8 rawByte = readSensor();         // 0xFE, as the bus delivered it
i8 signed = (i8)rawByte;           // -2: the same bits, read as signed
i16 tenths = (i16)signed;          // sign-extended: still -2, now in sixteen bits

Two casts preserve the meaning: re-read the bits as signed, then widen with sign extension. Widening from the unsigned byte instead gives 254, a large error no runtime check would catch. The source type is the whole story.

Narrowing keeps the low-order bits and discards the rest: 300 cast to u8 is 44. Widening preserves meaning by sign or zero extension; narrowing preserves bits.

The Sizeof Operator

sizeof answers how many bytes a value occupies. Its operand is a type or expression, and its result is an unsigned integer constant computed at compile time, with no runtime cost.

u64 size = sizeof(u64);      // 8 on a machine with 64-bit words
u64 byteSize = sizeof(u8);   // 1 by definition
u64 ptrSize = sizeof(u8*);   // 8 on a 64-bit machine

The results are constants of the target machine, so they can size allocations and arrays at compile time.

The library uses sizeof to convert bytes to elements:

u64 count = sizeof(storage) / sizeof(u8);   // the number of bytes the buffer holds

For an array, sizeof gives the whole array's size; dividing by element size gives the count. For a pointer, sizeof gives the pointer's size, not the pointee's. Passing an array to a function decays it to a pointer, so carry lengths explicitly.

Buffer sizing is a natural use. A renderer sizing a fixed buffer from its element type:

struct Vec2 { f64 x; f64 y; }
u64 samples = 1000;
u64 bufferBytes = samples * sizeof(Vec2);   // room for 1000 points

The multiplication is computed before the program runs, and changing the type updates the sizing automatically. The reader sees the allocation arithmetic in the line where it is decided.

A type's size is fixed by its layout, so sizeof bridges expressions and memory layout.

Operator Precedence

Operator precedence determines grouping. Coral's rules are C's, so a + b c means a + (b c). Knowing them prevents classic expression bugs.

The levels, highest to lowest:

parentheses                ( )     grouping, highest
postfix                    []  .  ->  ++  --
unary                      !  ~  -  *  &  ++  --
cast                       (T)x
multiplicative             *  /  %
additive                   +  -
shift                      <<  >>
relational                 <  <=  >  >=
equality                   ==  !=
bitwise AND                &
bitwise XOR                ^
bitwise OR                 |
logical AND                &&
logical OR                 ||
conditional                ? :
assignment                 =  +=  -=  ...  lowest

Do not memorize the table. Remember that multiplication and division precede addition and subtraction, and add parentheses when unsure. Parentheses always win and cost almost nothing.

Unary and postfix bind tightest, then arithmetic, comparisons, bitwise, logical, conditional, and assignment.

Multiplication and division bind tighter than addition and subtraction. Shifts bind tighter than relational and equality. Bitwise AND, XOR, and OR sit between equality and logical AND, so a & b == c groups as a & (b == c). Logical operators bind loosest of the condition operators.

Two shapes mislead readers who trust the characters on the line:

bool t = a & b == c;     // grouped as a & (b == c): a bitwise AND of a bool comparison
i32 v = x << 1 == y;     // grouped as (x << 1) == y: the shift happens before the test

The first groups as a & (b == c), rarely intended. The second groups as (x << 1) == y, usually intended. Neither needs memorizing; recognize ambiguity and parenthesize.

The most expensive real-code surprise is testing a flag bit, because the comparison must be parenthesized:

bool has = (flags & FLAG_HIGH) != 0;   // correct: compare the result of the mask

bool broken = flags & FLAG_HIGH != 0;  // groups as flags & (FLAG_HIGH != 0)

The unparenthesized line groups as flags & (FLAG_HIGH != 0), a bitwise AND of an integer and a comparison result. In C it compiles and silently masks with 0 or 1. In Coral it is a type error, forcing the parentheses and the correct comparison.

Know the table well enough to recognize ambiguity, and parenthesize when clarity demands. Parentheses cost keystrokes; a confused reviewer costs an afternoon.

Associativity

Associativity determines grouping for operators of the same precedence.

The arithmetic operators +, -, *, and / are left-associative: a - b - c is (a - b) - c. This matters for subtraction and division, where order changes the result.

i32 a = 10;
i32 b = 4;
i32 c = 3;
i32 r = a - b - c;   // (10 - 4) - 3 = 3, not 10 - (4 - 3) = 9

Left grouping gives 3; right grouping would give 9. Left-associativity makes a chain of subtractions a sequence of subtractions.

Divisions and remainders group the same way. 100 / 10 / 2 is 5, not 20, and a remainder chain reduces step by step:

u64 v = 100 / 10 / 2;   // (100 / 10) / 2 = 5, not 100 / (10 / 2) = 20
u64 r = 97 % 15 % 10;   // (97 % 15) % 10 = 7 % 10 = 7, not 97 % (15 % 10) = 2

The right grouping of the remainder line would be 2, a different answer from the same digits. Left-associativity makes chains read left to right.

Assignment is right-associative: a = b = c assigns c to b, then b to a. The conditional associates right as well. Unary operators apply right to left, so -!x is -(!x).

a = b = c;   // c is assigned to b, then b is assigned to a: all three become c

Assignment is an expression whose value is the assigned value, so the inner assignment produces a value the outer can consume.

Arithmetic, shift, and comparison operators are left-associative; assignment and the conditional are right-associative. The library relies on arithmetic's left grouping and rarely uses assignment chains.

Operator Overloading

Coral has no user-defined operator overloading. Operators have fixed meanings for built-in types, and a struct cannot redefine + or ==.

Overloading is a source of hidden complexity: a + that is not addition, a == that is not equality, a << that is not a shift. Reading such code requires knowing every operand type and every overload, and a small type change can silently change meaning. Coral declines the cost.

Operations on composite types are named methods: add, compare, eq, equals. Duration addition is add, string equality is equals, and the hash map takes an equality function. None can surprise a reader who does not know the type.

Operators are fixed for primitives, and composites use named methods. There is no third category and no hidden dispatch, consistent with type-first: types are explicit, so operations are explicit.

Operator Overloading as a Tradeoff

It is worth being precise about what Coral gives up.

Arithmetic on composite mathematical types cannot use operators. A vector cannot define u + v, a matrix cannot define a * b, and a rational cannot define a / b. Such code writes u.add(v) and a.mul(b), which is more verbose and a real cost for numerical code.

Vector3 u;
Vector3 v;
Vector3 w = u.add(v);   // addition is a named method, not a plus sign

The operation is spelled out and unambiguous, at the price of a few characters and arithmetic notation. For a stream of vector and matrix operations, the loss of density is genuine.

The library compensates with add, sub, mul, and component methods on its vector and matrix types. Extra verbosity buys a language where expressions always mean what the operators say.

The design keeps the language small: every operator has one meaning and one set of rules. The reader's load is on types, not symbols.

A Worked Example: The Frame Header

A real function uses several tools at once. Here is a frame header that packs three color bytes into one 32-bit word, then unpacks and verifies it.

First, packing: three bytes into one word, each shifted into its own eight-bit field:

u32 pack(u8 r, u8 g, u8 b)
{
    return ((u32)r << 16) | ((u32)g << 8) | (u32)b;
}

The casts widen the bytes, the shifts place them, and the ORs join them, the write direction of mask-and-shift.

Second, unpacking, the read direction: shift then mask:

u8 red   = (u8)((px >> 16) & 0xFF);   // the field in bits 16..23
u8 green = (u8)((px >> 8)  & 0xFF);   // the field in bits 8..15
u8 blue  = (u8)(px & 0xFF);           // the field in bits 0..7

Each line shifts its field low and masks the rest; the narrowing cast keeps the low eight bits on the way back.

Third, verification: a checksum folded from the three fields, using XOR to mix them:

u8 fold(u32 px)
{
    return (u8)(((px >> 16) ^ (px >> 8) ^ px) & 0xFF);
}

The shifts align the fields, the XORs mix them, and the mask keeps the low byte. A comparison then detects corruption.

Fourth, the bookkeeping: the display index cycles with a remainder, the rate is a guarded division, and the flag is a compound flip:

u64 slot = frame % SLOTS;                       // the ring position
u64 rate = renderSeconds == 0 ? 0 : frames / renderSeconds;   // guarded rate
busy ^= true;                                   // the toggle between two states

The remainder makes the ring, the conditional guards the division, and the compound XOR toggles.

Fifth, the whole header validated at once:

bool valid = header.checksum == fold(header.word) &&
             (header.word & 0xFF000000) == 0;

The mask clears the reserved high byte and compares against zero, with the parentheses precedence requires; && chains the checks so the second runs only if the first passed.

No operator here is remarkable; the whole is the sum of each operator's certainty. The casts say the width, the shifts and masks say the field, the XOR says the word is whole, the remainder says the ring holds, and the comparison says it arrived intact.

Chapter 3 Summary

Coral's operators are C's, with the same symbols and hardware semantics. The compiler picks the operation from operand types, and each compiles to machine instructions with no hidden behavior.

Integer division truncates toward zero; floating-point division follows IEEE 754. Remainder follows the dividend's sign. Integer division by zero is undefined; float division by zero is defined. Other rounding rules are built explicitly, as in divCeil and divRound.

Integer arithmetic wraps at the type width with no saturation and no panic. Code manages range, checking operands before risky operations.

Compound assignment combines an operation with assignment back to the left operand. Prefix and postfix increment differ in the value produced.

Expressions produce values and statements perform actions. Operand evaluation order is unspecified, so one expression must not read and write the same variable. Between statements, effects are fully sequenced.

Comparison operators produce bools for primitives. NaN comparisons are always false, and pointer == is reference equality.

Composite types have no built-in ==. Equality and ordering are explicit methods: equals, compare, and the negative/zero/positive protocol that sorting and ordered collections consume.

&& and || short-circuit, and the ternary shares the guarantee by evaluating only the chosen branch.

Null coalescing is Option's unwrapOr: use the value if present, otherwise the default. The default is an ordinary argument, evaluated before the call.

Bitwise operators treat integers as bit patterns. Shifts are logical for unsigned and arithmetic for signed values, and shift counts must stay within the type width.

The four core patterns are set, clear, toggle, and test a bit. Clearing the lowest set bit, power-of-two tests, low-bit masks, field extraction, alignment rounding, and range toggling complete the repertoire.

Address-of, dereference, dot and arrow access, subscript, and casting are C's pointer and conversion operations, with unsafe casts confined to unsafe contexts.

Widening preserves meaning by sign or zero extension; narrowing truncates to low bits. sizeof reports a type's size in bytes as a compile-time constant.

Precedence follows C. Arithmetic is left-associative; assignment and the conditional are right-associative. Parenthesize masked and shifted comparisons on sight, and spell out flag tests.

The frame-header example gathers the family: casts, shifts, and masks pack and unpack fields; XOR folds a checksum; remainder cycles a ring; guarded division computes a rate; and the ternary and short-circuit AND make one-line decisions.

Coral has no operator overloading. Operators are fixed for primitives; composite types use named methods such as add, compare, eq, and equals. The tradeoff is verbosity for numerical code in exchange for clarity and a small language.
