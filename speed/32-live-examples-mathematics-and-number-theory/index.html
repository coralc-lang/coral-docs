Live Examples: Mathematics and Number Theory

The Arithmetic Nobody Hands You

Coral's standard library has no primes module, no gcd, no fast power, and no binomial coefficient. std::math binds the C math library: sqrt, pow, exp, log, sin, cos, pi, e, clamping and interpolation helpers, and random generators. It knows nothing about integers or modular exponentiation.

That is normal. Number theory appears in hashing, checksums, cryptography, hash-table sizing, load balancing, identifier validation, and game seeding, none of it an API call. It is a handful of dozen-line algorithms, each with a cost and a range where it quietly fails.

This chapter works through fourteen such algorithms, starting from the obvious method and improving it where worthwhile. Each example gives the problem, why the obvious approach is slow, the implementation, the cost, the edge cases, and a variation.

Machine integers wrap. A u64 holds zero through 18,446,744,073,709,551,615 and then wraps to zero; an i64 wraps at about 9.2 quintillion either side. The language does not check every operation, since that is costly and hashing often wants the wraparound. You must prove your arithmetic stays in range.

Is This Number Prime?

The problem

Decide whether a whole number is prime, meaning its only divisors are one and itself.

The intuition

Trying every divisor from 2 to n−1 is correct but hopeless for large n. You only need candidates up to the square root: if n = a * b with both factors greater than one, at least one factor is at most the square root.

The approach

Show brute force, then the square-root bound, then the wheel: after handling two and three, every prime candidate is 6k − 1 or 6k + 1, so the loop steps by six and tests two offsets. That cuts the work by a further factor of three.

The implementation.

pub bool isPrimeBrute(u64 n) {
    // 0 and 1 are not prime
    if (n < 2) return false;
    // try every candidate divisor
    u64 d = 2;
    while (d < n) {
        // found a divisor: composite
        if (n % d == 0) return false;
        // next candidate
        d += 1;
    }
    return true;
}

pub bool isPrime(u64 n) {
    if (n < 2) return false;
    if (n < 4) return true;            // 2 and 3 are prime
    // even numbers above two are composite
    if (n % 2 == 0) return false;
    if (n % 3 == 0) return false;

    // test 6k-1 and 6k+1 only
    u64 i = 5;
    while (i <= n / i) {               // i*i avoids overflow
        if (n % i == 0) return false;
        if (n % (i + 2) == 0) return false;
        // wheel: skip multiples of two and three
        i += 6;
    }
    return true;
}

The natural bound while (i * i <= n) overflows near the top of u64: i * i wraps to a small number, so the loop runs forever or tests nonsense. i <= n / i says the same thing without a product that can overflow. Compare against the quotient, not the square.

Cost and notes

Brute force is O(n) divisions; the square-root version and the wheel are O(sqrt n), the wheel with a smaller constant. None scales to cryptographic sizes, which is why public-key cryptography exists. For hundred-digit primes, use Miller-Rabin instead.

Edge cases

Zero and one are not prime, handled by the guard. Negative inputs are impossible because the type is u64. Two and three are handled before the even check, which would otherwise reject two. The overflow-safe bound matters above about four billion.

Variation

Return the smallest divisor as Option<u64>: None for prime, Some(d) for composite. This is the shape the factorisation example (31.8) needs.

The Sieve of Eratosthenes

The problem

Produce every prime below a limit, not just test one number. Testing each with isPrime is the wrong tool when you need many primes.

The intuition

Mark composites all at once. Write down 2 through the limit; two is prime, so cross out its multiples; the next survivor is prime, cross out its multiples; stop at the square root of the limit. The work is per multiple, not per number.

The approach

Two versions: a byte vector for clarity, then std::collections::bitset, the honest structure for a dense range of yes-or-no answers.

The implementation, byte version.

import(lib) std::vec { Vec };

pub Vec<u64> sieve(u64 limit) {
    // collected primes
    Vec<u64> primes = Vec<u64>::new();
    // nothing below two
    if (limit < 2) return primes;

    Vec<u8> composite = Vec<u8>::withCap((usize)(limit + 1));
    // all candidates start unmarked
    for (u64 i = 0; i <= limit; i += 1) composite.push(0);

    for (u64 p = 2; p <= limit / p; p += 1) {
        // p is composite already
        if (composite.at((usize)p) != 0) continue;
        // mark multiples from p*p
        for (u64 multiple = p * p; multiple <= limit; multiple += p)
            composite.set((usize)multiple, 1);
    }

    // whatever survived the marking passes is prime
    for (u64 i = 2; i <= limit; i += 1)
        if (composite.at((usize)i) == 0) primes.push(i);
    return primes;
}

The inner loop starts at p * p, not at 2 * p, and that is why the sieve is fast. Every multiple of p below p * p has a smaller prime factor that already crossed it out, so starting at the square is part of the algorithm.

The implementation, bitset version.

import(lib) std::vec { Vec };
import(lib) std::collections::bitset { Bitset };

pub Vec<u64> sieveBits(u64 limit) {
    Vec<u64> primes = Vec<u64>::new();
    if (limit < 2) return primes;

    // one bit per number
    Bitset composite = Bitset::new(limit + 1);
    for (u64 p = 2; p <= limit / p; p += 1) {
        // a smaller prime already crossed p
        if (composite.test(p)) continue;
        // mark the multiples of p
        for (u64 multiple = p * p; multiple <= limit; multiple += p)
            composite.set(multiple);
    }

    // every still-clear bit is a prime
    for (u64 i = 2; i <= limit; i += 1)
        if (!composite.test(i)) primes.push(i);
    return primes;
}

The bitset uses one bit per number instead of one byte, an eight-fold saving, and bit operations are single instructions. For a million numbers that is 125 kilobytes instead of a megabyte, the difference between fitting in cache and streaming.

Cost and notes

The marking work is O(n log log n), famously close to linear, which is why the sieve embarrasses per-number tests. Space is O(n) bytes, or O(n/8) with the bitset. For a million, the sieve finishes in the time one stubborn isPrime call takes.

Edge cases

A limit below two produces an empty list. limit + 1 allocates the slot for index limit; forgetting the plus-one is an out-of-bounds trap. The bitset rounds up to whole 64-bit words and asserts that indices are in range.

Variation

Build a smallest-prime-factor table: a Vec<u64> where entry i holds the smallest prime dividing i. It is the same sieve with one extra assignment and powers fast factorisation.

Greatest Common Divisor, and the Trap in Least Common Multiple

The problem

Find two integers' greatest common divisor (the largest number dividing both) and least common multiple (the smallest number both divide).

The intuition

Factoring both numbers is slow. Euclid's insight: any common divisor of a and b divides a - k*b, so the common divisors are exactly those of b and a mod b. Replace the pair until the remainder is zero; the last nonzero remainder is the answer.

The approach

Iterative Euclid for the GCD, then the LCM. The formula lcm(a, b) = a * b / gcd(a, b) overflows when the product exceeds the type even though the answer fits, so divide before multiplying.

The implementation.

pub u64 gcd(u64 a, u64 b) {
    // Euclidean step until the remainder is zero
    while (b != 0) {
        // new remainder
        u64 t = a % b;
        // shift the pair along
        a = b;
        b = t;
    }
    return a;
}

pub u64 lcm(u64 a, u64 b) {
    // no LCM with zero
    if (a == 0 || b == 0) return 0;
    return (a / gcd(a, b)) * b;      // divide first, then multiply
}

pub i64 gcdSigned(i64 a, i64 b) {
    // sign is irrelevant to divisibility
    if (a < 0) a = -a;
    if (b < 0) b = -b;
    return (i64)gcd((u64)a, (u64)b);
}

Cost and notes

Euclid takes O(log(min(a, b))) remainder steps, at most a couple of dozen for u64, with consecutive Fibonacci numbers as the worst case. gcdSigned takes absolute values first, since sign is irrelevant; negating the most negative i64 overflows, so the unsigned path is safer.

Edge cases

gcd(0, 0) is zero and gcd(0, n) is n. LCM returns zero if either input is zero. Divide-before-multiply is not style: with a = 2^32 and b = 2^32 - 2, the product overflows u64 while the true LCM fits, silently giving a wrong answer.

Variation

Extended Euclid returns the GCD g and coefficients x, y with a*x + b*y = g. When g is one, x is the modular inverse, without needing Fermat's little theorem or a prime modulus.

Modular Arithmetic and Fast Exponentiation

The problem

Compute base raised to exp, modulo m, without forming the full power. This underlies public-key cryptography, rolling hashes, pseudorandom sequences, and divisibility tricks.

The intuition

Reduce after every multiplication: (a * b) mod m = ((a mod m) * (b mod m)) mod m, so no value exceeds m. Exponentiation by squaring reads the exponent's bits, squares at every step, and multiplies into the result when the bit is one, turning an exp-step loop into log exp.

The approach

Reduce the base, then walk the exponent's bits from the bottom with u64, noting the multiplication caveat.

The implementation.

pub u64 modPow(u64 base, u64 exp, u64 m) {
    // mod one, every value is zero
    if (m == 1) return 0;
    // product of the selected powers
    u64 result = 1;
    // reduce the base first
    base %= m;
    while (exp > 0) {
        // this exponent bit is set
        if ((exp & 1u) == 1u)
            result = (result * base) % m;
        // move to the next bit
        exp >>= 1;
        // square to reach the next power of two
        base = (base * base) % m;
    }
    return result;
}

(result * base) % m is correct only while the product fits the type, so m must be at most about four billion, the square root of the u64 maximum. For larger moduli, multiply by doubling and repeated addition, reducing at each step:

pub u64 mulMod(u64 a, u64 b, u64 m) {
    u64 result = 0;
    a %= m;
    while (b > 0) {
        // this bit of b is set
        if ((b & 1u) == 1u) {
            // accumulate a by repeated addition
            result = (result + a) % m;
        }
        // double a for the next bit
        a = (a * 2u) % m;
        // move to the next bit of b
        b >>= 1;
    }
    return result;
}

With mulMod, replace every result * base and base * base in modPow with a mulMod call. The algorithm is then correct for the full u64 range, at a cost of about sixty-four times the speed.

Cost and notes

modPow does one or two modular multiplications per exponent bit: O(log exp) steps, each O(1) while the modulus is small. mulMod makes each O(log m), so the full-range version is O(log exp * log m). The small-modulus version is the common case.

Edge cases

Modulus one means every value is zero, so return early. A base larger than the modulus is reduced first. Exponent zero returns one, the conventional value even for base zero. The naive modulus overflow is why mulMod earns its place.

Variation

Write modInverse with the extended Euclid from 31.3, returning None exactly when the base shares a factor with the modulus. Test it by checking (a * aInv) % m == 1 over a range of inputs.

Factorials, and Where Machine Integers Surrender

The problem

Compute n!, the product of one through n. It appears in combinatorics and series expansions and outgrows fixed-width types almost immediately.

The intuition

20! is about 2.4 quintillion, just inside u64, and 21! wraps silently. The interesting part is honesty: detect the overflow and report it, compute a floating-point approximation, or compute log(n!) as a sum to avoid huge integers.

The approach

A checked integer version returning bool and writing through a pointer, then the logarithm version for factorials used as intermediate values.

The implementation.

import(lib) std::math::math { log, exp, pi };

pub bool factorial(u64 n, u64* out) {
    // 0! and 1! are one
    u64 result = 1;
    for (u64 i = 2; i <= n; i += 1) {
        if (result > 0xFFFFFFFFFFFFFFFFu / i) return false;   // would overflow
        // safe now: no overflow
        result *= i;
    }
    // write the answer through the pointer
    *out = result;
    return true;
}

pub f64 logFactorial(u64 n) {
    // summing logs avoids huge integers
    f64 sum = 0.0;
    for (u64 i = 2; i <= n; i += 1) sum += log((f64)i);
    return sum;
}

// Stirling's approximation: n! ~ sqrt(2*pi*n) * (n/e)^n
pub f64 logFactorialStirling(u64 n) {
    if (n < 2) return 0.0;
    f64 fn = (f64)n;
    return 0.5 * log(2.0 * pi * fn) + fn * (log(fn) - 1.0);
}

The overflow test is the pattern to memorise: before multiplying, compare the running result with the largest value divided by the factor. If result exceeds MAX / i, stop. Testing after multiplication is useless, because the product has already wrapped.

Cost and notes

The checked version is O(n) multiplications and never lies. Sum-of-logs is O(n) calls to log, slower but usable where integers fail; Stirling is a cheap constant-time approximation. Use exact integers for small exact counts, logarithms for large probabilities and ratios.

Edge cases

0! is one because the loop starts at two. The checked version rejects 21! and beyond. The logarithm version accumulates error slowly but must never be compared for exact equality. Stirling is approximate; never use it for equality.

Variation

Write binomialProbability(n, k, p) using logFactorial, computing the coefficient and the powers in log space and exponentiating once. It handles n in the thousands without forming a factorial.

Fibonacci: Naive, Linear, and Fast

The problem

Compute the nth Fibonacci number, with each the sum of the two before it, starting one and one.

The intuition

The direct recursion fib(n) = fib(n-1) + fib(n-2) recomputes subproblems; fib(40) makes about a billion calls. The iterative fix remembers the last two values, linear time and constant space. The fast version treats a step as a two-by-two matrix multiplication, exponentiated by squaring, or uses fast doubling.

The approach

Show all three: the definition, the obvious repair, and the linear-map exponentiation.

The implementation.

pub u64 fibNaive(u64 n) {
    // fib(0) = 0, fib(1) = 1
    if (n < 2) return n;
    return fibNaive(n - 1) + fibNaive(n - 2);
}

pub u64 fibIterative(u64 n) {
    // fib(i) ...
    u64 a = 0;
    // ... and fib(i+1)
    u64 b = 1;
    for (u64 i = 0; i < n; i += 1) {
        // advance the pair one step
        u64 next = a + b;
        a = b;
        b = next;
    }
    return a;
}

// fast doubling: fib(2k) = fib(k) * (2*fib(k+1) - fib(k))
//                fib(2k+1) = fib(k)^2 + fib(k+1)^2
struct Pair { u64 first; u64 second; }

Pair fibPair(u64 n) {
    if (n == 0) return Pair { .first = 0, .second = 1 };
    // recurse on half; the identities jump ahead
    Pair half = fibPair(n / 2);
    u64 a = half.first;
    u64 b = half.second;
    u64 c = a * (2 * b - a);      // fib(2k)
    u64 d = a * a + b * b;        // fib(2k+1)
    // even n uses c; odd n shifts to d
    if (n % 2 == 0) return Pair { .first = c, .second = d };
    return Pair { .first = d, .second = c + d };
}

pub u64 fibFast(u64 n) {
    return fibPair(n).first;
}

Cost and notes

fibNaive is O(phi^n) time and O(n) stack. fibIterative is O(n) time and O(1) space, and is almost always what you should write. fibFast is O(log n) time and O(log n) stack, useful when n is astronomical and you work modulo something.

Edge cases

The 0, 1 and 1, 1 conventions differ by an index; this code uses 0, 1, so fib(0) = 0 and fib(10) = 55. All three overflow past fib(93) on u64; the fast version overflows too because the values are too large. In practice it runs modulo a prime.

Variation

Rewrite fibFast to take a modulus and reduce after every multiplication, then check it against fibIterative for small n.

Combinations: Choosing Without Overcounting

The problem

Compute "n choose k", the number of ways to pick k items from n without regard to order.

The intuition

n! / (k! * (n - k)!) overflows even when the answer is small, because it forms huge factorials before cancelling. Writing the ratio as (n - k + 1)/1 * (n - k + 2)/2 * ... * n/k keeps every intermediate value a smaller binomial coefficient, hence a whole number.

The approach

Use C(n, k) = C(n, n - k) to multiply fewer terms, and keep multiply and divide in the right order.

The implementation.

pub u64 choose(u64 n, u64 k) {
    // choosing more than exist is impossible
    if (k > n) return 0;
    if (k > n - k) k = n - k;          // symmetry: fewer factors

    // running binomial coefficient
    u64 result = 1;
    for (u64 i = 1; i <= k; i += 1) {
        result = result * (n - k + i) / i;   // exact at each step
    }
    return result;
}

Why is each step exact? After i steps the running value is C(n - k + i, i), a binomial coefficient and therefore a whole number, so the division leaves no remainder. That is a specific property of this formula, not a general license; a defending comment is worth more than the code.

Cost and notes

O(min(k, n - k)) multiplications and divisions on u64. For k near n/2 the answer overflows before the loop ends: C(67, 33) already exceeds u64. Use chooseMod or a Pascal's-triangle table at scale.

Edge cases

k > n returns 0. k == 0 and k == n return 1 via zero loop iterations. The symmetry line must run before the loop and use n - k after the guard so it never underflows. Test the exactness against Pascal's triangle for n below twenty.

Variation

Implement pascalRow(n) returning the nth row by successive addition, and use it to check choose(n, k) for every valid k.

Prime Factorisation

The problem

Write a number as a product of primes, such as 360 = 2^3 * 3^2 * 5. This is the inverse of primality and underpins fraction simplification and much recreational mathematics.

The intuition

Divide out the smallest prime, then the next, and keep going. Once every prime up to the square root of the remaining number is removed, what remains is prime, so no primality test is needed. Precomputing smallest prime factors makes repeated factorisation a table lookup.

The approach

A direct trial-division factoriser with no setup, then a smallest-prime-factor table for repeated work.

The implementation.

import(lib) std::vec { Vec };

pub Vec<u64> factorise(u64 n) {
    // collected prime factors
    Vec<u64> factors = Vec<u64>::new();
    // 0 and 1 have no prime factors
    if (n < 2) return factors;

    // strip every factor of two
    while (n % 2 == 0) { factors.push(2); n /= 2; }
    // then odd trial divisors
    u64 f = 3;
    // overflow-safe square-root bound
    while (f <= n / f) {
        // divide out every copy of f
        while (n % f == 0) { factors.push(f); n /= f; }
        // only odd divisors remain
        f += 2;
    }
    if (n > 1) factors.push(n);       // what remains is prime
    return factors;
}

// smallest prime factor table, built like the sieve
pub Vec<u64> smallestPrimeFactors(u64 limit) {
    Vec<u64> spf = Vec<u64>::withCap((usize)(limit + 1));
    // spf[i] will hold i's smallest prime factor
    for (u64 i = 0; i <= limit; i += 1) spf.push(0);
    for (u64 i = 2; i <= limit; i += 1) {
        // i is composite already
        if (spf.at((usize)i) != 0) continue;
        for (u64 j = i; j <= limit; j += i)
            // only the first (smallest) prime to reach j is recorded
            if (spf.at((usize)j) == 0) spf.set((usize)j, i);
    }
    return spf;
}

pub void factoriseUsing(const Vec<u64>* spf, u64 n) {
    // peel one prime factor at a time
    while (n > 1) {
        // smallest prime dividing n
        u64 p = spf->at((usize)n);
        println("{}", p);
        // divide it out
        n /= p;
    }
}

Cost and notes

The direct factoriser is O(sqrt n) divisions in the worst case, when n is prime, and less when n has small factors. The table costs O(n log log n) once, then factors any number up to the limit in O(log n) steps. Build the table only if you will factor many numbers.

Edge cases

Numbers below two factor into an empty list. The inner while keeps dividing, so 8 produces three twos. The f += 2 loop skips even divisors, which is safe because two was handled first. The final if (n > 1) catches a large prime left over.

Variation

Return factors grouped with exponents as pairs (prime, power), so 360 prints as 2^3 * 3^2 * 5. The grouping is a short pass over the flat list.

Floating-Point Pitfalls

The problem

f64 arithmetic is not real arithmetic: 0.1 + 0.2 is not 0.3, addition is not associative, and x != x is true for NaN. This section is a set of habits for avoiding surprises.

The intuition

An f64 stores 53 bits of mantissa, and most decimal fractions have no exact binary representation, so stored 0.1 is slightly off and errors accumulate. Never compare floats for exact equality; use a tolerance, remember operations are not associative, and treat NaN as poisoning comparisons.

The approach

Provide absolute and relative tolerance helpers, and demonstrate the traps with small functions that make failures visible.

The implementation.

import(lib) std::math::math { fabs, maxF64, isNan, isFinite };

pub bool nearlyEqualAbs(f64 a, f64 b, f64 eps) {
    // absolute difference within tolerance
    return fabs(a - b) <= eps;
}

pub bool nearlyEqualRel(f64 a, f64 b, f64 eps) {
    // scale by the larger magnitude
    return fabs(a - b) <= eps * maxF64(fabs(a), fabs(b));
}

// Absolute tolerance fails for large magnitudes; relative fails near zero.
// The combined test uses relative when the values are large and absolute
// when they are near zero.
pub bool nearlyEqual(f64 a, f64 b, f64 eps) {
    // try the absolute test first
    f64 diff = fabs(a - b);
    if (diff <= eps) return true;
    f64 scale = maxF64(fabs(a), fabs(b));
    // fall back to relative
    return diff <= eps * scale;
}

pub void demonstrate() {
    // not exactly 0.3 in binary
    f64 a = 0.1 + 0.2;
    println("{}", a);                        // 0.30000000000000004
    println("{}", a == 0.3);                 // false
    println("{}", nearlyEqual(a, 0.3, 1e-9)); // true

    // a NaN value
    f64 nan = 0.0 / 0.0;
    println("{}", isNan(nan));               // true
    println("{}", nan == nan);               // false, the only value not equal to itself
    println("{}", nan < 1.0);                // false
    println("{}", nan > 1.0);                // false
}

Cost and notes

The helpers cost almost nothing. The conceptual costs matter: addition and multiplication are not associative, so careful code uses a consistent order and Kahan summation; catastrophic cancellation occurs when nearly equal large numbers are subtracted; pow and exp are approximations, so equal expressions can differ in the last bits.

Edge cases

NaN is unequal to everything, including itself; check with isNan, never ==. Infinity is a real value, and isFinite identifies ordinary numbers. Negative zero compares equal to positive zero but has a different bit pattern. The relative helper can divide by zero, which is why the combined version checks absolute tolerance first.

Variation

Write sumStable using Kahan compensated summation and compare it with a naive loop on values mixing very large and very small magnitudes. The naive sum loses the small values; the compensated sum keeps a correction that recovers them.

The Extended Euclidean Algorithm and Modular Inverse

The problem

Find the GCD g of a and b and coefficients x, y with a*x + b*y = g. When g is one, x is the modular inverse of a modulo b, needed whenever you divide modulo a prime.

The intuition

Euclid replaces (a, b) with (b, a mod b) until the remainder is zero. Each remainder is a whole-number combination of its producers, so the final remainder is a combination of a and b. Then a*x + b*y = 1 means a*x ≡ 1 (mod b).

The approach

Run the Euclidean loop on three columns at once: remainders, a-coefficients, and b-coefficients. At the end, normalise the sign so the gcd is non-negative and the inverse lies in [0, m).

The implementation.

pub struct GcdResult { u64 g; i64 x; i64 y; }

pub GcdResult extendedGcd(i64 a, i64 b) {
    // remainders, oldR leading
    i64 oldR = a;
    i64 r = b;
    i64 oldS = 1;
    i64 s = 0;                     // coefficients of a
    i64 oldT = 0;
    i64 t = 1;                     // coefficients of b

    while (r != 0) {
        // quotient for this step
        i64 q = oldR / r;

        // new remainder
        i64 tmp = oldR - q * r;
        oldR = r;
        r = tmp;

        // update the a-coefficient
        tmp = oldS - q * s;
        oldS = s;
        s = tmp;

        // update the b-coefficient
        tmp = oldT - q * t;
        oldT = t;
        t = tmp;
    }

    // the gcd is not uniquely signed; make it non-negative
    if (oldR < 0) { oldR = -oldR; oldS = -oldS; oldT = -oldT; }
    return GcdResult { .g = (u64)oldR, .x = oldS, .y = oldT };
}

pub Option<u64> modInverse(u64 a, u64 m) {
    // the returned x is the inverse when the gcd is one
    GcdResult r = extendedGcd((i64)(a % m), (i64)m);
    if (r.g != 1) return Option<u64>::None;         // no inverse exists
    // may be negative
    i64 inv = r.x % (i64)m;
    if (inv < 0) inv += (i64)m;                     // normalise into [0, m)
    return Option<u64>::Some { .value = (u64)inv };
}

The three rows march together. oldR/r are the Euclid pair; oldS/s track how much of a is in the remainder; oldT/t do the same for b. When the loop stops, oldR is the gcd and oldS, oldT are the coefficients. Trace (240, 46) by hand once.

Cost and notes

The same length as plain Euclid: O(log min(a, b)) iterations, each a division and a few arithmetic operations, all O(1) on machine words. modInverse adds one normalisation. This is cheaper and more general than Fermat's little theorem, which needs a prime modulus and a full modular exponentiation.

Edge cases

gcd(0, 0) is zero, with no inverse. A shared factor makes the gcd exceed one, so the function returns None. r.x % (i64)m lies in (-m, m); the if (inv < 0) line moves it into [0, m). Casting m to i64 is safe only below 2^63.

Variation

Use extendedGcd to solve a*x + b*y = c: a solution exists exactly when c divides the gcd, and one solution is the gcd solution scaled by c / g. Add k * (b / g) to x and subtract k * (a / g) from y for the general solution.

Euler's Totient Function

The problem

Count the whole numbers from one to n that share no factor with n. This is Euler's totient, phi(n), used in choosing hash-table moduli, in multiplicative groups, and in Euler's theorem.

The intuition

Count by exclusion: n / p numbers below n are divisible by a prime factor p. Inclusion and exclusion collapse to phi(n) = n * (1 - 1/p1) * (1 - 1/p2) * ... over distinct prime factors, so the totient needs only factorisation.

The approach

For one n, factor by trial division and fold each distinct prime in with result -= result / p. For all n up to a limit, use a sieve seeded with i and scaled by each prime.

The implementation.

import(lib) std::vec { Vec };

pub u64 eulerPhi(u64 n) {
    if (n == 0) return 0;
    // start with n and scale down
    u64 result = n;
    // trial divisor
    u64 p = 2;
    // up to sqrt of the shrinking n
    while (p <= n / p) {
        if (n % p == 0) {
            while (n % p == 0) n /= p;        // remove every copy of p
            result -= result / p;             // result *= (p - 1) / p
        }
        p += 1;
    }
    if (n > 1) result -= result / n;          // a large prime left over
    return result;
}

pub Vec<u64> totientTable(u64 limit) {
    Vec<u64> phi = Vec<u64>::withCap((usize)(limit + 1));
    // seed phi[i] = i
    for (u64 i = 0; i <= limit; i += 1) phi.push(i);

    for (u64 p = 2; p <= limit; p += 1) {
        if (phi.at((usize)p) == p) {          // p is prime: nothing scaled it
            // scale every multiple of the prime
            for (u64 multiple = p; multiple <= limit; multiple += p)
                phi.set((usize)multiple,
                        phi.at((usize)multiple) - phi.at((usize)multiple) / p);
        }
    }
    return phi;
}

result -= result / p is the integer form of result = result * (p - 1) / p, with no fractions. The sieve's prime test is a gem: entry p still equals p exactly when no smaller prime has scaled it, so no separate sieve is needed.

Cost and notes

eulerPhi is O(sqrt n) divisions in the worst case, using the overflow-safe p <= n / p bound. totientTable is O(n log log n), like the sieve, and answers phi(n) in O(1) within the limit. Use the single function for one value and the table for many.

Edge cases

phi(1) is one because the loop body never runs, and phi(0) is conventionally zero. The inner while must strip every copy of p, or the formula applies the same prime twice. The leftover-prime line catches a large surviving factor. The sieve uses usize indices while arithmetic stays in u64, so casts are required.

Variation

Verify that the sum of phi(d) over every divisor d of n equals n, for n up to a few thousand, using the sieve and the single function. That identity is why totients appear in group theory.

Integer Square Root by Newton's Method

The problem

Given a u64, find the largest integer whose square does not exceed it. The library's sqrt returns f64, which has only 53 bits of precision and cannot distinguish adjacent integers above about nine quadrillion.

The intuition

Newton's method follows the tangent line. For f(x) = x^2 - n, the update is x = (x + n / x) / 2, averaging the guess with n divided by it. Starting above the root, integer guesses descend onto the floor in about log(log n) steps.

The approach

Start from the first power of two above the root, then iterate until the guess stops falling. Write the update so it never forms a square that could overflow.

The implementation.

u64 bitLength(u64 n) {
    u64 bits = 0;
    // shift out one bit per step
    while (n != 0) { n >>= 1; bits += 1; }
    return bits;
}

pub u64 isqrt(u64 n) {
    // 0 and 1 are their own roots
    if (n < 2) return n;
    u64 x = (u64)1 << ((bitLength(n) + 1) / 2);   // a power of two at or above sqrt(n)
    while (true) {
        // Newton step, division only
        u64 y = (x + n / x) / 2;
        if (y >= x) return x;                     // stopped moving down
        x = y;
    }
}

pub bool isPerfectSquare(u64 n) {
    // integer square root first
    u64 r = isqrt(n);
    if (r == 0) return true;                      // n is zero
    // avoids r*r overflow
    return n / r == r && n % r == 0;
}

The starting guess matters. Beginning at n itself overflows on the first update for n near the u64 maximum, because x + n / x wraps. A power of two just above the root keeps every intermediate sum below twice the root.

Cost and notes

Each iteration roughly halves the wrong bits, so the loop runs about log2(log2(n)) times, five or six for any u64. The divide-only update never computes x * x, which would sit at the type's edge near the maximum root.

Edge cases

isqrt(0) and isqrt(1) return themselves before the loop. The loop returns on y >= x, not y == x: below the root the sequence is monotone downward, so the first failure to decrease means x is the floor. isPerfectSquare checks division and remainder rather than r * r, for the same overflow reason.

Variation

Write icbrt(n) for the integer cube root with x = (2*x + n / (x*x)) / 3, starting one power of three above, and use it to test perfect cubes. Only the derivative in the update changes.

Base Conversion

The problem

Print an integer in a base up to thirty-six, or parse a string of digits in such a base. The I/O format specifiers cover common cases, but general conversion and parsing are yours to write.

The intuition

Decimal notation is a polynomial in the base: 123 means 1*10^2 + 2*10^1 + 3. To produce digits, divide by the base and peel off remainders from the least significant end, then reverse. To parse, start at zero and multiply by the base and add each digit. The directions are inverses.

The approach

One function turns a u64 into a String, using digits below ten and letters above; another folds a str back into a u64, returning Option for malformed input.

The implementation.

import(lib) std::text::string { String };

u8 digitChar(u64 d) {
    // 0-9 map to digit characters
    if (d < 10) return (u8)((u8)'0' + (u8)d);
    // 10-35 map to letters
    return (u8)((u8)'a' + (u8)(d - 10));
}

u64 digitValue(u8 c) {
    // a decimal digit
    if (c >= (u8)'0' && c <= (u8)'9') return (u64)(c - (u8)'0');
    // uppercase letters
    if (c >= (u8)'A' && c <= (u8)'Z') return (u64)(c - (u8)'A') + 10;
    // lowercase letters
    return (u64)(c - (u8)'a') + 10;
}

pub String toBase(u64 n, u32 base) {
    @assertOut(base >= 2u && base <= 36u, "base must lie in [2, 36]");
    // zero is "0" in every base
    if (n == 0) return String::from("0");

    u64 b = (u64)base;
    String out = String::new();
    while (n > 0) {
        // remainder is the next digit
        out.pushChar(digitChar(n % b));
        // move to the next position
        n /= b;
    }
    out.reverse();                 // digits came out least-significant first
    return out;
}

pub Option<u64> fromBase(str s, u32 base) {
    // empty input is not a number
    if (s.len == 0) return Option<u64>::None;
    // base out of range
    if (base < 2u || base > 36u) return Option<u64>::None;

    u64 b = (u64)base;
    // running value
    u64 value = 0;
    for (usize i = 0; i < s.len; i += 1) {
        u8 c = s.at(i);
        // reject characters outside 0-9/a-z/A-Z
        bool known = (c >= (u8)'0' && c <= (u8)'9') ||
                     (c >= (u8)'a' && c <= (u8)'z') ||
                     (c >= (u8)'A' && c <= (u8)'Z');
        if (!known) return Option<u64>::None;
        // turn the character into a digit
        u64 d = digitValue(c);
        // digit too large for this base
        if (d >= b) return Option<u64>::None;
        // shift left by one base and add
        value = value * b + d;
    }
    return Option<u64>::Some { .value = value };
}

digitValue trusts that the caller checked the character class; fromBase does that check, so the helper stays small. Lower and upper case both parse, so 0xFF and 0xff agree.

Cost and notes

Both directions are O(number of digits), one division or multiply-add per digit. The string allocation dominates. For fixed-width output such as a byte in hex, the format specifiers are shorter and faster; this pair is for runtime bases and parsing.

Edge cases

Zero is "0" in every base, handled before the loop. fromBase returns None for empty input, an out-of-range base, an unknown character, or a digit too large for the base. Overflow is quiet: value * b + d can wrap; a checked version compares against (U64_MAX - d) / b first.

Variation

Write convert(s, fromBase, toBase) to parse in one base and print in another, and add a leading - sign by handling it separately and negating.

Big-Integer Addition with Strings

The problem

Add two whole numbers too large for any machine integer, supplied as decimal strings. A hundred-digit number has no u64 representation but fits in a String, and this is the first step of arbitrary-precision arithmetic.

The intuition

This is school addition: line the numbers up on the right, add column by column, and carry. Columns are string positions from the end. A carry is at most one, so a column sum never exceeds nineteen, and the answer is at most one digit longer.

The approach

Walk both strings backward with two indices, accumulate the carry, push each result digit, then reverse. The while continues while either index is in range or a final carry remains, which handles the extra leading digit.

The implementation.

import(lib) std::text::string { String };

// char digit to numeric value
u64 decimalDigit(u8 c) { return (u64)(c - (u8)'0'); }

pub String addBig(str a, str b) {
    @assertOut(a.len > 0 && b.len > 0, "addBig needs two non-empty numbers");

    // result digits, least-significant first
    String out = String::new();
    // walk both strings from the right
    isize i = (isize)a.len - 1;
    isize j = (isize)b.len - 1;
    // carry into the next column
    u64 carry = 0;

    while (i >= 0 || j >= 0 || carry > 0) {
        // the column starts with the carry
        u64 sum = carry;
        // add a's digit if in range
        if (i >= 0) { sum += decimalDigit(a.at((usize)i)); i -= 1; }
        // add b's digit if in range
        if (j >= 0) { sum += decimalDigit(b.at((usize)j)); j -= 1; }
        // store the column sum modulo ten
        out.pushChar((u8)((u8)'0' + (u8)(sum % 10)));
        // carry the tens onward
        carry = sum / 10;
    }
    // digits came out least-significant first
    out.reverse();
    return out;
}

The two working lines are out.pushChar(... sum % 10) and carry = sum / 10; the rest is index bookkeeping. The reverse is required, because digits are discovered least significant first.

Cost and notes

O(max(len(a), len(b))) time and space, one pass with no nested loops, the fastest possible for this representation. Repeated addition costs O(total digits); feed the running result back as an operand. Multiplication is the next step, at O(len(a) * len(b)) with the same grade-school structure.

Edge cases

Both operands must be non-empty; the assertion refuses an empty string. A stray non-digit silently gives a wrong answer, so validate and return a Result. Leading zeros are accepted but never produced except for a single zero; carry > 0 grows "99" + "1" to "100".

Variation

Write multiplyBig(a, b) by summing shifted partial products: multiply a by each digit of b with carry, then add the results with trailing zeros. Test it against u64 multiplication for small operands.
