Speed Edition · Chapter 11

Memory Management

The Hard Truth

Every program moves bytes: it lays them out, reads and writes them, and returns them when done. How that return happens is a language's most consequential decision, and Coral hands you that decision.

Memory is acquired and released explicitly, through a small set of primitives and policies. defer guarantees a release at block exit, and the smart pointer types make ownership part of the type. The compiler refuses implicit conversions, runs comptime checks before the program exists, and keeps the model small enough to hold in your head.

From a garbage-collected language, release is now your job, written where you can see it; everything about objects and references still applies. From C, allocation and release stay your business, but pairing has a syntax, ownership has a type, and policy has names. This chapter covers regions, pointers, allocators, defer, smart pointers, compiler checks, and failure modes.

No Garbage Collector

A garbage collector scans memory, finds unreachable objects, and reclaims them. Coral rejects it on principle.

The rejection is about determinism. A collector reclaims when the program does not control it, so memory use climbs and drops in steps unrelated to the program's logic. A pause can miss a microsecond deadline, drop a frame, or exhaust a fixed embedded heap. The collector also spreads cost into every allocation and store.

Coral releases explicitly, immediately, and paired with acquisition. defer releases a resource as its block exits, and a smart pointer releases when its owner is disposed. There is no scan, pause, background thread, or hidden cost: memory returns to the allocator when the program wrote that it should.

A program that never forgets a release pays nothing beyond the release; one that forgets leaks, and the tooling finds the leak. Coral prefers a leak a tool can name over a pause no tool can remove.

The Three Regions: Stack, Heap, and Static

Memory lives in three places, decided by how a value was declared.

The stack is like trays: the newest comes off first, so a stack value lives as long as its call. The heap is a warehouse you sign for: you get an address and return it when done. The static region is poured before the program starts and unchanged until it ends.

The stack grows and shrinks with function calls. Each call pushes a frame holding parameters and locals, and the frame is popped on return. Stack allocation is nearly free because the space was reserved with the frame, and a stack value's lifetime is exactly that frame's lifetime, which is why most values live on the stack.

The heap is memory requested from the OS by the allocator and parceled out on demand. It holds values that must outlive a frame, whose count is unknown until runtime, or that must be shared. Heap allocation is slower because it must find a block of the right size, and it must be released when done.

The static region is memory the program owns before it starts: globals, constants, and machine code. Static memory is never allocated or freed. A string literal like "hello" lives in the binary, which is why a str view of it is always valid.

The region is visible in the code. A value declared without allocation lives on the stack; one requested from the allocator lives on the heap behind a pointer; one declared at module scope lives in the static region. Item item; chooses the stack; Item* item = alloc<Item>(1); chooses the heap. There is no fourth region.

A large local struct eats the small, fixed stack, while the same data on the heap is limited mainly by available memory. A function reading a gigabyte-long file allocates a heap buffer rather than a huge local array. The region decides both lifetime and capacity.

All three regions side by side:

coral
i32 local = 42;              // stack: dies when the call returns
i64* heap = alloc<i64>(1);   // heap: lives until dealloc
if (heap != null) { *heap = 7; dealloc<i64>(heap); }

The Pointer: The Raw View

A pointer holds an address, the location of another value. It is the raw view of memory. A pointer is written as the pointed-to type followed by *: i32*, str*, and i32** for a pointer to a pointer.

The ampersand takes a value's address; the asterisk follows a pointer to the value. ptr->field reaches a field through a pointer, while . accesses a field of a value directly. r.width is the width of r; p->width follows p to the struct and takes its width. The arrow is the dot after climbing the pointer.

coral
struct Rectangle {
    f64 width;
    f64 height;
}

pub extend Rectangle {
    f64 area() const { return self.width * self.height; }
}

Rectangle r = Rectangle { .width = 5.0, .height = 3.0 };
Rectangle* p = &r;
p->height = 4.0;
println("{}", p->area());

A pointer is exact: one address, not a range or handle. That is its power, since it costs nothing, and its danger, since the program must ensure the address still points at a live value. Every tool in this chapter exists for that responsibility.

A pointer is a house address on a card: the card is not the house, and following it is useful until the house is torn down and the address points at an empty lot.

A pointer has a type, and the compiler holds the program to it. An i32* points to an i32, and a const u8* points to bytes that must not be written. You cannot hand an i32* where a u64* is expected without a cast, and (u64*)p states that you know what you are doing.

Explicit Null

null is the pointer value that points at nothing. It is first-class and explicit: a pointer is either an address or null, and the code must say which it is using.

The classic pointer mistake is the null dereference, and Coral does not conjure null into places the program did not put it. A function returns null only where the code writes return null. When alloc<T> cannot satisfy a request it returns null, and callers check or have decided the allocation cannot fail.

coral
u8* buf = alloc<u8>(4096);
if (buf == null) {
    println("out of memory");
    return;
}

When absence is legitimate, Option<T> says so more strongly than a pointer that happens to be null. It forces inspection before unwrapping and is the type-safe spelling of may point at nothing; Chapter 15 develops it. Choose by type: Option<T> when the compiler should make you handle absence, a null check for raw machinery.

The Allocation Primitives

Heap memory is requested through the memory module in typed elements rather than raw bytes: you allocate ten u64s, not eighty anonymous bytes. The primitives live in std::mman, and alloc, dealloc, and realloc are available without an explicit import in ordinary code.

alloc<T>(count) requests space for count elements of T and returns a pointer, or null if count is zero or the allocator cannot satisfy it. dealloc<T>(ptr) returns a block to the allocator. realloc<T>(ptr, newCount) resizes an allocation; on success the original pointer may no longer be valid, so keep the returned one.

coral
u64* numbers = alloc<u64>(10);
if (numbers == null) return;

numbers[0] = 1;
numbers[1] = 1;
for (usize i = 2; i < 10; i += 1) {
    numbers[i] = numbers[i - 1] + numbers[i - 2];
}

numbers = realloc<u64>(numbers, 20);
dealloc<u64>(numbers);

The typed interface keeps the size right: the type parameter names the element type and the count names the number of elements, so no @sizeof multiplication is needed, and the returned pointer already has the right type. A raw malloc hands back an untyped pointer and requires casts and recomputation; alloc<u64> hands back a u64*.

alloc<u64>(10) means reserve room for ten u64 numbers. Because the kind is named in the call, the block comes back typed, so you cannot treat it as characters or addresses.

The module provides typed bulk operations: zero<T> fills a block with zero bytes, copy<T> copies elements, move<T> does the same when the blocks may overlap, and equal<T> compares blocks element by element.

coral
zero<u64>(numbers, 20);
copy<u64>(backup, numbers, 20);
if (equal<u64>(backup, numbers, 20)) println("identical");

The primitives are the vocabulary; every allocation policy in this chapter implements or wraps them.

The Allocator Abstraction

The primitives ask a global allocator, and the allocator is a value the program can replace. The Allocator type from std::allocator is a context pointer and three function pointers.

coral
pub struct Allocator {
    rawptr ctx;
    rawptr(rawptr, usize) alloc;
    void(rawptr, rawptr) free;
    rawptr(rawptr, rawptr, usize) realloc;
}

ctx is the allocator's private state: a region, a free list, a count. The three function pointers are its operations, each taking the context first. Any implementation can supply them, so a program can install a policy and every allocation flows through it. This is FILE* promoted to a full type.

The default allocator is installed by initDefaultAllocator and wraps malloc as an Allocator (libcAllocator); alloc<T> calls ensureDefaultAllocator first. The library also ships TLSF (std::tlsf), which finds a block in constant time, and mimalloc (std::mimalloc). Either can be installed. The choice is a value the program assigns.

Because allocation is a value, a program can wrap, count, confine, and change it, and the primitives need not know. The allocation strategy is a decision the program makes in code.

The Fixed Buffer Allocator

The fixed buffer allocator is the arena in its smallest form: a buffer handed in advance, a cursor, and nothing else. Each allocation checks whether the request fits; if it does, it returns the next aligned piece and advances the cursor.

coral
FixedBufferAllocator arena;
u8 backing[4096];
arena.init(backing, 4096);

Allocator a = arena.allocator();

The allocator never grows. When the buffer is full, allocations return null and the program decides what that means. Its hard bound is the buffer's size, and its cost is a compare and an add. It fits a known working set: a game frame, a request handler, a boot loader.

Resetting sets the used count to zero, abandoning all blocks at once, which is right when a whole batch dies together. remaining reports the space left so a program can check before a burst.

The Stack Fallback Allocator

The stack fallback allocator uses a small fixed buffer first and a general allocator when the buffer is exhausted. It is initialized with a fallback allocator and carries a one-kilobyte buffer inside the struct. Allocations try the buffer first; when it is full, the request goes to the fallback.

coral
StackFallbackAllocator sfa;
sfa.init(defaultAllocator);
Allocator a = sfa.allocator();

Most allocation requests in a well-written program are small and short-lived. The stack allocator serves those from its buffer with no heap round trip or thread contention, and only rare large or long-lived requests touch the general heap.

The Arena

The arena is the fixed buffer with growth. Like the fixed buffer, it hands out blocks from one contiguous region and advances a cursor, and freeing an individual block does nothing. Unlike the fixed buffer, when its region fills it asks its backing allocator for a larger region, moves its contents, and continues.

coral
ArenaAllocator arena;
arena.init(defaultAllocator, 4096);

Token* tokens = arena.pushType<Token>(256);
arena.reset();
arena.deinit();

push(size) requests a raw byte block, and pushType<T>(count) requests space for count elements of T and returns a typed pointer. reset abandons everything allocated since the last reset, remaining reports space left, and deinit returns the whole region to the backing allocator.

The arena fits batch-shaped work: a parser builds a tree that dies when its result is consumed, or a handler builds a response from pieces that die together. Allocation is a bump, release a single store.

Do not use an arena for data freed one piece at a time. It has no per-block free by design: reset abandons everything at once. If half a batch must outlive the other half, use the scoped allocator or the general heap. Match the allocator to the lifetime.

The Pool Allocator

The pool allocator handles fixed-size work. It is initialized with a source allocator, a block size, and a block count; it asks the source for one large region, slices it into blocks, and links them into a free list, each block beginning with a pointer to the next free one.

coral
PoolAllocator pool;
pool.init(defaultAllocator, @sizeof(Node), 1024);

rawptr n = pool.allocBlock();
pool.freeBlock(n);

Allocating pops the free-list head; freeing pushes it back. Both are a handful of instructions regardless of block count, and free blocks carry the list where their payload will go, so no per-block metadata is stored. The pool cannot grow: an empty free list means allocation fails, and the bound is explicit.

The library also provides Pool<T> in std::pool. It is built empty, grows its backing store when the free list runs dry, and hands out typed blocks:

coral
Pool<Node> pool = Pool<Node>::new();
Node* n = pool.acquire();     // null if the grow allocation failed
// ... use n ...
pool.release(n);
pool.dispose();

A pool fits a value created and destroyed many times with the same type and size: tree nodes, connection buffers, game objects. Reuse costs two pointer stores instead of an allocator round trip, and the small region stays in cache. Look here first when profiling shows allocation churn.

The Scoped Allocator

The scoped allocator remembers what it handed out so it can return it all in one call. It is initialized with a backing allocator and a capacity, and records every allocation's pointer and size. freeAll returns every pointer to the backing allocator, and deinit frees the records.

coral
ScopeAlloc scope;
scope.init(defaultAllocator, 1024);

rawptr buf = scope.alloc(256);
Header* h = scope.allocType<Header>(1);
scope.freeAll();
scope.deinit();

The scoped allocator is the manual defer discipline: the program decides when the batch is done and says so once. Each block is released through the backing allocator, so it fits when blocks must return to the general heap. bytesUsed reports tracked memory; after freeAll it is zero.

The Logging Allocator

The logging allocator counts. It wraps a parent allocator and records requested bytes, released bytes, outstanding bytes, and call counts in totalAlloced, totalFreed, currentUsed, allocCount, and freeCount, plus a tracking table of every outstanding pointer and size.

coral
LoggingAllocator logger;
logger.init(defaultAllocator);

Allocator a = logger.allocator();
rawptr p = a.alloc(a.ctx, 100);
a.free(a.ctx, p);

The logging allocator changes nothing about behavior; it only watches. Install it, run a representative workload, and check whether the outstanding count returns to the baseline. A currentUsed that does not return to zero is the leak, located by policy and quantified in bytes.

Because allocation is a value, observation is just another implementation of the same three function pointers. The production allocator and the leak-hunt allocator are two values of the same type, and the program cannot tell them apart.

Choosing an Allocator

The allocators are policies, and the right one depends on the shape of the allocation.

The fixed buffer fits a hard bound and known peak. The stack fallback fits mostly small, short-lived requests. The arena fits a batch that dies at once. The pool fits fixed-size churn. The scoped allocator fits a batch that must return blocks to the general heap. The general heap, libc or TLSF, fits everything else.

Match the allocator to the lifetime. General-purpose allocation is expensive for the bookkeeping that lets blocks of many sizes be freed individually in any order. The arena gives up individual frees and becomes a bump; the pool gives up general sizes and becomes a push and pop. The default is fine; the policies are the upgrade path.

defer: The Paired Release

Manual memory management means pairing every acquisition with a release that happens no matter how the code exits. defer makes the pair airtight.

A defer names a cleanup action for the current block. When the block exits, by falling off the end, returning, or any other path, the deferred action runs, in reverse order of the defers issued. The acquisition and release sit together, which makes the pair visible and correct.

coral
pub void processFile(str path) {
    Result<File, IoError> fo = fileOpen(path, "r");
    if (fo.isErr()) return;
    File f = fo.unwrap();
    defer fileClose(f);

    u8* buf = alloc<u8>(4096);
    if (buf == null) return;
    defer dealloc<u8>(buf);

    Result<isize, IoError> n = fileRead(f, buf, 4096);
    if (n.isOk()) handle(buf, n.unwrap());
}

Whatever happens after the two defer statements, the buffer is deallocated and the file is closed. They run in reverse order: the buffer is released first, then the file is closed, so the buffer never outlives code that might still look at it.

defer does for resources what the stack does for local variables: it ties a resource's life to a block by declaration. The smart pointer types are defer in type form, and the drop trait is defer supplied by the compiler.

defer is a note to your future self: when this block ends, no matter how, close the file. Writing it next to the line that opened the file keeps the pair together.

The Unique Pointer

The smart pointer is the ownership rule made into a type. SmartPtr<T> holds a heap-allocated value and owns it: disposing the pointer deallocates the value. It is a unique owner, the type's way of saying exactly one thing is responsible for the memory.

coral
pub struct SmartPtr<T> {
    T* ptr;
    // ...
}

A SmartPtr<T> is initialized with a value, which it allocates and copies into a fresh block; init returns bool, false on allocation failure. get returns the value, set replaces it, data and constData return raw pointers, isValid reports a live value, and take returns the value and relinquishes the block.

coral
SmartPtr<u64> p;
if (!p.init(42)) return;
println("{}", p.get());
p.set(7);
println("{}", p.get());
p.dispose();

A unique owner is the simplest ownership shape: one thing owns the memory, the memory dies with the owner, and there is never a question of who frees it. The ownership is the meaning of the type, not a convention to remember.

A unique pointer is like owning a pet: exactly one owner, so there is no argument about who frees it. Because SmartPtr<T> conforms to @drop, a local releases itself at scope exit unless disposed earlier, and dispose cancels the pending drop, so the block is freed exactly once.

The Shared Pointer

The shared pointer is the unique pointer with a count. SharedPtr<T> holds a value and a reference count stored together in the heap beside the value, in a RefCount struct holding one usize. Every holder uses the same count, and the last holder to be disposed frees the value and the count together.

coral
struct RefCount {
    usize count;
}

pub struct SharedPtr<T> {
    T* ptr;
    RefCount* rc;
    // ...
}

Initializing sets the count to one. Disposing decrements it, and at zero it deallocates both the value and the count. refCount reports how many holders share the value, and get, data, constData, and isValid behave as the unique pointer's. Because the fields are just ptr and rc, a new holder increments the count by hand:

coral
SharedPtr<Config> a;
if (!a.init(loadConfig())) return;

SharedPtr<Config> b;
b.ptr = a.ptr;
b.rc  = a.rc;
b.rc->count += 1;

println("{} holders", a.refCount());
a.dispose();
println("{} holder", b.refCount());

The shared pointer fits a value whose lifetime belongs to several places: a shared configuration, a cached resource, a document open in several views. Its cost is the count, an increment and decrement per copy and release, plus the zero check.

A shared pointer is like a library book with a checkout tally: several readers may hold it, and it returns to the shelf when the last one is done. Each new holder adds one, each release subtracts one, and zero frees the resource.

The unique pointer says one owner; the shared pointer says many owners, counted. Between them they cover the ownership shapes a program needs, and the choice states the value's life.

A common beginner mistake is to copy the two fields and forget the count:

coral
SharedPtr<Config> b;
b.ptr = a.ptr;
b.rc  = a.rc;          // but no increment here, so the count lies

Now two holders believe they share one resource, but the tally says one. When the first is disposed, the value is freed while the second still uses it: the classic use-after-free. The count is the entire reason the shared pointer is safe, so the increment must be written.

Ownership: Unique, Shared, and the Writer's Choice

Ownership answers who is responsible for this memory. The unique pointer says exactly one owner, and the memory dies with it; the shared pointer says many owners, counted, and the memory dies when the last one goes.

Coral does not automate the rest. There is no weak reference type and no ownership-tracking compiler. A weak holder is a raw pointer with a managed lifetime, or a shared pointer whose rc you do not increment. A cache that must not keep entries alive holds raw pointers and never touches the counts.

A cycle is the one shape counted ownership cannot resolve: two shared pointers pointing at each other keep each other alive, their counts never reach zero, and the pair leaks. Prefer acyclical structures. For an unavoidable graph, let one side hold plain pointers and the other shared pointers, or put the graph in an arena where who-frees-what disappears.

What the Compiler Checks, and What It Does Not

Coral has no borrow checker: no pass proves no pointer outlives what it points at, there is no lifetime annotation language, and there are no compiler-enforced reader and writer rules. This section maps what the compiler checks instead.

Every expression gets a type and every seam is verified: assignments, arguments, and operations. There are no implicit conversions, so a u32 is never quietly handed where a u64 is expected. Generic uses are checked against the operations the body names, and every comptime block runs at build time. The library asserts its own bounds at runtime.

The compiler does not check the pointer. Nothing proves a returned pointer still points at live memory, or that a block is freed exactly once by the right owner. That proof is the program's, written with defer, smart pointers, and allocators, and the compiler keeps it visible.

Lifetimes Are the Writer's Job

A lifetime is the span from creation to release. Coral has no lifetime syntax or checking, and the lifetime is what the writer makes it. Four rules keep the job sane.

A stack value's lifetime is its block. A local dies when its function returns, and any pointer to it dies with it. The classic C bug is returning the address of a local:

coral
u64* bad() {
    u64 x = 3;
    return &x;      // the address of a dead value
}

The pointer is returned, the frame is popped, and the address belongs to another function's stack; reading through it reads whatever moved in. Coral does not stop you, because the signature is the memory aid: returning a value that outlives the call means returning a heap value or a copy.

Heap values live until released: when dealloc is called, when the owning smart pointer is disposed, or when its arena is reset or its scope is freed. Every acquisition names a release, and defer writes the pair in one place.

The release must happen at the right moment. Too early is a use-after-free; too late is a leak. The right moment is after the last use and before anyone else needs the block: dispose after the borrowers are done, reset the arena after the batch is consumed, free the scope after the phase ends.

Ownership transfer is explicit. A function that takes ownership takes the pointer and the caller stops freeing it; take moves a value out of a smart pointer; a move on an owning assignment hands the resource on and cancels the source's release. Who frees this is written in the code at every step.

The compiler does not enforce these four rules; the program's structure does, built from the chapter's tools. The rules are few enough to hold in your head, the structure makes them visible, and the tooling makes them checkable.

The first rule matters most for a beginner. A local lives inside one function call, and its space is recycled on return. Returning its address returns the address of something about to stop existing. If a value must outlive its function, put it on the heap with alloc or return a copy.

Threads and Sharing

The hard truth about threads is that the memory model's front line is sharing. When two threads touch the same memory and at least one writes, the result depends on the hardware's ordering, not the program. Coral does not prove thread-safety; it provides tools, and the most important is the mutex.

Mutex wraps the platform's lock. Its declaration is an opaque block of storage sized for the platform's mutex, with operations that have no surprises.

coral
pub struct Mutex {
    rawptr impl[6];      // pthread_mutex_t is 40 bytes on 64-bit

    void init()    { /* pthread_mutex_init   */ }
    void lock()    { /* pthread_mutex_lock   */ }
    void unlock()  { /* pthread_mutex_unlock */ }
    void destroy() { /* pthread_mutex_destroy*/ }
}

The mutex rhythm is initialize, lock before touching the shared value, unlock after, destroy when done. The value several threads share lives behind the lock, and every access goes through the locked region. The lock serializes access, so work inside cannot overlap across threads. The discipline is the program's: forgetting one access races exactly that access.

Worker threads are created with threadCreate, which takes a function of one raw pointer and returns a Result:

coral
struct State {
    Mutex lock;
    u64   counter;
}

State state;
state.lock.init();
state.counter = 0;

Result<Thread, ThreadError> tc = threadCreate(worker, &state);
if (tc.isErr()) return;
Thread t = tc.unwrap();

state.lock.lock();
state.counter += 1;               // the only way to touch the counter
state.lock.unlock();

threadJoin(t, null);
state.lock.destroy();

The library also provides a thread pool, semaphores, and read-write locks. For a single word shared between threads, it ships AtomicU64 and AtomicU32 with load, store, and fetchAdd. Atomics protect one word; a shared structure uses a mutex. Shared memory requires explicit synchronization.

The Mutex and the Locked Value

A value read often and written occasionally, shared between threads, needs safe mutation. Class languages automate this with an interior-mutability wrapper; Coral uses a mutex and a plain struct, and the check is the lock.

coral
pub struct SharedCounter {
    Mutex lock;
    u64   value;
}

void increment(SharedCounter* c) {
    c->lock.lock();
    c->value += 1;
    c->lock.unlock();
}

The struct states the pattern openly: the lock and the value it protects, side by side, so the reader knows the value is not to be touched except through the lock. There is no wrapper magic or type machinery to decode. Coral expresses interior mutability as ordinary fields and an ordinary lock.

The cost is discipline: every access must lock, and a forgotten lock is a forgotten race. The payoff is that the program can be read. The locked region is the two lines between lock and unlock, and a reviewer can check every one.

Uninitialized Memory and the Init Discipline

The classic C failure is the uninitialized variable: memory is reserved, never written, and the program reads whatever was there before. Coral has no checker for this; the defence is the discipline of initialization.

The discipline has three parts. A value is initialized when declared or constructed, and a factory declares, fills every field, and returns. Memory needing a known state is given one on purpose, with zero<T> for a zero block. A value is not read before it is written.

coral
u64 total = 0;                       // initialized at birth
for (usize i = 0; i < n; i += 1) {
    total += values[i];
}

The rule is that uninitialized memory is not a value the program has built yet. A declaration reserves the bytes; the assignment fills them; between the two, the memory is the allocator's business. The compiler does not pretend otherwise, and initialization happens where the reader can see it.

comptime Checks Before the Program Exists

A comptime block runs during compilation, when concrete types are known, and performs the program's own assertions before a single instruction runs.

Its natural use is checking properties the type system does not express. The compiler knows a struct's size; whether that size is acceptable is the program's decision. A comptime block can ask directly and refuse to build:

coral
comptime {
    if (@sizeof(BigStruct) > 4096) {
        @compileError("BigStruct too large for the DMA ring");
    }
}

The compiler refuses to build because the program caught its own bug: a struct that would overflow a four-kilobyte ring slot becomes a build error, and @compileError states why.

The same mechanism checks an enum's count against a table's length, a computed buffer size against a platform limit, or an alignment against a requirement. The check is free at runtime because it never runs: it is a refusal, not a test.

Bounds Checks: The Libraries Assert

What compile-time checks cannot prove, the library checks at runtime. Container accesses are bounds-checked: the vector's at compares every index against the length, and an outside index is reported rather than silently read. The actual code from std::vec:

coral
T at(usize i) {
    @assertOut(i < self.len, "Index Out of bounds");
    return self.data[i];
}

@assertOut is a plain language construct, written where the access happens and visible to anyone opening the file. A vector knows its length, a hash map its table size, and a string its byte count. The difference is between corrupting adjacent memory and catching the bug at once with "Index Out of bounds."

The check is the default because the containers make it so. The raw pointer stays reachable: atPtr returns it, and data is public where present. Code that indexes a raw pointer has left the checked path deliberately, for speed. Safety is a library behavior, not a language promise.

Marking the Low-Level Exception

Coral has no unsafe keyword and no attribute that silences safety warnings, because there is no distinct unsafe subset. Low-level code marks itself with #[[no_drop_all]], the same attribute the library uses to take manual control.

coral
#[[no_drop_all]]

pub struct ArenaAllocator { /* ... */ }

The attribute disables automatic cleanup for the whole file and declares ownership manual. The memory module writes size headers into blocks, reinterprets bytes with casts, and frees with explicit dealloc. There is no separate warning to silence, because the low-level operations are ordinary features, and using them is stated at the top of the file.

Ordinary application code carries no marker, so a low-level cast or raw pointer stands out precisely because it is not the norm. Modules that must live close to the metal declare the exception once, at the top, so every reader knows what follows is reviewed.

The Failure Modes

A small family of classic failures motivates the chapter's checks. Each is a specific way of betraying the memory model, and each has a defence.

A buffer overflow writes past the end of a block, through an index past the array's length or a wrong copy length, corrupting a neighbor. The defence is checked access: at compares the index against the length, turning the overflow into a caught error.

A use-after-free uses a block after it was released, when the memory may belong to someone else. The defence is the ownership shape: the smart pointer makes release the pointer's own act, the arena and scope make a batch's death one chosen moment, and defer pairs every acquisition with its release in visible order.

A double-free releases the same block twice, corrupting allocator bookkeeping. The defence is the ownership shape plus the compiler: the unique owner is released once, the shared pointer's count makes once per holder the type's arithmetic, and a @drop type is released once at scope exit. A move leaves the source with no pending release.

A data race is two threads touching the same memory at once, at least one writing, without synchronization, so the value becomes a mixture of writes. The defence is the mutex and the locked value, written on every access.

Each failure is a way the program's belief about memory stops matching its actual use. The defer pairing, the ownership types, the checked containers, and the tooling exist to make them match.

These four failures are the four ways a program can lose track of memory: writing past a block, reading a block already returned, returning the same block twice, and two threads touching a block at once. Each is a mismatch between what the program thinks is there and what is.

Data Races and the Memory Model

The memory model is the understanding between program and hardware about how memory operations on different threads are observed. The hardware reorders, speculates, and batches as long as each thread's own behavior is preserved, so one thread's view of another's writes is not the issue order unless the program says otherwise.

The mutex is how the program says otherwise. The lock acquires and the unlock releases, and operations before an unlock are ordered before operations after the matching lock. A value shared behind a mutex is never observed torn: a reader has passed the same lock the writer passed.

A data race is the one failure hardware will not catch, because it only promises the ordering it was asked for. A program that respects the locks has deterministic behavior, because every shared access is ordered through a pair. One that touches shared memory outside the locks has none: hardware reordered it, and nothing asked it to agree.

A mutex is a turnstile in front of a shared room: one thread passes at a time. Two threads that went through the turnstile are never in the room together, so the value inside is never caught half-written, provided every visitor uses the turnstile.

The Tooling

The compiler's checks and the library's types catch what they catch; the tooling catches the rest. Because Coral lowers to C before becoming a native binary, the C toolchain's memory tools see the generated code.

AddressSanitizer instruments a program to detect memory failures while it runs. It records, for every block, where it was allocated, how large it is, and whether it was freed. An overflow, use-after-free, or double-free is reported with the allocation site. The several-fold slowdown makes it a test-build tool.

Valgrind watches every memory access from outside, without recompilation. It catches the same failures and reports the allocation's history: where it was allocated, how it grew or shrank, and where the pointer that should have freed it went. The sanitizer instruments the build; Valgrind observes the run, and a program can use both.

The tools turn a leak into a named thing:

coral
definitely lost: 4,096 bytes in 1 block
by loadConfig (config.crl:476)

The "definitely lost" line names the batch's size, 4,096 bytes, and the allocation stack points at the arena's init line, which in turn points at the loader's release. The fix is arena.reset() on the path that missed it, an early return before the reset or a call that never reached it.

The type system prevents one class of failures, comptime checks prevent another, the checked containers catch a third at runtime, and the tools verify the combination on the paths that ran. No single mechanism catches everything, so a program that wants certainty layers them: cheap in the shipping build, expensive in the test build.

A Worked Example: The Arena-Backed Loader

The chapter's pieces assemble into a loader that reads a configuration file into a batch of records, processes the batch, and releases it, using the arena for the batch and the scoped allocator for records that must outlive it.

The batch is a natural arena: the file is read into a buffer, records are built from the buffer's data, and the whole result is alive and dead at once.

coral
pub void loadConfig(str path) {
    Result<File, IoError> fo = fileOpen(path, "r");
    if (fo.isErr()) return;
    File f = fo.unwrap();
    defer fileClose(f);

    ArenaAllocator arena;
    arena.init(defaultAllocator, 4096);

    u8* buf = arena.pushType<u8>(4096);
    Result<isize, IoError> r = fileRead(f, buf, 4096);
    if (r.isErr()) { arena.deinit(); return; }

    parseInto(buf, (usize)r.unwrap(), &arena);
    report(&arena);
    arena.deinit();
}

The buffer and records come from the arena, and deinit returns the whole batch at once. The defer closes the file no matter how the parse turns out, even on an early return.

Records the rest of the program keeps outlive the batch, so the loader copies them into a scope that is released when the larger phase ends; freeAll returns them individually to the general heap:

coral
ScopeAlloc keep;
keep.init(defaultAllocator, 64);

for (usize i = 0; i < kept; i += 1) {
    Record* r = keep.allocType<Record>(1);
    copyRecord(r, &arenaRecords[i]);
}
reportRecords(&keep);

keep.freeAll();
keep.deinit();

The batch is an arena, the long-lived records are a scope, and the file is a defer, so the memory behavior is written in the code at each decision. Nothing scans the heap, nothing pauses, and the loader's memory is accounted for line by line.

The Drop Trait: The Compiler-Provided Release

defer binds a release to a block by writing it; @drop binds a release to a type, and the compiler emits it when a value goes out of scope, automatically, exactly once, on every exit path. This is RAII made compiler-provided: the destructor is a trait conformance, visible and guaranteed.

The trait is compiler-provided, so any type in any program may conform. The conformance is an ordinary extend block naming the trait with a colon:

coral
pub extend<T> SmartPtr<T> : @drop {
    void drop() {
        self.dispose();
    }
}

The compiler finds every local whose type conforms and emits the type's drop at the end of the scope where it dies. Drops run innermost-scope-first and in reverse declaration order, exactly like defer. Never call drop() by hand on the normal path; E1301 forbids it because the scope will also call it.

defer is the explicit pair, written by hand, and @drop is the type-level pair: the release is part of the type and every value carries it on scope exit. The two compose. A one-off resource gets defer; a type that owns its release gets the conformance once and inherits it everywhere.

Most standard library modules free by hand and carry #[[no_drop_all]], deliberately. The trait is implemented and supported, and SmartPtr<T> and SharedPtr<T> are examples, but most files free explicitly to keep compile times down because every program compiles the library.

The Memory Management Verdict

Memory management is the program's business, and this chapter is the toolbox. The language refuses to take the decision away because it is the source of control: determinism, predictability, and the ability to say exactly when memory is used and returned. The price is attention, and the language makes that attention productive.

defer makes release visible and guaranteed. The smart pointers make ownership a property of the type. @drop makes release automatic for conforming types. The allocators make policy fit lifetimes. Checked containers catch boundary violations. comptime checks assumptions at build time. The tooling verifies the result.

The result is a memory model the program can reason about: allocation is explicit, release is paired, ownership is unique or shared, and the allocator fits the lifetimes. The garbage collector is absent, so there is no scan, pause, hidden cost, or moment when memory acts without the program.

Chapter 11 Summary

Coral has no garbage collector: release is explicit, immediate, and paired with acquisition, and a leak a tool can name is preferred over a pause no tool can remove.

Memory lives in three regions: the stack, whose values die with their frame; the heap, requested from the allocator and released by the program; and the static region, which lives for the whole program.

A pointer is an exact address, zero-cost and exact-typed, and the program must ensure it points at a live value.

Null is explicit: a pointer is an address or null, and Option<T> is the checked spelling of possible absence.

The allocation primitives are typed: alloc<T>, dealloc<T>, and realloc<T> name the element type and count, and zero, copy, move, and equal operate on typed blocks.

The allocator is a value: an Allocator struct with a context and three function pointers. The default wraps the C library's malloc; TLSF and mimalloc are available for predictable timing or higher throughput.

The fixed buffer allocator is a hard-bounded bump allocator; the stack fallback serves small temporaries from a stack buffer and the rest from its fallback.

The arena is the batch allocator: bump allocation, no individual frees, growth by reallocating the region, and reset to abandon the whole batch.

The pool is the fixed-size allocator: one region sliced into blocks linked in a free list, constant-time alloc and free, an explicit block bound, and typed Pool<T> on top.

The scoped allocator records every block and returns them all with freeAll; the logging allocator counts bytes and calls and quantifies leaks.

Choose an allocator by matching the lifetime: fixed buffer for a hard bound, arena for a batch, pool for churn, and the general heap for everything else.

defer attaches a cleanup to a block and runs it on every exit, in reverse order, making acquisition and release a visible pair.

SmartPtr<T> is the unique owner; dispose frees the value. SharedPtr<T> is the counted owner; the last disposal frees the value and the count.

@drop is the compiler-provided release: a conforming type has its drop emitted once at the end of every scope where a value dies. The library supports it while most modules free by hand under #[[no_drop_all]] to keep compile times down.

There is no weak reference type: the weak idea is a raw pointer that does not touch the count, and cycles are broken by structure, direction, or the arena.

Coral has no borrow checker and no lifetime syntax: the compiler checks types, conversions, generics, and comptime blocks, and a pointer's lifetime is up to the writer.

The four lifetime rules are: stack values die with their block, heap values live until released, release comes after the last use, and ownership transfer is explicit.

Threads share through the mutex: init, lock, unlock, and destroy, with the locked pair ordering every shared access. threadCreate returns a Result, and atomics cover the single-word case.

The uninitialized-memory defence is the init discipline: initialize at declaration or construction, zero blocks on purpose, and read nothing before it is written.

comptime checks facts at build time, such as a struct size against a slot or an enum count against a table, and refuses the build with @compileError when an assumption is wrong.

The containers check bounds at runtime with @assertOut; the raw pointer path is the deliberate exception.

Low-level modules mark themselves with #[[no_drop_all]], declaring that ownership inside is managed by hand.

The failure modes have defences: checked access catches buffer overflow, ownership and the compiler's move catch use-after-free and double-free, and the mutex catches data races.

The memory model is the mutex pair: the lock's acquire and release order accesses around them, and shared values behind the lock are never observed torn.

AddressSanitizer and Valgrind verify the result because the compiler lowers to C: the sanitizer instruments the build, Valgrind watches the run, and a program that must be certain layers both.

The arena-backed loader is the discipline in miniature: the batch is an arena, the long-lived records are a scope, the file is a defer, and memory is accounted for line by line.

Coral's memory is the program's, accounted for, and the accounting is the control the language is for.
