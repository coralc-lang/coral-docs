Aggregate types: named and positional fields

An aggregate puts several values together and treats them as one value. Coral has named aggregates such as structs, and the current source also demonstrates tuples, whose fields are selected by position.

Tuple syntax and positional access shown in current source

What does “aggregate” mean?

Suppose a function needs to return two related numbers. One approach is to return them as two separate results, but a function call usually produces one result value. An aggregate solves this by packaging multiple component values together. The components keep their own types, and the aggregate gives the group one type of its own.

There are two useful ways to identify a component. A named aggregate identifies it by a field name. A tuple identifies it by its position in the sequence. Coral provides both forms in the current code sample.

Struct fields have names

In a struct, the declaration gives each component a name. The name tells a reader what the value means, and code can refer to the field by that name.

struct Point {
    i32 x;
    i32 y;
}

This is a simple illustration of the familiar named-field idea: one field is x, and another is y. The names carry the meaning. The tuple equivalent below has two values in an order, but it does not give those positions semantic labels such as x and y.

A tuple type lists component types in order

The current Coral source declares a function with this return type:

struct(i32, i32) foooo()
{
    return (2, 3);
}

Read struct(i32, i32) from left to right. It describes an aggregate with an i32 in its first position and an i32 in its second position. The function named foooo returns a value of that tuple type. Its returned value is written (2, 3): first comes 2, then 3.

The word struct in this tuple-type spelling can be surprising if you expect a tuple to have a completely separate keyword. Here it introduces the tuple type form. It does not mean the parentheses contain field names; they contain component types in positional order.

Tuple fields are positional

The current program stores the returned tuple in a and reads its components like this:

var a = foooo();
println("({}, {})", a.1, a.2);

a.1 means the first positional field of a; a.2 means its second positional field. The number identifies a position, not a field that the programmer named 1 or 2. Keep the order straight: first component, then second component.

This is useful when the order itself is small and obvious. It can also make a longer expression harder to understand: result.2 does not explain what that component represents. When the values have domain-specific meanings that need to be clear at every use, named struct fields communicate those meanings directly.

One-based positions in the shown syntax

The source example uses .1 and .2 for the first and second tuple fields. That is the concrete syntax demonstrated here. Do not silently rewrite it as .0 and .1 based on another language's indexing convention.

The example establishes those two accesses. The complete range of tuple positions, behavior for an out-of-range position, and rules for nested tuples should each be checked against the compiler before this lesson promises them.

Tuples and structs are both product-shaped

Both forms can combine more than one component into a value. Their important difference for readers is how components are identified:

  • Struct: fields have declared names; read the name to understand the component.
  • Tuple: fields have positions; read the order and numeric field selector.

This is why neither form makes the other pointless. A short pair returned together can be convenient as a tuple. A value with durable meaning is often easier to read when its components have explicit names.

How the example connects to var

The line var a = foooo(); declares a local and asks the compiler to infer its type from the function result. The function signature already states that result type: struct(i32, i32). So the reader can follow the type without a separate annotation at the call site.

Inference does not erase the tuple's positions. Once the value is named a, the sample still selects its first and second components with a.1 and a.2.

What changed from the old manuscript

An older textbook passage says that Coral has no tuple types. That statement is stale: the current source sample uses a tuple return type, a tuple value, and positional field access. This lesson follows the current syntax instead of repeating that outdated sentence.

The source sample is the basis for the syntax taught here. Broader rules about tuple layout, equality, assignment, nesting, or maximum arity still need direct compiler tests before they are added as guarantees.
