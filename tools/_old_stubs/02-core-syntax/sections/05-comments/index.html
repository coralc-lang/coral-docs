Comments and attributes

Comments are notes for people reading the program. Attributes look like annotations in the source, but unlike ordinary comments they may be read by the compiler.

Starter lesson · line comments in source; attribute effects vary

A line comment

// This note is for the reader.
var count = 3; // This note follows a declaration.

The two slashes begin a comment in the current source examples. A comment can explain why a choice was made, or give context that the code alone cannot show. Avoid comments that merely repeat the line word for word.

Comments are not executable statements

When reading code, mentally set the comment aside and focus on the program tokens around it. The comment does not declare the variable, set its value, or call a function; the non-comment source does those things.

The supplied lexer description explicitly notes that numeric comments inside the token enum are explanatory group labels, not token values. That is another example of comments helping readers without changing the program's token set.

Attributes look different

The source vocabulary includes a hash token, and the supplied token comments show an attribute-shaped form such as #[[no_drop_all]]. Unlike //, an attribute may affect compiler behavior. The attribute documentation distinguishes attributes that are honored from ones that are only parsed and ones that are planned.

So the beginner rule is: comments explain code to people; attributes are structured source annotations whose compiler effect must be checked one by one.

What still needs a lesson

The current sample establishes line comments. A complete comment reference should also test block comments, nesting behavior, and comment handling inside strings. A complete attribute lesson should link to each attribute's actual implementation status rather than imply that every parsed attribute has an effect.
