var: let the compiler fill in the type

Sometimes the initializer already makes the type clear. Coral lets you write var in the type position and asks the compiler to infer the declared value’s type.

Explicit type and inferred type

These two declarations show the idea:

i32 count = 42;
var message = "hello";

The first spells out the type. In the second, var means “infer the type from this initializer.” It does not mean that the value has a type literally named var.

Inference is not dynamic typing

Imagine a labeled box. If the label is printed on the box, the type is explicit. If the compiler reads what you put in the box and determines the type, the type is inferred. Either way, the compiler still knows the type; inference changes how much you write, not whether the value has a type.

The current sample uses var for a string, a decimal value, and the result of calling a tuple-returning function. That demonstrates local inference in those examples. It does not establish every place in the grammar where var is allowed.

Inference from a function result

struct(i32, i32) makePair()
{
    return (2, 3);
}

pub void main()
{
    var pair = makePair();
}

makePair declares its return type at the function boundary. When main calls it, the type of pair can follow from that return type. This is a useful place for inference because repeating a type already visible in the function signature may add noise.

What the spelling cannot tell us

The literal 3.14 looks like a decimal number to a person, but that does not tell us whether Coral infers f32, f64, or uses a context rule. The compiler decides. A lesson should record the result of compiling a small test rather than assume the answer from another language.

Quick check

In var result = makePair();, which piece asks the compiler to infer the type? var. Where can we learn what type is inferred? First inspect makePair’s return type, then confirm with the compiler when necessary.
