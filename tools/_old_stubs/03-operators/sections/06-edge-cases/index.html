Edge cases and operator policy

The ordinary case is easy to guess. The edge case is where languages differ, and where a beginner can get surprised. We use tests to find Coral’s real answers.

Needs compiler tests · old manuscript claims not promoted

Overflow and underflow

What happens when an arithmetic result is too large or too small for its type? Some languages wrap, some trap, and some leave cases undefined. The token list does not tell us which choice Coral makes. Test signed and unsigned operations independently and record target/compiler version.

Division by zero

Do not assume division by zero wraps, returns a special value, or always produces a runtime error. It can be rejected at compile time in some cases and behave differently for values known only at runtime. This needs precise, safe tests.

Shift boundaries

For shifts, check what happens when the shift amount is negative, equal to the bit width, or larger than the bit width, and whether signed and unsigned operands differ. The token names Shl and Shr identify spellings; they do not define these edge rules.

Operator overloading

The old manuscript says Coral does not allow operator overloading. Before presenting that as a design rule, check the current grammar, trait system, and compiler tests. A previous textbook sentence is not enough evidence for today’s compiler.

Turn a claim into a test

Write one small program for one behavior. Keep the input and expected observation simple. Run it with the current compiler. Record what happened and which target was tested. A clear test is easier for a beginner to understand than a long paragraph asserting behavior without evidence.
