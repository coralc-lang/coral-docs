Read the program in this workspace

We will not invent a toy program and pretend it proves the language. This walkthrough uses the current src/main.crl example and explains only what is visible there.

Source walkthrough · behavior claims kept narrow

First, the data declarations

var c = "the value of pi is: ";
var v = 3.14;

Each line declares a name and gives it an initial value. var is the inference form in the declaration slot. The string and decimal literal determine the declared value’s type at compile time; this is not a dynamic variable. The exact inferred numeric type is a compiler question, so we do not guess it here.

Next, a generic structure

struct foo<T, U> {
    T a;
    U b;

    T(U, i32) fn;
}

foo has two type parameters, and its fields use those types. The final field stores a function type. This is a compact example of Coral showing the types before the field names.

Then, named alternatives and an extension

enum Color {
    Red,
    Green,
    Blue
}

variant Option<T> {
    Some { value; },
    None
}

Color lists named cases. Option<T> lists two variant cases, with a field shown for Some. The source later writes an extend Option block. Treat that as visible syntax, not proof of all object-model details.

Finally, the entry function

struct(i32, i32) foooo()
{
    return (2, 3);
}

pub void main()
{
    var a = foooo();
    println("Hello, World! {}{}", c, v);
    println("({}, {})", a.1, a.2);
}

The first function returns two i32 values as a tuple. main calls it and stores the result in an inferred local. The print calls use braces as formatting placeholders in the example. The accesses a.1 and a.2 read the two tuple positions in this sample.

Notice the reading order: types first, then names, then initializers and bodies. This makes the program’s data shape visible before the details of what it does.

A note about the commented import

The file begins with a commented-out import of printf, and there is also a printf call later. Since the import is commented, do not assume that call is provided by that import or that the whole file currently builds. A good walkthrough records this discrepancy and checks the compiler output rather than silently editing the example in the book.
