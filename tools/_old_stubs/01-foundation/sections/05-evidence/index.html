What the compiler proves

A programming book is useful when its examples work and its statements can be checked. Coral is changing, so we make the evidence visible instead of turning an old paragraph into a new rule.

Editorial method · applies to every chapter

Three kinds of evidence

1. A lexer token

A token definition tells us that the lexer has a name for a spelling. For example, the provided enum lists U128 and I128. That establishes that the lexer vocabulary includes those names; it does not establish target support, type layout, or arithmetic behavior.

2. A parser rule

A grammar or parser rule tells us that text has a recognized syntactic shape. It does not guarantee that the type checker accepts it or that the resulting program behaves as intended.

3. A compiler-checked example

A minimal source file compiled with the current compiler tells us more: the syntax and relevant type checks passed for that configuration. If it is also run and its output observed, we can support a behavior claim for that tested case.

How to check a small claim

Suppose we want to teach whether a decimal literal inferred with var has type f32 or f64. Rather than choosing by intuition, write a tiny program that asks the compiler to use the value where one type is required, then try the other. Record the exact command, compiler version, target, and result.

The same method applies to i128: finding its token name is a start. Compile a declaration on each supported target before promising that it works everywhere.

How lessons are marked

  • Example-confirmed: the form appears in the current source or a compiler-checked test.
  • Vocabulary-confirmed: a lexer token exists, but grammar or semantics may still need verification.
  • Needs validation: an old manuscript claim or design idea has not been checked against current behavior.
