Coral editor protocol

The contract between an editor and coralc --serve.

Status: this document is normative. Both extensions are implemented and tested against it. coralc --serve is a work in progress; where it diverges, the divergence is listed explicitly under Current state so the gap is visible rather than assumed.

1. Transport

JSON-RPC 2.0 over stdio, with LSP base-protocol framing.

Every message, in both directions, is preceded by a header block and then exactly N bytes of UTF-8 JSON:

Content-Length: 143\r\n
Content-Type: application/vscode-jsonrpc; charset=utf-8\r\n
\r\n
{"jsonrpc":"2.0","id":1,"result":{…}}

Rules:

  • Content-Length is bytes, not characters. A UTF-8 multibyte character counts as its encoded length.
  • The header block ends with a blank line (\r\n\r\n). The server may omit Content-Type; clients must accept its absence.
  • Messages are not newline-delimited. A \n inside a JSON string is escaped as \n and does not terminate a message.
  • No JSON-RPC batching. LSP does not support it; clients and servers must not send arrays.
  • Stdout carries the protocol and nothing else. No banners, no progress, no debug prints. Anything human-facing goes to stderr.

Correction. Earlier revisions of this document specified one JSON object per line. That was wrong: the real coralc --serve already emits Content-Length framing. Both clients were fixed to match.

Startup

editor → coralc --serve        (newline-framed argv; the flag, not a subcommand)
coralc → stdio                 (nothing may be written before initialize is answered)

2. Lifecycle

editor → {"jsonrpc":"2.0","id":1,"method":"initialize","params":{…}}
coralc → {"jsonrpc":"2.0","id":1,"result":{"capabilities":{…},"serverInfo":{…}}}
editor → {"jsonrpc":"2.0","method":"initialized","params":{}}
editor → {"jsonrpc":"2.0","method":"textDocument/didOpen","params":{…}}
coralc → {"jsonrpc":"2.0","method":"textDocument/publishDiagnostics","params":{…}}
        …
editor → {"jsonrpc":"2.0","id":2,"method":"shutdown","params":null}
coralc → {"jsonrpc":"2.0","id":2,"result":null}
editor → {"jsonrpc":"2.0","method":"exit","params":null}
coralc → process exits

Hard requirements, per LSP 3.18:

  • initialize must carry protocolVersion, processId, rootUri, and capabilities. rootUri may be null (single-file session); the server then anchors analysis to the opened document's own directory, see §3b Standalone files.
  • Before responding to initialize, the server must not send any request or notification, with one exception: window/showMessage, window/logMessage, window/showMessageRequest, telemetry/event, and $/progress are permitted while initialize is in flight.
  • A request received before initialize must be answered with error -32002 (ServerNotInitialized). Notifications received before it are dropped, except exit.
  • initialize may be sent only once.
  • The client must not send anything else until it has received the InitializeResult.
  • shutdown is a request; exit is a notification.
  • Exit code 0 if shutdown was received, 1 otherwise. On stdin EOF the server should exit cleanly.

initialize, client → server

{
  "protocolVersion": "3.18",
  "processId": 4711,
  "rootUri": "file:///home/you/coralc",
  "workspaceFolders": null,
  "clientInfo": {"name": "coral-vscode"},
  "capabilities": {
    "textDocument": {
      "hover": {"contentFormat": ["markdown"]},
      "documentSymbol": {"hierarchicalDocumentSymbolSupport": false}
    }
  }
}

initialize, server → client

{
  "capabilities": {
    "textDocumentSync": 1,
    "hoverProvider": true,
    "definitionProvider": true
  },
  "serverInfo": {"name": "coralc", "version": "0.1.0"}
}

textDocumentSync: 1 means Full. Both extensions send full text and neither implements incremental sync.

3. Locating the compiler

Resolution order, first hit wins. Both extensions implement this identically.

  1. Explicit setting, coral.languageServer.path (VS Code) or language_servers.coral.path (Zed). Absolute or ~-prefixed.
  2. CORALC environment variable.
  3. CORAL_HOME → $CORAL_HOME/coralc[.exe].
  4. coralc on PATH.
  5. Platform install roots:
PlatformPaths
Linux~/.coral/bin/coralc, ~/.local/bin/coralc, ~/bin/coralc, /usr/local/bin/coralc, /usr/bin/coralc
macOS~/.coral/bin/coralc, ~/bin/coralc, /opt/homebrew/bin/coralc, /usr/local/bin/coralc
Windows%USERPROFILE%\.coral\bin\coralc.exe, %LOCALAPPDATA%\coral\coralc.exe, %LOCALAPPDATA%\Programs\coral\coralc.exe
  1. Give up. Log no coralc found; run no server. Highlighting is tree-sitter/TextMate only and keeps working.

A configured path that does not exist falls through to the next candidate rather than failing outright. A candidate that exists but fails to spawn is a real error and should be surfaced.

The launcher must invoke coralc --serve, never coralc serve.

How each editor starts it

EditorMechanism
VS CodeThe extension spawns the binary itself on activation, probing for coralc. No configuration.
ZedThe extension's language_server_command resolves coralc via worktree.which() and passes --serve. No configuration.

Neither editor asks the user to configure anything. A settings.json contributor would fix one machine and would not ship.

Library resolution is the compiler's problem

The editor never passes library paths, module maps, or CORAL_HOME. On Linux the compiler owns ~/.coral/{lib,store,projects} and the per-project .coral/{cache,modules.map,artifacts,graph.dot,metrics.json}. Encoding any of that in an editor breaks the moment the compiler changes its layout.

4. Document synchronisation

Full text, no incremental ranges. Coral files are small and the compiler parses whole files anyway.

// textDocument/didOpen
{"textDocument":{"uri":"file:///p/x.crl","languageId":"coral","version":1,"text":"…"}}

// textDocument/didChange, one full-content change
{"textDocument":{"uri":"file:///p/x.crl","version":2},"contentChanges":[{"text":"…"}]}

// textDocument/didClose
{"textDocument":{"uri":"file:///p/x.crl"}}

version is monotonic per document. The editor may coalesce rapid edits and send the latest text when the server goes quiet.

On didClose the server should clear that document's diagnostics.

6. textDocument/publishDiagnostics (server → editor)

{
  "method": "textDocument/publishDiagnostics",
  "params": {
    "uri": "file:///p/x.crl",
    "version": 2,
    "diagnostics": [
      {
        "range": {"start": {"line": 0, "character": 21},
                  "end":   {"line": 0, "character": 24}},
        "severity": 1,
        "code": "P0001",
        "source": "coral",
        "message": "expected '{', found 'u32'"
      }
    ]
  }
}

Rules:

  • severity is LSP: 1 error, 2 warning, 3 information, 4 hint.
  • code is the compiler's stable error-code identifier (P0001, P0002, P0003, …) so editors can key off identity rather than message text.
  • source is "coral".
  • Lines and characters are zero-based UTF-16 code units, not bytes.
  • The server must publish a full set per document after every change, including an empty array when a document becomes clean, an empty array is what clears the file in the editor. Silence is not "no errors".
  • Parse failures are diagnostics too. They must not abort the rest of the file; recover and keep going so one syntax error does not cascade.

7. textDocument/hover (editor → server)

Request:

{"method":"textDocument/hover",
 "params":{"textDocument":{"uri":"file:///p/x.crl"},
           "position":{"line":4,"character":6}}}

Response, Hover | null:

{
  "contents": {"kind": "markdown", "value": "```coral\nT at(usize i)\n```\n\nArray element access."},
  "range": {"start": {"line": 4, "character": 5}, "end": {"line": 4, "character": 7}}
}

null is a valid answer meaning "nothing to say here". It must not be an error, and the editor must not surface one.

8. textDocument/documentSymbol (editor → server)

Returns DocumentSymbol[] | SymbolInformation[] | null. The editor advertises hierarchicalDocumentSymbolSupport: false, so SymbolInformation[] is the expected shape.

[{"name": "at", "kind": 12,
  "detail": "T at(usize i)",
  "location": {"uri": "file:///p/x.crl",
               "range": {"start": {"line": 4, "character": 5},
                         "end":   {"line": 4, "character": 7}}}}]
CoralSymbolKind
struct, union, extend, variant, enum5 Class
trait11 Interface
functions, methods, constructors12 Function
fields, variant members8 Field
constants, locals13 Variable

detail is the declaration as written minus its body. Because Coral is type-first this is what makes an outline readable: T at(usize i), not at.

9. Coral-specific methods

coral/attributes, every attribute understood at a position, so the editor can complete inside #[[…]]:

{"result": [
  {"name": "no_drop_all", "doc": "disable auto-RAII for this file"},
  {"name": "packed",      "doc": "packed struct layout"},
  {"name": "generate",    "doc": "generate trait boilerplate",
                          "parameters": [{"name": "traits", "variadic": true}]}
]}

coral/typeInfo, the node under the cursor for the scopes/inspect affordances:

{"result": {
  "kind": "method", "name": "at", "qualified": "Arr.at",
  "type": "fn(usize) -> T", "doc": "Array element access.", "attributes": []}}

9b. Type information

This is the core of what makes Coral pleasant to edit, and it is three separate mechanisms. None of them work today.

Hover, the type and signature under the cursor

Hover | null. null is valid; an unimplemented feature must be -32601 instead, otherwise editors will keep offering a hover that yields nothing.

{"contents": [
    {"language": "coral", "value": "fn at(usize i) -> T"},
    "
Array element access. Returns `self.data[i]`.
"
  ],
 "range": {"start": {"line": 4, "character": 5}, "end": {"line": 4, "character": 7}}}

Contents is MarkupContent or an array mixing MarkedString and markdown. Both clients advertise hover.contentFormat: ["markdown"].

Semantic tokens, colour by meaning, not by syntax

Tree-sitter knows the shape of T at(usize i); only the compiler knows T is a type parameter and i is a parameter. Semantic tokens close that gap. This is what makes types visually distinct from values.

// result: { "data": [ ... ] }, flat u32 array, 5 ints per token
{"data": [0, 0, 4, 2, 0, 5, 0, 2, 0, 5, 0, 5, 2, 0, 0]}

Token types and modifiers are declared in the server's initialize result:

"semanticTokensProvider": {
  "legend": {
    "tokenTypes": ["type", "parameter", "property", "function", "method",
                   "struct", "genericParameter", "keyword"],
    "tokenModifiers": ["declaration", "readonly"]
  },
  "full": true, "range": false
}

Encoding: deltaLine, deltaStartChar, length, tokenType, tokenModifiers , all relative to the previous token, sorted, non-overlapping, never spanning lines.

Correction. An earlier revision said the editor never asks for semantic tokens, on the grounds that highlighting belongs to tree-sitter. That is right for syntax and wrong for types: tree-sitter cannot know that T is a type parameter. Zed supports "semantic_tokens": "combined" (LSP colours on top of tree-sitter) and "full". VS Code enables this automatically when the server advertises the capability.

Inlay hints, inferred types inline

{"label": ": T", "position": {"line": 8, "character": 20},
 "kind": 1, "paddingRight": true}

kind 1 is Type, 2 Parameter. Particularly valuable for let/const bindings whose type is not written.

Completion and signature help

textDocument/completion returns CompletionItem[] | CompletionList | null. For Coral the trigger characters matter more than usual:

TriggerCompletes
.fields and methods on the receiver, narrowed to its type
::module paths, types, associated constants
#[[attributes, from coral/attributes
` `` or identifierdeclarations in scope
{"label": "count", "kind": 2, "detail": "fn count() -> usize",
 "documentation": {"kind": "markdown", "value": "Number of elements."},
 "insertText": "count()", "sortText": "0000"}

completionItem/resolve fills in documentation lazily, so the initial response stays small. Both clients advertise completionItem.snippetSupport and documentationFormat: markdown.

textDocument/signatureHelp matters more for Coral than most languages because declarations are type-first and the return type sits in the middle:

{"signatures": [{"label": "at(usize i) -> T",
                 "parameters": [{"label": "usize i"}, {"label": "-> T"}],
                 "activeParameter": 0}],
 "activeSignature": 0}

Occurrences, navigation, quick fixes

  • textDocument/documentHighlight, every other occurrence of the symbol under the cursor (Read/Write/Text document highlight kinds). Cheap, and the most visible quality-of-life win after hover.
  • textDocument/definition returns Location | Location[] | LocationLink[] | null. Both clients advertise definition.linkSupport, which is preferred: it carries originSelectionRange so the editor can highlight the declaration site without a second round trip.
  • textDocument/typeDefinition, for Coral this is often the more useful jump: from a T use to the struct or variant that defines it.
  • textDocument/codeAction, quick fixes for diagnostics. Coral is a good fit because most diagnostics are mechanical (P0002 array size, unused import). A fix is returned as a WorkspaceEdit; apply it with workspace/applyEdit, which both clients advertise support for.

Beyond document sync, a conforming server must tolerate these without erroring:

9d. Messages the server should send

Without these the compiler fails silently, which is exactly how --serve behaved before build.crlb handling was fixed:

// surface a fatal configuration problem instead of exiting quietly
{"method": "window/showMessage",
 "params": {"type": 1, "message": "coralc: no build.crlb found in the project root"}}

// progress for whole-project analysis
{"method": "window/logMessage",
 "params": {"type": 3, "message": "indexed 412 files in 84 ms"}}

type is 1 Error, 2 Warning, 3 Info, 4 Log. These are permitted even while initialize is in flight.

9e. Position encoding

LSP 3.17 added general.positionEncodings. The server should pick the first encoding the client lists, defaulting to UTF-16 code units:

// client -> initialize
"capabilities": {"general": {"positionEncodings": ["utf-16", "utf-8"]}},
"positionEncoding": "utf-16"      // server -> initialize, echo the choice

publishDiagnostics positions must use the negotiated encoding. Coral source is UTF-8 and may contain non-ASCII identifiers and string literals, so this is a real off-by-N risk rather than a theoretical one. Both clients currently advertise UTF-16 only.

10. Errors

CodeMeaningWhen
-32700ParseErrorMalformed JSON on the wire
-32600InvalidRequestValid JSON, invalid JSON-RPC shape
-32601MethodNotFoundUnsupported method, the normal "not implemented" answer
-32602InvalidParamsBad params for a known method
-32603InternalErrorServer bug
-32002ServerNotInitializedRequest before initialize
-32800RequestCancelled$/cancelRequest was honoured

-32601 is the single most important one: a server that does not implement a method must answer with it rather than ignoring the request or crashing. Both extensions treat -32601 as "feature absent" and silently degrade.

Responding correctly

Any method not implemented must return -32601. That is how an editor learns a feature is absent and hides the affordance. Silence is worse than -32601: the editor waits for a response that never comes.

12. Current state

Verified against ~/.coral/bin/coralc 0.1.0 (coralc --help advertises --serve run the language server on stdio (LSP)), including the coral-vscode live handshake (tools/test-live-server.js, 9/9) and the compiler-side suite (lifecycle, exit codes, UTF-16 columns, project report, cleared markers).

Working:

  • Content-Length framing, exactly as specified above.
  • initialize → {textDocumentSync: 1, hoverProvider: true, definitionProvider: true}; a request before initialize answers -32002; a second initialize answers -32600.
  • Malformed JSON answers -32700; non-object messages -32600.
  • shutdown / exit with the specified exit codes: 0 after shutdown, 1 without; stdin EOF exits cleanly.
  • textDocument/didOpen / didChange / didClose (full text); didClose publishes an empty set, clearing the document's markers.
  • textDocument/publishDiagnostics with source: "coral", stable P#### / T#### codes, UTF-16 character offsets, and an empty array whenever a document becomes clean, silence is not "no errors".
  • Whole-project error report: opening any file analyzes the build entry (coral.crlb) and publishes diagnostics for every file in the import closure, so errors in files the open buffer never imports appear too. Files that stop having records are cleared on the next report.
  • textDocument/hover returns the markdown-typed declaration of the expression or symbol under the cursor. Verified for structs, fields, locals, generics, self, imports and libc, e.g. self → Arr<T, N>*, data → T, val → T val, printf → i32 printf(const cchar* fmt, ? ).
  • textDocument/definition resolves; 32 of 64 identifier positions in arr.crl.
  • -32601 for unimplemented methods; $/cancelRequest accepted.

Two behaviours that look like bugs but are not

Hover resolves by nearest-preceding-identifier. A caret resting between two symbols returns the earlier one, and whitespace or punctuation still resolves to the previous symbol. Always check the reported position before concluding that resolution is wrong.

Advertised capabilities are not evidence. definitionProvider: true was advertised while the method still returned null everywhere. Verify per position rather than trusting the initialize result.
