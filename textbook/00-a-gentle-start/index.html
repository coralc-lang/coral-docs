Chapter 0

A Gentle Start

Programming for the Very First Time

You have never written a program before. Maybe the whole idea sounds a little intimidating, like a skill other people are born with. It is not. Programming is a craft, and like any craft it is learned one small step at a time, by doing. This chapter is your first step. It assumes nothing. If you have never seen a line of code in your life, you are in exactly the right place.

By the end of this chapter you will understand what a program is, what a compiler does, and what the words the rest of this book uses actually mean. You will have read a complete program and understood every character in it. You will know how to make the computer decide something, repeat something, and package work into a reusable step. And you will know what to do when something goes wrong, which it will, constantly, for everyone, forever.

Take your time here. Nothing in this chapter is a race. The chapters after this one get deeper, but they build directly on what is on this page, and a reader who is comfortable with the basics will find the rest of the book much easier than a reader who skipped ahead.

What a Program Is

A program is a list of instructions that a machine carries out, one after another, in order. That is the whole idea, and it is worth sitting with for a moment because everything else follows from it.

Think of a recipe. A recipe is a list of steps: crack two eggs into a bowl, add a cup of flour, stir until smooth, pour into a pan, bake for twenty minutes. A cook follows the steps in order. Some steps can branch: if the dough is too sticky, add a little more flour. Some steps repeat: keep stirring until the lumps are gone. A program is a recipe written for a machine instead of a cook, with one important difference: a machine does not understand the language you and I write. It understands only its own extremely simple set of operations. So before the machine can follow your recipe, your recipe has to be translated into the machine's language.

That is where a compiler comes in, and it is the next section. For now, hold on to the core picture: a program is an ordered list of instructions, some of which decide things and some of which repeat things, all written down in a form a human can read.

What a Compiler Does

A compiler is a program that reads the program you wrote and produces the program the machine runs. It is a translator, but a very careful one.

You write your instructions in a language designed for people: clear, readable, close to English and arithmetic. Call it the source. The machine wants instructions in its own language of numbers and tiny operations, called machine code. These two languages are as far apart as Spanish and Morse code. The compiler reads your source and writes out the same instructions in the machine's language, so the machine can follow them. That output is your program, ready to run.

A compiler does a second job that matters just as much: it checks your work. If you misspell a word, forget a piece of punctuation, or use a number where the machine needs text, the compiler does not quietly produce a broken program. It stops and tells you what it could not understand, and roughly where. Learning to read those messages is a skill in its own right, and this chapter has a section on it. For now, know this: a compiler is on your side. It is the careful reader who catches your mistakes before the machine ever runs them.

Here is the vocabulary that follows from this. To compile a program is to translate it. To run a program is to have the machine carry out its instructions. When you change your source and compile again, you get a fresh program reflecting the change. The loop of writing, compiling, reading errors, fixing, and running is the daily rhythm of programming, and it never really goes away.

A Mental Model: Values, Memory, and Control Flow

Before we write anything, here is one picture to carry with you. It is not the whole truth, but it is a good first truth, and the book will refine it as we go.

Picture memory as a very long row of numbered mailboxes. Each mailbox holds one small piece of information: a number, a letter, a piece of text. A value is the piece of information inside a mailbox: the number 42, the text "hello", the answer yes. A variable is a label you stick on a mailbox so you can find it again later without remembering its number. When you write a line that puts 42 into a mailbox labeled count, you have created a value (42), stored it in memory, and hung a name on it (count). Later you can open the mailbox and read the value back.

Control flow is the order in which the machine opens mailboxes and follows instructions. Usually it goes straight down the list, top to bottom. But instructions can also decide: if the value in this mailbox is bigger than ten, do this; otherwise, do that. And instructions can repeat: keep doing this step until the mailbox says we are done. Those two ideas, deciding and repeating, are how a flat list of steps becomes a program that can solve real problems, and they get their own sections below.

That is the whole model: values in memory, names on values, and control flowing through instructions in order, sometimes branching, sometimes looping. Everything else is detail.

What Coral Is, and Why This Book Teaches It

Coral is a programming language. You write Coral, a compiler translates it, and the machine runs the result. There are hundreds of programming languages, so it is fair to ask why we are learning this one.

Coral is small. It has a short list of built-in ideas, and almost everything else is built out of those ideas rather than bolted on the side. Small means you can hold most of the language in your head at once, which is a rare and precious thing when you are starting out. You will not spend your first months memorizing special cases.

Coral is explicit. It does not do things behind your back. When a value changes type, you write the change down. When memory is used, the program shows where. This is good news for a beginner, because when something goes wrong, the reason is usually written right there on the line in front of you, not buried in a hidden mechanism you have never heard of.

Coral is C-shaped. Its style follows the C family of languages, which have been the workhorses of computing for fifty years. That means the habits you build here are not a private dialect. They transfer to a huge amount of existing software and to many other languages you may meet later. Learn to read Coral and you have learned to read a whole family.

And Coral has no magic. There is no layer of hidden machinery that secretly rearranges your instructions. The program you read is the program that runs. For someone trying to build an accurate mental model of what a computer actually does, that honesty is worth more than any convenience.

This book teaches Coral because it is a good first language and a good hundredth language: small enough to learn, honest enough to trust, and real enough to build serious software with. If you stick with it, you will not have learned a toy. You will have learned a tool.

How to Read This Book

A few words on getting the most out of the pages ahead.

The chapters build. Chapter 0 (this one) is the friendliest. Chapter 1 explains why Coral is the way it is, and Chapter 2 lays out the raw material of the language. After that, each chapter takes one area and goes deep: control flow, functions, collections, and so on, all the way to concurrency and the standard library. Later chapters assume earlier ones. If a topic feels hard, the fix is almost always to go back one chapter, not forward two.

The code claims something. Every time this book shows a program, it is making a claim: this is valid Coral, and here is what it does. Treat the examples as things to understand, not just to look at. Type them in. Reading code is not the same as writing it, and the gap between "I follow this" and "I can produce this" is where all the learning happens.

There are exercises. At the end of most chapters, including this one, are a handful of small problems. Do them. You will not learn to program by reading a book any more than you will learn to swim by reading about water. The exercises are where the knowledge becomes yours.

When you get stuck, do not stare at the screen for an hour. Read the compiler's message carefully (the next-to-last section of this chapter is about exactly this). Go back to the nearest example in the book and compare it to what you wrote, character by character. If it still will not budge, take a break and come back; the brain solves a surprising number of problems while you are doing something else. Asking for help is not cheating. Every programmer who has ever lived has done it, and will do it again tomorrow.

You will not understand everything on the first pass, and you are not supposed to. Programs reward re-reading. The same paragraph that seems opaque today will look obvious in a month, not because it changed, but because you did.

Your First Program

Time to see some actual Coral. Here is the smallest complete program. Type it into a file named hello.crl:

pub void main()
{
    println("Hello, world.");
}

That is a whole program. When you compile and run it, the machine will print the words:

Hello, world.

Now let us go through it one piece at a time, because every character is there for a reason, and nothing in it is a spell you have to chant.

pub

This word means "public." It says this function is visible from outside this file. For a program's starting point we mark it public, though for a first program the word is a formality. Think of it as a doormat by the entrance.

void

This is the type of the answer this function hands back when it finishes — and void is the type that means "nothing." It says main hands nothing back: the program does its work and stops. When a program returns nothing, the operating system still reads its exit status as zero, "everything went fine." If you come from C or C++, writing main this way may look strange, since there main returns an int and you end it with return 0. Coral lets you say void and skip that return, and that is the convention this book mostly uses; but returning an exit code is still allowed, and then i32 main with return 0 is perfectly fine. The type is written first, before the name, and that order is one of Coral's most consistent habits.

main

This is the name of the function. The name main is special: it is where the program begins. When you run the program, the machine looks for main and starts there. You could name other functions almost anything, but this one is the entrance, so it keeps the traditional name.

()

The parentheses hold the function's inputs. They are empty here, which means main takes no inputs. Later you will see parentheses filled with pieces of information the function needs, each with a type and a name.

{

This opens the function's body: everything between this brace and the matching one is the set of steps main carries out. Braces group instructions together, the way a paragraph groups sentences. Equality of indentation is not what groups them; the braces do that. We indent by four spaces purely so human eyes can see the structure, and the machine ignores the indentation entirely.

    println("Hello, world.");

This is the first real instruction inside the body. Read it as a sentence: println is the name of a ready-made action that comes with Coral. Its job is to print whatever you give it, followed by a new line. The parentheses hold the thing to print. The text "Hello, world." is called a string: a piece of text wrapped in double quotes. Put together, the line says "print this text and move to a new line." The semicolon at the end marks the end of the instruction, the way a period ends a sentence. Most lines in Coral end with a semicolon, and forgetting one is one of the most common mistakes a beginner makes, including every expert on their first day.

Why is println just there, without any setup? Coral automatically provides a small set of everyday tools to every program, including println and its sibling print (which does not add the newline). You do not have to ask for them. Other tools live in the standard library, Coral's large collection of ready-made code, and to use those you write an import line at the top of your file saying which ones you want. You will meet imports soon, but your first program does not need one.

}

This closes the body that the opening brace started. The function ends here, and so does the program.

Notice what is not in the program: no incantations, no setup, no configuration file. You wrote a handful of short lines, and each one did a visible, explainable thing. That is the shape of Coral, and it does not change as programs grow. They just get more of these lines.

One more small program, so you can see a value being printed rather than fixed text:

pub void main()
{
    i32 answer = 40 + 2;
    println("The answer is {}.", answer);
}

The new line creates a variable named answer and stores the result of adding 40 and 2 in it. The next line prints, and the pair of curly braces {} inside the text is a placeholder: at the moment of printing, Coral fills it in with the value of answer, here 42. The output is:

The answer is 42.

A placeholder in a print string is like a blank in a form letter. The letter is typed once; the blank is filled with a different name each time it is sent. You will use this constantly.

Variables, Types, and Values: A First Look

We met the word variable a moment ago. A variable is a name for a value stored in memory. You create one by writing what kind of value it holds, then the name, then an equals sign, then the value:

i32 score = 0;
f64 temperature = 98.6;
bool is_ready = true;
str greeting = "hello";

Read the first line left to right: "an i32 named score, holding 0." The second: "an f64 named temperature, holding 98.6." An f64 is a floating-point number: a number that can have a fractional part, like 98.6 or 3.14159. A bool is a yes-or-no value, and its only two possible values are true and false. A str is a piece of text, like "hello". (The name str is short for "string," which is what programmers call text.)

After you create a variable, you can change it by assigning a new value:

score = 10;
score = score + 5;

The first line puts 10 into score. The second looks at score (which is 10), adds 5, and puts the result back, so score becomes 15. The right side is worked out first, and the answer is stored on the left. This is not a mathematical equation; it is an instruction, and it is read right to left.

The kind of a value, such as i32 or f64 or str, is called its type. The type matters because the machine must know how much room to set aside and how to interpret the bits. It also matters because Coral will not let you mix types carelessly. If you try to store 98.6 in an i32, the compiler will stop you, because an integer mailbox cannot hold a fraction. That strictness feels fussy for about a week and then feels like a friend, because it catches real mistakes at the moment you make them rather than halfway through running.

Sometimes the type is so obvious from the value that writing it twice would be noise, and Coral lets you say var instead, leaving the type for the compiler to work out:

var count = 100;
var pi = 3.14159;

Here count is an integer and pi is a floating-point number, decided by the values on the right. You will see both styles in this book: explicit types when the type is the interesting fact, and var when it is not.

This section is deliberately shallow. There is a great deal more to say about types and values, including how big each one is and how they behave in arithmetic, and it is all waiting for you in Chapter 2. Do not try to absorb every detail now. The goal today is simply to recognize a variable when you see one and to know that every value has a type.

Making a Decision

Programs become useful when they can choose. The simplest way to choose is the if statement: check something, and if it is true, run a block.

if (age >= 18)
{
    println("You may vote.");
}

The condition, age >= 18, is a question with a yes-or-no answer: is age greater than or equal to 18? If the answer is true, the block runs. If not, nothing happens and the program moves on. Notice the condition is wrapped in parentheses, and the actions to run are wrapped in braces, just like a function body.

Usually you want an alternative when the answer is no, and that is what else is for:

if (age >= 18)
{
    println("You may vote.");
}
else
{
    println("Not yet.");
}

Now exactly one of the two blocks runs, never both, never neither.

You can chain several checks in a row. Each is tried only if the ones before it came up false:

char grade = 'F';
if (score >= 90)
{
    grade = 'A';
}
else if (score >= 80)
{
    grade = 'B';
}
else if (score >= 70)
{
    grade = 'C';
}
else if (score >= 60)
{
    grade = 'D';
}
else
{
    grade = 'F';
}

Read it top to bottom: is the score at least 90? If so, grade is A and we stop. Otherwise, is it at least 80? And so on, with the final else catching everything left over. This ordered chain of questions is one of the most common shapes in all of programming.

There is one rule about conditions that surprises people coming from other languages: the condition must be a genuine yes-or-no bool. You cannot use a number as a condition. In Coral, the number 1 is not the same as true, and 0 is not the same as false. If you want to test a number, you write a comparison, which produces a bool. This rule is a gift, because it makes "the comparison I forgot to write" impossible: the compiler simply will not accept a number where a yes-or-no answer belongs.

A decision can also produce a value directly rather than run a block. You may write:

i32 magnitude = if (x < 0) -x else x;

This says: if x is negative, the result is -x (its positive twin); otherwise the result is x. Either way, the chosen value is stored in magnitude. It is the same decision as an if statement, written compactly when all you need is a value back. Control flow gets a full, careful treatment in Chapter 4; this is just enough to read the idea.

Repeating Work

The other thing programs love to do is repeat. The simplest repetition is the while loop: keep running a block for as long as a condition stays true.

i32 sum = 0;
i32 i = 1;
while (i <= 5)
{
    sum = sum + i;
    i = i + 1;
}
println("The sum is {}.", sum);

Follow it once through. sum starts at 0 and i starts at 1. The condition asks whether i is at most 5. It is, so the body runs: add i to sum, then increase i by one. Now i is 2, and the condition is checked again. This continues while i is 1, 2, 3, 4, and 5. When the body runs with i equal to 5, it adds 5 and bumps i to 6. Now the condition is false, so the loop stops, and the program prints 15 (the sum of 1 through 5).

The pattern to notice is the counter: a variable set up before the loop, changed inside the loop, and tested in the condition. If i were never changed, the loop would run forever, and the program would never finish. Every loop needs something that moves toward stopping, and the counter is the usual something.

For walking through a collection of values, Coral offers a neater form, the ranged for loop. Here is the same idea over a list of numbers:

var numbers = Vec<i32>::withCap(4);
numbers.push(3);
numbers.push(5);
numbers.push(8);

i32 total = 0;
for (var n : numbers)
{
    total = total + n;
}
println("The total is {}.", total);

Ignore the mechanics of building the list for now (a Vec is a growable list of values, and Chapter 16 is where it gets its due). The part to read is the loop:

for (var n : numbers)

Read it aloud as "for each n in numbers." On each trip around the loop, n takes the next value from the list, and the body runs. You do not manage a counter, do not check bounds, do not bump anything by hand; the loop visits each element and stops on its own. This is the form you will reach for most often when you have a collection to process. Chapter 4 covers both kinds of loop, and more, in depth.

Functions: Named, Reusable Steps

Here is a small truth that turns out to be enormous: most programs are the same handful of steps reused in different places. Rather than write those steps out again each time, you give them a name and call the name. A named, reusable step is a function.

You have already been using one: main is a function, and println is a function. Here is one you write yourself:

i32 add(i32 a, i32 b)
{
    return a + b;
}

Read the first line as a sentence: "produces an i32, named add, and it needs two i32 inputs called a and b." The inputs are listed in parentheses, each with its type first, just like variables. The body adds the two inputs and returns the result. The word return hands the answer back to whoever called the function and ends the function right there.

Now you can use it anywhere you need it:

i32 total = add(2, 3);
i32 other = add(total, 10);

The first call passes 2 and 3 in as a and b; the function adds them and hands back 5, which is stored in total. The second call passes total (now 5) and 10, and gets back 15. You wrote the adding once, gave it a name, and can now do it anywhere, as many times as you like, without repeating the instructions.

This is the single most powerful idea in programming, and it has a lovely everyday face: a recipe can call another recipe. "Make the sauce" might be a step in three different dinners. You write it once, name it, and refer to it by name. Functions let you build big programs out of small ones, each small piece named and understandable on its own. It is also how we tame complexity: when a task is too big to hold in your head, you break it into named steps, then break each of those down further, until every piece is small enough to see at a glance.

Chapter 5 is devoted to functions and everything you can do with them. For now, the shape to remember is: type first, then name, then inputs in parentheses, then a body in braces, and return to hand back an answer.

A Short Glossary

The rest of this book assumes you know the following words. Keep this list nearby; you will meet every one of them again and again.

value
A single piece of information: the number 42, the text "hi", the answer true. Values are what programs compute with.
variable
A name for a value stored in memory. You create one by giving it a type, a name, and a value. You can change what it holds by assigning a new value.
type
The kind of a value, such as i32 (an integer), f64 (a number with a fractional part), bool (yes or no), or str (text). The type says how much room the value needs and what you may do with it. Coral's types are written before names.
function
A named, reusable set of instructions. It may take inputs (in parentheses) and may hand back a result (its return type). Calling its name runs it. main is the function where a program starts.
statement
A single instruction, usually ending with a semicolon. "Add these two numbers and store the result" is a statement.
expression
A piece of code that produces a value, such as 40 + 2 or age >= 18. Expressions are the raw material statements are made of, and they can appear inside other expressions.
compile
To translate a program you wrote into the language the machine runs, checking it for mistakes along the way. The tool that does this is the compiler.
run
To have the machine carry out a compiled program, following its instructions in order.
bug
A mistake in a program: a wrong instruction, a missing one, or an instruction that does not mean what you thought. Bugs are normal. Every program has some, and finding them is a large part of the work.
memory
The machine's storage, a long row of numbered places holding values. Variables name particular places so you can find them again. The book refines this picture as it goes, but it is a true place to start.

How Not to Panic

Sooner or later, and usually sooner, the compiler will refuse your program and show you a message you do not understand. This is not a sign that you are bad at this. It is what programming feels like from the inside, for everyone, at every level of experience. The professionals you admire spend much of their day reading error messages. Getting comfortable with them is not a detour from learning to program; it is a core part of learning to program.

Here is what to do when the compiler complains.

Read the message. All of it, slowly. It sounds obvious, but the urge to skim and guess is powerful. Compiler messages are written to help you. They usually name the problem and tell you where it is, often with a line number and a pointer at the exact spot.

Start at the first error. Compilers sometimes report one problem in several ways, or cascade: one real mistake triggers a dozen complaints that all vanish when the first is fixed. Fix the earliest one, compile again, and see what is left before chasing the rest.

Compare with a working example. The book is full of small programs that are known good. Find the closest one and lay your code next to it, character by character. Most beginner errors are small: a missing semicolon, a brace that was never closed, a name spelled two different ways, a type written where it did not belong, a condition that is not true-or-false. The eye skips these because it sees what it expects; comparing two texts side by side breaks that spell.

Change one thing at a time. When you are lost, resist the temptation to rewrite everything at once. Change one thing, compile, and see what happened. If you change five things and it still fails, you have learned less than if you had changed one and watched.

Trust that it makes sense. A message you do not understand today is a message you will read fluently in a few weeks. The vocabulary is small and repeats, and you are building it with every error. A program that will not compile is not a wall; it is a conversation, and the compiler is patient.

One last thing: keep your working programs. When something finally compiles and runs, save it. It becomes a reference you can return to, and the fastest way to fix a broken program is often to compare it with the last one that worked.

Exercises

These are small on purpose. Do them, typing each one yourself rather than copying and pasting, so your hands learn the shapes.

  1. Hello, by name. Write a program that prints "Hello, I am learning Coral." Then change the text to greet a different name, compile, and run it again.
  2. Print a number. Make a variable holding your age, and print a sentence that includes it using a {} placeholder. Then change the age and run it again to confirm the output follows.
  3. Add two numbers. Write a program with two integer variables and print their sum. Then change one value and predict the new output before you run it.
  4. Decide something. Write a program that sets a variable to a number and prints "positive" if it is greater than zero, "zero" if it is exactly zero, and "negative" otherwise. Test it with all three kinds of value.
  5. Count to ten. Use a while loop to print the numbers from 1 to 10, one per line. Then modify it to print only the even numbers.
  6. Sum a range. Use a while loop to compute the sum of the numbers from 1 to 100 and print the result. If your answer is 5050, you have it right.
  7. Write a function. Write a function named double that takes one integer and returns twice that value. Call it from main on a few different numbers and print the results.
  8. Combine ideas. Write a function named max that takes two integers and returns the larger one, using an if/else to decide. Call it with several pairs of numbers, including a pair where both are equal, and print each result. (Decide for yourself what max should return when the two are equal, and make the code say so.)

If you can do all eight of these, you are ready for Chapter 1. You have written real programs, made real decisions, repeated real work, and built a real function. Everything from here is more of the same ideas, deeper and in more places, which is the best possible news: you already know the shape of what is coming.
