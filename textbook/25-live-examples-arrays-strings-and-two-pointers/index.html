Chapter 25

Live Examples: Arrays, Strings, and Two Pointers

Two Fingers on the Same List

Chapter 24 was about single-pass bookkeeping. This chapter is about a pattern that cracks a surprising number of array and string problems with one idea: keep two positions in the data and move them by a rule. The pattern is called two pointers. It is less a technique than a way of seeing. Most problems a beginner solves with a double loop do not need one. The double loop is redundant: one of the two loops rediscovers information the other already has. Replace the nested loop with two coordinated pointers and the redundancy disappears. The brute force costs n²; the two-pointer version costs n.

Hold on. Let me make that concrete, because "two pointers" sounds like jargon until it clicks. Imagine looking for your friend in a single-file queue. The naive method: stand at the front and, for each person, walk the whole queue behind them comparing faces. That is the nested loop. The two-pointer method: put one finger at the front and one at the back, and move a finger based on what you see. You never revisit a position you already left behind, so the total number of steps is the length of the queue. The art is choosing which finger moves. That rule is always justified by a property of the data: sortedness, or a target, or symmetry. In each problem below I point at the property that licenses the move, because that is the part that transfers.

The other theme is the difference between a str and a String, and between a value you may overwrite and one you may only read. Reversing a string in place needs a mutable buffer, which in Coral means a String; a str is a borrowed, read-only view by design (Chapter 17). Several problems below also use a "write pointer" and a "read pointer" inside one array, a cousin of the two-pointer idea where one index writes the values that survive and the other scans. Once you see it, you see it everywhere. Filtering, deduplicating, and compacting are all the same three lines.

Reverse a String In Place

The problem

Given a mutable string, reverse its characters without allocating a second string.

Picture this

Two people standing at opposite ends of a row of boxes, each holding one item, walk toward the center swapping as they meet. When they pass each other, every box has changed places exactly once. Nobody copies the whole row; only one swap is in flight at a time.

Brute force

Build a new string by walking the original backwards and appending each character. Correct and linear, but it needs a second buffer the size of the first. The problem says "in place" precisely to forbid that.

The better approach

Two pointers, one at the left end and one at the right, swap the two characters they point at, then step inward. Stop when the pointers meet or cross. Every position is touched once, and the only extra storage is the one character being swapped.

The implementation

import(lib) std::text::string { String };
import(lib) std::io::ios { println };

void reverseString(String* s) {
    isize i = 0;
    isize j = (isize)s->len - 1;
    while (i < j) {
        u8 t = s->at((usize)i);
        s->atApply((usize)i, s->at((usize)j));
        s->atApply((usize)j, t);
        i++;
        j--;
    }
}

void main() {
    String text = String::from("hello");
    reverseString(&text);
    println("{}", text.asView());
}

Two details matter here: the types and the mutability. The loop counters are isize, signed, because j-- must reach zero and stop. An unsigned counter would wrap to a huge value on the final decrement and crash. The operations go through String, whose at and atApply give read and overwrite access. A str would not compile here, and that is no inconvenience. It is the type system telling you that reversing needs ownership of the bytes, not a view of them.

The cost

Time is linear: the loop runs about half the length, and each iteration does constant work (two reads, two writes). Space is constant, no matter how long the string. Compare the build-a-new-string approach: also linear in time, but linear in extra space. This is the first problem where two pointers buy a space improvement, not a time one. Both kinds of win are real.

Edge cases and a variation

The empty string and the single-character string exit the loop immediately, which is correct. A string of even length ends with j < i. A string of odd length ends with i == j on the middle character, which has nothing to swap with, so the loop stops. The variation: reverse the words in a sentence rather than the characters. "the sky is blue" becomes "blue is sky the". The classic trick is elegant. First reverse the whole string, then reverse each word back. Two applications of the primitive above, and the word problem is solved without a second buffer.

Valid Palindrome

The problem

Given a string, decide whether it reads the same forwards and backwards, considering only letters and digits and ignoring case. So "A man, a plan, a canal: Panama" is a palindrome.

Picture this

Two readers, one at each end of a sentence. Both ignore punctuation. Neither cares about uppercase. Each reads a character; if the two characters differ, the answer is no. If they meet in the middle having agreed on everything, the answer is yes. The punctuation between them is simply skipped.

Brute force

First strip the string of everything that is not a letter or digit and lowercase the rest, producing a cleaned copy. Then compare that copy to its own reverse. Two passes and an allocation. It works, and the cleaning step is error-prone (did you remember all the punctuation?). Reversing the cleaned copy also doubles the space for no reason.

The better approach

Two pointers, one from each end, advancing past anything that is not alphanumeric and comparing the survivors with case folded. No copy is made. The punctuation is skipped as the pointers travel. This is 24.1's skeleton with two changes: skip non-alphanumeric characters before comparing, and compare lowercase forms instead of swapping.

The implementation

import(lib) std::text::ascii { isAsciiAlnum, toAsciiLower };
import(lib) std::io::ios { println };

bool isPalindrome(str s) {
    isize i = 0;
    isize j = (isize)s.len - 1;
    while (i < j) {
        while (i < j && !isAsciiAlnum(s.at((usize)i))) i++;
        while (i < j && !isAsciiAlnum(s.at((usize)j))) j--;
        if (toAsciiLower(s.at((usize)i)) != toAsciiLower(s.at((usize)j))) {
            return false;
        }
        i++;
        j--;
    }
    return true;
}

The inner while loops are the new idea, and they are worth reading slowly. Each advances a pointer past characters that should not be compared. The condition i < j appears inside them too, so a string that is all punctuation, with no alphanumeric character at all, cannot run the pointers past each other and off the end. This guard-inside-the-guard is the detail most first attempts get wrong, and it only fails on inputs like "..." or " ".

The cost

Time is linear: each pointer moves inward and never retreats, so total movement is bounded by the length of the string, even though there are nested loops. Space is constant: two indices, no allocation. This is a recurring surprise with two pointers. Loops nested in the source do not necessarily mean a nested cost, if the inner loop draws from a shared budget.

Edge cases and a variation

The empty string and a single character are palindromes; the loop handles both. "0P" is not a palindrome, because 0 and P are different after folding (neither is punctuation to skip). The Unicode caveat belongs here in bold. This code compares bytes, so it is correct for ASCII and wrong for text with accented letters or emoji, whose UTF-8 encodings are multiple bytes. Chapter 17 explains the fix, decode with nextCodepoint and compare codepoints. It matters because a byte-by-byte comparison splits a multi-byte character and compares its halves, which is meaningless. The variation: allow the deletion of at most one character to make the string a palindrome, a classic follow-up solved by trying both skips when the two pointers disagree.

Two Sum in a Sorted Array

The problem

Given an array sorted in ascending order and a target value, find the two positions whose values add up to the target. Assume exactly one such pair exists.

Picture this

Two people stand at the ends of a number line, each holding a number, and they want their two numbers to sum to a target. If the sum is too small, the only way to raise it is to move the left person rightward, to a bigger number. If the sum is too big, move the right person leftward, to a smaller one. Because the line is sorted, each move is the unique sensible one, and the pair converges on the answer.

Brute force

Try every pair: for each i, scan every j after it and check the sum. About n² / 2 additions. It ignores the one piece of information the problem gave you, that the array is sorted, and that is the tell that the intended solution uses ordering.

The better approach

Two pointers, left and right. Compute the sum of the two values. If it equals the target, return the positions. If it is too small, no pair involving the smallest value and any value at or below the right pointer can reach the target except by advancing the left pointer, so advance i. If it is too big, advance j leftward. Each step eliminates one candidate entirely, so the pointers cross after at most n steps.

The implementation

import(lib) std::vec { Vec };
import(lib) std::io::ios { println };

Vec<i32> twoSumSorted(const Vec<i32>* v, i32 target) {
    Vec<i32> out = Vec<i32>::new();
    isize i = 0;
    isize j = (isize)v->count() - 1;
    while (i < j) {
        i64 sum = (i64)v->at((usize)i) + (i64)v->at((usize)j);
        if (sum == (i64)target) {
            out.push((i32)i);
            out.push((i32)j);
            return out;
        }
        if (sum < (i64)target) {
            i++;
        } else {
            j--;
        }
    }
    return out;
}

The comparison widens the sum to i64 before checking it. If both values are large i32s, their sum can overflow a 32-bit integer and wrap to a small number. Then the "too small" branch fires when the true sum was "too big." Widening the arithmetic is the smallest, cheapest guard against a whole class of silent bug.

The cost

Time is linear: each iteration moves one pointer one step inward, so at most n iterations. Space is constant. The brute force was quadratic. The improvement comes entirely from using the sortedness to decide which pointer must move, so each comparison rules out an entire row or column of the hypothetical table of pairs.

Edge cases and a variation

Fewer than two elements cannot contain a pair; the loop returns an empty vector, which the caller can read as "none found." The problem guarantees a pair exists, but a robust version should not assume it. Equal values are fine: [3, 3] with target 6 returns positions 0 and 1, since i < j. The variation that connects this chapter to the next: the same problem on an unsorted array cannot use two pointers, because no ordering justifies a move. Instead you keep a hash map from value to the position where you saw it and, for each number, ask whether its complement is already in the map. That is Chapter 26's opening problem. The contrast is the lesson: sorted permits two pointers, unsorted demands hashing.

Remove Duplicates from a Sorted Array

The problem

Given a sorted array, remove the duplicates in place so each value appears once, and return the new length. The elements beyond the new length do not matter.

Picture this

You are packing a shelf from left to right, and the items arrive already sorted, so copies of any item sit adjacent. Keep a "write hand" pointing at the next empty slot and a "read eye" scanning every item. Whenever the read eye finds an item different from the last one you kept, place it under the write hand and advance the hand. The read eye passes over the duplicates and never places them.

The better approach

Two indices, one reading, one writing, both starting after the first element. The read index visits every element. The write index advances only when the current element differs from the last one written. Because the array is sorted, the last written value is exactly what to compare against: no set, no memory, just one comparison. At the end, the write index is the count of distinct values, and everything from it onward can be discarded.

The implementation

import(lib) std::vec { Vec };
import(lib) std::io::ios { println };

usize removeDuplicates(Vec<i32>* v) {
    if (v->count() == 0) return 0;
    usize k = 1;
    for (usize i = 1; i < v->count(); i++) {
        if (v->at(i) != v->at(k - 1)) {
            v->set(k, v->at(i));
            k++;
        }
    }
    while (v->count() > k) {
        v->pop();
    }
    return k;
}

Vegetarians, note the comparison: compare the current read value against v->at(k - 1), the last value we kept, not against the previous read position v->at(i - 1). They are usually the same, but not always. After a write, the two positions diverge, and comparing against the last kept value is the correct invariant. The final pop loop trims the vector down to the distinct count. A Vec has no truncate method, so shrinking to a length is an explicit sequence of pops; the loop does the job in constant time per removed element.

The cost

Time is linear: one pass, one comparison and occasionally one write per element. Space is constant, two indices and no allocation, which is the entire point of an in-place problem. The pop loop is also linear in the number of duplicates removed, so the total stays linear.

Edge cases and a variation

An empty array returns zero; a single-element array returns one. All-equal input leaves one element and returns one. The variation: allow each value to appear at most twice, keeping the second occurrence but not the third. The write-pointer pattern is unchanged. Only the count compared against changes, from "differs from the last kept" to "differs from the value two positions back in the kept prefix." Problems like this are all the same skeleton with a different predicate. Recognizing the skeleton is worth more than memorizing the solution.

Move Zeroes

The problem

Given an array, move every zero to the end while keeping the relative order of the nonzero elements, in place.

Picture this

A conveyor belt carries items past a worker whose job is to slide all the empty boxes to the far end without disturbing the order of the full ones. The worker keeps a hand on the next open slot on the left; each time a full box comes by, it goes under that hand and the hand moves on. When the belt ends, every slot to the right of the hand is filled with empty boxes.

Brute force

Collect the nonzero elements into a second list in order, then write them back into the original followed by the right number of zeroes. Linear, but it allocates a second array the size of the first.

The better approach

The write-pointer pattern again, with the predicate "is nonzero." Walk the array with a read index. Whenever the value is nonzero, write it at the write index and advance the write index. When the scan ends, the first k positions hold all the nonzero values in their original order, and every position from k onward gets a zero. One pass to move the values, one pass to fill the tail.

The implementation

import(lib) std::vec { Vec };
import(lib) std::io::ios { println };

void moveZeroes(Vec<i32>* v) {
    usize k = 0;
    for (usize i = 0; i < v->count(); i++) {
        if (v->at(i) != 0) {
            v->set(k, v->at(i));
            k++;
        }
    }
    for (usize i = k; i < v->count(); i++) {
        v->set(i, 0);
    }
}

This version has a subtle property for free, and a common interview follow-up asks about it explicitly: the relative order of the nonzero elements is preserved, because the read pointer visits them in order and the write pointer accepts them in the same order. If order did not matter, a faster swap-based version touches each element once, but that is not required here.

The cost

Time is linear: one full scan plus a second scan of the tail, so at most twice the length in the worst case. Still linear. Space is constant. The second pass is the honest price of overwrite-and-fill rather than swap: you visit the tail once to zero it. The swap-based alternative avoids that second pass when order is not required, but it needs a branch the order-preserving version does not.

Edge cases and a variation

An array with no zeroes does one pass and then sets an empty tail, which is correct. An array that is all zeroes keeps k at zero and zeroes the whole array, also correct. The variation: move all instances of a given value to the end, or move the even numbers to the front. Same skeleton, different predicate; the only line that changes is the if. A harder variant, "sort the array by parity while preserving the relative order within each group," needs a two-pass version, because the write pointer must first count the odds to know where one group ends and the other begins.

Merge Two Sorted Arrays

The problem

Given two sorted arrays, merge them into the first, which has enough empty space at its end to hold both. Do not allocate.

Picture this

Two stacks of numbered cards, each already in order, and an empty table to the right. Fill from the left and you overwrite cards you have not read yet. But the empty space is at the right, so work backwards. Look at the largest remaining card in each stack and place the larger one in the rightmost empty slot. The biggest card of all must end up at the far right, so placing it there is safe, and everything else shifts into place behind it.

Brute force

Copy both arrays into a fresh buffer and sort it. That is O((m+n) log(m+n)), it allocates, and it squanders the fact that both inputs are already sorted.

The better approach

Three pointers, all walking backwards. Index i sits at the last real element of the first array, j at the last element of the second, and k at the last slot of the combined region. At each step, take the larger of a[i] and b[j], write it at k, and step that source pointer back. When the second array is exhausted, the first array's remaining elements are already in place. That is a small optimization: it avoids a redundant copy of the first array's front.

The implementation

import(lib) std::vec { Vec };
import(lib) std::io::ios { println };

void merge(Vec<i32>* a, i32 m, const Vec<i32>* b, i32 n) {
    isize i = (isize)m - 1;
    isize j = (isize)n - 1;
    isize k = (isize)(m + n) - 1;
    while (j >= 0) {
        if (i >= 0 && a->at((usize)i) > b->at((usize)j)) {
            a->set((usize)k, a->at((usize)i));
            i--;
        } else {
            a->set((usize)k, b->at((usize)j));
            j--;
        }
        k--;
    }
}

The loop condition is j >= 0, not i >= 0 && j >= 0, and that asymmetry is deliberate. Once the second array is exhausted, the leftovers of the first array already sit at the front of a in the correct order, so nothing is left to do. Loop until both run out instead, and you copy values onto themselves, which is harmless but pointless. The i >= 0 guard inside the condition protects the read of a[i] when the first array runs out before the second, a case that happens when the first array is empty.

The cost

Time is linear in the combined length: each iteration places exactly one element, and there are m + n elements. Space is constant. The backwards direction lets us avoid allocation, and it works because the destination is larger than the source and consumes the source from the same end it fills from.

Edge cases and a variation

Merging with an empty second array leaves the first untouched; merging with an empty first array copies the second into place. The variation that shows the pattern's breadth: merge k sorted arrays. Pairwise merging is O(k · N · log k) in the worst case, but a min-heap that always yields the smallest front element does it in O(N log k). That is what Chapter 16's PriorityQueue is for. It is the bridge from this chapter to the data-structure chapters.

Sort Colors (the Dutch National Flag)

The problem

Given an array containing only 0s, 1s, and 2s, sort it in place in a single pass.

Picture this

The name comes from the three bands of the Dutch flag. Imagine a row of buckets and three hands. A "left" hand owns everything that should be 0, a "right" hand owns everything that should be 2, and a "middle" eye has not yet decided about the element it is looking at. When the eye sees a 0, it throws it to the left region and grows it. When it sees a 2, it throws it to the right region. When it sees a 1, that element is already home, and the eye moves on. The regions grow toward each other until they meet, and the whole row is sorted.

Brute force

Count how many 0s, 1s, and 2s there are in one pass, then overwrite the array with that many of each. Two passes, linear, and honestly fine. It is not one pass as required, and it does not generalize to a large number of distinct values.

The better approach

Three pointers: low is the boundary after the region of 0s, high is the boundary before the region of 2s, and mid is the scanning eye moving between them. At each step, look at v[mid]:

  • if it is 0, swap it with the element at low, advance both low and mid;
  • if it is 1, it is in its final region, advance only mid;
  • if it is 2, swap it with the element at high, retreat high, and do not advance mid.

The last line is the one to understand. After swapping with high, the element now at mid is one we have never examined; it came from the unprocessed right end. So we must look at it again rather than step over it.

The implementation

import(lib) std::vec { Vec };
import(lib) std::io::ios { println };

void swapAt(Vec<i32>* v, usize a, usize b) {
    i32 t = v->at(a);
    v->set(a, v->at(b));
    v->set(b, t);
}

void sortColors(Vec<i32>* v) {
    isize low = 0;
    isize mid = 0;
    isize high = (isize)v->count() - 1;
    while (mid <= high) {
        i32 x = v->at((usize)mid);
        if (x == 0) {
            swapAt(v, (usize)low, (usize)mid);
            low++;
            mid++;
        } else if (x == 1) {
            mid++;
        } else {
            swapAt(v, (usize)mid, (usize)high);
            high--;
        }
    }
}

The mid <= high condition, with high inclusive, is the workhorse. The region between mid and high is exactly the part not yet processed; when mid passes high, nothing is left. Every iteration either shrinks that region or advances mid into territory whose status is already known. So the loop terminates in a single pass.

The cost

Time is linear, and not just asymptotically. This is a true single pass: each element is examined a constant number of times and swapped at most once. Space is constant, three indices. Counting sort takes two passes, so the improvement is a factor of two in array traversals. Small, but the single-pass property is what the problem asks for and what makes the pattern reusable.

Edge cases and a variation

An array with only one distinct value leaves all pointers in place and does nothing. All 0s advance low and mid together to the end. The subtle bug to avoid is advancing mid after a 2-swap; test it on [2, 0, 1] and you will see the unprocessed element arrive at mid. The variation: sort four or five distinct small values. The Dutch flag does not extend trivially to more colors; the number of boundary pointers grows awkwardly. For more than a handful of values, the honest answer is the counting approach of the brute force. Knowing where a technique stops scaling is as valuable as knowing the technique.

Container With Most Water

The problem

Given wall heights at positions along a line, choose two walls that together with the line form a container holding the most water. The container's area is the distance between the walls times the height of the shorter wall.

Picture this

You are looking at a skyline. Pick two buildings; the water they hold is limited by the shorter of the two, and the width is how far apart they are. Moving a building inward always reduces the width, so the only way to gain is to find a taller shorter-wall. The shorter wall is the one worth abandoning.

Brute force

Check every pair of walls, compute the area, keep the maximum. n² / 2 area computations, each constant work. Correct, and the baseline.

The better approach

Two pointers at the ends, the widest possible container. Compute its area. Now move the pointer at the shorter wall inward. Why that one? The current width is the maximum achievable for this pair, and the height is capped by the shorter wall. Keep the shorter wall and move the taller one inward, and the width only shrinks while the cap stays the same, so it cannot beat what we have. Moving the shorter wall inward is the only move that can find a taller cap. Repeat until the pointers meet.

The implementation

import(lib) std::vec { Vec };
import(lib) std::io::ios { println };

i64 maxArea(const Vec<i32>* h) {
    isize i = 0;
    isize j = (isize)h->count() - 1;
    i64 best = 0;
    while (i < j) {
        i64 width = (i64)(j - i);
        i64 hi = (i64)h->at((usize)i);
        i64 hj = (i64)h->at((usize)j);
        i64 shorter = hi < hj ? hi : hj;
        i64 area = width * shorter;
        if (area > best) best = area;
        if (hi < hj) {
            i++;
        } else {
            j--;
        }
    }
    return best;
}

All the arithmetic is i64, so even the largest possible area, a width near a billion times a height near a billion, cannot overflow. The move rule is the heart of the proof, worth restating: when we discard the shorter wall, we discard every container that could have used it, and none of them could have beaten the best already recorded. That is why the algorithm is allowed to be greedy.

The cost

Time is linear: each iteration moves one pointer inward, so exactly n - 1 iterations. Space is constant. The quadratic brute force collapses to linear because the move rule lets us throw away a whole family of candidate pairs without checking them.

Edge cases and a variation

Fewer than two walls yields an area of zero, which the loop returns naturally. Equal-height walls let us move either pointer; moving one is correct, because the other can be the shorter wall for the next candidate. The variation: return which two walls achieved the maximum, not just the area. Keep the indices whenever the best updates. A second variation: the "trapping rain water" problem just below looks similar, two walls and water, but asks for the total water trapped across all the gaps, not the best single container, and its two-pointer rule is subtly different.

Trapping Rain Water

The problem

Given an elevation map as an array of wall heights, compute how much rainwater is trapped in the valleys after a rainstorm.

Picture this

After a storm, water collects in every dip of a skyline, each basin filled to the level of the lower of its two bounding walls. Picture a cross-section of a mountain range. The water sits in the valleys up to the height of the shorter wall that encloses each valley. The amount above any one hill is the water level at that hill minus the hill's own height, and the water level at a point is the smaller of the tallest wall to its left and the tallest wall to its right.

Brute force

For each position, scan left to find the maximum height and scan right to find the maximum. The water above that position is the smaller of the two maxima minus the position's height, when positive. Three nested-ish scans give O(n²). It is the most direct translation of the definition and the easiest place to start.

The better approach

Two pointers with two running maxima, one from the left and one from the right. Here is the key insight: if the tallest wall seen so far on the left is shorter than the tallest seen so far on the right, then the water level at the left pointer is governed entirely by the left maximum. The right side is known to have a wall at least as tall, so it will never be the binding constraint. That means we can add leftMax - height[i] at the left pointer with confidence, and move it inward. Mirror the logic on the right. One pass, no per-position scanning.

The implementation

import(lib) std::vec { Vec };
import(lib) std::io::ios { println };

i64 trap(const Vec<i32>* h) {
    if (h->count() == 0) return 0;
    isize i = 0;
    isize j = (isize)h->count() - 1;
    i64 leftMax = 0;
    i64 rightMax = 0;
    i64 water = 0;
    while (i < j) {
        i64 hi = (i64)h->at((usize)i);
        i64 hj = (i64)h->at((usize)j);
        if (hi < hj) {
            if (hi >= leftMax) {
                leftMax = hi;
            } else {
                water += leftMax - hi;
            }
            i++;
        } else {
            if (hj >= rightMax) {
                rightMax = hj;
            } else {
                water += rightMax - hj;
            }
            j--;
        }
    }
    return water;
}

The condition hi < hj chooses which side to process, and the choice is exactly the insight above: the side with the smaller wall is the side whose water level is settled, because the other side already offers a taller wall. The if (hi >= leftMax) branch distinguishes a new high wall, which traps nothing above itself, from a valley position, which traps the difference.

The cost

Time is linear: the pointers move toward each other and each position is processed once. Space is constant: two maxima and an accumulator. The O(n²) brute force becomes O(n) by precomputing the running maxima on the fly instead of rescanning, the same "carry it forward" idea as the running sum of Chapter 24.

Edge cases and a variation

An empty array or a single position traps nothing. A monotonically increasing or decreasing skyline traps nothing, because there is no valley; the code handles this because every position either sets a new maximum or contributes a zero difference. The variation: the two-pointer rule here and the one in 24.8 look alike but answer different questions, and mixing them up is a common mistake. In 24.8 we move the shorter wall because we are optimizing one container. Here we move the side with the smaller maximum because we are accumulating water everywhere. Write both and compare the move rules side by side; the difference in the problem statement is exactly the difference in the rule.

Longest Common Prefix

The problem

Given a list of strings, find the longest prefix shared by every one of them. For ["flower", "flow", "flight"] the answer is "fl"; for ["dog", "racecar", "car"] it is the empty string.

Picture this

Lay the words out in a column, top to bottom, and read down the first character of each, then the second, then the third. As long as every word agrees on a column, that column belongs to the answer. The first column where any two words disagree ends the prefix. You never need to compare whole words; you compare one column at a time.

Brute force

Take every pair of words, find their shared prefix, and repeatedly shorten a running answer to the smallest one seen. It is O(n · L) in the worst case, but it rebuilds strings along the way and compares words that do not need comparing. It also duplicates work: two words that agree with the first word already agree with each other.

The better approach

Use the first word as the candidate prefix and shrink it. For each later word, compare it character by character against the candidate and cut the candidate down to the matching length. Once the candidate is empty, nothing more can be added and the scan can stop. This is the vertical scan, and it makes at most one pass over each word up to the current prefix length.

The implementation

import(lib) std::vec { Vec };
import(lib) std::io::ios { println };

str longestCommonPrefix(const Vec<str>* words) {
    if (words->count() == 0) return str::empty();
    str first = words->at(0);
    usize limit = first.len;
    for (usize i = 1; i < words->count(); i++) {
        str w = words->at(i);
        usize j = 0;
        while (j < limit && j < w.len && w.at(j) == first.at(j)) {
            j++;
        }
        limit = j;
        if (limit == 0) break;
    }
    return first.slice(0, limit);
}

limit is the only state, and it only ever shrinks, which is why the total work is bounded by the length of the shortest word times the number of words at the very worst, and usually far less. The returned str is a view into the first word's bytes, so no new memory is allocated at all; the caller's list must outlive the result, which the borrowed str type makes explicit.

The cost

Time is O(n · L) in the worst case, where L is the answer length: each word is scanned only up to the current prefix, and the prefix shrinks. Space is constant, one index and one length, because the answer is a view rather than a copy. A binary-search refinement halves the number of comparisons, but only pays off with truly enormous strings.

Edge cases and a variation

An empty list returns the empty string, and a single-word list returns that word in full. If any word is empty, the empty string is the shared prefix and the loop stops immediately. This compares bytes, so Unicode text with accented letters or emoji is compared as its UTF-8 encoding, which is correct for prefix purposes but treats a partial multibyte sequence as a character; Chapter 17's codepoint decoding is the fix. The variation: longest common suffix, by scanning each word from the back with a limit that counts from the end. The skeleton is identical; only the direction of the index and the meaning of limit change.

Rotate an Array by k

The problem

Rotate an array to the right by k places, in place. So [1, 2, 3, 4, 5, 6, 7] rotated right by 3 becomes [5, 6, 7, 1, 2, 3, 4].

Picture this

Cut a deck of cards and move the bottom k cards to the top. The obvious way is to repeatedly take the last card and move it to the front, k times, but that shuffles the whole deck k times over. The neat way is to flip the whole deck upside down, then flip each of the two piles back the right way up. Reversal plus reversal gives rotation, and it touches every card exactly twice.

Brute force

Rotate one position at a time, k times. Each rotation moves every element, so the cost is O(n · k), and for k near n that is quadratic. It is simple and it is in place, and it is the baseline.

The better approach

Three reversals. Reverse the whole array, reverse the first k elements, then reverse the remaining n - k. After the first reversal the two groups are in the wrong internal order but on the correct sides; the second and third reversals restore the order inside each group. Every element is moved a constant number of times, so the work is linear. Reduce k modulo n first so that k = n (or 0) is handled without special cases.

The implementation

import(lib) std::vec { Vec };
import(lib) std::io::ios { println };

void reverseRange(Vec<i32>* v, usize lo, usize hi) {
    while (lo < hi) {
        i32 t = v->at(lo);
        v->set(lo, v->at(hi));
        v->set(hi, t);
        lo++;
        hi--;
    }
}

void rotateRight(Vec<i32>* v, usize k) {
    usize n = v->count();
    if (n == 0) return;
    k = k % n;
    if (k == 0) return;
    reverseRange(v, 0, n - 1);
    reverseRange(v, 0, k - 1);
    reverseRange(v, k, n - 1);
}

The two guards at the top are not decoration. An empty array would make n - 1 wrap around when it is unsigned, and k % n would divide by zero; returning early avoids both. The k % n line also means a rotation by more than the length behaves correctly instead of reading out of bounds. reverseRange is the same two-pointer swap as 24.1, generalized to an arbitrary interval.

The cost

Time is linear: three passes, each moving each element at most once, so at most six writes per element. Space is constant, two indices and one temporary value. Compare the one-step-at-a-time version, which is also in place but k times slower.

Edge cases and a variation

An empty array and a k that is a multiple of n both do nothing. A single-element array is left alone even for large k. The variation: rotate to the left by k is the same routine applied to n - k, or equivalently the three reversals done with the two parts swapped. A second, genuinely different method is the "juggling" algorithm, which moves elements in cycles and does exactly n writes for the whole rotation rather than touching some elements twice. It is trickier to get right and worth reading once, if only to see the constant-factor trade.

String Compression (Run-Length Encoding)

The problem

Compress a string by replacing each run of repeated characters with the character followed by the run length, omitting the length when it is one. So "aabccc" becomes "a2bc3" and "abc" stays "abc".

Picture this

Walk the string and keep one finger at the start of the current run and another moving forward while the characters match. When the second finger finds a different character, the run is over: write the character, write the count if there was more than one, and move the start finger up to where the second one stopped. Every character is visited once by the moving finger and the runs are written in order.

Brute force

There is no meaningfully different slow version; a run-length compressor is naturally linear. The naive implementation instead rebuilds substrings and counts duplicates with an inner search for each position, which is quadratic and obscures the two-pointer skeleton that is the whole idea.

The better approach

One pass with a start index and a scan index. For each run, push the character into the output String and append the count when the run is longer than one. The only piece of machinery that is not obvious is turning a multi-digit count into its decimal characters, because Coral's formatting helpers are not the right tool for building a string one byte at a time.

The implementation

import(lib) std::vec { Vec };
import(lib) std::text::string { String };
import(lib) std::io::ios { println };

void pushUint(String* out, usize n) {
    if (n == 0) {
        out->pushChar(48);
        return;
    }
    Vec<u8> digits = Vec<u8>::new();
    while (n > 0) {
        digits.push((u8)(48 + (n % 10)));
        n = n / 10;
    }
    isize i = (isize)digits.count() - 1;
    while (i >= 0) {
        out->pushChar(digits.at((usize)i));
        i--;
    }
}

String compress(str s) {
    String out = String::new();
    usize i = 0;
    while (i < s.len) {
        u8 c = s.at(i);
        usize j = i;
        while (j < s.len && s.at(j) == c) {
            j++;
        }
        out.pushChar(c);
        usize run = j - i;
        if (run > 1) pushUint(&out, run);
        i = j;
    }
    return out;
}

pushUint peels the decimal digits into a vector in reverse, then emits them in order; it is the integer-reversal idea of 23.3, used here to write a number rather than read one. The byte constant 48 is '0', and adding a digit value to it produces the character. The compression loop itself is only six lines, which is the payoff for extracting the number-writing helper.

The cost

Time is linear in the input length: the scan index advances across each character once, and the digit work for the counts adds only a logarithm per run. Space is proportional to the length of the output, which for a highly repetitive string is far smaller than the input but in the worst case (no repeats) is the same size.

Edge cases and a variation

The empty string produces an empty string; the loop never runs. A string with no repeats returns a copy of itself with every count omitted. A run longer than nine exercises pushUint's multi-digit path, which a '0' + run shortcut would get wrong. The variation from the interview version: if the compressed result is not shorter than the original, return the original. Keep the original str and the built String, then compare their lengths before returning. A second variation: decode, or decompress, a run-length string, which is the same two-pointer walk in reverse and is a good check that you understand the format you invented.

Product of Array Except Self

The problem

Given an array, produce a second array where position i holds the product of every element except v[i]. Do it without using division, so zeros and negative numbers cause no trouble, and in linear time.

Picture this

The product of everything except position i is (the product of everything to its left) times (the product of everything to its right). So make two sweeps. On the way right, record at each position the product of everything before it. On the way back, multiply that by the product of everything after it, accumulated as you go. Neither sweep needs to know the whole array's product, so division never enters.

Brute force

For each position, loop over every other position and multiply. That is O(n²) and it recomputes the same partial products from every starting point.

The better approach

Two passes and one output array. The first pass fills out[i] with the running prefix product before i. The second pass walks backward maintaining a running suffix product and multiplies it into out[i]. The output array itself is the only extra storage, so beyond the answer the space is constant. Widen the accumulator to i64: a product of many i32 values overflows a 32-bit integer almost immediately.

The implementation

import(lib) std::vec { Vec };
import(lib) std::io::ios { println };

Vec<i64> productExceptSelf(const Vec<i32>* v) {
    usize n = v->count();
    Vec<i64> out = Vec<i64>::withCap(n);
    for (usize i = 0; i < n; i++) out.push(1);

    i64 prefix = 1;
    for (usize i = 0; i < n; i++) {
        out.set(i, prefix);
        prefix = prefix * (i64)v->at(i);
    }

    i64 suffix = 1;
    isize i = (isize)n - 1;
    while (i >= 0) {
        out.set((usize)i, out.at((usize)i) * suffix);
        suffix = suffix * (i64)v->at((usize)i);
        i--;
    }
    return out;
}

The forward pass stores the product of the elements strictly before i; the backward pass multiplies in the product strictly after i. They never overlap, which is why no division is needed and zeros are harmless: a zero simply makes every prefix after it zero and every suffix before it zero, and each answer ends up correct. The signed isize backward index is the same choice as 24.1, so the i-- can reach zero and stop without wrapping.

The cost

Time is linear: two passes, constant work per element. Space is linear only because the answer is the same length as the input; the working state is a single running product. This is the discipline that distinguishes "extra space" from "output space," and the problem is usually asked precisely to test that distinction.

Edge cases and a variation

An empty array returns an empty result. A single element returns a single one, since the product of nothing is one. A zero in the input is handled by the two-pass structure, unlike a divide-by-total approach which would break. The variation: allow division and solve it in one pass by taking the total product and dividing each element out, then handle zeros as a special case. It is shorter and it fails on the cases that matter, which is exactly the lesson of the problem.

3Sum

The problem

Given an array of integers, return every unique triple of values (not positions) that sums to zero. So from [-1, 0, 1, 2, -1, -4] the answer is [-1, -1, 2] and [-1, 0, 1].

Picture this

Sort the array first, so equal values sit together and we can skip repeats by hand. Fix the smallest value of the triple with an outer loop, then find the other two with the converging two-pointer walk of 24.3. Because the array is sorted, when the sum is too small we can move the left pointer right and know we have not missed a candidate, exactly as in the sorted two-sum.

Brute force

Three nested loops over all triples, checking each sum and then deduplicating the results. That is O(n³) and the deduplication is a fiddly second problem on top. It ignores the sortedness that a single sort would provide.

The better approach

Sort once, then fix the first element with an outer index i. For the remaining window (i, end], run the two-pointer two-sum against the target -v[i]. The sortedness licenses the pointer movement, and it also makes duplicate-skipping trivial: skip an i equal to the previous one, and after recording a triple, skip equal values on both ends of the window.

The implementation

import(lib) std::vec { Vec };
import(lib) std::collections::sort { sortI32 };
import(lib) std::io::ios { println };

Vec<Vec<i32>> threeSum(Vec<i32>* nums) {
    sortI32(nums);
    Vec<Vec<i32>> out = Vec<Vec<i32>>::new();
    usize n = nums->count();
    if (n < 3) return out;

    for (usize i = 0; i + 2 < n; i++) {
        if (i > 0 && nums->at(i) == nums->at(i - 1)) continue;
        isize lo = (isize)i + 1;
        isize hi = (isize)n - 1;
        while (lo < hi) {
            i64 sum = (i64)nums->at((usize)lo)
                    + (i64)nums->at((usize)hi)
                    + (i64)nums->at(i);
            if (sum == 0) {
                Vec<i32> triple = Vec<i32>::new();
                triple.push(nums->at(i));
                triple.push(nums->at((usize)lo));
                triple.push(nums->at((usize)hi));
                out.push(triple);
                lo++;
                hi--;
                while (lo < hi && nums->at((usize)lo) == nums->at((usize)lo - 1)) lo++;
                while (lo < hi && nums->at((usize)hi) == nums->at((usize)hi + 1)) hi--;
            } else if (sum < 0) {
                lo++;
            } else {
                hi--;
            }
        }
    }
    return out;
}

There are three places duplicates could sneak in, and each is guarded once. The outer skip handles repeated first elements; the two inner skips handle repeated second and third values after a hit. The sum is widened to i64 so three large i32s cannot overflow and flip the sign of the comparison. The returned triples come out in the order the sorted array produces, one per distinct value combination.

The cost

Sorting is O(n log n), and the outer loop with its inner two-pointer walk adds O(n²), so the total is O(n²), which beats the cubic brute force by a full factor of n. Space is constant beyond the sort and the output. The sorting cost is negligible next to the quadratic scan for any interesting input.

Edge cases and a variation

Fewer than three elements returns nothing. All-zero input yields exactly one triple [0, 0, 0], because the two inner skips collapse the repeats. The variation: k-sum generalizes this by fixing the first k - 2 elements with nested loops and running the two-pointer walk for the last two; for fixed k that is O(n^{k-1}), and the pattern of "sort, fix, then converge" is identical all the way down. The 3Sum closest variant replaces the equality test with a running best distance, and is often the easier interview version because it does not need the duplicate guards.

Find All Anagrams in a String

The problem

Given a string s and a shorter pattern p, return the starting indices of every substring of s that is an anagram of p. So for s = "cbaebabacd" and p = "abc", the answer is 0 and 6 ("cba" and "bac").

Picture this

An anagram is fully described by how many of each letter it contains, not by their order. So slide a window exactly as wide as p across s, and at each position ask whether the window's letter counts match p's. When the window moves one step, only two letters change: one enters on the right and one leaves on the left. Update two counts instead of recounting the whole window.

Brute force

At every start position, copy the next m characters, sort them, and compare to the sorted pattern. There are n - m + 1 windows, and each costs O(m log m), for O(n · m log m) overall. It re-sorts windows that differ from their neighbours by a single letter.

The better approach

A fixed-size sliding window with two frequency arrays, one for the pattern and one for the current window, each of 26 counters. Seed both from the first window, then compare. On each step, add the entering character to the window count and subtract the leaving one. Since the alphabet is tiny and fixed, comparing the two arrays is a constant 26 operations, and the total is linear in n.

The implementation

import(lib) std::vec { Vec };
import(lib) std::io::ios { println };

Vec<i32> findAnagrams(str s, str p) {
    Vec<i32> out = Vec<i32>::new();
    usize n = s.len;
    usize m = p.len;
    if (m == 0 || n < m) return out;

    Vec<i32> need = Vec<i32>::withCap(26);
    Vec<i32> win = Vec<i32>::withCap(26);
    for (usize i = 0; i < 26; i++) {
        need.push(0);
        win.push(0);
    }

    for (usize i = 0; i < m; i++) {
        usize k = (usize)((i32)p.at(i) - 97);
        need.set(k, need.at(k) + 1);
    }

    for (usize i = 0; i < n; i++) {
        usize enter = (usize)((i32)s.at(i) - 97);
        win.set(enter, win.at(enter) + 1);
        if (i >= m) {
            usize gone = (usize)((i32)s.at(i - m) - 97);
            win.set(gone, win.at(gone) - 1);
        }
        if (i >= m - 1) {
            bool same = true;
            for (usize c = 0; c < 26; c++) {
                if (win.at(c) != need.at(c)) {
                    same = false;
                    break;
                }
            }
            if (same) out.push((i32)(i - m + 1));
        }
    }
    return out;
}

The subtraction (i32)s.at(i) - 97 maps 'a' to index 0 and 'z' to 25; the constant 97 is 'a'. The two conditions delimit the window: remove the leaving character only once i >= m, and test only once the window is full at i >= m - 1. The comparison loop breaks on the first mismatch, which makes the common (non-matching) case cheap.

The cost

Time is O(26 · n), which is O(n) because the alphabet size is a constant. Space is constant: two arrays of 26 integers, regardless of how long s and p are. This is the fixed-alphabet cousin of 25.6's sliding window, where the map grows with the number of distinct characters instead.

Edge cases and a variation

An empty pattern is not a valid anagram and returns no indices; a pattern longer than s cannot fit and also returns none. This assumes lowercase a to z; an uppercase letter or a space would compute an out-of-range index and must be rejected first, or the counters must be widened to cover the full byte range. The variation: at most k distinct characters, or "find all anagrams of any permutation of a list of patterns," both loosen the fixed-size comparison into a count of how many letters are satisfied and how many distinct letters are present. Fixed size becomes sliding maximum, but the two-array diffing idea stays.
